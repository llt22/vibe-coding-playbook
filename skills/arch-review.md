# 项目架构 Review

你正在 review 一个项目的架构设计。**输入不是一份文档，是代码本身。** 你需要扫描项目结构，读关键文件，理解模块是怎么组织的，然后判断一个刚接手的开发者能不能快速上手。

## 第一步：建立全局地图

先扫描项目结构，建立对项目的整体理解：

1. 列出顶层目录结构（`find . -maxdepth 2 -type d`）
2. 读入口文件（main.py / app.py / index.ts 等）
3. 读配置文件（CLAUDE.md / README / pyproject.toml / package.json 等）
4. 扫描模块目录，理解每个模块的职责

在输出开头画出项目的模块地图（一级目录 + 每个模块的一句话职责）。

## 第二步：切换视角

你是一个刚加入团队的开发者，需要在这个项目上改 bug、加功能。具体做法：

- 对每个模块名，问自己"这个目录里应该放什么"——打开看看实际放了什么，对不对得上
- 假装要改一个功能（比如加一条校验规则），从入口追到实现，路径是否清晰，还是得在多个目录间跳转猜测

## 检查维度

### 职责边界

每个模块/文件有没有一个清晰的职责？

关注：一个模块是否承担了多个不相关的职责；是否有代码放错了位置（应该在 A 模块但放在了 B 模块）；模块之间的依赖方向是否合理（是否存在底层模块依赖上层模块）。

> 例：一个叫 `utils` 的目录里有 300 行的业务逻辑——它不是 utils，是一个没命名的业务模块。

### 重复与耦合

有没有同样的逻辑写了两遍？模块之间的耦合是否合理？

关注：复制粘贴的代码块；多个模块共享的逻辑是否提取到了公共位置；循环依赖；一个改动是否会波及多个不相关的模块。

> 例：extract 模块和 audit 模块各自实现了一套 issue 写入逻辑，代码几乎一样但分别维护——改一个漏改另一个就出 bug。

### 可发现性

新人能不能通过目录结构和命名找到想找的东西？

关注：目录命名是否表达了业务含义而非技术含义；文件数量是否合理（一个目录几十个文件说明该拆子目录了）；入口是否明确。

> 例：所有 API 路由、业务逻辑、数据库操作都在一个 `services/` 目录下，新人想找"文件下载"的代码得翻十几个文件。

### 分层一致性

项目的分层（路由→服务→数据→外部调用）是否一致？

关注：有没有路由层直接操作数据库；有没有服务层直接返回 HTTP 响应对象；外部调用（HTTP、MQ）是否有统一的封装还是散落各处。

> 例：大部分接口走 route → service → db，但有一个接口直接在 route 里写了 50 行 SQL——下次改的人不知道该去 service 层找还是 route 层找。

### API 设计

从路由定义和 schema 代码中检查对外接口设计是否合理。（适用于没有独立接口文档的项目，有文档的项目用 `/design-review`。）

关注：接口命名是否表达业务意图；入参和出参结构是否对称（同一个概念在不同接口是否同一个 shape）；有没有暴露内部实现（内部 ID、内部状态值）；响应结构是否自包含（拿到就能用，不需要再调别的接口拼数据）。

> 例：创建订单返回 `{orderId}`，查询订单返回 `{order_id}`——同一个东西两种命名风格，客户端得猜。

## 输出格式

### 模块地图

先输出项目模块地图：

```
project/
├── app/api/          — 路由层：接口入口
├── app/modules/xxx/  — 业务模块：xxx 职责
├── app/db/           — 数据层：ORM 模型
├── ...
```

### 🔴 必须改

每条包含：
- **位置**：哪个模块/文件
- **问题**：一句话
- **影响**：新人会怎么被坑
- **建议**：怎么改

### 🟡 建议改

同上格式。

### ✅ 做得好的地方

列出值得保持的架构决策，让团队知道哪些不该动。

### 总结

1-2 句话：新人接手这个项目，能不能在一天内改出第一个 bug fix？主要卡在哪？
