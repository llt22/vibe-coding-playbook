# 整理 Paseo 工作区会话

## 核心原则

整理的目标是让活跃列表成为清爽的工作台：只保留正在推进的入口和近期交付待验的结果；把已沉淀的历史安全归档。

- **用户认知闭环第一**：Agent 产出完成 ≠ 用户认知闭环。先判断“用户是否已经接收并处理结果”，再判断任务本身是否完成。代码部署、测试通过、文档写完只代表交付，不代表用户已看过。
- **时间顺序严格成立**：用户在执行前说“可以，开始吧”只是授权，绝不是对最终结果的确认。收口证据必须发生在交付结果之后。
- **工作区即业务主线**：一个工作区代表一条独立业务主线。标题中严禁冗余的 `【主线】` 前缀。每个工作区默认标记一个贯穿全局的主会话；同一需求下若存在两个差异明显、各自长期推进的事项，可以保留两个主会话，均以标题后缀 `· 主` 标记。
- **状态不占标题**：待查看、待检查、进行中等流转状态只在整理汇报中呈现，不写进标题；每轮根据会话记录重新判断，不依赖历史标题标签。
- **标题先于去留**：每个会话都先改成一眼能看懂事项和结果的标题，再决定保留、归档或列为删除候选。归档后的检索同样依赖标题；不得因会话即将归档或可能删除而跳过标题整理。
- **结论回流主会话**：主会话是主线上下文的汇合点。子会话里产生的新结论如果主会话不知道，主会话会按旧信息继续工作。整理时要把这些结论同步给主会话，这是整理的固定步骤，不等用户提醒。
- **工作区底线保护**：普通整理严禁清空一个工作区的所有活跃会话，除非用户当次明确指令结束整条工作线。
- **归档可逆，硬删审慎**：归档是常规工作台整理，可随时恢复；硬删是不可逆销毁，只对空会话和测试残骸列出候选，绝不自动执行，必须当次逐个确认。

## 会话分类决策树

对项目下的每个未归档会话，按以下四类互斥落位：

### 1. 保留·正在推进（In Progress）
- 存在明确下一步、未完成待办、未决技术难点；
- 正在等待用户决策、外部系统接入或第三方业务反馈；
- 明确承担长期入口（如需求基线、业务口径、交接知识库、跨会话看板）；
- 当前会话（`←本会话`）或运行中的会话（`running`）；
- 无法查明记录或难以判断状态的会话，默认保持原状保留。
- **处理**：保留在活跃列表；清除遗留状态前缀。

### 2. 保留·近期待查看（Pending Review，≤14天）
- 最后一条实质消息是 Agent/Advisor/worker 的交付成果（部署报告、测试结论、文档链接、决策分析），且**其后没有用户任何回复**；
- 且最后活动时间在 **14 天以内**。
- **处理**：保留在活跃列表，标题只保留事项与可选主会话后缀，待查看状态作为整理汇报的核心重点呈现给用户。

### 3. 归档·已收口（Archived）
符合以下任一条件的会话执行归档：
- **用户显式收口**：在收到交付结果后，用户明确回复“知道了、可以、先这样、结束、不用继续”等，且无遗留待办；
- **用户显式转向**：用户明确要求放弃、搁置或改走其他技术方案；
- **成果已被吸收**：子会话、排查分支或 Advisor 的结论已被主会话或后续会话完整吸收（本轮或之前轮次已回流主会话也算），旧会话无独立待办；
- **超期待查看（>14天自然沉淀）**：交付结果后超过 14 天没有任何用户交互，且无未决阻碍。视为结果已被线下消化或事项已自然过峰，归档收起，避免死锁活跃列表；
- **处理**：`paseo archive <id> -q`。归档时保留原有事项标题及 `· 主` 后缀（如有）。

### 4. 删除候选·无保留价值残骸（Deletion Candidates）
- 仅限：零有效产出的空会话、纯招呼/网络试探（如仅一句“hi”、“test”）、误创建或完全重复且无独立上下文的垃圾会话。
- 只要包含实质讨论、决策过程、排查分析或代码沉淀，**严禁**列为删除候选。
- **处理**：普通整理**绝不自动执行删除**。仅在汇报末尾单独列为删除候选并说明理由，等待用户明确批准。

## 主会话标记规范

- **定义**：每个工作区/业务主线中贯穿始终、承载核心背景、关键决策链、阶段进展和后续分支发起的顶层会话。
- **数量限制**：同一工作区默认 **1 个**活跃主会话，必要时可以有 **2 个**。第二个主会话只用于同一需求或业务主线下两个差异明显、各自有独立背景、决策链和后续待办的长期事项；不要为了满足数量规则强行合并它们，也不要把普通分支升级为主会话。原则上不超过 2 个。判据是**两个事项能各自独立对外描述、各自有自己的待办清单**；同一条需求的排查→修复→上线三个阶段属于同一事项，不构成两个主会话；一个事项的调研分支、验证脚本、临时 worker 同样不算。
- **后缀标记**：标题末尾加 ` · 主`，事项始终放在开头；不叠加状态标签。
- **非主会话**：单一任务排查、临时调研、短期子 worker、已被吸收的阶段会话不标。
- **归档保留**：整条主线彻底收口归档时，`· 主` 后缀继续保留，方便日后全局搜索时一眼认出骨干会话。
- **纠偏**：发现同工作区有 2 个主会话时，先判断是否分别承载两个差异明显的长期事项；符合则保留。只有主题实际重合、其中一个只是短期分支，或主会话超过 2 个时，才摘除多余标记。

## 标题规范与动态清洗

- **命名结构**：`具体业务事项[ · 主]`。唯一可选标记是主会话后缀，禁止叠加角色、状态或工作区前缀。
  - 主会话：`合同比对方案与验证 · 主`
  - 待查看的主会话仍为：`合同比对方案与验证 · 主`；待查看只出现在汇报中。
  - 普通待查看会话：`签章识别接口验证`
  - 普通会话：`月结卡片交互优化`
- **长度与语义**：完整标题（含后缀）尽量不超过 20 字，前 12 字应能辨认具体事项；先删冗余措辞，不机械截断关键词。反映长周期主题，不用临时的报错或单次碎步覆盖全局。
- **历史标题迁移**：先依据内容识别真正的主会话，再将 `【主会话】` 改为末尾 `· 主`；清除 `【待查看】`、`【待检查】` 等状态标签及重复工作区名。即使仍待用户查看，也不保留状态前缀。已有清晰且符合规范的标题无需重写。

## 结论回流主会话

每轮整理都对每个有主会话的工作区做一次回流：把上次回流之后、本工作区其他会话产生的新结论发给对应主会话。若工作区有两个主会话，先按事项归属建立子会话到主会话的对应关系；只同步给后续会用到该结论的主会话。确实同时影响两个事项的共用结论才发给两个主会话，并避免重复发送已知内容。

- **归属落点**：子会话到主会话的对应关系写进本轮汇报的「各工作区主线台账」，每个主会话下面列出归属它的子会话和一句话依据。下一轮直接沿用这张表，只在出现新会话或事项归属变化时调整，并写明调整原因；不要每轮从零重新猜一遍。
- **回流什么**：主会话后续工作会用到的事实，例如用户的决定和口径、查清的根因、提交号、部署或上线状态、资源和环境状态变化、待办转给了谁、仍在进行的子会话在做什么。上次回流的内容后来变了（如“还没停”变成“已停”），要明确写成更正。
- **不回流**：过程细节、试错经过、与这条主线无关的杂事。
- **先查再发**：上次回流的时间和内容看主会话记录里最近一条「【会话整理同步】」。再用 `paseo logs <主会话id> | grep -c <提交号或关键词>` 确认主会话还不知道，已知的不发；没有新结论的主会话不发。
- **怎么发**：每个主会话一条消息，不等回复：
  ```bash
  paseo send --no-wait <主会话id> "【会话整理同步】以下是其他会话的近期结论，只记进你的上下文，不要据此动手，简短回复\"已同步\"即可。
  1. 会话 <短id>（<标题>，<已完成/仍在进行>）：<结论，带数字、提交号、路径>" -q
  ```
- **不打扰**：仍在做事的子会话不发消息，只在给主会话的同步里写一句它在做什么；主会话是 `running` 时本轮不发，留到下一轮。
- **与归档的关系**：子会话按“成果已被吸收”归档前，它的结论必须已经回流到主会话。本轮刚回流、用户还没看过的交付，可以留到下一轮再归档。

## 工作区与移动规范

项目层级为：`项目 (Project) → 工作区 (Workspace/主线) → 会话 (Agent)`。

- **拆分原则**：几条彼此独立的业务主线混在一个工作区且会话较多时，按主线新建 local 工作区。同一需求下两个差异明显的长期事项可以留在同一工作区并各设主会话；不能仅因存在两个主会话就拆工作区。
  ```bash
  paseo workspace create --isolation local --path <项目绝对路径> --project <prj_id> --title "<主线名称>" --json
  ```
- **移动会话**：必须使用配套脚本，不要直接手改配置：
  ```bash
  ~/skills/paseo-tidy/scripts/move.sh <会话id> <wks_id>
  ```
- **防空壳约束**：归档执行前必须按工作区统计剩余活跃数。若归档会导致某个仍在进行的业务工作区活跃会话清零，**必须阻止归档**，至少保留 1 个主会话或最新待查看会话。
- **误归档恢复约束**：若需恢复历史误归档会话，必须先从原会话配置中记录原 `workspaceId`，调用 `paseo import <sessionId>` 后立即用 `move.sh` 移回原工作区，严禁遗留在默认工作区。
- **运行中保护**：`running` 状态的会话和当前正在执行整理的会话不能移动、不能归档。

## 执行流程

1. **提取摘要**：在项目目录下运行
   ```bash
   python3 ~/skills/paseo-tidy/scripts/digest.py [cwd] [--all]
   ```
   查看未归档会话的最后活动时间（末 YYYY-MM-DD）、头尾用户消息、最后 AI 回复及所在工作区。
   整机（所有项目 + 孤儿工作区）整理时用 `scripts/digest_all.py`，输出按「项目 / 工作区」分组，带末事件类型（user 表示用户最后一句没被回复，多半是未完成）。

2. **逻辑推断与查验**：
   - 依据决策树判断去留与标题；
   - 摘要足以判断时直接定案；若交付结果模糊、接续关系不明确，按 provider 追查底层记录（Claude 会话查 `~/.claude/projects/*/<sessionId>.jsonl`；Codex/omp 会话查 `paseo logs <id>`）。

3. **安全执行**：
   - 先做工作区活跃数模拟，确认无误空壳；
   - 先为所有待处理会话执行标题修改和前缀清洗，包括本轮拟归档及删除候选；标题必须能独立说明事项，禁止保留用户口语原句作为标题；
   - 再执行工作区移动；
   - 按「结论回流主会话」给各主会话发同步；
   - 批量归档证据充分的会话：
     ```bash
     paseo agent update <id> --name "规范化标题" -q
     paseo archive <id> -q
     ```

4. **结构化汇报**：整理完成后重新提取一次统计，按固定模板清晰汇报：
   - **数据总览**：未归档总数（前 → 后）、主会话数、待查看数、本轮归档数。
   - **待查看焦点（Top Priority）**：逐个列出待查看会话及交付成果一句话摘要，提醒用户优先查阅。
   - **各工作区主线台账**：列出每个工作区的主会话、归属它的子会话（存在两个主会话时必填，按上面的归属落点格式写）及当前推进状态。
   - **回流主会话**：每个主会话同步了哪些结论、来自哪个会话；没发的说明原因（已知、无新结论、主会话在运行）。
   - **本轮归档清单及证据**：列出归档会话及对应的收口证据（如“用户显式确认”、“成果已并入主会话”或“超14天自然沉淀”）。
   - **删除候选**：逐个说明不可恢复的删除理由，等待用户明确批准。无候选则注明“无”。

## 其他机器会话

`digest.py` 和 `move.sh` 仅针对本机 `~/.paseo`。跨机整理时：
- 推荐在对应机器新建整理会话（通过 `create_agent` 传入对方 `serverId` 与 `workspaceId`）。
- 远程临时运维：使用 `scripts/paseo-at <host> ls -g --json` 查询，`paseo-at <host> agent update` / `archive` 执行，依然严格遵循本决策树。

## 硬核工程避坑

- `paseo inspect --json` 返回字段名首字母大写（`Name`、`Archived`、`Id`），解析时注意区分大小写。
- `paseo archive <id>` 解析不到 background / 子会话（`paseo ls --all` 里能看到，`archive` 报 `Agent not found`）。这类会话用 `scripts/archive-agent.sh <id...>` 直接调 daemon 归档。
- `paseo import <sessionId>` 会丢失原工作区归属并跌落到默认工作区，必须配合 `move.sh` 恢复。
- 直接修改 `~/.paseo/agents/*.json` 里的 `archivedAt` 无效，daemon 以内存状态为准。
- `move.sh` 的原理是临时归档后重新导入到指定工作区。导入时 daemon 会拉起原模型，若模型已下线，导入会卡死在归档状态。移动前可先确认 `paseo logs <id>` 正常。
- 会话开头的 `<chat-history-summary>` 是分叉或接续上下文，不属于本会话的新增工作，但不影响该会话作为独立工作入口的有效性。
