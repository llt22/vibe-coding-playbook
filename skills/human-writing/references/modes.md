# 文体模式：共同底线，不同写法

本站的共同底线是清楚、具体、克制、有证据。不同文章不必使用同一种声音。

动笔前先选一个主模式。可以混合，但只能有一个主模式。

## 1. 教程 / 操作说明

目标是让读者照着做成功。

- 先写前置条件、输入和完成标准。
- 步骤使用 STE 规则：编号、祈使句、一个步骤一个主要动作。
- 每个关键步骤写预期输出和失败处理。
- 不加入与操作无关的个人感想。
- 结尾写适用范围、未覆盖情况和回退办法。

核心问题：读者能不能不问作者就做完？

## 2. 实测 / 工具体验

目标是让读者知道工具在什么条件下好用，什么条件下不好用。

- 先交代环境、版本、任务和评价标准。
- 记录成功和失败，不只展示最好的一次。
- 把事实、判断、预测分开。
- 给出成本、耗时、限制和适用边界。
- 结论可以明确，但不要替读者制造兴奋。

核心问题：别人能不能判断这个结果是否适用于自己？

## 3. 观点 / 评论

目标是提出一个能被讨论的判断。

- 开头尽快交代主张，不用宏大背景铺垫。
- 只保留能支撑主张的案例和资料。
- 处理最强反例，不把个人体验冒充行业统计。
- 允许保留作者的立场、犹豫和判断，不要把文章改成中性公文。
- 结尾停在最后一个有证据的判断，不强行升华。

核心问题：读者是否清楚你在判断什么，以及凭什么这样判断？

## 4. 调研 / 资料整理

目标是把分散来源整理成可核对的事实。

- 每个关键结论紧跟来源，不把多条来源混成一句。
- 区分原文说法、你的归纳和未经验证的推测。
- 记录来源日期、版本和访问条件。
- 来源冲突时并列呈现，解释采用哪一条以及原因。
- 不用资料数量制造可信度。五条重复的转载只算一条证据。

核心问题：读者能不能沿着来源复核你的结论？

## 5. 随笔 / 个人记录

目标是保存一次具体经验和作者自己的声音。

- 只写真实发生过的事，不编造“像真人”的小故事。
- 允许长短句、口语和情绪，只要它们属于作者本人。
- 具体写当时看见什么、做了什么、哪里改变了判断。
- 不要强行把个人经历提炼成普遍规律。
- 不要为了符合技术文章结构，删掉真实的犹豫和失败。

核心问题：如果删掉作者本人，这篇文章还剩下什么？

## 6. 技术方案 / 设计文档

目标是让没参与过的人看懂要解决什么、怎么解决、为什么这样选、还有什么风险，并能据此评审、接入或维护。

动笔前先想清楚读者是谁、各自来找什么。设计文档通常有好几类读者，结构要让每类人都能直接翻到自己那一节。

常用结构如下，按需取舍，顺序基本不变。

1. 背景与目标。要解决什么问题，做到什么程度算成功。
2. 范围。做什么，明确不做什么。
3. 名词。文中的关键叫法，第一次出现就定义，全文统一。
4. 方案概述。一段话加一张图，讲清整体怎么做。图只画步骤和走向，每个框写步骤名，阈值、规则、参数这些细节放正文。
5. 详细设计。按模块或步骤展开，写清输入、输出、依赖和关键规则。
6. 接口。调用方式、数据格式、成功和失败的例子。
7. 备选方案。考虑过但没采用的做法，以及没采用的依据。
8. 效果与验证。怎么测的、测了什么、结果如何。
9. 风险、限制与待决问题。影响多大，下一步谁来处理。

写法上有五条要求。

- 每节标题能看出内容，标题下第一句交代这一节讲什么。
- 写最终方案。被否掉的做法放到「备选方案」，不和正式方案混写。
- 结论要有依据。数字注明来源和条件，同一个数全文一致。
- 宁可不写，不写讲不圆的话。解释不了的数字、没实测过的判断、读者本来不会问的保证（「数据不出网」「不会伪装」这类），写了反而招来追问，删掉。
- 写给外部读者的文档，不留内部过程、本机路径、本地链接和占位。

核心问题：一个没参与过的人，只看标题和每节第一句，能不能说出这份文档在讲什么、自己该看哪一节？

这类文档用 `check.py --doc` 检查，会多跑一遍结构检查。脚本只能发现明显的结构问题，读者能不能看懂，还要按上面的核心问题自己通读一遍。

## 不要混用的规则

- 教程需要完整步骤，观点文章不必把每个观点排成编号列表。
- 实测需要环境和限制，随笔不必伪造实验表格。
- 调研需要来源密度，个人记录不必把每句话都包装成结论。
- STE 只约束说明性内容，不约束正常叙事。
- 设计文档靠标题导航，随笔和观点文章不必每两段就加一个小标题。
- 阮一峰的短句和留白是技术解释的范例，不是所有文体的唯一声音。
