# 说明性段落：逼 AI 讲大白话（STE 原则）

用 STE（简化技术英语）的唯一目的，就是**治 AI 不说人话的毛病，逼它讲通俗大白话**。

直接对 AI 说“写得通俗易懂一点”，AI 往往只会打幼稚浅薄的比方、堆口语废话，或者换个花样继续绕弯子。STE 的作用是一个硬性的物理紧箍咒：通过限制句长和结构，剥夺 AI 故弄玄虚的空间，逼它像宜家说明书一样，把复杂的事情讲得明明白白。

## 什么时候用

- **只在讲步骤、解释代码、说操作流程时用。** 目标是读者看一眼就能跟着做，绝不会看岔。
- **文章的开头、观点、体验和吐槽不用。** 说明书写不出真人的情感与判断。观点和叙事部分长短句混着写，参考 `style.md`。
- **不要跟读者掉书袋。** 博客里不要动辄念叨“ASD-STE100”或航空标准，直接说是“像说明书那样把步骤讲透”。

## 转换成中文的 5 条硬规矩

| 规矩 | 为什么这么做 | 具体怎么写 |
| --- | --- | --- |
| **句子要短** | 句子一长，AI 就开始塞从句和修辞 | 每句尽量在 20 字左右，超过 30 字就拆成两句 |
| **只用主动** | 被动句掩盖责任和主体，读着费劲 | 谁做的就写谁。不写“被处理了”，写“程序删除了它” |
| **一句只说一件事** | 一个句号前堆四五个动作是中文最常见的病 | 一句话只讲一个核心动作，做完一步再讲下一步 |
| **叫法从头到尾统一** | AI 最爱中途换同义词显摆词汇量 | 前面叫“手册”，后面就绝不换成“文档”“说明”。第一次出现时解释清楚 |
| **指代必须明确** | “它”“这个”最容易造成歧义 | 只要读者可能有一秒钟疑惑“它到底指谁”，立刻把具体名字写出来 |

## 步骤段落的标准格式

解释操作步骤时，一律用**祈使句 + 编号列表**，每行一个主要动作：

```markdown
1. 打开终端。
2. 运行安装命令。
3. 检查输出里的成功提示。
```

`check_ste.py` 默认检查 Markdown 编号步骤。没有编号但确实需要按 STE 检查的说明段落，用下面的标记圈定：

```markdown
<!-- ste:on -->
1. 打开终端。
2. 运行安装命令。
<!-- ste:off -->
```

检查器不会扫描普通观点、体验和叙事段落，避免把整篇文章写成僵硬的说明书。

## 怎么验证

先运行专项检查器：

```bash
python3 ~/skills/human-writing/scripts/check_ste.py <文章路径>
```

检查器会拦截过长步骤、一步多个动作、隐藏执行者的被动句、含糊指代，以及显式 STE 区块里遗漏编号。术语是否统一仍需人工复核，因为脱离领域词表自动判断容易误报。

最后找一个完全没看过代码的人读一遍：
- 对方能一眼看出先后顺序、能直接照着做，就是合格的；
- 对方停下来问“这个词跟前面那个是一个东西吗”或者“出错了往哪走”，说明没写透，继续拆短句。
