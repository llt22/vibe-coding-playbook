# AI 工作方法调研服务：设计

目标：把“怎样在工作中把 AI 用到最好”的新线索变成**别人拿到就能照做、能明显改善工作方式的手册**，而不是资讯汇总。**全自动闭环**：定时采集 → 模型初筛打分 → 模型挑选并深入调研 → 可照做的结论合并进按场景组织的手册 → 提交到仓库。人只看手册和周报，不需要手动触发或决定。失败必须可见。

最终产物是 `playbooks/`；逐条调研报告（`research/radar/`）只是手册的证据和素材。

五个研究问题见 [research/catalog/build.py](../research/catalog/build.py) 的 `QUESTIONS`，服务直接复用。

## 总体结构

```
            ┌──────────── Mac（24 小时开机，第一阶段也是宿主）────────────┐
            │                                                          │
 GitHub ─┐  │  服务进程（Node + SQLite）                                │
 HN     ─┼─►│   采集器 ─► 归一去重 ─► 对照清单 ─► LLM 初筛 ─► 自动调研 ─► 报告/周报 │
 RSS/网页┘ │      ▲                                   写入 research/radar 并提交 │
            │      │ POST /ingest（带 token）                           │
            │   Ego 定时采集 X（本机登录态）                               │
            └──────────────────────────────────────────────────────────┘
```

- **第一阶段全部跑在 Mac 上**，只监听 127.0.0.1。Mac 常开，已有 Ego、claude、codex、omp 登录态和 `~/skills`，没有必要先上服务器。
- **以后迁到服务器时**：网页、数据库、GitHub/HN/RSS 采集搬过去；Mac 退为 worker，只做需要本机登录态的事（X 采集、深度调研），通过出站请求把结果推给服务器。服务器不需要能访问 Mac。
- **X 不在服务器上跑。** 服务器上跑登录态的无头浏览器违反 X 条款，也容易封号。官方 API 按量计费（二手资料称约 $0.005/次读取，需在开发者后台核实）；将来要接，也走同一个 `/ingest` 格式。

## 数据来源（MVP）

| 采集器 | 方式 | 频率 | 说明 |
|---|---|---|---|
| `github-search` | Search API，按关键词/topic，限近 7 天新建且星数过阈值 | 6 小时 | 无 token 每分钟 10 次，够用；设 `GITHUB_TOKEN` 可提高限额 |
| `github-active` | Search API，不限创建时间，近 7 天有推送且星数过 500/1000，补上只看新建会漏掉的成熟项目 | 每天 | 4 条查询之间隔 7 秒，避开无 token 时的限流 |
| `github-trending` | 解析 github.com/trending 页面 | 每天 | 无官方 API；解析出 0 条视为失败 |
| `hn` | HN Algolia API，按关键词，限分数阈值 | 3 小时 | |
| `rss` | 博客、newsletter 和官方博客的 feed（含 claude.dev、OpenAI News） | 6 小时 | 每个 feed 单独记成功或失败 |
| `pages` | 没有 feed 的文章列表页（Anthropic Engineering），解析卡片的链接、标题、日期 | 12 小时 | 解析出 0 篇视为失败（可能改版） |
| `ingest` | 外部推送（X/Ego、以后的官方 API） | 被动 | 记录推送方的最后心跳 |

每次采集都记一条运行记录，GitHub 结果顺带记星数快照，用来算增长。

暂不做：关注仓库的 Releases、arXiv、Reddit、V2EX。

## 处理流程

1. **归一**：每条线索有唯一 key。GitHub 仓库统一为 `github:owner/repo`，其余用去掉跟踪参数的 URL。同一 key 只保留一条，后续采集只更新热度。
2. **对照清单**：启动时载入 `research/catalog/catalog.jsonl`。命中已有条目的线索标记为“已在清单”，不重复初筛，页面上显示清单里的状态。
3. **LLM 初筛**：每批 10 条，结构化输出。每条给出：
   - 相关度 0–3（3 = 可能改变工作方式，0 = 无关）
   - 对应的研究问题
   - 一句中文理由，说清楚它能在真实工作里做什么；看不出实际用途的算“花架子”，给低分
   - `deep`：是否值得自动深入调研。只有相关度 ≥ 2 且原文可能提炼出可照做的步骤、配置或流程时才选；纯新闻、产品发布、观点文不选，宁缺毋滥
   研究对象是“人怎样和 AI 一起工作”；生成视频、游戏之类的 AI 应用本身最多给 1。
   失败（接口错误、拒答、截断）标为“初筛失败”并显示原因，下一轮重试，不当作 0 分。
4. **自动调研**：模型标了 `deep` 的条目进入调研队列，手动加入的最先、其余按相关度优先，每小时最多 5 条，不设每日上限。每条：
   - 取原文：GitHub 仓库先读 raw README（不受匿名 API 每小时 60 次的限流），失败再走 API；X 帖子用采集时保存的正文，其余抓网页转文本。取不到时只依据摘要，并在报告里写明
   - 找出原文提到的清单条目及其状态，让模型对照已有结论
   - 模型输出结论（建议采用 / 值得一试 / 值得研读 / 继续观察 / 不值得跟进）、一句话理由和 Markdown 报告（是什么、编号的具体做法、对应研究问题、与已有做法的关系、证据与局限、怎么试和验证）。只有提炼得出具体步骤时才能给“采用 / 一试”，否则最多“研读 / 观察”
   - 报告写到 `research/radar/日期/`，用 `git commit -- 这些文件` 提交，不带上工作区里其他改动。提交失败记为运行失败
   单条失败最多重试 3 次，每次间隔至少 1 小时。
5. **合并进手册**：有待合并的就处理，最多每小时一次、每次最多修订 6 篇，把还没合并的“建议采用 / 值得一试”调研合并进 `playbooks/`：
   - 分配：一次模型调用把最多 20 条调研分到手册 slug，优先归入现有场景，避免一条线索一篇
   - 修订：每篇手册一次调用，输入数据库里保存的上一版正文和新调研报告，输出完整新版（解决什么问题 / 适用与不适用 / 前置条件 / 操作步骤 / 怎么判断变好了 / 常见坑 / 证据与来源）和本次改动列表。每轮最多修订 6 篇，没轮到的调研下一小时重新分配
   - 写 `playbooks/<slug>.md`（头部标“未经实测”，末尾自动列出依据的调研）并重写 `playbooks/README.md` 目录，提交信息写明改了什么、依据哪些调研
   - 失败的手册不标记合并，1 小时后重试；服务不改人工维护的 `experiences/`
6. **周报**：每 7 天把近 7 天手册新增或修改的做法写到 `playbooks/weekly/日期.md` 并提交；没有修订就不写。

JSON 输出偶尔不合法（多为字符串里的引号没转义），统一由 `llm.ts` 的 `askJson` 立即重答一次，错误信息带出错位置前后的原文。

模型走任意 OpenAI 兼容接口（需支持 `response_format: json_object`），在 `service/.env` 配置 `LLM_BASE_URL`、`LLM_API_KEY`、`LLM_MODEL`。输出用 zod 校验，不合格记为初筛失败。

## 网页

| 页面 | 内容 |
|---|---|
| 手册 `/` | 所有手册：标题、解决的问题、先试这一步、最近修订、依据几篇调研，都标“未经实测”。顶部显示异常 |
| 手册正文 `/playbooks/:slug` | 手册全文和依据的调研链接 |
| 调研证据 `/research` | 逐条调研的结论，可按结论筛选，分页；调研失败的列在第一页顶部 |
| 调研报告 `/research/:id` | 单条报告全文，注明已合并进哪篇手册 |
| 线索 `/candidates` | GitHub 仓库以外的线索和初筛结果，可按来源、研究问题、是否选中深入筛选，分页；只读，用于排查 |
| 仓库 `/repos` | GitHub 仓库类线索，筛选同上，可按星数排序 |
| 运行记录 `/runs` | 每个采集器、初筛、调研、周报最近的运行、条数、错误，分页；每个推送方的最后心跳 |

网页上没有任何需要人操作的按钮：不需要手动采集，也不需要逐条决定。

**失败必须可见**：某个采集器最近一次失败，或超过两个周期没有成功运行，首页顶部标红。“没有新线索”和“采集失败”在页面上必须能区分开。

鉴权：默认只监听 127.0.0.1。在 `.env` 设 `HOST=0.0.0.0` 可让家里内网（如手机）直接访问，不需要密码；要暴露到公网时再设 `WEB_PASSWORD` 启用 Basic Auth。`/ingest` 始终要求 `INGEST_TOKEN`。

## 推送接口

```
POST /ingest
Authorization: Bearer $INGEST_TOKEN
{
  "source": "x",              // 推送方名称，也作为心跳
  "items": [{ "url": "...", "title": "...", "summary": "...", "author": "...",
              "published_at": "ISO 时间", "metrics": { "likes": 120 } }],
  "error": "可选：推送方自身的部分失败"
}
```

返回新增条数。空 `items` 也合法，相当于只报心跳。带 `error` 时本次运行记为失败并在首页标红，已收条目照常入库。`config.pushers` 登记推送方的约定周期，超过两个周期没推送也标红。

## 存储

单个 SQLite 文件（默认 `service/data/radar.db`，不入库），使用 Node 自带的 `node:sqlite`。

- `items`：线索、热度、初筛结果（含是否深入）；旧的 `decision` 列保留不再使用
- `research`：调研队列和结果：状态、重试次数、结论、报告正文、仓库文件路径、错误、合并进的手册
- `playbooks`：每篇手册的最新版本（正文以数据库为准，文件由它生成）
- `playbook_updates`：每次修订的改动列表和依据的调研，周报从这里取
- `runs`：每次采集的开始、结束、状态、条数、错误
- `star_snapshots`：仓库每日星数
- `pushers`：推送方最后心跳

## 技术选择

- Node 24 直接运行 TypeScript（类型擦除），不需要构建步骤；`tsc --noEmit` 只做类型检查。
- 依赖只有 `openai`、`zod`、`fast-xml-parser`。HTTP 服务用 `node:http`，页面服务端渲染，不引前端框架。
- 调度在进程内：启动时和每分钟检查一次，距离上次成功运行超过周期就执行。重启不丢进度，因为时间取自 `runs` 表。

## 分阶段

1. **MVP（本次）**：上述采集器、初筛、三个页面、推送接口，在 Mac 上用 launchd 常驻。
2. **X 采集（已完成）**：`x/run.sh` 每 3 小时用 Ego 里已登录的 X 会话只读搜索 `x/queries.json` 里的账号和关键词（取自 ai-engineering-radar 方法文档），推到 `/ingest`。遇到登录墙直接失败，不绕过。
3. **自动深度调研（已完成）**：模型在初筛时选出值得深入的条目，服务自己取原文、调用 `.env` 里配置的模型写报告，写回仓库并提交。
4. **落地成手册（已完成）**：可照做的调研每小时合并进按场景组织的手册，周报改为“手册新增或修改了哪些做法”。
5. **沙箱实测**：挑手册里的步骤在隔离环境实际跑一遍，记录结果，通过的去掉“未经实测”标记。
6. **到期复查**：清单条目按状态设复查期限，到期自动重新调研；调研结论回写 catalog.jsonl。
7. **迁服务器**（需要时）：Docker 部署，Mac 转为 worker。

## 运行

```bash
cd service
pnpm install
pnpm collect        # 排查用：立即跑一轮全部采集、初筛和到期的调研，有异常时退出码非 0
pnpm start          # http://127.0.0.1:4317，进程内每分钟检查到期任务
pnpm typecheck
```

- **配置**：`cp .env.example .env` 后填写，`.env` 不入库。脚本用 `--env-file-if-exists=.env` 读取。
- **代理**：本机直连 github.com 不稳定。Node 的 fetch 默认不走系统代理，脚本带了 `--use-env-proxy`，在 `.env` 里设 `HTTPS_PROXY` 即生效（`NODE_USE_ENV_PROXY` 写在 env 文件里无效）。模型接口不需要代理时加进 `NO_PROXY`。
- **推送接口**：设置 `INGEST_TOKEN` 后才启用。
- **常驻**：`launchd/ai-work-radar.plist` 用登录 shell 启动 `pnpm start`，配置全部来自 `.env`。启用方式：
  ```bash
  cp launchd/ai-work-radar.plist ~/Library/LaunchAgents/
  launchctl load ~/Library/LaunchAgents/ai-work-radar.plist
  ```
- **X 定时采集**：`launchd/ai-work-radar-x.plist` 每 3 小时执行 `x/run.sh`，日志在 `data/x.log`。需要 Ego 已登录 X，且主服务已启用推送接口。plist 里的仓库路径按本机实际位置填写。
- **费用**：初筛每批 10 条调用一次模型。首轮 176 条约 18 次调用，之后只处理新增。自动调研每条一次调用（输入最多约 3 万字原文），每小时最多 5 条、每天最多约 120 条；合并手册有待合并时每小时 1 次分配调用加每篇 1 次修订调用。上限在 `config.ts` 调整。
- **自动提交**：调研报告、手册和周报由服务直接 `git commit` 到当前分支，只提交自己写的文件，不推送。设 `RESEARCH_GIT_COMMIT=0` 只写文件不提交。

原始会话日志（Codex、Claude Code、omp）不进入本服务，也不上传服务器。
