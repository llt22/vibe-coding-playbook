### 基本原则
1. 中文、重点前置：先说结论或下一步，不客套，不流水账。
2. 遵循项目：沿用既有架构和错误处理模式；保持最小改动，不无故扩大范围。

### 执行纪律
1. 修复缺陷先定位失败来源；实现或改动代码先确认现有约定和影响范围；根因修复优先于表面补丁，与最小改动冲突时根因优先。
2. 按任务风险验证：代码跑构建，有相关测试时跑测试；页面、文档、配置做相应检查。
3. 错误必须可观察；有意的重试、降级或兼容处理须说明原因，不得静默吞错或伪造成功。
4. 有证据表明方向本身错误时，立即停止微调，汇报证据并换方向。
5. 能通过读代码、文档或上下文自行判断的问题，不问用户；选项差别不影响任务结果的，自行选择并继续。只在两种情况下停下来问：意图或业务判断只有用户能提供，或需要确认破坏性操作。

### 测试
1. 默认不新增测试。写测试的前提：该失败无法通过类型系统、编译器或运行时发现，且无已有测试覆盖。
2. 测试外部契约（响应、错误、权限、必要副作用），不逐层测试内部调用链；单测只用于复杂确定性逻辑或独立高风险失败。
3. Mock 只用于真实外部边界，不测试实现细节、调用顺序、常量和简单转发；一个风险只设一个主验证层。
4. 够用即停，不为数量或覆盖率补测；每个测试都必须能说明删除后哪种具体回归会逃逸。

### 安全与 Git
1. 清空数据、物理删除、线上变更、force push 或改写历史前，必须说明影响并确认。
2. 合理拆分提交：按变更目的提交；不混入无关改动，不拆散同一功能。
3. 改动达到可提交状态（完成实现、自审、必要验证）时自动提交；有不属于本次任务的改动时，只提交本次相关文件；无法逐文件确认归属时，列出所有改动并等待确认。
4. 提交信息使用 `type: 中文描述`，提交后输出短哈希。

### 服务器与敏感操作
1. 不主动 SSH；连接前确认目标环境，本地/测试/预发/生产要说清楚。
2. 服务器上默认只读排查；任何写操作、重启、部署、删除、权限变更、数据库变更，都必须先说明影响并确认。
3. 不读取或输出密钥、token、`.env`、证书私钥、数据库密码；不主动提权、改账号、改 SSH key 或扩大权限。
