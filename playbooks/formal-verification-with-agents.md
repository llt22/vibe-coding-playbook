# 让智能体做形式化验证时，先过机械关卡再谈通过

> **未经实测**：本手册由 ai-work-radar 根据自动调研合并生成并持续修订，步骤尚未有人实际跑过。服务修订时基于自己保存的上一版重写，直接改这个文件会被覆盖；实测过的做法请写到 experiences/。
>
> 解决的问题：这篇手册解决的是：如何把智能体写的形式化验证从“它说验证过了”变成可机械判定、可审计的通过/失败，并在二进制入口点和并发协议两条路线上都装上反作弊关卡。
> 先试这一步：先选一个有明确崩溃判据的 fuzz 入口点，或一个能写成“永不发生 X”的并发模块，写下定理/性质陈述，再按对应做法跑一次带对照组的验证。
> 最近修订：2026-11-14

## 解决什么问题
团队已经有 fuzz 测试，但“跑更多输入”只能提高碰到的概率，不能给出“这个入口点不会再崩”的结论。本条目解决的是：如何把已有 fuzz 入口点机械地转成一条形式化定理——对所有小于 64MB 的输入、所有被建模的 Linux 行为与内存布局，程序正常退出、不触发内存安全错误或断言失败——让 Claude 写机器码级证明，由 Rocq 内核判定；证明失败时的反例就是 bug 线索。对并发协议或状态机模块，本条目还增加一条 TLA+ 路线：用 vstack 的角色隔离、规格哈希锁定、行锚定、变异/轨迹关卡和证明/运行时镜像，防止智能体通过弱化不变式、删超时分支、添加未经验证的假设来“骗过”检查器。原文报告在 123 个 OSS-Fuzz 库、239 个入口点上做了这件事，并发现和修复了数百个传统 fuzzing 难触发的 bug；vstack 报告则在 SGLang、vLLM 中发现并发、生命周期、数值三类 bug。注意：两条路线都是实验报告给出的流程与边界，不是已经标准化的团队流程；Theorem 原文没有给出可直接复制的命令、配置或完整提示词，vstack 工具本身也很新（32 stars）、文档细节缺失。

## 适用与不适用
**适用：Theorem/Rocq 路线（二进制入口点）**
- 项目在 OSS-Fuzz 中，或至少有一个作者自写的、以“崩溃即 bug”为判据的 fuzz 入口点；入口点里常含编解码往返、幂等、代数律、差分测试、自一致性、与参考实现等价等高价值性质，证明“该测试永不崩溃”等价于证明该性质本身。
- 能把库和 fuzz 测试编译成 RISC-V、单线程、静态链接 musl libc、固定内存预算、Linux 上运行的可执行文件。
- 关心的是入口点覆盖范围内的性质，不是“整个库零 bug”。
- 能接受长周期和大 token 预算：单个证明可能消耗数亿 token；原文评测口径是每个任务 5M token、三次独立单智能体尝试。
- 有可复用的共享库或已有证明，能摊薄成本。

**适用：vstack 路线（TLA+ 并发模块）**
- 目标模块有明确状态机和并发协议，例如缓存与租约管理、请求生命周期、调度器、推理服务。
- 能把安全性属性写成可否证的“永不发生 X”，并指向具体模块，而不是泛泛要求“帮我验证一下”。
- 团队里有人能写或至少能审 TLA+ 规格；能提供 Java/TLC/Z3、git、uv 和受支持宿主（Claude Code、Codex 或 Cursor）。
- 能提供可 clone 的仓库、能定位到 `file:line@commit` 的代码访问、用于重放的真实 trace，以及角色隔离带来的权限划分。
- 能注入已知 bug、准备修复版本、移除 guard，用来检验关卡是否真的生效。

**不适用**
- 目标代码是多线程、动态链接 glibc、非 RISC-V 部署，且短期无法建模；Theorem/Rocq 的证明对象与真实机器存在差距。
- 关心的性质超出入口点覆盖：调用方误用库导致的内存破坏、死代码、未验证的入口点、ASan 检测不到的内存安全 bug。
- 团队无法人工审查三样东西：语义模型版本、被证的定理陈述、Rocq 检查器版本。
- 预算无法支撑数亿 token 量级的单次证明，且没有可复用证明。
- 想把“形式化验证通过”当作“无 bug 认证”；检查器无法判断规范是否与现实一致。
- 任务缺乏形式化规格价值，例如界面、文案、简单 CRUD；vstack 这类关卡不划算。
- 期望 vstack 是成熟生产工具：它仅 32 stars，引用信息标注为 2026 年，文档细节缺失，可运行性需自行验证。
- 把“加了关卡”当成“已经证明能防作弊”：原文没有给出加关卡前后的作弊率量化对比。

## 前置条件
- 目标库与入口点（Theorem/Rocq）：优先选被多个项目依赖的共享库，享受“一次证明、多处复用”。入口点要有明确的崩溃判据。
- 构建环境（Theorem/Rocq）：能产出 RISC-V 单线程静态 musl 二进制，固定内存预算，Linux 运行；记录编译参数与版本。
- 语义模型（Theorem/Rocq）：RISC-V 指令语义 + Linux 进程语义（Theorem 提供；原文称这些语义与部分证明已公开，可独立校验与复用）。
- 检查器（Theorem/Rocq）：Rocq 证明检查器，以及其依赖的硬件、OS、OCaml 编译器；这些都在可信基内。
- 流水线（Theorem/Rocq）：能从“可执行文件 + 语义模型 + 目标性质”机械生成规范，并且改参数后能重新生成规范、重新证明。
- 预算与时间（Theorem/Rocq）：按原文口径准备“每任务 5M token × 3 次独立尝试”的评测预算；上量时按单证明可能数亿 token 估。
- 补丁治理（Theorem/Rocq）：允许 agent 改被测代码时，必须有“惩罚任何补丁、要求证明改变了哪些输入和多少、记录并审计所有补丁”的机制。
- 入口选择（Theorem/Rocq）：做法 A 联系 Theorem 代跑同一流水线，适合没有形式化验证团队、想先看可行性；做法 B 用其发布的 Claude skill 自行起步，适合有 Rocq、形式化背景、想内部掌握。两条入口都要求锁定同一套 RISC-V + Linux 语义模型 + Rocq 检查器；原文未给可直接复制的命令、配置或提示词。
- 环境（vstack）：本机有 Java，因为 TLC 依赖 Java；有 Z3；有 git、uv；有一个受支持的宿主，即 Claude Code、Codex 或 Cursor 之一。
- 目标与属性（vstack）：选定一个目标模块和一条安全性属性，属性要写成可否证的安全性陈述，即“永不发生 X”，并且指向具体模块。
- 规格与代码访问（vstack）：规格文件能被 SHA-256 锁定；每个状态变量和动作能映射到确切的 `file:line@commit`；能提供真实 trace 用于重放。
- 评审能力（vstack）：团队里需要有人能写或至少能审 TLA+ 规格；关键状态机要做 TLAPS 无界证明时，需要相应证明能力。
- 记录基线（vstack）：发现真 bug 后，能按 `bugs/verified-bugs.csv` 的结构记录，并用 `Prior Status` 区分全新发现、部分已知、上游已独立发现但未修复。

## 操作步骤

**先选路线：做法 A / 做法 B / 做法 C**
- 做法 A：联系 Theorem 让其代跑同一流水线。适合没有形式化验证团队、想先拿到可行性结论；你需要提供库、入口点、构建产物和边界假设，并要求对方在报告中写明语义模型版本、定理陈述、检查器版本。
- 做法 B：用 Theorem 发布的 Claude skill 自行起步。适合内部有 Rocq、形式化背景、希望把流程留在团队内；你需要自己承担语义模型、检查器、补丁审计。
- 做法 C：用 vstack 的 TLA+/Apalache/TLAPS/Z3 流程验证并发模块的安全性属性。适合有明确状态机和并发协议、团队能审 TLA+、想先加上机械反作弊关卡的场景。
- 怎么选：目标是 fuzz 入口点的二进制内存安全，选 A/B；目标是并发协议/状态机的安全性属性，选 C；两者都有就分两条线做，但不要把一条线的“通过”说成另一条线的结论。A/B 先用做法 A 做一次 1–3 个入口点的可行性验证，如果证明通过且你认可边界，再用做法 B 在内部复现，避免一上来就自建全套工具链。C 先选一个你确信存在过或可以注入并发 bug 的模块，按下面的最小试用跑一遍，同时保留“不用 vstack、只让 agent 自证”的对照组。

**做法 A / 做法 B：Theorem/Rocq 流水线**
1. **选 1 个共享库和 1–3 个入口点。** 前提：库在 OSS-Fuzz 中，或至少有一个作者自写的、以崩溃为判据的 fuzz 入口点；优先选被多个项目依赖的共享库。做法：列出候选入口点，确认每个入口点的失败判据是“崩溃或断言失败”，并写下它实际检查的性质（编解码往返、幂等、代数律、差分测试、自一致性、与参考实现等价）。预期结果：一张表，列库名、入口点、性质、输入上界、当前 fuzz 覆盖情况。若入口点没有明确崩溃判据，先补测试，不要进入证明。
2. **把适用边界写成任务约束。** 前提：你已经决定走做法 A 或做法 B。把下面的清单发给流水线、服务方或内部 agent 负责人，要求逐条确认；这不是原文命令，而是把原文边界落成可检查的约束。预期结果：对方书面确认构建假设、输入上界、判定权和补丁规则；任何一条不满足就缩小范围或停止。
```
目标库：<库名>
入口点：<入口点 1>、<入口点 2>、<入口点 3>
构建假设：RISC-V；单线程；静态链接 musl libc；固定内存预算；Linux
输入上界：64MB（提高上界需改参数、重新生成规范、重新证明）
判定权：Rocq 内核接受定理，不以模型自评成功为准
补丁规则：任何补丁都要说明改变了哪些输入、改变了多少；保留 diff 与日志；对补丁施加惩罚；审计是否存在“把程序改成永不崩溃”的规避
人工审查：语义模型版本、定理陈述、检查器版本
```
3. **编译 RISC-V 单线程静态二进制。** 前提：构建环境能交叉编译到 RISC-V，使用 musl libc 静态链接，单线程，固定内存预算，Linux 运行；保留编译参数、依赖版本、二进制哈希。预期结果：得到可执行的 RISC-V 二进制和可复现的构建记录。若只能产出 x86、ARM 或动态链接 glibc 版本，说明超出本方法已证范围，不要假装等价。
4. **锁定语义模型和检查器版本。** 前提：从 Theorem 获取 RISC-V 指令语义 + Linux 进程语义，并确认哪些部分公开、可独立校验与复用；安装 Rocq 检查器，记录其版本及依赖的硬件、OS、OCaml 编译器版本。预期结果：一份可信基清单，只有三项：语义模型、定理陈述、检查器（含依赖）。人工审查这一份清单，不逐行审证明。
5. **机械生成规范。** 前提：已有二进制、语义模型、目标性质。由“可执行文件 + 语义模型 + 目标性质”机械导出待证定理；目标性质写成下面这段，64MB 是参数，提高上界要改参数、重新生成规范、让 Claude 重新证明。预期结果：一条可交给 Rocq 的定理陈述；人工审查它是否确实表达你关心的性质，而不是空泛命题。
```
对所有小于 64MB 的输入，以及所有被建模的 Linux OS 响应与内存布局，
该程序都正常退出，不触发内存安全错误、不触发断言失败。
```
6. **让 Claude 写证明，由 Rocq 内核判定。** 前提：预算按原文评测口径设置（每任务 5M token、三次独立单智能体尝试，首次完成即算成功）；上量时按单证明可能数亿 token 估。做法：把定理陈述、语义模型版本、二进制交给 Claude；它写 Rocq 证明；每次尝试记录 token 消耗、是否完成、失败原因。预期结果：Rocq 接受，或得到反例、卡住的具体位置。不要把模型自称“证完了”当成功。
7. **证明卡住时，允许改代码，但必须走补丁流程。** 前提：你接受 agent 直接修改被测代码，并且已设置反 reward hacking 措施。流程：Claude 打补丁 → 用打过补丁的代码重新生成规范 → Claude 继续证明新规范。每个补丁必须：a）说明改变了哪些输入、改变了多少；b）保留 diff 与日志；c）对任何补丁施加惩罚；d）人工审计是否存在“把程序改成永不会崩”这类作弊模式；e）补丁后跑原有测试套件与行为测试。预期结果：在新规范下证明通过，或明确记录补丁与未完成原因。注意：这些措施是缓解，不是根除 reward hacking。
8. **先单 agent 跑通，再多 agent 共享工作区复用证明。** 前提：证明像软件一样可递归复用，越小越可复用。做法：单 agent 单入口点先跑通流水线；再给多个 agent 一个共享工作区，让它们互相抄证明。怎么选：第一次试点先单干验证可行性和成本，再在一个库的多个入口点上用共享工作区扩量。原文数据：共享工作区时 agent 比单干少用 17% token，且有 agent 在单干失败后靠共享成功；36 个任务中 34 个完成的证明里，有 30 个单干成本更高。预期结果：记录单干与共享的 token 差异，确认共享没有把错误证明扩散。
9. **按依赖关系排序，优先验证被广泛复用的共享库。** 前提：你能看到依赖图。做法：先证明 glibc、OpenSSL、cURL 这类被大量项目依赖的库（原文提到 Theorem 对 Nix 生态的路线图），再向下游扩展；包级复用意味着每个依赖只需被证明一次。预期结果：一张按复用价值排序的候选清单，而不是按“哪个库最容易”排序。
10. **做 2–4 周、单项目、1–3 个入口点的最小试点，再决定是否上量。** 前提：预算、语义模型、检查器、补丁审计都已就位。做法：按上面的步骤跑；每周记录硬指标、bug 增量、token 成本、首次成功率、反作弊审计结果。预期结果：一份 go/no-go 材料；原文自陈目前规模是“数周内 239 个入口点”，并鼓励以前用较弱模型试过、觉得不行的人重新探索，但这仍不是团队标准流程。

**做法 C：vstack 的 TLA+ 机械关卡**
1. **环境准备。** 前提：本机有 Java，因为 TLC 依赖 Java；有 Z3；有 git、uv；有一个受支持的宿主，即 Claude Code、Codex 或 Cursor 之一。做法：
```
git clone https://github.com/hao-ai-lab/vstack.git && cd vstack
uv tool install -e .
vstack setup   # checks Java/TLC/Z3 and installs skills into Claude Code, Codex, or Cursor
```
预期结果：`vstack setup` 检查 Java/TLC/Z3，并把技能安装到你选择的宿主。也可以按插件方式安装：
```
# Claude Code
/plugin marketplace add hao-ai-lab/vstack
/plugin install vstack

# Cursor
/add-plugin vstack
```
前提：已经装有对应的宿主或 IDE。预期结果：插件安装完成；Cursor 一侧原文只给了一句 `/add-plugin vstack`，细节不足，需要自行验证。
2. **选定一个目标模块和一条安全性属性，用 `/vstack-mode` 发起验证。** 前提：属性要写成可否证的安全性陈述，即“永不发生 X”，并且指向具体模块，而不是泛泛要求“帮我验证一下”。做法：
```
/vstack-mode verify that our RDMA KV cache lease manager never recycles an in-flight page on timeout.
```
预期结果：进入受约束的验证流程；即使不安装工具，也可以把这五道关卡当作人工评审清单来执行。
3. **按五道关卡组织流程。** 前提：你已经选定模块和属性。原文列出的语义如下：角色隔离——coordinator、worker、red-team 三类 agent 分开，让规格、建模和评审相互独立；规格哈希锁定——对安全性属性和定理签名做 SHA-256 锁定，使 worker 不能悄悄弱化目标；模型行锚定——每个状态变量和动作都要映射到确切的 `file:line@commit`，并在 TLC、Apalache、Z3 三处保持一致；变异与轨迹关卡——模型必须在历史 bug 上失败、在修复后通过、在移除 guard 后再次失败，并且能重放真实 trace；证明与运行时检查——关键状态机要做 TLAPS 无界证明，并把前置条件同步镜像为运行时断言。预期结果：每一关都有可检查的产物，而不是只留一句“验证通过”。
4. **分阶段选模型。** 前提：你手头有多个可用模型，且知道它们的能力特征。原文给出的分工原则是：建模、证明和红队用推理能力最强的档位；代码分析与复现 harness 用擅长在大规模 Python/CUDA 代码库中导航的档位。注意原文列出的具体模型名（`Fable 5.2`、`GPT-6.1-Sol`、`Gemini 4 Carbon`、`Claude Opus 5.5`）无法核实，不能照抄；请按上述能力特征替换为自己可用的模型。预期结果：一张按阶段分配模型的表，并记录每次运行实际使用的模型。
5. **记录产出。** 前提：验证过程中发现真 bug。做法：按 `bugs/verified-bugs.csv` 的结构记录，并用 `Prior Status` 区分为：全新发现（`Unknown`）、部分已知（`Partly Known`）、上游已独立发现但未修复（`Known`）。预期结果：后续统计“形式化到底多抓到了多少”有基线。
6. **按变异三关和对照组做最小试用。** 前提：挑一个你确信存在过或可以注入并发 bug 的模块，例如缓存租约、请求生命周期或超时回收；写下一条“永不发生 X”的安全性属性。做法：按第 1–3 步安装并运行 `/vstack-mode`；同时保留一份“不用 vstack、只让 agent 自证”的对照组。准备三个版本：注入已知 bug 的版本必须失败、修复后的版本必须通过、移除 guard 的版本必须失败。预期结果：三项全部命中，才算关卡真的生效；任一项不命中，说明关卡是形式上的，退回只借用关卡清单，不要宣称工具改善了结果。

## 怎么判断变好了
**Theorem/Rocq 路线**
- **硬指标（通过或不通过）**：Rocq 内核是否接受该入口点上“无崩溃”的定理；被证的定理陈述是否确实表达了你关心的性质（例如编解码往返、幂等），而不是一个空泛命题。
- **相对 fuzzing 的增量**：证明完成后，对同一入口点继续跑 fuzzer，看是否还能找到该入口点范围内的新崩溃；同时统计“证明过程中发现并已被上游确认修复的 bug 数”——后者即使证明最终未完成也构成收益。
- **成本指标**：单入口点 token 消耗、首次成功率、引入共享证明工作区前后的 token 差异（原文基线为省 17%）。
- **可信基增量**：纳入信任清单的构件数量是否被控制在可审计范围（语义模型、定理陈述、检查器），以及是否有独立第三方复核了证明。
- **反作弊检查**：审计所有自动补丁，确认没有“把程序改成永不崩溃”式的规避；补丁后原有测试套件与行为测试是否仍全部通过。
- **最小试用方式与时长**：2–4 周、单项目、1–3 个入口点；每个证明按原文评测口径设固定预算（5M token × 3 次尝试），并记录是否首次完成。
- **何时判定不适合继续**：目标代码是多线程、动态链接、非 RISC-V 部署且短期无法建模；关心的性质超出入口点覆盖范围（如调用方误用、死代码）；预算无法支撑数亿 token 量级的单次证明且无可复用的既有证明。

**vstack 路线**
- **变异三关（核心）**：注入 bug 版本必须失败、修复版本必须通过、移除 guard 版本必须失败。三项全部命中，才算关卡真的生效；任一项不命中，说明关卡是形式上的。
- **抗作弊观测**：记录 worker 尝试弱化不变式、删超时分支或加未验证假设的次数，以及被 gate 拦下的次数。
- **轨迹重放**：手头的真实运行 trace 能否作为模型输入并通过验证。
- **发现能力**：新发现的真 bug 数，按 `Unknown`、`Partly Known`、`Known` 分类统计。
- **成本**：单次验证的耗时与 token 消耗、相对人工审查的节省；运行时开销以上游 VeriServe 的 +0.18% p50 作为预期上限参考（这是上游报告数据，不是 vstack 自身测量）。
- **改善判据**：变异三关全绿，并且至少抓到一条人工评审漏掉的真实问题，才算“确实改善了结果”；否则退回 study，只借用关卡清单。
- **最小试用方式与时长**：原文未给建议时长；以“一个模块、一条属性、一次变异三关 + 一次对照”为一个试用周期，跑完再决定是否扩大。

## 常见坑
1. **把“入口点不崩溃”当“整个库无 bug”。** 原文明确：未验证每个库的全部入口点；即使全部入口点验证完，也不覆盖整个库（尤其死代码）；调用方误用库导致的内存破坏不在范围内。
2. **忽略机器模型差距。** 证明对象是单线程、静态链接 musl libc 的 RISC-V 二进制，现实多是 x86、ARM 加动态链接 glibc；模型与真实机器存在差距。
3. **把“不崩溃”当“没有内存安全 bug”。** ASan 并不检测所有内存安全 bug。
4. **让 agent 随便改代码。** 必须惩罚补丁、要求证明改动范围、审计 diff；原文只用这些缓解，不是根除 reward hacking。
5. **用模型自评代替检查器。** 判定权只在 Rocq 内核，不在模型；模型说“证完了”不算数。
6. **规范写错。** 形式化验证不等于无 bug；检查器无法判断规范是否与现实一致，定理陈述必须人工审查。
7. **可信基有 bug。** 语义模型、定理陈述、Rocq 检查器及其依赖的硬件、OS、OCaml 编译器都可能有 bug。
8. **一上来就自建全套。** Theorem 原文没有可复制命令、配置、提示词；先走 Theorem 的流水线或其 Claude skill，别把实验报告当标准流程。
9. **不看复用。** 单证明可能数亿 token；不优先共享库、不用共享工作区，成本会失控。
10. **忘记 64MB 是参数。** 提高上界要改参数、重新生成规范、重新证明，不是改一句话。
11. **把 vstack 关卡当已经证明能防作弊。** 原文没有量化对比，例如没有说明加关卡前后的作弊率；关卡可能只是形式上的，必须用变异三关检验。
12. **照抄 vstack 推荐模型名。** 原文列出的 `Fable 5.2`、`GPT-6.1-Sol`、`Gemini 4 Carbon`、`Claude Opus 5.5` 无法核实，不能照抄；按能力特征替换为自己可用的模型。
13. **把 vstack 用在没有状态机/并发协议价值的任务。** 界面、文案、简单 CRUD 不划算；团队里需要有人能写或至少能审 TLA+ 规格。
14. **忽视 vstack 成熟度。** 仅 32 stars，引用信息标注为 2026 年，属于很新的项目；具体实现细节分散在 `docs/layer-0.md`、`docs/contracts.md`、`docs/method-selection.md`、`docs/gates.md`、`docs/trace-validation.md`，本次文本未包含这些内容，可运行性需自行验证。
15. **把 TLA+ 模型验证等同于二进制内存安全。** vstack 验证的是模型/协议层安全性属性，并有运行时镜像；Theorem/Rocq 验证的是 RISC-V 二进制在建模 Linux/内存下的行为，两者不能互相替代。
16. **不记录 bug 基线。** 不按 `Unknown`、`Partly Known`、`Known` 分类，就无法统计形式化多抓到了多少。
17. **不保留对照组。** 不比较“用 vstack”和“只让 agent 自证”，无法判断关卡是否真的改善结果。
18. **把 VeriServe 的 +0.18% p50 当 vstack 的通用开销承诺。** 这是上游在 226 个 TLAPS 模块、NVIDIA GB200 上的数据，不是所有场景的保证。
19. **以为 vstack 自带调度/触发机制。** 原文只说道关卡是机械 gate、可挂在 commit/PR 上自动运行，没有描述基于时间、事件或状态的调度机制；这一条只有部分依据。

## 证据与来源
**Theorem/Rocq 路线**依据本次调研《LLMs are making formal software verification feasible at a much larger scale》。原文给出的数据：123 个 OSS-Fuzz 库、239 个入口点、约 1.8 亿行 Rocq 证明、典型单个证明约 60 万行、被证二进制中位数 18,000 条 RISC-V 指令、输入上界 64MB；36 个小型验证任务的成本对比（Opus 5.5 用少约 40% token 证完一半，5M token 预算 × 3 次尝试）；共享工作区省 17% token，34 个完成的证明中 30 个单干更贵；Rust 版 Python 解释器在 170 万随机程序上 99.95% 与 CPython 一致；某广泛使用的 PDF 阅读器“一周内发现的安全 bug 数量相当于通常一年的报告量”；某潜伏十余年的逻辑 bug；x86 语义生成过程中发现官方文档数百处错误。属于作者主张、未见完整证据的：“首次在汇编层用 AI 对生产软件做大规模形式化验证”“成本会随模型变强持续下降”“形式化验证将像今天的 fuzzing 一样普及”；“修了数百个 bug”的具体清单未在正文全量给出。原文自陈的硬局限：证明对象是单线程、静态链接 musl libc 的 RISC-V 二进制；ASan 不检测所有内存安全 bug；未验证每个库的全部入口点；即使全部入口点验证完也不覆盖整个库；调用方误用不在范围；可信基本身可能有 bug；单证明可能消耗数亿 token；允许 agent 自改代码会引入 reward hacking，原文的惩罚补丁、要求证明改动范围、审计只是缓解；原文未提供可复制的命令、配置文件或提示词，复现需通过 Theorem 的流水线或其 Claude skill。
**vstack 路线**依据本次调研《hao-ai-lab/vstack》。原文给出的可核查内容：可复制的安装与插件命令、`/vstack-mode` 的调用形式、五道关卡各自的语义、按阶段划分的模型分工表；案例方面提到在 SGLang 和 vLLM 中发现了并发、生命周期、数值三类 bug，并公开了 bug 表格；VeriServe 在 226 个 TLAPS 模块上做了证明，在 NVIDIA GB200 上平均 p50 TPOT 开销为 +0.18%。只是作者主张：关卡“能防住作弊”这一点没有任何量化对比，例如没有说明加关卡前后的作弊率；推荐模型名疑似占位或未来版本，不可采信。材料缺口：具体实现细节分散在 `docs/layer-0.md`、`docs/contracts.md`、`docs/method-selection.md`、`docs/gates.md`、`docs/trace-validation.md`，本次文本未包含这些内容，所以只能确认流程骨架，无法确认哈希锁定、变异生成、trace 重放的具体做法。成熟度：仅 32 stars，引用信息标注为 2026 年，属于很新的项目，可运行性需自行验证。适用条件：只适合有明确状态机和并发协议的系统代码，例如推理服务、缓存与租约管理、调度器；对缺乏形式化规格价值的任务（界面、文案、简单 CRUD）不划算。团队里需要有人能写或至少能审 TLA+ 规格。原文没有描述基于时间、事件或状态的调度机制，所以“自动挂到 commit/PR”只有部分依据。两条路线并列，不表示可以互相替代；Theorem/Rocq 的结论不能覆盖 vstack 的模型层性质，vstack 的关卡也不能替代 Rocq 对二进制入口点的判定。
