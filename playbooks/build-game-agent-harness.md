# 让 agent 在游戏项目里能自己验证改动：确定性状态、可寻址命令、截图 diff

> **未经实测**：本手册由 ai-work-radar 根据自动调研合并生成并持续修订，步骤尚未有人实际跑过。服务修订时基于自己保存的上一版重写，直接改这个文件会被覆盖；实测过的做法请写到 experiences/。
>
> 解决的问题：当 AI 在非网页的游戏项目上反复失败时，怎样把游戏改造成 agent 能直接寻址、状态可复现、效果可量化的形态，从而缩短它的验证回路。
> 先试这一步：在一个新模块或新小项目上（先别动既有大项目），只做两件事：接入单一带种子的随机源和一条最小可用的“保存/加载指定状态”路径，再给产出物接上截图入口和图层开关，然后用命令行图像 diff 工具算出相似度数值交给 agent，要求它每轮报告该数值并朝着提升它迭代。
> 最近修订：2026-10-14

## 解决什么问题

作者自称在网页栈（Svelte 等）上已几乎找不到 LLM 做不了的事，但一碰非网页的游戏就失败，由此得出“LLMs are Bad At Games”。他把原因归结为结构性而非模型能力：游戏里大量内容不是代码（资产、布局、场景、数据），这些对 LLM 是“不透明”的；游戏训练数据远少于网页项目；也没有标准化工具。结论是：让 LLM 做好游戏是一个 **context 问题**，要靠 harness（一组针对特定预期输入的 agent 行动模式）把游戏“打开黑盒”，变成 agent 能直接寻址的东西。

需要说明：以上是作者的论证链和个人经验主张，不是评测结论。作者也承认自己可能有偏见——他是 15 年经验的游戏程序员，对游戏代码更挑剔，对 Svelte 代码则倾向认为 LLM 产出是“good”。

## 适用与不适用

**适用**：
- 自研 / 可控引擎的游戏项目，且这些做法**越早越好**——原文把它当作“写第一行代码前就该设定的目标”级别的架构约束。
- 有视觉产出、能截图对比的任务（UI 样式微调、布局对齐、某个视觉效果的逼近）。
- 想让非程序员、其他团队成员和 AI agent 在**已有 build 上**迭代的项目。

**不适用或迁移价值有限**：
- 常规软件，尤其网页栈：多数改造（Thing 化、命令回放、独立模拟库）并不必要。原文认为这几条里只有“截图 diff 定量评估”“外置数据/配置”“减少编译等待”有较直接的迁移价值。
- 已在生产末期的项目：作者明确说代价极高（“VERY hard”），甚至需要临上线时做根本性改动。
- 图像 diff 只适用于有视觉产出的任务，而且相似度数值本身不等于“做对了”。
- 原文通篇没有可复制的代码、命令或提示词，也没有基准测量、失败案例或对照数据；“效果更好”缺少量化证据。

## 前置条件

- 项目处于起步阶段（或至少在一个新模块/新小项目上试，而不是既有大项目）。
- 引擎提供截图 API 或功能（原文称 most engines have some built in screenshot API or functionality）。
- 一个命令行图像 diff 工具：原文点名免费的 `odiff`，但**没有给出安装或调用方式**，落地前需自行查该工具文档。
- 愿意放弃强 OOP 继承模型（做“Thing 驱动开发”时）。
- 有一定工程投入用于重构引擎与逻辑的边界（做“独立模拟/黑盒”时）。
- 一个放静态数据的外部数据源与反序列化路径（做“数据外置”时）。原文作者用自研的 Depot（正在产品化），也提到其他团队用 Google Sheets 或自建工具。

## 操作步骤

下面分两条路走。**做法 A 是做法 B 前几步的子集**：做法 A 用于 1–2 天验证“这条路对我有没有用”，做法 B 是在新项目上按原文的完整架构约束落地。

### 做法 A：最小试用（建议 1–2 天）

只在**一个新的小项目或新模块**上做，不要全面重构。

1. **引入单一带种子的随机源，并做一条最小可用的“保存/加载指定状态”路径。**
   - 前提：项目刚开始。
   - 做法：在游戏启动时创建一个唯一的、带种子的随机源；让所有非确定性调用（原文举例 `Random.Float` 之类）都走这个源，而不是在 30 个地方各自调用全局随机。
   - 预期结果：第 N 次随机调用的结果每次都一样，从而能确定性地重建几乎任意游戏状态；保存/加载能精确保存和加载任意状态。

2. **给产出物接截图入口，并加上图层开关。**
   - 前提：引擎有截图 API 或功能。
   - 做法：接入截图能力；再加上 UI 层 / gameplay 层等独立开关，便于只保留当前要处理的那一层，减少视觉干扰。
   - 预期结果：agent 每次改动前后都能取到一致的画面用于比较。

3. **用命令行图像 diff 工具做定量评估，把相似度数值喂给 agent。**
   - 做法：用 `odiff` 对两张图（改动前 / 改动后，或产出 / 目标图）求差，输出一张 diff 图和**量化的相似度数值**（原文举例形如“85% similar”）。把 diff 图和这个数值一起交给 agent，要求它每一轮报告该数值，并朝着“降低差异 / 提高相似度”迭代。
   - 预期结果：每个 agent turn 都有一个稳定的评估基线。
   - 注意：原文没有给出 `odiff` 的安装或调用命令，不要凭想象写。

4. **选一个“有明确目标图”的任务，让 agent 独立跑多轮。**
   - 任务类型：UI 样式微调、布局对齐、某个视觉效果的逼近。
   - 人只在数值停滞或震荡时介入。

5. **如果第 1–4 步顺利，再加第三条：把该模块的数值型参数挪到外部数据文件。**
   - 先用 CSV / JSON 即可，不必上 Depot 这类工具。
   - 预期结果：验证 agent 能否**不改代码、不重编译**就完成一次调参迭代。

### 做法 B：完整架构约束（在写第一行代码前就当作目标）

原文自称这组做法“very tangible, actionable”，并且即使不用 AI，对普通游戏开发也是净收益。

1. **单一随机源（Fixed Randomness）**——同做法 A 第 1 步的前半部分：唯一一个带种子的随机源，所有非确定性调用都走它。
2. **可截图 + 图层开关（Screenshot-ability）**——同做法 A 第 2 步。
3. **用图像 diff 做定量评估**——同做法 A 第 3 步。为什么不直接把截图丢给多模态模型：原文说这会带来 **context pollution**——模型会同时处理你没想让它改的所有区域。作者用“会议官网首页 + 把骨架改成海盗”的标注例子说明，未被请求的绿色区域全是噪声。所以要先 diff、再裁剪，只把需要判断的东西给模型。
4. **确定性状态：一开始就做 save/load**——不要像业余做法那样把保存/加载拖到最后当成一个“feature”，而是从最初就与核心架构一起设计。这是后面所有可复现、可评估的前提。
5. **Thing 驱动开发（fat struct / 单一对象类型）**
   - 前提：愿意放弃强 OOP 继承模型。
   - 做法：假设游戏里所有东西本质上是同一种东西，代码里就用单一类型（原文建议直接叫 `Thing`）。每个 `Thing` 带一组 stat 类数值、一个 `isAlive` 之类的共用标记、以及一个 `type` 枚举，具体行为由实现代码根据 `type` 分派。
   - 原文给的收益：对象模型只有一个真相来源，AI 不需要理解 100 个类和它们的关系（那会塞满 context，并且让它纠结“该继承？该改类型？该新建类？”）；序列化/反序列化只有一个入口一个出口，避免 polymorphic deserialization 和多类型继承树带来的奇怪反序列化竞态。原文明确说这并不像想象中那么费内存，并推荐 Wookash podcast 中与 Dreams 创作者的对谈作为延伸阅读。
   - 原文未给出 `Thing` 的实际代码。
6. **可寻址状态：命令模式（Command Pattern）**
   - 前提：已采用第 5 步的单一对象类型。
   - 做法：不要把状态变更写成松散函数调用，而是表示为（理想情况下可序列化的）命令对象，统一经过一个处理类来应用到对象上。复现 bug 时，从起始状态“回放”序列化的命令即可，而不用去问玩家当时做了什么。
   - 关键延伸：命令**不必由游戏本身产生**——可以在文本编辑器里手写（或由 AI 生成），直接回放到运行中的游戏实例上，**无需编译**。
   - 目的：给 AI（和你）一个带类型的游戏交互界面，把游戏变成“可操纵的”（puppet-able）；同时减少编译等待，让 agent 循环更紧。原文的一般性原则是：能让游戏不编译就产生变化的能力越强越好。
7. **数据外置（Data Management）**
   - 前提：愿意把静态数据从代码里搬出去。
   - 做法：把描述“东西本来是什么样”的静态运营数据（原文举例 `Type`、`attackDamage`、`walkSpeed`、`boatSpeed`）放在游戏外部的数据源里，游戏启动时反序列化并套用到对应对象上。改数值 = 改数据源，不再需要重编译或写 console 命令之类的绑定。
   - 工具：作者用自研的 Depot（正产品化），也提到其他团队用 Google Sheets 或自建工具。
   - 预期结果：非程序员、其他团队成员和 AI agent 都能在**已有的 build 上**迭代，甚至不需要编辑器权限。作者在 Cantata 项目里就是约 7 名非程序员拿 build + Depot 迭代。
8. **独立模拟 / 黑盒（Standalone Simulation / Blackbox）**
   - 前提：有一定工程投入，愿意重构引擎与逻辑的边界。
   - 做法：把游戏模拟逻辑从引擎的操作逻辑中抽出来，物理上作为独立的 DLL/library 存在；引擎与模拟之间通过“命令”（即第 6 步的命令）通信，模拟返回更新后的状态，引擎通过对比上一次收到的状态做 diff 来理解发生了什么，并“Dumb”地照做——模拟说动了就动，不质疑。
   - 原文举的例子：移动请求发给模拟，模拟判断目标是否合法并结算，返回“该对象已移动”的状态对象；引擎 diff 前后状态后播放动画、模型、音效。
   - 收益：任何来源（网络、LLM、其他）都能向核心发命令，网络编程因此变简单得多。

**怎么选**：时间预算 1–2 天、或面对的是既有项目/新模块 → 做法 A；新项目、自研可控引擎、愿意为长期的 agent 循环付架构代价 → 做法 B。两者的差别主要是覆盖面，不是互相替代。

## 怎么判断变好了

- **可复现率（硬门槛）**：同一份种子 / 同一串命令回放，能否 100% 复现同一状态。这一条不达标，后面所有指标都不可信。
- **图像 diff 的相似度数值**：原文举例形如“85% similar”，可作为每个 agent turn 的稳定评估值，要求 agent 每轮报告并朝“降低差异 / 提高相似度”迭代。
- **达成目视效果所需的人工介入次数与 agent 轮数**，与不使用该 harness 的基线对比。（原文这一句在材料中截断，未给出完整对照方式，落地时需自行定义基线。）
- 原文还把“任何改动都做到最小必要变更”作为一个可被近乎隔离评估的目标，以避免积累 spaghetti 式技术债。

**最小试用方式**：在一个新模块或新小项目上做做法 A 的第 1–4 步，先只做“确定性 + 截图 diff”，不要全面重构。

**试多久**：原文建议的最小试用是 1–2 天；同时因为原文强调这些是“越早越好”的架构约束（生产末期再补代价极高），验证窗口本身也应放在项目早期。

## 常见坑

- **原文没有可复制的东西**：全篇没有命令、配置或提示词；`odiff` 只被点名，没有安装或调用方式。落地前必须自行查该工具文档，不要把网上找到的写法当成原文做法。
- **别直接把截图丢给多模态模型**：会带来 context pollution——模型会同时处理你不想让它改的区域。应先 diff、再裁剪，只给需要判断的部分。
- **相似度数值不等于“做对了”**：图像 diff 只适用于有视觉产出的任务，数值本身不保证结果正确。
- **别在生产末期补这些约束**：作者明确说“VERY hard”，甚至需要临上线做根本性改动。
- **别把整套改造搬到普通软件上**：Thing 化、命令回放、独立模拟库对网页栈等常规软件并不必要。
- **别把“主动推进”当成有依据的做法**：原文只覆盖单次任务内的自主多轮迭代（agent 先做多轮内循环，再回到截图比对/diff，直到相似度提升）。它泛泛提到 harness 可接入浏览器迭代、telemetry、profiling，乃至工单、文档等完整 SDLC 工作，但**没有给出任何基于时间、事件或状态触发的具体调度做法**。
- **别忽略作者的自认偏见**：他是 15 年经验的游戏程序员，对游戏代码更挑剔，对网页栈代码更宽容；“游戏训练数据比网页少若干个数量级”也用了 “I imagine”，属推测。
