# 在写代码前，用零上下文评审逼出设计规格里的隐含假设

> **未经实测**：本手册由 ai-work-radar 根据自动调研合并生成并持续修订，步骤尚未有人实际跑过。服务修订时基于自己保存的上一版重写，直接改这个文件会被覆盖；实测过的做法请写到 experiences/。
>
> 解决的问题：需要设计决策的功能，如何在编码前暴露规格中的未言明假设、遗漏约束和实现风险，并由人完成架构取舍与批准。
> 先试这一步：选一个中等复杂度、确实需要设计取舍的功能，先让掌握完整上下文的代理起草规格，再把规格文本单独交给一个不共享上下文的会话，要求列出歧义、缺失约束、未说明假设和不可测试之处；人逐条处理并批准后才编码。
> 最近修订：2026-11-08

## 解决什么问题
需要先做设计决策的功能，常见问题是设计中的未言明假设、遗漏需求、约束和实现风险直到编码后才暴露，造成返工。本手册给出一套“深上下文起草规格 → 零上下文压力测试 → 人做架构取舍并批准 → 再实现”的做法；有完整 EGM 插件时按插件流程走，没有插件或能力不满足时用手工会话隔离先验证流程骨架。

## 适用与不适用
适用：一个功能在实现前确实需要设计取舍，例如新增 webhook 投递，需要讨论投递失败、同一事件到达两次等设计问题。也适用于已有笔记转设计文档、为已有代码库补文档、处理评审发现、检查文档与代码漂移等单点任务。

不适用：小型、明确的 bug 修复仍走普通编码流程，不要强行套完整流程。设计评审不能替代测试或人的判断。若编码代理不能创建全新子代理，完整 EGM 的金鱼评审无法进行，EGM 会停止评审；此时只能改用做法 C 的手工骨架，且要承认它只是近似隔离。EGM 不是 Google 官方支持产品，采用前要按团队要求评估。推文级材料只确认了流程骨架，未确认插件安装、配置、提示词和实际实现；不要把“开源插件”当成成熟工具直接全量采用。

## 前置条件
- 选用完整 EGM 路线时：编码代理支持插件，并且当前会话能创建新的子代理（fresh subagents）。README 明确说金鱼评审需要全新子代理上下文；代理无法创建时，EGM 会停止评审。
- 选用手工骨架路线时：能另开一个不共享起草阶段上下文的会话，并只把规格文本交给它；这只能近似零上下文评审，隔离强度和可重复性弱于 fresh subagent。
- 准备好项目上下文、需求、约束、先前决策、被评审文档及其引用的源材料。
- 有人参与：每节草稿后给反馈，评审发现逐条取舍，最终批准规格后才实现；提前指定审批人，并约定“未批准不写代码”的门禁。
- 安装完整插件，而不是只拿技能提示；材料说完整插件便于技能读取评审提示和文档标准。
- Claude Cowork 和 ChatGPT Work 需按 README 指向的 setup guide 配置；本次材料未提供该 setup guide 正文。
- 记录试用：保留概念简报、设计草稿、评审发现、采纳决定、批准规格和实现后的返工/缺陷记录。

## 操作步骤

1. 先选路线并确认能力。前提：你有一个需要设计决策的功能，而不是小型明确 bug。做法：如果要用 EGM 完整流程，先确认代理支持插件且能创建 fresh subagent；如果只是先验证流程骨架，确认你能另开会话并只提供规格文本。预期结果：明确走做法 A、B 还是 C；若既不能创建 fresh subagent，也不接受手工隔离的弱化，请不要声称完成了零上下文评审。

2. 安装完整 EGM 插件（做法 A/B 的前置）。前提：按所用代理选择命令。Claude Code：
```sh
claude plugin marketplace add google/elephant-goldfish-model
claude plugin install egm@egm
```
Antigravity：
```sh
agy plugin install https://github.com/google/elephant-goldfish-model
```
Codex：
```sh
codex plugin marketplace add google/elephant-goldfish-model
codex plugin add egm@egm
```
预期结果：插件安装完成。安装后开始一个新会话。Claude Cowork 和 ChatGPT Work 按 README 指向的 setup guide 配置；材料未提供该指南内容。若安装不了或团队不允许装插件，跳到做法 C，不要臆造其他安装命令。

3. 选择一个需要设计决策的功能。前提：功能不是小型明确 bug 修复，而是需要先讨论设计取舍。示例：README 用“给项目增加 webhook 投递”举例，并明确要讨论“投递失败怎么办”“同一事件到达两次怎么办”。预期结果：你能写出几个必须由人拍板的设计问题；若写不出，可能不该套用本流程。

4. 做法 A：走完整 EGM 流程，从想法到批准规格。前提：插件已装好、能创建 fresh subagent，你希望把一个功能从模糊想法推进到可实现的批准设计。按下面顺序做：

4.1 探索想法并形成概念简报。Antigravity（agy CLI）和 Claude Code 加 `/egm:` 前缀；Codex 从技能选择器中选择对应 EGM 技能。README 示例：
```text
/egm-brainstorm Add webhook delivery to this project.
```
与代理讨论需求和取舍；新评审者会挑战提案；代理把达成的一致方向保存到 `concepts_brief.md`。预期结果：得到一份概念简报，关键取舍有记录。

4.2 起草规格文档：
```text
/egm-draft
```
代理把简报转成 `design_draft.md`，每写完一节暂停，等待你在对话中反馈。预期结果：逐节形成设计草稿，而不是一次性生成后无人校对。

4.3 用零上下文评审者评审草稿：
```text
/egm-review design_draft.md
```
使用代理返回的草稿路径。新评审者检查设计本身、清晰度、与代码的契合度以及实现计划；你选择要处理哪些发现。预期结果：拿到一份可逐条处理的评审发现清单。

4.4 处理发现并定稿。可使用 `egm-resolve` 技能逐条处理评审发现并商定修改。预期结果：对采纳和不采纳的发现都有明确结论；README 提到完整流程会把批准的规格保存在 `docs/designs/` 下。

4.5 人工批准后再实现。你负责解决取舍、批准设计，然后让编码代理按批准的设计实现。预期结果：实现前已有批准规格，而不是边写边改设计。未批准不写代码。

5. 做法 B：按需单独使用 EGM 技能。前提：你不需要完整序列，只想补一个环节。可按任务选择：`egm-brainstorm` 测试想法并写概念简报；`egm-draft` 把简报或已有笔记转成设计文档；`egm-resolve` 处理评审发现并商定修改；`egm-bootstrap` 为已有代码库创建或更新文档；`egm-review` 用新代理分五阶段评审设计；`egm-review-loop` 为特定评审任务运行一组配置好的评审者；`egm-drift-report` 把已检入文档与当前源代码对比。预期结果：只补所需环节，但不要因此跳过人的取舍和批准。怎么选：从模糊想法到批准规格用做法 A；已有简报只差文档用 `egm-draft`；已有评审发现用 `egm-resolve`；已有代码库缺文档用 `egm-bootstrap`；要检查文档与代码是否一致用 `egm-drift-report`。

6. 做法 C：没有插件或不能创建 fresh subagent 时，手工搭最小流程骨架。前提：你不能安装 EGM，或代理不能创建全新子代理，但你仍想先验证“深上下文起草 + 零上下文压力测试 + 人工批准”的方法。注意：这不是完整 EGM 的金鱼评审，隔离强度和可重复性较弱；原文只给出流程骨架，没有给出插件命令、配置和固定提示词。

6.1 用掌握完整上下文的代理起草规格。把需求、约束、现有系统信息、已定架构方向交给同一个上下文完整的会话，让它输出一份可评审的规格文档。预期结果：得到一份可评审的规格文档，至少能看见需求、约束、待决问题和关键失败场景；具体模板材料未给出，不要假装是插件固定格式。

6.2 另开一个不共享起草阶段上下文的会话做压力测试。只把规格文本交给它，不附带起草阶段的隐含背景；要求它列出歧义、缺失约束、未说明假设和不可测试之处。预期结果：拿到一份可逐条处理的问题清单；若只能得到泛泛意见，说明输入或任务还不够具体。

6.3 人逐条处理并做架构决策。对每个发现决定采纳、不采纳或待补证据，并明确架构取舍。预期结果：对采纳和不采纳都有理由；关键取舍由人拍板，而不是让评审者替你决定。

6.4 批准后才编码。指定审批人确认规格，约定未批准不写代码；批准后再让编码代理实现。预期结果：实现前有批准规格，编码阶段不再反复改设计。

6.5 记录试用材料。保留规格、压力测试问题清单、采纳决定、批准记录和实现后的返工/缺陷记录。预期结果：能回答“编码前发现的问题是否减少了返工”，而不是只凭感觉。

7. 用 `egm-drift-report` 做一致性检查（有插件路线）。前提：已有检入文档和当前源代码。做法：使用 `egm-drift-report` 技能对比文档与当前代码。预期结果：发现文档与代码漂移，作为后续维护输入；材料未给出该技能的具体命令形式，不要臆造命令。手工骨架路线若没有该技能，只能人工对照，不要假装跑过。

8. 保留试用记录（所有路线）。前提：你准备判断效果。做法：保留 `concepts_brief.md`、`design_draft.md`、评审发现记录、采纳决定、批准后的规格和实现后的返工/缺陷记录；手工路线保留规格文本和问题清单。预期结果：能回答“评审是否在编码前发现了会导致返工的问题”，而不是只凭感觉。

## 怎么判断变好了
- 最小试用：选一个中等复杂度、确实需要设计取舍的功能（README 示例是新增 webhook 投递）。有插件时，在 Claude Code 中安装 EGM，按 `/egm-brainstorm` → `/egm-draft` → `/egm-review` 走一遍，保留 `concepts_brief.md`、`design_draft.md` 和评审发现记录；由人决定采纳哪些发现后再实现。没有插件时，用做法 C：完整上下文起草一份规格，另开会话只给规格文本，要求列出歧义、缺失约束、未说明假设和不可测试之处，人逐条处理并批准后再编码。
- 试多久：材料没有给出固定试用时长或样本量。可把“完整走完一个中等复杂度功能从设计到实现”作为一个试用单元；推文级调研建议用 3 到 5 个同类规格与常规评审对照，但没有给出改善阈值。不要只做一次评审就下结论。
- 看这些指标：对比使用前后，设计评审中发现的“未言明假设 / 遗漏需求 / 实现风险”的数量与质量；记录评审发现中被采纳的比例；记录是否在编码前发现了会导致返工的问题；记录从设计到实现的返工次数、规格变更次数、实现后缺陷数；记录评审到批准耗时和人工决策数量；检查批准后的设计文档是否可用于后续实现和交接；有插件时用 `egm-drift-report` 检查文档与代码是否保持一致。
- 降级或停止条件：如果评审只能产生泛泛意见、无法创建 fresh subagent 且手工隔离也没有实质发现，或发现的问题在编码前没有实际减少返工，应降级为 study 或停止使用。不要把互动数据、仓库 stars 或项目自述当成效果证据。

## 常见坑
- 把小型明确 bug 修复套完整流程。README 明确说小型明确 bug 修复仍走普通编码流程。
- 让金鱼带着先前对话上下文评审。金鱼评审要零上下文、全新子代理；代理不能创建 fresh subagent 时 EGM 会停止评审。手工做法 C 另开会话只是近似，不能宣称等价。
- 只安装技能提示，不安装完整插件。材料说完整插件便于技能读取评审提示和文档标准。
- 安装后不开始新会话。README 要求安装后开始一个新会话。
- 把评审当测试或人的判断替代。README 明确评审不能替代测试或人类判断。
- 不选评审发现、不人工批准就进入实现。流程要求人选择处理哪些发现、解决取舍并批准规格。
- 只看评审意见数量，不看采纳和返工。材料没有量化改善数据；泛泛意见不等于有效发现。
- 把项目自述或互动数据当效果证据。README 声称“数千名 Google 工程师使用 EGM”，仓库显示 5242 stars；推文约有 921 赞、135 转发、47 回复，但材料没有使用效果、缺陷率、返工率或评审命中率数据；“金鱼评审能暴露未言明假设和盲点”是项目主张，不是对照实验结论。
- 把推文级材料当完整文档。原文是 Google Cloud Tech 推文，链接未展开，正文在“before”处截断；只能确认“深上下文起草、零上下文压力测试、人工架构批准”的流程骨架，无法确认插件安装、配置、提示词、许可证和实际实现。
- 忽略材料边界。EGM 原文是 GitHub README，不是完整文档；`docs/getting_started.md`、`docs/harnesses.md` 等链接内容未提供；Claude Cowork 和 ChatGPT Work 的 setup guide 也未提供。
- 误以为 EGM 是 Google 官方支持产品。材料明确说该项目不是 Google 官方支持产品。
- 在没有插件时臆造命令或提示词。做法 C 只照流程骨架写清输入和要评审的类别；不要编造 `/egm-*` 之外的命令。
