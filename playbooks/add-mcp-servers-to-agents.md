## 适用与不适用

适用：

- 本机已经能用 Hermes CLI（终端里 `hermes` 命令存在），并且有 Node.js / npx 运行环境、能访问 npm registry。
- 你愿意并且能够在隔离环境（容器、虚拟机或专用账号）里先跑第三方 npm 包。
- 你的目标是“让代理一次性获得一整套外部工具”，而不是解决某个具体任务。

不适用：

- 不能隔离、必须直接在主力工作目录上试用。
- 需要稳定可复现的生产接入，或需要原文给出完整工具清单、权限范围和失败排查步骤。
- 原文内容在工具清单处被截断；如果你依赖“139 个工具”的完整能力来规划任务，目前不适用。

## 操作步骤

### 做法 A：隔离环境接入并验证（默认）

1. 准备隔离环境并确认前提。

   在容器、虚拟机或专用账号中打开终端，确认 `hermes` 命令存在、`npx` 可用、能访问 npm registry。

   预期结果：后续命令能在不接触主力工作目录的环境中执行。

2. 注册 REA MCP 服务器。原文原样命令：

```
hermes mcp add rea --command npx --args -y rea-agents@6.3.0 mcp
```

   参数含义（按命令字面）：服务器名 `rea`；启动方式 `--command npx`；参数 `--args -y rea-agents@6.3.0 mcp`，即用 npx 自动确认安装并运行 `rea-agents` 的 6.3.0 版本、以 `mcp` 子命令启动。

   前提：npm registry 可访问；首次运行 npx 会拉取并执行第三方包。

   预期结果：命令完成注册，`rea` 成为一个名为 `rea` 的 MCP 服务器。是否真的出现，需要下一步核对。

3. 核对注册与工具清单。

   原文没有给出查看已注册 MCP 服务器或工具列表的具体命令，需要查阅 Hermes 自身文档（例如对应的 list / 工具枚举命令），确认 `rea` 是否出现在列表中。

   预期结果：记录代理是否在不需要用户点名工具的情况下自动调用 rea 工具。

5. 与未挂载时做对照。

   对同一任务，在不挂载 rea 的情况下再跑一次，比较代理能否自主选用工具、需要多少人工干预、步骤数和耗时。

   预期结果：得到一组“挂载 vs 未挂载”的对照记录。

6. 版本与安全检查。

- 注册失败，或注册后工具无法被代理实际调用。
- 无法提供隔离环境。
- 需要完整的工具清单、权限说明和失败排查步骤，而原文只给了一条命令。

做法：不把 `rea` 挂到任何工作环境，只记录“用 MCP 协议把外部工具集一次性喂给代理”这一供给方式，作为后续遇到类似工具集时的参考。

## 怎么判断变好了

可观察指标（来自本次调研的最小试用设计）：

- 注册是否成功，`rea` 是否出现在服务器列表中。
- 工具数量是否与作者所称的 139 个大致相符；记录实际名称。
- 面对自然语言请求时，代理能否在不需要用户点名工具的情况下自动调用 rea 的工具。
- 同一任务与未挂载时相比，人工步骤数和耗时是否减少。
- 安全负向指标：是否出现越权访问、读取工作目录之外的文件、或执行非预期命令；出现即回滚并降级为 study。
