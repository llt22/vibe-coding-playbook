>
> 解决的问题：子代理文件格式有误时可能被静默跳过，导致你把“模型不肯委派”误判成能力问题，实际是子代理从未被加载。
> 先试这一步：先拿一个正在用的 agent 文件，按首行、name 冒号、description、YAML 四项逐条核对，再用一个边界清晰的任务测它是否真的由子代理承接。
> 最近修订：2026-11-09

## 解决什么问题

你新建或修改了一个 Claude Code 子代理，却发现主代理总是自己把活干完，于是判断“Claude 不愿意委派”。这条线索指向另一种可能：agent 文件存在格式问题时被静默跳过，不报错，子代理从未被加载。本文给出一套先自检、再反例验证、最后固化的流程，避免把配置问题误判成能力问题。

## 适用与不适用

适用：

- 你已经在使用 Claude Code 子代理，并怀疑“主代理不肯委派”。
- 你刚新建或修改了 agent 文件，想确认它到底有没有被加载。
- 团队里反复出现“Claude 不肯委派”的抱怨，需要先排除配置问题。

不适用：

- 你还没有使用子代理功能。
- 任务本身边界不清、不适合委派，此时先改任务描述，而不是先查文件格式。
- 你需要官方目录路径、字段 schema 或完整 YAML 判定规则；原文没有给出，本文只提供自检与验证流程。
- 你注入缺陷后子代理照样能被调用，说明该版本可能已不再静默跳过，此条应降级为“历史坑”或删除。

## 前置条件

- 已在使用 Claude Code 子代理功能，并知道自己的 agent 文件放在哪个目录。原文未给出目录路径与字段 schema，需按你所用版本的官方文档核对。
- 有一个明确、边界清晰、本来就应该委派给子代理的任务，用来做固定测试。
- 改完文件后能够重新加载或重启，使改动生效；原文未说明加载时机，需自己确认。
- 能保留一份可正常工作的 agent 文件副本，用于反例实验。

## 操作步骤

1. **先建立“文件是否被加载”的基线。** 前提：你有一个固定任务。做法：在改动之前，用一个边界清晰、本来就该委派的任务测 3 次，记录几次由子代理承接；也可以让主代理列出可用子代理。预期：得到修复前的委派基线，避免修复后无法判断是否变好。

2. **逐条核对四个静默失败条件。** 前提：找到待检查的 agent 文件。按下面清单检查；YAML 是否合法可用你环境里的校验方式或编辑器提示，原文未给出具体判定。预期：能明确指出是否存在首行、name 冒号、缺 description、YAML 解析问题。

```text
[ ] 文件第一行恰好是 ---（前面没有空行、BOM、说明文字、注释）
[ ] name 字段的值里没有冒号 :
[ ] name 和 description 同时存在
[ ] frontmatter 的 YAML 能正常解析（缩进、引号、冒号后空格）
```

3. **按四项约束写一个最小骨架。** 前提：你要新建或修正 agent 文件。下面只是把原文四条约束落成形状，不是原文给出的示例；字段名请对照官方文档确认。预期：得到一个不触发已知四坑的 agent 文件。

```markdown
---
name: code-reviewer
description: 当需要对改动做静态审查时使用该子代理
---

（子代理的指令正文写在这里）
```

注意 `name: code-reviewer` 而不是 `name: reviewer:strict`——冒号是原文明确点名的第一个坑。

4. **做反例实验，确认这四条在你当前版本上确实成立。** 前提：你有一份能正常工作的 agent 文件副本，且实验不影响生产。两种做法按目的选：

   - **做法 A：复制副本做反例实验（推荐，先确认根因）。** 每次只注入一个缺陷：改名前加冒号 / 在首行前插一个空行 / 删掉 description / 破坏 YAML 缩进。每次重新加载后看该子代理是否消失或不再被调用。预期：若四类缺陷都能稳定复现“静默不加载”，说明这条清单在你的环境里有效；若注入缺陷后照样能被调用，说明该版本已不再静默跳过或已有报错，此条应降级为“历史坑”或直接删除。
   - **做法 B：直接修生产文件后复测（文件已坏、需要先恢复时用）。** 先修正明显问题，重新加载，再用同一个固定任务测 3～5 次，记录由子代理执行的比例。预期：子代理恢复被调用；但根因确认弱于做法 A，恢复后应补做 A。

   怎么选：要判断清单是否有效、是否该写进手册，选 A；只想尽快恢复工作，选 B，之后补 A。

5. **把验证过的检查固化成模板或提交前检查项。** 前提：第 4 步确认至少部分条件在你的环境成立。例如在仓库里放一个 `agents/_template.md` 骨架，并在 code review 清单里加一行“agent 文件首行为 `---`、name 无冒号、name+description 齐全、YAML 可解析”。预期：下次新建或修改 agent 文件时，格式问题在提交前被拦住。

6. **修正后做一次端到端确认。** 前提：文件已修正并重新加载。用一个本来就该委派的任务去触发，确认这次确实由子代理执行，而不是主代理自己顺手做完。预期：委派链路端到端可用。

## 怎么判断变好了

- **加载可见性**：注入缺陷后子代理是否“消失/不再被调用”。若四类缺陷都能稳定复现“静默不加载”，说明清单在你的环境里有效。
- **委派成功率**：同一定义清晰的任务，修复前后各跑 3～5 次，比较“由子代理执行”的比例；修复后应明显上升。
- **误判率下降**：团队里出现“Claude 不肯委派”这类抱怨时，先跑一遍格式自检，统计有多少抱怨其实由格式问题导致。这是把经验转化为可衡量收益的直接方式。
- **反向指标**：如果注入缺陷后子代理照样能被调用，说明该版本已不再静默跳过（或已有报错），此条应降级为“历史坑”或直接删除，不要写进手册。
- **最小试用方式**：取一个你已经在用的 agent 文件（没有就按第 3 步骨架新建一个职责非常明确的），记录基线，依次注入四个缺陷，全部恢复后重测同一个任务 3 次。半天内可完成。
- **试多久**：先用半天完成单文件最小试用；如果要在团队层面看误判率，至少覆盖多次“不肯委派”抱怨后再下结论（原文无团队数据，需自己积累）。

## 常见坑

- 把“子代理没被调用”一律归因于文件格式是过度概括：也可能是指令描述不清、任务不匹配，或模型自行判断无需委派。原文标题式写法本身就在描述这种误判。
- 原文在“when the yaml doesn't ...”处被截断，YAML 的具体判定条件缺失；不要把本文的清单当成完整 schema。
- 文件路径、字段定义、加载时机（是否需要重启）原文均未说明；照做前先核对官方文档，并用反例实验确认。
- 只在生产文件上改、不做反例实验，容易把别的原因误判为格式问题。
- 首行前有空行、BOM、说明文字或注释，都会破坏“第一行恰好是 `---`”。
- `name` 里含冒号是明确坑，例如不要写 `reviewer:strict`。
- 只写 `name` 不写 `description` 也会触发问题；两者要同时存在。
- 改完不重新加载就下结论，可能测到的还是旧文件。
- 没有基线就只测“修复后”，无法判断改善是否来自这次修改。
- 这条线索来自单一实践者推文，互动量低、无版本号、无错误日志、无“修复前 vs 修复后”对比；不要把它当官方结论。
