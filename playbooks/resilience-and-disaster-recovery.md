## 解决什么问题

这篇手册解决的是：当系统依赖第三方模型或自有基础设施，而模型供应商可能不可用、被限流、改变行为或涨价，基础设施也可能在故障时买不到容量时，团队如何事先定义恢复目标、准备降级与备援路径，并用演练和 eval 验证，而不是等故障发生后再补救。

材料来自一篇书籍节选，覆盖两块：灾难恢复（DR）中的 RPO/RTO 与四种 DR 模式，以及 AI 韧性与不确定性中的模型降级、备援、eval 回归、超时、多模型多供应商。原文给的是原则和流程步骤，没有可直接复制粘贴的命令、配置或提示词。

## 适用与不适用

适用：

- 能自行决定基础设施与灾备投入的团队。
- 对成本敏感，想用备份恢复、把备用基础设施复用为负载测试环境等方法降低容灾成本的团队。
- 把第三方模型嵌入产品关键路径的团队。
- 愿意先小范围试点，再决定是否全盘采用的团队。

不适用或要谨慎：

- 不能自行决定基础设施与灾备投入，只能等平台团队安排的团队。
- 期望直接复制粘贴命令、配置或提示词就能完成的人。原文没有给出现成配置。
- 不愿做演练、不愿维护 eval 回归用例的团队。
- DR 四种模式对多数团队投入偏重，原文也承认 RPO/RTO 越小，成本和复杂度越高。不要一上来就追求 Active-Active。

## 前置条件

- 能说清系统的关键程度，并能召集干系人（产品、业务、合规）一起谈目标。
- DR 侧：有可复用的 IaC（例如 Terraform 脚本）、跨站点数据复制能力、供应商容量预留能力，并知道哪些资源不可预留。
- AI 侧：有备用供应商账号与 API 通道、eval 工具与测试数据、token 数与流式输出的可观测数据、成本数据。
- 愿意把模型变更当作触发 eval 回归的事件。
- 接受一个前提：原文是书籍节选，Warm Failover、Multisite Active-Active、成本透明与供应商分析部分被截断；以下步骤只写材料中已给的做法。

## 操作步骤

材料建议先做 AI 韧性试点，再挑一个非关键服务做备份—恢复演练。因此下面分成做法 A 和做法 B。如果只能做一件，先做做法 A；如果团队当前最大风险是机房级故障，先做做法 B 的一次演练。

### 做法 A：AI 韧性试点

1. 选一个最依赖模型的 AI 功能，明确它在模型不可用时希望保留的最小功能。
   - 前提：产品、工程能一起判定哪些功能可降级、哪些不能。
   - 预期结果：得到“限制功能而不是整体挂掉”的降级目标，也就是 graceful degradation。

2. 加一层模型调用抽象，使替换模型不需要重写业务代码。
   - 前提：现有调用点能收拢到统一入口。
   - 预期结果：后续接备用通道和换模型时，改动集中在这一层。

3. 接一条备用供应商通道。原文举的例子是：通过 Azure 访问 OpenAI 模型，通过 Google 的 Gemini Enterprise Agent Platform 访问 Anthropic 模型。
   - 前提：接受备用通道上新模型上线可能有滞后。原文认为软件中嵌入的模型不必总用最前沿版本，这个滞后通常可接受。
   - 预期结果：主通道不可用时，能切到备用通道继续提供受限功能。

4. 为模型不可用、被限流、token 额度耗尽设计降级路径。
   - 前提：明确哪些功能可以降级、哪些功能必须报错或排队。
   - 预期结果：模型侧出问题时，用户看到的是功能受限，而不是整个产品崩掉。

5. 给模型调用补可观测性和超时策略。原文给出的技术手段是：按生成 token 数动态设置超时；监控流式输出，追踪响应何时开始返回，而不是等完整响应。
   - 前提：能拿到 token 数与流式事件。
   - 预期结果：能区分延迟来自供应商当时性能、被限流，还是 prompt 本身处理时间长；也更容易判断“是卡住了还是要生成很长输出”。

6. 维护一套针对 AI 行为的测试，由传统功能测试和 AI 评估工具（evals）两部分组成。为其整理一小组真实输入，作为“模型变更后必须跑”的回归清单。
   - 前提：有一组能代表真实场景的输入。
   - 预期结果：模型小改动带来的行为差异先在你这里暴露，而不是用户那里。原文的目标是“意外先发生在你这里，而不是用户那里”。

7. 把模型变更当作触发 eval 回归的事件。换模型时重新评估 prompt，即使同厂内换版本也一样。
   - 前提：能感知供应商模型变更，或至少能在升级模型版本时主动触发回归。
   - 预期结果：降低 prompt 处理结果被模型版本变化根本改变的风险。原文提到有模型在供应商未明确提示重大变更的情况下行为改变的报告。

8. 多模型、多供应商地构建，但不要在单个流程里混用多家模型。
   - 前提：先做到软件支持替换模型。
   - 预期结果：便于跟进最新模型、也便于在某个供应商涨价时快速换。反例要记住：在单个流程里混用 Anthropic、OpenAI、Gemini，任一不可用，整个流程就无法执行。

9. 定期做成本透明与供应商分析。
   - 前提：能观测模型调用成本。
   - 预期结果：从发现某供应商涨价到完成切换的工时应该下降，用来衡量“换供应商的门槛”是否真的降低。
   - 注意：原文在 Cursor 案例后即被截断，这一条只给了方向，没有给出具体做法。

### 做法 B：做一次备份—恢复 DR 演练

1. 定义 RPO 与 RTO，按工作负载分别定。
   - RPO（恢复点目标）= 数据最后一次备份/同步之后可容忍经过的最长时间，也就是可容忍的数据丢失时长；每小时备份一次，RPO 就是一小时。
   - RTO（恢复时间目标）= 事故后系统可容忍不可用的时长，包含从最近恢复点恢复数据、备好计算资源、把流量切到新站点所需的全部时间。
   - 与干系人讨论终端用户需求、监管与法律要求，再和实现成本、复杂度做平衡。原文例子：银行支付需要低 RPO/RTO，新客开户可以放宽。目标应高于任何 SLA 中规定的要求。
   - 前提：不同服务的 RPO/RTO 可以不同，允许混合使用多种 DR 模式。
   - 预期结果：每个服务有事先谈定的恢复目标。

2. 选择 DR 模式，从低到高演进。不确定就从左侧开始。原文列出四种模式：备份与恢复、Pilot Light、Warm Failover、Multisite Active-Active。
   - 备份与恢复：定期备份数据，备份必须在主站点以外；在故障站点 provision 基础设施，理想情况是自动化；从备份把数据恢复到故障站点新建的基础设施；把流量从主站点切到故障站点。前提：能接受较长 RTO、想压低成本；故障站点最好跑同一套核心技术栈，这样主站点 IaC（例如 Terraform 脚本）可以复用。若两站技术栈不同，则更必须定期测试 DR 流程。
   - Pilot Light：数据提交到主站点后持续复制到故障站点，可用数据库原生能力，也可应用层复制；在故障站点 provision 剩余基础设施，假设数据库和数据存储已在故障站点存在，只需 provision 计算等资源；流量切换到故障站点。前提：数据存储支持或能实现持续复制；改造既有系统时，如果所用数据产品不支持原生复制，复杂度会明显上升。适合公有云场景，因为不 provision 就不付费。
   - Warm Failover：数据持续复制到故障站点，并且在真正切换之前就预先 provision 至少一部分基础设施。常见做法是在故障站点优先为最关键的子系统准备容量，使核心功能有更短 RTO。注意：原文标注 how it works / when to use 在节选中被截断。原文还提示：各家厂商对 cold/warm/hot 的定义差异很大，通常只是 RTO 依次降低，不必纠结命名。
   - Multisite Active-Active：系统分布在两个或更多站点，写入可发到任意站点，数据在站点间持续复制，任意用户的流量可随时由任意站点服务。它绕开了“故障切换”这个动作，RTO/RPO 在四种模式中最低，但成本和复杂度显著更高。注意：how it works / when to use 同样被截断。

3. 按备份与恢复的 4 步做一次演练：异地备份、自动化 provision、恢复数据、切换流量。
   - 前提：选一个非关键服务，不要拿最关键业务做第一次演练。
   - 预期结果：全程计时并记录卡点；如果两站使用同一套自动化脚本，可以更接近原书说的“同一技术栈复用 IaC”。

4. 在规划里纳入“故障时基础设施未必能买到”的现实。
   - 向供应商预留容量：例如 AWS 上可付费预留 EC2 实例的可用性，预留费不论是否使用都要付，用的时候单价低于按需价格；注意并非所有云资源都能预留，例如 Lambda 调用量无法购买保证可用性。
   - 按关键性分配稀缺容量：如果保证可用性有成本、或基础设施总量有限，应优先给关键性更高的工作负载。这就是分服务设置不同 RTO/RPO 的实际用途。
   - 全冗余自建：如果复杂度与费用可接受，保持一整套冗余基础设施随时可用；缓解成本的办法是平时把冗余资源拿去做别的用途。原文案例：BankCo 把闲置备用工作站同时用作计算资源池，DR 站点启用时中止计算任务。也可把备用基础设施用作负载测试环境，DR 需要时随时中止。
   - 前提：知道哪些资源能预留、哪些不能。
   - 预期结果：故障发生时，关键工作负载更可能拿到容量。

5. 定期验证 DR 流程本身。
   - 备份恢复流程必须定期测试，不能只写在文档里。
   - 原文推荐做法：把“向二级站点做一次备份—恢复”并入其他例行活动，例如常规负载测试演练。
   - 前提：有一个可以定期触发的例行活动。
   - 预期结果：RPO 由备份频率决定；RTO 取决于恢复数据、provision 资源、切换流量三段中最慢的一段。全自动 + 小数据量可到分钟到小时级；手工流程、TB 级备份会显著拉长；如果还要临时采购硬件，可能拖到数周以上。

### 怎么选 A 和 B

- 先做 A：产品关键路径依赖第三方模型，且你担心模型不可用、被限流、行为变化或涨价。材料建议先小范围试 AI 韧性，再试 DR。
- 先做 B：你已经有明确的机房级或站点级故障风险，且能接受先拿非关键服务做一次演练。
- 两者都做时，按材料建议的顺序：先挑一个 AI 功能做降级/备援与 eval 回归，再挑一个非关键服务做一次备份—恢复演练并实测 RTO/RPO。

## 怎么判断变好了

最小试用方式：

- AI 韧性试点：1–2 周内，选一个最依赖模型的 AI 功能，先加一层模型调用抽象，接入一条备用供应商通道，并给调用加上按 token 数动态计算超时 + 流式首字节监控；如果模型不可用，走降级路径而不是报错。
- eval 回归试点：为这个功能整理一小组真实输入，配传统功能测试 + 一份 eval 用例，作为“模型变更后必须跑”的回归清单。
- DR 试点：选一个非关键服务，按备份与恢复的 4 步走一遍——异地备份、自动化 provision、恢复数据、切换流量——全程计时并记录卡点。

试多久：

- AI 韧性试点按 1–2 周可动。
- DR 侧至少做一次完整演练，之后把备份—恢复并入常规负载测试，定期重复。

可观察指标：

- DR 侧：实测 RTO，也就是从故障宣告到流量切回的时间，是否达到事先和干系人谈定的目标；RPO 是否等于备份频率；演练中自动化步骤占比与人工介入次数；切换后功能是否完整。
- AI 侧：eval 通过率与回归失败次数；供应商故障或限流时降级路径的触发成功率；超时错误率与 P99 延迟变化；模型替换后需要重写/重调的 prompt 数量；因模型供应商问题导致用户可见故障的次数。
- 成本/供应商侧：模型调用成本变化是否可被观测；从发现某供应商涨价到完成切换所需的工时，用来衡量“换供应商的门槛”是否真的降低。

注意：原文指出 RPO/RTO 不适合直接当 SLO，因为灾难发生频率太低、收集不到有意义的 SLI，但可以用“数据复制速度”这类生产上可程序化测量的指标定义相关 SLO。

## 常见坑

- 只在文档里写 DR 流程，不实际测试。原文明确说备份恢复流程必须定期测试。
- 手工 provisioning。它会拉长 RTO 并增加出错概率；理想情况是自动化。
- 故障站点与主站点技术栈不同，却又不加强定期测试。原文说两站技术栈不同时，更必须定期测试 DR 流程。
- 以为所有云资源都能预留。AWS EC2 实例可用性可以付费预留，但例如 Lambda 调用量无法购买保证可用性。
- 在单个流程里混用多家模型。Anthropic、OpenAI、Gemini 任一不可用，整个流程就无法执行。多模型多供应商的目标是“可替换”，不是把多个模型串在一条关键路径上。
- 换模型时不重新评估 prompt。即使同厂内换版本也一样，模型版本变化可能从根本上改变 prompt 的处理结果。
- 以为备用通道一定能立刻用到最前沿模型。原文认为软件中嵌入的模型不必总用最前沿版本，备用通道的滞后通常可接受。
- 忽略供应商自身的单一依赖。如果你的供应商自身只依赖某一家模型/API，你也会暴露在该模型的波动或突然涨价之下。原文案例：Cursor 在 2025 年因依赖 Anthropic 服务、而 Anthropic 调整定价，被迫向客户转嫁大幅涨价。
- 纠结 cold/warm/hot 命名。原文提示各家厂商定义差异很大，通常只是 RTO 依次降低，不必纠结命名。
- 对 RPO/RTO 只谈一个数。不同服务可以有不同的 RPO/RTO，也应允许混合使用多种 DR 模式。
- 一上来就做 Multisite Active-Active。它 RTO/RPO 最低，但成本和复杂度显著更高。
