# 让 agent 读懂你们的内部行话：按业务上下文生成一份可查询的术语表

> **未经实测**：本手册由 ai-work-radar 根据自动调研合并生成并持续修订，步骤尚未有人实际跑过。服务修订时基于自己保存的上一版重写，直接改这个文件会被覆盖；实测过的做法请写到 experiences/。
>
> 解决的问题：LLM 会误解组织内部的自造词、缩写，以及“认识但被用在陌生含义上的常见词”；用一份按业务上下文分片、经专家审校、可版本化刷新的术语表，把领域词汇变成可维护的上下文资产。
> 先试这一步：挑一个子系统，用它的文档或聊天记录让 LLM 抽术语并写定义，请领域专家审校后存进版本库，再拿两个真实任务对比带与不带术语表的效果。
> 最近修订：2026-11-12

## 解决什么问题

LLM 在组织里常犯的错误之一是读不懂内部行话：自造词、缩写，以及它认识、却被用在陌生含义上的常见词——最后这类最容易造成混乱。本手册给出一条低成本路径：用组织内现成文本让 LLM 抽出术语、写成词典式定义，经领域专家审校后，放到其他 LLM 能查询的地方，按业务上下文（bounded context）分片，并做版本控制和定期刷新，把专业词汇误解这个高发失败点，变成一份可增量改进的上下文资产。

## 适用与不适用

**适用**：组织有一定规模的内部文本（文档、邮件、聊天记录）；有愿意花时间审校的领域专家；存在多个 bounded context（大组织里同一个词在不同地方有细微不同的定义）；下游真的会把术语表接进去，比如指导代码生成，或在 harness 里放 sensor 检查用词。

**不适用或收益很小**：小团队；术语本来就公开、模型已经理解的领域；拿不到专家审校时间；以及没有下游消费场景——那样做出来的只是一份好看的文档，不会改变工作方式。

## 前置条件

- 能拿到组织内部文本：文档、邮件、聊天记录。音频/视频转写“在某些情况下有帮助”，但多数组织产生的文本已经够用，不必强求。
- 有一位愿意花时间审校的领域专家，审校环节不可省。
- 有一个 agent 能读取的存放位置。
- 这份术语表能接入版本控制，并由 agent 与人类按固定间隔复审。
- 下游有使用点：代码生成的命名约束、检查用词的 sensor 等。

## 操作步骤

**1. 选一个 bounded context 作为起点**
前提：清楚组织里有哪些子系统或上下文边界。优先选一个子系统连同它的周边文档，或者直接选一个代码库——代码库本身就特别值得单独做一份术语表，因为能看出术语在代码里怎么用。
预期结果：得到明确的语料范围和一个存放位置。不要一上来就做全公司。原文作者的原话是：劝所有人抵制做一份统一标准术语表的诱惑，他说自己还没见过这种办法成功；术语表的价值往往不在固定唯一定义，而在凸显它在不同上下文中的不同用法。

**2. 准备语料**
前提：有对这些文本的访问权限。来源可以是组织内的文档、邮件、聊天记录。
预期结果：一批能代表该上下文用词习惯的文本，够抽出一版术语候选即可。

**3. 让 LLM 抽术语**
要求它同时找两类东西：
- 单个词，以及“经常一起出现、构成一个有意义的术语”的多词短语；
- 对它来说是新的词，以及它认识、但被用在陌生含义上的词（原文特别强调后者最容易造成混乱）。

原文没有给出提示词原文，需要自己写。自行编写时，至少要覆盖上面这两类抽取目标；可以先把要求列成清单，再交给 LLM：

```
抽取目标（自行编写提示词时至少覆盖）：
1) 单词术语 + 经常共现、构成有意义术语的多词短语
2) 对模型而言的新词
3) 模型认识、但在本上下文中被用于陌生含义的常见词
输出：术语候选清单
```

预期结果：一份术语候选清单，其中包含“常见词被非常规使用”这一类。

**4. 让 LLM 生成定义**
要求：输出格式跟词典一致，重点是精确与简洁；同一个词有不同用法时，给出替代定义，并注明这些差异出现在什么上下文中。
预期结果：一份词典式草稿，一词多用处已经分列，并标注了上下文。

**5. 人类专家审校**
前提：找到该领域的专家。由专家审阅草稿，改掉 LLM 理解有偏差的地方。这一步不可省。调研建议的起点是 30–60 分钟审校时间，实际按语料规模调整。审校时记录改了哪些、为什么改——这本身就是后面判断流程是否在改进的指标。
预期结果：一版经过专家修正的定义，以及一份改动记录。

**6. 放到其他 LLM 能查的地方**
形态要求有两条：便于 LLM 查询；模型为找到某个词的含义所消耗的 token 尽量少。两种做法按术语表大小和手上的查询条件选：

- **做法 A：整份表放进上下文。** 适合表还小、或没有现成的按需查询手段时。简单，但表一大就吃 token。
- **做法 B：初始上下文只放“术语清单 + 指向定义的链接”**，模型在工作中只去取它真正需要的那些完整定义。适合表很大、token 预算紧张时；代价是需要一个能按链接取定义的存放与查询方式。

预期结果：模型能用尽量少的 token 拿到某个词在本上下文中的定义。

**7. 版本控制 + 排期刷新**
把术语表放进版本库，以便看到它随时间怎么变；设定日程，由 agent 和人类一起按固定间隔复审刷新。原文没有给刷新频率，需要自己定一个并写下来。
预期结果：术语表有变更历史，且有一个明确的复审节奏。

**8. 收录“不该用的词”**
术语表可以包含禁用词，并给出应当改用哪个词；废弃词用这种方式处理，条目里标明该词在什么时间段内有效。
预期结果：除了“该怎么说”，还能查到“不该怎么说、换成什么”。

**9. 有多个上下文时做跨表比对**
可以比较不同术语表，或让 LLM 去比较并描述用法的差异。拿代码派生的术语表和人写的文本对比，原文说“特别有启发性”。
预期结果：看清同一个词在不同上下文里的差异，而不是强行统一。

**10. 在下游用起来**
- 指导代码生成，让生成的软件里的命名贴合企业词汇；
- 在 harness 里放 sensor 检查这种用词，既查软件内部，也查用户界面；
- 注意生成代码或文档时可能引入新的 bounded context：面向客户的 UI 不应暴露内部名称，因为客户处在与“服务他们的那部分企业”不同的上下文。

预期结果：术语表被真实任务消费，而不是停留在文档里。

## 怎么判断变好了

**最小试用（调研建议 1–2 天）**：
1. 只选一个 bounded context，不要做全公司。
2. 取该上下文内 20–50 份文档/邮件/聊天记录（数量来自调研建议，原文只说“组织内材料”）。
3. 让 LLM 按第 3 步的两类目标产出术语候选清单。
4. 让 LLM 按词典格式写定义；一词多用时给替代定义 + 上下文说明。
5. 请领域专家审校，记录改了哪些、为什么改。
6. 存成 markdown 放版本库，同时按“术语 + 链接”的形态做一份精简索引版。
7. 挑两个该领域的真实任务（例如生成一段业务代码、写一份内部说明），各做两遍：一次不带术语表，一次把术语表放进上下文。

**可观察的指标**：
- **抽取质量**：专家认为“本该入表”的术语里，LLM 抽到了多少（召回）；专家审校时被改动的条目占比（定义准确率的反向指标）。
- **下游效果**：生成代码或文档中内部术语误用的次数；面向客户的产出中泄漏内部名称的次数；因术语理解错误导致的返工轮次。
- **成本**：每次刷新产生的 diff 大小、人工复审耗时；带术语表与不带术语表时，完成任务所消耗的上下文 token 与总时长的变化（用来验证“索引 + 链接”是否真的省 token）。
- **趋势**：如果第一轮专家改动很多、第二轮刷新后改动明显变少，说明这套流程在收敛；否则可能是语料或抽取目标设错了。

原文没有提供任何可对标的目标数值，以上阈值都要先在自己的场景里测一次基线再定。

## 常见坑

- **想做一份全公司统一的标准术语表。** 原文作者说没见过成功的案例。价值往往在凸显同一词在不同上下文的不同用法，而不是确定唯一定义。
- **跳过专家审校。** 抽取和定义都可能出错，审校不可省；审校与刷新成本原文没有量化，容易被低估。
- **只产出一份文档，不接下游。** 如果下游没有实际使用，收益不会体现；接进代码生成或 sensor 才算完整。
- **只抽“新词”，漏掉“认识但被用在陌生含义上的常见词”。** 原文说这类最容易造成混乱，而这恰恰很难用规则筛出来。
- **一开始就把全量术语表放进上下文。** 表大时 token 成本高，先用“术语清单 + 链接”，按需取全文。
- **忘记面向客户的 UI 是另一个上下文。** 内部名称泄漏到客户界面，是生成代码或文档时容易引入的新边界问题。
- **当成一次性产物。** 不版本化、不排期刷新，组织用语一变它就失效。

## 证据与来源

- **做法出处**：以上流程均来自调研《Bliki: Generated Glossary》（Martin Fowler 的 bliki 文章）。文中明确给出的做法包括：用组织内文本作语料、让 LLM 抽术语（含“认识但被用在陌生含义上的词”）并写词典式定义、由人类专家审校、放到其他 LLM 能查询的地方、表大时只放“术语清单 + 链接”、版本化并按 bounded context 分片、收录禁用词与废弃词、跨上下文比对，以及在下游用 sensor 检查代码与 UI 的用词。
- **性质**：这是经验型主张，不是实验报告。作者说，他和大组织里做 agent 的人交流时，“专业语言难处理”是个共同主题；致谢里提到 Eric Nagler 和 Unmesh Joshi 提供了实践经验。
- **没有数据**：文中没有任何数据、案例细节、提示词原文或工具配置；也没说明用哪个模型、术语表多大、刷新频率多高、“定期”是多久。唯一带强断言的判断是“我还没见过做单一标准术语表的成功案例”，这同样是作者个人观察，没有给出反例细节。
- **本手册中不属于原文的部分**：最小试用的具体参数（1–2 天、20–50 份文档、30–60 分钟审校、两个任务各做两遍）来自该调研报告给出的试用建议，不是原文数据；所有指标的阈值都需要自己测基线；第 3 步的清单块只是把原文的抽取要求整理成可核对的形式，不是原文提示词模板。
