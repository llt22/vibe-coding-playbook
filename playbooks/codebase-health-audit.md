# 让强模型做一次全库体检，并把不确定项交回人审

> **未经实测**：本手册由 ai-work-radar 根据自动调研合并生成并持续修订，步骤尚未有人实际跑过。服务修订时基于自己保存的上一版重写，直接改这个文件会被覆盖；实测过的做法请写到 experiences/。
>
> 解决的问题：如何把一次性的全仓库健康检查交给强模型，同时用分支、回归测试和人工复核控制误改风险。
> 先试这一步：先在一个有测试、非核心业务的中等规模仓库新建分支，原样跑一次全库体检提示词，统计它直接改了什么、列了哪些待审项。
> 最近修订：2026-11-10

## 解决什么问题

日常让 AI 写局部函数、修单个报错很常见，但很少有人让它通读整个项目做全局体检。这篇手册给出一个可直接复制的提示词：让能读全仓库的强模型找出坏掉的、不一致的、低效的、已无用的东西；它确定的部分直接修，不确定的列成清单交人复核。关键不是“让 AI 全自动改完”，而是把“确定修改”和“待审清单”分开，配合分支、回归测试和人工审 diff 控制风险。

## 适用与不适用

适用：
- 有一个能读取整个代码库并写文件的强模型环境（CLI 编程智能体、挂载仓库的 IDE 智能体等）。
- 仓库在版本控制下，能在独立分支上操作，便于回滚和逐条审 diff。
- 仓库有可运行的测试/构建命令，用于事后校验。
- 有人工时间处理“待审清单”和逐条审 diff。

不适用或需谨慎：
- 没有版本控制、没有测试/构建、也没有人工复核资源时，不建议直接跑。
- 不要在核心业务仓库的主分支上直接操作；至少先建分支或在非核心仓库试点。
- 仓库大到模型装不下全部上下文时，全库提示词会失真，应先缩小范围。
- 不能把它当成替代人工审计的“一次性全自动清理”；原文没有给出有效性数据，效果依赖模型能力和仓库规模。

## 前置条件

- 选定一个中等规模、有测试、非核心业务的仓库做试点。
- 新建独立分支，保留可回滚状态。
- 在仓库根目录启动智能体会话，确认它能读到全部源码，而不是只看到个别文件。
- 确认它有写文件权限，并准备好项目自带的测试/构建命令。
- 预留人工审阅时间：既要审已改 diff，也要逐条判断待审清单。

## 操作步骤

1. **选试点仓库并建分支。** 前提：中等规模、有测试、非核心业务；预期结果：所有修改可回滚，后续能逐条审 diff。

2. **在仓库根目录启动智能体会话，确认上下文范围。** 前提：智能体应能读取整个项目；预期结果：它能访问全部源码，而不是只读到个别文件。若读不全，先不要跑全库提示词。

3. **原样粘贴提示词，保持英文原文，不要拆成多轮。** 预期结果：它输出两部分——它已经直接改掉的内容（diff），以及它不确定、留给你复核的清单。

```text
Read this entire project and find everything that's broken, inconsistent, inefficient, or no longer needed. Fix what you're sure about and list the rest for me to review.
```

   注意：提示词里的 “everything”“inefficient”“no longer needed” 边界很宽；原文没有给范围约束，输出可能非常发散。

4. **让修改落在分支上，不直接落到主分支；跑一次项目自带的测试/构建做回归。** 前提：仓库有可运行的测试/构建命令；预期结果：能看到测试与构建结果，记录是否出现新失败。原文未提测试环节，这一步是使用时应自补的校验。

5. **把输出拆成两堆处理。** 已改的 diff 逐条过审；待审清单逐条判断是否成立、是否本轮处理。预期结果：只把通过审阅的修改合入；清单中判定成立但风险高的项，转成后续任务，不要混进本轮合入。

6. **范围选择：做法 A / 做法 B。**
   - 做法 A：按上面的提示词先对全库跑一次，适合中等规模、上下文装得下、有测试的仓库，用来做第一次盘点。
   - 做法 B：先限定目录或模块再复跑，适合仓库很大、上下文装不下，或第一次全库输出过于发散的情况。
   - 怎么选：第一次试点优先用 A 观察原始输出；如果输出发散、漏读或明显超出可审范围，改用 B 缩小范围再跑。原文没有给范围约束，B 是针对这一局限的保守做法。

7. **合入与后续。** 只合入通过审阅的修改；待审清单里成立但风险高的项作为后续任务处理，可再喂给同一提示词或另开小任务。预期结果：本轮变更可控，未处理项有明确清单，不会无声丢失。

## 怎么判断变好了

最小试用：
1. 选一个中等规模、有测试、非核心业务的仓库；
2. 新建分支，跑一次上面的提示词，记录耗时与消耗；
3. 不做任何筛选，先统计原始输出；再按操作步骤 5–7 人工处理；
4. 跑 2–3 个仓库后再判断，不要只凭一次感受下结论。

可观察指标：
- **待审清单有效率** = 人工判定成立的条目 / 清单总条目数。衡量它发现的问题质量。
- **直接修复采纳率** = 合入的 diff 数 / 它改动的 diff 总数。衡量 “Fix what you're sure about” 的可靠性。
- **回归情况**：跑测试与构建，看通过率是否下降、是否引入新失败。
- **人工审阅耗时**：与人工从零审计同一仓库的耗时对比，判断是否真的省事。
- **覆盖度抽查**：人工另找 3–5 个已知问题，看它是否命中，判断漏报程度。

判断改善的标准：修复采纳率明显高于回归问题出现的比例，且待审清单中有效条目占比过半、审阅总耗时低于人工自审，才值得固化成流程写进手册。原文没有给出任何指标或案例数据，以上验证方式需由使用者自建。

## 常见坑

- **把“全库”理解成“无边界”。** 提示词范围很宽，不限定目录或模块时输出容易发散；原文没有给范围约束。
- **把模型说的 “sure” 当成真确定。** 确定性判断由模型自行做出，大仓库上存在误改与遗漏风险，必须配合版本控制和人工审阅。
- **直接在主分支上跑。** 一旦误改，回滚和逐条审 diff 都会变困难；应先建独立分支。
- **不跑测试/构建就合入。** 原文未提回归测试，但这是使用时应自补的校验；没有测试时不要假定修改安全。
- **把待审清单当废纸。** 清单是这套做法的关键设计：不确定项显式转成人审队列，不能只看它改了什么。
- **一次提示词就想替代完整审计。** 原文只有一条提示词，推文正文还被截断，其余编号条目和流程说明缺失；配套 GitHub 仓库内容也未被抓取，无法确认是否有更完整流程。
- **把模型名称当成已核实事实。** 原文称 “Fable 5.2”，材料中无从核实，不应假定为某一具体产品；实际选择你能用的最强模型即可。
- **没有效果数据就全面推广。** 原文没有前后对比、缺陷发现率、误改率等支撑，先小范围试点。
