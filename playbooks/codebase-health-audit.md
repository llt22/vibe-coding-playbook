# 让强模型给代码库做体检，并把修复写成可执行计划

> **未经实测**：本手册由 ai-work-radar 根据自动调研合并生成并持续修订，步骤尚未有人实际跑过。服务修订时基于自己保存的上一版重写，直接改这个文件会被覆盖；实测过的做法请写到 experiences/。
>
> 解决的问题：解决的是：如何用 AI 对代码库做全局体检，并把确定修改、待审清单和可执行计划分开，控制误改与返工风险。
> 先试这一步：先在一个有可运行 build/test/lint 的非核心仓库建独立分支，跑一次 `/improve quick` 或原提示词，只挑 1 条高置信、小工作量的发现生成计划，人工审完再交给执行端。
> 最近修订：2026-11-12

## 解决什么问题

日常让 AI 写局部函数、修单个报错很常见，但很少有人让它通读整个项目做全局体检。这篇手册给出两条可落地的路径：一条是直接复制的全库提示词，让能读全仓库的强模型找出坏掉的、不一致的、低效的、已无用的东西，确定的直接改、不确定的列清单；另一条是用 `shadcn/improve` 这类 Agent Skill，让强模型只做审计并写出自包含的修复计划，把执行交给更便宜的模型或任意 agent，再由顾问复核。关键不是“让 AI 全自动改完”，而是把“确定修改 / 待审清单 / 可执行计划”分开，配合分支、回归测试和人工审 diff 控制风险。

## 适用与不适用

适用：
- 有一个能读取整个代码库并写文件的强模型环境（CLI 编程智能体、挂载仓库的 IDE 智能体等）。
- 仓库在版本控制下，能在独立分支上操作，便于回滚和逐条审 diff。
- 仓库有可运行的 build/test/lint 命令，用于事后校验；做法 B 的验证门槛尤其依赖它。
- 有人工时间处理“待审清单”、逐条审 diff，以及审阅 `plans/`。
- 想用做法 B 时，agent 需支持 Agent Skills 格式；加 `--issues` 需要 GitHub 写入权限。

不适用或需谨慎：
- 没有版本控制、没有测试/构建、也没有人工复核资源时，不建议直接跑。
- 不要在核心业务仓库的主分支上直接操作；至少先建分支或在非核心仓库试点。
- 仓库大到模型装不下全部上下文时，全库提示词会失真，应先缩小范围。
- 不能把它当成替代人工审计的“一次性全自动清理”；原文没有给出有效性数据，效果依赖模型能力和仓库规模。
- 做法 B 只适用于代码库类工作，非编码任务无法直接照搬；缺少测试/lint 的仓库里，验证门槛这一核心约束会退化。
- 做法 B 的平台绑定：需支持 Agent Skills 格式的 agent；本报告只依据 README，未读 skill 源码，也未读示例计划全文。

## 前置条件

- 选定一个中等规模、有测试、非核心业务的仓库做试点。
- 新建独立分支，保留可回滚状态。
- 在仓库根目录启动智能体会话，确认它能读到全部源码，而不是只看到个别文件。
- 确认它有写文件权限，并准备好项目自带的 build/test/lint 命令。
- 预留人工审阅时间：既要审已改 diff、待审清单，也要审 `plans/` 中的计划。
- 做法 B：安装 skill，并确认 agent 支持 Agent Skills 格式；如果仓库里存在 `docs/adr/`、PRD、`CONTEXT.md`、`DESIGN.md`、`PRODUCT.md`，让审计读到它们，避免把已决定的权衡重新报成问题。
- 做法 B 的执行端：准备一个更便宜/更小的模型或任意 agent；`/improve execute` 会在隔离的 git worktree 里启动 executor 子 agent，合并仍由你决定。

## 操作步骤

先做共同准备：

1. **选试点仓库并建分支。** 前提：中等规模、有测试、非核心业务；预期结果：所有修改可回滚，后续能逐条审 diff。

2. **在仓库根目录启动智能体会话，确认上下文范围。** 前提：智能体应能读取整个项目；预期结果：它能访问全部源码，而不是只读到个别文件。若读不全，先不要跑全库提示词。

**怎么选做法 A / 做法 B：** 做法 A 更快，让强模型直接改，适合第一次盘点、仓库规模中等、上下文装得下、你愿意逐条审 diff。做法 B 多一层计划审阅，强模型只审计和写计划，执行交给便宜模型或任意 agent，适合仓库有可运行的 build/test/lint、想把判断与执行分开、需要每步有验证门槛和 STOP 条件的场景。两者也可以组合：先用做法 A 看全库原始输出，再把选中的发现用做法 B 写成计划并交给执行端。

### 做法 A：直接全库提示词

3. **原样粘贴提示词，保持英文原文，不要拆成多轮。** 前提：智能体已能读取整个项目；预期结果：它输出两部分——它已经直接改掉的内容（diff），以及它不确定、留给你复核的清单。

```text
Read this entire project and find everything that's broken, inconsistent, inefficient, or no longer needed. Fix what you're sure about and list the rest for me to review.
```

   注意：提示词里的 “everything”“inefficient”“no longer needed” 边界很宽；原文没有给范围约束，输出可能非常发散。

4. **让修改落在分支上，不直接落到主分支；跑一次项目自带的测试/构建做回归。** 前提：仓库有可运行的测试/构建命令；预期结果：能看到测试与构建结果，记录是否出现新失败。原文未提测试环节，这一步是使用时应自补的校验。

5. **把输出拆成两堆处理。** 已改的 diff 逐条过审；待审清单逐条判断是否成立、是否本轮处理。预期结果：只把通过审阅的修改合入；清单中判定成立但风险高的项，转成后续任务，不要混进本轮合入。

6. **范围缩小。** 第一次试点优先按上面的提示词对全库跑一次；如果输出发散、漏读或明显超出可审范围，限定目录或模块再跑。前提：全库输出不可控或上下文装不下；预期结果：范围更清楚，待审清单更可处理。

### 做法 B：用 `shadcn/improve` 做审计—计划—执行

7. **安装 skill。** 前提：目标是 git 仓库，agent 支持 Agent Skills 格式；预期结果：skill 可用。在仓库或全局环境执行：

```bash
npx skills add shadcn/improve
```

8. **首次审计，先用 quick 档控制成本。** 前提：仓库有可跑通的 build/test/lint 命令；预期结果：返回一张 findings 表，列含 `#`、`Finding`、`Category`、`Effort`、`Confidence`。在仓库里打开 agent 后运行：

```text
/improve
/improve quick
```

   其他可选档位：

```text
/improve deep                 exhaustive: every package, every category
/improve security             focused audit (also: perf, tests, bugs, ...)
/improve branch               audit only what the current branch changes
/improve next                 feature suggestions — where to take the project
/improve plan <description>   skip the audit, spec one thing
/improve review-plan <file>   critique and tighten an existing plan
/improve ... --issues         also publish plans as GitHub issues
```

   审计覆盖九个类别：correctness、security、performance、test coverage、tech debt、dependencies & migrations、DX、docs、direction（功能建议，每条必须引用仓库自身证据）。流程为：Recon（映射仓库技术栈、惯例、精确的 build/test/lint 命令；若存在 `docs/adr/`、PRD、`CONTEXT.md`、`DESIGN.md`、`PRODUCT.md` 则一并读取）→ Audit（并行子 agent 分头审九类）→ Vet（顾问自己重读每个被引用的位置，剔除误报、修正错误归因、记录驳回理由）→ Prioritize（按 leverage = impact ÷ effort，以 confidence 加权排序）→ Plan。

9. **挑选要立项的发现。** 用自然语言回复编号即可，例如 `plan 1, 3 and 5`。前提：先看 findings 表里的 Effort 和 Confidence；预期结果：每条被选中的发现生成一个 `plans/` 文件，另有一份 index，包含推荐顺序和依赖图。计划是纯 markdown，任何 agent 或人都能接手。

10. **人工审阅 `plans/`。** 原文明确说这些计划「meant to be reviewed」，这一步不要跳过。按三条规范逐项检查：
   - **自包含**：所有上下文内联——精确文件路径、当前状态代码摘录、仓库惯例（附一个范例文件）、已验证的命令；不写「如上文所述」。
   - **验证门槛**：每一步以一条命令加其期望输出结尾，done criteria 必须机器可判定，执行器不需要自己判断是否成功。
   - **硬边界**：显式列出范围外清单，并写 STOP 条件（「若 X，停下并报告」），避免弱模型在现实与计划不符时自由发挥。
   另外确认每份计划打上了写作时的 git commit，执行器动手前先做一次机械的 drift check。预期结果：计划可以交给一个从未见过顾问会话、可能小得多的模型。

11. **交给执行端。** 两种方式：把计划丢给任意 agent（例如让它 `implement plans/001-*.md`），或让 skill 代派：

```text
/improve execute 001
```

   后者会在隔离的 git worktree 里启动一个更便宜的 executor 子 agent，拿到计划后执行，再由顾问角色像 tech lead 一样复核：重跑每条 done criterion、检查范围合规、对照意图读 diff，给出 approve（合并仍由你决定）/ 退回修改（最多 2 轮）/ block 并回头改计划。前提：执行端能读计划；预期结果：有明确三态结论，不自动合并。

12. **下一次会话做清账。** 运行：

```text
/improve reconcile
```

   验证已完成（DONE）的计划是否仍然成立、排查被 BLOCKED 的计划并绕过障碍重写、刷新已漂移的计划、退役被别人顺手修掉的发现。预期结果：backlog 不是一次性输出，而是需要持续维护的活对象。

13. **PR 前做范围化审计。** 运行：

```text
/improve branch
```

   可选：加 `--issues`，以同样的自包含正文把计划发布成 GitHub issue（需 GitHub 写入权限）。

### 合入与后续

14. **只合入通过审阅的修改或执行结果。** 待审清单或计划中成立但风险高的项，转成后续任务，不要混进本轮合入。预期结果：本轮变更可控，未处理项有明确清单，不会无声丢失。

15. **把 skill 的硬规则当作给 agent 设定边界的参考。** 原文列出的硬规则包括：从不修改源码，唯一写入是 `plans/`；执行器只在一次性 worktree 里改动；从不运行会改变工作树的命令，只读、搜索与只读分析；从不复现密钥值，只报位置和凭证类型并建议轮换；被要求直接实现时拒绝，指向计划或提供 `execute`。预期结果：审计与执行的动作边界清楚，减少误改和泄密风险。

## 怎么判断变好了

最小试用（先跑一个周期）：
1. 选一个中等规模、build/test/lint 能跑通的非核心仓库，在干净分支上操作。
2. 做法 A：跑一次上面的提示词，记录耗时与消耗；不做任何筛选，先统计原始输出；再按操作步骤 5–6 人工处理。
3. 做法 B：安装后跑 `/improve quick`，只挑 1 条 `Confidence=HIGH`、`Effort=S/M` 的发现生成计划；人工按三条规范逐项检查这份计划；用 `/improve execute <plan>` 或手动把计划交给一个更便宜/更小的模型执行，记录过程。
4. 与基线对比：同一仓库、同类任务，用单一强模型直接改一遍。
5. 跑 1 个仓库的 1 个计划周期后，再在 2–3 个仓库重复，不要只凭一次感受下结论。

可观察指标：
- **待审清单有效率** = 人工判定成立的条目 / 清单总条目数。衡量它发现的问题质量。
- **直接修复采纳率** = 合入的 diff 数 / 它改动的 diff 总数。衡量 “Fix what you're sure about” 的可靠性。
- **回归情况**：跑测试与构建，看通过率是否下降、是否引入新失败。
- **人工审阅耗时**：与人工从零审计同一仓库的耗时对比，判断是否真的省事。
- **覆盖度抽查**：人工另找 3–5 个已知问题，看它是否命中，判断漏报程度。
- **计划可执行率**：执行器无需追问、无需自行补充上下文即可完成的比例。
- **一次通过率与退回轮次**：原文上限 2 轮；另记 block 的发生频率与原因分类。
- **验证门槛的可靠性**：gate 报通过但实际有问题的次数（假阳性），以及人工复核发现漏检的次数。
- **审计信噪比**：vet 之后进入 findings 表、但被人工判为无效的条目占比；原文未给出该数字，需要你自己统计。
- **成本**：强模型 token 消耗与弱模型 token 消耗之和，对比全程使用强模型。
- **周期**：从审计到合并的墙钟时间；以及一个周期后 `/improve reconcile` 中 DONE 的占比、BLOCKED 的数量。

判断改善的标准：
- 做法 A：修复采纳率明显高于回归问题出现的比例，且待审清单中有效条目占比过半、审阅总耗时低于人工自审，才值得固化成流程写进手册。
- 做法 B：若一次通过率高（多数计划无需退回）、验证门槛假阳性接近零、且总成本低于单强模型基线，则可从 quick 档推进到常规 `/improve` 并扩大适用范围；若退回或 block 频繁，优先怀疑计划写作的三条规范没有落实（尤其是验证门槛与 STOP 条件），而不是直接否定这套分工。
- 两套做法原文都没有给出完整的量化效果数据；以上验证方式需由使用者自建。

## 常见坑

- **把“全库”理解成“无边界”。** 提示词范围很宽，不限定目录或模块时输出容易发散；原文没有给范围约束。
- **把模型说的 “sure” 当成真确定。** 确定性判断由模型自行做出，大仓库上存在误改与遗漏风险，必须配合版本控制和人工审阅。
- **直接在主分支上跑。** 一旦误改，回滚和逐条审 diff 都会变困难；应先建独立分支。
- **不跑测试/构建就合入。** 原文未提回归测试，但这是使用时应自补的校验；没有测试时不要假定修改安全。
- **把待审清单当废纸。** 清单是这套做法的关键设计：不确定项显式转成人审队列，不能只看它改了什么。
- **一次提示词就想替代完整审计。** 原文只有一条提示词，推文正文还被截断，其余编号条目和流程说明缺失；配套 GitHub 仓库内容也未被抓取，无法确认是否有更完整流程。
- **把模型名称当成已核实事实。** 原文称 “Fable 5.2”，材料中无从核实，不应假定为某一具体产品；实际选择你能用的最强模型即可。
- **没有效果数据就全面推广。** 原文没有前后对比、缺陷发现率、误改率等支撑，先小范围试点。
- **仓库没有可运行的 build/test/lint 就上 `/improve`。** 验证门槛是做法 B 的核心约束，缺少它这套流程会退化。
- **计划没写自包含、验证门槛和 STOP 条件就交给弱模型。** 弱模型会在现实与计划不符时自由发挥；退回或 block 频繁时，先检查这三条规范，而不是直接否定分工。
- **跳过人工审阅 `plans/`。** 原文明确说计划是给人审的，approve 后合并仍需人工决定；不要把 `execute` 的三态结论当成自动合并。
- **忘记 `reconcile`。** backlog 会漂移，DONE 可能不再成立，BLOCKED 需要绕过障碍重写；把它当一次性输出会留下过期计划。
- **把九类并行、vet 压误报、leverage 排序当成已验证效果。** 这些只是 README 的作者主张，没有量化证据；需要自己统计审计信噪比和退回率。
- **把平台兼容性当已核实。** 做法 B 需支持 Agent Skills 格式；把计划交给 Cline 等其他执行端是推断，原文没有验证，试的时候要自己确认兼容性。

## 证据与来源

本手册有两类来源，证据强弱不同。

**做法 A：全库提示词。** 来自调研《@chenchengpro: Prompts to use with Fable 5.2 to improve your codebase.》。该调研记录了一条可逐字复制的提示词，标题为 _Full health check_，并注明出处为 Anthropic 的 Alex Albert；推文还挂了一个 GitHub 链接卡片 `shadcn/improve`，描述为“用你最强的模型审计代码库并写计划”。互动数据为 403 赞、18 转发、8 回复。提示词原文、出处署名、链接卡片和互动数据来自原推文；“这样能改进你的代码库”只是作者主张，推文没有提供前后对比、缺陷发现率、误改率之类的数据。原文正文被截断，只保留了第 1 条提示词；链接的 GitHub 仓库内容未被抓取，无法确认它是否提供更完整的提示词集与执行流程；模型名称 “Fable 5.2” 在材料中无从核实。

**做法 B：`shadcn/improve` 的审计—计划—执行流程。** 来自调研《shadcn/improve》。该报告依据仓库 README，给出了完整安装命令、命令清单、五步使用流程、计划的三条写作规范、skill 的硬规则，并链接了一份真实产出的示例计划（`examples/001-extract-shadow-config-resolution.md`）。另有一次对 shadcn/ui 的示例运行，findings 表包含两条具体条目（`search.ts` / `view.ts` 中 shadow-config 重复且已漂移，`search.ts:31` 有 TODO；`migrate-icons.ts:168` 存在 O(n²) 的图标迁移），以及一条被驳回并记录理由的条目（`[SEC-01] https_proxy` 被判定为 by-design，不是 finding）。仓库当前 11,136 stars、当日 +361（来自指标，非 README 内容）。这些是有依据的部分。

需要区分证据强弱：
- 做法 B 中“九类并行子 agent 的覆盖面、vet 阶段能有效压掉误报、leverage 排序的合理性，以及‘面向最弱执行者写作’能提升可执行性”没有量化证据（修复率、返工率、误报率、强/弱模型成本对比一概没有），只是作者主张。
