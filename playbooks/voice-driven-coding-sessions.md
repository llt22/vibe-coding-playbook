# 一边做饭一边口述需求：用语音把一个小功能推到可审的 PR

> **未经实测**：本手册由 ai-work-radar 根据自动调研合并生成并持续修订，步骤尚未有人实际跑过。服务修订时基于自己保存的上一版重写，直接改这个文件会被覆盖；实测过的做法请写到 experiences/。
>
> 解决的问题：心里已经想清楚一个小功能时，怎么用语音口述需求驱动编码智能体在本地改代码，自己只在本地预览和 PR 审阅处介入，细节阶段再切回键盘。
> 先试这一步：挑一个自己已经想清楚的小功能，在本地仓库先打字发 `Start dev server and open in browser` 拿到预览，再点 Codex 标签页里话筒右边那个「Start new voice chat」，把需求连边界条件一起口述一遍。

## 解决什么问题

心里已经想清楚一个小功能，但不想从头到尾坐在键盘前敲需求；希望用嘴把需求讲一遍，让编码智能体在本地改代码，自己只在有预览可看、有 PR 可审的地方介入。

原文作者用 ChatGPT 桌面端 Codex 标签页的「语音对话模式」（模型为 GPT-6 Astra High），对着本地跑着的博客开发环境口述需求，几乎全程用语音做完了博客新功能「Newsletters 索引页」：一边做晚饭一边说需求，模型在本地改代码并给出本地预览；功能大致完成后开 PR，切回键盘审阅收尾，最后合并上线。

它真正解决的问题不是「语音能写代码」，而是：加上视觉预览、又能随时切回键盘打字/粘贴之后，语音驱动编码智能体变成了一种强得多的交互方式。它的杀手级特性是多任务——做饭时还能干活。

## 适用与不适用

适用：

- 自己心里已经有清楚构想、且足够简单的一个功能（规模可参照原文：一个新数据模型 + migration + 视图 + 模板 + 一个导入脚本）。
- 本地已经有能跑起来的开发环境和已 checkout 的仓库。
- 环境允许出声、又不打扰别人（作者在家工作；他明确说不会在共享办公空间里对电脑说话）。
- 你希望能一边做别的事（原文是一边做晚饭），一边瞄本地预览、用语音给设计反馈。

不适用 / 必须回到键盘：

- 细节阶段：粘贴示例、粘贴报错信息、直接选中要改的代码或功能，打字比用嘴描述更高效。
- 需要新建 API key、配置私有仓库凭据之类的活（原文作者说这类活他「知道自己得坐到键盘前一会儿」）。
- 需求本身没想清楚，或需要反复粘贴报错和示例。
- 作者自己的定位：它更适合多任务，不是他的日常主力（daily driver）。

## 前置条件

- 本地已 checkout 自己要改的代码仓库（原文是自己的 Django 博客项目），本地开发环境能跑起来。
- 装了 ChatGPT 桌面应用，能打开 Codex 标签页。
- 有视觉预览：能随时让模型展示新页面，用肉眼跟着看它的进度。原文说，加上视觉预览、并且能在需要时用键盘打字/粘贴，才让它比手机上的纯语音强得多。
- 键盘作为兜底输入通道：粘贴示例、粘贴报错、选中代码。
- 本地写文件和 Git 权限（建分支、开 PR）。
- 语音阶段做不完的环节要留出键盘时间：从私有 GitHub 仓库导入时需要新建 API key。
- 环境能出声，且不打扰别人。

## 操作步骤

### 做法 A：语音为主，键盘收尾（原文路径）

1. 在本地仓库上起会话，先用打字输入这句（原文原样）：

```text
Start dev server and open in browser
```

   前提：本地开发环境能跑起来。预期：拿到站点预览，之后可以随时让模型展示新页面，用肉眼跟着看它的进度。

2. 点击「Start new voice chat」按钮。原文特意强调：不是那个话筒按钮，是它右边那个。

3. 把笔记本放到厨房（原文：set my laptop up in the kitchen），一边做饭一边说话。前提：环境允许出声。

4. 用口语把要建的东西讲清楚，允许口语不流畅。原文的口述里包含大量「um」「oh, hold on」「no-」这类停顿和改口，模型仍然听懂了。口述时要把边界条件说出来——原文里起作用的部分正是这些：
   - 这是一种新的内容类型，需要新建一个模型；
   - 不要出现在 tag 页和博客首页，但要出现在按日期的归档页（例如 9 月 19 日那天发的 newsletter 要显示出来）；
   - 要能被搜索；Substack 的那些不索引（它们只是博客上已有内容的拷贝），按月发的那些含独有内容、公开一个月后要进搜索结果。

   预期：模型能从不流畅的转录里推断出完整的功能规格。

5. 让模型自己干活：它会回复、偶尔反问澄清，然后动手改代码。语音阶段持续了大约半小时——正好是做一顿晚饭的时间（作者自述）。期间可以瞄一眼厨房里的本地预览，用语音反馈设计。

6. 判断功能差不多完整后，让 Codex 建分支并开一个 pull request。预期：代码到「几乎可以上线」的程度。

7. 在 GitHub 的 PR 界面审代码。原文发现一条导入脚本用 subprocess 调 Git，而他要从私有 Git 仓库导入，认为走 API 更合适，于是切回键盘打字，让 Codex 把这条改成基于 API 的导入；同时顺手改了几处公开页面的展示。预期：改完之后可以合并。

8. 再花大约半小时打字提示，直到满意，合并 PR 部署到生产。

语音阶段实际产出的东西（可作为试点规模的参照）：

- 一个新的 Django 模型 + migration，以及对应的 Django Admin 配置；
- 四个能跑的导入：最近的 Substack 条目走 RSS；其余 Substack 条目走它们的未公开 API（模型直接试了 `/api/v1/archive`，再自己搜出分页办法，找到 Karen Spinner 的一篇文章）；已发布的月度 newsletter 来自 `simonw/monthly-newsletter-archive` GitHub 仓库；最近一期私有赞助者 newsletter 来自一个私有仓库；
- `/newsletters/` 和 `/newsletters/2026/` 公开归档页；
- newsletter 出现在日和月的归档页，但不出现在 tag 页和首页；
- 每周 Substack newsletter 链回 Substack，归档的月度 newsletter 有自己的页面；
- 接入站点搜索。

### 做法 B：只把语音用在「讲需求 + 看预览给反馈」

把语音缩到两个环节：口述需求与边界条件、看着本地预览给设计反馈；编码细节、粘贴报错、选中代码、配凭据全部打字。

说明：这种做法是原文边界判断（细节阶段打字更高效）的自然延伸，原文没有单独验证过，原文走的是做法 A。

怎么选：

- 需求清楚、能一边干别的活、环境能出声，选做法 A。
- 环境不方便出声，或任务里有大量粘贴报错、选中代码、密钥配置，选做法 B，或者干脆全程打字。

## 怎么判断变好了

- 最直接的指标：语音阶段结束时，代码是否到了「几乎可以上线」（almost ready to ship）的程度——这是原文作者的标准。
- 两段时间：从开口到开 PR 用了多久，从 PR 到合并用了多久。原文的自述参照是各约半小时。
- 审阅时你实际改了多少：原文只改了导入机制和几处展示细节，共两类问题。如果改动量大到接近重写，说明这个任务不适合语音驱动。
- 模型反问澄清的次数，以及是否答对：原文里它偶尔提问就动手了，没有反复问同一件事。
- 上线后功能是否按预期工作。原文可核查的锚点：`/newsletters/` 索引页和某期月度 newsletter 的页面确实存在，PR 上有他审阅时追加的 commit；归档页显示规则和搜索集成是否真的生效。

最小试用方式：

1. 挑一个自己已经想清楚的小功能，规模参照原文：一个新数据模型 + migration + 视图 + 模板 + 一个导入脚本。不要拿需求模糊或跨系统的大改造来试。
2. 在本地 checkout 起会话，先打字发原文那句 `Start dev server and open in browser`，确认能看到预览。
3. 点「Start new voice chat」（话筒右边那个），把设备放在你能顺手看到预览、又能一边干别的活的地方。
4. 对着它把需求讲一遍，允许停顿和改口，讲清「要什么、不要什么、要出现在哪些页面、要不要被搜索到」这类边界条件。
5. 让模型自己改代码并开 PR；在 PR 界面审，发现不对的地方切回键盘打字让它改，直到可以合并。

试多久：原文只给了单一案例的时长尺度（语音约半小时 + 打字约半小时）。就按这个规模做一次试点、走完到 PR 与合并的完整来回，用上面的指标判断；原文没有对照组，也没有量化收益，所以适合试点而非直接采用。

## 常见坑

- 点错按钮：原文特意强调是「Start new voice chat」，不是它左边那个话筒按钮。
- 以为语音能覆盖全部：细节阶段打字更高效；需要新建 API key 这类环节必须回到键盘。
- 拿需求模糊或跨系统的任务来试：原文的成功前提是作者对要建什么心里已经有清楚构想，且该功能足够简单；换成他自己都不清楚的需求，原文没给出结论。
- 环境不合适：作者说不会在共享办公空间里对电脑说话。
- 没有预览的纯语音场景：原文没有背书；视觉预览是它比手机纯语音强得多的关键条件之一。
- 指望「主动推进」：原文没有描述任何由时间、事件或状态触发、无人干预持续完成的工作——整段流程都需要你开口说话或打字。
- 忽略界面会变：具体依赖 Codex 标签页、语音模式、原文提到的具体模型（GPT-6 Astra High），这些都会变。
