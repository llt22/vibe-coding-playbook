# 把需求说出来：用语音驱动编码智能体做出可审的版本

> **未经实测**：本手册由 ai-work-radar 根据自动调研合并生成并持续修订，步骤尚未有人实际跑过。服务修订时基于自己保存的上一版重写，直接改这个文件会被覆盖；实测过的做法请写到 experiences/。
>
> 解决的问题：如何用语音口述需求、配合视觉预览、反问澄清和键盘收尾，让编码智能体完成一个小功能或应用 v1，并交付可预览、可审的版本。
> 先试这一步：挑一个已想清楚的小功能，先用语音把需求、边界条件和视觉参考讲全，让编码智能体先反问澄清，再在本地改代码并给出可预览、可审的版本。
> 最近修订：2026-10-26

## 解决什么问题

心里已经想清楚一个小功能，但不想从头到尾坐在键盘前敲需求；希望用嘴把需求讲一遍，让编码智能体在本地改代码，自己只在有预览可看、有 PR 可审的地方介入。两种语音用法可以选：一边做别的事一边口述、看本地预览给反馈（原文 A 路径）；或先录 1–5 分钟把细节讲全、附视觉参考、让代理反问澄清后再产出 v1（@nutlope 流程）。它真正解决的不是“语音能写代码”，而是把语音当成需求输入通道，把视觉预览、键盘兜底和 PR 审阅接在后面，让编码智能体在你能监督的范围内推进。

## 适用与不适用

适用：

- 自己已经想清楚、且足够简单的一个功能。A 的规模参照原文：一个新数据模型 + migration + 视图 + 模板 + 一个导入脚本。
- 本地有能跑起来的开发环境和已 checkout 的仓库（A）。
- 环境允许出声、不打扰别人（A；作者明确说不会在共享办公空间对电脑说话）。
- 你希望能一边做别的事，一边瞄本地预览、用语音给设计反馈（A）。
- B 还适合：有一个小应用想法，能用 1–5 分钟详细口述讲全，并能提供截图或视觉参考；你愿意先让代理用 grill-me 类技能反问澄清，再产出 v1。原文只展示到“收到 v1”，没有说明迭代、验收和部署。

不适用 / 必须回到键盘：

- 细节阶段：粘贴示例、粘贴报错信息、直接选中要改的代码或功能，打字比用嘴描述更高效。
- 需要新建 API key、配置私有仓库凭据之类的活。
- 需求本身没想清楚，或需要反复粘贴报错和示例。
- 复杂生产系统或严格验收场景：B 的原文没有案例结果、配置、提示词或质量数据，不能据此推断同样有效。
- 作者自己的定位：A 更适合多任务，不是他的日常主力。

- A：本地写文件和 Git 权限（建分支、开 PR）。
- A：语音阶段做不完的环节要留出键盘时间：从私有 GitHub 仓库导入时需要新建 API key。
- A：环境能出声，且不打扰别人。
- B：能使用 WisprFlow 录音转写；原文只点名 @WisprFlow，未给安装与配置。

## 操作步骤

先选做法：A 是边做边说、看本地预览、键盘收尾；B 是先讲全需求和视觉参考、让代理反问澄清、再产出 v1。两者也可以按阶段组合，见本节末尾“怎么选”。

### 做法 A：语音为主，键盘收尾（原文路径）

1. 在本地仓库上起会话，先用打字输入这句（原文原样）：

```text
Start dev server and open in browser
```

前提：本地开发环境能跑起来。预期：拿到站点预览，之后可以随时让模型展示新页面，用肉眼跟着看它的进度。

2. 点击“Start new voice chat”按钮。原文特意强调：不是那个话筒按钮，是它右边那个。

3. 把笔记本放到厨房（原文：set my laptop up in the kitchen），一边做饭一边说话。前提：环境允许出声。

4. 用口语把要建的东西讲清楚，允许口语不流畅。原文的口述里包含大量“um”“oh, hold on”“no-”这类停顿和改口，模型仍然听懂了。口述时要把边界条件说出来——原文里起作用的部分正是这些：
   - 这是一种新的内容类型，需要新建一个模型；
   - 不要出现在 tag 页和博客首页，但要出现在按日期的归档页（例如 9 月 19 日那天发的 newsletter 要显示出来）；
   - 要能被搜索；Substack 的那些不索引（它们只是博客上已有内容的拷贝），按月发的那些含独有内容、公开一个月后要进搜索结果。

预期：模型能从不流畅的转录里推断出完整的功能规格。

5. 让模型自己干活：它会回复、偶尔反问澄清，然后动手改代码。语音阶段持续了大约半小时——正好是做一顿晚饭的时间（作者自述）。期间可以瞄一眼厨房里的本地预览，用语音反馈设计。

6. 判断功能差不多完整后，让 Codex 建分支并开一个 pull request。预期：代码到“几乎可以上线”的程度。

7. 在 GitHub 的 PR 界面审代码。原文发现一条导入脚本用 subprocess 调 Git，而他要从私有 Git 仓库导入，认为走 API 更合适，于是切回键盘打字，让 Codex 把这条改成基于 API 的导入；同时顺手改了几处公开页面的展示。预期：改完之后可以合并。

8. 再花大约半小时打字提示，直到满意，合并 PR 部署到生产。

语音阶段实际产出的东西（可作为试点规模的参照）：

- 一个新的 Django 模型 + migration，以及对应的 Django Admin 配置；
- 四个能跑的导入：最近的 Substack 条目走 RSS；其余 Substack 条目走它们的未公开 API（模型直接试了 `/api/v1/archive`，再自己搜出分页办法，找到 Karen Spinner 的一篇文章）；已发布的月度 newsletter 来自 `simonw/monthly-newsletter-archive` GitHub 仓库；最近一期私有赞助者 newsletter 来自一个私有仓库；
- `/newsletters/` 和 `/newsletters/2026/` 公开归档页；
- newsletter 出现在日和月的归档页，但不出现在 tag 页和首页；
- 每周 Substack newsletter 链回 Substack，归档的月度 newsletter 有自己的页面；
- 接入站点搜索。

### 做法 B：先讲全 + 视觉参考 + 反问澄清，再产出 v1（@nutlope 流程）

1. 前提：可使用 WisprFlow（原文只点名 @WisprFlow，未给安装与配置）。打开录音，口述一个 1–5 分钟的应用需求，尽量把细节说全；将转写结果作为给编码代理的初始需求。原文未给出具体提示词模板。预期：得到一段比一句话更详细的需求，而不是让代理从短提示猜。

2. 前提：准备好产品/界面视觉参考截图，或可使用 Inspo MCP（原文只点名，未给配置）。把截图或通过 Inspo MCP 获得的视觉灵感附给代理，让它理解你想要的形态。预期：代理拿到视觉上下文。

3. 前提：已具备 @mattpocockuk 的 grill-me 技能（原文只点名，未给安装、调用方式或提示词）。让代理先使用该技能提出澄清问题；你回答问题并修正需求，不要急着让它直接实现。预期：在写代码前暴露需求遗漏。

4. 在澄清完成后，让编码代理产出 v1。原文到此结束，未说明如何迭代、如何验收或如何部署。预期：拿到 v1；后续迭代、验收和部署需要你自己补流程。

### 怎么选

- 需求清楚、能一边干别的活、环境能出声、本地有预览可看，选做法 A。
- 需求细节多、有截图或视觉参考、希望代理先反问澄清再动手，选做法 B；但要接受原文只到 v1，且没有配置、提示词和验证数据。
- 环境不方便出声，或任务里有大量粘贴报错、选中代码、密钥配置，选做法 B 的澄清环节加打字实现，或者干脆全程打字。
- 组合建议：先用 B 的 1–5 分钟详细口述、视觉参考和反问澄清把需求讲透，再按 A 起本地会话、看预览、开 PR、键盘收尾。这是本文对两份材料的组合建议，未被原文单独验证。

## 怎么判断变好了

- 做法 A 的最直接指标：语音阶段结束时，代码是否到了“几乎可以上线”（almost ready to ship）的程度——这是原文作者的标准。
- 做法 A 的两段时间：从开口到开 PR 用了多久，从 PR 到合并用了多久。原文的自述参照是各约半小时。
- 做法 A 审阅时你实际改了多少：原文只改了导入机制和几处展示细节，共两类问题。如果改动量大到接近重写，说明这个任务不适合语音驱动。
- 做法 A 的模型反问澄清次数，以及是否答对：原文里它偶尔提问就动手了，没有反复问同一件事。
- 做法 A 上线后功能是否按预期工作。原文可核查的锚点：`/newsletters/` 索引页和某期月度 newsletter 的页面确实存在，PR 上有他审阅时追加的 commit；归档页显示规则和搜索集成是否真的生效。
- 做法 B 的指标（来自 @nutlope 调研建议）：首次 v1 的需求遗漏数、v1 后重大返工轮数、澄清问题中被采纳的比例、从开始到可运行 v1 的时间、开发者对需求理解准确度的主观评分、首版验收通过率。若试用组在需求遗漏和返工上更少，且时间成本可接受，才可认为流程有改善；原文本身没有提供这些验证数据。

最小试用方式：

1. 挑一个自己已经想清楚的小功能，规模参照 A：一个新数据模型 + migration + 视图 + 模板 + 一个导入脚本。不要拿需求模糊或跨系统的大改造来试。
2. 做法 A：在本地 checkout 起会话，先打字发原文那句 `Start dev server and open in browser`，确认能看到预览；点“Start new voice chat”（话筒右边那个），把设备放在你能顺手看到预览、又能一边干别的活的地方；对着它把需求讲一遍，允许停顿和改口，讲清“要什么、不要什么、要出现在哪些页面、要不要被搜索到”这类边界条件；让模型自己改代码并开 PR；在 PR 界面审，发现不对的地方切回键盘打字让它改，直到可以合并。
3. 做法 B：选一个小的应用想法，做两组对照。对照组用普通文字需求直接让编码代理产出 v1；试用组按原文流程，先录 1–5 分钟详细需求，附截图/视觉参考，再让代理用 grill-me 类方式反问澄清，最后产出 v1。尽量使用同一代理和相近任务复杂度。记录上面列出的 B 指标。
4. 试多久：A 原文只给了单一案例的时长尺度（语音约半小时 + 打字约半小时）。就按这个规模做一次试点、走完到 PR 与合并的完整来回，用上面的指标判断；原文没有对照组，也没有量化收益，所以适合试点而非直接采用。B 原文没有给时长；按一个能跑出 v1 的小应用做一次，记录从开始到 v1 的时间，不做无依据的时长承诺。

## 常见坑

- 点错按钮：原文特意强调是“Start new voice chat”，不是它左边那个话筒按钮。
- 以为语音能覆盖全部：细节阶段打字更高效；需要新建 API key 这类环节必须回到键盘。
- 拿需求模糊或跨系统的任务来试：A 的成功前提是作者对要建什么心里已经有清楚构想，且该功能足够简单；换成他自己都不清楚的需求，原文没给出结论。
- 环境不合适：作者说不会在共享办公空间里对电脑说话。
- 没有预览的纯语音场景：原文没有背书；视觉预览是它比手机纯语音强得多的关键条件之一。
- 指望“主动推进”：两份材料都没有描述任何由时间、事件或状态触发、无人干预持续完成的工作——A 需要你开口说话或打字，B 也需要你回答问题、让代理澄清。
- 忽略界面会变：A 具体依赖 Codex 标签页、语音模式、原文提到的具体模型（GPT-6 Astra High），这些都会变。
- B 的坑：原文只给了 1–5 分钟的区间，没有给出“更长语音更好”的证据；不要把时长当成质量保证。
- B 的坑：grill-me、WisprFlow、Inspo MCP 都只被点名，原文没有安装、配置、调用方式或提示词；不要假设照四步就能复现。
- B 的坑：原文在“收到 v1”处结束，没有迭代、验收和部署；不要把 v1 当成上线版本。
- B 的坑：做对照时任务复杂度和代理要尽量相近，否则“需求遗漏数”“返工轮数”不可比。

## 证据与来源

做法 A 依据 Simon Willison 的《A new feature for my blog, built using my voice》（本次调研的原文）。可核查的一手材料包括：完整语音转录的 Gist（作者说有，含全部不流畅词）、审阅时追加 commit 的 PR 链接、上线后的页面链接。产出清单见“操作步骤”：新 Django 模型 + migration、Admin 配置、四个导入、两类公开归档页、归档页显示规则、搜索集成。自述耗时：语音阶段约半小时，之后打字约半小时。原文没有给出任何量化指标（没有节省时间百分比、没有 bug 率、没有对比组）。

做法 B 依据 @nutlope 的推文“我现在构建应用的方式：”。原文只有作者自述的四步工作流和该推文的互动数据（采集时 413 赞、19 次转发、67 条回复）；没有案例结果、前后对比、代码、配置或质量数据。原文在“收到 v1”处截断，grill-me 技能、WisprFlow 配置、Inspo MCP 用法、提示词和模型选择都缺失。因此 B 只是作者主张的流程，适用于能使用这些工具、以应用 v1 为目标的个人/小团队；不能据此推断在复杂生产系统或严格验收场景同样有效。

只是作者主张、不是本文证据的：A 中语音模式在 DevDay 那类演示场景里确实好用；这不是他的日常主力；细节阶段打字更高效；杀手级特性是多任务；不会想在共享办公空间里这么跟电脑说话。B 的四步流程能改善结果也仍是作者主张，调研只建议做小范围对照试用。迁移到其他编码智能体（例如清单里的 Claude Code）属于本文推断，两份原文都没有提到。
