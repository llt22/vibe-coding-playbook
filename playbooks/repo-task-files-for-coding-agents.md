# 把任务写进仓库，让编码智能体先出计划再改代码

> **未经实测**：本手册由 ai-work-radar 根据自动调研合并生成并持续修订，步骤尚未有人实际跑过。服务修订时基于自己保存的上一版重写，直接改这个文件会被覆盖；实测过的做法请写到 experiences/。
>
> 解决的问题：把开发任务从外部工单搬进 Git 仓库，并用“读任务→出计划→人工批准→实现并回写报告”的流程，解决智能体缺少任务上下文、需求到代码不可追溯的问题。
> 先试这一步：先选一个仓库，建一个私有任务目录，把一个小任务写成 Markdown，让智能体只做分析和计划，你审阅后再让它改代码。
> 最近修订：2026-10-27

## 解决什么问题
把开发任务从外部工单系统搬进 Git 仓库，写成 Markdown 文件，让编码智能体在同一个工作区里读任务、读代码、读文档，并按“读任务→出计划→人工批准→实现并回写报告”的流程执行。这样任务变更像代码一样被版本化、可审阅，原始需求、计划方案和实际改动留在同一个任务文件里，减少智能体缺少上下文和需求到代码断链的问题。

## 适用与不适用
适用：软件开发的代码任务；团队使用 Git；智能体能访问本地代码仓库、文档目录和任务目录；任务可能包含未完成安全修复、内部规划或未发布功能，需要独立配置访问权限；复杂任务需要补充验收标准、技术决策、依赖和测试要求。原文举例的本地编码助手包括 Claude Code 或 OpenCode。

不适用或先不要直接套用：任务不是代码开发任务；团队没有用 Git 管理代码和文档；不能给智能体稳定的仓库访问权限；你需要的是一套完整的工单系统能力（分配、评论、看板、冲刺等），而原文只主张这些功能不一定都需要，没有证明可以替代；使用远程或云端智能体，却还没有解决仓库访问和权限问题。

## 前置条件
- 团队使用 Git 管理代码和文档，并能配置仓库权限。
- 能创建一个私有任务仓库或任务目录；任务可能敏感，不要默认放进公开仓库。
- 本地开发环境能同时访问代码仓库、文档仓库和任务仓库。
- 智能体能读取本地代码仓库、文档目录和任务目录；原文以 Claude Code 或 OpenCode 这类本地编码助手为例。
- 有人负责审阅智能体写的计划，并明确批准后才进入实现。
- 不需要先引入专门工具：原文强调可以把任务文件本身当作规范，只需 Git 和智能体即可开始；Spec Kit 等工具是另一种选择，但不是本文流程的前提。
- 原文没有给出具体 git 命令、.gitignore 行内容或提示词模板；你需要按自己的仓库情况补足，不要照抄不存在的命令。

## 操作步骤

1. **决定任务放在哪里。**
   - 做法 A（原文完整示例）：代码、文档、任务分成三个独立 Git 仓库。任务仓库私有，文档仓库可公开，代码仓库照旧。适合任务含未完成安全修复、内部规划或未发布功能，需要独立配置访问权限的团队。
   - 做法 B（最小试用）：先建一个私有任务仓库或任务目录，只把任务写成 Markdown。适合先验证流程、不想一开始拆三个仓库的团队。注意：原文的完整布局是三仓库；做法 B 只是缩小试用范围，不改变“任务在 Git 中、智能体可读”的核心。
   前提：团队用 Git 管理代码和文档，能配置仓库权限；任务可能敏感时不要放到公开仓库。
   预期结果：你有一个明确的任务存放位置，且智能体可读、权限可控。

2. **在本地把文档和任务挂到代码仓库工作区。** 按原文示例，把文档仓库和任务仓库克隆到代码仓库下的 `/docs`、`/tasks` 文件夹；在代码仓库的 `.gitignore` 中排除这两个目录，使父仓库不跟踪它们。两个被克隆仓库仍保留自己的 Git 历史，可独立提交、推送和同步。原文布局如下：

```text
/code-repo
  /src
  /tests
  /docs                 # Separate documentation repository
    /user-guides
    /admin-manuals
    /developer-docs
  /tasks                # Separate private task repository
    /release-123
      task-551-something-descriptive.md
      task-552-something-descriptive.md
  .gitignore            # Excludes docs and tasks
```

   前提：本地开发环境可同时访问代码、文档和任务仓库；原文示例面向本地编码助手。若采用做法 B，可先只挂任务目录，但完整示例仍是上面的三仓库布局。
   预期结果：智能体在一个工作区能看到代码、文档和任务，同时代码仓库不会把嵌套仓库当作自己的文件跟踪。

3. **写任务 Markdown 文件。** 在任务仓库中写一段简短描述，说明要实现的变更或功能。复杂功能可在任务文件中加入验收标准、技术决策、依赖和测试要求；小型维护任务只需短描述。可按发布文件夹组织，例如 `/tasks/release-123/`。原文强调可以把任务文件本身当作规范，不必一开始就引入专门工具。
   前提：任务文件放在智能体可读取的路径中，并按需要组织发布文件夹。
   预期结果：任务文件足够让智能体理解要做什么；复杂任务的验收标准、技术决策、依赖和测试要求没有遗漏。

4. **让智能体分析需求。** 让智能体读取任务文件，并检查相关代码和文档。此步不要直接进入代码修改——原文的流程是先分析、再写计划、再人工批准。
   前提：智能体能访问本地代码仓库、文档目录和任务目录；原文举例 Claude Code 或 OpenCode。
   预期结果：智能体对任务和相关代码、文档形成理解，可以进入写计划。

5. **让智能体把实现计划写回任务文件。** 计划中应包含拟议解决方案，并列出打算做的变更。原文明确要求计划写回任务文件，而不是从任务描述直接跳到代码修改。
   前提：任务文件可写；团队接受把计划作为任务的一部分保存。
   预期结果：任务文件里出现可审阅的实现计划，开发者可以逐条检查方案和变更范围。

6. **人工审阅并批准。** 开发者审阅计划，明确批准后才允许实施。原文把这个批准步骤作为保持人类控制的关卡，智能体不应直接从任务描述进入实现。
   前提：流程中必须安排人工审批，不能省略。
   预期结果：计划被批准或退回修改；没有批准就不进入实现。

7. **智能体实施并报告。** 智能体修改代码，在需要时更新文档，并把实现报告追加到任务文件末尾。原文要求任务描述、实现计划和报告都留在同一个文件中，便于复核原始需求、计划方案和实际改动。
   前提：代码变更记录在代码仓库中，实现报告留在任务仓库中。
   预期结果：同一个任务文件里能看到任务描述、实现计划和实现报告；代码仓库里有对应变更。

8. **提交代码时引用任务文件名。** 原文建议在 Git 提交信息中引用任务文件名，把实现与原始需求连接起来。
   前提：团队接受这种提交习惯；原文未给出具体提交命令或格式。
   预期结果：从一条代码提交能回到对应任务文件，追溯不断链。

9. **可选：按发布组织任务，生成发布说明和文档更新线索。** 当任务按发布文件夹组织时，智能体可利用已完成任务和 Git 历史起草 changelog、release notes，并识别需要更新的文档。需要非技术用户浏览、编辑和组织文件时，可再引入 Typemill 等浏览器界面同步 Git 多仓库；Git 仍负责版本历史与同步。
   前提：需要额外界面时才引入；原文未给具体配置细节。
   预期结果：发布说明和文档更新有线索，非技术用户可参与浏览和编辑，但版本历史仍以 Git 为准。

## 怎么判断变好了
原文没有定义量化指标，也没有对照实验。试用时不要等一个“智能体自动变好”的结论，而是记录下面这些可观察项，并与原有工单流程并行比较：

- 计划审阅发现的问题数和返工次数。
- 需求遗漏或验收标准未满足的次数。
- 从任务到首个可审计划的时间。
- 从批准到完成的时间。
- 文档是否随同一任务更新。
- 代码提交与任务文件的可追溯性。
- 实现报告是否足以复核改动。
- changelog 或 release notes 起草是否更省力。

最小试用方式：选一个有代码和文档的仓库、一个能访问本地仓库的编码智能体、一个私有任务仓库或任务目录；按上面的布局把文档和任务目录挂到代码仓库下并加入 `.gitignore`。选少量任务，至少包含一个小型维护任务和一个需要验收标准的复杂任务；写 Markdown 任务文件，复杂任务补充验收标准、技术决策、依赖和测试要求。按流程执行：智能体分析→把计划追加到任务文件→人工审阅批准→实现并更新文档→把实现报告追加到任务文件；提交代码时引用任务文件名。与原工单流程并行对照。

试多久：原文未给时长；至少覆盖上述两类任务的完整周期，再决定是否扩大。若这些指标相对原流程没有改善，或人工审批成本过高，就不应直接推广。

## 常见坑
- **让智能体从任务描述直接改代码。** 原文明确不应跳过计划和人工批准；跳过之后任务文件里没有可审阅的计划，出了问题也难定位。
- **把敏感任务放进公开仓库。** 任务可能包含未完成安全修复、内部规划或未发布功能；原文用独立私有任务仓库解决权限问题。
- **忘记在代码仓库的 `.gitignore` 中排除 `/docs`、`/tasks`。** 父仓库会把嵌套仓库当成自己的文件跟踪，破坏各仓库独立历史。
- **复杂任务只写一句短描述。** 原文建议复杂功能补充验收标准、技术决策、依赖和测试要求；小型维护任务才可以只写短描述。
- **计划不写回任务文件。** 只让智能体口头说计划，事后无法复核它当时打算做什么。
- **实现报告不追加。** 任务描述、计划、报告分离后，复核原始需求、方案和实际改动的成本会上升。
- **提交信息不引用任务文件名。** 代码变更和任务文件之间失去直接链接，追溯变弱。
- **一开始就上浏览器界面或专门工具。** Typemill 等界面是可选项，原文未给配置细节；Spec Kit 等工具也不是开始的必要条件，任务文件本身即可先当规范。
- **把作者主张当成已验证结论。** “信息都在仓库里智能体工作最好”“未来工单系统功能不一定都需要”等只是作者主张，原文没有量化证据。
- **使用远程或云端智能体却没解决仓库访问和权限。** 原文示例面向本地编码助手；远程场景需要另行解决访问和权限问题。

## 证据与来源
本手册目前只依据一篇调研：《Tasks as Code: Move Your Tickets into the Repository》。它给出的是作者自己的设置和流程：三个独立 Git 仓库、本地把文档和任务仓库克隆到代码仓库下的 `/docs`、`/tasks` 并用 `.gitignore` 排除、按 release 文件夹组织任务、五步工作流、提交信息引用任务文件名，以及可选的 Typemill 多仓库同步界面。原文没有给出具体 git 命令、`.gitignore` 行内容、提示词模板，也没有量化数据、对照实验、团队规模或失败案例；因此本手册不补命令、不补提示词、不写效果数字。

以下只是作者主张，不是已验证结论：AI 编码智能体在所需信息都在仓库中时工作最好；任务 Markdown 加 Git 能改善版本化和审阅；人工批准能保持控制；未来工单系统的分配、评论、看板、冲刺等功能不一定都需要。原文提供的可审阅工件——需求、计划、报告同文件保存，Git 历史可追溯，人工批准关卡——可用于人工复核，但不能证明结果一定改善。

原文把 Claude Code、OpenCode 列为本地编码助手示例；提到 Spec-Driven Development 常由 Spec Kit 等专门工具支持，但强调更简单的方式即可开始：把任务文件本身当规范，只需 Git 和智能体。原文示例是本地编码助手；若使用远程或云端智能体，需要另行解决仓库访问和权限问题。
