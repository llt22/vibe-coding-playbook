## 解决什么问题
在高隐私、批量合同或尽调文档场景里，AI 可以帮忙做字段提取、审阅、报告生成和起草，但团队常常看不到客户 trace，错误又分散在每份文档里。直接全量跑，列定义或提示词一错就会放大；只看一个总分，也看不出模型在哪些法律工作上更好、哪些更差。这篇手册解决的是：怎么用“先小批量校准、再模拟评测、再生产灰度”的顺序，让 AI 审阅结果可校准、可评测、可追溯，而不是把工具接上就全量上线。

## 适用与不适用
适用：
- 法律、高隐私、大批量文档和受监管行业；任务包括批量合同字段提取和审阅、尽调报告生成并抓 red flags、Word 起草和编辑、法律检索。
- 有领域专家能快速判断每列问题对错，有工程支持能建项目权限、评测环境和生产检查。
- 源文档有页面和坐标信息，能做引用定位。
- 能收集脱敏或模拟的失败样本，做发布前后检查。

不适用或不要照搬：
- 小团队、低隐私、一次性少量文档：不必上复杂编排、专用合规基础设施或大专家池。
- 没有领域专家校对 10 行结果时，表格审阅的列定义无法校准，先别全量跑。
- 没有页面和坐标信息时，不要承诺 PDF bounding box 引用。
- 原文因律所合规选 Azure、配 legal engineers 和 FDE、对窄任务后训练开源模型，都有前提；不是通用建议。
- 原文是访谈，转录在约 15:00 处截断，后文只有摘要和时间戳，缺少具体提示词、failure mode 清单、指标定义和成本数据；不能当完整实施文档照抄。

## 前置条件
- 选一个高隐私、批量文档任务，把文件放进“项目”容器，让 agent 只在项目权限内读写；需要项目文件权限、审计日志和数据保留策略。
- 每列问题要能被人快速判断对错；有律师或领域专家能校对前 10 行。
- 能构造模拟数据室，放入已知 red flags 做发布前评测；或者能收集脱敏失败样本。
- 源文档有页面和坐标信息，供 citation 高亮 PDF bounding box。
- 如果用 lists 和 intake 做编排，需要有 Slack、任务队列和权限控制。
- 基础设施按客户合规要求选；原文的 Azure 选择只在客户合规要求类似时适用。
- 人员上，原文配置是 legal engineers 按高级用户方式无代码配置产品，forward deployed engineers 写生产代码、接 CRM 或文档管理系统，把经验回流核心产品但不碰客户数据；大客户签约时配 legal engineers，需要时加 FDE。小团队不必照搬这个规模。
- 窄任务后训练开源权重模型的前提是已有评测和窄任务数据；否则先不做。

## 操作步骤
以下步骤是把访谈中的可操作点整理成试行流程；原文没有给可直接复制的命令、配置或提示词，代码块是据原文示例字段整理的模板，不是原文原样。

先选做法：
- 做法 A（结构化批量提取）：用表格审阅，每行一份文档，每列一个问题。适合终止期限、知识产权归属条款、遣散条款这类能快速判断对错的字段。
- 做法 B（非结构化任务）：用 agent 起草、分析、编辑和检索。适合 Word 起草和编辑、尽调报告生成、法律检索。
- 怎么选：任务是批量字段核对，优先做法 A；任务是起草、分析、编辑、检索，优先做法 B；两者可组合，但都要先小批量校准。

1. 锁定一个批量文档任务，建项目容器。
前提：任务高隐私、批量、文件可归入项目；有项目权限、审计日志和数据保留策略。
做法：把文件放进项目容器，让 agent 只在项目权限内读写；原文的产品原语是 projects hold files，agent 可起草和编辑 Word 文档。
预期结果：文件不越权；后续表格审阅、引用和评测都有明确的文件来源。

2. 建表格审阅，先只跑 10 行。
前提：每列问题可被人快速判断对错；已选好第一批 10 份文档。
做法：每行一份文档，每列一个问题；先不要跑全量。
```text
表格审阅模板（据原文示例字段整理，不是原文原样）
行：一份文档
列：
- termination period（终止期限）
- IP assignment clause（知识产权归属条款）
- severance terms（遣散/补偿条款）
执行顺序：先填 10 行 → 人工校对并修正列定义/提示词 → 再跑全量
```
预期结果：得到 10 行可人工校对的结果，列定义和提示词的问题在小批量里暴露，而不是在全量里放大。

3. 用前 10 行校准，再决定是否全量。
前提：有律师或领域专家能逐行校对；每列问题有明确对错。
做法：先填 10 行，人工校对并修正列定义/提示词，再跑剩余文档。原文明确 Tabular Review 从 10 行开始，让人先修正提示词，再跑剩余文档；原文称可支持最多一百万单元格，但这不是一开始就跑满的理由。
预期结果：列定义和提示词被修正；错误模式初步显形；团队有依据决定扩到多少、是否继续。

4. 建模拟评测环境，补上看不到 trace 的缺口。
前提：不能读客户数据或 trace；有领域专家和工程支持。原文的评测团队是 3 名工程师加 3 名律师；团队更小时可以缩小，但这是原文未验证的缩小版。
做法：复制客户常做的工作类型，构造类似“10,000 文件数据室做尽调、最终报告要抓到正确 red flags”的 RL 环境。
预期结果：得到发布前可重复的评测集；不依赖客户 trace 也能比较模型和流程。

5. 画评测热力图，不要只看一个总分。
前提：评测集覆盖多个实践领域和任务类型。
做法：按实践领域乘任务类型记录模型表现，而不是只看一个总分。原文说新模型常常在某些法律工作上更好、在另一些上更差。
预期结果：能看出模型在哪些任务上进步、哪些任务上退化；避免一个总分掩盖局部变差。

6. 生产环境做失败分类，用 feature flag 放廉价检查。
前提：已能收集脱敏或模拟的失败样本；有 feature flag 机制。
做法：把失败归入 10–20 个已知 failure modes；用便宜的 LLM-based checks 放在 feature flags 后面运行。原文没有给 failure mode 清单，需要从 10 行校准和模拟评测中归纳，不要照抄一个不存在的清单。
预期结果：发布前后能按 failure mode 观察频次；检查可以灰度开关，出问题能关掉。

7. 做模型路由，不默认让终端用户选模型。
前提：有多个子任务和多个模型可选；能观测质量、成本、延迟、治理和区域可用性。
做法：按子任务路由，权衡质量、成本、延迟、治理和区域可用性。原文说律师不该判断一个合同是 Sonnet-high 还是 Opus-mid 任务；只有用户强烈需要实验时才提供 model picker。
预期结果：用户不用自己判断模型档位；平台按子任务选择模型。原文没有给路由规则和指标权重，这一步是原文主张，需要自己用评测补规则。

8. 给所有生成内容加可定位引用。
前提：源文档有页面和坐标信息。
做法：agent 写出的内容要带 citation，能高亮源 PDF 中的 bounding box，并支持多层下钻。
预期结果：审阅者能从生成内容回到源文档位置；引用可追溯率和引用准确率可以被观测。注意：原文案例中引用准确率从 70% 到 99% 是模型升级带来，不是他们做了修复；不要把这个提升归因于引用功能。

9. 需要多人协作时，再用 lists 和 intake 做编排。
前提：有 Slack、任务队列和权限控制；任务不是单次审阅。
做法：lists 是类似 Notion 的数据库，带 triggers 和 automations；agent 可创建和读取 lists，list 变化可启动 agent。Intake 是 Slack bot，把请求变成 list 上的 ticket。原文没有给具体触发配置。
预期结果：请求变成 ticket，列表变化可触发 agent；但触发条件和权限要自己补。单次审阅不必上这套编排。

10. 按条件选合规基础设施和人员分工。
前提：客户有明确合规要求；签约规模需要配置和集成支持。
做法：原文因律所不接受 AWS 或 GCP、微软已通过 365 成为批准供应商，所以全部跑在 Azure。大客户签约时配 legal engineers，需要时加 FDE；legal engineers 按高级用户方式无代码配置产品；FDE 写生产代码、接 CRM 或文档管理系统，把经验回流核心产品，但不碰客户数据；原文预计一年内可有轮转 FDE 驻场几个月。
预期结果：合规通过；配置和集成有人负责。注意：Azure、FDE 和百人级 legal engineers 不是通用建议，只在客户合规和规模类似时适用。

11. 窄任务后训练开源权重模型，放在评测之后。
前提：已有评测和窄任务数据。
做法：原文对法律研究等窄任务做后训练，但明确不训练自己的前沿模型。
预期结果：窄任务可能改善；没有评测和窄任务数据时先不做，避免把后训练当成绕过评测的捷径。

## 怎么判断变好了
最小试用：选一个批量合同或尽调流程，建项目文件；用表格审阅模板先跑 10 行并人工校对；把错误归入 10–20 类 failure modes；用一个小型模拟数据室放入已知 red flags 做发布前评测；上线后用 feature flag 开廉价 LLM 检查。

试多久：原文没有给具体时长，不要编一个固定天数。以完成一次“10 行校准 + 一轮模拟数据室评测 + 一次 feature flag 灰度”为一个最小周期；周期长短取决于文档量和领域专家可用性。

可观察指标：
- 每列字段抽取准确率：和前 10 行人工校对结果比。
- red flag 漏检和误报：用模拟数据室里已知的 red flags 检查。
- 报告人工返工时间：生成报告到可交付之间的人工修改时间。
- 引用可追溯率和引用准确率：能否定位到源 PDF 的 bounding box，引用内容是否对得上。
- 单文档成本与延迟：按子任务和模型路由分别看。
- failure mode 频次：按 10–20 类失败模式统计发布前后变化。
- reviewer 接受率：审阅者接受或直接修改的比例。

判断规则：和人工基线相比，核心指标稳定改善且重大漏检不增加，再扩到全量；如果模型升级已经解决某个问题（如原文引用问题），不要为评测而评测。

## 常见坑
- 直接全量跑表格审阅，不先跑 10 行。列定义或提示词一错，全量放大。
- 只看一个总分，不看实践领域乘任务类型的热力图。新模型可能在某些法律工作上更好、在另一些上更差。
- 把引用准确率从 70% 到 99% 说成自己修复的功劳。原文说这是模型升级带来，不是他们做了修复。
- 让终端用户选模型档位。原文说律师不该判断一个合同是 Sonnet-high 还是 Opus-mid 任务；只有用户强烈需要实验时才给 model picker。
- 无法读客户 trace 时不做模拟评测，直接上线。原文做法是用模拟数据室和领域专家补评测。
- 失败模式不分类，只靠感觉。原文用 10–20 类 failure modes 加廉价 LLM checks behind feature flags；但原文没给清单，需要自己归纳。
- 把 Legora 的做法当通用建议。Azure 是因律所合规；FDE、百人级 legal engineers、后训练开源模型都有条件；小团队或低隐私场景不必照搬。
- 没有页面和坐标信息却承诺 bounding box 引用。前提不满足时，不要承诺高亮定位；先确认源文档是否有页面和坐标信息。
- 把 Claude Code 等通用编码 agent 直接说成 Legora 用 Claude Code。原文没有这回事；只能类比 agent 加项目文件加工具调用。
- 把访谈摘要当完整教程。转录在约 15:00 处截断，后文只有摘要和时间戳，缺少具体提示词、failure mode 清单、指标定义和成本数据。
- 在评测和窄任务数据都没有时先做后训练。原文明确不训练自己的前沿模型，后训练只适合窄任务。
