# 发布后不再漏公告：让必须发生的收尾动作自动触发

> **未经实测**：本手册由 ai-work-radar 根据自动调研合并生成并持续修订，步骤尚未有人实际跑过。服务修订时基于自己保存的上一版重写，直接改这个文件会被覆盖；实测过的做法请写到 experiences/。
>
> 解决的问题：这篇手册解决发布后公告等“一次都不能漏”的收尾动作写在规则里却可能被模型跳过的问题，用钩子保证触发、用人工保证发布。
> 先试这一步：先打开专案共用设定档确认有没有钩子；没有的话，先挂一条只认强制推送指令的“挡下并说明理由”钩子，跑一次确认能挡下，再去做发布公告的钩子。
> 最近修订：2026-11-14

## 解决什么问题
发布完成后写公告、分发多平台、归档草稿这类收尾动作，不是不会做，而是忙起来就会被跳过；写进专案规则档只是给模型的建议，模型可能不执行。本手册把“一次都不能漏、一次都不能错”的触发与检查从规则档搬到 Claude Code 钩子：事件一到就执行，执不执行不由模型决定；文案生成和最终发布仍由人把关。

## 适用与不适用
**适用**
- 单一或少量人使用 Claude Code 做发布；
- 发布动作确实经过 Claude Code；
- 存在一个可写入草稿的发文排程工具，或可直呼的发文工具 API；
- 你要解决的是“漏触发、漏检查”，不是“文案质量”。

**不适用**
- 发布完全由 CI 驱动：钩子只看得见 Claude Code 自己做的事，CI 跑的发布它看不见，这条钩子不会触发；
- 发布是你在终端手敲命令完成：同样不在钩子视野内；
- 没有可写入草稿的发文工具；
- 你指望钩子自动发布：原文的验收画面是“草稿已生成、待人工排时间”，发布权留给人。

## 前置条件
- 已启用 Claude Code 的钩子机制；能编辑专案共用设定档或个人的钩子设定档。三种作用域要分清：全域管全部专案，专案共用管全队并进仓库，个人专用只管自己、不进仓库。
- 有一个能排程或存草稿的发文工具，并让 Claude Code 能呼叫它；若走直呼接口型，还需要该工具的 API，以及用版本号组成的防重复键。
- 钩子传入的事件资料里必须能取到版本号；发布说明或更新日志必须可被读取。
- 钩子需要能执行指令、发网路请求；专案共用设定档要放在共用位置，才能全队生效。
- 原文没有给出任何可直接复制的命令、配置、事件名、脚本语言或提示词，只给了流程和判据；落地时必须对照 Claude Code 官方文档补齐细节，不要照抄不明片段。

## 操作步骤
1. **先画边界：哪些动作值得挂钩子。** 前提：你能列出发布后必须发生的动作。做法：只挑“一次都不能漏、一次都不能错”的动作，例如发布后三平台公告草稿、强制推送挡下、贴文禁用词与字数检查。预期：得到一张短清单；清单外的“最好有”动作不要挂钩子，避免误挡和噪音。
2. **先挂一条低风险防呆：强制推送挡下。** 前提：你能编辑钩子设定档，并知道强制推送对应的那条指令。做法：在呼叫前拦下，匹配器只认强制推送那条指令，处理器回传“挡下代码 + 理由”。预期：跑一次强制推送，被挡下且理由可读；正常推送不被挡。原文建议把它作为起步动作，因为它风险最低、不依赖外部服务。同法可复制贴文品管：建立贴文之前先检查禁用词与字数，超标就挡下。
3. **接好发文排程工具，并让 Claude Code 能呼叫它。** 前提：你有一个能排程或存草稿的发文工具，且 Claude Code 能呼叫它。预期：Claude Code 能通过该工具生成草稿，而不是只能输出一段文本。
4. **选做法 A 或做法 B。**
   **做法 A：提醒型。** 钩子回传一段提醒文本，由模型写稿并存草稿。选它，如果你要文案品质、要人把关。前提：事件资料里带得到版本号；发布说明或更新日志可被读取。
   **做法 B：直呼接口型。** 钩子直接呼叫发文工具 API 存一篇简短草稿。选它，如果你要稳定、不要模型插手。前提：你知道该工具 API；请求里的连结和版本号写死；请求带上用版本号组成的防重复键。
   **不推荐把“写规则叫子代理写公告”当作唯一保证。** 原文明确说模型可能跳过，等于回到原点；它可以作为做法 A 的补充，但不能替代钩子。
5. **写处理器或脚本，职责越小越好。** 做法 A 的发布提醒脚本只做三件事：从钩子传入的事件资料里抓出版本号；抓不到就安静退出，不打扰、不报错刷屏；抓到了就回传提醒文本，内容是叫 Claude Code 先读发布说明，再帮 X、领英、蓝天各写一篇公告，存成草稿、不要排时间。做法 B 则把版本号写进请求，并用版本号组成防重复键，避免同一版本发布两次重复建草稿。预期：无版本号的事件资料不会触发提醒；有版本号时回传内容带对版本号。注意：原文没有给出脚本语言、事件名和设定档格式，这一步必须对照 Claude Code 官方文档补齐。
6. **在专案共用设定档里加“发布后触发”的钩子规则。** 前提：你要全队生效，所以放专案共用设定档，而不是个人专用档。做法：匹配器只认“建立发布”那条指令。预期：只有建立发布时触发，其他工具呼叫不触发。若匹配器写宽了，会误触发；写窄了会漏触发。
7. **先干跑，不要直接真发布。** 前提：脚本已接好但还没挂上真实流程。做法：喂一笔假的事件资料给脚本，检查回传文字里的版本号是否与假资料一致；再喂一笔没有版本号的假资料，确认脚本安静退出。做法 B 还要检查同一版本重复请求是否因防重复键只建一篇草稿。预期：版本号对、无版本号静默、重复请求不重复建草稿。
8. **在钩子选单里确认规则还在，再跑一次真实发布。** 前提：干跑通过。预期完整流程：你说一句“帮我打上 2.4 版标签、照更新日志建立发布”→ Claude Code 跑完指令 → 钩子立刻提醒它读说明、写三篇公告、存进排程工具 → 你打开工具、看过、排时间。原文的验收标准是“没有一篇是没经过你眼睛就发出去的”。
9. **人工审核并排时间，不要自动发布。** 前提：草稿已生成。做法：人只看草稿、改稿、排时间。预期：发布动作仍由人完成；钩子只保证草稿不漏。

## 怎么判断变好了
- **最小试用：** 先干跑一次假事件资料，再跑一次真实发布走完整流程。原文未给固定试用天数；要判断漏发率，只能按原文说的“一段时间内发布次数与三平台都生成草稿的次数之比”自行积累，材料没有给具体时长。不要用非发布事件代替真实发布作为最终验收。
- **漏发率：** 一段时间内“发布次数”与“三平台都生成草稿的次数”之比，对照上线前的手工基线。
- **误触发率或假阳性：** 非发布类工具呼叫触发提醒的次数；目标是 0，靠匹配器和静默退出保证。
- **误挡率：** 防呆钩子挡下正常操作的次数；过高说明匹配器写得太宽。
- **人工补写次数：** 上线后仍需人手补写公告的发布次数。
- **时延：** 从发布完成到三篇草稿可审阅的时间。
- **人的动作量：** 每次发布需要人工记住的步骤数，应从“记得写三篇”降为“审三篇、排时间”。
- **判断口径：** 漏发率下降、误触发为 0、误挡率可接受、人工补写次数下降、时延缩短，才算变好。公告质量是否改善，原文没有测量，不能拿“不漏”冒充“更好”。

## 常见坑
- **把规则当保证。** 写在规则档里的自然语言指令只是建议，模型忙起来可能跳过；一次都不能漏的动作要挂到钩子上。
- **脚本没有静默退出。** 事件资料里抓不到版本号时如果报错或刷屏，每次工具呼叫都会误触发；必须抓不到就安静退出。
- **匹配器写得太宽或太窄。** 太宽会把非发布类工具呼叫也触发提醒；太窄会在真正建立发布时不触发。先用假资料干跑，再跑真实发布验证。
- **把钩子放在个人专用档。** 要全队生效必须放专案共用设定档；放个人档只对自己有效。
- **忽略触发源边界。** 钩子只看得见 Claude Code 自己做的事；终端手敲的指令和 CI 跑的发布它一概看不见。团队真实发布走 CI 时，这条钩子根本不触发，不要为了挂钩子而改发布流程。
- **直呼接口型忘了防重复键。** 同一版本发布两次会重复建草稿；要用版本号组成防重复键。原文没有验证并发发布和平台侧去重，采用前要自己核对。
- **只盯“不漏”，不盯质量。** 钩子保证的是触发和检查，不是公告写得好；原文的案例也只谈了“不漏”，没有谈质量改善。
- **照抄不明代码。** 原文没有给出任何代码、设定档片段、事件名或 API 细节；落地必须对照 Claude Code 官方文档补齐。
- **把挡下写成自动发布。** 原文的验收画面是草稿待人工排时间；自动发布不在这个方案里。
