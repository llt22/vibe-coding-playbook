# 让 AI 修安全 bug 时同时控制攻击面与回归风险

> **未经实测**：本手册由 ai-work-radar 根据自动调研合并生成并持续修订，步骤尚未有人实际跑过。服务修订时基于自己保存的上一版重写，直接改这个文件会被覆盖；实测过的做法请写到 experiences/。
>
> 解决的问题：解决在大型代码库中用 AI 做安全修复时，如何系统缩减攻击面，并证明补丁没有引入回归。
> 先试这一步：先选一个可构建、有测试基线的仓库，固定版本；取 1 个已合入的历史 bug 修复 PR，按回归猎取四步流程跑一遍，并用动态 trace 确认至少一个发现。
> 最近修订：2026-10-22

## 解决什么问题

大型代码库里有两类互补的风险：一类是攻击面本身——某些代码在发布默认配置下就能被未认证的人走到，却没有任何默认功能真正使用它；某些敏感逻辑运行在认证、点击或协议状态转换之前；还有些配置单独看都合理，组合起来却静默关闭了安全控制。另一类是修复副作用——AI 或工程师修一个已报告 bug 时，可能引入回归、不完整修复，或只修了症状。

这篇手册把两套流程合在一起：先用攻击面三遍法找并收窄可达路径，再用“三步证明 + 回归猎取”验证每个补丁没有引入新缺陷。每个发现尽量用动态 trace 或 live PoC 确认；默认配置下的修复必须通过项目测试与黑盒回归，且结果与基线一致；无法产出 live PoC 的步骤记为 inconclusive。两份调研都没有公开完整 skill、提示词、安装命令和 schema，所以这是一套需要人工复核的流程，不是一键工具。

## 适用与不适用

**适用：**

- 代码库可构建、可动态运行或可做 trace。
- 项目自带稳定测试套件，最好另有黑盒回归套件；回归猎取还要求有 live deployment 和真实用户接口。
- 配置复杂、入口多，属于 Public 或 Gated 类型的大型项目。
- 有可复现的 bug 报告或待审查的 PR diff；有安全工程师能复核 trace、live PoC、补丁和影响范围。
- 有（或愿意补）项目专属的威胁模型与打补丁指南；原文覆盖 C、C++、Java、PHP、Python，可作为语言范围的参考。

**不适用：**

- 代码库无法构建、无法动态 trace，或无法提供 live 接口。
- 没有稳定测试基线，改完无法判断默认行为是否变化。
- 没有人能做安全复核和最终裁决，只能让 AI 自动改代码、自动报回归。
- 期望直接复制现成 skill、安装命令、提示词或 schema。两份调研都明确：完整 skill/提示词/配置未公开，插件安装命令和 schema 定义也未给出；regression-hunt 的流程可手工照做，但不要臆造命令。
- 深度依赖 Codex 生态；其他 agent 环境需要自行复刻流程。

## 前置条件

- 代码库读取与修改权限。
- 可构建运行的环境；攻击面审查需要动态 trace，回归猎取需要 live deployment 和真实用户接口。
- 项目自带测试套件；最好再有一套黑盒回归套件。固定版本并先建立基线，后续所有对比基于同一基线。
- 配置清单、认证/协议状态机等安全上下文。
- 一名能判断影响范围、复核 live PoC 和裁决回归的安全工程师。
- 回归猎取额外需要：`THREAT_MODEL.md`、`PATCHING_GUIDELINES.md`（或 `AGENTS.md`）、固定 I/O schema、明确的“回归”定义与裁决门槛，以及可编排的 agent 环境（Codex 或等价环境）。
- 如果暂不装插件，把下面做法 B 的步骤当作 agent 提示词/流程手工执行；不要编造安装命令。

## 操作步骤

先选做法：

- **做法 A：攻击面三遍法。** 适合时间、人力充足，目标是系统性缩减攻击面。按默认配置可达性、早期可达性、配置交互依次跑三遍。
- **做法 B：修复 bug 并猎取回归。** 适合已有可复现 bug 报告或待审查 PR diff，目标是让补丁有证据，并检查这次改动还弄坏了什么。
- **组合用法。** 当做法 A 产出 gate 补丁，用做法 B 的回归猎取复核；当做法 B 修复一个 bug，用做法 A 的配置组合/早期可达性做横向搜索。两者冲突时：做法 A 要求默认配置测试差异为 0；做法 B 要求每条回归有 live PoC。测试全绿不等于无回归，仍需枚举调用者并在 live deployment 上复现候选回归。

无论选哪种，三遍法每遍让 Claude 从空上下文开始，只带上一遍的短上下文，避免上下文污染；回归猎取的重放步骤也要用全新上下文的 agent。

### 做法 A：攻击面三遍法

#### A1. 固定版本并建立基线

前提：代码库可构建、测试可跑。

做法：选定一个中型 Gated 或 Public 开源项目，固定版本，记录基线构建结果和测试结果。

预期结果：得到一份可复现的基线，后续每次修改都拿它对比。

#### A2. 划定代码库类别，清点入口与配置

前提：已经明确“默认配置”是什么，以及项目预期提供哪些功能。

做法：先把目标归为 Public、Gated、Private 三类，再让 Claude 清点代码入口点和配置选项，形成清单，并标注哪些配置与安全控制或安全功能相关。

预期结果：入口点清单、配置选项清单、安全相关配置清单。原文在 25 个项目中清点出 17,000+ 个配置选项，其中 3,842 个与安全控制或功能配置相关，可作为量级参考，不是你必须达到的数字。

建议记录字段如下（这是自建记录模板，原文未提供提示词或命令）：

```text
入口点：文件/函数/触发条件/是否需要认证/是否默认启用
配置项：名称/默认值/安全相关与否/影响的代码路径
候选发现：编号/所属遍数/代码位置/可达路径/trace 证据/修复建议/是否改变非默认配置
验证：基线测试结果/修改后测试结果/黑盒回归结果/差异数
```

#### A3. 第一遍：查默认配置可达性

前提：已有入口与配置清单，且能对候选路径做动态 trace。

做法：找“在发布默认配置下可达，但不被任何默认功能使用”的代码。对每个候选发现，用动态 trace 确认可达路径，不能只凭静态阅读下结论。确认后设计并实现一个 gate，把这段代码移到认证后、点击后、显式开启后或协议状态机更深处。

预期结果：候选发现清单、每个发现的 trace 证据、对应的 gate 补丁。

#### A4. 验证默认行为不变

前提：第一遍已经产出默认配置 gate。

做法：在基线版本上运行项目自带测试套件和黑盒回归套件，要求修改后的构建结果与基线完全一致。会改变非默认配置的 gate 不要自动采用，交给人类决定。这一步是硬门槛，但不替代做法 B 的回归猎取；即使测试差异为 0，也要对补丁枚举调用者并尝试 live PoC。

预期结果：测试差异为 0；非默认配置变更单独列出，等待人工判断。

#### A5. 第二遍：查早期可达性

前提：同样需要动态 trace 能力。

做法：找在任何配置下运行于硬门之前的敏感且复杂代码。硬门包括认证；也包括无需受害者交互就能触发的路径，以及协议状态转换之前的路径。修复建议包括：把配置检查移到解析之前、增加 guard 强制状态顺序、在配置加载时拒绝危险组合。每个发现仍用动态 trace 确认。

预期结果：早期可达路径清单、trace 证据、修复补丁或修复建议。

#### A6. 第三遍：查配置交互

前提：已有配置清单，并能构造或观察到配置组合。

做法：找单独看合理、组合后却静默关闭安全控制、削弱控制或让行为未定义的配置对。原文特别关注“被接受但无错误、无警告、无文档说明”的组合。修复建议包括配置加载时拒绝组合、重排检查、增加 guard。每个发现用动态 trace 确认。

预期结果：危险配置组合清单、trace 证据、修复建议。

#### A7. 人工复核并上报

前提：三遍或单遍已经产出候选发现。

做法：安全工程师复核动态 trace、补丁和影响范围；对上游项目提交补丁并跟踪版本修复。OpenSSH 案例中，维护者先在 10.5 把检查移到解析前，后在 10.6 把检查放进 parser 内，修复了客户端谎报 key type 和证书 CA 签名路径的问题。

预期结果：每个发现都有复核结论；可提交的补丁与跟踪记录。

#### A8. 可扩展检查：对比运行时日志与配置

前提：能拿到运行时日志和实际配置。

做法：用 Claude 对比运行时日志与配置，确认只启用了必需功能；禁用未使用的 parser、遗留协议和 dashboard，以低成本降低风险。

预期结果：可关闭的未使用功能清单，以及关闭后的回归结果。

### 做法 B：修复 bug 并猎取回归

#### B1. 准备 live deployment

把项目构建成可运行实例，并通过真实用户会用的接口访问。原文明确：复现 bug、证明修复、确认回归时，如果某一步产不出 live PoC，该步结果记为 **inconclusive**。

#### B2. 写 THREAT_MODEL.md

它告诉 agent 什么算漏洞、什么算回归；regression-hunt 会把该文件作为全局上下文传给每一个 agent 步骤，强制每步对照它下结论。原文要求覆盖以下要素（下面是据原文要素整理的模板骨架，不是原文逐字给出）：

```markdown
# THREAT_MODEL
## 关键资产（被攻破会造成实际损失的资产）
## 信任边界
## 访问控制
## 受支持的配置（supported configurations）
## 什么算 / 不算漏洞
## 一个有效 bug 报告必须提供的证据
```

#### B3. 写 PATCHING_GUIDELINES.md（或 AGENTS.md）

告诉 agent 和 patching-bugs“本项目希望补丁怎么写”。原文要求覆盖：

```markdown
# PATCHING_GUIDELINES
## 如何构建与测试本项目
## 补丁的规模上限（一次改动应该多大）
## 补丁应该落在哪个位置
## 如何呈现拟议改动
## 回归测试必须证明什么
```

原文强调：这两个文件越贴合项目、代码约定和运维风格，输出越好；patching-bugs 会读取项目自己的打补丁规范。

#### B4. 安装并启用两个插件，或手工执行

原文只给入口链接，无命令原文，不要臆造命令行。若暂不装插件，可把下面 B5–B8 步作为 agent 提示词/流程手工执行。

#### B5. 用 patching-bugs 处理一个 bug 报告

按原文三条要求执行：

- **三步证明**：同一份复现脚本跑三次——原始代码必须失败；打上补丁后必须通过；完整回退补丁后必须再次失败。第三步是关键，用来排除“其实是环境或测试改动让它通过的”。
- **不变量引导修复**：修被违反的底层安全不变量，而不是修这一个具体症状，以便覆盖同类 bug 的变体。
- **强制回归分析**：任何补丁都必须走一遍 regression-hunt，不允许跳过。

#### B6. 用 regression-hunt 检查改动

四步固定流程：

1. **枚举候选回归**：沿着 diff 改动点追踪其调用者，一直追到真实接口。
2. **在 live deployment 上复现每个候选**。
3. **用全新上下文的 agent 重放同一 PoC**（避免原 agent 的上下文偏见）。
4. **裁决 agent 判定**：所有前序步骤的结果汇总，由裁决步判断证据是否满足“回归”的定义。

#### B7. 设置裁决门槛（举证责任在 agent）

只有全部通过才报回归；裁决时必须排除：假阳性、不完整修复、潜伏 bug、改动前就存在的既有 bug 等。原文的定义：回归是“改动引入的新缺陷，破坏了原本正确且被支持的行为，且位于真实用户或攻击者可达的路径上”。

#### B8. 每一步使用固定输入/输出 schema

至少包含：

```text
claim（断言）
code revision（代码版本）
required check（要求的检查项）
raw evidence（原始证据，非摘要）
open questions（未决问题）
```

目的是让每一步去验证上一步的原始证据，而不是相信上一步的总结。

#### B9. 模块化使用

两个插件不必端到端跑，各步骤的技能可以单用或串联；只想做回归检查时，把 B6–B8 单独拿来跑一个 PR diff 即可。

#### B10.（可选）基线对照提示词

原文用这个作为对比基线，可以原样拿来测自己的流程是否真的更好：

```text
review the PR for regressions
```

## 怎么判断变好了

**最小试用方式：**

- 攻击面试用：选一个可构建、可跑测试的中型 Gated 或 Public 开源项目，固定版本并建立基线；先只跑一个 pass，建议从第二遍早期可达性开始；产出候选发现后，每个都用动态 trace 确认；只对默认配置可达性发现自动生成 gate，并在基线跑项目测试和黑盒回归，要求结果完全一致；其余变更交安全工程师复核。
- 回归猎取试用（1–2 天，不必装插件）：选一个可构建运行的中等规模仓库，取 5–10 个已合入的历史 bug 修复 PR，其中至少 2–3 个是已知引入过回归的；只为其中 1 个仓库写最小版 `THREAT_MODEL.md` + `PATCHING_GUIDELINES.md`（各 1 页以内）；对每个 PR 按 B6 四段流程跑，全部记录原始证据；再用基线提示词 `review the PR for regressions` 跑同一批 PR；人工对每条“确认回归”和“borderline”判定真伪，与已知历史结论对照；另取 1 个真实 bug 报告跑 patching-bugs 流程，重点验证第三步（回退后必须再次失败）能否被稳定执行。

**试用周期：** 攻击面以“完成一个 pass 并至少确认一个发现”为一个试用周期；原文没有给出耗时数据，不要按固定天数承诺。回归猎取最小试用为 1–2 天。

**可观察指标：**

- 攻击面：确认可达的意外入口数；认证前可达代码的行数或比例；默认配置下可达但非预期功能的代码量；静默关闭安全控制的配置组合数；测试差异数（默认配置 gate 要求为 0）；人工确认的误报数；补丁被上游接受的数量。
- 回归猎取：假阳性率（每条被报出的回归里人工判为真的比例，与基线提示词对比）；borderline 比例（被判“有嫌疑但证据不足”的数量，这是主要代价，不能算作成功）；已知回归的召回（那 2–3 个已知回归是否至少被判为 borderline，不接受静默漏过）；证据完备率（报出的每条回归中带 live PoC 且三步证明齐全的比例，原文要求 100%）；人工筛检成本（每个 PR 平均需要人工处理多少条候选）；可重复性（同一 PR 重跑两次，结论是否一致）。

**判断改善的最低标准：** 攻击面至少一个发现被动态 trace 确认；修复后默认行为测试差异为 0；认证前或默认配置可达的敏感代码明显减少。回归猎取若在 5–10 个 PR 上假阳性率明显低于基线、已知回归无一静默漏过、且人工筛检量可接受，则纳入标准步骤；若 borderline 比例过高或 live deployment 成本压不住，则退回 study，只保留“三步证明”“强制 live PoC”“威胁模型全局注入”这三条可迁移原则。若无法动态 trace 或测试基线不稳定，则降级为人工辅助审查，不采用自动 gate。

## 常见坑

- **没有 trace 和测试基线就上自动 gate。** 这会导致无法验证可达性，也可能改坏默认行为。原文的效果验证完全依赖动态 trace 与测试套件。
- **自动采用会改变非默认配置的 gate。** 原文明确要求这类变更交给人类决定。
- **把配置组合直接当成可利用漏洞。** 部分问题本身不立即可利用，配置组合可能非标准或低频，需要人工判断。
- **以为有现成 skill、提示词、安装命令或 schema 可以直接复制。** 两份调研都未给完整内容，必须自行编写并人工复核；不要臆造命令行。
- **只跑一遍就想覆盖三类问题。** 默认配置可达性、早期可达性、配置交互是三类不同问题，应分开跑，每遍用空上下文。
- **外推自动触发机制。** 原文只说明 skill 会自动跑三遍，没有说明可由时间、事件或状态变化触发，不要自行假设。
- **只修一个点，不做横向搜索。** 一个 hostname/wildcard 规则在反向 DNS 关闭时与 IP 比较导致 deny 规则 fail open 的模式，在 4 个无关项目中出现；修完一个点后应在同类项目中横向搜。
- **忽略“被接受但无错误、无警告、无文档”的配置组合。** 这是原文重点关注的类型，最容易在常规审查中漏掉。
- **把候选回归当确认回归。** 原文单次运行 58 个候选里确认 21 个，约 36% 精确率，作者自评“review was noisy”；人工仍需筛掉约三分之二的候选。
- **为了低假阳性牺牲召回却不算代价。** 严格证据要求会使部分已知回归被判为 borderline；必须单独统计 borderline 比例，不能只报假阳性下降。
- **没有 live deployment 仍强行跑 regression-hunt。** 原文要求枚举→live 复现→fresh-context 重放→裁决；产不出 live PoC 的步骤记 inconclusive，不要用静态阅读替代。
- **只修症状，不修被违反的不变量。** patching-bugs 要求不变量引导修复，否则同类变体仍会复发。
- **跳过强制回归分析。** 任何补丁都必须走一遍 regression-hunt，不允许跳过。
- **用摘要替代原始证据。** 固定 schema 要求 raw evidence，目的是让下一步验证上一步的原始证据，而不是相信总结。
- **省略 fresh-context 重放。** 原 agent 的上下文偏见可能让同一 PoC 被误判；重放要用全新上下文的 agent。
- **误以为 patching-bugs 已经过评测。** 原文明确说还在 building an evaluation，只有 regression-hunt 有对比数据；不要把未评测插件当成熟工具直接全量采用。

## 证据与来源

攻击面三遍法的数据来自本次调研《Using Claude to reduce the attack surface of code》：25 个开源项目、500 万+ 行代码、17,000+ 配置选项，其中 3,842 个与安全控制或功能配置相关；共发现 493 个问题；11 个 Gated 项目全部存在非预期可达代码；默认配置下 93 个不必要认证前表面、37 处认证前执行或记录状态、61 个静默削弱认证前控制的配置组合；162 个安全敏感配置组合被接受且无错误、无警告、无文档，94 个静默关闭安全控制，68 个是同一安全机制的不一致；一个 hostname/wildcard 规则在反向 DNS 关闭时与 IP 比较导致 deny 规则 fail open 的模式在 4 个无关项目出现；一个证书检查被另一配置项完全禁用，该组合存在 21 年；一个项目的 TLS 客户端证书选项在某些端点因命名空间不同被静默忽略；OpenSSH 案例：默认配置下未认证客户端可达约 4,500 行 ML-DSA-44 实验代码，约占默认 sshd 认证前代码的 16%，修复链条涉及 10.4、10.5、10.6 三个版本。

回归猎取的数据来自本次调研《AI agent fixed the bug, but what else did it change?》：复核 130+ 个 PR 中确认 21 个回归（16 个功能性、1 个性能、4 个构建/测试），没有一个是破坏安全防护的；单次运行 58 个候选里确认 21 个，约 36% 精确率，作者自评“review was noisy”；regression-hunt 相比基线提示词 `review the PR for regressions` 假阳性少 25%，95% 置信区间 14%–38%；案例点名 Scapy、GPAC、liboqs、validator.js。patching-bugs 尚未做评测，原文明确说“we're building an evaluation”，只有 regression-hunt 有对比数据。

只是作者主张、无数据支撑的部分：减少攻击面能一次性降低所有未知漏洞的风险；OpenSSH 这种高强度审计代码仍有问题说明方法有普遍价值；四原则（极简指导、模块化步骤、严格 schema、每条断言都要 live PoC）的有效性；“不变量引导修复能泛化到同类变体”；“文件越具体输出越好”。

局限：两份调研都是初始研究总结，不是完整论文；可复用 skill/插件安装命令/schema 定义未公开；结果依赖动态 trace、live deployment 和测试套件，原文未给误报率、成本、耗时（回归猎取给了假阳性对比但样本有限）；部分问题本身不立即可利用，配置组合可能非标准或低频；非默认配置变更需要人类判断；回归猎取的严格证据要求会带来召回下降（borderline 比例上升），深度绑定 Codex 生态，其他 agent 需自行复刻流程。

## 依据的调研

- [Using Claude to reduce the attack surface of code](../research/radar/2026-10-21/5617-using-claude-to-reduce-the-attack-surface-of-code.md)：值得一试，建议按原文的三遍法，在一个可构建、可动态运行且有测试基线的代码库上小范围试用：先清点入口与配置，再查默认配置可达性、认证前/协议状态前可达性、配置组合，所有发现用动态 trace 确认，默认配置 gate 必须通过项目测试与黑盒回归且结果不变。理由是流程具体且有 OpenSSH 案例和批量数据支撑，但完整 skill、提示词与配置尚未公开，需要人工复核。
