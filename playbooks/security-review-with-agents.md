# 合并安全补丁前，先用 AI 找出默认配置下就能走到的代码

> **未经实测**：本手册由 ai-work-radar 根据自动调研合并生成并持续修订，步骤尚未有人实际跑过。服务修订时基于自己保存的上一版重写，直接改这个文件会被覆盖；实测过的做法请写到 experiences/。
>
> 解决的问题：用一套三遍法，在可构建、可动态 trace 的代码库里找出默认配置下和认证前就能到达的敏感代码，并用动态 trace 与零测试差异证明修复没有改变默认行为。
> 先试这一步：选一个能构建、能跑测试的中型项目，固定版本并建立基线，先只跑第二遍（认证前/硬门前的早期可达性），每个候选发现都用动态 trace 确认。

## 解决什么问题

大型代码库里有一类风险很难靠常规功能审查发现：某些代码在发布默认配置下就能被未认证的人走到，却没有任何默认功能真正使用它；某些敏感逻辑运行在认证、点击或协议状态转换之前；还有些配置单独看都合理，组合起来却静默关闭了安全控制。

这篇手册给出一套可执行的三遍法：先查默认配置可达性，再查硬门之前的早期可达性，最后查配置组合。每个发现都用动态 trace 确认；默认配置下的修复必须通过项目测试与黑盒回归，且结果与基线完全一致。原文没有公开完整 skill、提示词和配置，所以这是一套需要人工复核的流程，不是一键工具。

## 适用与不适用

**适用：**

- 代码库可构建、可动态运行或可做 trace。
- 项目自带稳定测试套件，最好另有黑盒回归套件。
- 配置复杂、入口多，属于 Public 或 Gated 类型的大型项目。
- 有安全工程师能复核 trace、补丁和影响范围。
- 原文覆盖 C、C++、Java、PHP、Python，可作为语言范围的参考。

**不适用：**

- 代码库无法构建或无法动态 trace。
- 没有稳定测试基线，改完无法判断默认行为是否变化。
- 没有人能做安全复核，只能让 AI 自动改代码。
- 期望直接复制现成提示词或 skill。原文明确说完整 skill、提示词与配置尚未公开，可复用 skill 仍在集成到 OSS-Scanner。

## 前置条件

- 代码库的读取权限与修改权限。
- 可用的构建环境。
- 动态 trace 能力，用来确认某个入口或路径是否真的可达。
- 项目自带测试套件；最好再有一套黑盒回归套件。
- 配置清单、认证/协议状态机等安全上下文。
- 一名能判断影响范围的安全工程师。
- 固定版本，先建立基线，后续所有对比都基于同一基线。

## 操作步骤

先选做法：

- **做法 A：完整三遍法。** 适合时间、人力充足，目标是系统性缩减攻击面。按默认配置可达性、早期可达性、配置交互依次跑三遍。
- **做法 B：单遍最小试用。** 适合第一次试用或资源有限。原文的最小试用建议是从第二遍“早期可达性”开始，只处理一个 pass，先证明流程能产出可被 trace 确认的发现，再扩展到另外两遍。

无论选哪种，三遍都让 Claude 从空上下文开始，只带上一遍的短上下文，避免上下文污染。

### 1. 固定版本并建立基线

前提：代码库可构建、测试可跑。

做法：选定一个中型 Gated 或 Public 开源项目，固定版本，记录基线构建结果和测试结果。

预期结果：得到一份可复现的基线，后续每次修改都拿它对比。

### 2. 划定代码库类别，清点入口与配置

前提：已经明确“默认配置”是什么，以及项目预期提供哪些功能。

做法：先把目标归为 Public、Gated、Private 三类，再让 Claude 清点代码入口点和配置选项，形成清单，并标注哪些配置与安全控制或安全功能相关。

预期结果：入口点清单、配置选项清单、安全相关配置清单。原文在 25 个项目中清点出 17,000+ 个配置选项，其中 3,842 个与安全控制或功能配置相关，可作为量级参考，不是你必须达到的数字。

建议记录字段如下（这是自建记录模板，原文未提供提示词或命令）：

```text
入口点：文件/函数/触发条件/是否需要认证/是否默认启用
配置项：名称/默认值/安全相关与否/影响的代码路径
候选发现：编号/所属遍数/代码位置/可达路径/trace 证据/修复建议/是否改变非默认配置
验证：基线测试结果/修改后测试结果/黑盒回归结果/差异数
```

### 3. 第一遍：查默认配置可达性

前提：已有入口与配置清单，且能对候选路径做动态 trace。

做法：找“在发布默认配置下可达，但不被任何默认功能使用”的代码。对每个候选发现，用动态 trace 确认可达路径，不能只凭静态阅读下结论。确认后设计并实现一个 gate，把这段代码移到认证后、点击后、显式开启后或协议状态机更深处。

预期结果：候选发现清单、每个发现的 trace 证据、对应的 gate 补丁。

### 4. 验证默认行为不变

前提：第一遍已经产出默认配置 gate。

做法：在基线版本上运行项目自带测试套件和黑盒回归套件，要求修改后的构建结果与基线完全一致。会改变非默认配置的 gate 不要自动采用，交给人类决定。

预期结果：测试差异为 0；非默认配置变更单独列出，等待人工判断。

### 5. 第二遍：查早期可达性

前提：同样需要动态 trace 能力。

做法：找在任何配置下运行于硬门之前的敏感且复杂代码。硬门包括认证；也包括无需受害者交互就能触发的路径，以及协议状态转换之前的路径。修复建议包括：把配置检查移到解析之前、增加 guard 强制状态顺序、在配置加载时拒绝危险组合。每个发现仍用动态 trace 确认。

预期结果：早期可达路径清单、trace 证据、修复补丁或修复建议。

### 6. 第三遍：查配置交互

前提：已有配置清单，并能构造或观察到配置组合。

做法：找单独看合理、组合后却静默关闭安全控制、削弱控制或让行为未定义的配置对。原文特别关注“被接受但无错误、无警告、无文档说明”的组合。修复建议包括配置加载时拒绝组合、重排检查、增加 guard。每个发现用动态 trace 确认。

预期结果：危险配置组合清单、trace 证据、修复建议。

### 7. 人工复核并上报

前提：三遍或单遍已经产出候选发现。

做法：安全工程师复核动态 trace、补丁和影响范围；对上游项目提交补丁并跟踪版本修复。OpenSSH 案例中，维护者先在 10.5 把检查移到解析前，后在 10.6 把检查放进 parser 内，修复了客户端谎报 key type 和证书 CA 签名路径的问题。

预期结果：每个发现都有复核结论；可提交的补丁与跟踪记录。

### 8. 可扩展检查：对比运行时日志与配置

前提：能拿到运行时日志和实际配置。

做法：用 Claude 对比运行时日志与配置，确认只启用了必需功能；禁用未使用的 parser、遗留协议和 dashboard，以低成本降低风险。

预期结果：可关闭的未使用功能清单，以及关闭后的回归结果。

## 怎么判断变好了

**最小试用方式：** 选一个可构建、可跑测试的中型 Gated 或 Public 开源项目，固定版本并建立基线；先只跑一个 pass，建议从第二遍早期可达性开始；产出候选发现后，每个都用动态 trace 确认；只对默认配置可达性发现自动生成 gate，并在基线跑项目测试和黑盒回归，要求结果完全一致；其余变更交安全工程师复核。

**试用周期：** 以“完成一个 pass 并至少确认一个发现”为一个试用周期。原文没有给出耗时数据，不要按固定天数承诺。

**可观察指标：**

- 确认可达的意外入口数。
- 认证前可达代码的行数或比例。
- 默认配置下可达但非预期功能的代码量。
- 静默关闭安全控制的配置组合数。
- 测试差异数，默认配置 gate 要求为 0。
- 人工确认的误报数。
- 补丁被上游接受的数量。

**判断改善的最低标准：** 至少一个发现被动态 trace 确认；修复后默认行为测试差异为 0；认证前或默认配置可达的敏感代码明显减少。若无法动态 trace 或测试基线不稳定，则降级为人工辅助审查，不采用自动 gate。

## 常见坑

- **没有 trace 和测试基线就上自动 gate。** 这会导致无法验证可达性，也可能改坏默认行为。原文的效果验证完全依赖动态 trace 与测试套件。
- **自动采用会改变非默认配置的 gate。** 原文明确要求这类变更交给人类决定。
- **把配置组合直接当成可利用漏洞。** 部分问题本身不立即可利用，配置组合可能非标准或低频，需要人工判断。
- **以为有现成 skill 或提示词可以直接复制。** 原文未给完整提示词、配置或命令，skill 仍在集成中，必须自行编写并人工复核。
- **只跑一遍就想覆盖三类问题。** 默认配置可达性、早期可达性、配置交互是三类不同问题，应分开跑，每遍用空上下文。
- **外推自动触发机制。** 原文只说明 skill 会自动跑三遍，没有说明可由时间、事件或状态变化触发，不要自行假设。
- **只修一个点，不做横向搜索。** 一个 hostname/wildcard 规则在反向 DNS 关闭时与 IP 比较导致 deny 规则 fail open 的模式，在 4 个无关项目中出现；修完一个点后应在同类项目中横向搜。
- **忽略“被接受但无错误、无警告、无文档”的配置组合。** 这是原文重点关注的类型，最容易在常规审查中漏掉。

## 证据与来源

来源：本次调研《Using Claude to reduce the attack surface of code》。

**原文给出的数据与案例：**

- 25 个开源项目、500 万+ 行代码、17,000+ 配置选项，其中 3,842 个与安全控制或功能配置相关。
- 共发现 493 个问题。
- 11 个 Gated 项目全部存在非预期可达代码；默认配置下 93 个不必要认证前表面、37 处认证前执行或记录状态、61 个静默削弱认证前控制的配置组合。
- 162 个安全敏感配置组合被接受且无错误、无警告、无文档；94 个静默关闭安全控制；68 个是同一安全机制的不一致。
- 一个 hostname/wildcard 规则在反向 DNS 关闭时与 IP 比较导致 deny 规则 fail open 的模式，在 4 个无关项目出现。
- 一个证书检查被另一配置项完全禁用，该组合存在 21 年。
- 一个项目的 TLS 客户端证书选项在某些端点因命名空间不同被静默忽略。
- OpenSSH 案例：默认配置下未认证客户端可达约 4,500 行 ML-DSA-44 实验代码，约占默认 sshd 认证前代码的 16%；修复链条涉及 10.4、10.5、10.6 三个版本。

**只是作者主张的部分：**

- 减少攻击面能一次性降低所有未知漏洞的风险。
- OpenSSH 这种高强度审计代码仍有问题，说明方法有普遍价值。

**局限：**

- 这是初始研究总结，不是完整论文。
- 可复用 skill 尚在集成 OSS-Scanner，原文未给完整提示词、配置或命令。
- 结果依赖动态 trace 和测试套件，原文未给误报率、成本、耗时。
- 部分问题本身不立即可利用，配置组合可能非标准或低频。
- 非默认配置变更需要人类判断，不能全自动采用。
