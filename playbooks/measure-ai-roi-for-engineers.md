# 在加 AI 预算前，用四件套指标验证有没有换来交付速度

> **未经实测**：本手册由 ai-work-radar 根据自动调研合并生成并持续修订，步骤尚未有人实际跑过。服务修订时基于自己保存的上一版重写，直接改这个文件会被覆盖；实测过的做法请写到 experiences/。
>
> 解决的问题：团队把 AI 花费或 PR 数增长当成产出提升，缺少分人、带护栏的前后对照，容易把更多更大的 PR 误读为提速。
> 先试这一步：选一个 5–10 人、工作类型可比的团队，取采用 AI 前连续 4–8 周（或去年同期）的数据，先算基线：PR/人/周、每 PR 变更行数中位数、合并 lead time 中位数、每月关闭用户故事数，并按人列出分布。
> 最近修订：2026-10-21

## 解决什么问题
AI 工具花得更多、PR 数更多，不等于交付更快。The Pragmatic Engineer 访谈 27 家公司后，给出了一组已被真实团队使用、同时带有反例的度量口径：人均每周 PR 数、每个 PR 的变更行数、PR 合并节奏、每月关闭用户故事数；同时记录人均月 AI 花费与预算上限。关键不是看团队均值，而是分人看分布：原文有团队 PR 数从 1.5 涨到 4 PR/人/周，但被一位生产率暴涨的工程师拉高，其他人变化不大；也有团队 PR 频率持平而 PR 体积涨到 3 倍；还有团队 PR 数上升但合并速度几乎没变。本手册把这些口径整理成一次可执行的前后对照，帮你在加预算、扩团队或宣布 AI 有效之前，先看见这些反例。

## 适用与不适用
适用：
- 已经开始或准备引入 AI 编码工具，想判断是否值得继续加预算。
- 有 PR 系统和代码评审流程，能拿到每个 PR 的作者、变更行数与合并时间。
- 有一个 5–10 人、工作类型可比的团队，且能取到采用 AI 前连续 4–8 周或去年同期的数据。
- 有用户故事/看板数据，愿意用业务价值口径补充代码口径。

不适用：
- 拿不到采用前基线，或同期还改了其他流程、组织，无法做前后对照。
- 团队工作差异极大，PR 数不可比。
- 想用它做模型/工具横向选型：原文只提到 Claude / Opus 5.5 是花费主流向，Cursor、Codex、GitHub Copilot 也被提及，但没有横向效果对比，不能据此选型。
- 想外推到全公司：样本 27 家公司、非随机、多为作者人脉且多数匿名，单家结论不可外推；Big Tech 部分在本次抓取中被付费墙截断，本手册不判断。
- 想把分人数据直接当绩效结论：原文只支持用它识别均值被个别人拉高，没有提供绩效评估方法。

## 前置条件
- PR 数据：每个 PR 的作者、变更行数、合并时间；能取采用 AI 前连续 4–8 周或去年同期。
- 成本数据：每人每月 AI 花费（$/dev/month）、所用模型/工具版本、预算上限与提额审批路径。
- 业务数据：每月关闭用户故事数；若用 Scrum/Kanban，最好有连续可比基线（原文案例有 5 年可比）。
- 质量护栏：人工评审记录、每条 PR 的评论数、回滚/返工记录；已有代码评审规范。
- 若要走预算上限流程：公司允许按人设上限；有可运行的 token 浪费诊断 skill（原文描述的 skill 会扫描 too many loops、subagents 等）。
- 一个 5–10 人、工作类型可比的团队，试用期 8–10 周，期间尽量不改其他流程。

## 操作步骤
1. 选团队和基线窗口。选一个 5–10 人、工作类型可比的团队，取采用 AI 前连续 4–8 周的数据，或直接用去年同期（原文各案例普遍用“比一年前”作对照）。预期结果：你手里有一张采用前基线表，而不是凭印象判断。
2. 按人采四件套，不按团队平均。至少输出中位数与分位数，并逐人列出前后差值。可复制下面这份口径清单：
```
按人统计，至少输出中位数与分位数：
1) PRs/dev/week
2) 每个 PR 的变更行数（PR size）
3) PR 合并 lead time / merged PR velocity
4) 每月关闭的用户故事数（user stories closed/month）
成本：$/dev/month；记录模型/工具版本与预算上限
```
预期结果：能看出改善是发生在多数人身上，还是只被一位高产出者拉高。原文明确警告过后者。
3.（可与度量并行）设预算上限并让花费可见。原文的两种形态：软上限（填一张短表说明理由即可提额，原文称“很容易绕过”）与硬上限（如跨国公司的 $4,000/人/月、AI SaaS 公司的 $2,000/人/月，后者很少获批提额）。原文给出的花费参照区间：低花费 < $300/人/月，中等 $300–500，高 $1,000+，个别到 $3,000；这些是受访者口述，不是行业基准。原文案例还用公开的 `#ai-limits` 频道自动点名接近上限与花费最高的人，原文形容“有点像公开处刑”，采用前要评估团队接受度。预期结果：每个人知道自己的上限与提额路径。
4. 提额前先跑 token 浪费诊断。原文描述的做法：
```
提额前置：运行一个 AI skill，扫描常见烧 token 的原因——
是否在跑太多循环（too many loops）、是否在用子代理（subagents）等，
并给出修复建议。
若诊断未发现可优化项，再向经理提交预算提升申请。
```
预期结果：提额申请不是因为“跑太多循环”或“子代理滥用”造成的浪费。原文还提醒给非工程角色也上限制：量化交易公司里交易员大量用 Claude，工程师在给他们补“限流”，防止“无意中跑出昂贵查询”。
5. 建 PR 审查代理，但保留人工评审。审查代理专门指出“过大的 PR”“啰嗦的代码”等模式，按原有 PR 体积与质量标准把关；原文案例称这部分效果不错。同时保留人工评审：一家 2,500 人 SaaS 公司的工程师说，人工评审仍能抓到代理与代理式评审漏掉的东西——完全不必要的改动、比应有体量大 10 倍的改动。预期结果：代理负责模式化提醒，人保留质量否决权。
6. 引入 AI 或继续使用，跑 8–10 周，期间尽量不动其他流程。每周用同一口径复算，并记录模型版本与人均花费。原文提醒指标对模型版本敏感：换成 Opus 5.5 后花费预期减半，6–7 月花费见顶回落。预期结果：你有一条按周可比的时间序列，跨期比较能注明版本。
7. 让每人每周记一条“AI 省下的时间”日志，只记四类任务：客户问题初筛、代码考古式调研、POC 原型、历史包袱清理。原文给出的收益量级：初筛从有时一整天到几分钟完成代理工作 + 最多 1 小时人工核验；代码调研从翻 Slack/设计文档/PR 历史的一两天到几分钟；复杂特性 POC 从一两周到几小时；一家 2 人 .NET 团队清理 5–10 年 backlog，自称每人每周约 60 个 PR（约每天 10–15 个），从原来每天 1–2 个提升 5–10 倍。预期结果：日志能复核“省下的时间”落在哪些任务上；以上均为案例自述，不是保证值。
8. 试用结束，输出分人前后对比表。表里至少放：每人的 PR/周、PR 体积、用户故事关闭数、AI 花费的前后差值；再给团队中位数与分位数。预期结果：你能回答“是多数人变快，还是一个人变快；PR 是不是变成更多更大的块；合并是不是更快；业务故事是不是更多”。
9. 按判定门槛决定继续、收缩或改流程。改善信号（报告设计的门槛，非原文数据）：团队 PR/人/周中位数上升，且 PR 体积中位数未同比例膨胀；或用户故事月关闭数上升；四类任务日志显示可复核的小时级节省。无改善模式（原文真实出现过的反例）：PR 数上升但合并 lead time 不变；PR 数持平而 PR 体积涨 2–3 倍；只有 1 人产出暴涨而中位数不动。护栏：人工评审每条 PR 的评论数、被回滚或返工的 PR 比例、评审中被判为“完全不必要”的改动数。若护栏恶化而吞吐上升，不判为改善；按原文那家 2,500 人公司的经验，应保留人工评审并把“完全不必要改动、体积大 10 倍”作为检查项。成本侧同时看：人均月花费是否在预设上限内；若需提额，是否已走过 token 浪费诊断。

## 怎么判断变好了
最小试用：1 个 5–10 人团队，基线取采用 AI 前 4 周以上或去年同期，试用 8–10 周；期间尽量不动其他流程；每周同一口径复算；让每人每周记一条四类任务的时间节省日志。

看三个层次：
- 代码吞吐：团队 PR/人/周中位数上升，且 PR 体积中位数未同比例膨胀；合并 lead time 不恶化。
- 业务价值：每月关闭用户故事数上升。原文有一家跨国团队用 Scrum+Kanban 与计划板，连续 5 年可比，2–3 月起关闭量达 3 倍，并首次出现“关闭数 > 新增数”；这是单案例，不是保证值。
- 成本与护栏：人均月花费在上限内；提额已做 token 浪费诊断；人工评审评论数、回滚/返工比例、完全不必要改动数不恶化。

判定门槛是报告设计的，不是原文验证过的标准。原文数据只说明这些反例会真实出现，不能保证你的团队一定改善。若只有 PR 数上升而合并速度不变，或 PR 数持平而体积涨 2–3 倍，应按“钱没换来速度”处理，而不是宣布提速。

## 常见坑
- 只看 PR 数或团队均值。原文有团队 PR 从 1.5 涨到 4 PR/人/周，但被一位生产率暴涨的工程师拉高，其他人变化不大。
- 把 PR 体积膨胀当产出。某 5,000 人公司 PR 频率持平但体积到 3 倍；作者只是自问“可能因为 LLM 啰嗦”，这不是已验证结论。
- 把合并速度没变当成提速。原文指出有团队 PR 数量涨了但合并速度没怎么变。
- 用厂商数据当独立证据。CodeRabbit 的周 PR +113%、月 PR +127%、同批 2 万开发者 +128%，以及 Gitar 的“AI 原生团队 60+ PR/人/周”，都来自工具厂商，用户群本身是“已采用 AI 代码工具”的偏样本。
- 把 27 家公司当行业基准。样本非随机、多为作者人脉、多数匿名，且所有 PR 数与 AI 花费的因果都是前后对比，无对照组、无随机化，不能证明因果。
- 忽略模型版本。换成 Opus 5.5 后花费预期减半、6–7 月花费见顶回落；跨时间比较要注明版本。
- 忽略订阅真实成本。订阅制会掩盖真实成本，部分补贴结束后账单可能涨 5–10 倍。
- 软上限容易被绕过，硬上限提额前不做诊断会浪费。原文说软上限填短表即可提额、“很容易绕过”；硬上限如 $2,000/人/月很少获批提额。
- 在复杂代码库里把思考外包给模型会做出奇怪的东西。原文受访者说，收益最明显的是 greenfield 项目或“没有 OSS 阻塞”的工作；即便是 Opus 5.5 这样的前沿模型，一旦人把思考外包给它，仍会做出奇怪的东西。
- 把“PR 吞吐尚未被开发者 gaming”当事实。这是作者个人判断，没有验证。
- 公开点名高花费者要谨慎。原文案例确实开了公开频道自动点名，但原文自己形容“有点像公开处刑”。
- 不要用本文推断 Meta / NVIDIA / Apple 的做法。Big Tech 部分在本次抓取中被付费墙截断。

## 证据与来源
本手册唯一依据是 The Pragmatic Engineer 付费文章《What’s the ROI of software engineers’ spending on AI?》的调研报告。作者 Gergely Orosz 访谈 27 家公司的工程负责人与资深工程师，并拿到 CodeRabbit、Gitar 两家工具的聚合数据。

- 四件套度量：口径取自原文案例，报告将其整理为操作步骤。原文最常用 PR/人/周；PR 体积 3 倍、合并速度不变、用户故事 3 倍、PR 1.5→4 被个别人拉高，均出自原文案例。数字是受访者口述或厂商数据，非独立审计。
- 预算上限与 token 浪费诊断：原文案例。软/硬上限、$4,000、$2,000、$1,200、$1,500、$2,200、$3,000、$25,000 等金额均为受访者口述；诊断提示词是原文描述的做法；公开 `#ai-limits` 频道也是原文案例。
- PR 审查代理与人工评审：原文案例。一家酒店业公司建代理按原有 PR 体积与质量标准把关，原文称“这部分效果不错”；一家 2,500 人 SaaS 公司的工程师说人工评审仍能抓到完全不必要的改动、比应有体量大 10 倍的改动。
- 四类任务收益：原文案例自述。客户初筛、代码考古、POC、backlog 清理的时长变化均来自受访者说法，不是对照实验。
- 最小试用 8–10 周、改善/无改善门槛、分人对比表：本报告设计，原文没有成体系实施步骤，也没有给出验证协议。
- 作者主张或推测：“PR 吞吐是尚未被开发者 gaming 的指标”是作者个人判断；“文化决定 PR 节奏”是作者推测（原文用 I suspect）；“PR 体积 3 倍可能因为 LLM 啰嗦”是作者自问（原文用 I wonder if）。
- 数据示例：CodeRabbit 周 PR +113%、月 PR +127%、同批 2 万开发者 +128%；Gitar 称“AI 原生”团队达到 60+ PR/人/周；2.5 万人公司 PR 从约 4 升至约 8 PR/人/周；2,500 人 SaaS 公司不足 5% 的人触到 $1,200 上限；100 人 AI SaaS 公司设 $2,000 配额、速度未变；2 人 .NET 团队 $3,000/人/月、约 60 PR/人/周；酒店业 200 工程师默认上限 $1,500，一人 9 月花 $2,200。
- 局限：27 家公司非随机、多为作者人脉、多数匿名；CodeRabbit 与 Gitar 数据来自工具厂商；付费文章 Big Tech 部分截断；没有 token 计价或订阅摊销细节；指标对模型版本高度敏感。
