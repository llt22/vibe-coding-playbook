# 让 AI 写的仓库文档不再各说各话：检查器出诊断，agent 照着修

> **未经实测**：本手册由 ai-work-radar 根据自动调研合并生成并持续修订，步骤尚未有人实际跑过。服务修订时基于自己保存的上一版重写，直接改这个文件会被覆盖；实测过的做法请写到 experiences/。
>
> 解决的问题：AI 写文档比人评审快，而过期版本号、多处不一致的事实又会被 agent 读回去当上下文，这篇手册给出用文档约定加检查器诊断、再让 agent 按诊断修复的可复制流程。
> 先试这一步：挑一个 AI 参与写文档最多的仓库，在根目录跑 `seiso init`、人工复核 `seiso.toml`，再跑 `seiso check`，把诊断数量和分类存成基线。
> 最近修订：2026-10-02

## 解决什么问题

AI 写 Markdown 文档的速度超过人工评审的速度。这些文档又会被编码智能体当作下一次修改的上下文读回去——一处过期的版本号，或者三份副本里只改了一份的字段列表，会同时误导人和智能体。调研报告把这条链路写成一个可检查的问题：给文档定一份“每篇声明一种 kind、每个事实只有一个归属地、长期页面不记录变化更快的值”的约定，再用检查器按约定出诊断，让 agent 照着诊断修。

## 适用与不适用

适用：

- 用 Git 管理、且存在（或即将有）AI 生成 Markdown 文档的仓库；
- 想让“文档一致性”变成可复制的命令、配置和成文约定，而不是评审时凭感觉看；
- 能接受先用 1–2 周，在一个仓库的一到两个文档目录里小范围试。

不适用 / 边界：

- seiso 不猜“文字读起来是不是机器写的”，格式和拼写检查交给别的工具；
- preview 规则是实验性的、会误报，只能在本地试，不能进 CI 门禁；
- 约定本身在 1.0.0 之前是临时性的（provisional），方向仍在 issue #37 开放讨论，规则可能变动；
- 原文没有任何“用了之后文档变好”的实测数据，效果要靠自己在仓库里采集。

## 前置条件

- 一个有 Git 的仓库，里面有（或即将有）AI 生成的 Markdown 文档；
- 本机可装 Rust / Python / Node 其中一种工具链；
- 能人工复核 `seiso init` 生成的配置，不要照单全收；
- 接入自动化前，先确认 stable 规则在你的仓库里结果可接受；
- Claude Code hooks / pre-commit / CI 的具体配置内容不在本次提供的原文里，需查阅仓库的 `docs/guides/integrations.md`；
- 不装工具也能只按约定整理文档（约定是独立发布的规范，另配 worked examples 和 adoption guide）。

## 操作步骤

### 做法 A / 做法 B 怎么选

- 做法 A：只用约定，不装工具，人工按六条规则整理文档。适合文档量小、还没想清楚要不要引入检查器的仓库。
- 做法 B：装 CLI，跑 `seiso check`，把诊断交给 agent 修，结果稳定后再接自动化。适合 AI 生成文档较多、已经出现“同一事实多处不一致”的仓库。
- 建议先用做法 A 借约定人工整理一遍（或至少读一遍约定），再上做法 B；不要跳过人工复核直接接 CI。

### 做法 B 的编号步骤

1. 安装（任选一种）。前提：本机可装 Rust / Python / Node 其中一种工具链。

```sh
cargo install seiso
uv tool install seiso    # or: pipx install seiso
npm install -g @scarletkc/seiso
```

   PyPI 和 npm 包内含预编译二进制，覆盖 Apple silicon / Intel 的 macOS、glibc 或 musl（如 Alpine）的 Linux x64 与 arm64、Windows x64 与 arm64。其他平台用 cargo；PyPI 包在其他平台也可用但从源码构建，需要 Rust 工具链。若从源码检出运行，用 `cargo run -- <command>`。
   预期结果：`seiso` 命令可用。

2. 在仓库根目录初始化配置。前提：处于 Git 仓库根目录。

```sh
seiso init
```

   它会在仓库根写入 `seiso.toml`，内含建议的排除项、kind 映射和文档站点条目。
   预期结果：得到 `seiso.toml`。**原文明确要求先复核这些内容再依赖结果。**

3. 人工复核 `seiso.toml`。逐项检查排除项、kind 映射、文档站点条目是否符合仓库实际。
   预期结果：一份你认可其 kind 映射和排除项的配置。这一步不做，后面的诊断会带错误的 kind 归属。

4. 跑一次检查，并把结果存成基线。

```sh
seiso check
```

   默认只跑 stable 规则（已满足其 promotion criteria 的规则）。
   预期结果：得到一份诊断列表。把诊断数量与分类（按规则 code）记下来，作为后续对比的基线。

5. 按诊断修文档。前提：agent 能读到 `seiso check` 的输出。原文说每条诊断会给出问题位置和修法，agent 仅凭 seiso 的输出就能修掉大部分发现项；当修复需要判断（比如两个页面里哪个拥有某个事实）时，诊断会把这个决策点指出来。
   预期结果：诊断逐条消除；需要判断的点由人裁决。注意“agent 能自修大多数”是作者主张，没有给出比例、案例或评测方法，要在自己的仓库里验证。

6. 需要时查规则、查文档模型。

```sh
seiso rule --all      # 列出所有规则及其状态
seiso rule <CODE>     # 解释某条规则并给示例
seiso parse           # 只看文档模型，不跑规则
```

7. 预览规则只在本地试，不要进 CI 门禁。

```sh
seiso check --preview
```

   原文说明预览规则是实验性的、会误报，只在加 `--preview` 时运行，并明确要求“先在本地试，不要把预览规则放进 CI 门禁”。
   预期结果：知道预览规则在你的仓库里误报是否高到不可用。

8. 接入自动化。前提：步骤 4 的 stable 规则在你的仓库里结果可接受。原文在 Integrations 文档中列出三类接入方式：Claude Code hooks、pre-commit、CI。**具体配置内容不在本次提供的原文里**，需查阅仓库的 `docs/guides/integrations.md`。把 stable 规则放进 CI，预览规则排除在外。

9. （可选，做法 A）不装工具：直接按下面的六条约定整理文档，项目可以只按规范整理。规范在 1.0.0 之前为临时性（provisional），且与 seiso 工具分别版本化。

六条约定（做法 A 和 B 都适用）：

1. 每篇文档声明一种 kind（如 `howto`、`reference`、`adr`），只写这个 kind 该写的东西——how-to 给步骤，设计为什么这样属于 ADR。
2. 每个事实只有一个归属地，其他页面链接过去而不是复述。
3. 长期存在的页面不记录比页面本身变化更快的值，如版本号、部署状态、计数。
4. 指针要指名文件或符号，别让读者自己去搜。
5. 完成的页面不面向“当初提需求的人”说话，也不叙述它自己或它描述的工作是怎么做出来的。
6. 工具无法做的判断要连同理由写下来；没有理由的例外本身就算违规。

## 怎么判断变好了

原文没有给出任何改善数据，下面这些指标需要由本方案自行采集。

最小试用方式（建议 1–2 周，限定在一个仓库的一到两个文档目录内）：

1. 选一个 AI 参与写文档最多的仓库，记录当前状态作为基线。
2. 按上面的步骤 1–3 安装、`seiso init`、人工复核 `seiso.toml`、`seiso check`。
3. 保存 baseline 的诊断数量与分类（按规则 code 统计）。
4. 让智能体仅凭诊断输出逐条修，人工只裁决诊断点名的判断项（如哪个页面拥有某个事实）。
5. 修完再跑一次 `seiso check --preview`，只看本地，判断预览规则是否值得关注（不进门禁）。
6. 如果结果可接受，再接 pre-commit 或 Claude Code hook；把 stable 规则放进 CI，预览规则排除在外。

可观察指标：

- stable 规则诊断数的下降幅度（修复前 vs 修复后），以及一周后再跑是否反弹；
- 智能体自主修复比例 = 无需人工介入即可消除的诊断数 / 总诊断数；用于检验“agent 能自修大多数”这一主张在你的仓库是否成立；
- 需要人类裁决的判断点数量，衡量规范与仓库实际情况的摩擦；
- 人工评审文档时发现的“同一事实多处不一致”类问题数量是否下降；
- 接入自动化后，问题是在提交时就拦下，还是仍在评审阶段才被发现；
- 预览规则的误报率是否高到不可用。

退回条件：若 stable 规则诊断数长期不降、或智能体自主修复比例很低、或判断点摩擦过大，说明这套约定在你的仓库不成立，应退回“只借用约定做人工整理”的用法，而不是继续加自动化。

## 常见坑

- 把 `seiso init` 生成的配置照单全收。原文明确要求人工复核，错误的 kind 映射或排除项会让后面的诊断失真。
- 把预览规则放进 CI 门禁。原文明确说预览规则会误报，只能在本地试。
- 把 stable 当永远稳定。规范在 1.0.0 之前是临时性的，方向仍开放讨论，规则可能变动。
- 指望找到“用了之后文档变好”的实测数据。原文没有；效果只能自己采基线对比。
- 把“agent 仅凭 seiso 输出就能修掉大多数发现项”当成已证事实。这只是作者主张，没有比例、案例或评测方法。
- 跳过人工裁决。遇到“哪个页面拥有某个事实”这类判断点时，诊断只会点名，不会替你决定。
- 以为装了工具就有完整接入方案。Claude Code hooks / pre-commit / CI 的具体配置不在本次提供的原文里，需另查 integrations 文档。
