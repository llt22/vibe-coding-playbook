# 让 agent 做架构清点：只要数字，不要意见

> **未经实测**：本手册由 ai-work-radar 根据自动调研合并生成并持续修订，步骤尚未有人实际跑过。服务修订时基于自己保存的上一版重写，直接改这个文件会被覆盖；实测过的做法请写到 experiences/。
>
> 解决的问题：把架构审查从主观评论改成可核对、可复测的计数任务，找出重复实现、重复公式和副本不一致。
> 先试这一步：选一个最令人痛苦的系统，在 AGENTS.md / CLAUDE.md 里写 2–3 条可计数的架构规则，让 Claude 只按这些规则清点文件数、公式副本数和不一致处数。
> 最近修订：2026-10-03

## 解决什么问题

架构审查很容易变成“这里应该重构”“这块不够清晰”这类主观评论，难核对、难复测。这条做法把审查改成窄口径的清点任务：先把架构规则集中写进项目级 `AGENTS.md` / `CLAUDE.md`，只挑一个最令人痛苦的系统，让 Claude 仅针对这些规则输出计数——每个持有其逻辑的文件、每个公式的每个副本、每个副本不一致的地方。结论由数字构成，天然可对比、可复测。

## 适用与不适用

适用：

- 项目里已有或可新建 `AGENTS.md` / `CLAUDE.md`，且会被 agent 读取。
- 你有一个“最令人痛苦的系统”：改动最频繁、最容易出错的子系统，收益集中在这里。
- 你怀疑代码库里存在跨文件的重复实现、同一公式多份副本、同一常量多处来源。
- 你能人工核对它报出的清单：至少知道一部分真实的重复实现，用来校验准确率。

不适用：

- 还没有可计数的架构规则。本次材料只到线程第 12 条，前 11 条的规则清单缺失，需要自己补全规则后才能落地。
- 想让它直接给重构方案或改代码。这里做的是清点与一致性审计，不是写新代码。
- 无法人工核对结论的场景：错报、漏报都判断不了，数字再漂亮也不能用。
- 期望照抄完整方案。原文没有完整提示词全文、示例输出，也没有代码库规模前提，只能当作方法骨架。

## 前置条件

- 一个会被 agent 读取的项目级指令文件：`AGENTS.md` 或 `CLAUDE.md`。
- 一份可计数的架构规则清单。每条尽量是“某类业务逻辑只允许有一个实现文件”“每个公式只允许有一份定义”“同一常量只允许一处来源”这种形态。原文只说“将以下规则放入”，具体规则需自己补。
- 选定一个“最令人痛苦的系统/目录”。
- Claude 能读到目标系统的代码上下文。
- 一份你已知的重复实现清单，用于核对它报出来的内容。

## 操作步骤

1. **备好指令文件。**
   前提：项目里已有或可新建 `AGENTS.md` / `CLAUDE.md` 这类会被 agent 读取的项目级指令文件。
   做法：把你要守的架构规则逐条写进去，每条尽量可计数。
   预期结果：Claude 每次都能看到同一套规则，而不是只在本次对话里临时输入。
   注意：本次材料没有采集到规则清单本身，下面只是形态示例，需替换成你自己的规则。

```markdown
# 架构规则（示例，需替换）
- <某类业务逻辑> 只允许有一个实现文件。
- 每个公式只允许有一份定义。
- 同一常量只允许有一处来源。
```

2. **选一个系统。**
   只选“最令人痛苦的系统”——改动最频繁、最容易出错的子系统。
   预期结果：审查范围可控，收益集中在真正痛的地方。

3. **提出审查请求。**
   让 Claude 以 staff engineer（资深/员工级）的视角对该系统做架构审查，并在请求里明确限定“仅针对这些规则”，避免它泛泛而谈。
   预期结果：请求被约束在指令文件里的规则上。

4. **强制数字输出。**
   要求它给出三类计数，而不是感受：每个持有其逻辑的文件（列出文件 + 数量）、每个公式的每个副本（列出副本位置 + 数量）、每个副本不一致的地方（列出不一致点 + 数量）。
   可复制的提示词模板如下（依据原文要点改写，原文未给出完整提示词文本，请按自己项目替换）：

```
读取本仓库的 AGENTS.md / CLAUDE.md，只以其中的架构规则为审查标准。

目标系统：<最令人痛苦的系统/目录>

请以 staff engineer 的身份对该系统做一次架构审查，仅针对上述规则。

输出要求：只要数字，不要意见。
1) 每个持有其逻辑的文件：逐个列出路径，并给出总数。
2) 每个公式的每个副本：逐个列出位置，并给出总数。
3) 每个副本不一致的地方：逐个指出差异点，并给出总数。

不要给改进建议，先把清点结果给我。
```

预期结果：拿到可核对、可复测的清单，而不是一段“应该重构”的建议。

5. **人工核对后再决定改什么。**
   用你已知的重复实现去校验它报出的清单，确认后再动代码。
   预期结果：分清哪些是真实问题、哪些是错报或漏报，再决定改动范围。

## 怎么判断变好了

可观察指标：

1. **可核对准确率**：它报出的“持有某逻辑的文件/公式副本”中，有多少与你的实际认知一致；错报、漏报各多少。
2. **信息增量**：报出的不一致处里，有多少是你此前不知道的。
3. **可复测性**：按清单改完后重跑同一提示词，副本数与不一致数是否下降；若两次跑出的数字波动很大，说明该方法还不稳定。
4. **成本**：一次审查的耗时/额度消耗 vs 人工清点的耗时。

最小试用方式：选一个你已知存在少量重复实现的小系统（例如某个工具模块），在 `AGENTS.md` 里只写 2–3 条可计数的规则，跑一次上述审查，把它的清单与你已知的事实逐条对照。

试多久：原材料没有给出时长或规模前提。可以先按“一次审查 + 改完后重跑一次”作为最小验证周期，再根据可复测性决定是否继续。

如果第 1 项错误率高，或第 3 项不可复现，就退回人工清点，把这条降级为“思路参考”。

## 常见坑

- **规则清单缺失**：本次材料只有线程第 12 条，前 11 条里的规则清单没采集到，不能照抄，只能自拟规则。
- **规则不可计数**：写成“代码要清晰”这类主观规则，输出又会回到意见。
- **铺开多个系统**：原文要求只选一个“最令人痛苦的系统”，铺开会让清点不可核对。
- **只要意见不要数字**：不限定“仅针对这些规则”和“只要数字”，容易得到泛泛的架构评论。
- **跳过人工核对**：清单可能错报、漏报，直接照着改代码风险高。
- **把一次输出当结论**：原文没有任何执行结果数据（实际查出多少处不一致、修复后降低了多少），数字本身也需要复测。
- **当成完整方案**：原文没有完整提示词全文、示例输出或代码库规模前提，这条更接近“可照做的方法骨架”。
- **指望它给改进建议**：这次做的是清点与一致性审计，不是重构。
