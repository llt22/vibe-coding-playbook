## Jev Review：评分与缺陷定位

### 历史 AI 回答 · 原会话第 110 行

来源：`~/.codex/archived_sessions/rollout-2026-09-18T14-44-29-01a0b342-6ac9-7d40-a304-d391eacc8461.jsonl:110`。

看完了。**这个项目有实际价值，但它不是“Jev 自动做代码审查”，而是给编码 Agent 加一个持续质量评分环。**

**它怎么工作**

Agent 完成一段代码后，把任务、diff、相关文件和项目约束交给 `jev_review`。一次 Jev 请求会同时完成：

- 19 个质量维度
- 每个维度判断是否适用
- 1–10 分评分
- 从预设列表选择一个主要弱点

共计 **57 个结构化判断**。然后 Agent 自己检查代码、修改、跑测试，再次评分，比较修改前后的变化。

例如：

```text
实现功能
→ 测试
→ Jev 评分
→ Agent 分析为什么“可靠性 5.2”
→ 修改
→ 再测试
→ 再评分
→ 检查是否提高、有没有其他指标退步
```

**做得比较好的地方**

- 不生成模糊的长篇 review，而是返回稳定的结构化评分。
- 没有合成一个容易误导的“总分”。
- `previousEvaluation` 只在本地计算差值，不发送给 Jev，减少旧分数影响新判断。
- Jev 缺少必要答案时直接报错，不伪造成功。
- API 有超时、有限重试、Schema 校验和明确错误。
- 不会自动读取整个仓库，只发送 Agent 明确提供的代码。
- 项目自带的类型检查、13 个测试和构建均通过。

**目前最大的不足**

1. **不告诉你具体哪里错了**

它只能说：

```text
Reliability: 5.4
主要弱点：错误传播存在问题
```

不会指出具体文件、行号和调用链。真正定位问题仍然依赖主 Agent。

2. **还没有效果基准**

现有测试主要验证 MCP、数据转换、重试和错误处理，全部使用模拟 Jev 响应。仓库没有证明：

- 能多发现多少真实 bug
- 修改后最终代码是否更好
- 同一份代码多次评分是否稳定
- 与普通 LLM code review 相比是否更准确或更便宜

3. **连续评分可能受模型更新干扰**

现在固定使用 `jev-latest`。如果两次评分之间 Jev 模型升级，分数变化可能来自模型，而不是代码。当前开放 PR 正在增加模型版本记录和固定模型能力，这是一个真实且重要的问题。

4. **弱点只能从预设选项中选择**

开放 issue 已经指出：通用弱点列表无法表达 Rails 等框架特有问题。因为是 Choice 判断，选项里没有的问题，Jev 就不能返回。

5. **“local-first”需要准确理解**

MCP 服务在本地运行、没有作者的中转服务器，但任务、diff 和文件内容仍会发送到 TypeSafe API，并不是完全离线。

**我的判断**

这个项目最适合定义成：

> **编码 Agent 的独立质量仪表盘和回归信号。**

它比普通“让另一个 LLM 再 review 一遍”更结构化，尤其适合判断一次重构究竟改善了复杂度、耦合和可维护性，还是只是表面变漂亮。

但现阶段不能把它当作最终 reviewer、质量门禁或安全审计工具。真正值得验证的是：拿一批包含已知缺陷的真实改动，测试它能否稳定地让正确维度降分，以及 Agent 根据这些分数修改后，缺陷修复率是否提高。项目很新，截至 **2026 年 9 月 18 日只有 4 个提交**，当前更接近设计扎实的早期原型。

## Jev Ultrafast：计时与结果核验边界

### 历史 AI 回答 · 原会话第 771 行

来源：`~/.codex/archived_sessions/rollout-2026-09-18T10-46-23-01a0b268-6ea1-78d3-b023-da1c7d970c71.jsonl:771`。

**这个项目有真东西，但它证明的是一套浏览器 Agent 的工程方案，不是“Jev 单独把网页操作做到了 7 秒”。**

它每轮把页面整理成带编号的可操作元素，让 Jev 在一次请求里选“做什么”和“操作哪个元素”；只有需要输入文字时，才调用另一个小模型。执行前还会检查页面是否变化、目标是否仍可操作。Google Flights 示例在结束后另查路线、日期和结果，不能只凭模型说 `DONE` 就算成功。不过，**通用 Agent 本身不会自动做这套业务结果核验**，那是示例额外写的。([github.com](https://github.com/browser-use/jev-ultrafast))

**7.073 秒值得关注，但要读准边界**：计时包含 17 次 Jev 请求、两次文字模型调用和页面等待；不包含初始导航及事后的独立核验。优化前后各跑了 3 次，同一航班任务的中位耗时从 9.450 秒降到 7.092 秒。提速很大一部分来自减少浏览器读取与协议调用，不能全算成 Jev 的功劳；样本也不足以证明它在任意网站都可靠。报告里的 `$0.00006272` 只是文字模型费用，**不是整次任务成本**。([raw.githubusercontent.com](https://raw.githubusercontent.com/browser-use/jev-ultrafast/main/docs/performance.md))

对我们最有用的启发是：**让快模型只在明确候选项中做判断，把执行约束和结果核验留给程序。** 这和先前 `model-native` 的检索实验思路相通，但浏览器操作与知识库检索是不同任务，不能拿“7 秒”和 Top-4 证据覆盖率直接比较。我的判断：这是值得借鉴的可运行 demo，还不是通用浏览器 Agent 的可靠性证明。

## Fast Jev Compaction：遗漏工具输出的风险

### 历史 AI 回答 · 原会话第 1077 行

来源：`~/.codex/archived_sessions/rollout-2026-09-18T10-10-08-01a0b247-3bfb-7390-9e61-4f972e6a3474.jsonl:1077`。

结论：**思路有价值、工程实现认真，但目前更像高质量实验插件，还不能证明比传统摘要更可靠。**

### 它实际怎么做

- 用户和助手正文保持原样。
- 只处理已经配对的 `tool_use` 与 `tool_result`。
- 每个工具调用向 Jev 问两个问题：
  - 还需不需要保留“调用发生过”。
  - 是否需要逐字保留完整结果。
- 默认保留最近 6 条消息。
- 结果可被完整保留、截成前 300 字符，或者连同调用一起删除。
- Jev 失败、响应异常、压缩不足 25% 时，回退到 Claude Code 内置摘要。

### 最大问题

**Jev 判断工具结果能否删除时，根本看不到结果正文。**

发送给 Jev 的状态只有类似：

```text
Read src/a.ts → ok, 4213 chars (omitted)
```

模型只能根据工具名、参数和后续对话猜测结果是否重要，却不能发现结果里尚未被讨论的重要细节。

仓库自己的实验已经暴露了这个问题：

- 一次 201-turn 对比中，该方案召回率为 `11/12`。
- Claude 内置摘要为 `12/12`。
- 丢失的是位于文档末尾、只在工具结果中出现的事实。
- 作者尝试为被删除部分额外生成摘要，召回恢复到 `12/12`，但压缩耗时从约 `440–615ms` 上升到 `30–76s`，最终没有合并。

这不是普通参数问题，而是当前架构的信息盲区。

### 做得好的地方

- 工具调用和结果按 ID 成对处理，不会留下孤立结果。
- 用户约束和助手正文不会被模型重写。
- 大状态会逐级缩减，并显式报错而不是静默截断。
- 大任务会拆批并发，响应缺失或格式错误直接失败。
- 有压缩收益下限，避免付费后只减少少量上下文。
- 日志记录每次判断概率，具备一定可观测性。
- 本地验证通过：类型检查、构建及 29 个测试全部通过。

### 仍需注意

- 默认 `0.5` 阈值对 Read、Bash 错误、测试结果等一视同仁；旧错误记录也可能被删除。
- 只保留结果开头 300 字符，不保留尾部，恰好容易丢掉日志结论和文档尾部信息。
- 没有显式请求超时；网络请求挂起时可能拖住压缩流程。
- 大会话会重复发送完整状态。真实记录中 165 个调用需要 5 次请求。
- “one fast request”的宣传只适用于较小会话。
- Claude Code 接入依赖早期功能钩子。仓库称 `2.1.274` 验证成功，但开放 issue 显示 `2.1.272 Windows` 安装后为 `Hooks (0)`，会出现安装成功却不工作的情况。
- 核心 npm 包版本为 `0.2.0`，插件 manifest 为 `0.3.0`，版本目前没有完全同步。
- `npm audit` 的 5 个漏洞都来自 Vitest/Vite 开发依赖；核心包没有运行时依赖，因此不是主要生产风险。

### 我的判断

这个项目证明了 **Jev 很适合做上下文“候选删除器”**，但没有证明它适合独立决定永久删除。

更合理的生产结构是：

1. 确定性保留用户约束、错误、修改记录和任务状态。
2. Jev 对低风险工具输出做候选过滤。
3. 给模型看结果的 head、tail 和结构化摘要，而不是只给字符数。
4. 被删除内容保留可恢复索引或短期缓存。
5. 用真实长任务测试压缩后的任务成功率，而不只测 token 减少率。

所以它不是噱头，但真正的价值是**启发式过滤层**，不是替代完整上下文管理。
