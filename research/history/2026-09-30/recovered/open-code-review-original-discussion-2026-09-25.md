**OpenCodeReview (`alibaba/open-code-review`)** 是阿里巴巴开源的 AI 代码审查（Code Review）CLI 工具，源自其内部运行两年的 AI 代码审查助手。

---

### 1. 核心定位与解决的痛点

通用 Agent（如直接用 Claude Code / Cursor / 通用 Skill）做代码审查时常见三大问题：
1. **大改动漏审/偷懒**：文件过多时 Agent 容易选择性忽略部分改动。
2. **行号与位置漂移**：大模型生成的 issue 容易与真实 diff 行号、文件路径脱节。
3. **Prompt 驱动不稳定**：纯自然语言规则受提示词波动大，难以精准调优。

---

### 2. 架构设计：确定性工程 × Agent 混合驱动

- **确定性工程（强约束）**：
  - **文件过滤与智能打包**：基于工程规则过滤无关文件，并将关联文件打包（如多语言配置、接口与实现），按单元派发给 sub-agent 隔离并发审查。
  - **规则引擎匹配**：基于模板引擎为不同文件路径匹配专属审查规则。
  - **外挂定位与反思模块**：独立的行号定位与评论反思（Reflection）组件，校准位置并过滤低质量误报。
- **Agent（动态召回与决策）**：
  - 支持调用工具读取完整文件、检索仓库、跨文件溯源上下文。
  - 针对代码审查裁剪的专属工具集与 Prompt。

---

### 3. 运行模式与集成方式

| 模式 | 工作方式 | 适用场景 |
|---|---|---|
| **默认模式（OCR 驱动）** | 配置 LLM API Key，直接由 `ocr` 命令行驱动模型分析 | 独立本地审查、CI/CD 流水线（GitHub Actions / GitLab CI 等） |
| **委托模式（Delegate）** | `ocr` 仅负责文件拆包、规则解析，交由宿主 Coding Agent（Claude Code / Cursor / Codex / Kimi Code 等）用自身模型评审 | 已接入 AI IDE / CLI 且不希望额外配置 LLM Key |
| **全量扫描（Scan）** | `ocr scan` 扫描指定目录或全仓（无需 Git diff / commit 历史） | 历史代码审计、无版本控制的目录体检 |

---

### 4. 关键特性与基准表现

- **基准测试（AACR-Bench）**：在 50 个开源仓库、200 个 PR 的测试中，相比纯通用 Agent，**准确率（Precision）与 F1 更高，Token 消耗约为 1/9**；设计上倾向于**低误报（Low Noise）**，以适度召回率换取高准确度。
- **会话与断点恢复**：支持 `ocr session list` 和 `--resume <session-id>` 恢复中断的审查。
- **可视化与导出**：支持 JSON 导出及本地 Web 会话查看器（可标记已修复/忽略）。

---

### 5. 快速上手

```bash
# 安装
npm install -g @alibaba-group/open-code-review

# 配置模型供应商（默认模式）
ocr config provider
ocr config model

# 常用审查命令
ocr review                             # 审查工作区未提交变更
ocr review --from main --to feature    # 审查分支分叉改动
ocr scan --path src/                   # 目录全量安全/规范扫描
ocr review --format json -o res.json   # 导出结构化结果
```

### 一、 为什么说它不是“花架子”？（做对了什么）

很多团队直接拿 Claude / GPT 挂个 GitHub Action 做 CR，通常不出两周就会被工程师痛骂并关掉。核心原因在于：**模型幻觉 + 废话点评 + 行号对不上 + 噪音疲劳**。

OpenCodeReview 的价值不在于它用了多神仙的模型，而在于它**用确定性工程包裹了不可控的 LLM**：

1. **直击痛点：以“高准确率（Precision）”换“召回率（Recall）”**
   - **痛点**：自动化 CR 工具一旦有 30% 以上的无意义点评（如风格挑刺、无病呻吟），工程师就会彻底无视所有评论（Alert Fatigue）。
   - **它的解法**：在基准设计中明确放弃对召回率的极致追求，通过反思与过滤机制，**宁可漏报，绝不乱报**。这才是企业级工具能活下来的设计取舍。

2. **解决大 PR 的“上下文爆炸与漏审”**
   - **痛点**：给通用 Agent 塞 50 个文件的 Diff，模型不仅 Token 消耗暴增，还会开始“偷懒”，随机跳过文件。
   - **它的解法**：通过工程算法对变更文件进行**精准分词、依赖打包与分治**，每个包启动隔离的 Sub-Agent 并发审查。这把原本 $O(N)$ 甚至更高复杂度的上下文塞模型问题，变成了确定性的分治工程。

3. **解决行号漂移与“虚空对线”**
   - **痛点**：LLM 经常在评论时把行号算错 3~5 行，或者评论的内容与当前行的代码对不上。
   - **它的解法**：剥离出专门的**行号定位与锚定模块**，由代码解析器校验 AST/Diff 行号，强制校准后再输出结构化 Comment。

4. **1/9 Token 消耗降本**
   - 裁剪了通用 Agent 不必要的工具调用链路（通用 Agent 喜欢频繁查不相关的目录或空转），把工具链收敛在“代码跳转、全文检索、关联文件查阅”，显著降低了 CI 调用的 API 账单。

---

### 二、 它做不到什么？（真实局限性与天花板）

评价一个工具不能只看宣传，必须看它的不可逾越边界：

1. **无法感知“业务语义与架构意图”**
   - 它能看出 `if (x == null)` 可能会空指针，或者某个 Goroutine 缺少取消机制；
   - 但它**绝对看不出**“这个字段应该存分而不是存元”、“这个状态流转跳过了风控审计”、“这个接口设计破坏了 DDD 聚合根契约”。
2. **深度跨文件/跨服务的语义追踪有限**
   - 虽然有 Repo 检索工具，但面对复杂微服务调用链、隐式事件驱动或深层继承体系，Agent 的召回能力依旧是启发式的，无法匹敌带全局符号图谱的静态分析引擎。
3. **依赖规则配置的维护成本**
   - 如果完全零配置（开箱即用），输出仍会偏向通用代码缺陷；要发挥最大威力，团队需要按模块、路径配置 Review Rules，这本身存在工程配置成本。

---

### 三、 在研发流程中的真实生态位

```
[ Linter / ESLint / GolangCI-Lint / SonarQube ]  -->  确定性语法、规范、安全基线扫描（0 误报，毫秒级）
                     ↓
[ OpenCodeReview / AI Reviewer ]                -->  边界条件、并发竞争、异常吞没、资源泄露、测试用例遗漏（智能反模式拦截）
                     ↓
[ 人工 Code Review ]                            -->  业务正确性、架构演进、可维护性、契约设计、安全合规
```

---

### 四、 选型与落地建议

- **非常值得用**的场景：
  - 团队处于快速扩张期，初中级工程师占比高，容易出现低级并发/边界/资源泄露 Bug；
  - 团队已有 CI/CD 流程，希望在人工 CR 介入前先机筛一遍“低级代码异味”；
  - 配合 Cursor / Claude Code 使用**委托模式（Delegate）**，让本地 Agent 借助其分治能力做本地 Pre-commit 自检。
- **没必要抱过高期望**的场景：
  - 指望它替代资深工程师做业务逻辑把关与架构评审；
  - 团队代码库本身极度缺乏文档、契约混乱，模型缺乏上下文，容易沦为纯语法层面的挑刺。
