# Are Harnesses Worth the Cost?

- 结论：**值得一试**。先按模型能力决定行为 harness 的运行节奏——用着便宜/不稳定的模型就在开发全程挂着契约化的 guides+sensors，用前沿模型则把这套确定性检查只在最终验收门禁跑一次。理由是实验中 GPT-6 Luna 从无 harness 的 3/10 提升到有 harness 的 10/10，且单次估算成本 $0.273 低于无 harness 的 GPT-6 Sol 的 $0.406，而 Sol 加 harness 只是把成本推到约 7 倍、通过率没有变化。

## 是什么

这是一篇实验报告：作者 Naresh Jain 让编码智能体在相同 brief 下构建同一个后端服务（product discovery 的 BFF，含 HTTP API、下游 Order API 调用、超时降级、Kafka 发布），对比“有/无行为 harness”两种条件下的成功率、可靠性、token、耗时与估算成本，并分别在一个前沿模型（GPT-6 Sol）和一个成本优化模型（GPT-6 Luna）上各跑 10 组配对实验。

行为 harness 沿用 Birgitta Böckeler 的框架：**guides**（事前引导，降低第一次就出错的机会：OpenAPI/AsyncAPI 契约、请求-响应示例、实现 skill）加 **sensors**（事后观测，帮助自我纠正：契约符合性检查、API 测试、副作用断言、CTRF 报告、API 覆盖率报告）。开发用内层循环（给 harness 组持续反馈），评估用外层循环（178 项自动化验收测试，内层拿不到答案）。

核心结论是条件性的：harness 不是对所有模型都划算，模型能力改变的是**传感器什么时候跑**，而不是要不要有独立验证门禁。

## 具体做法

前提：任务有清晰的功能/架构/技术/接口描述；有一批可机器执行的接口契约；能提供隔离的运行环境与独立的验收套件。

1. **写详细的应用 brief**。说明服务该做什么、架构与技术约束、外部接口、响应形状和失败行为，但把代码级实现细节留给 agent。本例中被明确写进 brief 的行为包括：下游创建超时要变成 deferred request，返回 202 和可轮询的响应头链接；瞬时搜索失败返回 429 并给可用的恢复间隔；依赖不可用或事件发布失败返回 503；成功响应要遵守请求的过滤条件否则 502；availability search 成功后只把**第一个**返回的产品发布到 Kafka（若发布全部产品，agent 就可以不做选择逻辑而蒙混通过）。

2. **把接口约定写成机器可读契约**，作为 guides：OpenAPI 覆盖 BFF 与下游 Order API，AsyncAPI 覆盖 Kafka。契约与 brief 互补，不是另一套需求。

3. **为接口配请求-响应示例**，覆盖下游超时、畸形载荷、过滤违规、重试序列、Kafka 事件确认。

4. **先校验示例再跑测试**，保证 guides 与 sensors 不互相矛盾：

   ```
   examples validate
   ```

   该命令检查示例载荷是否符合各自的 API 规格；测试再用这些规格和示例去检查实现，让 sensors 始终对齐其来源 guides。

5. **让检查来源独立于实现者**。契约检查由提供的规格确定性生成，示例加行为 fixture 定义取值与副作用断言；明确要求 agent 保留这些输入和验证 helper，失败时去查实现或执行设置，**不得削弱期望值**。否则 agent 自己解释需求、自己写测试、失败后再改期望，会把同一个误读或遗漏同时写进实现和测试。

6. **配置契约驱动的下游 mock**，把下游交互变成可执行的：agent 能对定义好的下游响应、失败、恢复序列来跑自己的实现；另有 helper 校验时序约束。

7. **提供一个 API 开发 skill**，给出实现实践、依赖模拟、行为验证、以及如何诊断和响应失败。

8. **把 harness 挂到项目自己的测试命令上**（这是 agent 的入口）。该命令依次：校验配置与示例 → 跑必需的构建与单元检查 → 启动下游 mock → 让应用对着 mock 启动 → 跑契约/HTTP 响应值/副作用检查。

9. **让反馈回路可诊断**：报告摘要指出具体的契约、响应值、交互不匹配；agent 按 skill 指示诊断，改实现或执行设置，用 helper 只重跑受影响的场景，通过后再跑完整套件作为最终门禁。注意本实验中**这个回路依赖 agent 主动调用这些工具，并非每次代码编辑后自动运行**。

10. **外层评估与开发分离**。开发停止后，用外层评估 harness 对 178 项功能检查（含非法输入、下游失败、恢复序列、成功请求产生的消息）跑一次；评估 harness 控制自己的下游 fixture 与消息捕获，不依赖应用的开发测试。内层 harness 从未接触评估套件的答案。

11. **隔离每次尝试**：每个尝试跑在独立 Docker 容器里，有自己的 workspace 和一份全新的、按尝试区分的 Codex home；除共享认证与语言依赖缓存外，不带入此前任何会话、记忆、插件、skill 或状态。

12. **按模型能力选择传感器节奏**（作者的实践建议）：
    - 成本优化模型结果不稳定时：**开发全程挂行为 harness**，把漂移当场抓住；
    - 前沿模型能一次做对时：**只在验收前把同一套自动化测试作为确定性最终门禁跑一次**，用最小开销拿到独立检查；
    - 不论哪种：都保留独立验收检查，并把精力投在清晰的规格与示例上——检查只能执行人类编码进去的期望，覆盖不到的地方靠人工审查。

13. **保留可复核证据**：skill 要求留下依赖交互与最终验证结果的可审查证据，完成与否不能只凭 agent 自述。

作者用的是 Specmatic 实现这套 harness，但指出等价的契约测试与服务虚拟化工具可以提供相同能力。

## 对应的研究问题

**1. 能力发现**：harness 不只是“让好模型更好”，而是把原本不可靠的便宜模型纳入可用范围——GPT-6 Luna 无 harness 时 10 次只成功 3 次，挂上 harness 后 10/10，达到与前沿模型相同的可靠性。另外原文记录了一些超出预期的实现行为：异步 202 工作流被端到端接通（监控端点、跟踪 pending 请求、用原 idempotency key 重试下游创建、在轮询 URL 上给出最终载荷）；Kafka 发布与搜索事务绑定（等 Kafka 确认后才响应 200，发布失败/超时转 503）；两个模型都做了防御性的边界校验（入站载荷按 schema 校验，下游响应结构与业务约束在用之前校验）。

**2. 任务匹配**：模型能力决定传感器节奏，而不是决定要不要传感器。任务特征上，本次验证的是绿地 Java 服务、brief 异常详细、契约明确；作者明确表示未验证遗留代码修改、其他语言/推理设置、模糊或不完整需求。

**3. 条件供给**：需要提供——详细的 brief；OpenAPI/AsyncAPI 契约；请求-响应示例；实现 skill；MCP 工具与 agent plugin；契约驱动的下游 mock；配置校验（例如校验环境变量）；一个可被 agent 调用的统一测试命令；隔离的容器与干净的 agent home；以及一套独立、答案不外泄的验收套件。

**4. 主动推进**：本实验的内层回路**不是**自动触发的，需要 agent 在开发中主动调用工具；外层评估在开发停止后自动跑。作者提出但**未测量**“只在最终门禁跑一次”的工作流开销与它捕捉到差异的频率。

**5. 效果验证**：判据是“应用能启动且通过全部 178 项外部验收测试”，可靠性 = 重复运行中产出可接受应用的一致性；token、耗时、估算成本是独立的效率指标。验证的关键设计是期望值来源与实现者解释分离（确定性计算型检查，不靠 agent 自述或 LLM 判断），并用 CTRF 报告、API 覆盖率报告、依赖交互证据支撑完成判定。

## 证据与局限

原文给出的数据（10 次运行均值，成本为按 token 用量和模型价格折算的 API 等价估算，非实际账单）：

| 模型 | harness | tokens | 耗时 | 估算成本 | 通过 |
|---|---|---|---|---|---|
| GPT-6 Sol | 有 | 11,331,970 | 19m53s | ~$2.679 | 10/10 |
| GPT-6 Sol | 无 | 1,076,371 | 6m51s | ~$0.406 | 10/10 |
| GPT-6 Luna | 有 | 22,933,648 | 35 min | ~$0.273 | 10/10 |
| GPT-6 Luna | 无 | 5,860,736 | 15m56s | ~$0.086 | 3/10 |

其他数据：harness 让 Luna 每次平均多花 17,072,912 tokens、19 分 4 秒自主运行时间、约 $0.187；harness 的 Luna 总 token 约为无 harness Luna 的 3.9 倍；无 harness 的 Luna 通过 94.8% 的功能检查；失败的 Java 应用也都至少通过 178 项中的 144 项。失败聚类：超时边界上 4 个应用返回 503、2 个返回 400、1 个返回 429（应为 202+monitor link），7 次运行因缺 monitor URL 引发次生失败，3 次 Kafka 消息实际送达但违反线上契约（Spring JSON 序列化器多加 `__TypeId__` 头；`"categories": null` 而该可选字段存在时必须是数组），另有 415（brief 明确要求 400）、非法请求落到通用 500、缺失 monitor 返回错误表示、配置名分歧（生成客户端读 `ORDER_API_API_KEY`，启动脚本提供 `ORDER_API_KEY`）导致普通创建返回 503。探索性运行中 Claude Sonnet 4.6、Claude Opus 4.6、Gemini 3.8 Flash（低推理努力）也都在无 harness 下一次完成。

属作者主张而非实验证明的部分：“executable attention”“attention lapse”是作者对失败机制的**解释性框架**，作者自己也说实验未确立因果关系（例如超时识别失败，只记录了错误响应，没记录实际客户端异常，所以“窄异常类型匹配”只是可能解释）。

适用边界（作者列明）：每个模型 10 组配对运行、1 个绿地 Java 服务、两个模型都是低推理努力；样本不足以判断长期失败率或“得到一个可接受应用的总成本”；brief 异常详细，未测试模糊需求、遗留代码、其他语言/推理设置；harness 的 guides 与 sensors 是**一起**加的，无法区分各自贡献。成本口径**不含**契约、示例、断言与 harness 的编写、评审和维护投入，也不含发现、诊断、修复不可接受结果的人力，作者未测量跨实现复用带来的摊薄。

## 怎么试、怎么验证

**最小试用方式**（照搬本文的配对设计，缩小规模）：

1. 选一个接口契约清晰、有明确外部验收标准的绿地服务（不要先拿遗留系统试）。
2. 写详细 brief，把不显眼的行为（超时降级、异步发布、精确错误码、过滤语义）明确写出来。
3. 做契约 + 示例 + `examples validate` 校验 + 契约驱动 mock + 一个统一的测试命令（校验配置 → 构建/单元测试 → 起 mock → 起应用 → 跑契约/响应值/副作用检查）。
4. 准备一套**独立**的验收套件（fixture 与消息捕获自持），不让开发侧接触答案。
5. 至少选一个成本优化模型和一个前沿模型，各跑 10 次配对（有/无 harness），每次在干净容器/干净 agent home 中开始。
6. 记录每轮的通过与否、token、耗时、估算成本，并把失败按位置聚类（协议边界、韧性路径、集成缝）。

**判断有没有改善的指标**：

- 主指标：外部验收通过率（必须应用能启动且全部检查通过才算通过，部分通过不算）。
- 可靠性：同一模型重复运行中通过次数的一致性（原文是 10 次里的通过数）。
- 效率：每次尝试的 token、墙钟时间、估算成本——注意把 harness 的编写/维护成本单列，别混进单次运行成本。
- 经济性判据：有 harness 的便宜模型单次成本是否低于无 harness 的前沿模型，同时通过率不下降（原文 $0.273 vs $0.406）。
- 缺口指标：失败是否集中在契约与示例覆盖不到的地方——这些应当转成新增契约/示例或人工审查清单，而不是放宽断言。
