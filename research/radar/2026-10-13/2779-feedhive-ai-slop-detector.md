## 是什么

一个「AI 味写作」模式清单：120 条模式，分 9 类（词表 20、套话 15、句式 22、结构与节奏 12、比喻 6、内容实质 12、格式与标点 10、聊天机器人残留 8、社媒/LinkedIn 15）。每条模式给出简短说明、一个 Bad 例子和一个大白话改写（Better）。

仓库同时提供三种落地形态：
- Claude Code / Codex 等 agent 用的 skill（`skills/ai-slop-detector`）；
- 结构化数据 `patterns.json`，配 `node scripts/build.mjs` 重新生成 README 和 skill；
- 浏览器端免费检测工具（README 里的外链），粘贴草稿即可查。

作者明确划了边界：**它不判断文本是人写还是 AI 写**（人也这么写，模型也可以被要求避开），也**不是单条命中即判死刑**——「一条模式在人类写作里很正常，一段里出现好几条才是 AI 味」。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

1. **装成 agent 技能（首选）**。前提：本机已装 Claude Code（或 Codex 之类能读仓库、写文件的 agent），且能访问 GitHub。
   最省事的做法是把仓库地址交给 agent，让它自己装：
   ```text
   Install the AI Slop Detector skill from https://github.com/FeedHive/ai-slop-detector
   ```
   或者自己手动装（原文给的是 Claude Code 路径）：
   ```sh
   git clone https://github.com/FeedHive/ai-slop-detector.git
   cp -r ai-slop-detector/skills/ai-slop-detector ~/.claude/skills/
   ```
   前提：`~/.claude/skills/` 目录是你 Claude Code 的 skills 目录，否则换成实际路径。

2. **写之前先约束**。在让 AI 起草前，把清单交给它并要求「写的时候避开里面每一条模式」。这一步决定的是生成时少产生 AI 味，而不是事后返工。

3. **写之后做检查（最实用的一步）**。把 README（或 skill）和草稿一起贴进对话，要求它逐条列出命中的模式，并给出**命中所在的那一行**。原文对这一步的说明是「ask for every pattern it finds, with the line it found it in」——要求带行号是关键，否则模型只会给你一堆泛泛评价。

4. **按 Bad→Better 的对照改写**。清单的价值不在「你错了」，而在每条都给了替换方向，规律大致是三类：
   - 把抽象名词换成具体数字/对象：V-04 `plays a pivotal role in growth` → `drives 40% of signups`；
   - 把装饰动词换成事实陈述：V-05 `The results underscore the importance of testing` → `Testing caught three bugs before launch`；
   - 把元话语（告诉读者这段多重要）整段删掉：C-08 `Surprisingly, the simple version won` → `The simple version got twice the clicks`。

5. **只做快速体检时**用浏览器版：把草稿粘贴到 README 里给出的免费工具页面即可（前提：文本不涉密、可以贴到外部网页）。

6. **接进自己的工具链**。前提：本机有 Node。
   ```sh
   # 编辑 patterns.json（增删/改写模式）
   node scripts/build.mjs   # 重新生成 README 和 skill
   ```
   许可为 MIT，可以改、可以塞进自己的产品。

7. **用它做中文写作时的前置动作**：清单原文是英文词表和英文句式，直接照抄到中文上会大批误报，需要自己建一张中英映射表（如「深入探讨/赋能/抓手/闭环/值得注意/在当今快速变化的时代」对应 V-01、V-07、V-15、V-20 一类），映射表也放进 `patterns.json` 用同一套 build 流程维护。

## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）

**1. 能力发现**：原文支撑的「没想到可以交给 AI」的事有两件——一是把 **AI 生成内容的事后质检**交给模型（逐条列命中模式并给行号），二是把清单当**生成前的约束条件**而不是事后修稿。另外，`patterns.json` + `build.mjs` 这类「结构化内容 → 生成分发物」的做法，本身就是可以交给 agent「安装并维护」的任务。

**2. 任务匹配**：原文给了明确的分工建议——agent 形态（Claude Code/Codex）走 skill 安装；聊天应用走「贴 README + 贴草稿」；自有产品走 `patterns.json` 结构化数据。三种场景对应三种集成方式，而不是一种方式硬套。

**3. 条件供给**：需要提供给 AI 的是——完整清单（README 或 skill）、待查草稿全文、以及「逐条 + 带行号」的输出要求。原文没有提到需要额外权限、工具调用或外部数据。清单本身是静态文本，因此上下文供给的成本很低，这也是它可以随手塞进任何对话的原因。

**4. 主动推进**：原文**没有**任何关于定时、事件或状态触发的内容，也没有提到持续运行、后台检查或与编辑器/CI 集成的机制。从给出的材料看，它只能按需手动调用。这条按原文无法支撑，属于潜在空白点而非原文能力。

**5. 效果验证**：原文**没有**给任何效果指标、评测或前后对比数据。唯一可用作验证口径的是作者自己给出的判据：「单条模式在人类写作里正常，一段里出现好几条才读起来像 slop」——这实际上提供了一个可计数的指标（单位文本内的命中模式数 / 单段内命中数），但作者并未据此做过测量。

- 每条模式都带一个 Bad/Better 对照例子，这是可核对的样板而非口号；

- 线索给出的仓库指标：34 stars。

**只是作者主张的部分**：

- 这些模式「读起来像 AI 味」——基于观察，没有语料统计佐证；
- 用清单能改善写作结果——原文完全没有效果数据、A/B 或案例。

**局限与适用条件**：
- 原文自认这是**启发式清单，不是作者归属检测器**，人也这么写，单独一条命中不算问题；把它当「是不是 AI 写的」判定去用是误用。
- 清单是**英文写作导向**（词表、句式、LinkedIn 套路都基于英文语料），迁到中文需要自己重建映射，否则误报率会很高。
- 社媒/LinkedIn 那一类（15 条）适用面窄，写邮件、写文档的人大部分用不上。
- 对「内容实质」类（C-01 到 C-12）的检查，本质上是在要求写作者给出事实和数字——工具只能指出缺失，填不了内容。

## 怎么试、怎么验证（最小试用方式和判断有没有改善的指标）

**最小试用（半天内可完成）**：
1. 挑一篇最近由 AI 起草、你觉得「读着有点假但说不出哪里假」的稿子，留一份原文做 baseline。
2. 把清单 + 原文贴进对话，要求逐条列出命中的模式并给行号，记下：命中模式总数、集中在哪几类、有没有同一段里命中多条。
3. 只改被指出来的地方（按 Better 那列的方向：换具体数字/名字/动作，或直接删掉整句），得到 v2。
4. 再跑一次同样的检查，对比命中数；同时把 baseline 和 v2 去掉标题后盲评（自己隔一天再看，或让同事二选一）：哪一版更像人写的。
5. 如果装了 Claude Code skill，可以再做一个对照：装 skill 前后各让模型写同一段内容（同一提示词），数命中模式数。

**判断有没有改善的指标**：
- 主指标：单位文本（如每 300 字/每段）命中的模式数，以及「同一段内命中 ≥2 条」的段数——这是原文自己给的口径，最好用；
- 次指标：改写后文本中出现具体数字、专有名词、可核实动作的句子占比；
- 主观校验：盲评「更像人写的」版本胜率；注意不要由做改写的人来当评审；
- 中文场景必须先建映射表再计数，否则命中数会被误报淹没，指标失去意义。

**什么时候该停**：如果跑了两三篇之后发现主要命中的都是「内容实质」类（即问题其实是没写事实，不是写得像 AI），那说明这个清单对你的场景帮助有限——它擅长抓措辞与形式，补不了信息量。
