## 是什么
GitHub 的 Project Rubicon 是面向智能体规模的新 Git 存储架构技术说明。它围绕两个原则展开：最小化协调，以及把存储与计算解耦。Git 对象放在 Azure Blob Storage，引用和 pack manifest 放在名为 Ref-CAS 的复制日志服务，虚拟副本负责读写，压缩和垃圾回收在独立后台节点完成。原文说该架构已在内部测试中支持 5,000 个并发智能体、每秒 7,200 次 push，目前处于有限私有预览。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）
原文没有给出读者可直接执行的命令、配置或提示词，也没有面向普通团队的迁移步骤。可提炼的架构做法如下，仅适合在设计多智能体并发写入系统时参考：
1. 前提：把 Git 对象视为不可变、按内容命名，因此多个写入者可以并行上传对象而不需要先达成一致；真正需要排序和共识的只有引用更新。
2. 写入路径：虚拟副本先索引传入的 pack，上传到 Azure Blob Storage；随后向 Ref-CAS 提交一个事务，把 pack 列入 pack manifest 并更新引用。前提是引用只能指向已经持久化的对象。
3. 引用并发控制：Ref-CAS 对每个引用做 compare-and-swap，由日志副本的多数派确认；事务只锁它触碰的引用，并检查引用值仍是写入者期望的值。每个提交获得 LSN，仓库版本取最新提交的 LSN。
4. 读取路径：虚拟副本先把本地持有的引用版本发给 Ref-CAS 做版本检查；若版本仍是最新，返回结果不携带引用，仓库未变化时只付一次比较成本；若落后，则取回当前引用、版本和 pack 指针，再从 Blob Storage 拉取所需 pack 到本地缓存。
5. 扩读与容错：Spokes 尽量把同一仓库流量路由到同一组虚拟副本以保持缓存热；虚拟副本是可丢弃计算，本地盘只是缓存，节点消失后其他副本继续服务，替换节点按流量重建缓存。忙时增加虚拟副本。
6. 后台压缩：压缩节点先在 Blob Storage 对分片取 lease，保证同一分片只有一个节点压缩；读取 manifest 找新 pack，收进 open segment；按 pack 数量、大小或年龄达到阈值后封存，合并成更少更大的 pack；发布前确认新 pack 与输入包含完全相同的对象；上传新 pack 并更新 manifest，第二个事务移除输入 pack，之后清理。
7. 垃圾回收：用专用 worker 处理计算量大的部分，删除已无引用的对象，例如删除分支和 force-push 留下的对象；原文说其做法与压缩类似，但未展开详细步骤。
8. 规划中的智能体优化：无克隆工作、原子提交 API、事件流等；这些是后续计划，不是当前可照做的步骤。

## 怎么试、怎么验证
不建议把采用 GitHub 私有预览作为试用目标。若团队正在设计多智能体共用一个仓库的流程，可做最小架构验证：让 N 个智能体各自向独立分支推送，只对引用更新做每引用 CAS，对象放不可变对象存储，后台独立做压缩和清理；观察并发写入数、持续 push 吞吐、p95 提交延迟、仓库无变化时的读延迟、同一引用冲突率、pack 数量是否随写入增长而失控，以及维护任务是否拖慢服务延迟。对一般 AI 工作流，可把它当作设计检查表：把不可变产物与协调状态分开，只对必须排序的小状态做共识，把重维护放到后台，避免每次操作都拉取全量上下文。判断改善的标准应是并发上升时延迟是否平稳、冲突是否只发生在同一引用、无变化读取是否足够便宜，而不是只看单次演示的峰值数字。
