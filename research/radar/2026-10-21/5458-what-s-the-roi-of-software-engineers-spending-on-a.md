## 是什么

《The Pragmatic Engineer》付费文章，作者 Gergely Orosz 访谈了 27 家公司的工程负责人与资深工程师，并拿到 CodeRabbit、Gitar（Sonar 的 AI 代码验证代理）两家的聚合数据，试图回答一个问题：公司在每个工程师身上花的 AI 钱，到底有没有换来交付速度（ship velocity）与 PR 产出（PR throughput）的提升。

核心结构：

1. 两家工具方的 PR 数据（CodeRabbit：周 PR +113%、月 PR +127%、同批 2 万名开发者跟踪 +128%；Gitar：把团队按“每人每周 PR 数”分档，称“AI 原生”团队达到 60+ PR/人/周）。
2. 27 家公司的 AI 花费分布（高/中/低三档），以及几条共同规律：公司规模与 AI 花费无关；6-7 月花费见顶后回落（API 方案约减半，原因多为换用 Opus 5.5 与开源模型）；中高花费档普遍设上限；订阅制掩盖真实成本，部分补贴即将结束（账单可能涨 5-10 倍）；Claude / Opus 5.5 是花费主流向，Cursor、Codex、GitHub Copilot 被提及。
3. 逐家案例（本文最有价值的部分）：每家的单价上限、实际人均月花费、PR 频率变化、以及工程师的原话解释。
4. Big Tech（Meta / NVIDIA / Apple）部分被付费墙截断，本报告无法覆盖。

对“怎样验证 AI 是否改善了结果”这个问题，这篇文章的价值不在于给出验证协议，而在于提供了一组**已被真实团队使用、且有反例**的度量口径：PR 数会涨，但 PR 体积会同步膨胀、合并速度可能不变、用户故事交付量才是业务价值。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

原文没有给出成体系的实施步骤，以下是把它给出的度量口径与两条具体流程整理成可执行方案。**凡标注〔原文〕的是原文明确出现的事实或做法，标注〔本报告设计〕的是我据其结论提出的试用步骤，原文未给。**

### A. 建立“AI 投入—产出”对照度量〔本报告设计，口径取自原文〕

前提：团队已有 PR 系统、能拉取每 PR 的变更行数与合并时间；有可对照的“采用 AI 前”窗口（文章用的是“与一年前相比”）。

1. 定基线窗口。取采用 AI 工具前连续 4-8 周的数据，或直接用去年同期（原文各案例普遍用“比一年前”作对照）。
2. 采四个核心指标，按**人**统计而非按团队平均：
   - 人均每周 PR 数（PRs/dev/week）——原文最常用的口径；
   - 每个 PR 的变更行数（PR size）——原文发现某公司 PR 体积涨到 3 倍；
   - PR 合并节奏（merged PR velocity / lead time）——原文指出“PR 数量涨了但合并速度没怎么变”的情况；
   - 每月关闭的用户故事数（user stories closed/month）——原文中一家跨国团队用 Scrum+Kanban 与计划板，连续 5 年可比，2-3 月起关闭量达 3 倍，并首次出现“关闭数 > 新增数”。
3. 同时记录分母：人均每月 AI 花费（$/dev/month）与上限规则。原文的分布可作参照区间：低花费 < $300，中等 $300-500，高花费 $1,000+，个别到 $3,000。
4. 看分布不要只看均值。原文明确警告：某团队 PR 数从 1.5 涨到 4 PR/人/周，但“被一位生产率暴涨的工程师拉高，其他人变化不大”。所以至少输出中位数与分位数，或逐人列出前后差值。
5. 每次模型或预算变更后重跑（原文提到换成 Opus 5.5 后花费预期减半、6-7 月花费见顶回落，说明指标对模型版本敏感）。

### B. 预算上限 + token 浪费自查流程

前提：公司按人设 AI 预算上限。原文的两种形态：软上限（填一张短表说明理由即可提额，原文称“很容易绕过”）与硬上限（如跨国公司的 $4,000/人/月、AI SaaS 公司的 $2,000/人/月，后者很少获批提额）。

1. 设默认上限，并公开可见。原文举例：一家约 100 人的 AI SaaS 公司设 $2,000/人/月，并开一个公开的 `#ai-limits` 频道，自动点名接近上限与花费最高的人，提醒收敛用量（原文形容为“有点像公开处刑”）。
2. 提额前先跑“token 浪费诊断”。原文描述的做法：

```
提额前置：运行一个 AI skill，扫描常见烧 token 的原因——
是否在跑太多循环（too many loops）、是否在用子代理（subagents）等，
并给出修复建议。
若诊断未发现可优化项，再向经理提交预算提升申请。
```

3. 给非工程角色也上限制。原文案例：量化交易公司里交易员大量用 Claude，工程师在给他们补“限流”，防止“无意中跑出昂贵查询”。

### C. 用代理做 PR 质量闸门

前提：已有 PR 流程与代码评审规范。

1. 建一个审查代理，专门指出“过大的 PR”“啰嗦的代码”等模式（原文案例：一家酒店业公司建了这样的代理，按原有 PR 体积与质量标准把关，“这部分效果不错”）。
2. **保留人工评审**。原文一家 2,500 人 SaaS 公司的工程师说，人工评审仍能抓到代理与代理式评审漏掉的东西：完全不必要的改动、比应有体量大 10 倍的改动。

### D. 优先把 AI 投到这三类任务上〔原文案例给出的收益量级〕

1. 客户问题初筛（triage）：原来有时要一整天，现在几分钟完成代理工作 + 最多 1 小时人工核验。
2. 代码考古式调研：搞清“某段代码为什么这么写”，从翻 Slack/设计文档/PR 历史的一两天，变成几分钟。
3. 概念验证（POC）原型：复杂特性的 POC 从一两周变成几小时，产品经理可直接上手玩。
4. 历史包袱清理：一家 2 人 .NET 团队用 AI 清 5-10 年的积压（backlog cleanup），自称每人每周约 60 个 PR（约每天 10-15 个），从原来每天 1-2 个 PR 提升 5-10 倍。

## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）

**1. 能力发现（AI 还能接手哪些没想到的工作）**
有据：客户问题初筛（全天→几分钟 + ≤1 小时人工核验）、代码历史/设计动机调研（1-2 天→几分钟）、POC 原型（1-2 周→几小时）、陈年 backlog 清理、PR 体积与啰嗦代码的自动把关。这几项都不是“写代码”，而是围绕代码的检索、判断与清理工作，是本文对“能力发现”最实在的贡献。

**2. 任务匹配（什么工作适合什么模型/工具/协作方式）**
有据：花费主流向是 Claude / Opus 5.5，Cursor、Codex、GitHub Copilot 亦被提及（原文未做横向效果对比，不能据此选型）。收益最明显的场景被描述为 greenfield 项目，或“没有 OSS 阻塞”的工作；在复杂代码库里，“即便是 Opus 5.5 这样的前沿模型，一旦人把思考外包给它，仍会做出奇怪的东西”。单一技术栈（C#/Blazor/Azure）被该团队明确称为“尤其现在是个好决定”。协作方式上：人保留评审与质量否决权，代理承担初筛、审查、原型。

**3. 条件供给（需要哪些信息、工具、权限、反馈）**
有据：明确的预算上限与提额路径（软上限需一份短理由表；硬上限需先做 token 浪费诊断）；花费可见性（公开频道点名高消费者）；对非工程角色的限流；单一技术栈降低上下文供给成本；以及一条隐含条件——“如果你有很强的主动性（high agency）并且知道要建什么，现在很好玩”，即目标清晰度是前提。

**4. 主动推进（时间/事件/状态触发并持续完成）**
依据很弱。原文只有两条接近的内容：PR 审查代理在每次 PR 时触发并给出提示；token 浪费诊断在申请提额时被触发。没有关于定时任务、状态机、长时无人值守推进的描述。此问题本文基本不覆盖。

**5. 效果验证（怎样判断确实改善了结果）**
这是本文的核心贡献。有据：
- PR 吞吐可作为“现成可取、尚未被开发者 gaming”的前后对比指标（作者主张）；
- 但必须配 PR 体积与合并节奏，否则会把“PR 变小/变多”或“生成更多代码”误读为提速（某公司 PR 频率持平而 PR 体积 3 倍；某公司 PR 数上升而合并速度几乎没变）；
- 业务价值口径优于代码口径：用户故事月关闭量 3 倍、首次“关闭数 > 新增数”（Scrum+Kanban + 计划板，5 年可比基线）；
- 必须分人看：均值会被个别高产出者主导；
- 单价口径：$/dev/month 与上限合规率（某 2,500 人公司不足 5% 的人触到 $1,200 上限）；
- 反例同样重要：至少三家（酒店业 200 工程师、5,000 人上市公司、100 人 AI SaaS）报告 PR 频率或速度基本没变；某工程师直言“当团队在意生产代码质量、想保持和 AI 之前一样时，实际开发速度没有提高多少”，并观察到“周围在加速生产 slop”。

## 怎么试、怎么验证

**最小试用（建议 1 个团队、8-10 周）**

1. 选一个 5-10 人、工作类型可比的团队，且能拿到 AI 采用前 4 周以上的 PR 数据。
2. 计算基线：PR/人/周、每 PR 变更行数中位数、PR 合并 lead time 中位数、每月关闭用户故事数、人均月 AI 花费。
3. 引入 AI（模型与工具不限，但记录版本与人均花费），期间不动其他流程；每周同一脚本复算上述指标。
4. 同时让每人每周记一条“AI 省下的时间”日志，只记四类：初筛、代码调研、POC、backlog 清理（对应原文收益最明确的四类任务），标注节省的小时数。
5. 试用结束，输出**分人**前后对比表（每人的 PR/周、PR 体积、故事数），以及团队中位数。

**判断有没有改善的指标（含护栏）**

- 改善信号〔本报告设定的判定门槛，非原文数据〕：团队 PR/人/周中位数上升，且 PR 体积中位数未同比例膨胀；或用户故事月关闭数上升；四类任务的日志显示小时级节省可复核。
- 无改善信号（原文真实出现过的模式，出现即视为“钱没换来速度”）：PR 数上升但合并 lead time 不变；PR 数持平而 PR 体积涨 2-3 倍；只有 1 人产出暴涨而中位数不动。
- 护栏指标：人工评审每条 PR 的评论数、被回滚或返工的 PR 比例、评审中被判为“完全不必要”的改动数——用来捕捉原文所说的“加速生产 slop”。
- 成本侧：人均月花费是否落在预设上限内；若需提额，检查是否已走过 token 浪费诊断（B 步骤）。

**结论用法**：若护栏指标恶化而吞吐上升，按原文那家 2,500 人公司的经验，应把 AI 收缩到初筛/调研/POC 这三类高收益、低风险任务上，而不是继续放宽预算。
