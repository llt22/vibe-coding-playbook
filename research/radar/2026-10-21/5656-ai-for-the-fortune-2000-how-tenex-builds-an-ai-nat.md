## 是什么
这是 Latent Space 对 Tenex 的访谈整理，主题是企业如何构建 AI 原生 SDLC：用 repo 中的计划、决策记录、验收标准和证据让人类与 agent 共享上下文；用 story points 和产出付费；把 agent 从编码扩展到非工程生产任务。原文还包含 Kill My SaaS 实验和企业 AI 采用里程碑的讨论。注意：原文在权限/RBAC 处截断，且没有给出可直接复制的模板、命令或提示词。

## 具体做法
原文没有给出可复制的命令、配置或提示词；以下是从访谈描述中可还原的机制，只适合作为研读和试点假设：
1. 在 Git repo 中标准化技能说明和项目文档，把计划、决策、验收标准、证据与代码一起入库。前提：团队使用 Git，agent 有读 repo 的权限。
2. 维护一份 canonical plan document，作为人和 agent 共同工作的主计划；原文称随着模型变强，可减少对文档结构的强制约束。前提：有明确项目 owner 和计划评审。
3. 要求 agent 在执行中记录决策、动作和产出，用 Markdown 或 HTML 形成可读记录，并全部 check in。前提：规定 agent 的写日志责任和 review 方式。
4. 用 CLI 包住创建计划、可视化、客户 readout 等流程，让模型通过 CLI 驱动工作。前提：团队有工程能力自建和维护 CLI；原文未给 CLI 命令或参数。
5. 在 Linear、GitHub 和客户更新中保留同一项目记录的视图，让人类和 agent 对着同一事实源工作。前提：工具之间可集成，且权限允许。
6. 用平均每人每月 story points 趋势判断流程是否有效，并至少每季度校准 story point 标准。前提：有稳定估算口径；原文提醒要平衡“奖励产出”和“模型变强后价值校准”。
7. 模型搭配上，团队多数以 Opus 5.5 为主，用 Codex 做 review，两者来回；AMP 可接 Claude Code 订阅以降低成本。前提：这是访谈中的团队偏好，不是强制配置。
8. 企业落地按顺序推进：先通用 LLM rollout，再培训 enablement，再 coding agents，再非工程生产 agent；同时解决数据权限和 RBAC。前提：原文基于约 100 家企业的观察，不是完整实施 SOP。

## 怎么试、怎么验证
最小试用：选一个 2 至 4 周的 repo 项目，先记录基线，再要求每个任务在 Git 中留下计划、验收标准、决策记录和证据；agent 完成任务时更新记录；每周由人 review 一次记录完整性。若要做非工程 agent，另选一个可重复的后台任务，先解决 RBAC 和人工复核，再小流量上线。验证指标：原文可用的是平均每人每月 story points 趋势和季度校准；外部团队应同时看周期时间、返工率、逃逸缺陷、review 通过率、任务记录完整率、新人上手时间，以及非工程任务的完成时间、错误率、人工修正率和权限事故数。只有产出指标上升而质量指标不恶化，才能判断流程可能有效；story points 本身主观，必须防止刷点。
