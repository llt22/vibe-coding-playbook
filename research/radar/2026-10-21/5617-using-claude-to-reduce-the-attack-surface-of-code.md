## 是什么
原文介绍 Anthropic 用 Claude 对大型开源代码库做自动化攻击面分析与缩减：先映射可达代码，再把部署不需要暴露的代码移到认证后、点击后、显式开启后或协议状态机更深处。作者把方法归为三类：默认配置可达性、配置交互、早期可达性；并把三遍流程整合成一个可复用 Claude skill，计划集成到 OSS-Scanner。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）
原文没有给出可直接复制的命令、配置或完整提示词，因此不应编造；以下按原文描述拆成可执行流程。前提是：代码库可构建、可动态运行/trace，项目自带测试套件，最好另有黑盒回归套件；Claude 可读取代码并修改代码；有安全工程师复核。
1. 划定代码库类别与默认配置。先把目标归为 Public、Gated、Private 三类，明确“默认配置”和预期功能；让 Claude 清点代码入口点和配置选项，形成清单。原文在 25 个项目中清点出 17,000+ 配置选项，其中 3,842 个与安全控制/功能配置相关。
2. 第一遍：查默认配置可达性。找“在发布默认配置下可达，但不被任何默认功能使用”的代码。对每个候选 finding，用动态 trace 确认可达路径。若确认，设计并实现一个 gate；在基线版本上运行项目自带测试套件和黑盒回归套件，要求修改后的构建结果与基线完全一致。会改变非默认配置的 gate 不要自动采用，交给人类决定。
3. 第二遍：查早期可达性。找在任何配置下运行于硬门（如认证）之前、无需受害者交互、或协议状态转换之前的敏感且复杂代码。修复建议包括：把配置检查移到解析之前、增加 guard 强制状态顺序、在配置加载时拒绝危险组合。每个 finding 仍用动态 trace 确认。
4. 第三遍：查配置交互。找单独看合理、组合后却静默关闭安全控制、削弱控制或让行为未定义的配置对；原文特别关注“被接受但无错误、无警告、无文档说明”的组合。修复建议包括配置加载时拒绝组合、重排检查、加 guard。每个 finding 用动态 trace 确认。
5. 验证默认行为不变。对第一遍产生的默认配置 gate，必须在基线跑项目测试套件和黑盒回归套件，并要求修改构建与基线结果相同；任何会改变非默认配置的变更只提交给人判断。
6. 人工复核并上报。安全工程师复核动态 trace、补丁和影响范围；对上游项目提交补丁并跟踪版本修复。OpenSSH 案例中，维护者先在 10.5 把检查移到解析前，后在 10.6 把检查放进 parser 内，修复了客户端谎报 key type 和证书 CA 签名路径的问题。
7. 可扩展检查。原文还提到可用 Claude 对比运行时日志与配置，确认只启用必需功能：禁用未使用的 parser、遗留协议和 dashboard，以低成本降低风险。

## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）
- 能力发现：AI 已可做配置选项清点、默认配置可达性分析、认证前/协议状态前可达性分析、配置组合冲突分析、动态 trace 确认、设计 gate、跑测试比较、生成补丁。原文报告 Claude 在 25 个项目、500 万+ 行代码中发现 493 个问题；OpenSSH 案例中发现默认配置下未认证客户端可达约 4,500 行 ML-DSA-44 实验代码，约占默认 sshd 认证前代码的 16%。
- 任务匹配：适合大型、配置复杂、可构建并可动态运行的安全代码审查，原文覆盖 C、C++、Java、PHP、Python；适合把工作拆成多个 Claude pass，每个 pass 用空上下文，只接收上一 pass 的短上下文。不适合无法构建、无法动态 trace 或没有稳定测试基线的代码库。
- 条件供给：需要代码库读取与修改权限、构建环境、动态 trace 能力、项目测试套件、黑盒回归套件、配置清单、认证/协议状态机等安全上下文，以及人类安全复核。反馈信号是动态 trace 能否确认 finding，以及默认配置 gate 后测试结果是否与基线完全一致。
- 主动推进：原文的 skill 会自动跑三遍：默认配置可达性、硬门/协议入口前可达性、配置组合。每遍重新开始空上下文，只带上短上下文；但原文没有说明可由时间、事件或状态变化触发，因此不要外推自动触发机制。
- 效果验证：用动态 trace 确认每个 finding 的真实可达路径；默认配置 gate 必须通过项目测试和黑盒回归，且修改构建结果与基线相同；非默认配置变更交人决定。效果指标可包括确认的意外可达入口数、认证前可达代码行数/比例、静默关闭安全控制的配置组合数、测试差异是否为 0、补丁是否被上游接受。

## 证据与局限（原文给了哪些数据或案例，哪些只是作者主张，适用条件是什么）
原文给出的数据：25 个开源项目、500 万+ 行代码；17,000+ 配置选项，3,842 个安全相关；493 个问题；11 个 Gated 项目全部存在非预期可达代码，其中默认配置下 93 个不必要认证前表面、37 处认证前执行或记录状态、61 个静默削弱认证前控制的配置组合；162 个安全敏感配置组合被接受且无错误/警告/文档，94 个静默关闭安全控制，68 个是同一安全机制的不一致；一个 hostname/wildcard 规则在反向 DNS 关闭时与 IP 比较导致 deny 规则 fail open 的模式在 4 个无关项目出现；一个证书检查被另一配置项完全禁用的组合存在 21 年；一个项目 TLS 客户端证书选项在某些端点因命名空间不同被静默忽略。OpenSSH 案例给出了版本 10.4、10.5、10.6 的具体修复链条。作者主张减少攻击面能一次性降低所有未知漏洞风险，并认为 OpenSSH 这种高强度审计代码仍有问题说明方法有普遍价值。局限：这是初始研究总结，不是完整论文；可复用 skill 尚在集成 OSS-Scanner，原文未给完整提示词、配置或命令；结果依赖动态 trace 和测试套件，未给误报率、成本、耗时；部分问题本身不立即可利用，配置组合可能非标准或低频；需要人类判断非默认配置变更。

## 怎么试、怎么验证（最小试用方式和判断有没有改善的指标）
最小试用：选一个可构建、可跑测试的中型 Gated 或 Public 开源项目，固定版本并建立基线；让 Claude 按三遍流程跑，先只处理一个 pass（建议从第二遍早期可达性开始），产出候选 finding；每个候选都用动态 trace 确认；只对默认配置可达性 finding 自动生成 gate，并在基线跑项目测试和黑盒回归，要求结果完全一致；其余变更交安全工程师复核。记录：确认可达的意外入口数、认证前可达代码行数或比例、默认配置下可达但非预期功能的代码量、静默关闭安全控制的配置组合数、测试差异数、人工确认误报数、补丁被接受数。判断改善的最低标准：至少一个 finding 被动态 trace 确认，修复后默认行为测试差异为 0，且认证前或默认配置可达的敏感代码明显减少；若无法动态 trace 或测试基线不稳定，则降级为人工辅助审查，不采用自动 gate。
