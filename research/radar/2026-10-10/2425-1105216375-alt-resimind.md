## 是什么

ResiMind 是一个独立、开源（MIT，v0.12.1 / Experimental，仓库 30 stars）的神经符号（neuro-symbolic）Agent 架构，核心不是「换个更强的模型」，而是把模型放进一条**先验证、后提交**的推理回路里：

- **神经部分**：模型（或规则/检索）只负责「提议」下一步候选与证据引用。
- **符号部分**：可信的领域代码独立重算结果，检查引用、前提、作用域、精确有理数运算和单位；模型不能靠置信度或一个 `verified` 字段给自己发验证。
- **残差（residual）**：未完成的目标、未知量和硬约束的集合，从已提交事实重建；拒绝不改变状态，只把原因回给提议方。
- **验证记忆**：任务完成后从已完成的推导中抽取候选规则，经独立准入、重载复检、每次新应用再检查，存进持久规则库；模型权重不变，知识长在模型之外。

README 自己的流程图概括为：`Propose → check → diagnose what remains → change strategy → check again → 完成证明 → 准入规则 → 复用并复检`。

**步骤 1：安装并跑第一个离线 demo**
前提：本机已装 Python 3.10+；无需 API key，demo 离线运行。

```bash
git clone https://github.com/1105216375-alt/resimind.git
cd resimind
python -m venv .venv
source .venv/bin/activate
python -m pip install .
python -m resimind demo --domain scheduling
```

Windows PowerShell 的激活命令改为 `.venv\Scripts\Activate.ps1`。安装过程可能下载 build tools。`python -m resimind` 和安装后的 `resimind` 命令在仓库目录之外也能用。
第一个 demo 会保存并重载已校验规则，然后比较「空规则库」与「已学习规则库」，并配置了一个模型回调——正常任务应当**不会**触发该回调；另有一个本地预算被故意设为 0 的用例，会触发一次脚本化提议来展示 fallback。全程不发起 API 调用。

**步骤 4：直接用 Python API 驱动 Agent**
前提：已完成步骤 1 的安装。下面是 README 原文代码。

```python
from resimind import Task
from resimind.domains.planning import DOMAIN, build_agent, demo_problem, verified_plan

agent = build_agent(demo_problem())  # Offline; inject complete=your_model for neural proposals.
result = agent.run(Task("day-out", "Plan a relaxed day with art and a meal.", DOMAIN))
run = result.run_result
if run.status == "solved" and run.residual.solved:
    print(verified_plan(result))
else:
    print("Still unresolved:", run.residual.pending)
```

注意：`solved` 只表示「声明的义务已完成」，**不自动等于存在可行解或满足工程限值**——每个适配器有自己的有界范围。

**步骤 5：接真模型（可选）**
前提：先设置本地环境变量，再接模型；实时调用会产生费用，也可能一直保持未解决状态，且**实时请求失败后没有离线回退**。

```bash
python -m pip install '.[deepseek]'
# Set DEEPSEEK_API_KEY and DEEPSEEK_MODEL in your local environment first.
python -m examples.open_planning --live --json
```

接入方式是把一个 provider 无关的回调交给 domain builder：`build_agent(problem, complete=your_complete)`；`ModelProposer` 接受 `complete(prompt: str) -> str`。回调会收到当前状态、未完成义务、证据、允许的动作列表和上一次验证器的反馈，返回一个 JSON 候选或 `null`。另有 OpenAI Responses 路径（`.[openai]`）和 LangGraph 外层连接器（`.[langgraph]`），后者只转发已校验事实或未解决义务，不提供额外领域验证规则。

**步骤 6：为自己的任务写适配器**
前提：先能明确写出「什么算通过」的独立检查。核心不 import 任何参考领域。

| 接口 | 你的职责 |
| --- | --- |
| `Proposer.propose(...)` | 用模型、规则或检索提出下一个候选 |
| `Verifier.verify(...)` | 独立检查当前输入与候选；返回 `accept` / `reject` / `defer` / `interrupt` |
| `Domain.rebuild(...)` | 从已提交事实重算所有剩余义务 |

再用 `Agent`、`Task`、注册的 `EvidenceTool` 以及可选 `RouteMemory` 组装起来。详细指南 `docs/adapters.md`、`docs/domain-contract.md` 目前是中文，英文实现地图见 `docs/neuro-symbolic.md`。

**步骤 7：跑测试与看历史校验记录**

```bash
python -m examples.agent_demo       # task → tool → model callback → verifier
python -m examples.inventory        # independent recomputation and rejection
python -m examples.document_review  # missing evidence stays unresolved
python -m examples.route_memory     # review, applicability, and revocation
python -m pip install -e '.[dev]'
python -m pytest -q
```

## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）

**1. 能力发现：AI 已经能做哪些还没想到交给它的工作**
原文最有价值的一点是：**凡是结果可被独立重算/校验的任务，都可以放心交给 Agent，而不必因为「可能胡编」而不敢交**。给出的可校验任务类别包括：有约束的行程规划（时间窗、预算、步行上限、路线连续性、室内要求）、退款金额与保单资格核对、带等式/非负/上界约束的二次优化与全局最优性证书、连续梁内力与位移协调、线性方程求解、轴向杆应力。这些任务的共同点是「对错由外部计算决定」，而不是由模型自评。

**2. 任务匹配：什么工作适合怎样的模型、工具和协作方式**
原文给出了一条明确的分工与成本策略：
- 先比较「已验证规则的预览、化简、本地展开」三种本地手段，再决定是否叫模型（v0.10 cost-aware scheduling）：能直接闭合任务的规则即使表达式更大也可以赢；如果更简单的本地工作更便宜，匹配的规则可以被跳过。
- 本地预算不足时才出现模型回调；demo 里正常任务不应触发回调，只有预算故意设为 0 的用例才触发一次脚本化提议。
- 精确算术与证明交给符号侧；等式证明可选 Lean 4.29.0 后端。
- 模型侧只负责「选一个已注册动作并带证据引用地提出主张」。

**3. 条件供给：需要提供哪些信息、工具、权限和反馈**
原文列得很具体：
- 给模型的上下文：**当前状态、未完成义务、证据、允许的动作列表、上一次验证器反馈**。
- 证据必须由**注册的 `EvidenceTool`** 先收集成类型化输入，再谈主张（evidence before claims）。
- 验证器必须**独立**，并检查引用、前提、作用域、精确有理数算术、单位；提交时原子地检查引用与冲突。
- 反馈机制：拒绝时保留状态、只回传原因；缺前提就让任务保持 open（例如缺配送日期、缺回程路线测量时都不产出完成态结论）。
- 预算与边界：跨策略变化时重试与动作预算仍然有界；attempt/stall budgets 限制循环；v0.12 引入显式累加的 overflow reserve 用于异常大的符号步，默认储备为 0（保持旧行为），每个被接受的步骤只付它估算的超额。

**4. 主动推进：哪些工作可由时间、事件或状态触发并持续完成**
有依据的是**状态触发**：残差从已提交事实重建后，直接驱动下一次提议；未完成的目标/未知量/硬约束一直可见，直到被领域适配器清偿。v0.11 的「目标进度」检查会在花 Lean 证明检查之前先看是否朝原问题推进，允许装饰性改写拿具体反馈、有用分解增长表达式、不确定中间步有有限的探索配额。
**没有**在原文中看到时间触发或外部事件触发的调度机制，也没有「后台持续运行」的说明——这一条只对上一半。

**5. 效果验证：怎样判断确实改善了结果**
原文给出的方法论可直接照抄：**Measure the Agent, not the model** —— 固定模型、任务和资源上限，只测完成率、无效交付、调用次数、跨任务复用。验收门槛是独立验证器，而不是模型的自我评价；每次尝试都记录决策、原因、状态、残差，并有 JSON 审计轨迹可查。

## 证据与局限

**原文给出的数据**
- 十题离线对照：固定规则库 vs 增长规则库，独立有效的完成任务都是 10/10；传递提议 84 → **24**（作者计算为 **71.4% fewer**），跨任务规则提交应用 0 → **8**；学习规则额外花了 **13** 次提议。两臂使用相同的确定性提议器和预算。原文明确：这只测「已发布开发任务上的复用」，**不测模型准确率提升，也不测总体算力节省**。
- 早期 8 题代数 pilot（v1，`deepseek-flash`，同模型设置，每题 8 次调用上限，独立精确 oracle 评分）：ReAct-style 5/8（3 个无效答案）、verify-and-retry 6/8、residual reasoning 6/8、residual + verified knowledge growth **7/8**；传递模型调用分别 8 / 22 / 22 / 20。原文明确：增长臂的 3 次跨任务规则应用都发生在其他臂也能解出的题上，多出来的那题没有规则应用，**所以 7/8 不能归因于复用**；学 3 条规则多花 3 次调用，学习+传递共 23 次，**不构成总体成本节省的证据**。这是单个手工 pilot，不是对优化过的 ReAct 系统的排名。
- 开发期重跑 v2（加了系数偏差反馈，且是**已见过的题**）：5/8、7/8、6/8、7/8；增长臂与 verify-and-retry 打平且调用更多。原文自称是 post-result development，不是新的 held-out 结果。
- 统一开发 fixture（无模型）：**150/150** 独立评分完成；规则复用让平均数学步数减少 **33.1%**；难表达式储备消融 **2/8 → 5/8**。（材料在此处被截断，后续「Same-model algebra: frozen v…」不完整。）
- 具体案例：规划场景里 50 分钟 > 45 分钟步行被拒、改到 22 分钟通过；真实 DeepSeek 提议的方案在「咖啡变成硬性要求」后被拒，**一次**新模型调用后给出 ¥73、35 分钟步行、13:04 返回的方案并被接受。客户支持里 ¥259 因实付 ¥249 被拒，缺配送日期时任务保持 open，超出窗口时建议人工复核。优化案例初值 (26/15, 1/5, 16/15) 因违反 x₁≤1 被拒，改为 (1, 3/4, 5/4)、目标 −73/8，并需通过 LDLᵀ 正定、原始可行性、KKT 平稳性与互补性、多项式全局最优性证书。桥梁案例给出 −7,281.94 / +3,403.57 / +6,241.85 kN·m。

**哪些只是作者主张 / 局限**
- 规划、优化、桥梁、客服的多数轨迹是**离线 fixture**，候选是刻意造错的，检查与状态转移真的执行，但错误**不归因于真实模型**；venue/transport 是虚构数据，“好不好玩”“最好的一天”仍是主观的。
- 桥梁是合成的 24 m + 30 m 等效线梁，带给定限值，不是设计规范评估，其中点校验不是全局挠度包络。
- 客服是虚构商户规则和合成订单，只产出建议，**不执行退款、不声称钱已到账**；缺证据的运行以非零退出码结束（任务仍 open）。
- 适配器范围有界，`solved` 不等于可行或满足限值。代数证明检查器有明确的表达式与资源上限。
- 版本状态：v0.12.1 / Experimental，仓库 30 stars，作者自研自发布（作者声明 Created and originally published by @1105216375-alt）。多数结论由仓库自己给出，属于自报数据，样本小、含已见任务、含脚本化 fixture。

## 怎么试、怎么验证

**最小试用（半天内）**
1. 跑步骤 1 的 quickstart，确认离线能跑通、无 API key、正常任务不触发回调。
2. 再跑 `python -m resimind demo --domain knowledge-growth`，观察「推导→准入→入库→重载复检→新任务复用并复检」整条链路；用 `--json` 看审计。
3. 跑 `python -m pytest -q` 确认本地环境与仓库自检一致。

**扩到自己的任务（1–2 天）**
4. 挑一个你已经在做、且**结果能被独立重算**的任务（账单核对、配额计算、排期满足硬约束、报表口径一致性等），先写出 `Verifier.verify` 的判定规则，再写 `Domain.rebuild` 的剩余义务清单。
5. 用 `build_agent(problem, complete=your_complete)` 接上你的模型回调，回调只允许返回已注册动作 + 证据引用 + JSON 候选或 `null`。
6. 从空规则库起步，跑一遍；再把成功推导抽取成规则入库，重载后跑**新任务**，确认规则被检索到、且应用时仍要过当前任务的检查。

**判断有没有改善的指标（照抄原文口径：固定模型/任务/预算）**
- **无效交付数**：应当是 0（原文所有带门的臂都是 0 个无效答案，这是最硬的一条对比）。
- **独立评分完成率**：分母是同一批任务、同一预算。
- **每题模型调用次数**：注意学习规则本身要额外花调用（原文十题对照是 +13 次提议；v1 pilot 是 +3 次调用），要把「学习成本 + 传递成本」一起算，别只看单题变便宜。
- **跨任务规则提交应用次数**：原文十题对照为 8 次；如果为 0，说明复用没真正发生。
- **平均步骤数**：原文无模型 fixture 里复用让平均数学步数降 33.1%，可作为你自己的对照口径。
- 反向检查：跑一次消融（关掉某条机制，如难表达式储备），看指标是否退化——原文该消融是 2/8 → 5/8，这种对照比总体数字更能说明机制是否真的在起作用。
- 审计可复核性：用 `--json` 检查每次拒绝是否保留了状态、是否只回传原因、未完成义务是否一直可见。如果某次「通过」找不到独立的检查记录，就不算通过。
