## 是什么

work-humanizer 是一个 Agent Skill（一份 `SKILL.md` 加两个辅助文件，另含 `check.py`），用来去掉工作写作里的 AI 腔，同时保持事实、承诺和限定条件的强度不变。适用的工作是销售邮件、营销文案、客服回复、HR 通知、法务信函这类「字面即承诺」的文本。它可以在任何加载 `SKILL.md` 的 agent 里跑，原文点名 Claude Code、Codex、Cursor。

它区别于「叫 AI 改得自然点」的地方在三点：

- 明确拒绝造假：不加错别字、不硬塞俚语、不编轶事。
- 保留承诺强度：不会把「知悉」升格成「道歉」，不会给 offer 附加条件，不会把责任推给客户。
- 草稿缺了只有作者知道的东西时，它先问你几个问题再写（Interview mode）。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

前提：有一个能加载 skills 的 agent（Claude Code、Codex 或其他），以及要处理的文本。

1. **安装。** 把 `skills/work-humanizer` 文件夹复制进 agent 的 skills 目录：

   | Agent | 目录 |
   |---|---|
   | Claude Code | `~/.claude/skills/work-humanizer`（所有项目）或 `.claude/skills/work-humanizer`（单个项目） |
   | Codex | `~/.codex/skills/work-humanizer` |
   | 其他 agent | 该 agent 自己的 skills 目录；work-humanizer 就是一个标准 `SKILL.md` 加两个辅助文件 |

   或者用 Skills CLI：

   ```text
   npx skills add phuryn/work-humanizer
   ```

2. **调用。** 三种用法（原文原样）：

   ```text
   Use work-humanizer on this: <paste text>
   Use work-humanizer on this and interview me first: <paste draft>
   Use work-humanizer on docs/launch-post.md
   ```

   第二种用于草稿信息不全、需要它先访谈你的场景；第三种直接给文件路径。

3. **尽量喂自己的原始素材（这条决定效果上限）。** 粘贴你的笔记、语音转写，或你自己写的粗稿。它会以你的论证、你的顺序为主干，能保留的句子就保留；如果你同时给了一份 AI 草稿，它只把草稿当作要点清单用。

4. **判断要不要走 Interview mode。** 原文给的判断标准：这篇草稿能不能被任何拿到同一句话要求的人写出来？如果能，编辑救不了它，缺的是真实的例子、数字、哪里出了错、作者本人怎么想。此时用第 2 步第二种写法触发；它会问最多 5 个「回答成本很低」的问题，措辞按「你会怎么说出口」来设计，然后按你的回答重建全文。

5. **Rewrite mode（默认路径）。** 它会先列出每一条事实及其确定程度，然后以作者本人的声音重新写（用缩略语、说话人自称、日常动词），而不是在 AI 句子上打补丁。它按 AI 痕迹的强弱优先修，最后给一份逐句事实审计。它针对的痕迹包括：没人主张过的对比（「不是 X，是 Y」）、停顿指路句、复述式结尾、堆叠格言、替读者思考的句子、夸大和泛泛而谈、位置错误的模糊限定、整齐划一的句长、什么也没说的标签、把破折号改道成分号、装饰、聊天残留。

6. **可选的机械扫描（前提：agent 能跑代码，或你本地有 Python）。** 原文说 agent 能执行代码时会把这一步当作最后检查：

   ```text
   python skills/work-humanizer/check.py draft.md
   ```

   它检查破折号、分号、AI 常用词、填充式过渡、停顿指路句、句长区间。

7. **需要更短版本时。** 在有理由的情况下它会另外给一个约一半长度的选项，并列出会删掉什么；它绝不自行删减，删不删由你决定。

仓库结构（用于按需查看或复现）：`skills/work-humanizer/`（`SKILL.md`、`tells.md` 词表、`check.py`）、`examples/`（测试里的前后对照）、`evidence/`（方法、结果、原始数据、评委判决、事实核查、复现脚本）、`tests/`（check.py 的单元测试）。许可证 MIT。

## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）

**1. 能力发现。** 原文把「去 AI 腔」从一个模糊要求变成了一个有清单、有边界的专职技能：`tells.md` 里是可逐条对照的 AI 痕迹表，`check.py` 是可机械化的最后一关；Interview mode 更进一步，把「发现草稿缺什么」也变成可交给 AI 的动作（缺真实例子、数字、哪里出了问题、作者的真实看法时，先问再写）。「以作者笔记为主干、AI 草稿只当要点清单」这条用法，属于不常想到但明确写出来的做法。

**2. 任务匹配。** 原文把适用对象限定在工作写作的文本类型：测试集覆盖销售、营销、客服、产品、内部写作。方法上，同一模型（Claude Sonnet）、同一 wrapper、同一会话新建，只有 skill 文本不同，说明效果差异来自提示词与流程，而不是换模型。原文明确说样本里没有合同或其他法律文件，所以对法务文书不能直接引用其结论。

**3. 条件供给。** 需要：agent 的 skills 目录写权限（安装步骤里给了具体路径）；最好能提供作者自己的笔记、语音转写或自写粗稿（这一条直接对应「给作者自己的材料时 Pangram 4/4 篇 100% human」的结果）；Interview mode 下需要你回答最多 5 个问题；跑 `check.py` 需要 Python 和能执行代码的 agent 环境。原文没有提到需要额外 API key 或联网权限。

**4. 主动推进。** 原文没有时间、事件或状态触发的自动运行设计，只给了手动调用的三种写法。可被串进流程的只有 `check.py` 这一步——原文说能跑代码的 agent 把它当作最后检查，即它可以作为一个固定收尾环节挂在改写之后。

**5. 效果验证。** 原文给了一套可照搬的验证范式：盲评（评委看不到标签、每个候选按两种随机顺序出现）、两个分开的问题（哪个更像熟练的人写的，且原稿混在候选里；哪个你会真的发出去，且把原稿作为「作者本意」展示）、事实核查（列出每一条被删、被改、被加的内容，编造事实逐条人工核）、以及用商用 AI 检测器 Pangram 4 打分。这套「愿意发出 + 意义改动条数 + 编造事实数」的三件套，比单看「读起来像不像人」更接近真实工作后果。

## 证据与局限（原文给了哪些数据或案例，哪些只是作者主张，适用条件是什么）

**原文给出的数据与案例：**

- 12 篇新的 AI 写作文本，每个工具在同一模型上改写，由来自不同公司的四个 AI 模型盲评，每一处意义改动都与原文核对。
- 评委「会发出去」的选择率：work-humanizer 48%，blader/humanizer 20%，单行「改写得更像人」提示 1%，Emulate-1 0%。
- 意义改动：12 篇里 work-humanizer 18 处，blader/humanizer 33 处，单行提示 42 处，Emulate-1 120 处；在五个测试集共 56 篇改写文本中 work-humanizer 没有编造事实。
- 单行提示在「更像人写」这一项上以 90% 胜过 AI 初稿、work-humanizer 为 75%，但它改写自由、会加作者没说过的东西：能看见原稿的评委在 96 次挑选里只选了它 1 次。
- Pangram：work-humanizer、blader/humanizer 和单行提示的重写版都仍被判定为 AI（2–4% human）；标称「不可检测」的 Emulate-1 靠改动最多达到 87%。
- 给作者本人的笔记时，work-humanizer 的版本在 4 篇里 4 篇 Pangram 得 100% human；它把文章建立在作者的推理上（作者的主张、作者自己的顺序、作者自己的 because 和 so），只在需要的句子上改写。词选影响最小：早前一次测试里，人类文章被 AI 换词重述后仍读作 99–100% human。
- 只有 work-humanizer 会向你索要缺失的信息：16 篇里它在 9 篇上发问，用掉了作者 39 条事实，编造 0 条，评委愿意发出的比例 69%（blader/humanizer 22%）。
- 案例图：一封回复客户对押金扣款提出异议的信——work-humanizer 写得更直白并保住承诺；blader/humanizer 为扣款道歉并丢掉善意框架；单行提示把减免费用和尽快结清绑定；Emulate-1 责怪客户。

**哪些只是作者主张：**

- 「保住每一条事实、承诺和限定条件的强度」是设计目标与自测结论，不是独立第三方验证过的性质；评测由造这个 skill 的人自己设计。
- 「拒绝造假」是技能文本里的约束声明，原文没有给出对抗性测试（例如刻意诱导它编造）的结果。
- Interview mode 里「作者」是模拟的，由 AI 按一份作者已知事实清单代为回答——真人场景未测，这是原文自陈的局限。

**原文自陈的局限：** 样本小（scoreboard 12 篇，全部集合 56 篇，notes 结果 4 篇）；文本类型只有销售、营销、客服、产品和内部写作，没有合同或其他法律文件；评委是 AI 不是人，且评委之间对「human」是什么有分歧；每篇每工具只有一个样本；Pangram 只测了一个版本、一天；interview mode 里的是模拟作者；测试由开发该 skill 的人设计。另有两条方法学细节：发布版本在 12 篇 scoreboard 文本生成前已冻结；同一轮里还有一个测试过但未采用的变体拿到了 25% 的 send 选择；重写版的 Pangram 数字来自 16 篇主测试文本（其中 work-humanizer 13 篇，账号额度用尽前），AI 初稿在这些文本上的起点是 4% human。

**适用条件：** 工作场景的对外/对内文本重写；有作者自己的素材（笔记、转写、自写粗稿）时收益最大；不要指望它把文本变成能通过 AI 检测；不要把结论外推到合同类法律文本、外推到「AI 评委同意就等于人类读者同意」。

## 怎么试、怎么验证（最小试用方式和判断有没有改善的指标）

**最小试用（半天以内可以做完）：**

1. 挑 3–5 篇手头真实的 AI 起草文本（例如一封销售邮件、一条客服回复、一篇内部通知），保留原始 AI 草稿。
2. 每篇做两个版本。A 版：直接对同一个模型说「改写得更像人写的」（这就是原文的单行提示基线）。B 版：装好 work-humanizer 后按第 2 步调用；如果能拿到自己的笔记或转写，就按第 3 步一起给；草稿信息明显不全的，按第 4 步走 interview 路径。
3. A、B 两版都跑一遍 `python skills/work-humanizer/check.py`，记录机械项通过情况。
4. 让 2–3 位同事盲看，问和原文同样的两个问题：哪个更像熟练的人写的（把原始 AI 草稿混进候选里），哪个你会真的发出去（把原始 AI 草稿当作「作者本意」展示给他）。
5. 逐条比对 A、B 相对原稿删了什么、改了什么、加了什么，重点看承诺、条件、道歉语气有没有被改动。

**判断有没有改善的指标：**

- 「愿意发出」的选择比例——对照原文，work-humanizer 48% 对单行提示 1%，如果 B 版明显高于 A 版，说明有效。
- 每篇的意义改动条数——对照原文约 1.5 处/篇（18 处 / 12 篇），比 blader/humanizer 的 33 处低。改动少不等于好，要单独确认必要改动有没有被漏掉。
- 编造事实数——目标是 0。把原稿里的每条事实列成表，逐条核重写版是否凭空多出内容。
- 承诺强度守恒——把原稿里的每条承诺和限定条件列出来，逐条核对重写后是否同级（「知悉」不能变成「道歉」，offer 不能多出条件）。
- `check.py` 的机械项通过情况——作为收尾硬门槛，适合在人工盲评之前先筛掉明显没改干净的版本。
- 注意：不要把 Pangram 当验收标准。原文自己的结果显示，三个工具的重写版在 Pangram 上都被判为 AI（2–4% human）；真正把它推到 100% human 的是「喂作者本人的笔记和推理」，而不是换词。
