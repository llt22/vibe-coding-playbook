# A new feature for my blog, built using my voice

- 结论：**值得一试**。可以按原文步骤小范围试一次：在本地已 checkout 的仓库里用 ChatGPT 桌面端 Codex 的语音对话模式口述一个自己已经想清楚的小功能，再用键盘收尾审 PR。理由是原文给出了可复现的完整流程、产出清单和作者自述的耗时，作者也明确了它的边界（细节仍需打字、不是日常主力），所以适合试点而非直接采用。

## 是什么

Simon Willison 用 ChatGPT 桌面端 Codex 标签页的「语音对话模式」（voice conversation mode），对着本地跑着的博客开发环境口述需求，几乎全程用语音做完了博客新功能「Newsletters 索引页」。他一边做晚饭一边说需求，模型（原文写的是 GPT-6 Astra High）在本地改代码，并给他本地预览页面看效果；功能大致完成后开 PR，切回键盘审阅和收尾，最后合并上线。

原文的核心主张不是「语音能写代码」（他说手机上用 ChatGPT 语音做过研究和头脑风暴，也偶尔让它写片段），而是：加了视觉预览、又能随时切回键盘打字/粘贴之后，语音驱动编码智能体变成了一种强得多的交互方式；它的杀手级特性是多任务（做饭时还能干活），但细节阶段打字仍然更高效，而且他不愿意在共享办公空间里对电脑说话。

## 具体做法（编号步骤）

前提：本地已 checkout 自己要改的代码仓库（作者是自己的 Django 博客项目），本地开发环境能跑起来；装了 ChatGPT 桌面应用并能打开 Codex 标签页。

1. 在本地仓库上起会话，先用打字输入这句（原文原样）：

```
Start dev server and open in browser
```

   目的是先拿到站点预览，之后可以随时让模型展示新页面，用肉眼跟着看它的进度。

2. 点击「Start new voice chat」按钮——原文特意强调：不是那个话筒按钮，是它右边那个。
3. 把笔记本放到厨房（原文：set my laptop up in the kitchen），这样就可以一边做饭一边说话。前提是环境允许出声，作者说自己主要在家工作，共享办公空间里他不会这么干。
4. 用口语把要建的东西讲清楚，允许口语不流畅。作者的口述里包含大量「um」「oh, hold on」「no-」这类停顿和改口，模型仍然听懂了。他在转录里表达的要点包括：
   - 这是一种新的内容类型，需要新建一个模型；
   - 不要出现在 tag 页和博客首页，但要出现在按日期的归档页（例如 9 月 19 日那天发的 newsletter 要显示出来）；
   - 要能被搜索；Substack 的那些不索引（因为它们只是博客上已有内容的拷贝），按月发的那些含独有内容、公开一个月后要进搜索结果。
5. 让模型自己干活：它会回复、偶尔反问澄清，然后动手改代码。作者估计语音阶段持续了大约半小时——正好是做一顿晚饭的时间。期间可以瞄一眼厨房里的本地预览，用语音反馈设计。
6. 判断功能差不多完整后，让 Codex 建分支并开一个 pull request。
7. 在 GitHub 的 PR 界面审代码。作者发现其中一条导入脚本用了 subprocess 调 Git，而他要从私有 Git 仓库导入，认为走 API 更合适，于是切回键盘打字，让 Codex 把这条改成基于 API 的导入；同时顺手改了几处公开页面的展示。
8. 再花大约半小时打字提示，直到满意，合并 PR 部署到生产。

作者明确说，私有仓库那条导入需要新建 API key，这类活他「知道自己得坐到键盘前一会儿」，语音阶段做不完。

语音阶段实际产出的东西（可作为试点规模的参照）：

- 一个新的 Django 模型 + migration，以及对应的 Django Admin 配置；
- 四个能跑的导入：最近的 Substack 条目走 RSS；其余 Substack 条目走它们的未公开 API（GPT-6 Astra 直接试了 `/api/v1/archive`，再自己搜出分页办法，找到 Karen Spinner 的一篇文章）；已发布的月度 newsletter 来自 `simonw/monthly-newsletter-archive` GitHub 仓库；最近一期私有赞助者 newsletter 来自一个私有仓库；
- `/newsletters/` 和 `/newsletters/2026/` 公开归档页；
- newsletter 出现在日和月的归档页，但不出现在 tag 页和首页；
- 每周 Substack newsletter 链回 Substack，归档的月度 newsletter 有自己的页面；
- 接入站点搜索。

## 对应的研究问题（对照五个问题逐条说明，只写有依据的）

**1. 能力发现**
- 能从带大量不流畅口语的转录里推断出完整的功能规格（作者原话：「Apparently this was clear enough that the model knew what I wanted to build!」）。也就是说，把「模糊口述 → 可运行功能」整段交给 AI 是可行的。
- 会自己去摸未公开的接口：尝试 `/api/v1/archive`，再搜索出分页方式，还找到了第三方写的说明文章。这是「自己去查文档外的做法」这类工作可以交给它的证据。
- 能一次产出跨层的整套改动：模型、migration、视图、模板、导入函数、公开页面、归档页显示规则、搜索集成。
- 能根据语音反馈改设计（原文：GPT-6 Astra 设计了页面，然后根据他从厨房里看本地预览给出的口头反馈调整了设计）。

**2. 任务匹配**
- 原文划定的适合范围：作者「心里已经有很清楚的构想」，而且是「足够简单的 Django 功能」，他有把握模型做得出来。
- 工具与模型：ChatGPT 桌面端 Codex 标签页的语音对话模式，跑在本地开发环境上；模型是 GPT-6 Astra High。
- 协作方式（原文呈现的节奏）：语音描述 → 模型反问澄清 → 模型改代码 → 看本地预览给口头反馈 → 开 PR → 在 PR 界面审阅 → 细节切回键盘打字改 → 合并部署。
- 原文明确的不匹配：细节阶段（粘贴示例、报错信息、直接选中要改的代码或功能）打字比用嘴描述更高效；需要新建 API key 之类的活必须回到键盘。作者的总结是：它更适合多任务，不是他的日常主力（daily driver）。

**3. 条件供给**
- 需要本地跑得起来的开发环境和已 checkout 的仓库（第一步就是让它起 dev server 并打开浏览器）。
- 需要视觉预览：原文说，加上视觉预览、并且能在需要时用键盘打字/粘贴，才让这种方式比手机上的纯语音强得多。
- 需要键盘作为兜底输入通道：粘贴示例、粘贴报错、选中代码。
- 需要本地写文件和 Git 权限（建分支、开 PR）。
- 需要私有资源凭据：从私有 GitHub 仓库导入时得新建 API key，作者为此必须坐回键盘。
- 环境条件：必须能出声且不打扰别人（作者在家工作才行）。

**4. 主动推进**
- 原文没有描述任何由时间、事件或状态触发、无人干预持续完成的工作。整个流程都需要作者开口说话或打字。
- 唯一带一点「持续」色彩的是产出物里的导入脚本：会从 RSS、未公开 API、公开/私有 GitHub 仓库拉数据。但这是建好的代码功能，不是原文讨论的工作编排方式，原文也没给出调度或触发配置。
- 结论：这条线索对「主动推进」这个问题没有可照搬的依据。

**5. 效果验证**
- 作者的判断标准是主观的「功能基本完整」（almost ready to ship）→ 开 PR → 审阅改完 → 合并部署到生产。
- 可验证的客观锚点：上线后的 `/newsletters/` 索引页和某期月度 newsletter 的页面确实存在；PR 上有他审阅时追加的 commit。
- 原文没给任何量化指标（没有节省时间百分比、没有 bug 率、没有对比组），只有「语音约半小时 + 打字约半小时」这两个自述时长。

- 自述耗时：语音阶段约半小时，之后打字约半小时。

- 「这不是我的日常主力」「细节阶段打字更高效」「杀手级特性是多任务」——都是作者个人经验自述，没有对照实验。

## 怎么试、怎么验证

**最小试用方式**
1. 挑一个自己已经想清楚的小功能，规模参照原文：一个新数据模型 + migration + 视图 + 模板 + 一个导入脚本。不要拿需求模糊或跨系统的大改造来试。
2. 在本地 checkout 起会话，先打字发 `Start dev server and open in browser`（原文原样），确认能看到预览。
3. 点「Start new voice chat」（话筒右边那个），把设备放在你能顺手看到预览、又能一边干别的活的地方。
4. 对着它把需求讲一遍，允许停顿和改口，讲清「要什么、不要什么、要出现在哪些页面、要不要被搜索到」这类边界条件——这些正是原文口述里起作用的部分。
5. 让模型自己改代码并开 PR；在 PR 界面审，发现不对的地方切回键盘打字让它改，直到可以合并。

**判断有没有改善的指标**
- 语音阶段结束时，代码是否到了「几乎可以上线」的程度（原文作者的标准就是 almost ready to ship）。这是最直接的指标。
- 从开口到 PR 的时间，和从 PR 到合并的时间，各自用了多久（原文的参照是各约半小时）。
- 审阅时你实际改了多少：原文只改了导入机制和几处展示细节，共两个类型的问题。如果改动量大到接近重写，说明这个任务不适合语音驱动。
- 过程中模型反问澄清的次数和是否答对：原文里它偶尔提问就动手了，没有反复问同一件事。
- 上线后功能是否按预期工作（原文的锚点是归档页显示规则和搜索集成是否真的生效）。

**什么时候判定该放弃这种方式**
- 需要新建密钥、配置权限、或在多个私有系统之间接线时，原文的经验是必须坐回键盘，这类环节别指望语音。
- 需求本身没想清楚，或者需要反复粘贴报错和示例时，直接打字更划算。
