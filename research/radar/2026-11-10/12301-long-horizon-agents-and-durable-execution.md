## 是什么

原文讨论的是长周期智能体（long-horizon agents）的持久化执行（durable execution）。这类智能体要完成跨天甚至跨周的任务，过程中要多次与人及外部系统交换信息，可能遇到进程崩溃、网络失败和现实世界行为变化。持久化执行的运行时会把每一步与外部世界交互的结果记录下来；失败后程序重新运行，已完成步骤被跳过，状态由记录重建。原文用“库存补货智能体”贯穿：零件低于安全库存时，它获取报价、选择供应商、请采购经理审批价格、下单，并跟踪到货。大部分时间花在等待上，等待期间工作流挂起，不占计算。

## 具体做法

前提：任务确实跨天/周、路径不可预测，且需要等待人或外部系统；有一个支持持久化执行的运行时（原文示例为 Temporal 和 Cloudflare）；外部写操作能用业务键做幂等。

1. 先判断任务是否适合。适合的是“目标明确但路径不可预测、需要持续追踪依赖”的流程；原文举了客户 onboarding、销售/法务/采购之间的交易推进、患者转诊/预约/改期/文书、库存补货。可预测的流程仍应交给传统软件。

2. 把流程拆成决策、动作、等待三类步骤。以库存补货为例：库存检查（触发）→ 获取报价（动作）→ 选供应商（决策）→ 草拟采购订单（动作）→ 请求审批（动作）→ 等待审批（等待）→ 下单（动作）→ 等待供应商确认（等待）→ 读取回复（动作）→ 等待收货（等待）→ 关闭订单（动作）。决策只做选择，动作才产生外部副作用。

3. 选一个持久化执行运行时，并先跑通原文示例。原文给出的示例运行方式是：

```
# Temporal：在 python/ 目录启动 Temporal dev server 和一个 worker（见其 README），然后重新运行
# Cloudflare：在 typescript/ 目录执行
cd typescript/
npm run dev
# 或设置 CF_URL 指向 replenish.live，然后重新运行
```

前提：这些是跑通交互示例的说明，不是生产部署步骤；生产环境要按运行时的文档配置持久化存储、worker 和重试策略。

4. 让运行时记录每个动作的结果。示例中的动作包括 get_quotes、draft_purchase_order、request_approval、place_order、read_supplier_reply、close_purchase_order；每一步的结果进入记录，崩溃后重放时跳过已完成步骤并重建状态。前提：动作结果可序列化保存，且重放不会重复产生副作用。

5. 把等待人工/外部系统改成挂起加信号恢复。示例用 wait_for_approval、wait_for_supplier_reply、wait_for_goods 三个等待步骤；时间线明确写“Compute used: None. The workflow is suspended.”。恢复靠信号：approval（经理批准 $4.20，上限 $4.41）、supplier-reply（供应商确认 1000 件、24 October、$4.20）、goods-received（收货 1000 件）。前提：人或外部系统能把事件送回工作流，运行时支持持久化定时器和信号。

6. 对外部写操作加幂等键，并在执行前重新校验约束。示例下单时使用“Idempotency key: PO 4473”，执行前做“Price re-checked: $4.20, within the approved $4.41”，结果供应商侧“Orders at the supplier for PO 4473: 1”。前提：外部系统接受幂等键，或你能用业务单号去重；审批上限等约束要写成可检查的条件。

7. 用崩溃恢复验证持久化是否真的生效。原文示例包含 worker 进程 down/up 的崩溃区间，并说明崩溃后工作流继续推进。最小验证：在等待审批或等待收货时重启 worker，确认恢复后不重复下单、不丢审批状态。前提：运行时和 worker 按生产方式配置，而不是只跑内存 demo。

8. 上线前补齐原文目录提到但正文未展开的四项：失败调用至少一次重试、持久化不等于业务正确、运行中代码变更、记忆与模型可见上下文。提供文本只有这些标题，没有具体步骤；不要在没有依据时编造配置，应另行调研或等原文完整内容。

## 对应的研究问题

1. 能力发现：原文认为长周期智能体可以把过去因“人的注意力稀缺”而不经济的任务接管过来，例如客户 onboarding、跨销售/法务/采购的交易推进、患者转诊与预约文书、库存补货。可交给 AI 的不是单轮问答，而是持续追踪依赖并推进到结果。

2. 任务匹配：适合路径不可预测、跨天/周、频繁等待人和外部系统的任务；可预测流程仍用传统软件。工具与协作方式：用持久化执行运行时（原文示例 Temporal、Cloudflare），把 agent 循环组织成 decision/action/wait，人通过审批信号参与。原文没有给出不同模型的选择标准；“Two kinds of models”只有标题，正文未提供。

3. 条件供给：需要运行时记录每步结果；需要外部系统发信号（审批、供应商回复、收货）；需要幂等键；需要审批阈值（示例 $4.41）；需要挂起/恢复和崩溃恢复；需要状态存储。权限上，agent 能草拟订单、请求审批、下单、读回复、关闭订单，但下单受审批上限约束。

4. 主动推进：由库存低于安全库存这一状态触发；之后由审批、供应商回复、收货等事件信号和时间等待持续推进；等待期间不占计算；崩溃后继续。原文示例完整展示了一次从短缺到收货的推进。

5. 效果验证：示例给出 outcome=received，以及“Orders at the supplier for PO 4473: 1”（防重复）、“Price re-checked: $4.20, within the approved $4.41”（合规）、“Compute used: None”（等待不耗算力）。原文没有给量化业务结果；验证指标需要自行定义，见下一节。

证据：原文给出一个完整的库存补货示例，包含 3 家供应商报价（A $4.20、5 天、98% 准时；B $4.05、12 天、91%；C $4.60、3 天、99%），选择 A 1000 件，PO 4473，总价 $4,200，审批上限 $4.41，经理 Priya 批准 $4.20，供应商确认 1000 件、24 October、$4.20，收货 1000 件，关闭订单，outcome 为 received；等待步骤明确标注工作流挂起且不占计算；下单步骤有幂等键和价格重校验，供应商侧订单数为 1；示例还包含崩溃区间。原文说明了持久化执行的机制：记录每步结果，失败后重跑、跳过完成步骤、重建状态。

局限：提供文本在“Making the loop durable”之后只有目录标题，正文缺失，因此无法提炼该文关于实体/工作流划分、等待、重试、正确性、代码变更、记忆、提示词控制的具体做法；示例是演示/模拟，不是生产部署；没有量化效果数据，作者关于“改变经济性”的判断是主张；适用条件是任务能拆成可记录的外部交互步骤、外部系统能发信号并支持幂等、团队能运维运行时；“Durable is not the same as correct”提示持久化只保证恢复，不保证业务正确，等待期间外部世界变化需要额外校验。

## 怎么试、怎么验证

最小试用：

1. 选一个真实但低风险的长周期流程（如采购审批或客户 onboarding 的某一段），限定 1 个流程、1-2 个外部系统、1 个审批人。
2. 用 Temporal 或 Cloudflare 搭最小工作流：步骤分成 decision/action/wait；等待审批和外部回复用挂起加信号；写操作加幂等键。可先跑通原文 demo 的命令，理解时间线。
3. 人为注入故障：在等待期间重启 worker/进程，验证恢复后不重复下单、不丢状态；重复发送同一信号，验证幂等。
4. 记录基线：传统流程的端到端时长、人工催办次数、重复操作数、审批越界数、等待期间计算成本。
5. 小范围跑 2-4 周，对比试点流程的完成率、平均端到端时长、人工干预次数、重复副作用数、崩溃恢复成功率、每次任务的计算成本。

判断改善：完成率提升、端到端时长缩短、人工催办/干预次数下降；重复外部写操作和审批越界为 0；恢复后状态一致；等待期间不持续消耗模型/计算资源；若这些指标没有改善或仍需大量人工兜底，说明流程还没达到可产品化的持久化执行条件。
