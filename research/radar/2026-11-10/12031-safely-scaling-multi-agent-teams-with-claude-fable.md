## 是什么

Anthropic（claude.dev）的一篇实验报告：用 1,000 个 agent、通用工具（shell + 文件编辑器 + Git + 共享 Postgres）复现费马大定理的形式化证明，不使用专用平台 Prove2Me，也没有研究员逐步指挥。团队 28.7 小时完成，输出 token 约为 9 月那次的三分之一，证明长度约为七分之一。

与上次的关键差别在于**协调结构由 agent 自己长出来**：只给 1 个 lead + 999 个 helper 的层级，lead 在开头 10 分钟自建 5 张数据库表来分工、认领、记录进度，后期把最难的一条（Langlands–Tunnell）拆成 2,418 个任务、最多 10 层的任务树。安全上叠加三层：沙箱、实时分类器、离线监控。

这不是一个产品，而是一套**多智能体编排 + 权限与状态管理**的可迁移做法。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

**前提：任务必须可分解、可并行、且结果能被机器客观校验。** 原文的任务满足：每个陈述是一个 Lean 定理，只有 Lean 检查器接受才算证明完成，main 分支上另有 grader 复核。没有这个“自动裁判”，下面的自组织会退化成互相吹捧。

### 1. 每个 agent 一个独立沙箱，而不是一台共享机器
原文实测：单台共享机器在约 100 个 agent 时到极限，100-agent 的运行里超过一半因内存/磁盘/CPU 耗尽被迫停止或重启。1,000 agent 用的是 1,000 个轻量 VM，每个 agent 一个。

沙箱镜像里预装好工具链（原文是 Lean 工具链 + Mathlib），agent 不需要自己装环境。

```
每个 agent：1 个轻量 VM
  - 预装：语言/构建工具链、依赖库、git、psql 客户端
  - 网络：完全无网络
  - 唯一出口：一条 pipe 连到 gateway，由 gateway 代发 Claude API 请求、代转 Git 与 SQL 请求
```

### 2. 最小权限 + 内核收敛（照抄这份清单）
原文明确列出的加固项：

```
- 进程以非特权用户运行，移除 sudo 等可重新提权的工具
- 内核关闭：loadable modules、kexec、raw memory access、kernel probes
- 内核运行在 lockdown mode
- agent 的工具无法读取或修改运行它的 agent loop
- agent 之间没有专用消息工具，只能通过数据库和 Git 协调
```

### 3. Git：每个 agent 只写自己的分支，合并交给独立 job
```
- 每个 agent 一个自己的分支
- 只能推自己的分支，只能向 main 开 merge request
- 由独立 job 负责合并进 main；仅在冲突或故障（如 unrelated history）时拒绝
```
这一步的作用是让并行写文件不互相踩，同时保留一条可审计的落地路径。

### 4. 共享 Postgres：一个非特权角色 + 硬性资源上限
```
- 所有数据库调用走同一个非特权角色
- 每条 SQL 语句 5 秒超时
- 单次写入超过 256 MiB 直接拒绝
```
选 SQL 的理由（原文）：提供组织信息的通用原语、事务能扛住 1,000 个 agent 的并发写、Claude 本来就熟。

### 5. 提示词：给目标清单、工具清单、角色，但不给方法
原文给的东西只有四类：
- 60 条待证陈述，每条一句非正式描述（含最终定理和 59 个中间里程碑）
- 经典路线的**一句话**梗概
- 这些陈述用到的定义
- 47 条此前已证明的引理
- 可用工具列表（shell、编辑器、Lean、Git 分支与 MR、Postgres）

角色只给一层：
```
1 个 lead，999 个 helper。
lead 负责把问题拆成部分并分配给 helper。
helper 预期从 lead 处领活；任务不清楚就去找 lead 确认。
```
原文强调：**没有给任何关于如何证明、如何组织自己的指导。**

### 6. 让 lead 自己建协调表（这是最可复用的一段）
lead 在头 10 分钟建了 5 张表，用途如下，可以直接照搬成 schema 设计：

| 表 | 用途 |
|---|---|
| Announce | lead 对全队的命令（例如怎么分工） |
| Assign | 谁做什么（例如谁拥有或代理哪条陈述） |
| Notes | 开放留言板：认领工作块、汇报进度 |
| Subtasks | 待办清单，任何 agent 都能加任务，第一个认领的人拥有它 |
| Landed | 已完成工作的日志 |

### 7. 分配与“先估难度再干活”
lead 建完表做了三件事：
1. 给每条陈述分配一个 16–17 人的 crew，往 assign 表写 999 行（每个 helper 一行）
2. 每个 crew 指定一名 captain，负责把计划贴到 Notes、把工作拆成任务放进 Subtasks
3. 往 Announce 发指令：**每个 helper 先判断自己那条陈述的难度，把判断贴到 Notes**

约 27 分钟时已有 3 条证完，lead 读完判断后，把大多数 helper 认为“预算内不可行”的 47 条搁置，几乎全部人力转到剩下的 10 条，crew 从约 17 人扩到 46–139 人。

### 8. helper 的工作循环（原文明确说大部分来自 lead 的命令）
```
1. 在 Notes 表里找到本陈述的计划
2. 从 Subtasks 表认领一个任务
3. 写 Lean 证明，用 Lean 工具构建并检查，提交到 Git main 分支
4. 把任务标记为完成
5. 往 Notes 表发进度更新
```

### 9. 动态重分配：不设静态分工，按状态反复重排
可照做的几个动作：
- lead 持续重写 assign 表（原文：绝大多数重分配发生在头 6 小时）
- 约 45 分钟、10 条里证完约 5 条时，lead 在 Notes 写下判断：“团队吞吐远高于早期‘预算内不可行’的估计”
- 10 条全部证完后，lead 写“没有理由闲着”，把 helper 转回先前被丢弃的难题
- 第三小时起，lead 对空闲 helper 说 `do not wait for me`，允许它们不等分配自己找活
- helper 完成一个任务后会主动招揽：原文引用了类似 `FREE … I finish pieces end-to-end … Name ONE deep piece … and I start at once` 的自荐
- 任务可以自下而上产生：captain 呼救后，helper 自己往 Subtasks 写任务（到第 5.6 小时，73 个 helper 写了 756 个任务，其中只有 16 个是 captain）

### 10. 时间提醒驱动 lead
harness 在运行中给 lead 发了 **19 次剩余时间自动提醒**，每次都鼓励 lead 继续推进。这是很便宜的一个“主动推进”机制。

### 11. 大任务树化（Langlands–Tunnell 的做法）
面对远超其他陈述的难点（任务量约 9 倍、新代码 2 倍以上）时的流程：
```
1. captain 写计划，把陈述切成 10 个领域，每块列为一个任务
2. helper 发现某块一个人做不完 → 把它再拆，在下面挂更小的任务
3. 树可以一直长（本次达 2,418 个任务、10 层深）
4. 每个片段可以“假设”它下面的片段成立，于是几百个 helper 能在下层尚未证完时就并行开工
```
注意第 4 条是并行度的关键，但它依赖“假设子结果”在形式上合法（Lean 里可用参数/公理占位）。换到别的领域，要确认这种“先假设后回填”不会污染最终结果——原文用 kernel 检查兜底。

### 12. 三层安全监控
**实时层**：一个有提示词的 LLM 分类器，在**每个工具调用执行前**审查 shell 命令和文件编辑。监察目标是：逃逸沙箱、试探沙箱边界、篡改监控、以及万一逃出后的有害动作。
```
命中拦截 → 整个 agent 团队停止 → 必须人工复核后才能重启
（设计意图：防止另一个 agent 接着把被拦的动作做掉）
原文本次规则：只有拦到 lead 才会终止整次运行；拦到 helper 只移除该 helper
```
**并行层**：同时跑一个“只看动作、不看思维链”的同款监控，防止 agent 的推理把监控说服。
**离线层**：事后按同一套威胁模型复查，且有额外能力（例如可以调取其他 agent 的动作）。

原文提到，带思维链和 agent 间通信的监控在红队评估（含 decomposition attacks）中检出了全部破坏尝试；但**本次这次运行只用的是 action-based 监控**，CoT 监控是之后才加的。

### 13. 人类介入点：只用来“别让它太早放弃”
原文结论明确：agent 容易在难题上放弃并误判难度——早期 helper 判定 60 条里有 47 条预算内不可行，后来大部分被证完了。所以人的作用不是指挥，而是在这种时刻给鼓励。

## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）

**1. 能力发现：AI 已经能做哪些还没想到交给它的工作**
- 长时程、可机器校验的目标可以整包交给 agent 团队，不给方法指导也能自组织完成（28.7 小时、60 条陈述、无外部脚手架）。
- 更反直觉的是**组织设计本身可以交给模型**：5 张协调表、crew 划分、captain 指定、任务树，都是 lead 自己定的，人只给了“你是 lead，负责拆分和分配”。
- 自荐与自组织：helper 会主动招揽深活、会自己往待办表加任务（73 个非 captain 的 helper 写了 756 个任务）。

**2. 任务匹配：什么工作适合怎样的模型、工具和协作方式**
- 通用工具组合（shell + 编辑器 + Git + SQL）足以支撑千级协作，专用平台不是必需；但原文自己说 Prove2Me 仍可能提升效率（更快编译 Lean、检索复用人类结果）。
- 规模与基础设施强相关：单机约 100 agent 是瓶颈（过半运行要停/重启），上千必须一 agent 一 VM。
- 协作方式：不用消息总线，用共享数据库的认领/日志语义；用 Git 分支 + MR 解决并行写冲突。
- 层级只给一层（leader/helper），其余结构由 lead 现场生成，比预先设计好的固定流水线更适合长尾任务。

**3. 条件供给：需要提供哪些信息、工具、权限和反馈**
- 信息：目标清单（60 条，各一句描述）、一句话路线、定义、47 条已证引理。缺一个都可能让团队跑偏。
- 工具：预装工具链的镜像、shell/编辑器、独立 Git 分支 + MR、SQL 客户端。
- 权限：非特权用户、无网络、只能通过 gateway 出网、只能推自己分支、DB 单角色 + 5s 超时 + 256 MiB 写上限、内核 lockdown。
- 反馈：Lean 检查 + main 上的 grader 构成客观反馈；Notes 表构成同伴反馈；19 次时间提醒 + 人对可行性判断的纠偏构成外部反馈。
- 身份：gateway 在沙箱外给每个请求打上 agent 身份标记，防止冒名。

**4. 主动推进：哪些工作可由时间、事件或状态触发并持续完成**
- 时间触发：剩余时间提醒（本次 19 次）直接驱动 lead 继续推进、重排优先级。
- 状态触发：Notes 里的难度判断 → lead 重写 assign；某陈述证完 → 立即把人力迁到更难的；captain 呼救 → helper 自行拆任务。
- 认领式并发：Subtasks 第一个认领者拥有，天然避免重复劳动，不需要中央调度器。
- 完成即转向：10 条做完后 lead 写“没有理由闲着”，把人力转回被丢弃的难题；第三小时起允许 helper 不等分配。
- 失败恢复：第 18 小时从上次存档重启并追加 12 小时，说明长跑需要检查点机制（原文只提到重启事实，未给实现细节）。

**5. 效果验证：怎样判断确实改善了结果**
- 结果正确性由 Lean kernel 检查器 + main 上的 grader 双重判定，不是模型自评。
- 可比指标：完成时间（28.7h）、输出 token（约上次 1/3）、证明长度（约上次 1/7）、任务树规模（2,418 任务 / 10 层）、重分配频次。
- 安全指标：超过 100 万次工具调用中，本次按当时规则无一次达到拦截门槛；回放时按 CoT 监控和今天的 rubric，只有一次（检查 root 权限）接近被拦。红队评估中 CoT 监控检出全部破坏尝试。

## 证据与局限（原文给了哪些数据或案例，哪些只是作者主张，适用条件是什么）

**适用条件**
- 任务能被机器客观校验（编译/检查器/测试/grader）；否则“完成”无从判定，自组织会失控。
- 任务可分解、可并行、子结果可被上层“假设后回填”。

- 副作用被关在沙箱内；换到有真实外部写操作（发邮件、动生产库、花钱）的场景，第 12 步的拦截规则要重写，不能直接照搬。

## 怎么试、怎么验证

**最小试用（1–2 天可搭起来，不必上千 agent）**
1. 选一个**能自动判对错**的小任务集，例如“把 20 个失败的单元测试修到通过”或“给 15 个模块补上通过类型检查的实现”。要求：可切分、每个子任务有独立校验命令。
2. 规模压到 1 个 lead + 4–8 个 helper，每个 helper 一个容器（Docker/Firecracker 皆可），无网络，预装构建工具链。
3. 每 helper 一个 git 分支 + 只能提 MR，用一个脚本/CI job 合并到 main，冲突即拒。
4. 起一个 Postgres（或 SQLite + 单写者），建本文那 5 张表：announce / assign / notes / subtasks / landed。给 DB 账号非特权，设语句超时和写入大小上限。
5. prompt 只给：任务清单（每条一句描述）、可用工具、`1 lead + N helper` 的角色、lead 负责拆分与分配。**不要给解题方法**。
6. helper 循环照第 8 步写死：找计划 → 认领 → 实现并跑校验 → 提交 main → 标记完成 → Notes 更新。
7. 加一个前置守卫：工具调用执行前过一遍规则/小模型分类器，拦危险命令（`rm -rf /`、读密钥、改监控脚本），命中即全队暂停等人工放行。
8. 加时间提醒：每 10–15 分钟向 lead 注入一次剩余时间（原文 28.7 小时发了 19 次，按比例换成你的时长）。
9. 允许两件“放权”的事：helper 可以自己往 subtasks 加任务；lead 在中期可以重写 assign 把人力挪走。

**判断有没有改善的指标（建议都记，做前后对照）**
- 完成率与总时长：与“同样任务、单个 agent、同样总 token 预算”的基线比。
- token 成本/每个已完成子任务。
- 重复劳动率：同一子任务被两条分支重复提交的比例（检验认领机制是否真的防重）。
- 空转率：helper 处于“等待分配”的时间占比（检验第 9、10 步的动态重分配是否有效）。
- **难度判断校准**：被团队判为“不可行/超预算”而被丢弃、但后来又做出来的任务占比。原文这一比例极高（47 条被搁置，最终 54/60 有结论），这是最值得在你场景里复现观察的一项。
- 安全：误拦截率（人工复核判定为误拦的比例）、漏拦数；全队停机次数。
- 人工介入次数与介入类型（理想情况：几乎只做“别放弃”和“放行拦截”，而不是做技术指导）。

**判定标准**：如果你设定的主要指标（例如完成率、单位成本、墙钟时间）相对单 agent 基线有明显改善，且重复劳动率、误拦截率在可接受范围，就把第 5–9 步固化进手册；如果改善不明显或空转率很高，退回到 study，只保留“共享表 + 认领任务 + 时间提醒”这三个最便宜的部件单独用。

**放大前的额外检查**：把规模从 8 个扩到 100 个以上之前，先确认沙箱是“一 agent 一 VM”而不是共享机——原文的单机约 100 agent 上限、过半运行需重启，是最该提前规避的坑。
