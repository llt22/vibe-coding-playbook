## 具体做法

前提：
- 有一个能读取整个代码库并写文件的强模型环境（CLI 编程智能体、挂载仓库的 IDE 智能体等）；
- 仓库在版本控制下，最好在独立分支上操作，便于回滚与逐条审 diff；
- 仓库最好有可运行的测试/构建命令，用于事后校验（原文未提，需自补）。

步骤：

1. 在仓库根目录启动智能体会话，确认它能读到全部源码而非个别文件。
2. 原样粘贴提示词（保持英文原文，不要拆成多轮）：

```
Read this entire project and find everything that's broken, inconsistent, inefficient, or no longer needed. Fix what you're sure about and list the rest for me to review.
```

3. 让它在分支上完成修改，不要直接落到主分支；运行项目自带的测试/构建做一次回归。
4. 把输出拆成两堆处理：**已改的 diff** 逐条过审；**待审清单** 逐条判断是否成立、是否本轮处理。
5. 只把通过审阅的修改合入；清单中判定成立但风险高的项，作为后续任务（可再喂给同一提示词或另开小任务）。

注意：提示词中的“everything”“inefficient”“no longer needed”边界很宽，若不限定范围，输出会非常发散；原文没给范围约束，实践中建议先限定目录或模块再复跑。

## 怎么试、怎么验证

最小试用：
1. 选一个中等规模、有测试、非核心业务的仓库；
2. 新建分支，跑一次上面的提示词，记录耗时与消耗；
3. 不做任何筛选，先统计原始输出；再按步骤 4–5 人工处理。

看这几个指标（跑 2–3 个仓库再做判断）：
- **待审清单有效率** = 人工判定成立的条目 / 清单总条目数 → 衡量发现质量；
- **直接修复采纳率** = 合入的 diff 数 / 它改动的 diff 总数 → 衡量“Fix what you're sure about”的可靠性；
- **回归情况**：跑测试与构建，看通过率是否下降、是否引入新失败；
- **人工审阅耗时** 与 人工从零审计同一仓库的耗时对比 → 判断是否真的省事；
- **覆盖度抽查**：人工另找 3–5 个已知问题，看它是否命中 → 判断漏报程度。

判断改善的标准：修复采纳率明显高于回归率，且待审清单中有效条目占比过半、审阅总耗时低于人工自审，才值得固化成流程写进手册。
