## 是什么

Latent Space 与 Resend 联合创始人兼 CEO Zeno Rocha 的对话，主题是“为智能体设计”（agent experience / AEO）：当技术选型的第一读者从人变成编码智能体时，产品文档、定价页、MCP 工具应该怎么改，才能让 agent 读懂并选中、成功调用。文章的出发点是：开发者让 agent 实现“发邮件”功能时，agent 选了谁，基本就定了谁；开发者接受了补丁后，很少再去试第二选择。

注意：这是播客的回顾/摘要页，不是教程，具体做法只以零散例子出现。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

1. **给“需要读数”的页面做机器可读版本。**
   前提：你有定价、配额、规格这类人要靠交互组件（滑块、计算器）才能读出结论的页面。
   原文做法：Resend 的定价页是滑块，人拖动到某个体量再读价格；在该 URL 后加 `.md`，agent 一次请求就能拿到可读的表格。原文没有给出路由规则、模板或生成方式。

2. **自测这一页能不能回答客户的问题。**
   前提：上一步已完成。
   做法：原文的表述是“打开你自己的定价表，看它能不能回答一个客户的问题”，即把页面内容直接交给模型，问一个真实客户会问的问题（例如某发送量下要多少钱、含不含某项）。答不出或答错，就说明页面还需要被改写成可读形式。

3. **把自己日常的 agent 工具调用展开来看。**
   前提：你在用带 MCP/工具调用的客户端，且会话里的工具调用是可展开的。
   做法（原文称这是“便宜、值得借用”的实验）：挑一个你每天都触发的调用，展开被折叠的返回结果，看实际返回了什么、有多大。原文的例子是：有一次返回大到根本放不进上下文。据此判断模型真正需要其中哪些字段。

4. **把“减少工具数量”和“减少单次返回体”当成两件事。**
   原文的对照：Resend 的 MCP server 从发布时约 20 个工具涨到 80 多个，目标是让聊天客户端里的人能做到面板里能做的事（发信、邀请同事、查用量、管账单）；Cloudflare 的 Code Mode server 则只暴露两个工具：
   ```
   search()
execute()
   ```
   原文没有断言哪种更好，只指出一个常被混淆的点：减少工具数量本身不会让某一次调用的返回变小。所以第 3 步的瘦身要单独做。

5. **用“楔子”先进仓库，再谈选型。**
   前提：你的产品处于被 agent/开发者选型的位置。
   原文做法：先发布一个开发者即使不用你的 API 也会用的免费工具（React Email 做邮件模板），并明确写出怎么配合竞品（SendGrid）使用；等开发者真要换供应商时，你的代码已经在仓库里了。

6. **度量“被推荐率”。**
   前提：你关心 agent 选型结果。
   做法：用统一的实现类请求跑多个模型/应用，统计“第一个被推荐”和“作为备选出现”的次数。原文引用的数据见下节。

## 证据与局限（原文给了哪些数据或案例，哪些只是作者主张，适用条件是什么）

**给出的数据**：一项 AEO 研究中，Claude Code 在研究者能提取的 102 次邮件推荐里，64 次首选 Resend，SendGrid 首选 7 次但作为备选出现 55 次；另一次更新的综合研究中，Postmark 在多数模型上排到第一——说明领先位置随模型版本变动，不稳。Resend 自称录制时有 430 万用户、12 万付费客户。案例：Zeno 通过在客户库里筛短的 `.com` 域名，偶然发现有 Warner Bros. Discovery 这个客户（与 AI 无关的轶事）。

**只是主张/未验证**：80 个工具是否优于 2 个工具，原文只呈现两种做法与访谈者的兴趣，没有对照结果；“减工具数量不会自动减小返回体”是受访者观察，非受控实验；`.md` 定价页带来多少转化，没有数据。

**局限**：播客回顾，不是操作指南；`.md` 页面只有一句话描述，没有模板、路由或生成方式；推荐率数据是第三方研究的一次快照，换模型版本即失效；受访者是利益相关方，正在解释“为什么我们被选中”。

**适用条件**：你做的是开发者工具 / API / SaaS，且存在“agent 替人做选型、并直接写进代码”的场景；若你的工作不涉及被 agent 选型，本文只剩第 3、4 步（工具返回体审计）可迁移。

## 怎么试、怎么验证（最小试用方式和判断有没有改善的指标）

**最小试用（约一周）**

1. 选 1–2 个最常被问的页面（定价、快速开始），产出纯文本/Markdown 版本，放在可预测的 URL 上（原文用的是加 `.md` 后缀这一约定）。
2. 固定一个真实提示词（例如“帮我在这个项目里接入邮件发送”），在 2–3 个客户端/模型各跑 5 次，记录是否选中你、第一次调用是否成功。
3. 在自己日常会话里展开 3 次高频工具调用的返回结果，记下体积和“模型实际用到”的部分，据此砍字段。
4. 用同一组请求做一次小型推荐率统计，作为基线。

**指标**

- 首次被选中率（首选次数 / 总请求数），以及“作为备选出现”的次数。
前者决定是否被采用，后者决定是否进入比较清单。
- 从提问到成功跑通一次真实调用（如发出第一封测试邮件）的轮数与失败次数。
- 单次工具返回体的字符/Token 规模，以及“超出上下文”的发生次数。
- 需要人工补充信息（补文档、补参数）的次数。

**怎么判断改善**：同提示词、同模型版本、同客户端做前后对比，每组至少 5 次；只换模型版本或只跑一次的结果不能作为改善证据。若指标无变化，说明瓶颈不在可读性/返回体，而在选型本身（如模型训练数据里的先验），此时第 1、3 步的收益有限。
