## 怎么试、怎么验证

**最小试用**：

1. 选一个活跃仓库，给评审 Agent 换成只读凭证（去掉 write/merge），观察它是否仍能完成评审、是否出现“想改但改不了”的失败。
2. 把评分输出从分数改成 pass / fail 两档，记录每次判定的判据。
3. 自定义 4–6 个风险维度算一个风险分，用阈值把变更分成“重评审”和“轻评审”两档。
4. 抽一批变更做 A/B：一组全量对抗评审，一组按风险分阈值触发。

**判断有没有改善的指标**（建议同时看，不要只看一个）：

- **缺陷逃逸率**：评审通过但后续被发现的问题数，按千行或按 PR 归一；
- **误报率 / 人工推翻率**：评审提出的问题中被人工判定为无效的比例；
- **单位成本**：每个 PR 的评审 token/时长开销，用来复现“+140%”这个量级是否在自己的仓库成立；
- **人工复核时长**：真正的收益应体现在这里下降，而不只是评论条数增加。

**停止条件**：若在自己的数据上同样出现“成本接近翻倍、质量提升不到 10%”，就说明不该全量跑，应把重评审收缩到高风险子集（即第 4 步的用法）；若只读隔离导致 Agent 大量评审动作失败，说明隔离边界切得太粗，需要为“提改动”单独开一条受控通道。
