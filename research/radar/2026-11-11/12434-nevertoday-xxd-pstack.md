## 是什么

这是一个**第三方中文教程站**（`nevertoday/xxd-pstack`，32 stars）的 README，教程对象是 **pstack**——poteto（React 核心团队成员、在 Cursor 工作）写给自己日常用的一套 Agent Skills，通用镜像在 `backnotprop/pstack`。

它要解决的失败模式很具体：AI「没看懂就改，没试过就说做完」。pstack 的做法是把顺序和标准固定下来：动手前先复述目标、先读懂代码；修 bug 先让问题再出现一次、找到第一个出错点；说「做完了」必须贴真实命令输出、存下来的值、前后对比；能删就删、最小改动；同一个错误用 `/correct` 写回仓库，让下一个 AI 犯不了。

README 本身是教程站的入口页，给出了安装命令、首个任务提示词原文、提示词五要素、场景索引和「跑一夜」的合同要素；34 个技能、9 步教程、17 篇 How-to、20 条 Wiki 的具体内容都在外链页面，**不在本次材料里**。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

**1. 安装 pstack**（前提：已有 Claude Code / Cursor / Codex / OpenCode 之一；Codex、OpenCode 路线需要 Node.js 22.20+，`-g` 表示装到全局）

```bash
# Claude Code（命令会带 pstack: 前缀，比如 /pstack:poteto-mode）
/plugin marketplace add cursor/plugins
/plugin install pstack@cursor-plugins

# Cursor
/add-plugin pstack

# Codex、OpenCode 等（Node.js 22.20+；加 -g 装到全局）
npx skills add backnotprop/pstack
```

**2. 初始化**（前提：装完后新开一个对话，不要沿用旧上下文）

**3. 用一件真实但不大 的事跑第一个任务**（前提：任务是可执行验证的，比如能跑命令、能看 storage）

```text
/poteto-mode 收藏列表刷新后偶尔会重复。先复现，不要先改代码。
修好的标准：连点十次收藏，列表和 chrome.storage 里都只有一条。
把修之前和修之后 storage 里的实际内容给我看。
```

**4. 按五要素写提示词**：一句好提示词最多五样东西——目标、怎么算做完、想看什么证据、你已经知道的、不能碰的地方。**最好别写**的两样：具体怎么做，和你猜的原因。

**5. 日常只记一个命令**：`/poteto-mode`。它会从 23 套剧本里挑一套（修 bug、加功能、重构、查性能……），把步骤抄进待办清单，一步步调用其他技能；决定不做的步骤不会悄悄消失，会写明 `skip: 理由`。

**6. 按场景换提示词**（README 只给了一句话要点，具体提示词在外链 How-to 里）：修 bug → 先让问题再出现一次再动手；加功能 → 说清哪些旧行为一点都不能变；重构 → 先录下现在的输出，改完证明没变；性能 → 给测量值不要给感觉；接手陌生项目 → 「先别改代码」只让它调查；提交前 → 让几个模型挑刺、只留能跑出失败的问题；写文档 → 先写 README；大迁移 → 完成条件要能判断过没过，不写「做 4 小时」。

**7. 验收时索取证据**：要求贴真实命令输出、存下来的值、修前修后对比；汇总看 `/show-me-your-work`。

**8. 跑一夜（时间触发 + 自验证）**（前提：任务完成条件可机械判定，且在独立 worktree 里跑）

睡前给它一份「合同」，五个要素：**目标**、**能判断过或不过的完成条件**、**一个新的 worktree**、**决策日志**、**卡住时的逃生口**。每一轮：检查完成条件 → 做最小改动 → 验证 → 提交或丢弃 → 记一行日志。早上先读 `/show-me-your-work` 回复里的「需要注意」部分，审决定，不重读整夜。

**9. 纠偏与沉淀**：跑偏时用一句话拉回（外链 howto/steer）；同一个错用 `/correct` 改仓库本身；不熟的代码先用 `/how` 读懂再动手。

## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）

**1. 能力发现**
- 值得交给 AI、但很多人没想到的：让 AI **先复现问题再修**（而不是直接改）、**自证修好了**（贴命令输出和存储内容）、**重构前先录基线输出、改完证明行为未变**、**用测量值而非感觉描述性能**、**接手陌生项目时只调查不改码**、**多模型互挑刺且只留能跑出失败的问题**、**把犯过的错写回仓库让后续 Agent 不再犯**（`/correct`）。
- README 用对照表明确点出差异：平常 AI「直接改 / 表面加个判断 / 应该没问题了 / 越改越多 / 下次还犯」，pstack「先复述目标 + `/how` 读懂 / 先复现找第一个出错点 / 贴真实证据 / 能删就删最小改动 / `/correct` 改仓库」。

**2. 任务匹配**
- 工具面：同一套技能可装在 Claude Code（plugin marketplace）、Cursor（`/add-plugin`）、Codex/OpenCode（`npx skills add`）。
- 任务面：23 套剧本对应不同任务类型，由 `/poteto-mode` 自动挑选，不必自己记技能名。
- 协作方式：会「多派帮手 AI、让几个模型互相挑刺」；并行时各用各的 worktree，避免抢同一目录。
- 明确的不适用边界（作者主张）：**更慢、更费 token**，小改动不用它。

**3. 条件供给**
- 信息：目标、怎么算做完、想看什么证据、你已经知道的、不能碰的地方（并明确不要给「具体怎么做」和「你猜的原因」）。
- 工具与权限：安装插件/技能、Node.js 22.20+、独立 worktree。
- 反馈闭环：要求贴真实命令输出与前后对比；`skip: 理由` 让被跳过的步骤可见；决策日志记录每轮提交/丢弃；`/correct` 把纠正写回仓库形成长期供给。
- 逃生口：跑一夜时必须留「卡住时的逃生口」。

**4. 主动推进**
- 「跑一夜」是明确的事件/状态触发的持续执行：睡前下合同，循环「检查完成条件 → 最小改动 → 验证 → 提交或丢弃 → 记一行日志」。
- 关键设计：完成条件必须**能判断过或不过**（而不是「做 4 小时」），这是能否无人值守的前提。
- 早上不是重读全过程，而是读 `/show-me-your-work` 的「需要注意」+ 审决策日志——把人的注意力放在异常点。

**5. 效果验证**
- 核心机制就是验证：修 bug 要给「修之前和修之后 storage 里的实际内容」；完成标准写成可执行断言（「连点十次收藏，列表和 chrome.storage 里都只有一条」）。
- 重构验证方式：先录下现在的输出，改完证明没变。
- 性能验证方式：给一个测量值，不是一个感觉。
- 审查方式：只留下能跑出失败的问题（把「挑刺」也收敛到可验证的问题上）。

## 怎么试、怎么验证（最小试用方式和判断有没有改善的指标）

**最小试用（1 人、1 件真实小 bug、半天到一天）**
1. 选一个**当前真实存在、可复现、可自动判定**的小 bug（有明确断言，例如「连点十次只留一条」）。
2. 按本文第 1、2 步安装并在新会话跑 `/setup-pstack`，验证技能选「要」。
3. 用第 3 步的提示词模板，只替换场景，保留三个要件：**先复现不要先改**、**可判定的完成标准**、**要看修前修后的实际内容**。
4. 同一件任务再用普通对话（不装 pstack）跑一次，作为对照；记录下面指标。
5. 若有效，再试一次「跑一夜」：挑一个完成条件可机械判定的中等任务，给它 worktree + 决策日志 + 逃生口，第二天只读「需要注意」和决策日志。

**判断有没有改善的指标（都可直接从对话记录里数）**
- **返工轮数**：从提出到真正修好之间「还是不行」的往返次数（原文举的失败场景是「来回五轮，一个下午没了」，可作对照基线）。
- **首次交付即通过率**：AI 第一次说「修好了」时，完成标准是否真的通过。
- **证据完整性**：回复里是否包含真实命令输出 / 存储前后对比（有/无，二元判断），而不是「应该没问题了」。
- **改动面**：改动文件数与 diff 行数（对应「能删就删、最小改动」的主张，需与不加 pstack 时对比）。
- **重复错误率**：同一类错误在后续任务中再次出现的次数（配合 `/correct` 观察是否下降）。
- **成本**：token 消耗与墙钟时间（作者已声明会更高，关键是判断「省下的返工」是否大于「多花的成本」）。
- **跑一夜专项**：早上「需要注意」条目数、需要人工介入的次数、决策日志中被你推翻的决定比例、产出中被丢弃的比例。

**判定规则（建议）**：若「首次交付即通过率」上升、「返工轮数」下降、「证据完整性」从无到有，且成本上升幅度可接受，则把 `/poteto-mode` + 三要件提示词固化为标准做法，并考虑把 pstack 条目补进清单；若只有成本上升而返工不变，则限定为「大改 / 重构 / 迁移 / review」专用，日常小改仍用普通对话。
