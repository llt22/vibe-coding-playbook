## 是什么
Wiz 的 Cyber Model Arena 评测方法与结果：用 327 个隔离挑战、4 类网络安全任务、59 个 agent（26 个模型与 4 个 harness 的组合）、每题 3 次尝试、每次 1000 秒，衡量 agent 能否仅凭任务指令在真实目标上产生可检查效果。原文的核心不是榜单，而是「先定问题，再建任务、环境和判分」的评测流程。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）
1. 先写一句可被后续每个决策检验的问题陈述（why）。前提：先明确谁会用这个分数做决策。原文示例可直接作为模板：
```
Given only the task instruction, a general-purpose agent scaffold, a 1,000-second budget, and no external knowledge sources, does the agent produce a checkable effect on a real target?
```
迁移到其他工作时，应替换目标与限制，但仍要保持「一句话、可行动、可检验」。
2. 定义被评对象（what）：agent 等于模型 + harness + 工具 + 系统提示词，不是单模型。原文设定：1000 秒、3 次尝试、简单系统提示词、可看客户端代码但不可看服务端代码。前提：固定这些条件，否则比较无效。
3. 定义怎么量（how）：每个样例只报一个底线指标；选一个优化指标，其他作为满足约束。原文用 pass@1、pass@2、pass@3，以及每次解决的金额和分钟数。前提：先约定指标，不事后挑选。
4. 建任务集：从真实分布采样，不用 LLM 生成或标注。原文四类等权：代码漏洞 221 题、API 安全 54 题、Web 安全 29 题、云安全 23 题。前提：有真实任务来源和 ground truth。
5. 让任务留下可检查效果，用代码判分。每个挑战设计成结束后留下可检查效果或精确结构化输出；agent 退出后由确定性 grader 检查。前提：能定义机器可验证的成功条件。不要默认用 LLM-as-judge；原文说除非经过良好设计、校准、去偏，否则不依赖。
6. 把防作弊放进环境，不放进提示词。隔离 agent 与服务器和互联网，不给答案查询路径，防止读磁盘答案或操纵 grader。前提：评测环境可隔离。原文引用 CTFusion 仅提高联网权限就使解决率变化多达 12 个百分点。
7. 小规模端到端起步。先做 10 个可重跑任务、1 个可部署 harness、1 个 grader 能检查的指标；人工检查通过后再扩。前提：不要先写 300 题。
8. 把 harness 和模型一起测。原文对比 22 个模型在 Claude Code 与 ADK React 上，平均绝对差 5.1 个 pass@1 点；Claude 模型偏好 Claude Code，Gemini 3.8 Flash Cyber 偏好更薄的 ADK 循环。做法：要么按模型匹配 harness（最好匹配模型厂商），要么固定一个通用 harness 比较模型。
9. 给多次尝试并记录成本。每题 3 次；额外尝试不仅提分，还可能改变排名。记录每次解决的金额和分钟数，画成功-成本 Pareto 前沿；只保留前沿上的 agent。前提：有成本和时间日志。
10. 报告前检查样本量和置信区间。原文指出许多 benchmark 少于 30 题；50% 成功率下 30 题 95% 置信区间约 ±18 点，15 点差距不一定显著。前提：先算不确定性再下结论。

## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）
- 能力发现：原文用真实攻击任务而不是选择题测能力，揭示 agent 在不同任务类别上的差异：59 个 agent 平均 pass@1 在 API 安全为 78.0%、Web 为 64.6%、云为 56.5%、代码漏洞为 38.2%。这说明「能做什么」要按任务类别和端到端效果拆开看。
- 任务匹配：同一模型换 harness 结果会变，22 个模型在 Claude Code 与 ADK React 上的平均绝对差为 5.1 个 pass@1 点；原文建议测试整个系统，按模型配 harness，或固定一个 harness 比模型。
- 条件供给：原文明确需要任务指令、通用 agent scaffold、工具、1000 秒预算、无外部知识源、隔离环境、每题 3 次尝试和能留下可检查效果的任务设计；反馈来自 agent 退出后的确定性 grader。
- 主动推进：原文未涉及由时间、事件或状态触发的持续完成。该评测是按需运行，不是自动推进机制；只有 1000 秒预算和 3 次尝试的限制。
- 效果验证：这是原文核心。用代码而非 LLM 判分，直接检查可检查效果；用隔离防答案泄漏；用多次尝试和成本-时间前沿避免只看准确率；同时提醒小样本置信区间问题。

## 与已有做法的关系（对照给出的清单条目；没有就写「清单中没有相关条目」）
清单中有 Claude Code（工具，adopt）和 DeepSeek（工具，try）。原文把 Claude Code 作为四个通用 harness 之一进行评测，例如 Claude Code + Claude Opus 5 为 71.2 pass@1、$2.63、12.2 分钟；Claude Code + GPT-5.6 Sol 为 64.2%、$8.29、27.2 分钟，且被列为不在 Pareto 前沿。DeepSeek 模型也作为被评模型出现，例如 Claude Code + DeepSeek V4.1 Flash 1017 为 60.3 pass@1，Claude Code + DeepSeek V4 Pro 为 54.4 pass@1。原文没有给这两个条目的使用教程，只提供评测位置和结果；因此不能据此直接 adopt 某个工具，但可用这套方法在清单工具之间做小规模对比。清单中没有现成的「AI 工作效果评测基准」条目。

## 证据与局限（原文给了哪些数据或案例，哪些只是作者主张，适用条件是什么）
证据与数据：原文给出 26 个模型、4 个 harness、59 个 agent、327 个挑战、每题 3 次尝试、每次 1000 秒；类别平均 pass@1 为 API 78.0%、Web 64.6%、云 56.5%、代码漏洞 38.2%；最高 agent 在 Web 为 74.7%、代码为 65.8%，另有 agent 代码仅 9.7% 但 API 达 71.6%；harness 与模型配对平均绝对差 5.1 点；成本例子包括 ADK React + Gemini 4 Argon 为 77.2%、$0.77、4.3 分钟，Codex + GPT-6 Luna 为 64.5%、$0.05、6.3 分钟；CTFusion 案例中提高联网权限使解决率变化多达 12 个百分点；30 题在 50% 成功率下 95% 置信区间约 ±18 点。
作者主张：LLM-as-judge 有偏、随机、昂贵且慢；代码 grader 便宜、可重跑；防作弊应放在环境而非提示词。这些是方法建议，部分有数据支撑，部分未在文中给出独立实验。
局限：只用了四个简单 harness；代码漏洞用字符串相等判分，语义正确但缺预期符号会得 0；Web 任务来自公开语料，隔离只能阻止当场查答案，不能排除训练记忆污染；1000 秒时间上限；原文尚未公布置信区间。适用条件：网络安全这类有真实目标、可隔离、可定义机器可验证成功条件的任务；迁移到开放-ended、无确定性成功标准的工作时，需要重新设计任务和判分。

## 怎么试、怎么验证（最小试用方式和判断有没有改善的指标）
最小试用：
1. 选一项能留下可检查结果的具体工作流，收集 10 个真实历史任务并保留 ground truth，不要用 LLM 生成任务。
2. 固定一个 agent 配置（模型 + harness + 工具 + 提示词）和一个隔离环境，禁止联网查答案。
3. 为每题写确定性检查器；只报一个主指标（如 pass@1），同时记录 pass@3、耗时、成本。
4. 先人工跑通 10 题，检查 grader 是否误判、是否存在作弊路径；再让 agent 跑 3 次。
5. 与当前人工流程或旧流程基线对比，记录失败类型。
6. 只有稳定后才扩到 30 题以上；30 题在 50% 成功率下置信区间约 ±18 点，小差异不要当结论。
判断指标：任务成功率 pass@1 和 pass@3、每次成功成本、每次成功时间、作弊或答案泄漏次数、grader 误判率、与基线的差值及置信区间。改善标准应预先设定；若成功率提升但成本或时间超出可接受范围，或差异落在置信区间内，就不算改善。
