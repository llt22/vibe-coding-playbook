### A. 把正确性前移到类型层（前提：语言支持 sum type / 代数数据类型，如 Rust、OCaml、F#、Standard ML；Java/Python 等只能部分近似）

1. 先用一句话写下这个模块的“不变量”——即“我的软件确实做到了它该做的事”的保证。原文的定义是：correct 就是“达成业务目的，且不会凌晨两点把人叫起来处理故障”。
2. 列出该模块所有可能的状态，以及允许的状态迁移，把它们写成 sum type（“这个值只可能是这几种之一”），而不是用布尔标志、可空字段、字符串常量拼接。
3. 对所有分支使用穷尽匹配（exhaustive matching）而非 if 链。原文给出的收益是：把 sum type 从 5 个变体改成 6 个时，编译器会把代码库里所有没处理第 6 种情况的位置全部报出来——“忘记处理新分支”这类 bug 变成编译错误。
4. 把这条当作设计评审的检查项：凡是“理论上不该发生”的组合，问一句“能不能让它在类型上就写不出来”，而不是加一行运行时断言或补一个测试。
5. （推断，非原文）对不支持 sum type 的语言，退化为：枚举 + 编译期/静态检查 + 在改动枚举时用全量搜索找出所有分支点。原文只说这类语言“几乎不给你正确性方面的帮助”。

### B. 用 workload 而不是样例来做验证（前提：被测对象是有状态系统，如数据库、KV 存储、队列、分布式服务）

6. 定义 workload 的两个组成部分（原文明确给出）：
   - **Inputs**：由你构造、用来驱动代码的操作集合；
   - **Validation**：你用来判断“它是否正常工作”的规则，包括键的数量、键的取值范围、键与值的最大尺寸等边界。
7. 用不变量而不是预期输出做判定。以原文的 key-value store 为例：操作是 GET / PUT / DELETE，验证是“键空间与值大小必须在设定范围内”，而不是“PUT a=1 之后 GET a 应该返回 1”。
8. 关键一步：**不要让随机性替你探索**。原文的批评是——纯随机地在 GET/PUT/DELETE 里选，做完 PUT 往往紧接着 DELETE，永远不会连续做 10,000 次 PUT，也就永远碰不到换盘、GC、reshard 这些真正出问题的路径；比喻是“像醉汉走路，走不出起点多远”。因此 workload 要能把系统推向边界（长写序列、写放大、极端键分布），而不是均匀采样。
9. 复现 Bank Test（原文给出的完整设定，唯一可直接照做的具体流程）：
   - 系统中共有 $10,000；
   - 拆成 10 个账户，每账户 $1,000；
   - workload 在一个事务内把金额从一个账户转到另一个账户；
   - 同时另起一个组件，持续查询系统内所有账户的总额；
   - 判定：只要隔离性保证成立，这个观察者读到的值**永远只能是 10,000**，出现任何其他值即失败。
10. 在 workload 之上叠加故障注入（原文提到的做法：节点间网络故障、kill 节点）。原文的说法是：经过严格测试的老系统跑 Bank Test 可能什么都不会冒出来，但一旦放到 Jepsen / Antithesis 那类带故障的环境里，bug 就会“疯狂地冒出来”。
11. 用 TDD 写 API 的形状，但不要停在样例测试。原文给的路径是：先写测试驱动出接口（他认为这是写好好 API 的最佳机制之一），然后在结对 kata 里用“硬编码返回值”这种极端偷懒逼对方把输入随机化——一旦输入随机化，就已经进入 property-based testing 的领域。

## 怎么试、怎么验证

**最小试用（约一周，选一个模块，不要全仓推）：**
1. 选一个“有明确不变量”的模块：余额/额度、库存扣减、配额计数、订单状态机，任一即可。
2. 写下 2–5 条不变量（例如“任意时刻所有账户总额恒等于初始总额”“订单不可能从已取消回到已支付”）。
3. 在代码里把这些状态与迁移写成 sum type，分支处用穷尽匹配；然后做一次“加一个变体”的实验：故意新增一种状态，看编译器/检查工具能否把所有需要改的位置列全。
4. 按第 9 步复现一个最小 Bank Test：并发执行转账事务，同时用独立观察者轮询总额，断言恒等于初始值。若环境允许，再叠加延迟、超时、进程 kill 中的一种故障。
5. 把随机操作改成有偏序列（例如连续 1,000+ 次写、极端键分布），对比两种输入生成方式各自暴露的问题数。

**判断有没有改善的指标（这些是我建议的度量，原文未提供任何基线数字）：**
- 新增状态/分支后，被静态检查捕获的遗漏点数量（对应“忘记处理新情况”类 bug 是否归零）。
- 该模块在 workload 下违反不变量的次数，以及其中有多少是既有样例测试没发现的。
- 相同运行时长下，有偏 workload 与均匀随机 workload 各自触发的不变量违反数之比。
- 灰度期内该模块的生产事故数 / 回滚次数，与上一个同等变更量周期对比。
- 副作用指标（负向要留意）：为建模状态花的设计时间是否挤占了交付；若模块很小且只有一人维护，作者本人的经验是收益不明显，应当及时叫停。
