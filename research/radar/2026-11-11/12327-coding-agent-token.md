## 怎么试、怎么验证

**最小试用方式**：

不动任何架构，只做观测。选 2～3 个你日常真实会做的编码任务（例如一个小 bug 修复、一个新增函数、一次跨文件重命名），用现有代理正常完成，同时从日志里把 token 按“读文件 / 搜索 / 命令输出 / 写代码 / 其他”五类归账。每个任务类型至少重复若干次以排除偶然，具体次数按你手上的日志可得性决定，不要少于三次。

**判断指标**：

1. **结构指标**：写代码类 token 的实际占比是多少，是否落在 4%～10%。这是决定“要不要继续读原文”的开关。
2. **总量指标**：单任务总 token 与完成所需轮数。
3. **质量护栏**：任务一次通过率与返工次数。

**判定改善的标准**：只有在通过率与返工次数不明显变差的前提下，总 token 或轮数下降，才算改善。若 token 降了但返工率上升，属于把成本从上下文转移到了重试，不算改善。
