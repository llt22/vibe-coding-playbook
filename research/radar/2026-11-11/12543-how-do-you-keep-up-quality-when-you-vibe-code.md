## 是什么

这是 Hacker News 上的一条求助帖及其 27 条评论。提问者用 Claude 大量生成代码后，出现复杂度失控：功能随意扩张、缺少统一的行为定义、修 bug 变成反复修补（whack-a-mole）、边界条件和 UI bug 越积越多，且 agent 每次只盯着当前会话附近的代码，不理解全局。讨论的核心就是「vibe-coding 时怎么保住质量」。

帖子本身没有系统方法论，但评论里有若干条可以直接照做的个人工作流：以 CLAUDE.md/docs 承载规则与规格、大改先出计划文档、PR 前用子代理和第二个模型交叉审查、用静态分析器和 CI 让 agent 自己撞墙自纠、定期跑技术债审计、用测试和变异测试兜底。这些是本文的可用部分。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

以下做法来自不同评论者，彼此独立，可挑选组合。前提统一为：使用支持项目级规则文件（如 CLAUDE.md）和子代理/多模型调用的编码 agent，且代码库是需要持续维护的。

### A. 把规则和规格写进仓库（评论者 sadilek、Marco012、提问者本人）

1. 在仓库根放 `CLAUDE.md`，写入三条硬规则（据评论原意改写，非原文逐字）：

```md
# CLAUDE.md
- 任何代码改动必须同时更新 docs/ 下对应文档。
- docs 只写“有经验的工程师从零重建这套系统所需要的信息”，不写外观/呈现细节。
- 跨多个 PR 的大改动，先在 docs/plan/ 下写计划文档；计划模板的最后一步固定为：
  删除该计划，把其中仍有长期价值的内容并入 docs/。
- 创建 PR 前：先由子代理审查代码，再由第二个（另一家/另一个）模型审查，
  主代理按审查意见迭代修复，直到审查通过。
```

2. 为计划文档准备一个固定模板，模板必须包含「计划完成后删除计划、把长期有效内容折叠进 docs」这一步，避免计划文档变成第二套腐烂的文档。
3. 让产品规格、历史决策也进入仓库（评论者 Marco012：每个任务与决策都写成 .md，并互相引用；提问者本人打算把 product spec 提交进 repo）。目的是让每个新会话的 agent 不必从相邻代码「猜」产品该怎样表现。

### B. 先规划再动手（评论者 bahung1221、sadilek、gabe84700、alexjplant）

4. 简单改动直接提；不简单的先要一份 brief / 计划，人工审完再决定「一次做完」还是「拆成多 PR 计划」。规则：在有计划说明它如何契合现有代码之前，不让 agent 改代码；并且要真的会反驳它。
5. 先设计再编码（「vibe design before vibe code」）：先把 CRUD、数据实体、数据库清理这类底座做扎实。
6. 可参考 OpenSpec 的三段式（planning → implementation → archiving）：规划阶段把「要做什么 + 业务原因」讲清楚并和技术方案争论，实施阶段换一个新上下文执行；规格可以走 PR 给同事先审。

### C. 审查与门禁，让 agent 自己发现错误（sadilek、llbknapik、EduardoBautista、smallerize）

7. PR 前跑两级审查：子代理自审 + 第二个模型交叉审查（评论者举例 Opus 5.5 high 与 Codex Sol 6.1 high，型号请以自己可用版本为准），让主代理迭代到审查通过。
8. 把团队规范变成构建期硬门禁，而不是提示词里的软要求。评论者 llbknapik 的做法是把规则接进 .NET 静态分析器管线，agent 构建失败后自己回来改；例如禁止表达式体 `=>` 语法（原文示例，具体规则 ID 原文未给）：

```ini
# .editorconfig（示意：把不想要的写法设成 error，构建失败 → agent 被迫修正）
# 原文只给了「禁止 => 表达式体」这个例子，未给具体 rule id，需按所用版本自行查。
```

9. 用一条「模式检查」提示词/技能文件压住重复造轮子，评论者 smallerize 的 skill 文件里原样写着：

```
inspect existing code under [subdir] for implementation patterns.
```

前提：代码量决定 token 成本；代码多时改为列出想要的模式清单，或在 skill 的 references 里放一小段样例代码。
10. 更硬的版本：做成独立 gate —— 新代码与已有工具函数重复、重命名了已有命名、该用列表推导却写 for 循环等，直接让提交失败。
11. 把 `simplify`、`code-review` 这类技能固定在「验证」环节跑（EduardoBautista）；CI 至少要有测试、构建、lint、SQL 破坏性变更与重迁移检查。

### D. 定期清理与技术债

12. 每隔一段时间（评论者举例每月一次）对所有代码库跑一次「技术债」审计技能，让 agent 出报告再修；问题多时走计划流程。sadilek 的版本是定期要求一次代码审计，检查维度为 DRY / YAGNI / KISS。
   前提与理由：技术债越多，模型越容易照着坏样例继续写（提问者也观察到 repo 里遗留的坏代码会被 agent 抄走）。清理顺序按 mpd 的建议：先把已知坏代码枚举出来，逐个「修或删」，先清路再前进。

### E. 交接与自检

13. 让 agent 交接时录一段 demo 视频（sadilek 的做法）。经验是它在录制过程中常自己发现并修掉问题，而且责任转移到 agent 一侧——要说服人，就得自己把活做出来，而不是让你当它的 QA。

### F. 质量兜底（评论者 mpd，风格与他人差异最大）

14. 先固化架构再加功能；尽可能 TDD；代码写完后跑全量变异测试（mutation testing）。他称自己 agent 写的代码库里约 70%+ 是测试、基准和实验代码。人做变异测试很痛苦，交给机器才现实，这一步能解决很多微妙 bug。

## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）

- **能力发现**：这些评论把几类工作显式交给了 AI，而多数人不会想到：代码改动时同步维护 docs、PR 前的自我审查与交叉审查、定期技术债审计、用录制 demo 视频的方式自检并修 bug、清理重复实现。
- **任务匹配**：
  - 简单直白的改动 → 直接提需求；不简单的 → 先 brief/计划再实施（第 4 条），这是按任务复杂度分派协作方式。
  - 大改动 → 计划文档 + 多 PR；实施放在新上下文里跑（OpenSpec）。
  - 审查 → 交给另一个模型/供应商交叉做，避免同源盲区。
  - 机械但人做起来痛苦的验证（变异测试）→ 交给机器。
- **条件供给**：
  - 信息：CLAUDE.md 规则、docs/ 下的系统级文档、产品规格与历史决策记录、计划模板、现有代码的模式样例。
  - 工具：静态分析器/编译期规则、CI（测试/构建/lint/迁移检查）、技能文件（simplify、code-review、tech-debt）、变异测试工具。
  - 权限：允许构建失败阻断 agent 并让它自行回头修改（门禁必须能真的拦住）。
  - 反馈：审查意见回流给主代理迭代；构建错误本身就是反馈信号。
- **主动推进**：有明确的事件/时间触发形态——构建与提交触发（静态分析失败→agent 自纠；PR 前自动跑审查；commit 后更新架构图，评论者提到商业产品 archme）；时间触发（每月技术债审计）。
- **效果验证**：CI 全绿、变异测试覆盖、测试占比、审查通过作为合并前置条件；提问者的原始痛点是「修 bug 变 whack-a-mole、漏边界条件」，可用同类缺陷复现次数衡量是否改善。

## 证据与局限

**给出了什么**

- 一条完整可执行的个人工作流（sadilek 的 0–8 条），包含规则文件、计划模板、双模型审查、定期审计、交接方式。
- 一个可量化的经验值：mpd 称其 agent 生成的代码库中约 70%+ 是测试、基准与实验；以及「写完后跑全量变异测试」的做法。
- 一个失败模式的现场描述（提问者）：功能扩张导致无中心行为定义、修 bug 变反复修补、agent 只看会话周边代码、坏样例被复制。
- 一条具体的门禁实现路径（llbknapik）：静态分析器 + editorconfig 让构建失败，agent 被动自纠。

**哪些只是主张**

- sadilek 自己声明「没做过系统的消融实验，这些不一定都必要」，即 8 条里哪条真正起作用未知。
- 「变异测试能解决很多微妙 bug」「测试占比 70%+」都是个人经验陈述，无数据、无对照。
- 「demo 视频常让它自己发现问题」是轶事。
- 帖子仅 31 分、27 条评论，样本小，且发言者多为已有较强工程习惯的人（bottom-up 编程、TDD 偏好），存在选择偏差。

**内部分歧（重要）**

- sjducb 明确反对：pre-PMF 阶段别管代码质量，先冲功能找客户；而 mpd 主张早点还技术债以免在关键时刻撞墙。提问者自己正处在 pre-PMF、需要快速试错的阶段——这意味着**本报告的多数流程对他本人未必划算**，对已进入维护期、代码库中大型的团队更适用。
- 还有一派认为 LLM 代码只配当「电影布景」，用完即弃（mikewarot），只建议极度收紧提示词范围——这与「建流程保质量」是相反结论。

**适用条件**

- 需要长期维护、多人协作的代码库；一次性脚本或原型不必上全套。
- 需要 agent 支持项目级规则文件、子代理与多模型调用；工具链要能跑静态分析与 CI。
- 评论中出现的模型版本名（Opus 5.5、Codex Sol 6.1）可能有笔误或为作者内部叫法，落地时按自己可用的最强档位替换，不要照抄型号。

## 怎么试、怎么验证

**最小试用（建议 2 周，单仓库或单子目录）**

1. 选一个正在维护、规模中等偏小的仓库，别选 pre-PMF 冲刺中的主仓库。
2. 写一份 CLAUDE.md，只放三条：改代码必须改 docs；大改先出计划（模板最后一步是删计划、并入 docs）；PR 前子代理审 + 第二个模型审。
3. 挑下一个「中等复杂度」需求，强制走「brief → 人审 → 实施」流程，记录人工审 brief 花的时间。
4. 加一条构建期门禁（重复实现/命名冲突/lint 任一），确认 agent 真的会因构建失败自己回头改，而不是绕过门禁。
5. 第 2 周周末跑一次技术债审计（DRY/YAGNI/KISS 三问），产出报告后只修前 3 条。
6. 若仓库已有测试，试跑一次变异测试，看误报与耗时是否可接受。

**判断有没有改善的指标**

- 同一模块内「修了又坏」的反复修补轮次（提问者的 original pain）：试用前后各统计一批 bug 的平均返工次数。
- 回归缺陷数 / 每千行新增代码的缺陷数。
- PR 人工审查时长与审查意见条数（若流程只是把工作从写代码挪到审计划，需能看出来）。
- docs 与代码的偏离程度：随机抽 5 处改动，检查文档是否同步更新。
- 测试/基准代码占比、变异测试得分（如可运行）。
- agent 因门禁失败而自纠的比例（衡量门禁是否真的在起作用）。

**否证条件**：若两周后反复修补次数没降、PR 审查时长反而明显上升、或团队处在 pre-PMF 冲刺期，则说明这套流程对当前阶段不划算，应退回只保留「计划文档 + docs 同步」两条轻量做法。
