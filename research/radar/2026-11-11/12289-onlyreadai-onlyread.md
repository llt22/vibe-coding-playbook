## 是什么

OnlyRead 是一个 Chrome Manifest V3 扩展，给在浏览器里行动的 AI 代理加「只读模式」：代理可以读，但任何 send / post / like / edit / delete / 设置变更都在离开浏览器之前被拒。

作者给出的核心论点很关键：**让模型「小心一点」不是保证**，因为这条指令和提示注入藏在同一个地方（邮件或网页正文里），注入可以说服模型放弃它。所以 OnlyRead 在**模型之下、网络层**强制执行——通过 Chrome 的 debugger API 观察请求，与代理是哪个产品无关（Claude in Chrome、ChatGPT in Chrome、Gemini in Chrome、Comet、Manus Browser Operator、BrowserOS、Browser Use、Playwright 等都被覆盖）。

判定是四层漏斗，绝大多数请求走不到 AI：

1. **规则**：纯写方法、会导航的表单 post、上传、beacon 直接拒；实时 socket 在已知协议时解码，不知道就拒；纯读和已知遥测放行。
2. **按站点解码器**：读写共用同一端点的应用（Google sync channel、LinkedIn server actions、Facebook GraphQL）被解码，每个操作按名字识别。
3. **判定缓存**：随扩展发布的、来自录制测试会话的已复核判定。
4. **AI 裁判**：只回答一个问题——「这个请求会改变服务端数据吗？」；第一个模型定不了的交给第二个模型复核；**不确定或裁判不可达 = 拒**。

裁判只看到出问题的那个请求的地址和 body 简短预览（密码、token、卡号已剔除），看不到 cookie、header、响应和页面。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

前提：你需要一个 Chromium 系浏览器（Chrome / Edge / Comet / Dia / Opera / BrowserOS 等能装 Chrome 扩展的），并且已经或打算让某个 AI 代理在这个浏览器里操作你的真实登录态账号。**建议用一个专门 profile 做这件事，不要用日常主 profile。**

1. **安装扩展**。商店安装：在 Chrome 应用商店装 OnlyRead（README 给出的链接为 `https://chromewebstore.google.com/detail/onlyread/foajfkjhcigaillohhdbfadobkhpddij`）。
   离线安装：从 latest release 下载 `onlyread-<version>.zip`，解压后把其中的 `onlyread/` 文件夹在 `chrome://extensions` 里用开发者模式「加载已解压的扩展程序」加载。每个 release 都列出两个 zip 的 SHA-256，与商店版本同一构建。
   从源码构建：
   ```bash
   npm install && npm run bundle
   ```
   然后解压 `bundles/onlyread-<version>.zip`，在 `chrome://extensions` 开发者模式加载其中的 `onlyread/` 文件夹。注意 README 明确警告：`npm run build` 是**开发构建**，会接受本地测试 harness 的命令，**只能在专用 profile 里用**。

2. **配置 AI 裁判**（决定被拦截/放行的兜底判据）。在打开的窗口里二选一：
   - 登录 **OnlyRead Pro**：自带 1,000 次免费判定请求，不用自己管 key；
   - 或粘贴自己的 **OpenRouter** 或 **Vercel AI Gateway** key：裁判逻辑相同，OnlyRead 不收费，你按网关用量付费。
   不确定的请求会发往你选的网关（用自己的 key 时）或 OnlyRead Pro 服务（登录时）。

3. **选择守护哪些站点**。在设置里打开「代理可以使用的站点」。默认行为是：**只有 AI 代理在浏览器里干活时才守护**，你自己用时不拦。
   如果要全天候拦截（包括你自己手动操作），在设置 Security 下选 **Always**，并设一个 settings PIN（第二道锁）。

4. **临时加一个站点**。设置页可以守护任意站点，弹窗里也有 **Guard this site**。README 声称不需要逐站点规则，未测试过的站点「很可能也能用」。

5. **跑一个纯读任务来标定**。把这类任务交给代理，观察是否有请求被拒：整理收件箱、总结长邮件线程、找一封带发票的邮件、在 LinkedIn 上做调研。这些是 README 明确举的「读任务」例子，也是投毒邮件/网页最危险的场景。

6. **需要写的时候按站点放开**。README 的建议不是全局关掉守护，而是：当你想让代理写某个地方，就把**那个站点**关掉（switch that site off）。

7. **处理误拒**。被拒时页面会显示一条说明，代理可以继续完成任务的其他部分。如果某个站点上的**读**请求反复被拒，按 README 指引去提 false-block issue——「标注它」正是站点被深度测试的途径。

8. **知道它拦不住什么**。任何人都还能在 `chrome://extensions` 里手动禁用扩展，只有 Chrome 企业策略能阻止；守护期间 Chrome 会显示「started debugging this browser」横幅；Monitor 模式切换会重载受守护站点的已开标签页，且 Monitor 模式只存在于开发构建。

## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）

**1. 能力发现：AI 已经能做哪些还没想到交给它的工作**

README 没有列任务清单，但它给了一个很有用的分类轴：**读任务 vs 写任务**。它明确点名的读任务有：分诊收件箱（triaging an inbox）、总结线程（summarizing threads）、找发票（finding an invoice）、在 LinkedIn 上做调研。作者的判断是：人们交给浏览器代理的大多数事情本来就是读任务。这条可以直接写进手册——**先把工作拆成「只读就能完成」和「必须写」两类，只读那一类可以立刻放开授权。**

**2. 任务匹配：什么工作适合怎样的模型、工具和协作方式**

- 适用工具形态：**浏览器内代理**（在你已登录的会话里操作），而不是 API 集成。
- 适配范围：守护在浏览器层，不绑定具体代理，agent 扩展、AI 浏览器、自动化框架（含 Playwright、Browser Use）一视同仁；用别的代理，只要它能装 Chrome 扩展就覆盖。
- 一条重要的匹配判断：**浏览器代理用不了 OAuth scope**——它们拿着你的 cookie 在你已登录的会话里行动，没有 scope 可收窄，所以「网络层」是剩下唯一能强制只读的地方。这条解释了为什么不能靠授权范围解决。
- 模型角色：AI 裁判是一个**两模型接力**的配置（第一个判，第二个复核第一个定不了的），且规则/解码器/缓存先兜住大部分流量——这是「小模型/贵模型分工」的一个具体样例。

**3. 条件供给：需要提供哪些信息、工具、权限和反馈**

这一条是本篇最强的部分：

- **权限**：给代理真实账号的读写权限之前，先在网络层把写能力切掉；这是「授权边界」的可操作形态。
- **信息**：AI 裁判只拿到请求地址 + body 摘要（剔除密码/token/卡号），不给 cookie、header、响应、页面——这是一条可以直接抄的**最小信息披露**设计。
- **配置项**：守护站点清单、默认/Always 模式、settings PIN。
- **反馈回路**：误拒会在页面出提示、代理可继续；false-block issue 是把误拒转成站点深度测试的通道。
- **防篡改**：代理工作时不能关掉 OnlyRead、不能降低设置；settings PIN 是第二道锁。

**4. 主动推进：哪些工作可由时间、事件或状态触发并持续完成**

依据很弱。唯一相关的是默认模式：**OnlyRead 在检测到 AI 代理工作时自动附加守护，代理停下就退出**——这是一种「状态触发的自动启用」，不是任务编排。原文没有任何关于定时、事件驱动或持续完成工作的内容。

**5. 效果验证：怎样判断确实改善了结果**

原文给的不是指标，而是一条**决策原则**，而且这条原则本身就值得写进手册：

> 不确定就拒绝：漏掉一次读的代价是一次重试，漏掉一次写的代价无法撤销。

也就是说，验证的重点不是「拦得多不多」，而是**两类错误的代价不对称**：误拒（false block）可恢复，漏放（false allow）不可逆。这直接决定了阈值该往哪边偏。除此之外，README 给出的验证线索只有：100+ 站点被测、若干站点逐个读/逐个写深度测试、判定有缓存所以重复请求通常只判一次。没有任何准确率数字。

**原文自己列出的硬局限（这些直接决定能不能用）**：

- 守护期间 Chrome 会显示「started debugging this browser」横幅（默认只在代理工作时）；
- WebSocket 目前大多**整体放行或整体拒绝**，还没做到逐条消息判定；
- **按账号守护还没做**：同一 profile 里受守护站点的每个标签页都被守护，不管登录的是哪个账号；
- 在浏览器之外驱动屏幕的代理，目前只有 **Always** 模式能覆盖；
- 逐站点角色权限（比如允许评论、拒绝删除/支付/设置变更）还在路线图上，**现在受守护站点对代理是全站只读**；
- 只支持 Chrome 及能装 Chrome 扩展的 Chromium 浏览器，**Firefox / Safari 不支持**；
- 键盘前的人仍然可以在 `chrome://extensions` 里禁用扩展，只有企业策略能阻止。

**适用条件**：Chromium 浏览器 + 浏览器内行动的代理 + 以读为主的任务。如果你要让代理写（发邮件、发帖、改日历），当前版本只能整站放行，颗粒度不够。

## 怎么试、怎么验证（最小试用方式和判断有没有改善的指标）

**最小试用（半天内可完成）**：

1. 建一个**专用 Chrome profile**，只装 OnlyRead 和你要试的那一个代理，不登任何其他账号。
2. 只守护 2 个站点：**Gmail + Google Calendar**（README 说这两个被逐个读、逐个写深度测过，是最有把握的组合）。设置里设一个 settings PIN。
3. **先测拦截**（写侧）：让代理做 5 件明确的写操作——发一封草稿邮件、删一封邮件、改一个日历事件时间、新建事件、改一个设置。逐条记录是否被拒。
4. **再测误拒**（读侧）：让代理连做 10 次读操作——总结一个线程、找一个发件人、找一封带附件的邮件、读本周日程、统计未读数等。记录哪一次被误拒、代理能否自行继续。
5. 重复第 3、4 步各一轮，观察**判定缓存是否让第二轮更快/更稳**（README 说重复请求通常只判一次）。

**判断有没有改善的指标**：

| 维度 | 指标 | 可接受的判据 |
|---|---|---|
| 安全性 | 写操作拦截率 | 5/5 全拒。出现一次漏放，就说明这个站点组合不适合用，缩小范围重来 |
| 可用性 | 读任务误拒率 | 10 次读里误拒不超过 1 次、且代理能自行换路继续；否则这个站点当前不可用 |
| 恢复成本 | 误拒后代理是否仍能完成任务 | 能继续 → 可接受；每次都卡死 → 不可接受 |
| 打扰度 | Chrome 调试横幅、标签页重载 | 是否影响你同时手动用这个浏览器 |
| 自主性 | 完成任务过程中人工接管次数 | 与不装 OnlyRead 时比，接管次数不应显著上升 |

**扩大使用的门槛**：只有拦截率 100% 且误拒可接受，才把守护站点扩到 LinkedIn / X / Linear 等；只要开始需要代理「写」某个站点，就按 README 的做法**只对该站点关掉守护**，而不是全局关闭。

**一个必须自己补的验证**：README 承认 AI 裁判可能判错，且 WebSocket 是整体放行/拒绝。所以对**高度依赖实时推送的应用**（聊天类），要么先不守护，要么专门测一轮——因为那一层的判定粒度还不够细。
