## 是什么

Weave Router 2.0 是一个面向编码智能体的开源模型路由器：它可以插进任意编码 agent（原文举例 Claude Code、Codex、OpenCode、Pi），在一次会话中智能切换不同 LLM。原文给的典型例子是：棘手的调试或复杂系统设计交给能力强的模型（Astra），简单的前端改动交给便宜模型（Deepseek v4 Flash）。

原文给出的两个入口：

- 开源仓库：https://github.com/weave-os/router
- 托管版本：https://weaveos.com/router

作者称 2.0 相比之前的版本有三项改进：新架构（隐藏马尔可夫模型 HMM 追踪会话状态 + 分类器把会话映射到“能力相近的模型桶”）、更大的训练数据（用前沿 LLM 标注更多样化的编码会话）、更准的缓存逐出影响计算。作者说架构改造是最大的一次性能提升，缓存收益计算是成本下降的主要来源。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

**重要前提：原文没有给出任何安装命令、配置示例、API 参数或提示词。** 下面第 1 条是原文给出的入口，第 2–6 条是原文描述的、可迁移到自建路由方案的架构做法（属于思路，不是可直接复制的操作步骤）。

1. **获取工具**（原文仅给链接，未给步骤，需要自行阅读仓库 README 或注册托管版）：
   ```
   https://github.com/weave-os/router
   https://weaveos.com/router
   ```
   前提：已有一个可用的编码 agent 工作流，以及多家模型提供方的访问权限。作者说自托管版用 OpenRouter 上手更方便，因为不必分别配多个 provider 的账号和 API key；托管版则不用 OpenRouter，由官方挑选 provider。

2. **用 HMM 追踪会话状态**，而不是只看当前这一步。作者主张：两个用朴素分类器看起来很相似的会话，用 HMM 能更好地区分开——因为 HMM 不只评估“会话现在在哪”，还评估“它是怎么走到这一步的”。

3. **先选“模型桶”，再选具体模型。** 分类器把会话映射到一个能力相近的模型桶（例如 Deepseek 4.1 Flash 和 Astra 不会在同一个桶里）。先定桶可以把候选模型大幅缩减，从而收缩搜索空间；作者称这是单次最大的性能解锁。前提：只要某个桶里还有至少一个可用模型、且能按适配度排序，路由对不同可用模型集合是有韧性的。

4. **用前沿 LLM 标注大量、多样的真实编码会话数据**，用来引导（bootstrap）上面的 HMM 和分类器，并为强化学习提供更丰富的奖励信号。作者承认这一步“技术上有趣程度低”，但很重要。

5. **单独计算“换模型”的期望收益，包含缓存成本。** 切换模型意味着要付一次性成本去填充另一个模型的缓存，所以要更准确地算出这次切换值不值，避免不必要的高成本切换，同时在收益大于成本时照常切换。

6. **对 provider 做质量治理**：把质量下降的 provider 放进冷却期或降权。托管版由官方挑选 provider，自托管版如果走 OpenRouter 则可能受 provider 质量波动影响。

7. **可设置预算上限**（原文评论区问答确认支持），以及把路由接入任意 harness（作者称“接入 Copilot 能发的所有 LLM”，但**不支持本地或局域网部署的 Qwen 等开放权重模型**，训练出的路由模型本身也不是开放权重）。

## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）

- **能力发现**：原文把“选择用哪个模型”这件通常由人预先设定的工作，交给一个专门训练的模型在每轮自动完成，属于把决策类工作交给 AI 的例子。
- **任务匹配**：这是原文的核心。匹配粒度是**会话内的每一轮**，而不是整个会话或整个子代理；作者明确对比说，Copilot 的 Auto 模式“每个会话或子代理只路由一次”，他认为这基本不可能做对——因为同一个提示“把这个用 Rust 重写”，在一周的仓库里很简单，在 VSCode 这种仓库里极难。任务类型与模型的对应示例：复杂调试/系统设计→Astra，简单前端改动→Deepseek v4 Flash；桶=能力相近的模型集合。
- **条件供给**：需要多模型的访问凭证（托管版由官方管理 provider，自托管可用 OpenRouter 降低配置成本）；需要会话状态与历史（HMM 依赖“怎么走到这里”）；需要缓存状态与成本数据（切换期望收益计算依赖它）；需要预算参数；需要 provider 质量信号（用于冷却/降权）。原文未给出这些信息的具体格式或接入方式。
- **主动推进**：路由决策本身是逐轮自动触发、无需人工干预的；切换时机由会话状态、成本和缓存状态驱动。
- **效果验证**：原文用两个基准对比“路由器 vs 单一前沿模型”，同时看三个量：通过率、成本、墙钟时间。这是一个可迁移的验证框架（见下一节数据）。

## 证据与局限（原文给了哪些数据或案例，哪些只是作者主张，适用条件是什么）

**原文给出的数据（均为作者自测）**：

- Terminal Bench 4.0：路由器与 GPT-6 Astra 通过率相当；成本为 Astra 的 52%；完成任务快 2.2 倍。
- SWE Atlas：成本为 Astra 的 54%；快 2.5 倍。
- 原文说完整结果在 weaveos.com/router，本次材料中没有第三方复现或独立评测。

**只是作者主张的部分**：“模型集成一定胜过任何单一模型”是作者的假设与信念（他说这次里程碑“验证”了这个假设）；“架构改造是最大性能解锁”“成本改善主要来自缓存计算”都是自述归因，没有对照实验数据。

**评论区提出的质疑与未解问题**：

- 频繁切换会产生大量非缓存输入 token，这部分开销有多大、如何缓解，提问者未得到明确回答。
- 有人质疑 10^100 路径这个算法（认为实际每轮只决定下一步，应是 10×100），作者和另一位评论者坚持路径组合数应按 10^100 计。这条争议未解。
- 有人建议与 GPT-6.1 Sol 单模型对比，而不是只跟 Astra + Deepseek 的组合比；也有人指出 6.1 Sol 很慢，把慢模型的活外包给便宜快模型本身就可能值。
- 评论者希望看到与 Claude Code advisor 模式、Copilot HydraFusion 在架构规划与代码评审上的对比，作者表示愿意但尚未做。

**作者自己承认的局限**：错误的路由决策无法完全挽救（每次错误都有性能惩罚，只能靠会话继续时升级补救）；不支持本地/局域网开放权重模型；路由模型不开源权重；自托管走 OpenRouter 时 provider 质量波动可能影响效果。

**适用条件**：能同时访问多家模型 API；任务可以分解到会话轮次级别；成本或延迟是主要关切；能接受厂商自测数据作为初步依据。

## 怎么试、怎么验证（最小试用方式和判断有没有改善的指标）

**最小试用方式**

1. 选一条你自己经常做的、风险可控的编码任务流（例如“小范围重构 + 跑测试”）。
2. 先跑基线：全部用你当前惯用的单一前沿模型完成同一批任务（建议 10–20 个任务，记录结果）。
3. 再跑路由器：从 https://github.com/weave-os/router 或托管版 https://weaveos.com/router 接入你已有的 coding agent（安装与配置步骤需自行从仓库 README 获取，原文未提供）；设置预算上限；保留你原来的 agent 不变，只替换模型选择环节。
4. 同一批任务重跑，逐任务记录指标。
5. 若自托管走 OpenRouter，注意 provider 质量波动，先小样本验证再扩大。

**判断有没有改善的指标**

- 任务通过率 / 完成质量（用测试是否通过、或人工评审打分），这是第一优先，不能下降。
- 总 token 成本与美元成本。原文基准是降到单一强模型的 52%–54%。
- 墙钟时间。原文基准是快 2.2–2.5 倍。
- 模型切换次数，以及切换带来的非缓存输入 token 增量（评论提出的风险点，需要自己量化）。
- 错误路由导致的人工介入次数或返工次数（作者承认错误路由有性能惩罚但可补救）。

**判定标准**：通过率不下降（原文基准是“持平”）的前提下，成本或时间明显下降，才算改善；如果通过率下降、或新增的 token 开销抵消了成本收益，就不算改善。建议先用低风险、可回滚的任务做小样本对比。
