## 是什么

Claude Mods 是 Claude Code 的插件形态，用 function hooks 扩展代理的运行时行为，而不只是提供指令或外部工具。原文对机制的具体描述是：模块入口为 `register(on, options)`，其 handler 收到 `($, e, next)`——`e` 是事件，`$` 是该 handler 可用的引擎接口，`next` 是沿剩余链路的延续。作者强调「这更接近中间件，而不是更长的 system prompt」。Mod 还能参与受支持的界面渲染（如 diff 面板）。

原文明确 Mods 与其他机制是互补而非替代：

| 机制 | 主要职责 | 何时优先选它 |
| --- | --- | --- |
| Skills / 项目指令 | 提供任务知识与可复用流程 | 代理需要你的约定、清单或设计上下文 |
| MCP | 暴露外部工具、资源与集成 | 代理需要到另一个系统的受支持通路 |
| 经典 hooks | 在受支持的生命周期事件上跑已配置逻辑 | 已有事件能触发你的检查或审批规则 |
| Claude Mods | 围绕运行时事件与受支持 UI 面组合 function hooks | 需要更深的事件组合或界面行为 |
| Plugins | 打包与分发扩展 | 需要可复用的安装单元（其中可含 Mod） |

选择规则是「用满足验收标准的最小扩展面」。Mod 是一种插件，不替代插件系统。

可用性状态：官方 9 月 9 日更新点名该特性并给出测试用开关，称「数周内」扩大发布；Mods 源码目录明确标注接口为 early access，API 可能不通知就变。另有一个无关社区仓库 `0xDarkMatter/claude-mods`，不要与其混淆。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

前提（全部步骤共用）：一次性项目、合成数据、已获批准的 Claude Code 安装、不接触任何生产凭据。原文声明这些是「源码记录的命令」，作者并未声称在真实 Claude 会话中执行过；能否跑通取决于已安装的 build 与组织管控。

1. 确认版本。

```
claude --version
```

2. 用实验开关启动。

```
CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 claude
```

3. 在兼容会话中生成与当前安装匹配的类型声明，并与试点测试证据一起留存。

```
/plugin-types
```

前提与停机条件：如果命令或特性不可用，停下来找管理员确认受支持权限，**不要为了跑通示例而关掉组织托管保护**。升级后要重新生成声明，不要假设旧的类型还适用。

4. 从官方仓库的已审阅 revision 检出，在该 checkout 的根目录运行文档中的 diff 示例与测试脚手架（每个进程都带上实验开关）。

```
CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 claude --plugin-dir ./mods/diff
CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 claude plugin test ./mods/diff
```

注意：`/diff` 已是内置命令，会与你的实现争夺命令归属；「加载了一个目录」不足以证明某个 handler 真的跑了，要用测试或显式的非敏感诊断证据确认当前生效的实现。

5. 自制 Mod 时使用这个目录结构（一个已发布的 Mod 就是一个带 manifest 和 hooks 模块的普通插件目录）。

```
my-reviewed-mod/
├── .claude-plugin/plugin.json
├── hooks/
│   ├── hooks.json
│   └── register.ts
└── tests/
```

6. 官方 diff 的 `hooks.json` 用下面这个字段指向模块。原文强调这只是加载器片段，既不是完整可用的插件，也不是安全控制。

```
{
  "modules": ["./register.ts"]
}
```

7. 按第 3 步生成的声明构建入口，加测试，并**在加载前审阅完整源码**。不要使用凭空发明的命令（例如所谓「万能 Mod 安装器」）。

8. 选型时逐级降级：先看 Skills/项目指令、MCP、经典 hook、CI 是否能满足；只有确实需要更深的事件组合或界面行为时才写 Mod。例如品牌一致性通常用 Claude Code 的设计系统上下文栈就够了。

9. 分发走受支持的插件机制与组织审批流程，不要用搜索引擎找来的任意脚本。

10. 加载前按原文的验收矩阵逐项建测试（下表由原文表格改写）。

| 风险 | 测试方法 | 需要的证据 |
| --- | --- | --- |
| 版本或 API 漂移 | 改 CLI 或 Mod revision 后重跑整套 | 确切版本、重新生成的类型、审阅过的行为差异 |
| 链式组合不安全 | 在已批准的层之间混合允许、拒绝、转换的事件 | 预期顺序、最终决策、无意外的重复副作用 |
| 保护缺失或损坏 | 触发 handler 错误、超时、禁用 Mod、重载 | 保护不可用时，必需动作仍被某个独立控制阻断 |
| 敏感数据泄漏 | 让合成金丝雀值穿过每个目的地 | 在测试范围内，模型输入、导出日志、留存产物中都没有禁止值 |
| 只考虑 UI 的假设 | 跑受支持的交互与非交互路径 | 没有无人值守流程在等待不可用的界面 |
| 运维回归 | 禁用 Mod 并恢复已批准的基线 | 已知的回滚流程、负责人、基线检查通过 |

原文特别提示：**绝不要从一次正常的成功运行推断出 fail-closed 行为**；拒绝路径和不可用路径要用够不到生产环境的凭据故意去测。

11. 供应链审阅：用官方 plugin-marketplace 文档配合源码审阅，记录发布者、审阅过的 revision、依赖、申请的能力、更新路径与吊销流程；并且要测「实际会部署的那个组合」（含管理层与其他插件），而不是逐个孤立审批。

12. 成本核算方法（原文自述这是其评估方法，不是 Anthropic 的计费公式）：

```
每被接受任务总成本 =（可归属的模型与工具费用 + 工程与评审时间）
                    ÷ 通过同一验收标准的任务数
```

在相同的任务集、模型配置与质量线下比较基线与启用 Mod 的运行，并且要报告失败与回归，而不只是最快的那个成功样例。

## 对应的研究问题

**1. 能力发现**：原文给出的、此前不太会交给 AI 的用法是——让扩展参与引擎事件与界面渲染。可核实的例子是内置 diff Mod：把未提交改动与文件 hunk 渲染在 transcript 旁边，并在编辑与命令发生时更新面板；源码还处理了非 Git 目录和已注册 `/diff` 命令这两个边界情况。原文只把它当作「具体的 UI 用例」，未声称模型因此更聪明。更深的能力边界（自定义检查、转换）只是提出的试点设计，不是已验证能力。

**2. 任务匹配**：给了一张明确的选型表（见「是什么」）和一条规则——「用满足验收标准的最小机制」。可直接照做的判断顺序：需要约定/清单/设计上下文 → Skills 或项目指令；需要连外部系统 → 先 MCP；已有生命周期事件能触发检查或审批 → 经典 hook；确需更深事件组合或界面行为 → Mod；需要可复用安装单元 → plugin。

**3. 条件供给**：需要提供的具体输入有——已批准且版本已知的 Claude Code 安装、实验开关 `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1`、由 `/plugin-types` 按当前 build 生成的类型声明、带 `.claude-plugin/plugin.json` 与 `hooks/hooks.json` 的插件目录、受控测试数据（合成金丝雀值）、组织托管配置（`prependPlugins`；若组织提供了自己的 prepend 列表，必须显式处理 `sec-default@builtin`）、以及在禁用/重载时仍生效的独立控制与回滚负责人。

**4. 主动推进**：有依据的部分是事件驱动的机制——handler 注册在引擎事件上，包装型 handler 可以先行动再委托、然后检查返回值，`next` 控制链的延续；经典 hooks 也已在受支持的生命周期事件上做决策。原文提示要专门检查「哪一层拥有拒绝权、重试是否会重复副作用、continuation 是否按预期被调用一次」。但原文没有给出时间触发或状态触发的持续任务闭环（后台循环、定时任务）的具体做法，这部分无依据。

**5. 效果验证**：这是原文最可直接照搬的部分。验证手段有两块：一是上面那张六行验收矩阵（版本漂移、链式组合、保护缺失、数据泄漏、UI 假设、运维回归），每行都写明必须拿出什么证据；二是「每被接受任务总成本」指标，要求基线对照、同任务集同质量线、并把失败和回归一并报告。原文还给出两条判据：交互时间省了但返工变多可能是净亏；反之，在某个高频且昂贵的评审环节上的小改进，可以支撑一个范围很窄的 Mod。

## 怎么试、怎么验证

**最小试用方式**（全部在一次性项目、合成数据、无生产凭据下进行）：
1. 跑 `claude --version` 记录版本，用 `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 claude` 启动，在里面执行 `/plugin-types` 并保存生成的声明。
2. 从官方仓库的已审阅 revision 检出，用 `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 claude --plugin-dir ./mods/diff` 加载 diff 示例，并用 `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 claude plugin test ./mods/diff` 确认真正生效的是哪个实现（内置 `/diff` 会抢命令）。
3. 再自建一个范围最小的 Mod（只做只读界面渲染，或一次非敏感的数据转换），套用第 5、6 步的目录结构与 `hooks.json`，在加载前完整审阅源码并补测试。
4. 若任一步不可用，停下向管理员确认，不要关闭托管保护去凑通示例。

**判断有没有改善的指标**：
- **每被接受任务总成本**：基线 vs 启用 Mod，同一任务集、同一模型配置、同一质量线；分子含可归属的模型与工具费用加工程与评审时间，分母是通过同一验收标准的任务数。
- **拒绝/不可用路径**：handler 出错、超时、Mod 被禁用、重载后，必需动作是否仍被一个独立控制挡住（不能由一次成功运行推断 fail-closed）。
- **金丝雀追踪**：合成敏感值在模型输入、导出日志、留存产物中都不出现；界面上被遮住不等于从模型上下文移除，也不等于已存储副本被删除。
- **非交互路径**：无人值守流程不因等待不可用的界面而卡住。
- **回归与回滚**：禁用 Mod 后能恢复已批准基线，有负责人和已知回滚流程。
- **API 漂移**：每次改 CLI 或 Mod revision 后重跑整套，记录确切版本、重新生成的类型与审阅过的行为差异。
- **判定**：同一质量线下被接受任务总成本下降、或某个高频昂贵评审环节明显改善且无回归，才算净收益；交互变快但返工增多算净亏；同时必须报告失败与回归，而不只是最快的成功样例。
