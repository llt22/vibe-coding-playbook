## 是什么

seiso 是一个面向“AI 写、人和智能体读”的项目文档的 Markdown 约定 + 检查器（linter）。它要解决的问题：AI 写文档的速度超过人工评审速度，而这些文档又会被编码智能体当作下一次修改的上下文读回去，一处过期版本号或三份副本里只改了一份的字段列表，会同时误导人和智能体。

它由两部分组成：

- 一份独立发布的 **约定**（specification），不装工具也能照着做，含 worked examples 和 adoption guide；
- 一个**参考实现 CLI**（就是本仓库），按约定检查文档，stable 规则默认运行，其余为需要 `--preview` 的预览规则。

约定了六条规则：

1. 每篇文档声明一种 **kind**（如 `howto`、`reference`、`adr`），只写这个 kind 该写的东西——how-to 给步骤，设计为什么这样属于 ADR。
2. 每个事实只有一个归属地，其他页面链接过去而不是复述。
3. 长期存在的页面不记录比页面本身变化更快的值，如版本号、部署状态、计数。
4. 指针要指名文件或符号，别让读者自己去搜。
5. 完成的页面不面向“当初提需求的人”说话，也不叙述它自己或它描述的工作是怎么做出来的。
6. 工具无法做的判断要连同理由写下来；没有理由的例外本身就算违规。

作者对边界的说明：seiso 不猜“文字读起来是不是机器写的”，格式和拼写交给别的工具。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

前提：你有一个用 Git 管理、且存在（或即将有）AI 生成 Markdown 文档的仓库；本机可装 Rust / Python / Node 其中一种工具链。

1. **安装**（任选一种）：

```sh
cargo install seiso
uv tool install seiso    # or: pipx install seiso
npm install -g @scarletkc/seiso
```

   PyPI 和 npm 包内含预编译二进制，覆盖 Apple silicon / Intel 的 macOS、glibc 或 musl（如 Alpine）的 Linux x64 与 arm64、Windows x64 与 arm64。其他平台用 cargo；PyPI 包在其他平台也可用但从源码构建，需要 Rust 工具链。若从源码检出运行，用 `cargo run -- <command>`。

2. **在仓库根目录初始化配置**：

```sh
seiso init
```

   它会在仓库根写入 `seiso.toml`，内含建议的排除项、kind 映射和文档站点条目。**原文明确要求先复核这些内容再依赖结果。**

3. **跑一次检查**：

```sh
seiso check
```

   默认只跑 stable 规则（已满足其 promotion criteria 的规则）。

4. **按诊断修文档**。原文说每条诊断会给出问题位置和修法，agent 仅凭 seiso 的输出就能修掉大部分发现项；当修复需要判断（比如两个页面里哪个拥有某个事实）时，诊断会把这个决策点指出来。

5. **需要时查规则、查文档模型**：

```sh
seiso rule --all      # 列出所有规则及其状态
seiso rule <CODE>     # 解释某条规则并给示例
seiso parse           # 只看文档模型，不跑规则
```

6. **预览规则先在本地试，不要进 CI 门禁**：

```sh
seiso check --preview
```

   原文说明预览规则是实验性的、会误报，只在加 `--preview` 时运行，并明确要求“先在本地试，不要把预览规则放进 CI 门禁”。

7. **接入自动化**（前提：先确认步骤 3 的 stable 规则在你的仓库里结果可接受）。原文在 Integrations 文档中列出三类接入方式：Claude Code hooks、pre-commit、CI。**具体配置内容不在本次提供的原文里**，需查阅仓库的 docs/guides/integrations.md。

8. **不装工具也能照做的部分**：约定本身是独立发布的规范，另配 worked examples 和 adoption guide，项目可以只按规范整理文档。规范在 1.0.0 之前为临时性（provisional），且与 seiso 工具分别版本化，方向在 issue #37 开放讨论。

## 怎么试、怎么验证

**最小试用方式**（建议 1–2 周，限定在一个仓库的一到两个文档目录内）：

1. 选一个 AI 参与写文档最多的仓库，记录当前状态作为基线。
2. 按上面的步骤 1–3 安装、`seiso init`、人工复核 `seiso.toml`、`seiso check`。
3. 保存 baseline 的诊断数量与分类（按规则 code 统计）。
4. 让智能体仅凭诊断输出逐条修，人工只裁决诊断点名的判断项（如哪个页面拥有某个事实）。
5. 修完再跑一次 `seiso check --preview`，只看本地，判断预览规则是否值得关注（不进门禁）。
6. 如果结果可接受，再接 pre-commit 或 Claude Code hook；把 stable 规则放进 CI，预览规则排除在外。

**判断有没有改善的指标**（原文未提供指标，以下是可由本方案自行采集的）：

- 稳定规则诊断数的下降幅度（修复前 vs 修复后），以及一周后再跑是否反弹；
- 智能体自主修复比例 = 无需人工介入即可消除的诊断数 / 总诊断数，用于检验“agent 能自修大多数”这一主张是否在你的仓库成立；
- 需要人类裁决的判断点数量，衡量规范与仓库实际情况的摩擦；
- 人工评审文档时发现的“同一事实多处不一致”类问题数量是否下降；
- 接入自动化后，问题是在提交时就拦下还是仍在评审阶段才被发现（事件触发是否真的起作用）；
- 预览规则的误报率是否高到不可用。

若稳定规则诊断数长期不降、或智能体自主修复比例很低、或判断点摩擦过大，则说明这套约定在你的仓库不成立，应退回“只借用约定做人工整理”的用法，而不是继续加自动化。
