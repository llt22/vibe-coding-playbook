## 是什么

一个 Agent Skill 仓库（`XiaoMaColtAI/math-modeling-skill`，版本 1.3.0，GitHub 1848 stars），把数学建模任务拆成 **建模分析 → 代码实现 → 论文撰写** 三个阶段。既可以按顺序跑完整道题，也可以只执行其中一个阶段。

每个阶段绑定三类东西：

| 阶段 | 角色 | 固定交付物 | 独立门禁 |
|:--:|---|---|---|
| ① | 建模手 | `题目分析报告.md`、`术语表格.md` | `M1` 建模终检 |
| ② | 编程手 | 代码、结果表格、三类各至少 3 张候选图、至少 1 幅总体建模流程图、`results/复现清单.json` | `P1` 最小可运行结果、`P2` 编程终检 |
| ③ | 论文手 | 至少 8 幅正式图、默认 `完整论文.docx`；显式要求时加 LaTeX 源码/PDF/哈希清单 | `W1` 证据大纲、`W2` 论文终检 |

质检由阶段内的**只读 Subagent**执行，不是第四个固定角色；默认只启用固定质检，其他协作需用户显式选择。

## 具体做法

**前提**：需要一个支持本地 Skills 或 Agent 工作流的宿主（README 列出的有 Claude Code、Codex、Cursor、Trae、Qoder，具体加载方式以各工具当前文档为准）。

1. **安装 skill**（二选一）：

```bash
git clone https://github.com/XiaoMaColtAI/math-modeling-skill.git
```

```bash
npx skills add https://github.com/xiaomacoltai/math-modeling-skill --skill math-modeling
```

克隆后把仓库放进所用 Agent 的 Skills 目录，或按该工具的方式加载本目录（也可下载 ZIP 解压放入）。

2. **约定目录契约**：`SKILL_ROOT` 为本仓库根目录，只读，角色规范/算法资料/脚本/模板从这里读；`PROJECT_ROOT` 为用户题目目录，所有运行产物只写这里；题目与附件保持只读，需要改模板时先复制到 `PROJECT_ROOT`。典型产物结构：

```text
PROJECT_ROOT/
├── data/                         # 题目附件，只读
├── 题目分析报告.md
├── 术语表格.md
├── 问题1_求解.py 或 问题1_求解.m
├── results/
│   ├── 问题1_结果.csv
│   └── 复现清单.json
├── figures/
│   ├── raw_q1_*.svg / raw_q1_*.png
│   ├── process_q1_*.svg / process_q1_*.png
│   ├── result_q1_*.svg / result_q1_*.png
│   ├── flow_overall_model.svg / .png     # 总体建模流程图（必须）
│   └── _qa/                       # 自动生成的灰度质检预览
└── 完整论文.docx                 # 默认交付的 Word 论文
```

3. **用提示词触发**（原文给出的可直接抄的示例）：

```text
使用数学建模 Skill 完成这道题，默认生成 Word 论文。
使用数学建模 Skill 完成这道题，额外启用附件盘点、文献调研和算法原型 Subagent。
使用数学建模 Skill 完成这道题，除固定质检外不使用其他 Subagent。
只做建模分析，输出题目分析报告和术语表格。
只实现现有模型，使用 MATLAB 运行并生成全部结果和图。
根据现有代码结果生成完整论文.docx。
```

单阶段执行是把这个流程迁移到自己任务时最有价值的部分——可以只借“先出分析报告和术语表”“先验证最小可运行结果”这类断点。

4. **按门禁顺序推进，不要攒到最后再质检**：`P1`（最小可运行结果）必须在全量计算和正式出图之前执行；`W1`（论文证据大纲）必须在长篇正文和双格式排版之前执行；原文明确“禁止等全流程结束后才首次质检”。

5. **走阶段反馈回路**：编程手发现公式、约束或参数无法实现时，携带实际报错返回建模手修正；论文手发现关键结论缺少真实结果、图表或文献支撑时，返回对应阶段补齐；任一独立门禁返回 `FAIL`，由原阶段执行者按证据修正并重新派发复验，**主 Agent 不得自行覆盖失败结论**；修正后从被阻断阶段继续，不重复已通过的阶段。

6. **按需调用集成工具**：科研可视化（数据剖析→选图→出版级绘制→自检闭环→多格式导出）、双引擎论文搜索、DOCX 工具（官方模板、递归 LaTeX→DOCX、OMML 公式、三线表、校验）、LaTeX 工具（环境诊断、模板溯源、真实编译、哈希绑定、PDF 质量校验）、Excel 工具（模板处理、公式重算、错误检查）、PDF 工具（读题 PDF，提文本/表格/图片）。

7. **跑双引擎文献检索**（OpenAlex + AnySearch 并行，按 DOI 或题名交叉核验；正式检索默认同时跑两个引擎，单引擎参数只用于诊断）：

```bash
python tools/paper_search/scripts/hybrid_scholar.py \
  --query "robust optimization vehicle routing" \
  --limit 10 \
  --json
```

OpenAlex 可用 `--email` 提供礼貌池邮箱；AnySearch 需要密钥时设置环境变量 `ANYSEARCH_API_KEY`。

8. **动态依赖检查**，只检查实际用到的功能：

```bash
python references/roles/编程手/scripts/check_env.py \
  --features data visualization optimization
```

```matlab

report = check_matlab_env(["data", "visualization", "optimization"]);
```

9. **算法资料渐进式加载**：先读算法索引，再按问题类型加载对应资料；每道子问题最多使用两个独立模型体系。类别覆盖优化、预测、评价、图论、统计、综合、机器学习。

10. **跑回归验证**：

```bash

python tools/docx/scripts/self_check.py

```

## 对应的研究问题

**1. 能力发现**：它把几个通常不交给 AI 的环节显式纳入流程——出版级科学可视化（色觉友好编码、SVG + 300 DPI PNG 导出、成图自检闭环）、Word 原生 OMML 公式与三线表排版、LaTeX 整篇转 DOCX、官方模板溯源与真实 PDF 编译、双引擎文献检索交叉核验。这些是“已经能交给 AI、但一般想不到”的候选能力。

**2. 任务匹配**：用角色切分任务——建模手负责读题/拆子问题/选模型/设计求解与验证；编程手负责 Python 或 MATLAB 实现与出图；论文手基于真实结果构建论证并生成文档。约束是“每道子问题最多两个独立模型体系”（物理题同一机理的基础近似与高精度展开算一个模型族）。

**3. 条件供给**：需要提供——可写的工作目录（`PROJECT_ROOT`）与只读的 skill 根目录分离、题目附件保持只读、官方模板（没有官方模板时才用内置构建基线）、算法资料库、动态依赖检查、以及渐进式加载机制（只读当前阶段需要的角色规范、算法资料和工具说明）。

**4. 主动推进**：门禁是状态触发的——`P1` 在全量计算和正式出图前触发，`W1` 在长篇正文和双格式排版前触发，任一 `FAIL` 触发原阶段返工并重新派发复验，修正后从被阻断阶段继续。这套“按阶段状态触发质检 + 阻断即返工”的机制不依赖人盯着。

**5. 效果验证**：有明确的判断物——五个门禁的通过/失败、回归测试套件（覆盖双引擎搜索、公式转换、DOCX、LaTeX 模板与校验、Excel 重算、论文结构、动态依赖、复现清单和科学绘图工具）、`results/复现清单.json`（随机种子、输入文件 SHA-256、运行时与依赖版本、关键参数、唯一复现命令）、LaTeX 侧的权威资源—源码—产物哈希绑定、成图自检与 `_qa/` 灰度质检预览。

## 怎么试、怎么验证

**最小试用（建议按这个顺序，成本从低到高）**：

1. 克隆仓库，直接跑三条验证命令，确认在本地环境能装上、测试能过（这是零风险的第一步，也是对“这东西是不是真的完整”的检验）。
2. 挑一道**已经做过、知道正确答案**的建模题，只用单阶段提示词跑“建模分析”，产出的 `题目分析报告.md` 和 `术语表格.md` 与你当初的人工版本对比。这一步不需要跑代码、不需要出图，最便宜。
3. 再挑一道小题，跑完整三阶段，重点观察 `P1` 门禁有没有在全量计算之前真的拦下不可运行的方案。
4. 把骨架平移到非建模任务上做一次压力测试：例如把“建模分析→代码实现→论文撰写”换成自己领域的“分析→实现→交付”三段，把五个门禁换成自己领域的检查点，看目录契约（只读根目录 + 可写项目目录）和只读质检 Subagent 这两个机制是否仍然成立。

**判断有没有改善的指标**（选 3–5 个记录即可，关键是和人工基线对比）：

- **门禁拦截率**：`P1`/`W1` 提前拦截的问题数 ÷ 总返工问题数。如果拦截率接近 0，说明门禁是摆设，流程价值主要在交付物契约而非质检。
- **阶段返工率**：从论文阶段退回建模阶段的次数。原文设计的目标是“修正后从被阻断阶段继续，不重复已经通过的阶段”，这个数字应当下降。
- **复现成功率**：只拿 `results/复现清单.json`，在另一台机器上不复用任何上下文，能否跑出同样的结果图。这是原文给出的最可验证的硬指标。
- **格式校验通过项**：`python tools/docx/scripts/self_check.py` 的通过情况，以及最终文档在公式、图表编号引用、参考文献上的人工返工次数。
- **端到端时间与人工干预次数**：同一道题，用 skill 与不用 skill 各一次，记录总耗时和你被迫介入的次数（介入越少越说明流程自洽）。
- **横向对照**：`只做建模分析` 与 `完整三阶段` 两种用法分别记录，判断收益主要来自阶段拆分还是来自工具集成；如果前者贡献大，说明这个 skill 值得学的是流程而非代码。
