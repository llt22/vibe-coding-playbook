# Using Claude Code: Spending your effort

- 结论：**值得一试**。把 Claude Code 的 effort 档位当成一种可调的工作方式：用「让模型先采访你→低档实现→低档迭代→高档验证」的循环做功能开发，并按任务类型选档（低档在环讨论、中档常规实现、高档验证与边界情况、最高档全自主难题）；理由是原文给出了明确的档位分工和一组可复现的效果对比，但数据来自厂商内部运行，具体倍率需自己试。

## 是什么

Claude Code 官方博客（claude.dev）的一篇工程文章，作者 Thariq Shihipar，讨论 Claude Code 里的 effort（努力档位）到底是什么、什么时候用哪一档。

核心定义：effort 是给模型的一个「你愿意让它花多少算力」的近似值。作者用类比说明——如果要求别人 12 小时做完一件事，对方会尽力做；如果只给 1 小时，对方会先给一个满足需求的版本，然后等你迭代。高档位下模型会「更多地为判断和验证采取自主行动」，低档位则快速给出起点。

文章给出三样可直接用的东西：

1. 一条作者自己在用的功能开发循环（访谈 → 低档实现 → 低档迭代 → 高档验证）。
2. 一张按任务类型选档的经验法则。
3. Claude Code 里切换档位的入口 `/effort`，可在对话中途切换。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

**前提**：在 Claude Code 中使用，模型为 Opus 5.5 或 Fable 5.1（文章只测了这两个及 Fable 5）。作者提到这些模型的 effort 调整不会破坏 Claude Code 的 prompt cache。

### A. 功能开发循环（作者自述在用的做法）

1. 给 Claude 一份 spec，并让它就你遗漏的细节采访你。
   - 前提：你手上已有一个大致成形的需求描述，哪怕不完整。
2. 用低档（low）实现它。
3. 审查实现，确认它抓住了要点（gist）正确；需要的话继续在低档迭代。
4. 用高档（high）做验证和测试。

### B. 切换档位

在 Claude Code 对话里使用：

```
/effort
```

可以按任务切换，也可以在同一段对话中途切换（原文：“Try varying effort for Opus 5.5 and Fable 5.1 based on your task or even mid-conversation by using /effort in Claude Code”）。

### C. 按任务类型选档（作者的原话规则）

| 档位 | 用在什么任务 | 原文场景举例 |
| --- | --- | --- |
| Low | 需要快速响应、人在环里 | 头脑风暴、草图（sketching）、简单改动 |
| Medium | 大部分常规软件工程工作 | 新功能实现 |
| High | 验证重要、或存在边界情况的工作 | 在存量代码库里修 bug |
| Max | 希望 Claude 完全自主解决困难问题 | 端到端构建并验证一个应用；在关键软件里找安全漏洞 |

经验补充：

- 规格化程度会改变档位差异。作者做「高度指定的构建任务」实验时，先让 Claude 深入采访他形成 spec，再拿这份 spec 让不同模型在不同档位实现，结果各档位表现明显趋同（设计和实现相似，只是细节不同；高档还花时间简化了一些细节）。也就是说，spec 越细，升档带来的差异越小。
- 升档解决的是「遗漏边界情况」，不解决「方向选错」。原文的失败分布图结论是：提高 effort 会减少「缺边界情况」类失败，但不会修复模型走错路线（wrong approach）的失败。
- 边界情况密集的任务最值得升档：安全、硬件、代码审查、性能优化，以及生产要求高的复杂任务。

### D. 成本预期（来自作者自己的玩具实验，Opus 5.5）

| 任务 | low | medium | high | max |
| --- | --- | --- | --- | --- |
| 未充分指定的构建（健身追踪 app） | 1.5 分钟 | 4 分钟 | 11 分钟 | 67 分钟 |
| 轻度指定的设计任务（重做 /config 菜单） | 1 分钟 | — | — | 28 分钟 |
| 高度指定的构建任务 | 16 分钟 | 22 分钟 | 33 分钟 | 79 分钟 |

用法：如果只想要一个可迭代的基底，低档就够；如果想要最好的一次成型结果，用最高档。

## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）

**1. 能力发现（AI 已经能做哪些还没想到交给它的工作）**

原文展示了高档位下模型自发去做、而低档位不会做的一批「元工作」，这些通常不会被显式要求：

- 对自己的初稿做对抗性审查（adversarial review）。
- 去读已安装解析器的源码找 bug。
- 写随机文档 fuzzer；写随机化测试并与一个从不做 compaction 的参考实现对比。
- 检查自己新写的测试是否真能抓住原始 bug（「did not check that its new test would have caught the original bug」是低档的失分点，高档会检查）。
- 对同一份数据尝试两种预处理方式，发现显著结果列表变化后，先弄清原因再选正确的那一种。

**2. 任务匹配（什么工作适合怎样的模型、工具和协作方式）**

这是本文最直接的贡献：给出了 effort 档位与任务类型的对应表（见上一节 C），以及「人在环 vs 不在环」的匹配结论——原文指出 gsea-proteomics 这类任务如果有用户在环，Claude 可能会直接问用户该用哪种数据准备方式；没有用户在环时，高档位表现更好。此外，规格化程度也是匹配变量：spec 越细，档位间差异越小。

**3. 条件供给（需要提供哪些信息、工具、权限和反馈）**

- 需要提供：一份 spec，并允许/要求模型就缺失细节采访你（循环第 1 步），这是让后续低档实现不跑偏的前提。
- 反馈是循环的一部分：第 3 步的人工审查决定是否需要继续在低档迭代。
- 权限/访问条件会影响结果：文中注明 Opus 5.5 的测评响应上限 128k tokens，且没有 GitHub 或 PyPI 访问权限；安全类任务在无网络访问下运行。这提示工具的可得性（网络、包源）是外部条件。

**4. 主动推进（哪些工作可由时间、事件或状态触发并持续完成）**

只有间接依据：max 档被定义为让 Claude 完全自主解决困难问题（如端到端构建并验证一个 app）。原文没有给出任何时间/事件触发机制或持续运行的编排方式。

**5. 效果验证（怎样判断确实改善了结果）**

原文给出了一套可借用的验证方式：

- 用有标准答案的基准（Terminal-Bench 3.0）在固定任务集上比较不同档位。
- 同时看通过率和 token 消耗（文章图表即为「通过率 vs token 花费」）。
- 对失败做分类统计，区分「缺边界情况」「走错方向」「测试没抓到 bug」「误读需求」等类型，用来判断升档到底修复了哪类问题。
- 具体可比数据（见下一节）。

## 证据与局限（原文给了哪些数据或案例，哪些只是作者主张，适用条件是什么）

**原文给出的数据与案例**

- Terminal-Bench 3.0：同一批 70 个任务（4 个 GPU 任务被排除），每个模型都跑；Opus 5.5 晚约三周运行，响应上限 128k tokens，无 GitHub 或 PyPI 访问；Opus 5 的最高纪录是其 effort-120 那次运行。
- 类别通过率（Fable 5.1，低档合并两个最低档位、最高档合并三个最高档位，因为类别样本小）：Security 64%→87%，Hardware 34%→75%，ML 54%→73%，Science 41%→61%，Software 43%→56%，Media 18%→30%，Operations 12%→22%。
- 失败分布（Fable 5.1，每任务 5 次尝试共 370 次）：低档 140 passed；最高档 214 passed。低档失败里「a bug its tests missed」40 次、「misread a requirement」45 次；最高档对应为 14 和 26。
- 单任务案例（Opus 5.5，每任务 5 次尝试）：
  - html-js-filter（HTML 消毒器，穷举所有 JS 注入方式）：Fable 5.1 低档 1/5 → xhigh 5/5；低档约 2 分钟/次，高档约 33 分钟。
  - mvcc-lsm-compaction（按崩溃报告修存储引擎 bug）：Opus 5.5 低档 0/5 → xhigh 4/5。
  - cli-2ph-simplex（Python CLI 线性规划求解器）：Opus 5.5 低档 0/5 → high 5/5。
  - gsea-proteomics（蛋白质组学 GSEA）：Opus 5.5 低档 0/5 → high 4/5。

**只是作者主张、无量化支撑的部分**

- 「effort 是算力的近似」「高档位会采取更多自主判断和验证」是概念性解释。
- 「spec 越详细各档位越趋同」只有几个玩具实验支撑，作者也自称是 toy examples / individual runs。
- 玩具实验的耗时表来自单次运行，不是多次采样的统计。
- 「effort 不破坏 prompt cache」是作者对自家产品的陈述，未给测量方法。

**明显的适用条件与局限**

- 数据来自厂商内部运行（作者明确说明：自己的内部跑，每任务 5 次尝试，Fable 5.1 关闭了生产安全干预；在 Claude 产品里 Fable 5.1 的部分安全请求会被转给 Opus；安全任务在无网络访问下运行），因此数字与公开排行榜或发布文章不一致。
- 失败类型由「模型评委」判定，原文自己标注为 approximate。
- 只在 Opus 5.5 / Fable 5.1 上测过，档位名称（low / medium / high / xhigh / max）在不同图表中不完全一致，规则表与基准图用的档位标签并不完全对齐。
- 作者供职于 Claude 团队，文章属于官方工程博客，立场不完全中立。
- Terminal-Bench 3.0 的题目复杂度作者自己也说「远高于我平时会遇到的平均任务」，因此这些对比的绝对收益未必能线性迁移到日常开发。

## 怎么试、怎么验证（最小试用方式和判断有没有改善的指标）

**最小试用 1：跑一遍四步循环**

挑一个你下周本来要做的新功能，按 A 节的四步走：让 Claude 先采访你补齐 spec → low 实现 → 你 review、按需 low 迭代 → high 验证测试。对照组：用你原来的习惯做法（比如直接中/高档一次做到底）做另一个规模相当的功能。

**最小试用 2：对同一任务做档位对照（成本最低、信号最强）**

选一个「边界情况多」的任务（例如输入校验/清洗、HTML 或模板消毒、性能优化、在存量代码里修 bug），分别在 low 和 high（或 max）各跑一次，比较结果。原文的判据是：如果低档失败是因为「缺边界情况/测试没抓到 bug」，升档应有效；如果失败是「需求读错/方向选错」，升档基本无效，应该改 spec 而不是加档。

**判断是否改善的指标**

- 一次通过的比率（同一任务多次跑，而不是只看一次）。
- 你的 review 发现的问题数、返工轮次。
- 进入验证阶段后才暴露的缺陷数（对应原文的「a bug its tests missed」）。
- token 消耗与墙钟时间（原文的核心图表就是「通过率 vs token 花费」——升档要值回票价的 token）。
- 失败归因：记录失败属于「缺边界情况」还是「走错方向」。这是决定「该升档还是该补 spec」的分叉点。
- 规格化的边际收益：同一任务给一份粗 spec 和一份经过采访补全的细 spec 各跑一次，看各档位的差距是否收窄。若收窄，说明性价比更高的做法是先把 spec 采访清楚，而不是无脑开最高档。
