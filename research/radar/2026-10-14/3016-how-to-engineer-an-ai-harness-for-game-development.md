## 是什么

这是 Kyle Kukshtel 把一场 45 分钟演讲（“Your Game Is A Harness”，Indie Rodeo Calgary）改写的博客文章，主题是如何在日常游戏开发（而非 Twitter 上的一次性 demo）中用好 LLM。

核心论证链：作者自称在网页栈（Svelte 等）上已几乎找不到 LLM 做不了的事，但一碰非网页的游戏就失败，得出“LLMs are Bad At Games”。他把原因归结为结构性而非模型能力：游戏里大量内容不是代码（资产、布局、场景、数据），这些对 LLM 是“不透明”的；加上游戏训练数据远少于网页项目，且没有标准化工具。结论是：让 LLM 做好游戏，是一个 **context 问题**，要靠 harness（一组针对特定预期输入的 agent 行动模式）把游戏“打开黑盒”，变成 agent 能直接寻址的东西。文章后半段给出了一组明确称之为 “very tangible, actionable” 的做法。

注意：原文是演讲的复述，不是教程，通篇没有可复制的代码、命令或提示词（唯一点名的工具是 `odiff`，但未给用法）。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

**总前提**：作者反复强调这些是“越早越好”的架构约束，在生产末期再补会“VERY hard”，甚至需要临上线时做根本性改动；因此建议在写第一行代码前就当作目标。原文自称这些做法即使不用 AI，对普通游戏开发也是净收益。

1. **单一随机源（Fixed Randomness）**
   - 前提：项目刚开始。
   - 做：在游戏启动时创建一个唯一的、带种子的随机源；让所有非确定性调用（原文举例 `Random.Float` 之类）都走这个源，而不是在 30 个地方各自调用全局随机。
   - 目的：让第 N 次随机调用的结果每次都一样，从而能确定性地重建几乎任意游戏状态。

2. **可截图 + 图层开关（Screenshot-ability）**
   - 前提：引擎提供截图 API 或功能（原文说“most engines have some built in screenshot API or functionality”）。
   - 做：接入截图能力；另外加上 UI 层 / gameplay 层等的独立开关，便于只保留当前要处理的那一层，减少视觉干扰。
   - 目的：让 agent 每次改动前后都能取到一致的画面用于比较。

3. **用图像 diff 做定量评估（原文最可直接照做的一环）**
   - 前提：上一步的截图能力；以及一个图像 diff 工具。
   - 做：用原文点名的免费命令行图像 diff 工具 `odiff`，对两张图（改动前 / 改动后，或产出 / 目标图）求差，输出一张 diff 图和**量化的相似度数值**（原文举例形如“85% similar”）。把这个数值交给 LLM 读，作为每个 agent turn 的稳定评估基线，让它朝着“降低差异 / 提高相似度”迭代。
   - 原文给出的理由：直接把截图丢给多模态模型会带来“context pollution”——模型会同时处理你没想让它改的所有区域（作者用会议官网首页 + “把骨架改成海盗”的标注例子说明，未被请求的绿色区域全是噪声），所以要先 diff、再裁剪，只把需要判断的东西给模型。
   - 注意：**原文没有给出 odiff 的安装或调用命令**，落地前需自行查该工具文档；此处不代为编造。

4. **确定性状态：一开始就做 save/load**
   - 前提：与第 1 步同样在项目早期。
   - 做：不要像业余做法那样把保存/加载拖到最后当成一个“feature”，而是从最初就把它与核心架构一起设计，使你能随时精确保存和加载任意状态。
   - 目的：这是后面所有可复现、可评估的前提。

5. **Thing 驱动开发（fat struct / 单一对象类型）**
   - 前提：愿意放弃强 OOP 继承模型。
   - 做：假设游戏里所有东西本质上是同一种东西，代码里就用单一类型（原文建议直接叫 `Thing`）。每个 `Thing` 带一组 stat 类数值、一个 `isAlive` 之类的共用标记、以及一个 `type` 枚举，具体行为由实现代码根据 `type` 分派。
   - 原文给的收益：对象模型只有一个真相来源，AI 不需要理解 100 个类和它们的关系（那会塞满 context，并且让它纠结“该继承？该改类型？该新建类？”）；序列化/反序列化只有一个入口一个出口，避免“polymorphic deserialization”和多类型继承树带来的奇怪反序列化竞态。原文明确说这并不像想象中那么费内存，并推荐 Wookash podcast 中与 Dreams 创作者的对谈作为延伸阅读。
   - 原文未给出 `Thing` 的实际代码。

6. **可寻址状态：命令模式（Command Pattern）**
   - 前提：已采用第 5 步的单一对象类型。
   - 做：不要把状态变更写成松散函数调用，而是表示为（理想情况下可序列化的）命令对象，统一经过一个处理类来应用到对象上。复现 bug 时，从起始状态“回放”序列化的命令即可，而不用去问玩家当时做了什么。
   - 关键延伸：命令**不必由游戏本身产生**——可以在文本编辑器里手写（或由 AI 生成），直接回放到运行中的游戏实例上，**无需编译**。
   - 目的：给 AI（和你）一个带类型的游戏交互界面，把游戏变成“可操纵的”（puppet-able）；同时减少编译等待，让 agent 循环更紧。原文的一般性原则是：能让游戏不编译就产生变化的能力越强越好。

7. **数据外置（Data Management）**
   - 前提：愿意把静态数据从代码里搬出去。
   - 做：把描述“东西本来是什么样”的静态运营数据（原文举例：`Type`、`attackDamage`、`walkSpeed`、`boatSpeed`）放在游戏外部的数据源里，游戏启动时反序列化并套用到对应对象上。改数值 = 改数据源，不再需要重编译或写 console 命令之类的绑定。
   - 工具：原文作者用自研的 Depot（正产品化），也提到其他团队用 Google Sheets 或自建工具。
   - 目的：非程序员、其他团队成员和 AI agent 都能在**已有的 build 上**迭代，甚至不需要编辑器权限。作者在 Cantata 项目里就是约 7 名非程序员拿 build + Depot 迭代。

8. **独立模拟 / 黑盒（Standalone Simulation / Blackbox）**
   - 前提：有一定工程投入，重构引擎与逻辑的边界。
   - 做：把游戏模拟逻辑从引擎的操作逻辑中抽出来，物理上作为独立的 DLL/library 存在；引擎与模拟之间通过“命令”（即第 6 步的命令）通信，模拟返回更新后的状态，引擎通过对比上一次收到的状态做 diff 来理解发生了什么，并“Dumb”地照做——模拟说动了就动，不质疑。
   - 原文举的例子：移动请求发给模拟，模拟判断目标是否合法并结算，返回“该对象已移动”的状态对象；引擎 diff 前后状态后播放动画、模型、音效。
   - 收益：任何来源（网络、LLM、其他）都能向核心发命令，网络编程因此变简单得多。

## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）

- **能力发现**：文章的核心贡献是“还有哪些工作可以交给 AI”的扩展——不只写代码，还包括：回放序列化命令来复现 bug、通过外置数据源调数值、通过截图 diff 反复逼近目标视觉结果。前提是先把这些能力做成机器可读的接口。
- **任务匹配**：原文给出的匹配判断是负面的/边界性的——默认状态下 LLM 不适合游戏，原因是游戏含大量非代码、不可寻址的内容，且训练数据量比网页项目少“orders of magnitude”（作者推测）。适合的形态是：目标可量化（图像相似度）、状态可复现（确定性 + 命令回放）、循环短（无需编译）的任务。原文提到 Claude Code 与较新的 Claude 模型是作者当前的主力工具，并称在网页栈上几乎无可不能（属作者个人经验主张，非评测结论）。
- **条件供给**：需要提供的东西文中列得很实：种子随机源、早期就存在的 save/load、引擎截图能力与图层开关、一个图像 diff 工具（`odiff`）+ 量化相似度、外置数据格式与反序列化路径、可序列化且可在文本编辑器中编写的命令接口及其回放通道、以及把模拟核心做成独立库。反馈信号主要是“截图 diff 的相似度数值”。
- **主动推进**：原文只覆盖了**单次任务内的自主多轮迭代**（agent 先做多轮内循环，再回到截图比对/diff，直到相似度提升）。它泛泛提到 harness 可以接入浏览器迭代、telemetry、profiling，乃至工单、文档等完整 SDLC 工作，但**没有给出任何基于时间、事件或状态触发的具体调度做法**，不宜据此写进手册的这一节。
- **效果验证**：这是全文最有依据的一环——确定性（同种子/同命令回放 → 同状态）保证起点可复现；`odiff` 给出“85% 相似”这类**定量基线**，可作为每个 agent turn 的稳定评估值；作者还提出把“任何改动都做到最小必要变更”作为可被近乎隔离评估的目标，以避免积累 spaghetti 式技术债。

## 怎么试、怎么验证（最小试用方式和判断有没有改善的指标）

**最小试用（建议 1–2 天，在一个新模块或新小项目上，而不是既有大项目）**

1. 先只做两件事，不做全面重构：
   - 引入单一带种子的随机源 + 一个最小可用的“保存/加载指定状态”路径；
   - 给产出物接一个截图入口，并能开关不同图层。
2. 装一个命令行图像 diff 工具（原文推荐 `odiff`，具体用法需自行查其文档），把“目标图 / 上一版图”和“当前图”做 diff，把 diff 图和相似度数值一起喂给 agent，要求它每轮报告该数值并朝着提升它迭代。
3. 选一个**有明确目标图**的任务（UI 样式微调、布局对齐、某个视觉效果的逼近），让 agent 独立跑多轮，人只在数值停滞或震荡时介入。
4. 若试得顺利，再加第三条：把该模块的数值型参数挪到外部数据文件（先用 CSV/JSON 即可，不必上 Depot 这类工具），验证 agent 能否不改代码、不重编译就完成一次调参迭代。

**判断有没有改善的指标**

- **可复现率**：同一份种子 / 同一串命令回放，能否 100% 复现同一状态（这是硬门槛，不达标则后面一切指标不可信）。
- **达成目视效果所需的人工介入次数与 agent 轮数**：与“不给 diff 数值、只丢截图”的对照跑法相比是否下降。
- **相似度数值的走势**：是否单调改善；若长期震荡不收敛，说明该任务无法被这个指标衡量，应停止使用而不是硬调。
- **回归量**：agent 每轮改动是否“最小必要”，是否引入无关区域的差异（diff 图里未请求区域的变化量就是直接证据）。
- **调参类任务的循环时间**：改一个数值到看到结果，是否需要重编译、耗时是否下降。

**停止条件**：若任务没有可对照的目标图、或者相似度数值与主观质量明显不一致，就不要把 diff 数值当验收标准，退回人工判断。
