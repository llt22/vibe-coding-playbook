## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

前提：你需要先能说清系统的关键程度，且能召集干系人（产品、业务、合规）一起谈目标。以下步骤按原文可照做的部分整理。

1. **定义 RPO 与 RTO，按工作负载分别定。**
   - RPO（恢复点目标）= 数据最后一次备份/同步之后可容忍经过的最长时间，也就是可容忍的数据丢失时长；每小时备份一次，RPO 就是一小时。
   - RTO（恢复时间目标）= 事故后系统可容忍不可用的时长，包含从最近恢复点恢复数据、备好计算资源、把流量切到新站点所需的全部时间。
   - 与干系人讨论终端用户需求、监管与法律要求，再和实现成本、复杂度做平衡。原文例子：银行支付需要低 RPO/RTO，新客开户可以放宽。目标应高于任何 SLA 中规定的要求。
   - 前提：不同服务的 RPO/RTO 可以不同，允许混合使用多种 DR 模式。
2. **从低到高选择 DR 模式，不确定就从左侧开始逐级演进。**
   - **备份与恢复（Backup and Restore）**
     1. 定期备份数据，备份必须存放在主站点以外的地方。
     2. 在故障站点 provision 基础设施；理想情况是自动化，手工 provisioning 会拉长 RTO 并增加出错概率。
     3. 从备份把数据恢复到故障站点新建的基础设施。
     4. 把流量从主站点切到故障站点。
     - 前提：能接受较长 RTO、想压低成本；故障站点最好跑同一套核心技术栈，这样主站点的 IaC（例如 Terraform 脚本）可以复用，切换成功率更高；若两站技术栈不同，则更必须定期测试 DR 流程。
   - **Pilot Light 故障切换**
     1. 数据提交到主站点后持续复制到故障站点（可用数据库原生能力，也可应用层复制）。
     2. 在故障站点 provision 剩余基础设施；假设数据库和数据存储已在故障站点存在，只需 provision 计算等资源。
     3. 流量切换到故障站点。
     - 前提：数据存储支持或能实现持续复制；改造既有系统时，如果所用数据产品不支持原生复制，复杂度会明显上升。适合公有云场景，因为不 provision 就不付费。
   - **Warm Failover**（原文标注 how it works / when to use 在节选中被截断）
     - 数据持续复制到故障站点，并且在真正切换之前就预先 provision 至少一部分基础设施。
     - 常见做法：在故障站点优先为最关键的子系统准备容量，使核心功能有更短 RTO。
     - 原文提示：各家厂商对 cold/warm/hot 的定义差异很大，通常只是 RTO 依次降低，不必纠结命名。
   - **Multisite Active-Active**（how it works / when to use 同样被截断）
     - 系统分布在两个或更多站点，写入可发到任意站点，数据在站点间持续复制，任意用户的流量可随时由任意站点服务。
     - 它绕开了“故障切换”这个动作，RTO/RPO 在四种模式中最低，但成本和复杂度显著更高。
3. **在规划里纳入“故障时基础设施未必能买到”的现实。**
   - 向供应商预留容量：例如 AWS 上可付费预留 EC2 实例的可用性，预留费不论是否使用都要付（用的时候单价低于按需价格）；注意并非所有云资源都能预留，例如 Lambda 调用量无法购买保证可用性。
   - 按关键性分配稀缺容量：如果保证可用性有成本、或基础设施总量有限，应优先给关键性更高的工作负载。这就是分服务设置不同 RTO/RPO 的实际用途。
   - 全冗余自建：如果复杂度与费用可接受，保持一整套冗余基础设施随时可用；缓解成本的办法是平时把冗余资源拿去做别的用途。原文案例：BankCo 把闲置备用工作站同时用作计算资源池，DR 站点启用时中止计算任务。也可把备用基础设施用作负载测试环境，DR 需要时随时中止。
4. **定期验证 DR 流程本身。**
   - 备份恢复流程必须定期测试，不能只写在文档里。
   - 原文推荐做法：把“向二级站点做一次备份—恢复”并入其他例行活动，例如常规负载测试演练。
   - RPO 由备份频率决定；RTO 取决于恢复数据、provision 资源、切换流量三段中最慢的一段。全自动 + 小数据量可到分钟到小时级；手工流程、TB 级备份会显著拉长；如果还要临时采购硬件，可能拖到数周以上。
5. **给 AI 功能做降级和备援。**
   - 模型不可用、被限流、token 额度耗尽时，限制功能而不是整体挂掉，即 graceful degradation。
   - 为同一模型准备备用供应商通道：例如通过 Azure 访问 OpenAI 模型，通过 Google 的 Gemini Enterprise Agent Platform 访问 Anthropic 模型。前提：接受备用通道上新模型上线可能有滞后；原文认为软件中嵌入的模型不必总用最前沿版本，这个滞后通常可接受。
6. **用功能测试 + eval 兜住模型行为变化。**
   - 维护一套针对 AI 部分行为的测试，由传统功能测试和 AI 评估工具（evals）两部分组成。
   - 前提认知：LLM 本身不确定，模型小改动也可能带来很大行为差异；原文提到有模型在供应商未明确提示重大变更的情况下行为改变的报告；升级模型版本可能从根本上改变 prompt 的处理结果。目标是“意外先发生在你这里，而不是用户那里”。
   - 原文推荐延伸阅读：Gayathri Mohan《Full Stack Testing》第 2 版（测试通论与 AI 系统验证）、Shreya Shankar 与 Hamel Husain《Evals for AI Engineers》（深入 eval）。
7. **给模型调用补可观测性和超时策略。**
   - 难点：发给模型或 agent 后延迟波动大，原因可能来自供应商当时性能、被限流、或 prompt 本身处理时间长；如果 prompt 直接来自用户，更难判断“是卡住了还是要生成很长输出”。
   - 原文给出的技术手段：按生成 token 数动态设置超时；监控流式输出，追踪响应何时开始返回，而不是等完整响应。
8. **多模型、多供应商地构建。**
   - 让软件支持替换模型，以便跟进最新模型、也便于在某个供应商涨价时快速换。
   - 注意反例：在单个流程里混用多家模型会放大问题——Anthropic、OpenAI、Gemini 任一不可用，整个流程就无法执行；换模型时 prompt 必须重新评估，即使同厂内换版本也一样。
   - 供应商层面同理：如果你的供应商自身只依赖某一家模型/API，你也会暴露在该模型的波动或突然涨价之下。原文案例：Cursor 在 2025 年因依赖 Anthropic 服务、而 Anthropic 调整定价，被迫向客户转嫁大幅涨价。
9. **成本透明与供应商定期分析。**

## 怎么试、怎么验证

**最小试用方式**

1. AI 韧性试点（1–2 周可动）：选一个最依赖模型的 AI 功能，先加一层模型调用抽象，接入一条备用供应商通道（如经 Azure 调 OpenAI），并给调用加上按 token 数动态计算超时 + 流式首字节监控；如果模型不可用，走降级路径而不是报错。
2. eval 回归试点：为这个功能整理一小组真实输入，配传统功能测试 + 一份 eval 用例，作为“模型变更后必须跑”的回归清单。
3. DR 试点（一次演练）：选一个非关键服务，按备份与恢复的 4 步走一遍——异地备份、自动化 provision、恢复数据、切换流量——全程计时并记录卡点。用同样的自动化脚本复用到故障站点，可以更接近原书说的“同一技术栈复用 IaC”。

**判断有没有改善的指标**

- DR 侧：实测 RTO（从故障宣告到流量切回的时间）是否达到事先和干系人谈定的目标；RPO 是否等于备份频率；演练中自动化步骤占比与人工介入次数；切换后功能是否完整。
- AI 侧：eval 通过率与回归失败次数；供应商故障或限流时降级路径的触发成功率；超时错误率与 P99 延迟变化；模型替换后需要重写/重调的 prompt 数量；因模型供应商问题导致用户可见故障的次数。
- 成本/供应商侧：模型调用成本变化是否可被观测；从发现某供应商涨价到完成切换所需的工时（衡量“换供应商的门槛”是否真的降低）。
