## 是什么

`visual-review-page` 是一个给 Claude Code 和 Codex 用的免费 skill（单文件夹形态，MIT 许可）。它改变智能体"交计划"的方式：不再在聊天里丢一大堵嵌套列表并以"第 1–3 项你怎么定？"结尾，而是在你的项目目录里生成一个本地可视化页面，把"改什么、为什么、怎么运作"展示出来，并在**每个条目下面**留一个回答框；你直接在页面上批注，智能体读取后再改版，并在每条回答上方标注改了什么或为什么没改。

README 给出的五条页面原则（配前后对比截图）：

1. 说人话：不写"webhook 和 grace period"，而写"现在怎么运作 / 之后怎么运作 + 一个真实例子"。
2. 能展示就不描述：画面帧、截图、方案并排，区域直接在真实画面上用绿/红标注。
3. 放一处：图、说明、问题并排，而不是"文件 1 这样、文件 2 那样"。
4. 短而清：要点三行，细节按需索取。
5. 每个提案都有批注位：不是末尾一句"这些我们同意哪些？"，而是每项各自的回答框。

仓库内含三个文件：`SKILL.md`（给智能体的指令：展示什么、决策如何措辞、页面形态、回答轮次）、`assets/page.html`（页面模板：单阅读栏、回答框、自动保存）、`scripts/serve.py`（本地服务器：发页面与媒体、支持拖动播放、存回答）。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

**前提**：Claude Code 和/或 Codex；Python 3.7 或更新（服务器只用标准库）；一个浏览器，最好是 Claude/Codex 桌面应用的内置浏览器，因为智能体可在给你看之前自查页面；Windows 需在 WSL 里执行下述命令。

1. 取回仓库：

```bash
git clone https://github.com/pavel-molyanov/visual-review-page.git
```

2. 安装到 Claude Code（全局）：

```bash
mkdir -p ~/.claude/skills && cp -R visual-review-page/visual-review-page ~/.claude/skills/
```

3. 安装到 Codex（全局；Codex 也读旧的 `~/.codex/skills/`）：

```bash
mkdir -p ~/.agents/skills && cp -R visual-review-page/visual-review-page ~/.agents/skills/
```

只想在单个项目里用：把内层 `visual-review-page/`（含 `SKILL.md` 的那层）拷进该项目的 `.claude/skills/` 或 `.agents/skills/`。用 ZIP 下载的，解包后同样拷内层文件夹。**装完重启智能体会话。** skill 与你自己装的 skill 并列，只有你要求"可视化展示计划"时才启用。

4. 更新（先删再拷，避免旧版本残留文件）：

```bash
git -C visual-review-page pull
rm -rf ~/.claude/skills/visual-review-page && cp -R visual-review-page/visual-review-page ~/.claude/skills/
```

（Codex 用户把第二行的 `~/.claude/skills` 换成 `~/.agents/skills`。）

5. 触发。智能体带着计划来时，对它说（原文给的提示词）：

```text
show it visually
```

```text
pack it into a page
```

```text
present the solution
```

普通问题和短计划仍走聊天。

6. 智能体在项目某个文件夹里生成页面，起一个小本地服务器，并用内置浏览器打开；若智能体没有浏览器，自己打开它打印的 `http://127.0.0.1:<port>/`。

7. 在各条目下的回答框里写答复，边打字边保存。**空框表示"未回答"，绝不等于"同意"。**

8. 回到聊天，用任意说法告诉智能体"我答完了"。它读回答、改页面，并在每条回答上方显示改了什么或为什么没改。已同意的条目折叠，回答框清空进入下一轮；上一轮的回答保留为 `answers-<round>.json`。

9. 工作**只在你明确下令后才开始**。页面上的回答只表示同意或修改条目，永远不触发起工。

## 怎么试、怎么验证

**最小试用（半天内可完成）**

1. 按上节步骤 1–3 装好并重启会话，确认 `/skills` 或等价入口里能看到它。
2. 选**一个真实的中等规模计划任务**（例如一次包含 3–5 个决策点的改动方案），先照常用聊天方式让智能体给计划，记下这次的表现作为基线。
3. 换一个同类任务，用 `pack it into a page` 触发页面，逐项在回答框里批注，其中**故意留一个空框**，验证空框确实不被当成同意。
4. 回聊天说"答完了"，检查三件事：它是否读到全部回答；每个答复上方是否标了"改了什么/为什么没改"；已同意项是否折叠、框是否清空、`answers-<round>.json` 是否生成。
5. 只在你确认后再显式下开工指令，观察它是否在你下令前不动手。

**判断有没有改善的指标（建议自定，原文未提供）**

- 往返轮数：从"智能体首次给计划"到"人可以开工"之间的消息轮数，与基线对比。
- 澄清成本：同一任务中聊天里追问/重述的条数。
- 误改率：最终交付中因理解偏差需要返工的决策点数。
- 遗漏率：你实际有意见但未被处理的条目数（页面模式下应接近 0，因为每项都有框）。
- 作答完成度：已回答框 / 总条目数，以及"空框被误判为同意"的次数（应恒为 0）。
- 起工纪律：在你未显式下令前智能体擅自开工的次数（应为 0）。

若 3–5 次试用后往返轮数与返工率没有下降，或页面生成质量不稳定（经常退回文字墙），把 verdict 下调为 study。
