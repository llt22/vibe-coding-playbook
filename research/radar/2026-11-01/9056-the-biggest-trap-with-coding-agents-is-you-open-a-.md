1. 前提：工作在 git 仓库中进行，当天有若干次智能体会话；智能体有执行 shell 命令的权限（Claude Code / Codex 的默认终端能力即可）。
2. **（原文主张）** 每天结束工作、关闭会话之前，不要用「今天开了几个会话、干了多久」来判断进度，改为让智能体检查 git 历史。
3. **（原文缺失，以下为我方复原，非原文）** 向 Claude Code / Codex 提交类似如下的收尾检查指令：

```
请检查本仓库今天（本地时区当日 00:00 之后）的真实产出，只依据 git 证据，不要依据我们的对话内容：
1. 运行 git log --since="today 00:00" --oneline --author-date-order
2. 运行 git diff --stat 以及 git status --short（含未提交改动）
3. 输出表格：每个提交/改动块 → 对应解决了什么任务 → 涉及文件 → 是否为可用状态（能编译/能跑/有测试）

5. 最后给一句话结论：今天的实际净产出是什么；如果没有可交付产出，直说没有
```

4. 对照自己当天的任务清单，逐条判定「有 git 证据 / 只有会话记录 / 什么都没有」，把第三类记为无效会话。
5. 前提与风险：不要把未提交的改动直接提交；先看 `git status`，确认没有把无关文件（密钥、临时文件）纳入；检查结论仍需人复核，智能体对自己产出的自评容易偏高。

## 证据与局限

- 证据强度很弱：原文只有作者的经验性断言（「最大的陷阱是假忙碌」），**没有给出任何数据、案例、前后对比或失败样本**；采集到的正文也在关键处被截断，那句提示词的原文无从核对。
- 互动量低（76 赞、0 转发、19 回复），不足以作为可信度背书。
- 适用条件：任务产出必须可落到 git 可追踪的文件改动上；对探索性工作、重构中途、设计讨论等「当期无提交但仍有价值」的工作，该方法会误判为无效，需要人工区分。
- 反向风险：可能诱导智能体为了「有 git 证据」而产生碎提交或凑数改动，因此指标应看改动质量而非提交数量。

## 怎么试、怎么验证

**最小试用**：在一周的编码工作中，保留原有工作方式不变，仅在每天结束时加入第 3 步的 git 审计（用上面复原的提示词，或改写为自己的版本），把结果记入一张两列表：当天开启的会话/任务 vs 有 git 证据支撑的任务。

**判断改善的指标**（建议连续记录 5 个工作日再判断）：

1. 有产出会话占比 = 有 git 证据支撑的任务数 ÷ 当天开启的会话数，观察是否上升。
2. 次日返工率：第二天需要回头修补前一天「声称完成」的改动的次数，观察是否下降。
3. 当日结论与人工复核的一致率：智能体自评「完成」而人工复核认为未完成的比例（衡量该方法本身是否可信）。
4. 无效会话的识别速度：从「靠回忆复盘」到「靠 git 一分钟出结论」，收尾耗时是否缩短。

若第 1、2 项无变化，或第 3 项一致率明显偏低（例如低于一半的结论需要人工推翻），说明该做法在此工作流中收益有限，不必纳入日常流程。
