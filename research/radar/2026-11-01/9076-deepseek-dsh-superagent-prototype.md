## 怎么试、怎么验证（最小试用方式和判断有没有改善的指标）

**前置动作**：先拿到仓库 README 与部署文档；若拿不到，本线索只停留在研读层面。

**最小试用方式**：
1. 选一个**非关键、低风险的单个仓库**（测试仓或文档仓），不要用主业务仓。
2. 只接入 GitHub 侧事件，先不接飞书，减少权限面。
3. 第一阶段**只让它产出任务建议、不提交 PR**，人工看它“自主立项”的质量。
4. 第二阶段放开建分支和提 PR，但**全部 PR 走人工 review，禁止自动合并**；人工介入面板保持开启。
5. 跑满 2–4 周后与“人类自己提的 PR”做同仓对比。

**判断是否改善的指标**（均为建议指标，原文未给）：
- 它提交的 PR 中被人**接受或合并的比例**；
- 每个 PR 平均需要人工修改的时间或行数；
- **无效 PR / 重复任务**的数量（衡量“主动”带来的噪音成本）；
- 从事件发生到 PR 提交的**时延**；
- 人类在面板上的**介入次数**——这直接对应它自己的理念“少占用人类精力”。

**判定门槛**：只有当“被接受的 PR 带来的人工成本 < 人自己动手的成本”，且无效 PR 数量可控时，才算改善；否则宁可退回“人派任务 + agent 执行”的旧模式。
