## 怎么试、怎么验证（最小试用方式和判断有没有改善的指标）

**最小试用（一周内可完成，只借用顺序原则，不假装复现 pstack）**

1. 选一个你熟悉、能在本地跑起来的中小仓库。
2. 先只做一件事：把“怎样算改对了”写成 agent 可执行的一步命令（启动 + 关键路径检查），并让它跑通一次。
3. 再写一页 feature map（模块、入口、关键文件、常见改动落点）。
4. 让 agent 独立完成 3 个同类型小任务，全程只允许它用第 2 步的验证手段自证，人只在最后验收。
5. 对比：同样 3 个任务，在**没有**验证 skill 与 feature map 时的表现（用历史任务或另开一次对照）。
6. 只有在第 4 步通过率稳定后，才尝试同时开 2 个 agent；自动合并放到最后，并保留人工合并作为对照。

**判断有没有改善的指标**

- agent 自行验证通过的比例（一次通过 / 需人介入次数）
- 人工介入次数与介入原因分布（是“它不知道改哪里”还是“它不知道对不对”）——分别对应 feature map 与验证 skill 的缺口
- 从下达任务到验证通过的时间
- 返工率与误报率（验证通过但实际坏了的比例，说明验证 skill 本身是否可信）
- 开启并行后：冲突率、合并失败率、需要人工判断的次数是否随并行数上升而恶化

若第 2 步的验证手段本身不可靠（误报率高），则原文的整个顺序前提不成立，应先修验证而不是加并行。
