## 怎么试、怎么验证

**最小试用方式**

1. 选一个中小型、有可运行测试的仓库，固定一个快照。
2. 只切 2–3 个低耦合类别（例如“缺失的错误处理”+“死代码”），起 2–3 个沙箱，不要一上来 100 个。
3. 同时跑一条**串行基线**：用单个 Claude Code 会话做同样这几类，作为对照。
4. 人工逐条复核每个实例的产出，记录哪些是真问题、哪些是误报、补丁是否能合入。

**判断有没有改善的指标**

- 每类**有效发现数**与**误报率**（人工复核后统计）——这是最关键的，耗时再短也抵不过误报。
- 补丁合入率，以及合入后测试通过率 / 是否引入新的失败用例（回归）。
- 是否越界：实例有没有去改不属于自己类别的东西，导致与其他实例冲突。
- 人工总投入（复核 + 合并 + 冲突处理）与单 agent 串行基线的差值；如果并行省下的时间被复核冲突吃回去，就不值得。
- 端到端成本：墙钟时间、token 消耗、沙箱并发费用，分别与基线对比。

**判据建议**：只有在“误报率可接受 + 人工复核总时间显著低于串行基线 + 无回归”同时成立时，才把这条流程从研读升级为可写入手册的 try；仅凭原文的启动耗时和批次耗时不足以支撑这一判断。
