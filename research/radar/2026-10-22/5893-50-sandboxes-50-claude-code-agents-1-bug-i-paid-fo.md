## 是什么

一条推文（@fluixoo，35 赞）描述的做法是：准备一个带有目标 bug 的沙箱环境，把它快照（snapshot）；再从该快照分叉出 50 个带独立内存和运行中进程的副本，每个副本交给一个 Claude Code 代理并行修复同一个 bug；只有胜出者的修复被合入，其余 49 个全程停在零成本状态（“sat on pause at $0”）。作者的卖点是“只为一个代理付费”。

本质上这是“并行探索 + 单点合并”的代理编排模式：用同一份已复现的环境状态作为起点，换取多条独立解题路径的多样性，再用某种裁决方式收敛到一条。

## 怎么试、怎么验证

**最小试用（把 50 缩小到 3–5，先验证机制而不是规模）：**

1. 选一个已能稳定复现、且有一条自动化测试可以判定成败的 bug。这是前置条件，不满足就不要开始。
2. 在沙箱中复现后打快照，分叉 3 个副本，各挂一个 Claude Code 代理，给完全相同或明确标注差异的提示词（提示词差异本身可作为变量记录）。
3. 预先写死裁决规则：以测试通过为唯一胜出标准；多个通过时按预设规则（如改动行数最少）取一。
4. 记录每个分支的耗时、token 与费用、是否通过测试、改动范围。
5. 只合并胜者，其余分支暂停或销毁，核对账单是否确实只为胜者计费。

**判断有没有改善的指标：**

- 与“单代理跑 3 次”的对照组比较：首次成功率（任一分支通过测试的比例）。
- 从开始到测试变绿的实际耗时（并行是否真的更快，而不是被分叉开销抵消）。
- 单位成功修复的总成本（含所有分叉的环境成本，而非只算代理费用）——“只付一个”若被环境开销吃掉，这个模式就不成立。
- 分支间解法差异度：如果 3 个分支给出几乎相同的补丁，说明并行没有带来多样性，应停止放大并行度。

只有在上面几项都不劣于单代理基线、且成本可控时，才值得把这个模式写进手册并放大并行度。
