## 是什么

Trail of Bits 发布两个 Codex 插件，把“修 bug”和“查这次改动还弄坏了什么”拆成两条标准化流水线：

- **patching-bugs**：复现已报告的 bug → 开发修复 → 测试修复。核心是“三步证明”和“不变量引导修复”。
- **regression-hunt**：检查改动是否破坏了原本正常且被支持的行为。核心是强定义“什么是回归/什么不是回归”，以及每条结论必须有 live PoC。

两者来自 Trail of Bits 与 OpenAI 的 Patch the Planet 计划（已为多个广泛使用的开源项目合入数百个安全补丁）。插件本身是 Codex 的技能/工作流封装，原文只给出“Install patching-bugs and regression-hunt”的入口链接，**未给出可复制的安装命令或 schema 原文**；但工作流、判定门槛和所需项目文件是可以在任意 agent 环境里照做的。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

**前提**：仓库能被真实构建并运行（有可访问的真实用户接口），有可复现的 bug 报告或一个待审查的 PR diff；使用 Codex 或等价的可编排 agent 环境；有人负责指方向和最终 review。

1. **准备 live deployment**。把项目构建成可运行实例，并通过真实用户会用的接口访问。原文明确：复现 bug、证明修复、确认回归时，如果某一步产不出 live PoC，该步结果记为 **inconclusive**。

2. **写 `THREAT_MODEL.md`**。原文说它告诉 agent 什么算漏洞、什么算回归，regression-hunt 会把该文件作为全局上下文传给每一个 agent 步骤，强制每步对照它下结论。原文要求覆盖以下要素（下面是据原文要素整理的模板骨架，不是原文逐字给出）：

```markdown
# THREAT_MODEL
## 关键资产（被攻破会造成实际损失的资产）
## 信任边界
## 访问控制
## 受支持的配置（supported configurations）
## 什么算 / 不算漏洞
## 一个有效 bug 报告必须提供的证据
```

3. **写 `PATCHING_GUIDELINES.md`（或 `AGENTS.md`）**。告诉 agent 和 patching-bugs“本项目希望补丁怎么写”。原文要求覆盖：

```markdown
# PATCHING_GUIDELINES
## 如何构建与测试本项目
## 补丁的规模上限（一次改动应该多大）
## 补丁应该落在哪个位置
## 如何呈现拟议改动
## 回归测试必须证明什么
```

原文强调：这两个文件越贴合项目、代码约定和运维风格，输出越好；patching-bugs 会读取项目自己的打补丁规范。

4. **安装并启用两个插件**（原文只给链接，无命令原文，不要臆造命令行）。若暂不装插件，可把下面第 5–8 步作为 agent 提示词/流程手工执行。

5. **用 patching-bugs 处理一个 bug 报告**，按原文三条要求执行：
   - **三步证明**：同一份复现脚本跑三次——原始代码必须失败；打上补丁后必须通过；完整回退补丁后必须再次失败。第三步是关键，用来排除“其实是环境或测试改动让它通过的”。
   - **不变量引导修复**：修被违反的底层安全不变量，而不是修这一个具体症状，以便覆盖同类 bug 的变体。
   - **强制回归分析**：任何补丁都必须走一遍 regression-hunt，不允许跳过。

6. **用 regression-hunt 检查改动**，四步固定流程：
   1) **枚举候选回归**：沿着 diff 改动点追踪其调用者，一直追到真实接口。
   2) **在 live deployment 上复现每个候选**。
   3) **用全新上下文的 agent 重放同一 PoC**（避免原 agent 的上下文偏见）。
   4) **裁决 agent 判定**：所有前序步骤的结果汇总，由裁决步判断证据是否满足“回归”的定义。

7. **设置裁决门槛（举证责任在 agent）**。只有全部通过才报回归；裁决时必须排除：假阳性、不完整修复、潜伏 bug、改动前就存在的既有 bug 等。原文的定义：回归是“改动引入的新缺陷，破坏了原本正确且被支持的行为，且位于真实用户或攻击者可达的路径上”。

8. **每一步使用固定输入/输出 schema**，至少包含：

```text
claim（断言）
code revision（代码版本）
required check（要求的检查项）
raw evidence（原始证据，非摘要）
open questions（未决问题）
```

目的是让每一步去验证上一步的原始证据，而不是相信上一步的总结。

9. **模块化使用**。两个插件不必端到端跑，各步骤的技能可以单用或串联；只想做回归检查时，把第 6–8 步单独拿来跑一个 PR diff 即可。

10. **（可选）基线对照提示词**。原文用这个作为对比基线，可以原样拿来测自己的流程是否真的更好：

```text
review the PR for regressions
```

## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）

- **能力发现**：原文把两类常被忽略的活交给 agent——一是沿 diff 追踪到调用者与真实接口、枚举出“这次改动可能弄坏了什么”；二是修底层被违反的不变量而非单点症状。原文还做了“审阅全部已合入补丁”这件通常没人系统做的事（130+ PR 全覆盖复核）。
- **任务匹配**：Codex agent + 插件式技能编排；多角色分工——复现 agent、全新上下文的重放 agent、裁决 agent，人负责指方向、提供安全假设和最终 review。适合“有明确 bug 报告、项目可构建运行、有威胁模型”的场景；不适合没有 live 环境的项目。
- **条件供给**：`THREAT_MODEL.md`（关键资产、信任边界、访问控制、受支持配置、漏洞判定、报告所需证据）、`PATCHING_GUIDELINES.md`/`AGENTS.md`（构建测试方式、补丁规模与位置、变更呈现、回归测试要求）、live deployment、固定 I/O schema、明确的“回归”定义与裁决门槛，以及把 threat model 注入每一步的全局上下文机制。
- **主动推进**：原文流程由 bug 报告 / PR 改动触发，串成“复现→修复→回归检查”的固定流水线，并规定补丁必须强制走回归检查；原文还提到下一步要让维护者可选“最小化补丁集”或“放宽 regression-hunt 规则以暴露更多候选”。关于时间/状态触发的持续运行，原文没有展开，依据有限。
- **效果验证**：live PoC 是唯一的结论依据（产不出即 inconclusive）；三步证明排除伪通过；裁决门槛排除各类假阳性；并用“同一份 PoC 在全新上下文 agent 里重放”做独立复核。数据侧用 21 个已确认回归作为评测集，与基线提示词对比假阳性率。

## 证据与局限

**原文给出的数据/案例**：
- 复核了全部由 Trail of Bits 工程师编写、被上游合入的补丁：130+ 个 PR 中确认 **21 个回归**（16 个功能性、1 个性能、4 个构建/测试），**没有一个是破坏安全防护的**。
- 单次运行中，58 个候选里确认 21 个，约 **36% 精确率**，作者自评“review was noisy”。
- regression-hunt 相比“review the PR for regressions”基线 Codex agent，**假阳性少 25%**，95% 置信区间 14%–38%。
- 案例点名：Scapy、GPAC（工程师为其写了威胁模型和项目专属打补丁技能）、liboqs、validator.js（按此指南发布了威胁模型）。

**属于作者主张、无数据支撑的部分**：四原则（极简指导、模块化步骤、严格 schema、每条断言都要 live PoC）的有效性；“不变量引导修复能泛化到同类变体”；“文件越具体输出越好”。

**局限**：
- 原文未给出安装命令、schema 定义、插件源码位置，无法逐字复制落地。
- **patching-bugs 尚未做评测**——原文明确说“we're building an evaluation”，只有 regression-hunt 有对比数据。
- 假阳性下降是有代价的：严格证据要求使部分已知回归被判为 borderline（识别到可能有问题但证据不足以确认），即**召回下降**。原文自认这是 tradeoff，尚在改进。
- 数据来自单一组织（Trail of Bits）的自评，样本是 21 个回归、130+ PR，规模有限；36% 精确率意味着人工仍需筛掉约三分之二的候选。
- 强依赖可构建的 live deployment 与真实接口；对无法本地运行或接口不可达的项目不适用。
- 深度绑定 Codex 生态，其他 agent 需自行复刻流程。

## 怎么试、怎么验证

**最小试用**（1–2 天，不必装插件）：

1. 选一个可构建运行的中等规模仓库，取 5–10 个**已合入的历史 bug 修复 PR**；其中至少 2–3 个是已知引入过回归的（没有已知回归的也要标出来，用于测假阳性）。
2. 只为其中 1 个仓库写最小版 `THREAT_MODEL.md` + `PATCHING_GUIDELINES.md`（按上面骨架，各 1 页以内）。
3. 对每个 PR：agent 按第 6 步四段流程跑（枚举→live 复现→fresh-context 重放→裁决），全部记录原始证据；再用基线提示词 `review the PR for regressions` 跑同一批 PR。
4. 人工对每条“确认回归”和“borderline”判定真伪，与已知历史结论对照。
5. 另取 1 个真实 bug 报告跑 patching-bugs 流程，重点验证第三步（回退后必须再次失败）能否被稳定执行。

**判断有没有改善的指标**：

- **假阳性率**：每条被报出的回归里，人工判为真的比例；与基线提示词对比，看是否复现原文 ~25% 的下降量级。
- **borderline 比例**：被判“有嫌疑但证据不足”的数量——这是该流程的主要代价，必须单独统计，不能算作成功。
- **已知回归的召回**：那 2–3 个已知回归是否至少被判为 borderline（不接受静默漏过）。
- **证据完备率**：报出的每条回归中，带 live PoC 且三步证明齐全的比例（原文要求 100%）。
- **人工筛检成本**：每个 PR 平均需要人工处理多少条候选（原文是 58 → 21）。
- **可重复性**：同一 PR 重跑两次，结论是否一致（原文的固定 schema 声称能降低跑间波动，可实测）。

**继续 / 停止的判据**：若在 5–10 个 PR 上假阳性率明显低于基线、已知回归无一静默漏过、且人工筛检量可接受，则纳入手册作为“改动副作用审查”的标准步骤；若 borderline 比例过高或 live deployment 成本压不住，则退回 study，只保留“三步证明”“强制 live PoC”“威胁模型全局注入”这三条可迁移原则。
