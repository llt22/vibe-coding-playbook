# Using LLM for confidence scoring is a bad idea

- 结论：**值得一试**。不要采用 LLM 自报置信度来做校验或分流；改用可观测信号、历史正确率和定期校准的规则，并先在有人工复核的窄流程中小范围验证。原文给出了可操作的记录与校准步骤，但证据以论证和示例为主，尚不足以直接全面采用。

## 是什么

原文的核心主张是：不要让 LLM 自报置信度（confidence score），因为这个数字只是模型逐 token 生成出来的文本延续，不是对内部状态的测量，也没有针对“它是否答对”做过校准。

作者提出，可信的置信度需要两个条件：

1. 反映预测所依据的信息量；
2. 在同类问题上与实际结果核对过。

替代方案是像天气预报员一样，用可观测信息建立一条“信息到置信度”的规则，持续记录结果并按实际正确率校准。LLM 仍可负责写回答、做摘要等任务，但置信度来自规则，不来自 LLM 的自我报告。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

1. **选择可观测信息。** 前提：任务是重复出现的同类问题，且每个回答可以事后判定对错。列出不询问 LLM“感觉”就能观察到的信号，例如：检索是否命中相关文章、命中几篇、此类问题以前是否处理过、同一问题问两次两个回答是否一致。原文把这些比作天气预报里的气压、湿度和风。
2. **用历史基率作为初始置信度。** 前提：有一批复核过的历史回答。原文举例：若检查 200 条历史回复、其中 150 条正确，则新回复的初始置信度都设为 75%。这是冷启动值，不是最终值。
3. **为每条回复留档。** 前提：有复核结果或客户不再追问等结果信号，并能记录。每条保存：第 1 步的可观测信息、规则给出的置信度、最终是否正确（例如复核通过，或客户没有再次追问）。
4. **用记录更新规则。** 前提：累计足够样本，能按信号分组。把历史回复按可观测信息分组，计算每组实际正确率。原文举例：有匹配文章且两次回答一致的组历史正确率为 95%，该组下次置信度就用 95%；无匹配文章的组仅 40%，就用 40%。样本少时分组粗，数据增加后再细化。
5. **定期校准并修正。** 前提：能按周或固定周期汇总结果。按置信度档位做表：说 90% 的组实际正确率是多少。若 90% 档实际只有 70% 正确，说明规则过度自信，用新记录调整。原文中的 90%/70% 是说明性例子。
6. **把规则用于分流。** 前提：有人工复核通道和可接受的延迟。LLM 仍负责生成回答；置信度来自上述规则；低置信度回复在发送前交给人。原文没有给出具体阈值，阈值需按自身复核能力设定。

## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）

- **能力发现：** 原文没有提出新的 AI 能力，也没有给出“还有哪些工作可交给 AI”的正面清单；它主要提醒不要把“让 LLM 自评置信度”新增为可用能力。
- **任务匹配：** 有直接依据。生成任务可继续交给 LLM，但置信度评估和低置信度分流不适合交给 LLM 自报，更适合交给可观测规则和人工复核。
- **条件供给：** 有直接依据。需要提供可观测信号、历史复核记录、每条结果是否正确、定期汇总和更新规则的流程；没有这些记录，规则无法校准。
- **主动推进：** 只有有限依据。原文提出“每周左右”检查校准表，但没有展开事件触发、状态触发或持续自动推进的机制。
- **效果验证：** 核心依据。用历史记录和校准表检查“说 90% 的到底有多少正确”，而不是相信单个置信度数字。原文还强调，校准本身不够：一个永远输出历史基率的规则也可能校准，但没有利用新信息；好的规则应随信息变化而给出更有区分度的置信度。

## 证据与局限（原文给了哪些数据或案例，哪些只是作者主张，适用条件是什么）

- 原文用天气预报员和一张校准表说明“置信度要与实际频率匹配”，但这是解释性示例，不是真实实验数据。
- 原文用客户支持回复分流作为案例，给出 6 步式流程，但没有代码、配置文件或完整系统实现。
- “同一问题再问一次数字会变”“换个措辞数字会变”“数字前面的文本决定数字”是作者提出的可观察后果，原文没有给出实验统计或基准测试。
- 核心论证成立与否取决于：是否有同类问题的历史记录、是否能判定每次输出正确与否、记录是否足够支撑分组。没有人工复核或结果标签时，这套方法无法落地。
- 规则只和记录一样好；如果没人检查回复是否正确，就没有可学习的标签，最终仍是“没人测量过的数字”。
- 校准必须针对同类问题；在一个任务上校准出的规则，不能直接假定适用于另一类任务。
- 校准本身不等于有用：始终输出基率的规则也可能校准，但没有利用信息。需要同时看高置信度与低置信度组的实际正确率是否有明显差异。

## 怎么试、怎么验证（最小试用方式和判断有没有改善的指标）

最小试用方式：

1. 选一个窄而重复、已有真人复核的流程，例如客服回复、工单回复或文档问答。
2. 按原文例子记录可观测信号：是否检索到相关文章、命中数量、同类问题是否处理过、重复生成是否一致。
3. 用已复核历史数据算初始基率；对每条新输出记录规则置信度和最终是否正确。
4. 先做影子模式，不自动发送；把低置信度输出送人工复核，积累记录后再调整分组规则。
5. 按周或固定周期生成校准表，检查每个置信度档位的实际正确率。

判断有没有改善的指标：

- **校准偏差：** 每个置信度档位的“声称正确率”和“实际正确率”差多少；例如 90% 档实际只有 70%，就是过度自信。
- **信息利用程度：** 高置信度组的实际正确率是否明显高于低置信度组；如果所有组都接近同一个基率，说明规则没有利用信息。
- **稳定性：** 相同可观测信息是否得到相同置信度；若是 LLM 自报分数，可额外记录重复提问的波动作为对照。
- **分流效果：** 低置信度被送人工的比例，以及这些被送人工的回复中实际错误的比例；用来判断规则是否真的把不确定项筛出来。
- **记录覆盖度：** 有多少回复留下了可核对的结果标签；没有足够标签，上述指标都不可信。
