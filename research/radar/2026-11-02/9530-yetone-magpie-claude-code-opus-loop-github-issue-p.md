## 是什么

这是一条推文对 yetone 维护 Magpie 项目时所用 AI 运维方法的二手总结。核心是把日常维护拆成三条并行常驻循环（Claude Code 的 `/loop`），每条只负责一类输入：

1. GitHub issue/PR + Discord 讨论；
2. X（Twitter）上的用户反馈；
3. 定时的技术债清理、教训沉淀、低质提交拉黑。

模型侧用 Claude Code + 官方 Opus 作为主力，X 反馈这一路前面加一个便宜模型（原文写作 Jev）先做粗筛省 token。人的位置被明确压缩到“晚上只铲 UI/UX”。

注意：原文是一条推文长度的概述，没有给出具体 prompt、loop 间隔、判断标准等细节，下面步骤中凡原文未写的部分均已标注为“需自行补齐”。

## 具体做法（编号步骤）

前提：有一个自己维护的开源仓库（有 issue/PR 流）、有 Discord 或同类讨论区、有 X 账号接收反馈；已装好 Claude Code 并能使用官方 Opus；另有一个便宜的模型接口用于预筛。

1. **确定分工边界**。把维护工作切成三类互不重叠的输入源：代码协作面（issue/PR/Discord）、舆情面（X）、内部质量面（技术债与规范）。每条 loop 只吃自己那一路，避免三路互相污染上下文。

2. **起第一条 loop：代码协作值守**。用 Claude Code + Opus 起一个 `/loop`，职责是盯 GitHub issue/PR 与 Discord。
   - 关键约束（原文明确强调）：**PR 不能只看 diff 就判，必须拉下来真跑一遍再判断合不合**。即 `git fetch` 该 PR 分支 → 本地跑构建与测试 → 依据实际结果给结论或评论。
   - 间隔与具体 prompt 原文未给，需自行设定（建议先用较长间隔，人工检查几轮输出后再收紧）。

3. **起第二条 loop：X 反馈筛选**。职责是盯 X 上的用户反馈。
   - 关键约束（原文明确）：**前面先用便宜模型拦一道**，把大量噪声挡在 Opus 之外，只把有价值的反馈送进主模型，以省 token。
   - 筛选标准、如何把便宜模型的输出传给 Opus，原文未给，需自行补齐。

4. **起第三条 loop：定时清债与沉淀**。定时任务，做三件事：清理“屎山”（技术债）、把教训写下来、拉黑低质提交者。
   - 触发方式为“定时”，具体周期原文未给。
   - “写教训”的存放形式（文件、issue、文档）原文未说明，需自行决定——建议落成仓库内可被后续 loop 读到的文本，否则沉淀无法回流。

5. **三条 loop 并行常驻**，各自独立运转，不合并成一条大循环。

6. **人工保留 UI/UX 环节**。原文明确“人晚上只铲 UI/UX”，即审美/交互决策不外派，其余交给循环。这一步是整套方法能成立的前提：人被解放出来不是因为 AI 全包，而是因为人被限定在少数不可替代的环节。

7. **回收低质输入**。第三条 loop 中“拉黑低质提交”是闭环的一环——不清理输入源，前两条 loop 的负担会持续膨胀。

- **适用条件**：适合有稳定外部输入（issue/PR/社媒反馈）且技术债在累积的开源或个人项目维护场景；单人小项目输入不足时，三条常驻 loop 的成本可能高于收益。
- **主要风险**：常驻循环 + Opus 的 token 消耗；自动拉黑与自动评论的误判风险；原文未提及任何人工审核环节在 loop 内部如何设置。

## 怎么试、怎么验证

**最小试用**：只在一个仓库上做，且**先只跑一条 loop**（代码协作值守那条），跑一到两周。三条同时上是原文形态，但首轮验证没必要承担三倍成本。等第一条稳定后再加定时清债那条，最后再加 X 反馈那条（它依赖外部流量，价值最不确定）。

**判断有没有改善的指标**：

- issue/PR 首次响应时间（人工介入前）；
- 你本人每天花在非 UI/UX 事务上的时长（这是原文主张的直接检验点）；
- 每天/每周 token 与 API 成本，与人工时薪对照；
- loop 给出的 PR 判断中，被事后推翻的比例（衡量“拉下来真跑”到底降低了多少误判）；
- 定时清债那条：技术债清掉了多少、教训文档是否被后续 loop 实际读取到（若无人读，说明沉淀没闭环）；
- 被拉黑的提交中误伤的比例。

**止损条件**：若两周内人工审核 loop 输出所花的时间接近自己直接做的时间，说明该场景输入量不足或判断标准没调好，应退回单条 loop 或放弃。
