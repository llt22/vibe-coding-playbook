## 怎么试、怎么验证

不要照搬“整体重写”，先用一个模块级的最小试验验证这套方法本身是否成立：

1. **选件**：挑一个中等规模、有真实请求、行为可对照的模块（不是整个服务）。
2. **人写规格**：把旧实现的接口契约、错误码、边界行为、性能预算写成可执行测试集，同时记录写规格所花的人时（这是成本项，必须计入）。
3. **模型实现**：用新语言/新框架实现该模块，保留人工 review。
4. **双跑差分**：抽样真实请求（脱敏）同时打到新旧实现，逐字段 diff 响应。
5. **看四个指标**：
   - 差分率 = 不一致响应数 / 总请求数（目标收敛到 0，或每一处差异都能被规格解释）；
   - 性能：P50/P99 延迟、CPU 占用、内存，与旧实现同负载同环境对比；
   - 质量：人工 review 每千行发现的问题数、上线后回归缺陷数；
   - 成本：人写规格 + review 的人时，对比传统重写人时。
6. **判定**：差分率长期无法收敛到可解释范围，说明规格不清或任务边界选错，应停止而不是加人；差分率为 0 且性能改善明显，但人时成本高于传统方式，则该做法只在“性能瓶颈 + 行为可差分”的场景成立，不能作为通用重写方法。

关键是把“人写计划”的成本和“差分验证能覆盖多少行为”一起量出来——这两项决定了这条线索最终是 adopt 还是 drop。
