## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）

- **能力发现**：部分有依据。代理具备“识别文档与代码不一致”的能力（原文说“能看出文档不再与代码匹配”），但这种识别不会自动转化为行动。这是一个容易被误判为“已具备”的伪能力。
- **任务匹配**：弱相关但有信号。同一任务下 Claude Code 与 Codex 表现有差异（80 次中 79 次 / 4 次中 1 次），提示模型选择会显著影响代理在冲突情境下的行为，但样本与实验设置不明，不能据此下选型结论。
- **条件供给**：有依据，且是反向证据。AGENTS.md 属于典型的“提供给代理的上下文与规则”，一旦过时会从正供给变成负供给——提供得越明确，代理越可能照着错的方向做。这说明供给不仅要“给全”，还要“保时效、可证伪”。
- **主动推进**：原文没有涉及由时间、事件或状态触发的持续执行机制。
- **效果验证**：有依据。用“陷阱 + 多次重复 + 统计命中率”来测代理行为，是一种低成本、可复现的验证范式，可直接借鉴为指令文件变更后的回归检查。

## 怎么试、怎么验证

最小试用（半天内可完成，不依赖原文缺失的那一行）：

1. 选一个非关键仓库，在 AGENTS.md 中写入一处与实际代码不符的描述。
2. 构造一个会触发该描述的任务，重复运行 10–20 次，记录：按旧文档行事次数、误改正确代码次数、主动指出冲突次数。
3. 以“主动指出冲突率”和“误改率”为基线；再加上自己写的时效性约束（例如要求代理在动手前先核对文档与代码是否一致、发现冲突必须停下报告），用同样任务再跑一批。
4. 判断是否改善的指标：误改正确代码的比例下降；主动报告冲突的比例上升；任务本身的一次通过率不下降（避免用“更听话”换“更不敢做事”）。
5. 把该检查固化为例行项：每次修改 AGENTS.md 或重构目录/接口后，跑一次小规模陷阱测试。
