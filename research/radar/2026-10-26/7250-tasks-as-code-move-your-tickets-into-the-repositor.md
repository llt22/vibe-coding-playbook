## 是什么
Tasks as Code 是把开发任务从 Jira、Redmine 等外部工单系统移到 Git 仓库中，用 Markdown 文件保存。AI 编码智能体可以直接读取任务、代码和文档，在同一仓库上下文中分析需求、制定计划、实施变更，并把实现报告追加回任务文件。任务变更像代码一样被版本化、可审阅。原文还给出一种个人实践：代码、文档、任务分成三个独立 Git 仓库，本地把文档和任务仓库克隆到代码仓库下的 `/docs`、`/tasks` 目录，并用 `.gitignore` 让父仓库不跟踪它们，各仓库保留自己的 Git 历史。可选浏览器界面通过 Typemill 同步 Git 多仓库，方便产品负责人和技术写作者使用。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

1. **建立仓库结构。** 按原文示例，使用三个独立 Git 仓库：代码、文档、任务。文档可公开，任务可能包含未完成安全修复、内部规划或未发布功能等敏感信息，因此分开仓库便于独立配置访问权限。前提：团队使用 Git 管理代码和文档，并能配置仓库权限。

2. **在本地把文档和任务仓库挂到代码仓库下。** 开发者在本地把文档仓库和任务仓库克隆到代码仓库内的 `/docs`、`/tasks` 文件夹；在代码仓库的 `.gitignore` 中排除这两个目录，使父仓库不跟踪它们。两个被克隆仓库仍保留自己的 Git 历史，可独立提交、推送和同步。原文布局如下：

```text
/code-repo
  /src
  /tests
  /docs                 # Separate documentation repository
    /user-guides
    /admin-manuals
    /developer-docs
  /tasks                # Separate private task repository
    /release-123
      task-551-something-descriptive.md
      task-552-something-descriptive.md
  .gitignore            # Excludes docs and tasks
```

前提：本地开发环境可同时访问代码、文档和任务仓库；原文示例面向本地编码助手。

3. **写任务 Markdown 文件。** 在任务仓库中写一段简短描述，说明要实现的变更或功能。复杂功能可在任务文件中加入验收标准、技术决策、依赖和测试要求；小型维护任务只需短描述。原文强调可以把任务文件本身当作规范，不必一开始就引入专门工具。前提：任务文件放在智能体可读取的路径中；可按发布文件夹组织，例如 `/tasks/release-123/`。

4. **让智能体分析需求。** 智能体读取任务文件，并检查相关代码和文档。前提：智能体能访问本地代码仓库、文档目录和任务目录；原文举例 Claude Code 或 OpenCode。

5. **让智能体写实现计划。** 智能体在任务文件中追加拟议解决方案，并列出打算做的变更。前提：计划写回任务文件，而不是从任务描述直接进入代码修改。

6. **人工审阅并批准。** 开发者审阅计划并授权实施。原文明确这个批准步骤用于保持人类控制，智能体不应直接从任务描述跳到实现。前提：流程中必须安排人工审批关卡。

7. **智能体实施并报告。** 智能体修改代码，在需要时更新文档，并把实现报告追加到任务文件末尾。任务描述、实现计划和报告都留在同一个文件中，便于复核原始需求、计划方案和实际改动。前提：代码变更记录在代码仓库中，实现报告留在任务仓库中。

8. **提交代码时引用任务文件名。** 原文建议在 Git 提交信息中引用任务文件名，把实现与原始需求连接起来。前提：团队接受这种提交习惯；原文未给出具体提交命令或格式。

9. **可选：生成发布说明和文档更新线索。** 当任务按发布文件夹组织时，智能体可利用已完成任务和 Git 历史起草 changelog、release notes，并识别需要更新的文档。可选使用 Typemill 等浏览器界面同步 Git 多仓库，让非技术用户浏览、编辑和组织文件；Git 仍负责版本历史与同步。前提：需要额外界面时才引入；原文未给具体配置细节。
