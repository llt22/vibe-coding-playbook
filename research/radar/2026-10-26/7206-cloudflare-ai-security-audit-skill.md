## 怎么试、怎么验证

**最小试用方式**

1. 先到 `cloudflare/security-audit-skill` 仓库确认是否真有可用的 skill 定义与调用说明（本材料未提供，属于必须先补的前置动作）。
2. 选一个**已知漏洞答案**的小型仓库（例如历史上有明确 CVE 或人为植入若干漏洞的项目），作为测试集。
3. 跑三组对照：A 单 Agent 单轮“扫一遍代码找漏洞”；B 按本流程的多阶段 + 多 Agent 并行；C 在 B 之上加第 3 阶段的证伪环节。同一仓库、同一模型，只改流程。
4. 记录每条发现的证据链（文件、行号、触发路径），供人工复核。

**判断是否有改善的指标**

- **召回率**：植入或已知漏洞被找到的比例（这是“是否真能发现”的核心）。
- **误报率**：人工复核后判定为假的发现占比；重点看第 3 阶段证伪环节把误报压掉了多少（B 与 C 的差值）。
- **证据质量**：带可复现调用链的发现占比，而非只有一句“这里可能有问题”。
- **成本**：单次审计的 token 消耗与 wall-clock 时间相对 A 组的倍数。
- **人工复核耗时**：这是最终是否值得接入工作流的决定性指标：若误报下降带来的复核节省抵不过多 Agent 的开销，就只保留“架构分析 + 证伪”两个环节，砍掉并行扫描。

**判定门槛建议**：只有在 C 组相对 A 组在误报率上有明显下降、且召回率不降低时，才值得从 study 提升为 try/adopt 并写进手册。
