## 怎么试、怎么验证（最小试用方式和判断有没有改善的指标）

**最小试用（前提：先自行找到并核对仓库本体，确认 MIT 许可与 skill 内容）**

1. 选一个**已有的 Rust 小项目**（或一组固定的 10~20 个 Rust 任务），冻结任务集和提示词，全程不改。
2. **基线轮**：不装插件，用同一个 Claude Code 模型跑完任务集，记录结果。
3. **实验轮**：装上 BeautifulRust，用**完全相同的提示词**重跑同一任务集。为避免顺序效应，可两轮交替各跑一次。
4. **自己出题，不用它的 30 项**：检查表按你项目的真实痛点写，例如：`cargo build` 是否一次通过、`cargo clippy` 警告数、是否符合 API 命名惯例（如 `as_`/`to_`/`into_` 的用法）、错误类型是否用 `thiserror`/自定义 enum 而非 `String`、是否出现不必要的 `clone`、公开 API 是否有文档注释。
5. 记录**人工 review 后需要改动的行数**——这是比“检查项通过率”更难造假、也更贴近实际收益的指标。

**判断有没有改善的指标（建议同时看，不要只看通过项数）**

- 检查表通过率（对应原文的 x/30 口径，便于横向对照）；
- 人工 review 修改行数 / 每任务修改次数；
- `cargo clippy` 警告数、编译一次通过率；
- 回归率：为了满足规范而引入的新问题数量（防止“为了规范而规范”）；
- 稳定性：同一任务重复 3 次，结果方差有多大——如果提升只在某一次出现，多半是噪声。
