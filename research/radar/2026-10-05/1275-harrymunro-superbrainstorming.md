## 是什么

Superbrainstorming 是 Claude Code 的一个插件（fork 自 Jesse Vincent / Prime Radiant 的 Superpowers），核心只有一件事：在你让编码智能体开工之前，先让它把设计讲清楚并等你点头。

流程是一个带闸门的循环：

- 你提出需求 → 智能体先提问并给出设计 → 你批准？
- 未批准 → 回到设计（继续改）
- 批准 → 智能体在同一个会话里立刻开始构建

作者的立论是：编码智能体「会建东西」但不知道你指什么、给谁用、你在意哪些取舍，所以「一个很有能力的智能体仍然可能把错误的东西建得很好」。

与上游 Superpowers 的关键差异：Superpowers 是完整工作流（头脑风暴 → 写详细计划 → 每个任务交给全新子代理，全程 TDD + 代码审查）；本 fork 只保留头脑风暴，删掉了 writing-plans、executing-plans、subagent-driven-development、test-driven-development、systematic-debugging、verification-before-completion、代码评审类、git worktree 类等技能，也删掉了 Claude Code 之外的工具集成。作者给出的理由是：当前模型（原文提到 Claude Opus 5.5、Sonnet 5.5、Fable 5.1）能把已达成的设计保持在上下文里并自己推进完成。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

1. **前提**：使用 Claude Code。若要启用可选的「视觉伴侣」（画布局、mockup、示意图），另需本机有 Node.js。

2. **安装前先处理 Superpowers 冲突**：如果你已经在用 Superpowers，先通过 `/plugin` 把它禁用或卸载。原因是两个插件都带 `brainstorming` skill 和 session-start hook，而 Superpowers 那一版在同一位置会转而进入「写计划」而不是直接构建。

3. **安装插件**（在 Claude Code 中运行）：

```bash
/plugin marketplace add harrymunro/superbrainstorming
/plugin install superbrainstorming@superbrainstorming
```

然后**新开一个会话**（session-start hook 在会话开始时生效）。

4. **做一次冒烟验证**：在全新会话里发送：

```
Let's make a react todo list
```

预期行为：智能体加载 `superbrainstorming:brainstorming` skill、声明把这件事当作 architectural 工作处理、并在写任何代码之前先问这个应用是做什么用的。如果没出现这些行为，说明 hook 或 skill 没生效。

5. **确认三选一的路径，且你有否决权**。智能体会按任务规模选一条并**明确告诉你选了哪条**，你可以推翻它：

| 路径 | 适用 | 会发生什么 |
|---|---|---|
| **Spike** | 「这事到底可行吗」类问题 | 智能体建议一个快速实验，你点头后它去跑，回来汇报发现；产出的东西是一次性的、可丢弃 |
| **Bounded** | 对现有代码的小范围、边界清晰的改动 | 智能体问清什么重要，在对话里给一个简短设计 |
| **Architectural** | 新项目、新子系统、大的结构性改动 | 智能体一次只问一个问题，给出两三个方案，并把 spec 写到 `docs/specs/` |

6. **在批准之前，要求它复述三件事**（原文明确说它会主动做）：想达成什么、给谁用、「done（完成）」长什么样，并回写给你让你纠正。发现复述不对就在这里改，这是最便宜的纠错点。

7. **只有你批准后才动工**。三条路径都遵守这一点。批准后它立刻在同一会话里开始，自己做步骤跟踪，遵循你项目在测试和提交上的既有约定，并在宣布完成前自检。

8. **中途发现问题时，它应该停下来问你**，而不是悄悄改道。如果它没停，这就是流程失效的信号。

9. **想跳过设计就直接说**，原文说「say so and the agent will」——即直接构建是被支持的逃生口。

10. **换用其他智能体**：skill 是 `skills/brainstorming/` 下的标准 `SKILL.md`，任何支持 Agent Skills 的智能体都能加载。但没有 session-start hook 时它可能不会自动触发，需要**按名字显式要求它**。原文提到 Superpowers 有面向许多其他工具的集成，可供移植参考。

11. **可选：视觉伴侣**。对布局、mockup、示意图这类「看一眼比描述更清楚」的问题，智能体可以提议在你的浏览器里开一个标签页展示选项。它是 opt-in、需要 Node.js、完全在你本机运行、不从互联网加载任何东西。生成的 mockup 存在项目内的 `.superbrainstorming/`，**记得把它加进 `.gitignore`**。

12. **（改插件本身时）跑测试**：

```bash
# Visual companion server
cd tests/brainstorm-server && npm ci && npm test

# Session-start hook
bash tests/hooks/test-session-start.sh
```

原文提醒：改动 `skills/brainstorming/SKILL.md` 或 `hooks/bootstrap.md` 会改变智能体的行为，合并前要在真实会话里试过。

## 对应的研究问题

**1. 能力发现**：把「设计讨论」当成编码智能体的一个显式阶段，而不是让它直接从需求跳到代码。这是最容易被忽略、也最容易产生「把错误的东西建得很好」的环节。

**2. 任务匹配**：原文给出了明确的分档规则——按任务规模选 Spike / Bounded / Architectural 三条路径。更值得注意的是选型建议：**用当前前沿模型且只想要一次快速设计确认 → 选本插件；用较小或较旧的模型、或需要强制 TDD、逐任务代码审查、git worktree 管理 → 选上游 Superpowers**。这正好回答了「什么样的协作方式配什么样的模型」。

**3. 条件供给**：需要提供给智能体的信息在原文里是可列的——目标、受众、「done」的定义；此外它还要读取你项目的测试与提交约定。需要给的权限/信号是「批准」（批准设计即批准开工）；还要给的是一种否决权：对路径选择可以推翻。可选项上，视觉伴侣需要 Node.js 和 `.gitignore` 配置。

**4. 主动推进**：session-start hook 在会话开始时主动提醒智能体「先头脑风暴再构建，批准后就构建」——即用状态/事件触发行为约束，而不靠人每次记着。构建开始后，智能体自行跟踪步骤、自检、完成后给总结；中途发现设计有问题会主动停下询问。批准后的构建在同一会话内连续进行，不需要重新交接上下文。

**5. 效果验证**：原文只给了自检与完成总结（「你拿到它建了什么、以及它怎么检查的总结」），**没有给出任何效果指标**。它对插件自身质量的验证方式是 `tests/brainstorm-server` 的 npm test 和 `tests/hooks/test-session-start.sh`（验证的是插件机制，不是工作效果）。

## 怎么试、怎么验证

**最小试用方式**

1. 选一个你近期真实要做的、规模在 1–3 小时内的编码任务（不要用玩具任务，也不要上大重构）。
2. 按上面第 2–4 步安装并做冒烟验证，确认 skill 被加载、且它在写代码前先提问。
3. **做对照**：同一个任务，先在**不装插件**的会话里让智能体直接构建一遍（或回忆你上次同类任务的经历），记录结果；再在装插件的会话里做一遍。不要只做后者——没有对照就看不出改善。
4. 观察并记录这四个检查点是否发生：
   - 它是否回写「目标 / 受众 / done 定义」给你确认；
   - 它是否声明选了哪条路径；
   - 它是否在你批准前一行代码都没写；
   - 批准后是否在同一会话里直接开工，而不是转去写计划。
5. 若走 Architectural 路径，检查 spec 是否真的落到 `docs/specs/`，以及它是否遵循了你项目的测试与提交约定。

**判断有没有改善的指标**

- **返工轮数**：从首次交付到「我想要的」之间需要几轮修改（对照实验里应下降）。
- **理解偏差类问题数**：事后 review 中属于「它做错了东西」而非「它写错了代码」的问题条数。
- **设计阶段耗时**：从提出需求到你按下批准的时间。原文的卖点是这一步很「快」，如果它明显拉长（例如提问过多、反复给方案），就说明这条路不适合你的任务类型。
- **中途改道次数**：它在构建中停下来说「设计有问题」的次数——偏高说明前期提问/确认不够，偏低（且最后发现理解错了）说明闸门形同虚设。
- **完成总结的可核对性**：它给的「我建了什么、我怎么检查的」总结，是否能让你不读代码就判断改动范围。

**什么时候不该继续用**：任务需要强制测试先行、需要独立代码审查、或需要并行多代理时——原文自己说了这类场景应回到 Superpowers。
