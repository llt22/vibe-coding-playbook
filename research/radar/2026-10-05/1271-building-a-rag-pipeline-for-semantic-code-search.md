## 是什么

JetBrains 关于 Air Context（文中也以 JetBrains Context 名义出现）的开发手记第一篇，讲一条面向代码库的语义检索 RAG 流水线中“原始源码 → 可检索向量”的三段：解析与分块、向量化、以及为检索准备的元数据与隐私约束。目标不是给人用的搜索框，而是给编码智能体提供精确、可引用的证据，替代只能靠关键字命中的 grep。作者明确这是系列第一篇，存储、毫秒级查询服务、持续评估、智能体接入都留到后续篇章。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

原文没有给出代码、命令或配置文件，以下是对原文所述流水线的整理，实施时需自行补齐工程。

1. 前提：确定要支持的语言。结构感知解析覆盖 9 种语言——Kotlin、Java、Python、JavaScript、TypeScript、C#、PHP、Go、Rust；其余语言回退到按行的朴素切分，以保证任何语言都能被索引。
2. 前提：有语言解析器。用解析器把源文件拆成语法节点流（注释、空白、修饰符、声明等），分块算法按节点类型、大小及其子孙做决策：节点超阈值但没有子节点时退化为更原始的切分策略；前缀（文档注释、注解、可见性修饰符、关键字）与声明绑在一起，后缀（通常是闭合语法）跟随其所属结构；再做语言特定清理，例如去掉 @NotNull、@Override 这类语义无意义的 Java 注解。
3. 对每个 chunk 做归一化：去首尾空白、删空行、去掉公共缩进但保留相对缩进。
4. 把相对路径作为元数据，与归一化后的 chunk 内容一起送入嵌入模型。
5. 路径过长时按“两端保留”规则截断：保留最长可容纳的前缀，加上最后两段（直接父目录与文件名），中间省略为 `…`；若父目录加文件名仍然超长，只保留文件名本身。
6. 索引侧与查询侧用同一个模型，但形态不同：文档（代码 chunk）在索引时原样嵌入；查询用指令模板包裹，原文给出的示例是：
```
given this search query, find the code that answers it
```
7. 目录范围检索不要用“先照常检索、再丢弃范围外结果”的元数据过滤，而要把范围按与索引时相同的缩写函数、相同的分隔符渲染进查询文本。例：某个 chunk 以 `community/plugins/kotlin` 的缩写形式入索引，限定到该目录的查询就带完全相同的字符串，让查询向量落到同一区域。
8. 向量压缩时优先保维度、放弃精度。量化规则是每个分量大于等于 0 记 1、负值记 0，幅度信息直接丢弃，得到 1 bit/维，比 32 位浮点小 32 倍：
```
bit = 1 if component >= 0 else 0
```
9. 度量随之改变：二值向量用 Hamming 距离（两个位模式不同的位置数）而非余弦相似度。实现上 4096 位向量存成 64 个 64 位字，逐字 XOR 后数 1，原文称一次完整比较约为百条指令量级，而浮点余弦需要数千次乘法。
10. 但需要绝对相关性判断的场景不要用二值向量：二值量化把相似度分数压进一条窄带（不相关对靠随机也能有一半位相同，强相关对约三分之二），排序仍然有效、阈值判断失效。原文举的例子是“边写边主动推荐已有实现”的提示面板——它最难的需求是知道何时保持沉默，因此这里保留 16 位浮点并接受存储代价。
11. 索引与查询分开部署调优：索引是吞吐受限（原文称 GPU 单批约 32 个 chunk 后饱和），查询要快（原文称用户最多容忍几秒），一个优化 chunks/秒，一个优化首个结果的时间。
12. 隐私前提：chunk 只存簇引用、条目类型、文件路径、起止偏移、向量引用和可选元数据，不保存任何源码内容；检索返回的是坐标（原文举例：服务器只知道某路径第 4102–4890 字节处有相关内容），片段在用户自己的 checkout 上组装。嵌入使用自托管的开放权重模型，请求不离开自有基础设施，也不用于训练。

## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）

- 能力发现：把“按语义找代码”交给智能体——grep 要求事先知道确切文本（找 session token 在哪刷新时，代码里不一定有 refresh），语义检索让智能体能用自由文本按含义取回片段；另一类是主动型能力，即边写边推荐已有实现的提示面板，其核心难点是“何时保持沉默”的阈值判断。
- 任务匹配：索引与查询是两类不同负载，需分别优化；嵌入选指令跟随、且查询/文档两侧刻意不对称的模型；排序场景可以用 1 bit + Hamming，需要阈值判断的场景必须换成 16 位浮点；分块质量依赖语言级解析器，只覆盖 9 种语言，其他语言退化。
- 条件供给：要给检索层提供语言解析能力、相对路径等元数据、把检索范围写进查询文本的约定、可自托管嵌入的 GPU 资源，以及“只存坐标不存原文”的存储设计；智能体一侧需要一个能用自由文本查询的接口。
- 主动推进：本篇只给了提示面板这一条主动能力的线索（难点在阈值，二值向量做不到），并明确把“怎么让智能体真正用上这套 RAG”列为后续篇章，没有可照做的触发-持续执行机制。
- 效果验证：用 LLM-as-a-judge 检查 chunk 边界是否合理，找脱落的文档注释、孤立的闭合语法、被切断的完整结构；源码处理流水线的每次改动都要过一遍端到端检索评估；把二值量化的召回损失计入决策（原文称“几个点”）；用自建代码检索基准把开放权重嵌入与各家托管 API 做对比。

## 证据与局限（原文给了哪些数据或案例，哪些只是作者主张，适用条件是什么）

原文给出的数据与案例：IntelliJ IDEA 单体仓库超过一百万文件，源码文件中位路径深度 9 层、91 字符，近 1 万个源码文件路径超过 150 字符，最长 218 字符（且未计入 checkout 根）；最长路径对应的文件本身只有 24 行。一个几千维的 32 位浮点向量约 16KB，几百万 chunk 即数十 GB 索引。二值化后比 32 位浮点小 32 倍。索引侧 GPU 单批约 32 个 chunk 后饱和。存储预算 512 字节/向量时，128 维 32 位与 4096 维 1 bit 占用字节相同。

仅是作者主张、原文未给量化证据的部分：同一字节预算下“保维度”明显优于“保精度”（原文只说“在测试中你会发现”）；二值量化只损失“几个点”召回且对智能体消费基本无感；自托管开放权重嵌入在自家基准上超过托管 API；隐私约束不带来检索质量代价。这些都需要自行验证。

适用条件：面向大型或单体仓库、以智能体为消费方的代码检索；结构感知分块受限于 9 种语言；需要能自托管嵌入模型的基础设施；本文是系列第一篇，存储、查询服务与评估流水线的细节尚未给出，且属于厂商博客、带有产品宣传成分（文末推广 Air Context 公开预览）。

## 怎么试、怎么验证（最小试用方式和判断有没有改善的指标）

最小试用：选一个中大型仓库（最好多语言、含较深目录结构），构造 30–50 条自然语言查询，每条人工标注正确答案的位置（文件与范围）。

- 分块：跑一版结构感知分块（原文提到与 cAST（Zhang et al., 2025）思路相近，可据此进一步查阅该工作或自行用语言解析器实现），与固定行数分块做 A/B。
- 检索：用开放权重嵌入模型，文档原样嵌入、查询按指令模板包裹；路径按“两端保留”规则截断后随 chunk 一起嵌入。
- 压缩：在同一“字节/向量”预算下比较两种混法（少维度×高精度 vs 全维度×1 bit），各自使用正确的度量（余弦 / Hamming）。

判断有没有改善的指标：recall@12（正确片段是否进入前十几条，原文认为这是智能体场景的关键，而非前十的精确排序）；索引体积（字节/向量）与检索延迟（首个结果时间）；对需要阈值判断的功能（如主动推荐）单独测“该沉默时是否沉默”的误报率，若二值向量做不到就换回 16 位浮点；最后做端到端对照，把该检索层接进编码智能体，比较同一批任务的成功率、人工介入次数与耗时。
