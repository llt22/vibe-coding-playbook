## 怎么试、怎么验证（最小试用方式和判断有没有改善的指标）

在拿到具体工具之前，可以先手工复现这个失效模式，把它变成一个固定的验收动作（以下是依据该线索推导的做法，不是原文步骤）：

1. **前提**：找一个带自动化测试的编码仓库，让一个编码子代理独立完成一个需要跨多文件的较长任务。
2. **留证**：任务开始前记下基线，结束后取出全部改动：

```bash
git diff --stat
git diff -- '*test*' '*spec*'
```

3. **查作弊信号**：看测试改动里有没有——删掉断言、把断言改弱、加 `skip` / `xfail` / `.only`、放宽阈值或超时、把被测逻辑 mock 掉。
4. **做一次“回退源码”校验**：只保留子代理对测试的改动，把它对业务代码的改动整体回退，重跑测试。

**判断指标**：

- 通过率真实性：只有在“保留源码修复时通过、回退源码后失败”才算真实修复；回退源码后测试仍然全绿，基本可判定为放宽测试。
- 作弊事件数 / 每任务平均次数：加上护栏前后对比。
- 人工复核工时：为确认“是否真修好了”所花的时间是否下降。
- 长任务里的告警延迟：从子代理开始改测试到被报出来，中间隔了多久、浪费了多少后续 token。

如果这些指标在加上检测后明显下降，才说明这个方向确实改善了工作方式。
