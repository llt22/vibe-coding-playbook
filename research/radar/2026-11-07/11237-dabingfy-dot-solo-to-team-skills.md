## 是什么

一套面向「一个人总控 + 多个长期 AI 助手」的协作技能包（MIT，仓库 `dabingfy-dot/solo-to-team-skills`，文档状态自标 v0.9-draft）。交付物是 4 支技能 + 1 个登记行模板 + 教学示例 + 2 份脱敏案例，核心是一条流程线：**提目标 → 分工 → 交接 → 核对 → 判断**（派 → 收 → 核 → 判）。技能以 `SKILL.md` 目录形式分发，可拷进 8 家 Agent 宿主按名调用。

四支技能分工：

| 技能 | 管哪段 | 来路 |
|---|---|---|
| `dispatch-accept-verify`（派出去的活要收回来） | 分工＋交接 | 借鉴改写（含 obra/superpowers 一段） |
| `evidence-before-done`（交活前要有证据） | 核对 | 改写自 obra/superpowers（MIT） |
| `beginner-ops-writing`（新手操作说明） | 须人做时的写法 | 原创 |
| `ops-case-notes`（脱敏运营记录） | 真实弯路参照 | 原创，两个案例 |

它要解决的不是「AI 不够聪明」，而是四类协作漏损：活派出去没人收、说做好了其实没核过、给新手的步骤只有自己看得懂、同一个坑踩两遍。

## 具体做法（编号步骤；每步写清前提）

**步骤 1｜取得技能目录**
前提：能下载/克隆仓库；对目标目录有写权限（多数在用户目录下）。
拿到 `skills/` 下四个子目录，每个里一个 `SKILL.md`。
⚠️ 手动拷贝时**整目录拷**，不要只拷 `SKILL.md`——`dispatch-accept-verify` 必须连它的 `templates/` 一起拷，否则登记行模板会丢。宿主只收一份正文时（如 Grok Bot），把模板一并贴进去。

**步骤 2｜选宿主并装上（选一个先跑）**
前提：已装对应宿主并能正常登录。下列命令/路径是原文写明的走通做法，以各宿主官方当日文档为准。

- Codex（本机目录作源，正式建仓前不要填 GitHub URL）：
```bash
cd /path/to/solo-to-team-skills
codex plugin marketplace add "$(pwd)"
codex plugin add solo-to-team-skills@solo-to-team-skills
```
非 0 退出就停，检查是否指到含 `.agents/plugins/marketplace.json` 的包根；装完**新开一次会话**。撤回：
```bash
codex plugin remove solo-to-team-skills@solo-to-team-skills
codex plugin marketplace remove solo-to-team-skills
```
- 目录拷入型（整目录放到下列路径之一）：
  - WorkBuddy：`~/.workbuddy/skills/<技能名>/` 或项目 `.workbuddy/skills/<技能名>/`（也可界面上传 zip）
  - DeepSeek Harness：`.dsh/skills/`、`~/.dsh/skills/` 或 `.agents/skills/`；需自备 DeepSeek 账号或 API，本包不提供密钥；`dsh plugin add` 不是装技能正文的办法
  - Cursor：`~/.cursor/skills/<技能名>/`
  - CodeBuddy：`~/.codebuddy/skills/<技能名>/` 或项目 `.codebuddy/skills/<技能名>/`
  - 千问办公 QwenWork：`~/.qwenworkcn/skills/<技能名>/`
  - Kimi Work（桌面端）：`~/Library/Application Support/kimi-desktop/daimon-share/daimon/skills/<技能名>/`（社区路径，官方另支持上传 zip／md 或商店）
- Grok Bot：不走一键安装，在对话里把某支 `SKILL.md` 正文 **Save 为私有技能**，四支分别存；存 `dispatch-accept-verify` 时把 `templates/登记行模板.md` 一起贴进去。
- Claude Code：结构已备（`.claude-plugin/`），原文明确「走通待补」，不纳入首发支持。

易混点（原文点名）：CodeBuddy ≠ WorkBuddy；千问办公 ≠ 通义灵码；Kimi Work ≠ Kimi Code CLI；通义灵码/TRAE/Comate 未验证。

**步骤 3｜先只启用两支**
`dispatch-accept-verify` 的「已验收」一步依赖 `evidence-before-done`，两支一起装；`evidence-before-done` 单装也能独立用。另外两支是可选搭配，不装不影响主流程。

**步骤 4｜按名调用，确认能出活**
前提：技能已拷入、会话已新开/刷新。
Codex 非交互示例：
```bash
codex exec -s workspace-write --skip-git-repo-check -C "$(pwd)" '请使用技能 dispatch-accept-verify，写一行待收登记到 T044_dispatch_line.md'
```
Cursor 的 CLI 形态如 `cursor agent --print`；对自己新建的工作区做非交互运行可能要加 `--trust`（这是信任该工作区，不是关安全开关）。判据：能打出一行可读的「待收」登记行。

**步骤 5｜派活前先登记一行「待收」**
用 `templates/task-register-line.md`（可直接复制），或先用记事本/表格手写。一行至少写清：做什么、结果放哪、几点交、谁在干、谁来收、谁到点查。

**步骤 6｜交接：三态分开记，只有一种能划掉**
到点去查 → 记「已接单」→ 收到成果记「已收到成果」并写明结果在哪 → 核过记「已验收」。**只有「已验收」或授权取消才从未完清单里拿掉**；没人接就升级、续期。
前提：原文明确 `hooks: {}`——本包**不带定时、不带叫醒、不带自动回执**；到点查由宿主自带定时能力做，宿主没有就由人按点查。最低配置是「一份共享记录 + 一个会按时查看的人」。

**步骤 7｜宣布完成前先取证（evidence-before-done）**
说「做好了」之前，拿到**对得上当前版本**的有效证据：打开文件看、重算、照原步骤再走一遍。改过或失败过的部分补核，没变的部分可复用上一回的核验结论。核过才记「已验收」。

**步骤 8｜划边界：危险动作与拍板权**
花钱、发出、删除、登录、付款确认这类只写「请本人来」，不写代做办法；收下/退回/改方向由人拍板。`beginner-ops-writing` 用来写这类说明，原则是一次一步、点名唯一、写清做完会看到什么。

**步骤 9｜完整跟做一遍（含一次退回）**
照 `examples/walkthrough-meeting-notes/` 走「给定输入 → 成果 → 证据 → 验收」，并**故意走一次退回**。注意：该 walkthrough 是作者写的教学样例，不是实测记录。

## 对应的研究问题

**1. 能力发现**：原文把五类「元工作」显式列为可交给 AI 做的事——派活登记、到点催收/续期、交活前取证、新手说明改写、脱敏复盘记录。更有用的是那张三栏分工表（本包技能负责 / 宿主能力负责 / 须人做），它直接给了一个判断「这件事该交给谁」的切分框架：技能管方法与字段，宿主管会话/定时/读写，人管目标、优先级、验收与危险动作。

**2. 任务匹配**：按宿主分别给了装法与调用方式，并承认各家不同（有的使用者本人在宿主里发出、有的命令行、有的代点）。可提炼的匹配结论：正文跨宿主共用、只换入口与加载方式；能力差异主要在「有没有定时/跨助手发消息/叫醒」，而不在技能本身。给出了一个量化点：Cursor CLI 非交互、提示词事先备好时约 29.6 秒打出登记行。

**3. 条件供给**：所需条件写得很具体——目标目录写权限、宿主已登录、DeepSeek 需自备账号/API、一份共享记录（表/记事本）、一个会按时查看的人、宿主侧定时能力（有则用、无则人工）。反馈链路是三态迁移（待收 → 已接单 → 已收到成果 → 已验收）加验收结论。

**4. 主动推进**：原文对此是**明确的否定式回答**——`hooks: {}`，不提供自动派工、自动叫醒、自动回执；到点查、记接单/收到成果/验收、叫开工这三件事，按技能正文步骤由你或宿主来做。也就是说，时间/状态触发这一环本包只给流程与字段，触发能力要向宿主借。

**5. 效果验证**：原文用「两条硬标准」验收自己——(a) 能装能调（取得 → 装/配置 → 按名调用 → 产出登记行）；(b) 能完成一件实际小任务（真实成果 → 证据 → 验收结论）。并诚实标注第二条只是「八家各一例有限任务」，不代表稳定性。

## 证据与局限

**原文给出的数据/记录**：
- Cursor CLI 实测约 **0.5 分钟（29.6 秒）**，从把四支技能拷进 `~/.cursor/skills/` 算到打出可读「待收」行；前提是已装并登录 Cursor（含 CLI）、已取得本包、网络可用；**不含**装宿主、注册、手动打字时间。原文明确禁止把「约十分钟」写成已测保证。
- 八家宿主「能装能调」均有走通记录；另各有一例有限任务验收（Codex 是此前单独验证的一例，其余七家按**同一会议转写题**补验，部分宿主**受阻重跑或退回修订后才通过**）。
- 队内日更主链跑了约**两周余、复盘 3 次**，产出的改法（提交和接收分开记、放行后当场叫开工、素材先复核再交）写进了技能。

**只是作者主张、未证实的**：全队错误率是否下降、催办是否变少——**没有对照实验**；不表示每家四个技能都逐一被调用；部分宿主未保留技能加载的原始轨迹；主示例 walkthrough 是教学样例而非实测。

**适用条件**：一个人带多个长期 AI 助手、有一份共享记录、能接受「定时靠人补」；不适合指望开箱即自动组队或自动催办的场景。文档自标 v0.9-draft，正式公开前还会改，命令与界面入口会随宿主版本漂移。

**本次材料的局限**：只抓到 README，四支 `SKILL.md` 正文、登记行模板原文、两个案例正文都未取到——技能内部的具体提示词与字段格式无法核对，只能依据 README 的描述判断。README 中的日期（多处写「截至 2026-11-06」）与发起人传播量数字，本材料内无法核实，与研究方法无关，不应作为采用依据。

## 怎么试、怎么验证

**最小试用（一人、一宿主、一件小活）**
1. 选 Cursor 或 Codex，只装 `dispatch-accept-verify` + `evidence-before-done` 两支（连 `templates/` 整目录拷）。
2. 建一张表当共享记录，用登记行模板；先不开任何其它分支。
3. 派一件**两周内能收**的真实小活（可直接复刻原文的会议转写题），派前写「待收」，到点人工去查（本包不叫醒）。
4. 走完 待收 → 已接单 → 已收到成果（写明结果在哪）→ 取证 → 已验收；过程中**人为触发一次退回**，看退回后状态是否还看得见。
5. 跑满两周（对齐原文队内日更链的观察窗口），期间不加新字段，避免把记账负担也算成收益。

**判断有没有改善的指标（试用前后同口径对比）**
- 说「完成了」但核不过的比例（目标：下降）——这是本包主打的那一条。
- 超期未接单/未收的活数量，以及**从超期到被发现的天数**（目标：后者显著缩短）。
- 同一类错误重复出现的次数（对应 `ops-case-notes` 的「同一个坑踩两遍」）。
- 每件活的返工轮次与从派到验收的总时长。
- 登记行里「已验收」占比，与「待收」积压量。

**停用/降级判据**：若「核不过比例」和「超期发现延迟」两项**都没有**下降，说明多出来的只是记账，应停用或砍字段；若降不下来是因为宿主没有定时能力而人也没按点查，那是流程执行问题，别记到技能头上——先把「谁到点查」这一个责任人补上再复测。
