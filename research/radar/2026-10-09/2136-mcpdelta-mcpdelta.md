## 是什么

Delta MCP 是一个宣称“位于 AI 应用与其 MCP 服务器之间”的免费应用，定位接近本地代理（作者自称“更接近本地 proxy，而不是企业网关”），用于让 AI 处理 MCP 工具时更快、更省 token、并且可撤销。

它宣称的核心机制（原文 How it does it 三条）：

1. **一个任务一段程序，而不是一步一次调用。** AI 把整个任务写成一段短程序；用户的 MCP 服务器保持原样，每个原有工具仍可按原名调用（原文称在最大的服务器上 152/152 个工具仍可调用）。
2. **先检查、全有或全无地应用、再读回结果。** 在第一次调用之前检查该程序，用最少的调用次数执行，全部成功或全部不执行，然后读回结果。
3. **记录在 Activity 中并可撤销。** 每个任务连同每项改动的前后状态进入 Activity，一键 Undo；对于无法撤销的操作（例如已经发出的消息），会明确告知。

宣称兼容 12 个 AI 应用：Claude Desktop、Claude Code、Cursor、VS Code、Windsurf、Gemini CLI、Cline、Roo Code、LM Studio、Amazon Q、Codex、Zed；前十个可自动切换，Codex 与 Zed 目前需手动配置。数据不出本机（原文称除版本检查外，唯一可发送的是每天一个匿名的“节省 token 数”，首次启动由用户选择，可在 Settings 一键关闭）。

## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）

**1. 能力发现：AI 已经能做哪些还没想到交给它的工作**

原文的主张是：把“多步 MCP 操作”从逐步的“读—决策—调用—等待—再读”改成“AI 一次写出整个任务的一段程序”。这提示了一类此前默认由人/逐步调用完成的工作（修复 release、补测试、批量清理 ticket、登录后加联系人并列出、批量改任务列表）可以整体交给模型编排。同时它给出一条反向的能力边界：**单步任务不该用这种编排**——原文称单个一步问题反而多用约 1.25 倍 token。

**2. 任务匹配：什么工作适合怎样的模型、工具和协作方式**

原文明确区分了两类任务：

- 适合：多步、跨工具、可回滚的任务。原文列出的场景包括 “Fix a release, as text”（Cerberus，152 个工具）、“Add tests, as text”、“Fix a release, as code”、“Clean up 20 late tickets”（ticket manager）、“Log in, add 3 contacts, list them”（Microsoft Playwright MCP）、“Make 6 changes to a task list”（taskqueue-mcp）、“A documentation question”（Context7）。
- 不适合：单步问题（“A one-step question”，Playwright，books.toscrape.com），原文明确说成本更高。

模型与客户端条件：基准是在 **Claude Code + Sonnet 5.5** 上测的，并且原文称测量时 **Tool Search 是打开的**，即收益被主张为叠加在 Tool Search 之上（“Tool Search 只是让工具列表变短，每一步仍然是独立的一次模型请求；Delta MCP 去掉这些请求”）。

**判断有没有改善的指标：**

- 同一任务在开启/关闭 Delta MCP 两种情况下的**计费 token 数**与**模型调用轮次**；
- **端到端耗时**；
- **结果正确性**（在有权威校验的地方核对，例如测试是否真的通过、ticket 是否真的被正确清理）；
- **撤销成功率与撤销后状态一致性**；
- **单步任务是否退化**（token 是否上升约 1.25 倍）。
