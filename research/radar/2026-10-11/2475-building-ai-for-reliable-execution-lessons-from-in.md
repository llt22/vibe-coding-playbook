## 是什么

Latent.Space 对工业机器人公司 Standard Bots 两位负责人（CEO Evan Beard、AI 负责人 Leif Jentoft）的访谈，主题是其“AI 栈”如何让机械臂可靠执行工厂任务。核心做法可以概括为：

- 一个共享基座模型，客户用**示范（demonstration）+ 微调**做任务适配；
- 模型只负责**感知/零样本识别定位**，运动与工位逻辑仍用**传统编程**；
- **云上训练、本地推理**（工厂不依赖可靠外网，uptime 是客户接受的前提）；
- 从**真实部署**中采集失败信号与人工纠正，非气隙客户通过 **fleet learning** 回流改进模型；
- 数据理念是“**质量远重于体量**”，边缘 case 可以用“几十个样本”级别的现场干预修好。

原文最后一段作者自己点题：这套“把模型角色收窄、用真实部署的纠正来修边缘 case”的思路，可以迁移到软件 agent 上。这就是它对本次调研的价值，但原文并没有给出迁移后的具体做法。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

**先说明：原文没有给出任何可复制的命令、配置文件、提示词或代码。** 下面是把原文描述过的架构按“可执行顺序”重排出来的，属于**对原文的转写而非原文配方**；每一步后面标注了它在原文中的依据。任何涉及你具体系统的实现细节，原文都未提供。

1. **拆任务：先划出“需要学习”和“不需要学习”的边界。**
   前提：有一个端到端工作流。
   原文依据：机器 tending 场景中，“模型负责感知——定位和识别零件——而传统编程负责其周围的运动与工位逻辑”；公司对“不需要学习行为”的流程部分使用常规编程。
   落地动作：列出工作流的全部环节，只把“识别/定位/判断”这类感知型环节交给模型，其余编排、状态机、重试、权限校验等写成确定性代码。

2. **给模型一个窄角色，并要求它输出可直接对接下游的结构化结果。**
   前提：第 1 步的边界已划定。
   原文依据：零样本系统让用户“告诉机器人本次任务要找哪些零件”，模型输出感知结果；另一处描述模型“生成 action chunks，流式送到低层控制”。
   落地动作：让模型输出结构化字段（识别到什么、位置/置信度或下一步动作块），下游由确定性代码消费，而不是让模型自己决定整条流程。

3. **用少量示范做基线适配。**
   前提：有一个共享基座模型或可微调的基础模型。
   原文依据：“共享基座模型，客户通过示范和微调来适配”；“真实世界的示范也是学习过程的一部分”，并演示了用手持触控设备示教机器人。
   落地动作：为任务录制/标注一组示范样本，做轻量微调或少量示例注入；原文未给出样本条数、训练超参、微调方法。

4. **把推理放到离执行最近的地方。**
   前提：有本地算力与内网。
   原文依据：训练在云、推理在本地；“工厂大部分场景需要 on-premise 推理”；腕部相机与其他传感器经内部千兆以太网传原始像素与信号，边缘 GPU 处理并生成 action chunks 流式送给低层控制；理由是没有可靠外网、uptime 至关重要。
   落地动作：把模型调用放在执行侧（本地/内网），只把训练和批处理放在云上；为断网设计降级路径。

5. **能仿真就仿真，仿真不了的用真机示范。**
   前提：有仿真环境。
   原文依据：涉及液体、吸附、切割柔性材料的生产任务“在当前仿真器中难以复现”。
   落地动作：先筛一遍哪些场景能在仿真里高保真复现，不能的走真实数据路线。

6. **在部署中采集失败信号与人工纠正，用它修边缘 case。**
   前提：客户允许数据回流（原文明确指出国防客户在气隙环境部署、什么都不回传）。
   原文依据：“我们从部署中捕获失败信号和人工纠正，怎么用这些数据取决于客户”；“现场干预（in-situ interventions）可以用几十个样本修好一个边缘 case”。
   落地动作：把每次失败与人工纠正记录下来，按“一个边缘 case → 几十条针对性样本”的粒度做修补，而不是无差别堆数据。

7. **用 fleet learning 做持续改进，并把“性能”作为回传数据的交换条件。**
   前提：非气隙部署、且客户认可收益。
   原文依据：“对非气隙客户，fleet learning 给他们自己的应用带来足够收益，我们通常看不到对贡献数据的抵触”。
   落地动作：原文只说明了这个交换逻辑存在，没有给出协议、脱敏、合规或统计口径的做法。

## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）

**1. 能力发现（AI 已经能做哪些还没想到交给它的工作）**
- 零样本感知：原文称其为 machine tending 做的零样本系统，模型能“定位并识别零件”，基座在超过十亿张图像上训练，因此能区分光照条件、材质类型、物体与背景。
- 生成动作：模型可生成 action chunks 流式送入低层控制。
- 对知识工作的启示：可以先把“识别/定位/分类判断”这类曾经默认要写规则引擎的环节，改成小样本或零样本交给模型；但原文只给了工业场景证据。

**2. 任务匹配（什么工作适合怎样的模型、工具和协作方式）**
- 任务粒度：原文明确公司聚焦**短时域（short-horizon）任务**，以满足生产对节拍和可靠性的要求——这是“什么任务适合模型”的直接判据。
- 模型规模：最大的模型在“低数十亿参数”量级，原文借此强调不追大。
- 人机分工：感知交给模型，运动与工位逻辑交给传统编程。
- 部署形态：训练在云、推理在本地；强调自己掌控机械臂、末端执行器、控制系统与 AI 的全栈，从而能“联合优化模型与控制策略”，并称没有模型是真正硬件无关的。

**3. 条件供给（需要提供哪些信息、工具、权限和反馈）**
- 信息：任务说明（本次要找哪些零件）、示范数据、腕部相机等传感器的原始像素与信号。
- 工具：内部千兆以太网（避免线缆缠绕）、边缘 GPU、仿真器、手持示教触控设备、StandardOS 的 API 与 SDK（开发者可自带模型，例子里提到 NVIDIA Cosmos，但原文说今天仍需开发者自己写集成代码）。
- 权限：数据是否允许回传——气隙部署的国防客户什么都不回传。
- 反馈：部署中的失败信号与人工纠正，粒度是“几十个样本修一个边缘 case”。
- 环境条件：工厂/仓库往往没有可靠外网，uptime 是客户接受的硬门槛。

**4. 主动推进（哪些工作可由时间、事件或状态触发并持续完成）**
- 原文**没有**描述基于时间或状态触发的任务调度、后台代理或自动化触发机制。
- 唯一接近“持续运行”的是 fleet learning：部署 → 捕获失败与纠正 → 回流 → 改进模型，这是一个由**部署事件**驱动的循环，而非定时任务。把它当作“触发源来自线上失败信号”而非“工作流自动化”来读。

**5. 效果验证（怎样判断确实改善了结果）**
- 原文给出的判据是**节拍（cycle time）、可靠性、uptime**，即生产指标而非模型指标，并说“为满足生产要求而对短时域任务的聚焦”正是为此。
- 商业侧的一个间接验证据：客户愿意用回传数据换取性能提升，原文称“fleet learning 给他们自己的应用带来足够收益”。这属于作者/受访者的主张，不是量化证据。
- 原文**没有**给出准确率、成功率、修一个边缘 case 的耗时、数据量-效果曲线等任何可比较的数字。

## 怎么试、怎么验证

**最小试用方式（在软件 agent 场景，1～2 周）**
1. 选一个你已有的、**短时域、高频重复**的工作流，只把它当试验田（对应原文“聚焦短时域任务”）。
2. 按第 1 步划边界：把一个“识别/判断”环节交给模型，其余编排与副作用（写库、发请求、改状态）全部用确定性代码包裹，模型输出必须经过校验才能触发动作。
3. 做一份基线：记录当前流程的完成率、人工介入次数、单次耗时。
4. 建立纠错日志：每一次模型输出被人改过，就把「输入 / 模型输出 / 人工纠正结果」记一条（这正是原文“捕获失败信号与人工纠正”的最小版本）。
5. 每周从日志里挑出重复出现的失败模式，作为边缘 case，各补一组针对性样本或规则（对齐原文“一个边缘 case 用几十个样本”的粒度，不要无差别扩数据量）。
6. 把修好的 case 固化成回归测试，避免回退。

**判断有没有改善的指标（原文给的是节拍与 uptime，这里做对应转写并明确标注为转写）**
- **节拍对应**：单次任务端到端耗时（原文 cycle time）。
- **uptime 对应**：流程可用率 / 失败后可自动恢复的比例（原文 uptime、可靠性）。
- **纠错回流效果**：人工纠正次数随时间的下降斜率、每个边缘 case 从发现到修好所需样本量与轮次。
- **数据效率**：新增样本数与指标提升的比值——用来验证“质量重于体量”在你这里是否成立。
