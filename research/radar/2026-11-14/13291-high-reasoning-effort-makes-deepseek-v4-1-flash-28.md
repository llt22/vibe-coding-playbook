## 是什么

一条推文报告了作者在 Hugging Face Harness Leaderboard 上做的对照实验：用 5 个编码智能体（Claude Code、Codex、OpenCode、Pi、mini-swe-agent），在两个 reasoning effort 档位（low / high）下跑 Terminal-Bench 2.1 与 DeepSWE 的 198 个编码任务，每个智能体在两档各跑 3 次。

结论是两个模型结论相反：

- DeepSeek-V4.1-Flash：成本 +28%，分数没有提升，差异在噪声内（95% CI -1.8 ~ +2.0 点）。作者推测原因是该模型在 low 档每次调用已经用掉约 470 reasoning tokens，high 档只再多 19%。
- GLM-5.3-Flash：同样这 5 个 agent 提升 5.8 个百分点（95% CI +3.5 ~ +8.0），high 档推理 token 比 low 档多 60%。

一句话：reasoning effort 不是一个普遍有利的选项，而是一个需要按模型实测的预算开关，判断依据是 high 档带来的边际推理 token 增量。

1. 选任务集。前提：任务要和你实际要干的活同类；原文用的是编码类基准（Terminal-Bench 2.1 + DeepSWE，合计 198 个任务）。任务数太少时，任何差异都会被噪声淹没。
2. 固定其他变量。同一个 agent 框架、同一套工具权限、同一个模型版本、同样的系统提示，**只改 reasoning effort 一个变量**。原文的 5 个 agent 各自都跑了两档，而不是让不同 agent 分别跑不同档位。
3. 每档每任务重复多次。原文用 3 次尝试（three attempts each），用来抵消采样随机性。
4. 除了分数，同时记录成本和推理 token 消耗。原文的成本数值是 DeepSeek 提档后 +28%；token 数值是 DeepSeek low 档约 470 reasoning tokens/次调用，high 档只比 low 多 19%，而 GLM 是 +60%。
5. 算差值的 95% 置信区间，而不是只看均值。原文把 -1.8 ~ +2.0 判为噪声，把 +3.5 ~ +8.0 判为真实提升，这条判据可以直接照搬。
6. 只有区间下界 > 0 且增益对得起成本时，才把默认档位调到 high；区间跨 0 就保持 low。

一个可直接套用的决策规则（依据原文数据形态，不是原文原文）：

```
若 模型在 low 档的推理 token 已经很高（如 ~470/次）
   且 high 档的边际增量很小（如 +19%）
则 预期 high 档收益落在噪声内 → 保持 low，省下 ~28% 成本
若 high 档的边际增量大（如 +60%）
则 值得做一次小规模对照再决定是否默认升档
```

## 怎么试、怎么验证（最小试用方式和判断有没有改善的指标）

**最小试用**：

1. 从你真实工作里挑 20–30 个有明确对错判据的任务（不必是 198 个，但要能自动或半自动判分）。
2. 选你正在用的模型 + agent 组合，low / high 两档各跑 3 次，其他设置完全一致。
3. 每次记录：是否通过、耗时、总 token、reasoning token、折算成本。
4. 算 high−low 的通过率差值及其 95% 置信区间；算每任务成本增幅和每任务 reasoning token 增幅。

**判断指标**：

- 主指标：通过率差值的 95% CI。跨 0 → 判定为噪声，保持 low。
- 成本指标：每任务成本增幅（原文 DeepSeek 为 +28%）。
- 机制指标：high 档相对 low 档的 reasoning token 增量（原文 DeepSeek +19%、GLM +60%）。若增量很小而 low 档 token 已经很高，预期收益低。
- 性价比指标：每多花 1 单位成本换来的百分点提升。

**判定标准**：CI 下界 > 0 且性价比可接受 → 把 high 设为该模型在该类任务上的默认；CI 跨 0 → 保持 low 并把省下的预算用到别处（换模型、加工具、加反馈环节）。跑完后把结果记进自己的对照表，下次换模型版本时重测，不要沿用旧结论。
