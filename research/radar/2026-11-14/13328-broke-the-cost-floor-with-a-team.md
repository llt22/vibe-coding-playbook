## 具体做法
以下按原文流程整理为可试用步骤；原文未给出的文件语法和提示词需在你的 agent 工具中自行配置，模型名按原文保留、实际使用时替换为可用模型。

1. 前提筛选：只选满足原文三类委派之一的任务——可拆成独立部分、单次会话做不完、含可重复任务。任务能一次做完时不要上多智能体；原文称 plan mode 下 agent teams 的 token 消耗是 solo session 的 7 倍。
2. 建四个 agent 文件，每个文件绑定自己的模型：brain/规划者、builder/构建者、checker/检查者、routine/例行执行者。原文说 Fable 做 brain，Opus 5.5 做 builder，Sonnet 5.5 做 checker，Haiku 5.5 做 routine；这是原文的模型分工，不是已验证的通用选型。
3. 只让 brain 规划、拆分和评判返回结果；brain 只在输入 `/brain` 时运行。builder 只按 brief 构建，不自行改需求；checker 只审查、不编辑；routine 只跑重复任务，且不碰代码。
4. 按原文的交接顺序执行：
```
I describe the job
→ Fable writes the spec at $8 / $40
→ Opus builds at $4 / $20
→ Sonnet reviews at $2 / $10
→ Haiku runs routine at $0.10 / $0.50
→ Builder fails twice, Fable takes over
```
价格对和 80x 成本差是原文主张，未说明计价口径，试用时用你自己的账单核对。
5. brain 委派三类工作：独立部分、单个会话过大的工作、可重复任务；不要把所有任务都拆给多个执行者。
6. 加交接硬约束：同一文件同一时间绝不让两个 helper 同时改；checker 签字后才能算完成；builder 连续失败两次后由 brain 接管。

```
consult the advisor before the approach, on a repeating error, before calling done.
```

8. 运行前明确每个 agent 的文件所有权和可写范围；原文没有给权限配置，需在工具侧用目录/文件白名单或人工审查补上。
