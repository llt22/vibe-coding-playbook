## 是什么
这条线索是一条推文，它转述了 Semgrep CEO 在 Stanford 课程 The Modern Software Developer 上关于“Black October”之后 AI 代码安全的分享。核心主张是：前沿模型已经能找到漏洞并写出可用的 exploit，过去靠“人力稀缺”把攻击成本抬高这道门槛已经消失；逐条追着修 bug 并不划算（已公开漏洞中被实际利用的不到 2%），真正的抓手在预防。原文给出四条措施：

1. 沙箱化 agent：至少放进容器，microVM 是“最佳”；凭据要与 agent 能触达的范围分开。
2. 用确定性 hooks 而不是提示词强制规则：先让 agent 对工具有明确取向（pnpm 而非 npm），再用 hook 强制；拒绝发布时间少于 N 天的包的“依赖冷却”是最便宜、最有效的供应链防御；一个便宜的密钥扫描 hook 胜过告诉 agent“别提交密钥”。
3. 让 agent 交付安全改造而不是只找 bug：给它一个业务风险，让它构建修复，例如把 CI 里每个 GitHub Action 固定到确切版本、删除死代码。
4. 保护新代码：漏洞集中在近期写的代码里，老代码会慢慢变得坚固；Android 没有重写技术栈，而是改变了新代码的写法，报告的漏洞数就大幅下降。

## 怎么试、怎么验证（最小试用方式和判断有没有改善的指标）
最小试用：选一个仓库、一到两周。
1. 把 agent 放进容器或 microVM，容器内不挂任何生产凭据。
2. 只加两个 hook：密钥扫描（命中阻断）+ 依赖冷却（拒绝 N 天内新包），N 先取一个保守值并记录在案。
3. 给 agent 一件“交付型”任务：把 CI 里的 GitHub Action 全部固定到确切版本。
4. 观察指标（试用前后各取一段对比）：
- hook 阻断次数（密钥命中数、被拒的新包数）：应为正，否则说明 hook 没生效或规则太松。
- 逃逸事件数：合并进主干的提交中出现明文密钥、未固定版本的 Action、N 天内新依赖的次数——目标为 0。
- 完成同类任务的时间与人工 review 时长：确认防护没有吃掉 agent 的产出效率。原文主张“修复很便宜”，但没给耗时数据，需要自测。
- 若可测：新写代码上发现的安全问题数（对应“保护新代码”的主张）。

判断：逃逸事件降到 0 且任务耗时没有明显上升，可认为该做法在本团队成立；若逃逸为 0 但人工 review 时间大幅上涨，说明 hook 规则过严或沙箱配置成本过高，需要调整 N 与规则后再试。
