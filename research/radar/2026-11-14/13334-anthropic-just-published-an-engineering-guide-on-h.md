## 是什么

这条推文称 Anthropic 发布了一份关于如何构建 always-on agents（常驻代理）的工程指南，作者把其中的要点提炼为 5 个核心部件，并给出一个反直觉的判断：常驻代理并不是 24/7 一直运行，而是绝大部分时间休眠，短时间被唤醒运行、保存状态后再睡回去。

五个部件分别是：

1. **Event Inbox（事件收件箱）**：在 webhook 和代理之间放一张数据库表。
2. **Timers（计时器）**：计时器单独存表，与收件箱分开；分为一次性跟进和周期性日程。
3. **Lean Memory + Dreaming（精简记忆 + 定期“做梦”）**：只保存无法再次查到的东西；唤醒时只加载一个小索引；周期性清理陈旧事实。
4. **Unattended Permissions（无人值守权限）**：不把明文 API key 放进代理沙箱，改由外部代理注入；用 Deferred Tool Calls 把高风险动作挂起等待审批，而不阻塞 worker。
5. **Outbox（发件箱）**：把对外回复排队，让代理控制通知节奏，而不是在凌晨三点随意发消息。

## 具体做法

原文只给出了架构层面的做法，没有可直接复制的代码或配置。下面按原文描述整理成实现清单，每项注明前提；括号内为实现时必须由使用者自行决定、原文未给出的细节。

1. **给 webhook 加一层收件箱表**
   - 前提：代理由外部事件（webhook）驱动，且同一用户可能短时间收到多条消息。
   - 做法：在 webhook 与代理之间插入一张数据库表；webhook 收到后快速确认（ack）并写入表中，不在请求路径里直接跑代理。
   - 并发约束：每个用户只允许一个活跃 worker，避免多次运行互相碰撞。
   - 合并策略：对快速连续到达的消息做批处理，合并成一次运行。
   - （原文未给：表结构、ack 的超时阈值、批处理窗口长度。）

2. **把计时器独立成表**
   - 前提：任务中存在“稍后跟进”和“周期性执行”两类时间驱动需求。
   - 做法：计时器单独建表，不放进收件箱；区分为一次性 follow-up 和 recurring schedule 两类。
   - 触发方式：后台轮询器（poller）把到期的计时器投递进收件箱，从而复用第 1 步的同一套运行通路。
   - （原文未给：轮询间隔、时区处理、错过触发时的补偿策略。）

3. **把记忆精简到最低限度**
   - 前提：代理会被反复唤醒，且上下文窗口和启动成本有限。
   - 只存四类“无法再查回来”的内容：用户指令、用户笔记、过往消息、任务进度。
   - 唤醒时只加载一个小索引，而不是把所有文件一次性读入。
   - 周期性执行“dreaming”清理：删除或更新陈旧事实。
   - （原文未给：索引形态、清理频率、判定“陈旧”的规则。）

4. **把权限放到代理沙箱之外**
   - 前提：代理在沙箱内运行，且需要调用带密钥的外部 API。
   - 明文 API key 不进入沙箱，由外部代理（proxy）注入凭据。
   - 高风险动作使用 Deferred Tool Calls：先把动作挂起等待人工审批，但不阻塞 worker 继续处理其他工作。
   - （原文未给：代理实现方式、审批超时与降级行为、哪些动作算“高风险”。）

5. **给对外输出加发件箱队列**
   - 前提：代理会主动向用户发通知或回复。
   - 做法：回复不直接发送，先进入发件箱队列，由队列控制发送节奏，避免深夜打扰和消息刷屏。
   - （原文未给：发送窗口、限流参数、优先级规则。）

## 对应的研究问题

- **能力发现**：原文指出一类此前较少被交给 AI 的工作形态，即“被事件唤醒的短跑式持续服务”，包括 webhook 触发的响应、一次性跟进、周期性日程执行、对外通知的节奏控制。这属于“可交给 AI 的工作形态”层面的提示，而不是新能力清单。
- **任务匹配**：给出了一条明确的形态匹配原则：常驻任务不应实现为长时间运行的单次会话，而应实现为“短运行、保存状态、休眠、再唤醒”，并配合每用户单活跃 worker 的隔离方式。对高风险动作，匹配“挂起等审批”而不是“阻塞等待”的协作方式。
- **条件供给**：需要提供数据库表（收件箱、计时器）、外部凭据代理、人工审批通道、精简记忆索引、发件箱队列，以及 webhook 侧的快速 ack 能力。这些都对应“要让代理持续工作，必须先供给什么基础设施”。
- **主动推进**：这是原文最集中的部分。时间触发 = 计时器表 + 后台轮询器投递到期项；事件触发 = webhook 写入收件箱；状态触发 = 用任务进度记录和 dreaming 清理陈旧事实来维持状态一致性。
- **效果验证**：原文没有给出任何指标。只能从架构反推可验证点：运行碰撞是否消失、通知是否集中在合理时段、凭据是否曾出现在沙箱内、陈旧事实是否导致错误回答。这些是推断，不是原文主张。

## 怎么试、怎么验证

**最小试用方式**（不追求全量落地，只验证架构假设）：

1. 选一个单用户、单场景、有真实外部事件的小流程（例如“收到表单提交 → 生成初稿 → 24 小时后跟进一次 → 发送通知”）。
2. 建两张表：收件箱（事件）与计时器（一次性跟进）。写一个轮询器把到期计时器投入收件箱。
3. 强制每用户单活跃 worker，并开启短时间内消息合并。
4. 记忆只保留指令、笔记、消息、进度四类，唤醒时读索引。
5. 把对外凭据放在沙箱外的代理里；给“发送”动作加人工审批挂起。
6. 所有外发消息先进发件箱队列，设定发送时间窗口。
7. 跑 1–2 周，记录下述指标，再决定是否推广。

**判断是否改善的指标**：

- 同一用户的并发运行次数 / 运行碰撞次数（目标为 0）。
- 因重复消息导致的重复回复率（对比合并前后的下降幅度）。
- 计时器到期到实际执行之间的延迟分布，以及漏触发次数。
- 挂起等审批的动作数与平均等待时长，以及 worker 在此期间是否仍在处理其他任务（验证“不阻塞”这一主张）。
- 凭据扫描：沙箱内是否出现过明文凭据（目标为 0）。
- 非预期时段（如深夜）发出的通知占比。
- 因陈旧记忆导致的错误回答或错误动作次数（对照 dreaming 清理前后）。

**注意**：以上指标是依据架构假设推导的验证方案，原文并未给出任何基准值或验收标准，需要自己在试用中建立基线。
