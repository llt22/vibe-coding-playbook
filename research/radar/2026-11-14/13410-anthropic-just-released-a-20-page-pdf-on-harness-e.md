## 是什么

一条推文转述的“Harness Engineering”（智能体外壳工程）落地清单。核心公式 `Agent = Model + Harness`：模型之外的上下文、工具、反馈回路、记忆、权限和日志构成“外壳”，外壳决定同一模型的实际产出。推文称，LangChain 在同一模型、同一基准上只改外壳，得分从 52.8% 提升到 66.5%；并称 OpenAI 用这套方法做出约 100 万行代码、0 行手写。六个步骤构成一条可操作的 checklist：guides（仓库地图）→ sensors（自动检查）→ loop（计划-构建-验证-修复）→ memory（特性清单/进度日志/一任务一提交）→ permissions（放行循环命令、禁密钥、闸门不可逆操作）→ traces（日志与失败分类）。

注意：材料只有推文正文，文中提到的 20 页 PDF 内容未提供，上述数值与案例均为推文转述，不是原文一手数据。

## 具体做法

前提（六步共同的落地条件）：有一个能跑 lint / 类型检查 / 测试的代码仓库，并已接入可执行命令的编程智能体。缺任一前提，第 2、3、5 步没有执行对象。

1. **写 guides：把仓库地图交给智能体。** 在仓库根目录建一个约 100 行的 `AGENTS.md`，内容定位是“地图”而不是“手册”：代码在哪、模块边界、怎么跑、什么不能碰。前提：仓库结构相对稳定；结构常变时这份文件会过期，需要随目录调整同步更新。

   以下骨架是依据推文第 1 步描述补写的示例，原文未给出具体文本，需按自己仓库改写：

   ```markdown
   # AGENTS.md
   ## 目录地图
   - src/api/    HTTP 入口，改这里要同步 src/api/__tests__
   - src/core/   业务逻辑，无 IO 依赖
   - scripts/    一次性脚本，不参与构建
   ## 怎么跑
   - 安装：<命令>
   - 单测：<命令>（改完必跑）
   - 类型检查 / lint：<命令>
   ## 硬约束
   - 不要改动 <目录/文件>：<原因>
   - 不提交密钥；不执行 <不可逆操作>
   ```

2. **加 sensors：每次编辑都跑自动检查，并把修法写进错误信息。** 把 lint、类型检查、测试挂在每次编辑/每次提交上自动执行；关键是错误信息里直接给出“怎么改”，而不只是“哪里错”。前提：已有可自动判定的检查；没有测试的项目要先补最基本的冒烟测试，否则这一步只有 lint 一层。

3. **塑造循环：plan → build → verify → fix，并让智能体用证据证明“做完了”。** 规则是：不接受自我声明的“done”，必须贴出验证输出（测试通过记录、命令回显、复现步骤）。前提：验证命令是确定性的、可重放的；否则“贴证据”会退化成贴一段文字。

   以下提示词是依据第 3 步描述补写的示例，原文未给出模板：

   ```text
   按 plan → build → verify → fix 推进。
   每一步先写出计划，再改代码。
   在宣布完成之前，必须粘贴 verify 步骤的真实命令输出。
   没有输出证据的“已完成”一律视为未完成。
   ```

4. **给记忆：特性清单 + 进度日志 + 一任务一提交。** 维护一份功能清单（要做什么、做到哪），一份进度日志（每轮做了什么、卡在哪），并且一个任务对应一次提交，便于回滚与定位。前提：任务是可拆分的；单次任务过大时这条会失效。

5. **设权限：放行循环所需命令、禁止读取密钥、对不可逆操作设闸门。** 第 3 步的循环会反复执行命令，这些命令走白名单；密钥类文件（如 `.env`、凭证）明确禁止读取；无法撤销的操作（推主干、部署、数据迁移、批量删除）单独设人工确认闸门。前提：工具支持命令级/路径级权限控制。

6. **读 traces：记录每次运行、给失败分类、一次只改一处。** 每次运行都留下日志（做了什么、跑了什么命令、在哪失败），把失败归类成少数几类（如：上下文缺失、命令不存在、测试不稳、方向理解错），每轮只改一个变量再观察。前提：有地方存日志，并且有人真的定期读。

## 对应的研究问题

- **能力发现（AI 还能接管什么）**：推文称智能体可自主完成“计划-实现-验证-修复”闭环，并称 OpenAI 以约 100 万行、0 行手写的规模产出。这提示可交出去的不只是“写代码片段”，而是包含自检与返工的完整任务单元。此为转述主张，无一手细节。
- **任务匹配（什么工作配什么模型/工具/协作方式）**：核心论点是“同一模型、只改外壳，分数 52.8%→66.5%”，即产出差异有很大一部分来自外壳配置而非换模型。这为“先调外壳、再换模型”的取舍顺序提供了依据（单一数据点）。
- **条件供给（要给什么信息、工具、权限、反馈）**：这条线索最扎实的部分——上下文（AGENTS.md 仓库地图）、工具（lint/类型/测试）、反馈（错误信息内嵌修法）、记忆（特性清单与进度日志）、权限（白名单/禁密钥/不可逆闸门）、可观测（运行日志）。六项都以“缺了会怎样”的方式给出。
- **主动推进（时间/事件/状态触发并持续完成）**：部分相关。“每次编辑即触发检查”是事件触发，“不许自称 done 直到贴出证据”是状态门控。但推文未给出定时调度、任务队列、跨会话续跑等机制，长时程自主推进没有依据。
- **效果验证（怎么判断真的改善）**：给出两条可操作做法——用证据（verify 输出）代替声明；用日志+失败分类+单变量改动做归因。基准分数对比是唯一的量化示例。

## 证据与局限

- 给出的数据/案例：LangChain 同模型同基准 52.8%→66.5%；OpenAI 约 100 万行产品、0 行手写。均为推文一句话转述，未给基准名称、任务类型、评测口径、时间跨度，无法核验。
- 属于作者主张而非证据的：六步清单本身的有效性、“外壳比模型更关键”的普适程度，都没有对照实验支撑。
- 材料层面的局限：只有推文正文，声称的 20 页 PDF 不在材料中，因此没有任何可直接复制的命令、配置、提示词原文。本报告中的模板均为按步骤描述补写，使用时须自行改写。
- 适用条件：仓库具备自动可判定的验证信号（测试/类型/lint）；任务可拆分为单次提交粒度；工具支持命令与路径级权限。对没有确定性验证信号的领域（设计、策略、写作文案），第 2、3 步难以照搬。
- 规模存疑：1M 行、0 行手写属于极端宣称，未说明人工介入比例与返工量，不宜作为预期基线。

## 怎么试、怎么验证

**最小试用（1–2 周，单仓库）**
1. 选一个测试覆盖尚可的仓库与一类重复性任务（如修 bug、加小功能），挑 10–15 个历史任务作为固定测试集。
2. 先跑基线：用现有方式（无 AGENTS.md、无强制证据）完成这批任务，记录指标。
3. 再按六步依次加：AGENTS.md → 检查挂到每次编辑 → 强制贴证据 → 特性清单/进度日志/一任务一提交 → 命令白名单与密钥禁用、不可逆闸门 → 运行日志与失败分类。每加一步只观察一轮，避免同时改多项。
4. 用同一批任务重跑，对比指标。

**判断有没有改善的指标**
- 首次通过率：一次交付即通过测试与评审的任务占比。
- 平均往返轮次：从下任务到“有证据的完成”所需轮数/时长。
- 人工返工次数与返工原因分布。
- 逃逸缺陷数：合并后才发现的问题数（这是“不许自称 done”是否真的生效的关键指标）。
- 失败分类分布的变化：如果上下文缺失类失败明显下降，说明 AGENTS.md 起了作用；如果集中在“命令不存在/权限被拒”，说明第 5 步配置需要调整。
- 成本侧：每任务 token 与耗时，避免用 3 倍成本换 5% 提升。

**判定标准**：首次通过率与逃逸缺陷数同向改善、且成本增幅可接受，才认为这套外壳值得固化；只有速度提升而逃逸缺陷上升，说明“证据门”只是形式。
