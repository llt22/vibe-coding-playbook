## 是什么

一条 X 推文，转述（并声称）OpenAI 内部运行 500+ 个后台自主 Agent 的做法：这些 Agent 会从产品反馈直接开 PR、跑数据实验。作者主张这套设置与任务类型无关，编码、研究、支持、数据任务共用一套。核心规则是一句话：**Agent 以及它写出的任何代码都视为不可信，只有纯确定性代码可信**。

围绕这条规则给出六点架构：配置 Agent 的网关与 Agent 本体分属不同集群；Agent 在沙箱内工作，联网只走白名单、只能写自己的目录、碰不到 `~/.ssh`；密钥放在凭证代理里，Agent 永远看不到 token；每个动作由第二个 Agent 复核，人类只审批高价值项；每个 Agent 有独立身份与独立推理凭证，可审计、可单独切断推理；每次配置变更和每一轮 Agent turn 都写日志。

## 具体做法

原文给出的是一组原则而非可直接执行的步骤，以下是把它翻译成可操作形态的方式；每条都标注了前提，并说明哪些是原文明确说的、哪些是我基于原文做的展开。

1. **控制面与执行面分离**（原文明确）
   - 前提：你有能力把服务部署到两个独立集群/命名空间。
   - 做法：负责下发配置、注入身份的“网关”不要和 Agent 运行时同集群；Agent 运行环境不应有权限修改自己的配置。

2. **给 Agent 一个受限沙箱**（原文明确）
   - 前提：沙箱能配置出网白名单与文件写入边界。
   - 三条边界：出网只走 allowlist；写操作只能落在自己的目录；不挂载 `~/.ssh` 之类的主机凭证目录。
   - 原文给的落地方式是“把 allowlist 换成你的 Agent 实际需要的站点”，即从默认拒绝出发，逐条添加，而不是先放开再收紧。

3. **凭证托管：Agent 不见 token**（原文明确）
   - 前提：有一个能代为调用外部服务的凭证代理（credential broker）。
   - 做法：真实密钥只存在于代理侧，Agent 侧拿到的是受限的、可撤销的调用能力；Agent 的上下文、日志、代码里都不应出现明文 token。

4. **二次审查：第二个 Agent 复核每个动作**（原文明确）
   - 前提：有一个能读取动作/变更内容的复核 Agent。
   - 做法：由复核 Agent 过滤掉绝大多数低风险动作，只把高价值项推给人。原文给的理由值得记：让人对每一条都点“allow”，人会进入自动驾驶式点击，审批就失效了。

5. **身份与推理凭证隔离**（原文明确）
   - 前提：推理调用可以按主体签发凭证。
   - 做法：每个 Agent 一套独立身份 + 独立推理凭证，与操作者本人的凭证分开；由此可以做到“逐动作可审计”和“单独关掉某个 Agent 的推理”。

6. **全量日志**（原文明确）
   - 做法：配置变更 + 每一轮 Agent turn 都留痕。

原文给出的“照抄”路径只有一句：在 Codex 里用图片中的配置运行 Agent、替换 allowlist、打开 auto-review。**该配置图片不在材料中**，所以这一段无法还原成可复制的命令或配置文件；原文另一条建议“把这条推文发给你的编码 Agent，让它带你完成设置”属于使用建议，不是步骤。

## 怎么试、怎么验证

**最小试用（一两周，单点）**：
1. 选一个低风险仓库和一个明确任务类型（例如“从 issue 生成修复 PR”），只放 1 个后台 Agent。
2. 只做原文中成本最低的四条：出网白名单默认拒绝、只能写工作目录、不挂载 `~/.ssh` 与个人凭证、每轮 turn + 每次配置变更写日志。
3. 凭证先用只读/可撤销的代替真实密钥，Agent 侧不出现明文。
4. 加一层复核（先用人或脚本扮演“第二 Agent”），记录它拦下了什么。
5. 明确一个 kill switch：能单独停掉该 Agent 的推理调用。

**判断有没有改善的指标**（全部可在本地测，不需要原文数据）：
- 越权尝试被拦截数：白名单/写入边界实际触发次数（0 说明边界没生效或任务太窄，需要检查）。
- 人工审批量：单任务平均需要人工点“通过”的次数，目标是下降而返工率不上升。
- 审批质量：抽查被人工放行的动作中，事后需要回滚的比例。
- 可审计性：随机抽 3 个已完成的 Agent 任务，能否仅凭日志完整重放“谁触发、做了什么、改了哪些文件、用了哪些外部调用”。
- 结果质量基线对比：同一任务类型，Agent 产出的 PR 合并率 / 返工次数，与人工或旧流程对比。
- 事故半径：任一次误操作影响到的最大范围（应被限制在单仓库/单目录）。

若“可审计性”这一项做不到，这套做法就没有被真正复制，其余指标也不用看。
