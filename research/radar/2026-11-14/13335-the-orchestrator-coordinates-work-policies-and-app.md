## 是什么

原文描述的是一套“可控代理平台”的分层结构，核心主张是一句话：编排层决定做什么，策略/审批层决定是否允许，任何真实工具调用必须同时穿过这两层。

原文列出的结构如下（按原文顺序）：

```
入口：用户 / 聊天 / Slack / API
  → agent gateway
  → agent orchestrator（plan → act → observe）
       输入四类：
         1) 身份与认证（SSO、OAuth、scopes）
         2) agent registry（定义、提示词、版本）
         3) LLM router（reasoning / fast / fallback）
         4) memory service（Redis、向量库、偏好）
       职责：上下文管理、委派、重试、恢复
  → 权限引擎（逐动作检查、最小权限、读/写分级）
       三分支：allowed → 直接执行
               needs approval → 人工审批（批准/拒绝、超时升级）
               denied → 拒绝并终止，永不触达工具
  → 授权工具执行
       tool registry（schema、发现、限流）
         → MCP gateway（server 认证、代理、响应清洗）
              → MCP servers：GitHub、Jira、数据库
       code sandbox（隔离容器、时间与资源限制）
       工具结果回传编排器 → 平台回复用户

支撑设施（横跨三层）：
  任务队列 / 持久化作业（Kafka、Temporal）
  追踪与可观测（步骤、成本、replay；OpenTelemetry、Langfuse）
  evals 与 guardrails（输出检查、注入防御、回归测试）
  审计日志（活动与事件）
```

本质上它讲的不是某个产品，而是一条“控制面与执行面分离”的架构原则：模型可以自由规划，但规划结果必须先变成“待审动作”，由与模型无关的策略层裁决。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

**前提说明：原文没有给出任何命令、配置文件、策略语言或提示词模板，只有分层清单与组件命名。** 因此下面不是原文的可执行步骤，而是把原文的结构主张转成“自建时的落位顺序”；每一层内部的具体规则需要自行设计，原文未提供。

1. **先设入口网关。** 前提：存在多个入口（聊天、Slack、API）。所有请求统一进 agent gateway，再进编排器，避免绕过控制层。
2. **建编排器，只负责“下一步做什么”。** 前提：已有可用的模型与工具清单。编排器执行 plan → act → observe 循环，并负责上下文、委派、重试、恢复。原文强调它不负责判断“允不允许”。
3. **给编排器配四类输入。** 前提：需要有身份系统与提示词版本管理。①身份与认证（SSO、OAuth、scopes）；②agent registry（定义、提示词、版本）；③LLM router（reasoning / fast / fallback 三种档位）；④memory service（Redis、向量库、偏好）。
4. **在编排器和工具之间插入权限引擎。** 前提：能枚举出所有“动作”。对每个提议动作做逐动作检查，按最小权限与读/写分级裁决，输出三分支：直接放行、转人工审批、直接拒绝。拒绝的分支必须在到达工具前终止。
5. **给审批分支定规则。** 前提：有可承接审批的人或队列。原文只给了形态：批准 / 拒绝 / 超时升级（timeout and escalate），未给超时时长与升级对象。
6. **工具执行走注册表 + 网关。** 前提：工具有 schema 且需要限流。经 tool registry（schema、发现、限流）→ MCP gateway（server 认证、代理、响应清洗）→ 具体 MCP server（GitHub、Jira、数据库）。
7. **代码执行放进沙箱。** 前提：需要跑模型生成的代码。用隔离容器，并设时间与资源上限。
8. **工具结果回传编排器再回复用户**，不要让工具直接对用户说话，否则审计链断裂。
9. **铺支撑设施。** 任务队列与持久化作业（Kafka / Temporal）；追踪与可观测（步骤、成本、replay；OpenTelemetry / Langfuse）；evals 与 guardrails（输出检查、注入防御、回归测试）；审计日志。

原文给出的唯一硬性约束可以当作验收条件：**没有同时通过编排层与权限层的动作，不得触达任何真实工具、GitHub、Jira 或沙箱容器。**

## 怎么试、怎么验证

**最小试用方式（不引入原文的整套基础设施）：**

1. 选一条已有的、会调用外部工具的代理流程（例如“读工单 → 改工单状态”）。
2. 只在工具调用前加一层前置检查：把动作按读/写分级，写操作默认进“待审批”，读操作默认放行，明确越权的直接拒绝。
3. 记录每次裁决：动作、级别、裁决结果、审批人、等待时长。
4. 跑两周，只观察不优化，再决定是否扩到第二条流程。

**判断有没有改善的指标：**

- 未授权工具调用次数（目标为 0，这是硬指标）；
- 被拦截动作中“确实不该执行”的比例（衡量误拦，过高说明分级太粗）；
- 审批平均等待时长与超时升级次数（衡量人工环节是否成为瓶颈）；
- 出问题后定位到具体步骤所需时间（对应原文的 replay / 追踪主张）；
- 单次任务成本与步骤数（原文点到的两个可观测维度）。

**证伪条件：** 如果两周内拦截率接近 0 且没有一次真实阻止了错误动作，说明当前场景不需要这层闸门，应退回更轻的做法；如果误拦率过高导致人工审批排队，说明分级规则需要重做而不是加更多层。
