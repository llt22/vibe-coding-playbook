## 是什么

一条推文给出的“增量生长个人 wiki”工作流骨架：不再用 AI 逐次答题，而是用 AI 把你读过的材料沉淀成一个持续变大的本地知识库，再由这个库回答问题。

组件只有三个：

- **Obsidian vault** 作为本地仓库和浏览界面；
- **Claude Code** 作为读写该目录的 agent；
- **一个根目录 CLAUDE.md** 作为 agent 的行为规则。

目录按用途分三层：`raw`（原始素材）、`wiki`（agent 写的笔记）、`outputs`（回答产出）。日常动作只有两个：把文章剪藏进 `raw`；让 agent “ingest the new sources”。每周额外做一次“找矛盾”。

原文对机制的描述是：agent 读新素材 → 写笔记 → 与既有笔记建立链接 → 归档；作者强调“不用打标签、不用分类、没有死笔记”。

## 具体做法

以下按原文顺序列出，并标注每步的已知前提与缺口。**原文没有给出 CLAUDE.md 的任何内容，也没有给出“完整分步指南”正文**（推文只说 “Full step-by-step guide with Claude and Obsidian below”，采集文本到此为止）。

1. **安装 Obsidian 并新建一个 vault**
   前提：本地已装 Obsidian。用途是获得一个纯 markdown 目录 + 可浏览的界面。

2. **在 vault 根目录建三个文件夹**

   ```
   <vault>/
   ├── raw/      # 原始素材（剪藏进来的文章、论文、thread、播客笔记）
   ├── wiki/     # agent 写的笔记
   ├── outputs/  # 回答产出
   └── CLAUDE.md # agent 的运行规则
   ```

3. **在根目录放一个 CLAUDE.md，告诉 Claude 这个 wiki 怎么运转**
   前提：需要你**自己写**这份规则。原文只说明“它存在且规定 wiki 如何运行”，未给出任何一行内容。这是整个流程的真正核心，也是最主要的缺口。

4. **用 Obsidian Web Clipper 把文章剪进 `raw/`**
   前提：浏览器装 Web Clipper 插件。采集动作由人做，消化动作交给 agent。

5. **对 Claude Code 下指令，让它处理新素材**
   原文的触发语原样如下，可直接复制：

   ```
   ingest the new sources
   ```

   预期行为（据原文描述）：读取 `raw/` 中的新文件，在 `wiki/` 写笔记，把新笔记与之前保存的内容互相链接，然后归档。注意原文**没有**说明 agent 如何判断“新”（是否维护已处理清单、是否按 mtime、是否移动 raw 文件），这一步需要自己在 CLAUDE.md 里定义。

6. **就整个库提问**
   原文表述为“Ask it anything about everything you saved”，未给具体提问模板。

7. **每周让它找矛盾**
   原文表述：“once a week let it hunt for contradictions”。未给指令原文、未给输出格式、未给结果写到哪里（推测应落到 `outputs/`，但这是推测，原文未说）。

## 对应的研究问题

- **能力发现**：把两件人通常不会做的事交给 AI——(a) 每读一篇就顺手整理并与旧知识互链；(b) 跨全部历史材料做矛盾排查。第二件事尤其符合“还没想到交给 AI”的特征：人工几乎不可能周期性重读全部旧笔记找冲突。
- **任务匹配**：agent 型工具（Claude Code，可读写本地文件系统）负责消化与链接；Obsidian 这类本地 markdown 仓库负责采集入口和浏览。协作分工是“人剪藏、agent 消化、人提问”。原文只点了工具名，未讨论模型选择或失败模式。
- **条件供给**：明确给出最小上下文供给集合——目录约定（raw/wiki/outputs）、根目录规则文件（CLAUDE.md）、素材采集通道（Web Clipper）、以及一句固定触发语（`ingest the new sources`）。这正是“条件供给”问题的一个干净样例。
- **主动推进**：有两处触发点——“有新素材时”触发 ingest（状态/事件触发），以及“每周”触发矛盾排查（时间触发）。但原文**只说了频率，没有给任何自动化实现**（未提 cron、hook、watcher、CI），目前仍需人手动发起。

## 怎么试、怎么验证

**最小试用**：一个主题、一周、10–20 篇素材。建一个目录（可不用 Obsidian），写一份最小 CLAUDE.md 规定：`raw/` 只读、`wiki/` 一源一笔记、笔记需显式链接相关旧笔记、已处理素材记入清单文件、`outputs/` 存放回答与每周矛盾报告。每周跑一次 ingest + 一次矛盾扫描。

**基线对照**：同一批素材，只用“把全文丢给模型直接问”的方式回答同一组问题。

**指标**：

- 回溯命中率：对 10 个需要跨 3 篇以上素材才能回答的问题，两种方式答对的比例；
- 孤立笔记比例：`wiki/` 中没有任何入链的笔记占比（检验“没有死笔记”是否成立）；
- 链接质量抽查：随机 10 条链接中真正相关的比例；
- 矛盾排查产出：每周报告中被人工判定为有效冲突的条数（区分真冲突 / 模型误报）；
- 成本：单篇 ingest 的实际耗时与 token 开销，对比人工整理同篇的耗时；
- 留存：30 天后 `wiki/` 中仍被后续回答引用到的笔记占比。

**判断改善**：只有当回溯命中率明显高于基线、且孤立笔记比例随时间下降时，才认为这套增量 wiki 真的在起作用；若链接质量抽查低于可接受水平，说明需要先补 CLAUDE.md 里的链接规则，而不是扩大素材量。
