## 是什么

原文主张把「不可遗漏的动作」从**专案规则档**（写在规则档里的自然语言指令，模型可能跳过）迁移到 **Claude Code 钩子**（挂在流程固定点上的小程式，事件一到就一定执行，执不执行不由模型决定）。作者自己的场景：每次发布都要到 X、领英、蓝天三个平台手动写公告，经常漏掉其中一个；挂上钩子后三个平台一次都没漏过。

钩子的组成被拆成三样东西：

- **事件**：触发的时间点，例如「工具呼叫后」
- **匹配器**：把范围缩到某一种工具，例如只管命令列工具
- **处理器**：真正跑的东西，可以是一段指令、一通网路请求或一段提示词

钩子写在设定档里，按作用域分三种：**全域**（管全部专案）、**专案共用**（管全队、进仓库）、**个人专用**（只管自己、不进仓库）。

作者还给出了一条必须说清楚的边界：**钩子只看得见 Claude Code 自己做的事**，你自己在终端机敲的指令、持续整合（CI）跑的发布，它一概看不见。

## 具体做法

原文给出的是流程级步骤，没有给出任何可直接复制的代码、设定档片段或事件名，下面是原文明确写到的部分；括号内标注了每步的前提。

1. **接好发文排程工具，并把该工具的呼叫能力加进 Claude Code。**（前提：你有一个能排程发文的工具，且 Claude Code 能呼叫它。）
2. **写一支「发布提醒脚本」**，职责被明确限定为两件事：
   - 从钩子传入的事件资料里抓出版本号；**抓不到就安静退出**（不打扰、不报错刷屏）；
   - 抓到了就**回传一段提醒文本**，内容是叫 Claude Code 先读发布说明，再帮 X、领英、蓝天各写一篇公告，**存成草稿、不要排时间**。
   （前提：事件资料里带得到版本号；脚本对「没有版本号」的情况必须做静默处理，否则每次工具呼叫都会误触发。）
3. **在专案共用设定档里加一条「发布后触发」的钩子规则**，匹配器**只认建立发布那条指令**。（前提：用共用设定档而不是个人档，才能全队生效。）
4. **挂上去之前先喂假资料测一次**：不用真的发布，喂一笔假的事件资料给脚本，检查回传文字里的版本号对不对。
5. **挂好之后在钩子选单里确认规则还在**，再跑一次真发布验全程。
6. 预期的一次完整流程（原文描述的验收画面）：你只说一句「帮我打上 2.4 版标签、照更新日志建立发布」→ Claude Code 跑完指令 → 钩子立刻提醒它读说明、写三篇公告、存进排程工具 → 你打开工具、看过、排时间。**没有一篇是没经过你眼睛就发出去的。**

### 第二条路：钩子直接呼叫发文工具介面

不想让模型插手文案时，可以让钩子直接呼叫发文工具的 API 存一篇简短草稿：连结跟版本号**写死**在请求里，请求带上**用版本号组成的防重复键**，这样同一版本发布两次也不会重复建草稿。

原文给出的选型判据：

- 要文案品质、要人把关 → **提醒型**（钩子回传提示词，模型写稿存草稿）；
- 要稳定、不要模型插手 → **直呼介面型**（钩子直接建草稿）；
- 不想写脚本 → 写规则叫子代理写公告，**但模型可能跳过**，等于回到原点。

### 另外两条防呆（原文举例，可同法复制）

- **挡下强制推送**：在呼叫前拦下，认到那条指令就回传「挡下代码 + 理由」。
- **贴文品管**：建立贴文之前先检查禁用词与字数，超标就挡下。

### 分工原则（原文的核心判据）

> 规则是建议，钩子是保证。**一次都不能漏、一次都不能错**的事才值得挂钩子。

原文建议的起步动作：打开专案共用设定档看一眼，没有钩子的话，先挂一条「强制推送挡下」规则再说（这条风险最低、不依赖外部服务）。

## 对应的研究问题

**1. 能力发现（AI 已能做、但没想到交给它的工作）**
原文点出了一类很少被交出去的工作：**发布之后的收尾事务**（公告撰写、多平台分发、草稿归档）。这类工作不是「做不出来」，而是「忙起来就被跳过」，因此被长期留在人手上。

**2. 任务匹配（什么工作适合什么模型/工具/协作方式）**
原文给了一条清晰的切分线：**确定性、不可遗漏的触发与检查交给钩子（脚本、网路请求）**；**需要文案品质的生成交给模型**；**最终发布权留给人**（只看草稿、由人排时间）。并明确对比了三种协作方式（提醒型 / 直呼介面型 / 写规则叫子代理）在「稳定 vs 品质」上的取舍。

**3. 条件供给（需要哪些信息、工具、权限、反馈）**
- 工具：发文排程工具及其 API、Claude Code 的钩子机制；
- 信息：事件资料中必须能取到**版本号**，发布说明/更新日志必须可被读取；
- 权限：钩子需要能执行指令、发网路请求；设定档需放在**专案共用**位置才能全队生效；
- 反馈：钩子回传的提醒文本本身即反馈；「钩子选单里确认规则还在」是一种人工巡检反馈。

## 怎么试、怎么验证

**最小试用（建议分两步，先零风险后真实场景）**

1. 第一步（不依赖外部服务）：在**专案共用设定档**里挂一条「强制推送挡下」钩子，匹配器只认强制推送那条指令，处理器回传挡下代码和理由。跑一次，确认被挡下且理由可读。
2. 第二步（真实场景）：接好发文排程工具，写发布提醒脚本，只做「抓版本号 / 抓不到静默退出 / 抓到回传提醒」三件事；匹配器只认建立发布那条指令。
3. **干跑**：喂一笔假的事件资料给脚本，检查回传文字里的版本号是否与假资料一致、以及无版本号时是否真的静默。
4. 在钩子选单确认规则仍在，再跑一次真发布，走完整流程到「草稿已生成、待人工排时间」。

**判断有没有改善的指标**

- **漏发率**：一段时间内「发布次数」与「三平台都生成草稿的次数」之比，对照上线前的手工基线；
- **误触发率/假阳性**：非发布类工具呼叫触发提醒的次数（目标为 0，靠匹配器和静默退出保证）；
- **误挡率**：防呆钩子挡下正常操作的次数（过高说明匹配器写得太宽）；
- **人工补写次数**：上线后仍需人手补写公告的发布次数；
- **时延**：从发布完成到三篇草稿可审阅的时间；
- **人的动作量**：每次发布需要人工记住的步骤数（应从「记得写三篇」降为「审三篇、排时间」）。

**建议的止损条件**：若干跑阶段发现事件资料里取不到版本号，或团队发布由 CI 驱动导致钩子根本不触发，应判定本方案不适用，退回「写进规则档 + 人工检查清单」，不要为了挂钩子而改发布流程。
