## 是什么

这条线索讲的是 Google Antigravity（Pro / Ultra 可用）上线的 Dynamic Workflows（入口命令 `/run-workflow`）。它的核心做法不是用自然语言长对话去指挥一群子 Agent，而是让主 Agent 先产出一段 Python 脚本，把**并发、先后顺序、交接格式**写死成确定性代码，人先审代码再放行执行；跑通后可存成 `.py` 文件复现。

推文把它定位为与“多 Agent 自由群聊”相对的另一条路线：把控制流从 prompt 里搬回代码里。这是作者的观点表述，不是官方结论。

## 具体做法

以下步骤全部来自推文对官方文档的转述，原文没有给出完整脚本示例，因此只能列出动作骨架与出现过的字面标识，不要当作可直接运行的代码。

1. **前提**：使用 Antigravity，账号为 Pro 或 Ultra 档；工作对象是代码库，需要 Git。
2. **提需求，不要让它直接动库**。原文明确：Agent 收到需求后不直接改仓库，而是先生成一个 Python 脚本，弹窗请人审查。
3. **审脚本的控制流**。检查脚本里是否用了两个编排原语：
   ```text
   parallel()   # 并发分支
   pipeline()   # 顺序/流水线阶段
   ```
   原文只说脚本“包含 parallel() 与 pipeline()”，没有给出参数签名，具体用法需查官方文档再确认。
4. **执行，让子 Agent 在独立会话里干活**。每个子 Agent 自己翻文件、查代码、跑报错日志，这些都留在主会话之外。
5. **约定交接格式**。子 Agent 只按预设的 JSON Schema 把干净结果交回脚本，主窗口上下文不被污染。Schema 的具体字段原文未给。
6. **按任务分配模型**。可以在脚本里给不同子任务指定不同模型，例如用轻量的 flash 并发扫几十个文件以节省配额。
7. **并发写代码时做 Git 隔离**。多个 Agent 同时改代码跑测试时，在脚本里设置：
   ```text
   workspace="branch"
   ```
   它描述的效果是自动为每个 Agent 切出独立 Git worktree，互不踩踏。
8. **保留跨阶段状态做复查**。同一个找 bug 的 Reviewer Agent 可以保留状态，等并发的 Fixer 修完后被叫回来逐一验收。
9. **存盘复用**。跑通后把脚本存成 `.py`，下次一行命令精确复现，不用重新“抽卡”。
10. **迁移旧资产**。旧版“单个 Markdown 文件工作流”已被官方标记废弃，需通过 `/migrate-workflows` 转成 Agent Skills。

## 怎么试、怎么验证

**最小试用（不依赖该工具也能先验范式，能开通则直接验）**

1. 选一个中等规模仓库和一个可拆分的真实任务（例如“跨 N 个文件排查同一类缺陷”）。
2. 只读阶段：让主 Agent 输出编排脚本骨架（并行扫描分支 + 汇合阶段 + 交接用的 JSON 字段清单），**人审后再跑**，全程不写仓库。
3. 观察交接质量：子 Agent 返回是否严格落在 Schema 内、主会话上下文是否明显变干净。
4. 写入阶段：对少量文件启用 `workspace="branch"`（或自建等价 worktree 隔离），让多个 Agent 改代码并跑测试，再由保留状态的 Reviewer 逐一验收。
5. 固化：把跑通的脚本存成文件，第二次同类任务只用脚本复现，记录是否需要重新调 prompt。

**判断有没有改善的指标（都可直接从执行记录里取）**

- 主会话上下文规模 / token 消耗，与“长 prompt 群聊”基线对比；
- 同一任务的脚本复用次数，以及复现时人工干预次数；
- Reviewer 打回率：子 Agent 结果被验收退回的比例（衡量交接 Schema 是否够严）；
- 并发阶段的冲突/返工次数（衡量 worktree 隔离是否生效）；
- 端到端完成时间，以及最终 diff 被人工接受的比例（衡量是否真的改善了结果，而不只是流程更整齐）。

若第 2、3 步在只读阶段就拿不到干净的结构化交接，说明该范式在你当前工具条件下尚不成立，停在 study。
