## 是什么

材料是 X 上一条推文，转述 AWS 发布的一套「可插拔 agent 参考架构」（七层，配套电商售后参考实现），作者认为它类似 dsh 的插件化理论。

它针对的问题很具体：多 agent 原型演示顺利、上生产就出问题，原因是原型阶段把**模型名称、子 agent 调用地址、数据库查询逻辑**全写死在业务代码里；等到要换小模型控成本、过安全合规、或排查线上故障时，任何一处改动都会牵动别处。

解法是把智能体系统拆成七个插件化的层，层与层之间只通过**固定的接口契约 + 配置中心**通信，换掉任何一层组件都不影响其他模块。推文只具体展开了其中三层的内容（数据与推理层、编排层、网关/可观测），其余层未点名说明。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

> 说明：材料中**没有任何可复制的命令、配置文件或提示词**，以下是把推文描述还原成可执行动作的顺序，具体参数需回到原博客/仓库确认。

1. **前提：先把现状盘点清楚。** 列出业务代码里所有硬编码的模型名、子 agent 地址、数据库/知识库查询入口。没有这份清单，后面拆层无从下手。
2. **把模型接入抽象成统一推理接口。** 不让后续 Agent 直接绑定某家厂商的 SDK，在底层「数据与推理层」用 LiteLLM 做一层统一推理接口。前提：现有代码里存在多处厂商 SDK 直连调用。
3. **把可变项注册到配置中心。** 把当前启用的模型 ID、退货政策知识库 ID 等写入配置中心（推文用的是 AWS SSM）。
   效果（推文主张）：换轻量模型、或把推理后端从 AWS 原生服务换成第三方托管，只需在配置层改一个字符串，上层智能体代码一行不动。
4. **用工信注册表替掉总 agent 里的硬编码地址。** 各专职子 Agent 部署后自己往注册表登记能力；总 Agent 收到请求时通过运行时 harness 动态去注册表发现可用子 Agent，并用 A2A 协议派发任务。前提：需要先定义好「能力登记」的字段和 A2A 的调用契约。
5. **把所有底层工具调用收口到统一网关。** 子 Agent 查数据库/知识库一律走网关，由网关做精细权限校验，而不是让每个子 Agent 自己持有凭据。做完这步，子 agent 的增删改才成为热插拔。
6. **在网关上挂拦截器做脱敏。** 工具返回的数据（订单详情里的真实邮箱、电话、家庭住址）在送达总控大模型**之前**，先在网关被拦下、自动打码脱敏，再交给上层继续推理。推文给出的理由是防隐私泄露和提示词注入。
7. **打通全链路追踪。** 因为所有跨层调用都遵循统一接口，分布式追踪可以把一次对话从前端入口 → 总控分发 → 网关拦截 → 数据库查询的耗时和 Token 账单完整串起来，用于判断问题出在知识库没召回、模型算错日期，还是别处。

## 怎么试、怎么验证

**最小试用（不改架构，只做两件事，各一周内可完成）：**

1. 在现有 2–3 个子 agent 的原型上，把模型 ID 与知识库 ID 抽到配置（环境变量或配置中心均可），跑一次「换模型」演练：从较大模型切到一个更便宜的模型。
2. 在子 agent 与数据库/知识库之间插一个薄网关代理，只做两件事：权限校验 + 返回字段的 PII 打码。子 agent 代码不改。

**判断有没有改善的指标：**

- 换模型所需改动：目标从「多处代码 + 重新发布」降到**代码改动 0 行**，只改配置。
- 敏感字段到达模型的次数：用日志抽样核对工具返回值，目标为 **0**（邮箱、电话、住址）。
- 故障定位时间：人为注入一个「知识库召回为空」和一个「日期算错」的故障，计时从发现到定位到具体层，与改造前对比。
- 成本：同一批请求在切换后的 Token 账单变化（追踪打通后可直接读）。
- 追踪覆盖率：抽 20 次对话，能完整串起「入口 → 分发 → 网关 → 数据查询」的比例，目标 100%。

**不建议在这一步就做的：** 子 agent 注册表 + A2A 动态发现。它需要先有稳定的能力登记契约和多个会独立演进的子 agent，否则引入的复杂度大于收益；等上面两项验证有效、且子 agent 数量增长到「加一个就要改总控代码」成为真实痛点时再上。
