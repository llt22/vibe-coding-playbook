## 是什么

Linear 工程负责人 Tom Moor 在 AI Engineer 大会上分享 coding agent 的上下文问题：代码库只能告诉 Agent 当前代码长什么样，看不到功能背后的前因后果，例如为什么做这个功能、之前放弃过哪些方案。结果是 Agent 容易做出单个 PR 逻辑正确、但长期把产品打乱的改动，比如每遇到一个新需求就往设置页加一个开关。

Linear 的做法是在需求、实现、审查到沉淀的外循环上搭一套系统，把散落在工单和历史讨论里的上下文串进开发闭环。原文是推文摘要，附有 YouTube 链接卡片，但未提供完整演讲文字、提示词或配置。

## 具体做法

原文未给出可直接复制的命令、配置或提示词；以下按原文复述流程，落地时需自行设计提示词、权限和检索方式。

前提：团队有工单系统，能关联历史工单、讨论、事故记录和回滚记录；有代码评审流程；能运行定时任务；维护 `AGENTS.md` 或对应模块文档；Agent 有权限读取工单、PR diff、评审评论和历史档案。

1. 在需求入口放一个 Agent，写代码前先把反馈整理成完整上下文。
   - 前提：新需求或反馈进入工单系统。
   - 动作：提炼反馈情况；判断能否复现，能复现时让 Agent 尝试复现；翻历史档案，把以前动过这块地方的关联工单和当时的取舍决定挂到当前工单上。
   - 分支：如果是小 Bug，直接触发自动修复。

2. 在代码审查阶段派一个产品历史 Review Agent。
   - 前提：PR 已提交，且能读取原始工单、客户背景、编码会话中间决策和过去一年的产品历史。
   - 动作：不只审查代码 diff 的逻辑 Bug，而是把原始工单意图、客户背景、编码会话里做过的中间决策、过去一年的产品历史拉出来交叉比对。
   - 输出：标出高危写法、已否决方案、违背产品惯例的细节；判断这次改动涉及的取舍应该拉哪位产品负责人来决策，而不是只找程序员看代码。

3. 每天跑一次经验提炼循环，把人类判断反哺回代码库。
   - 前提：每天代码合并完成，定时任务有权限扫描当天 PR。
   - 动作：后台定时任务自动扫描当天所有 PR 里的审查评论、打回修改和回滚记录，从中提炼具体教训，自动更新到代码库的 `AGENTS.md` 或对应模块的文档里。

4. 把人工纠正作为下一轮上下文输入。
   - 前提：人类在需求、审查、回滚环节做出判断后留下记录。
   - 动作：每日循环把上述判断沉淀为文档，下一轮需求入口和 Review Agent 再读取这些沉淀。

## 证据与局限

原文给出的案例：一是某次改动一直占着数据库事务锁不放，单看代码的 Codex 没察觉，Review Agent 翻出六个月前的事故记录，标出这是曾引发线上故障的高危写法；二是有人提 PR 想加一套图标，代码没毛病，但 Agent 翻出一年前的记录，指出这套图标早因界面太乱被团队否决删掉过；三是某处改动把工作区标签排在团队标签下面，代码里没有统一地方定义上下级顺序，Agent 靠翻查以前的一次历史回滚记录抓出这个违背产品惯例的细节。

这些是演讲中的案例叙述，不是可复核的数据；原文也没有给出 Agent 的具体实现、提示词、检索方案、误报率和评审耗时。适用条件是团队有较完整的历史记录和评审文化；历史档案缺失或质量差的团队，效果会受限。

## 怎么试、怎么验证

建议选一个模块或一个小组做 2—4 周轻量试点，先不追求全自动阻断。

1. 建立最小历史上下文库：把该模块相关工单、事故记录、回滚记录、评审评论接入可检索位置，维护该模块的 `AGENTS.md` 或文档。
2. 需求入口加一步上下文整理：Agent 产出“反馈情况、能否复现、关联历史工单、历史取舍”的上下文卡，由人复核后再进入编码。
3. 审查阶段加 Review Agent：只对涉及历史敏感模块的 PR 启用，输出“风险点、历史依据、建议决策人”，先人工确认，不直接阻断合并。
4. 每日定时任务：扫描当天 PR 的审查评论、打回修改和回滚记录，生成教训候选，人工审核后写入 `AGENTS.md` 或模块文档。

验证指标建议对比试点前后：单看 diff 难以发现、由 Review Agent 拦截的高危问题数；因历史上下文被拦截的 PR 数；回滚率；线上事故数；PR 返工轮次；评审评论中重复旧错误的次数；`AGENTS.md` 更新被后续引用或采纳的次数；人工复核耗时。判断改善的标准是：在不显著增加评审时间的前提下，能稳定拦截需要历史上下文才能发现的问题，并让同类纠正减少。
