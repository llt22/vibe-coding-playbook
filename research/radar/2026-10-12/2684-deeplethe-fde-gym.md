## 是什么

FDE Gym 自称“LLM 时代的在线评测系统（online judge）”，对象是前向交付工程师（FDE）。每个 case 是一次真实客户交付：一个正在运行的系统、文档、历史记录，以及几位可以提问的客户员工。你用编码智能体来干活，交付后系统会在客户从未展示过的流量上上线运行，按客户自己那个指标改善了多少来打分。

它和经典 OJ 的差别（README 的对照表）：

| | 经典 OJ | FDE Gym |
|---|---|---|
| 题目 | 完整精确，照做 | 客户发起人的一段话，他说的未必是该建的东西 |
| 给你的 | 输入输出格式、几个样例 | 运行中的系统、文档、历史、几个可问的人 |
| 你要做 | 写程序 | 找出真问题、问对人、指挥编码智能体改系统 |
| 判定 | 隐藏测试用例，输出对不对 | 上线到客户未见流量，客户自己的数字改善多少 |
| 判决 | Accepted 与否 | 百分制：0 = 什么都没改，100 = 参考解，≥80 通过，生产事故最高 0 分 |
| 成本 | 错就再交一次 | 一次运行只交付一次；占用客户人员时间要扣分 |

README 明确把“听出真问题 / 找出没人写下来的规则 / 做判断 / 为线上结果负责”列为编码智能体写代码之外、留给人的部分。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

前提：本机安装 Docker、Python 3.9 或更高版本，并准备一个 [OpenRouter](https://openrouter.ai) key（一个便宜模型用来扮演客户员工），key 放在仓库之外的文件里。

1. 克隆仓库并写入 key（key 存放在仓库外，避免提交进版本库）：

```bash
git clone https://github.com/deeplethe/fde-gym.git && cd fde-gym
mkdir -p ~/.fdegym && echo "sk-or-..." > ~/.fdegym/openrouter_key
```

2. 拉取三个公开 case 到 `cases/`（站点启动时会导入该目录下发现的内容）：

```bash
python3 scripts/fetch_cases.py        # the three open cases, into cases/
```

3. 启动站点（会起四样东西：站点本身、runner 即运行 case 的机器（此处为容器）、PostgreSQL、S3 兼容对象存储）：

```bash
docker compose up --build             # http://127.0.0.1:8787
```

4. 打开 `http://127.0.0.1:8787`，第一个注册的账号自动成为 admin。选一个 case，按 Begin 进入工作台。
5. 在在线工作台里干活：工作区文件、终端、接受你指令的编码智能体，以及“坐在旁边”的客户员工（由那个便宜模型扮演）。
6. 交付：把系统交上去，它会在客户没展示过的流量上运行，得分就是客户自己指标改善的幅度。一次运行只交付一次，不能像 OJ 那样反复提交。
7. 也可以完全走命令行：底层 harness 在 `harness/`，只用 Python 标准库；同一个 case 既能由人、也能由 AI 智能体从命令行完成，细节见 `harness/README.md`，版本用 `python3 harness/run.py --version` 查看。
8. 安全前提：站点会执行人写出来的代码，默认只监听本机；在让其他人接入之前，先读 `docs/self-hosting.md` 的 Security 一节。
9. 扩展案例：三个完整公开案例在 HuggingFace 的 `DeepLethe/FDE-Gym-examples`；另有 20 个覆盖银行、医疗、物流、制造、能源等场景的 case 需申请（`DeepLethe/FDE-Gym`）。管理员也可以在 admin console 上传案例，并暂停、重新归档或删除案例。
10. 管理侧可配置项（admin console）：成员与运行记录面板、案例库上传/归档/暂停/删除、运行 case 的机器、编码智能体的模型与花费上限、邮件。

## 对应的研究问题

- **能力发现**：README 把“听出客户真正的问题（发起人描述的通常只是他想象中的修法）”“找出没人写下来的规则（什么可自动化、什么必须交给人、谁说了算，往往只有一个人知道）”“做判断（把不确定全丢给人看似安全，但客户请你来就是不想这样）”“为线上后果负责”列为写代码之外、留给人的能力清单。它提示了一条人机分工的边界清单，但没有给出 AI 侧的能力清单。
- **任务匹配**：分工写得很直接——智能体写代码，人负责找真问题、问对人、做决定、担线上责任；客户员工由“一个便宜模型”扮演，编码智能体用哪个模型、花费上限多少可在 admin console 配置。
- **条件供给**：case 本身供给“运行中的系统 + 文档 + 历史 + 几个可以问的人”；人需要给编码智能体下指令（direction）；占用客户人员时间要扣分，等于把“向人提问”标上了成本。
- **主动推进**：原文没有涉及时间、事件或状态触发的持续执行。
- **效果验证**：这是最相关的一块。判分口径是：0 = 什么都没改，100 = 参考解，≥80 通过；生产事故最高 0 分；一次运行只交付一次，不可反复试；验证发生在客户从未展示过的流量上，指标是“客户自己那个数字”改善了多少。这套口径可以直接搬去设计自己工作的验证方式。

## 怎么试、怎么验证

最小试用方式：在一台本机按上面第 1–3 步起站点，让一名工程师带编码智能体跑通一个公开 case 的完整交付，记录最终得分。

判断有没有改善的指标：

1. **是否达到通过线**：一次交付能否拿到 ≥80 分；因为一次运行只交付一次，这个分数比“反复提交后通过”更有参考价值。
2. **有无人可用信息的对照**：同一人 + 同一编码智能体，在“可以问客户员工”与“不可以问”两种条件下分别记分，同时把占用客户人员时间的扣分算进去，看边际收益是否为正。
3. **人机对照**：用 `harness/` 从命令行跑同一个 case，一次由人主导、一次交给 AI 智能体主导，比较交付分数。
4. **口径迁移**：把该 case 的判分方式搬到团队真实任务上——先定义“什么都不改”的 0 分基线和“参考解”的 100 分，用业务方自己那个数字做上线后度量，并设一条“出事故即归零”的红线，检查这样得到的分数是否可复现、能否区分不同做法。
