## 是什么

Claude Code 团队公开的代码审查流程说明：当 agent 大量产出代码后，如何把「读 diff」主要交给机器，把人的时间留给机器做不好的决策，同时保证不增加回滚和事故。

原文给出的背景数据：Claude 写了约 90% 的 Claude Code 自身代码；2026 年 6 月到 9 月，合并进 Claude Code 代码库的 PR 翻了一倍多，而被回滚的比例下降超过 40%；Anthropic monorepo 每天落地的变更从 5 月约 2,500 涨到 9 月超过 30,000。

核心主张：不要问「有没有人读过这段代码」，要问「这个变更可能出什么问题，哪一层检查（自动的还是人的）最适合抓它」。审查从「路尽头的关卡」变成「写代码时的拼写检查」——大多数变更在人类看之前已被 Claude 至少审过并修过一轮。目标状态是：大多数 PR 至多一个人类在环（可以是作者本人），且回滚率和事故率不上升。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

### A. 开 PR 之前（前提：已有 Claude Code 可用，仓库里有测试/构建/截图等可执行验证手段）

1. 给 Claude 一个它能自己跑的验证方式，并要求它展示输出，而不是说「做完了」。原文举例：跑 bash 命令、跑测试套件、在浏览器或手机模拟器里试应用、拿截图和设计稿对比。
2. 写一份简短的 `CLAUDE.md`，说明项目是什么：技术栈、约定、目标和非目标。大代码库里要短，并指向其他文档；每次审查都会加载它。审查者还会标记违反其中约定的代码，以及让其中某一句话过时的改动。
3. 在 `CLAUDE.md` 之外配置 hooks，自动跑 formatter 和 linter。
4. 在本地跑轻量审查，或让一个全新上下文的 subagent 审 diff：

```
/code-review
/security-review
```

前提：`/code-review` 是本地较轻的版本；`/security-review` 对应开源的 security review GitHub Action 的同等能力。
5. 加一份 `REVIEW.md`，由 code owners 写，告诉审查者在这块代码里什么才算重要。按原文，好的 `REVIEW.md` 要：说明该部分代码里「失败」长什么样（对文档是「它在说谎」，对配置是「它错误路由」）；限制 nit 的数量；列出应跳过的路径；要求以文件和行号作为证据，而不是凭名字猜；要求摘要以数量开头，并且没什么可修时直说。还要单独检查审查者是否真的遵守了它。
6. 把重复出现的审查评论搬进 `REVIEW.md`；如果某类问题被反复标记，就在源头修：改 skill、加 lint 规则，或更新指令文件。
7. 开 PR 前跑内部 skill：一个找 bug，一个简化 diff，一个做端到端行为检查；UI 变更还要对照设计规范检查。（原文只描述这三类 skill 的作用，未给出其内容。）

### B. 每个 PR 上（前提：CI 可运行，仓库在平台上有分支保护能力）

8. 每个 PR 在人类看之前先过一次 Claude 审查：读 diff，对照整个仓库和 PR 声明的意图，问「这个改动是否解决了它的问题、是否契合系统、是否破坏了别的东西」，对 bug 修复还要看根因。
9. 让发现结果先由其他 agent 验证再给人看：多个 agent 同时找 bug，另一组对每条发现投票，足够多同意才发布；只涉及风格、诊断或清理的发现直接丢掉（这些过滤规则在团队自己的 PR 上做过 A/B 测试才保留）。留下的按严重度排序为行内评论，并标记 `Important`、`Nit` 或 `Pre-existing`（后者用于区分「不是这个 PR 引入的 bug」）。
10. 每条发现都必须被回应：要么修，要么用理由 resolve 掉这个 thread。经常由 agent 在夜间接手修复，作者第二天回来时 PR 已经又过了一轮。
11. 加自动化安全审查，并且让它能阻断合并：bug 审查或安全审查只要有未关闭的发现，PR 就不能合并；修掉或写一句简短理由关闭 thread（这是清除误报的方式）；后续 commit 修好了，发现会自动清除。
12. 上常规阻断性检查：lint、类型检查、所有平台的测试、构建。原文称一个典型 CLI PR 在有人看之前可能跑几十个检查。
13. 在 PR 模板里加三个字段，Claude 可以代填，但提出变更的人要签字确认：

```
## Testing
## Risk
## How to revert
```

### C. 审批（前提：先写下风险分级，并从严开始）

14. 用变更本身而不是作者来定风险等级，由分类器读变更后选择层级；再用第二个分类器判断「即使层级说不需要，这个变更是否还需要另一个人」。原文的分级表：

| 风险 | 例子 | 需要的人类审批 |
| --- | --- | --- |
| 低 | 文档、文案、仅内部功能、flag 后面的增量变更 | 自动审查和安全检查全绿后不需要 |
| 中 | 普通产品变更，以及缓存、auto-updater、system prompt 等敏感区域的变更 | 一人 |
| 高 | 最高风险的代码，加上一小批始终需要两人的路径 | 两人 |

15. 有些路径永远需要人：owners 列为敏感的路径，以及任何 CI workflow 文件。用 CODEOWNERS 和分支保护把 auth、billing、CI 和发布流程、安装器固定为「始终需要一个人」。
16. 只有仓库 trusted list 上的作者（主要是拥有该仓库的团队）能走轻路径，其他人都需要第二个人审批。agent 的审批永远不能算作人类审批，也不能填补一个要求人类的槽位。
17. 谁提示了变更，谁就计入必需审查人——agent 写的 PR，指挥 agent 的人算一个审查人，和亲手写代码一样。
18. 审批只覆盖某一个具体 commit：如果有系统无法担保的新 commit 落地（比如 agent push，或有人手工解的合并），审批必须重新给。
19. 先严后松：起始从严，有证据再放宽。

### D. 合并与之后（前提：具备 merge queue、feature flag、分阶段发布和一键回滚能力）

20. 用 merge queue 把每个检查对着 main 重跑一遍，避免两个各自通过的 PR 合起来弄坏 main。
21. 新行为先放在 flag 后面只发给内部人员使用（原文是发给 Anthropic 员工），公开版本先进 latest channel，stable channel 滞后。
22. 留最后一层「快速发现、快速回滚」：flag 不用部署就能关；保持每周 on-call 轮换；事故复盘要问「哪一层本该抓到它」。原文明确说他们还没有在回滚/事故指标变动时自动收紧审批的 circuit breaker，工程师希望在更多代码走向零人工合并之前有这个东西。
23. 把事故和回滚变成 eval 集：收集过去引发事故的 PR 连同它们的修复和回滚，请熟悉那段代码的工程师逐条确认是什么 bug、在哪里，然后让审查者每天跑这个集合；审查者的 prompt、工具或模型一变，就用整套 eval 重新打分。
24. 测噪声，而不是只测召回：把审查者留下的每条评论按当事人的反应分类（他修了／他说这条错了／他说这是有意为之／他觉得不重要），另外在已知干净的 PR 上跑审查者，统计有多少报告会引导人做出有害改动。原文写下的优先级是：先抓真 bug，其次才是减少审查轮次。注意噪声对 agent 作者代价更高——人能几秒钟摆手放掉一个 nit，agent 会去修，意味着又一个 commit、又一轮审查。
25. 让审查收敛（这四条是团队为治「50 多轮」问题加的）：轮次上限，超过三轮后审查者要求作者退一步重新考虑方案；前几轮之后只复审新 diff；标记 bug 的类别，让作者修掉所有实例而不是一行；不重复已经贴过的发现。
26. 让审查 agent 每晚在存量代码上跑，在旧 bug 冒出来之前先抓到。

### E. 人留在哪里

27. 把人力集中在五类决策上，其余交给检查：是否该做这件事（方向、品味、范围）；高风险代码（billing、auto-updater、CI workflows）；会被别人复制的架构模式；读证据（测试输出、跑过的命令及其返回、截图、审查者的发现——如果说不出检查会漏什么，就要求一次真正的审查而不是快速批准）；对结果负责。
28. 让 Claude 写指定代码切片的解释，需要的话让它生成一个可视化该部分代码的小工具，用来替代「靠逐行读同事的 diff 来学代码」。（原文明确说他们没有正式流程，也没人脑子里装着完整模型。）
29. 采纳「你落地，你负责」：小到中等变更出问题通常由落地者修，前提是变更小、一切可逆、爆炸半径决定审查门槛、回归能通过遥测和内部使用快速浮现，且事故复盘看系统不追责。原文补充：所有权也是共享的，团队大量在开放 Slack 频道工作。

## 对应的研究问题

**1. 能力发现：AI 已经能做哪些还没想到交给它的工作**
- 逐个 PR 读 diff 并对照整个仓库和 PR 声明意图提问（是否解决问题、是否契合系统、是否破坏别处），对 bug 修复追根因。
- 安全审查并阻断合并。
- 多个 agent 并行找 bug，再由另一组 agent 投票验证每条发现，只发布票数足够的；风格/诊断/清理类发现自动丢弃。
- 按严重度排序输出行内评论并打 `Important`/`Nit`/`Pre-existing` 标签。
- 夜间自动接手修复，使作者第二天看到的是已再过一轮的 PR。
- 夜间在存量代码上跑审查，找老 bug。
- 为指定的代码切片写解释文档，甚至生成可视化小工具。
- 填 PR 模板字段。
- 开 PR 前的三类 skill：找 bug、简化 diff、端到端行为检查；UI 对照设计规范。

**2. 任务匹配：什么工作适合怎样的模型、工具和协作方式**
- 本地/轻量：`/code-review`（本地较轻版本）、`/security-review`、全新上下文的 subagent 审查。
- 仓库级：Code Review for Claude Code（Team 和 Enterprise 计划已 GA；按仓库设 Quick / Standard / Deep，Deep 用在「漏一个 bug 的代价高于多花审查时间」的地方）、Claude Code GitHub Action、开源 security review GitHub Action。
- 分工：机器读 diff 和跑检查，人做五类决策；风险层级决定需要 0/1/2 个人类审批；agent 的审批不算人类审批；只有 trusted list 上的作者走轻路径。

**3. 条件供给：需要提供哪些信息、工具、权限和反馈**
- 信息：简短的 `CLAUDE.md`（技术栈、约定、目标与非目标，指向其他文档）；由 code owners 写的 `REVIEW.md`（该处代码「失败」长什么样、限制 nit、跳过路径、要求 file+line 证据、摘要以数量开头、没问题就明说）。
- 工具与权限：agent 可运行的检查（测试、构建、截图对比、浏览器/模拟器）；跑 formatter 和 linter 的 hooks；CI；阻断性安全审查；merge queue；feature flag；一键回滚；CODEOWNERS 与分支保护；PR 模板的 Testing / Risk / How to revert。
- 反馈闭环：每条发现必须修或用理由 resolve；重复出现的评论写回 skill、lint 规则或指令文件；「当审查漏掉东西时，问模型当时眼前缺了什么，把修复放进 CLAUDE.md、skill 或一个新检查」。

**4. 主动推进：哪些工作可由时间、事件或状态触发并持续完成**
- 事件触发：每个 PR 自动进入 AI 审查；安全审查与 bug 审查未关闭则阻断合并；后续 commit 修好则发现自动清除。
- 状态触发：分类器自动定风险层级；新 commit 自动使已有审批失效；merge queue 自动对 main 重跑检查。
- 持续运行：agent 夜间接手修复；审查 agent 每晚扫存量代码；审查者每天对事故 eval 集跑分，其 prompt/工具/模型变更时重新打分。
- 原文指出的缺口：还没有在回滚/事故指标变动时自动收紧审批的 circuit breaker。

**5. 效果验证：怎样判断确实改善了结果**
- 人力的主指标：每个 PR 的人类审批数（中位数和 95 分位）、人类评论数、PR 等人等待的时长。

- 审查者质量：用历史事故 PR（含修复和回滚，由熟悉代码的工程师逐条确认）构成 eval 集每天跑；噪声用当事人的反应分类（修了/说错了/说是有意的/觉得不重要），以及在已知干净 PR 上统计会误导人做有害改动的报告数。
- 收敛：把 rounds-to-pass 和召回率一起追踪。原文给出的一次诊断：对审查者反复标记的内容跑 git blame，约 59% 是审查者第一轮时就已经存在的代码——它在每轮多翻出几个老 bug，而不是在找新 bug。

## 怎么试、怎么验证

**最小试用（先在一个仓库，2–4 周）**
1. 只挑一个仓库。写一份简短 `CLAUDE.md`（栈、约定、目标/非目标，超出部分指向其他文档），加 formatter/linter hooks。
2. 写第一版 `REVIEW.md`：定义在这个仓库里「失败」长什么样，限制 nit 数量，列出跳过路径，要求 file+line 证据，要求摘要以数量开头。
3. PR 模板加 `Testing` / `Risk` / `How to revert` 三个字段，要求 CI 必过。
4. 本地先用 `/code-review`、`/security-review`；然后接入 AI reviewer，只在一个仓库上跑，先按 Standard（高风险路径用 Deep），调 `REVIEW.md` 几周再考虑铺开。
5. 要求所有 review thread 解决后才能合并；设置 3 轮上限，前几轮之后只复审新 diff。
6. 写下风险分级（低=自动检查全绿即可 / 中=1 人 / 高=2 人），并保持 CODEOWNERS 与分支保护，让 auth、billing、CI/发布流程、安装器始终需要人；确认 bot 审批不会填人类槽位，新 commit 会作废审批。

**判断有没有改善的指标**
- 主指标：每个 PR 的人类审批数（中位数与 P95，原文用这两个统计量）、人类评论数、PR 等待人的时长、rounds-to-pass。
- 护栏：回滚率与事故率。原文的判据是——如果这两个上升，就没有省下人力时间，只是把时间挪到了修 bug 上。
- 审查者质量：把已经发生过的回滚和事故整理成一个固定案例集，每次改 prompt/工具/模型都重跑；同时按当事人的反应给评论分类，统计误报比例，并在已确认干净的 PR 上跑一遍看它会不会诱使人做有害改动。
- 前提检查：如果本地跑下来人类审批数和回滚率都没动，说明真正起作用的层（可运行的验证、`REVIEW.md` 的明确度、风险分级）还没建好，先补这几处，再谈扩大范围。
