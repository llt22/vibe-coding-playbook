## 怎么试、怎么验证

**最小试用（不依赖原文提示词，自行搭一版）**：

1. 选一个近期真实 bug：要求现象可稳定复现，且有一个可量化信号（慢查询耗时、失败测试用例、错误日志计数）。
2. 先做基准记录：把当前信号数值或失败用例清单原样写下来，作为“修复前”的唯一判据。
3. 手写 4 条互斥假设，每条必须附带“能证伪它的具体命令或测量”，再分派给 4 个独立 Claude Code 会话各查一条。
4. 只允许在“该假设对应的验证命令已跑出结果”后再改代码；改完后必须重跑第 2 步的基准。
5. 全部假设被排除但仍未修复时，记录为流程失败案例，而不是让 agent 继续自由发挥。

**判断有没有改善的指标**：

- 从开工到定位根因的时间（与最近 3 个同类 bug 的手工排查对比）；
- 被排除的错误假设数量／总假设数（衡量并行排查是否真的收敛）；
- 修复后回归失败率、“声称修好但实际未修好”的次数（这是该思路的核心承诺，必须单独统计）；
- 单位 bug 的 token/会话成本（多 agent 并行的主要代价）。
