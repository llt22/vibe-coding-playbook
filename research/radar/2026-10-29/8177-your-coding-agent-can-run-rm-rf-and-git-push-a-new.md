## 是什么

一条关于开源仓库 `ai-setup` 的推文（附 GitHub 链接卡片：`sebabottero/ai-setup`）。它主张为编码 agent 装一套**共享策略**，让 Claude Code 与 OpenCode 在同一套规则下工作：

- **需审批（ask first）**：`commit`、`push`、`merge`、删除这类难以撤销的操作，不直接执行，先请求确认，并附带一个**风险标签**；
- **硬拒绝（hard deny）**：读取 SSH 私钥、云厂商凭证这类凭据文件，直接拒绝，不进入审批环节。

推文的开场是个很具体的风险场景：编码 agent 能够执行 `rm -rf` 和 `git push`。所以这个项目的定位不是增强能力，而是**给已有能力加护栏**，并且强调“一套策略、两个 agent 通用”。

### A. 拿到仓库后的核实顺序（前提：能访问 GitHub 上的 sebabottero/ai-setup）

1. 读 README，确认安装方式的形态：是脚本安装、还是把策略文件复制/软链到 Claude Code、OpenCode 各自的配置目录。**这一步决定它是否可迁移到你的机器**（团队共享机器、受限网络环境通常跑不了安装脚本）。
2. 找到策略文件本体，逐条对照推文的三类断言：
   - `commit` / `push` / `merge` / 删除 是否各自有独立规则；
   - 规则是否携带风险标签字段，标签的取值集合是什么；
   - 凭据路径（SSH 私钥、云凭证）是否在**硬拒绝**列表中，而非审批列表。
3. 确认“共享”的含义：是同一份文件被两种 agent 读取（真共享），还是两份各自维护、只是内容相近（伪共享）。后者在 agent 升级后极易漂移，是主要风险点。
4. 确认规则的匹配粒度：按命令名、按正则、还是按参数。`rm -rf` 这类命令的判定如果用宽泛正则，容易漏（如 `find -delete`、`git clean -fdx`）；如果是白名单式（默认拒绝、显式放行），则更稳。
5. 在**一次性容器或临时目录**里跑三条冒烟测试：读 `~/.ssh/id_rsa`；执行一次无害的 `git push`（推到本地裸仓库）；删除一个临时文件。看是否分别命中“硬拒绝 / 审批 / 审批”。

### B. 不装该仓库时，如何按同样思路自建（这部分是依据推文描述的三条原则推演，非原文内容）

6. 把你常用的 agent 的高危操作列成一张清单，分成三档：**硬拒绝**（读凭据、写系统目录）、**需审批**（提交/推送/合并/删除/装依赖）、**直接放行**（读文件、跑测试、搜索）。默认档位设为“需审批”，再逐步放行。
7. 每条**需审批**规则配一个人可读的风险标签（例如“会改写远端历史”“会不可恢复地删除文件”），让审批弹窗本身携带判断信息，而不是只有一个“是否允许”。
