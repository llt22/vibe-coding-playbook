## 是什么

这是一篇 Latent Space 的播客文字综述（嘉宾为 Supabase 创始人 Paul Copplestone 与 Ant Wilson），主题是“为什么 agent 喜欢 Supabase”。文章的核心不是功能清单，而是作者从产品发布里挑出的几个对 agent 友好的方向：

- **本地后端可无 Docker 启动**（新的 alpha 运行时）。作者用 Colima 而非 Docker Desktop，认为少一个依赖就少一层摩擦；对人是每周一次的小事，对反复创建/测试环境的 agent 则是高频摩擦。
- **声明式 schema**：不再靠“建表后不断 migrate”的历史累积，而是用文件描述“我想要的状态”，让 agent 能像读代码一样读它、改它、fork 它。作者称之为数据库的“Terraform 时刻”。
- **计算贴近数据库**：Supabase Compute（private alpha）把容器跑在数据库旁边，用于文档切块、生成 embedding 等长时任务，减少需要单独配置和向 agent 解释的服务。
- **Operate 侧的可观测性**：日志、检查、连接、上下文，让能发 SQL 的模型知道库里有什么、应用怎么用它、失败时发生了什么。

## 怎么试、怎么验证

**最小试用（一周，单项目）**
1. 选一个已有小应用（有数据库、代码在 Git、由编码 agent 参与改动）。
2. 把当前库结构整理成一份声明式的“期望状态”文件，提交到仓库，作为唯一事实来源；此后 agent 的改动只走“改文件 → 产生变更”的路径。
3. 让 agent 在本地从零拉起一次后端并跑通应用（尽量不装 Docker 之外的新依赖，条件允许时试无 Docker 方式）。
4. 每个任务开始前，把日志/连接/库结构说明作为上下文提供给 agent。
5. 记录一周内发生的每一次“agent 改后端”事件。

**判断有没有改善的指标**
- **环境就绪时间**：从零到应用可运行的中位耗时，改造前后对比。
- **人工干预次数**：agent 改数据库时人必须插手的次数（每次介入记一条原因）。
- **schema 漂移事件**：仓库中的声明式状态与实际库不一致的次数。
- **迁移/变更失败率**：agent 发起的变更中失败或需回滚的比例。
- **一条龙完成率**：给一个陌生环境，agent 能否无人值守走到“应用跑起来”。

**判据建议**：若干预后环境就绪时间与人工干预次数明显下降、且漂移事件为零或极少，说明“声明式 schema + 可重复本地后端”这条路在你的场景成立；若漂移或失败率上升，多半是缺少 Operate 侧上下文（日志、连接、库说明），应先补条件供给而不是换工具。

**注意**：上述指标与判据是本报告为验证目的提出的，原文未提供任何量化结果。
