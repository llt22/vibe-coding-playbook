## 是什么

Cursor 发布的 Agent SDK：一个把「团队自建智能体」当普通软件项目来写的框架。智能体由代码定义——引导它的指令是 Markdown，工具是 TypeScript 函数，外加对外服务的连接和用于测试的 evals；项目目录里每类文件代表它「知道什么」或「能做什么」。写完后用一条 `agent-sdk deploy` 部署到 Cursor 基础设施（得到一个 URL），也可以自托管——每个 agent 是单个 Node 进程，可打包进容器。

官方定位是「事件触发的重复性开发流程工作」：响应 PR 事件、执行合规流程、调查线上事故。Cursor 自家的 Bugbot、Security Reviewer、Rollouts 就是用这个 SDK 构建的。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

前提：Node 环境；能访问 Cursor 账号与 dashboard（用于管理 secrets 和集成的场景）；有 GitHub/GitLab/Bitbucket 等事件源可用于触发。原文未给出安装命令，`@cursor/agent-sdk` 的安装方式需查官方文档（原文只说“读文档并开始”）。

1. 建一个项目目录，像起一个普通软件项目一样组织它：提示词（Markdown）与工具代码（TypeScript 函数）、外部服务连接、evals 放在一起，一起进版本控制和评审。
2. 用 `defineAgent` 定义 agent（原文给出的示例，模型 id 与参数原样保留）：

```ts
import { homedir } from "node:os" ; 
import { join } from "node:path" ; 
import { defineAgent } from "@cursor/agent-sdk" ; 

export default defineAgent ({ 
 name: "Robo" , 
 model: { 
 id: "composer-2.5" , 
 params: [ 
 { id: "effort" , value: "high" }, 
 { id: "fast" , value: "true" }, 
 ], 
 }, 
 local: { 
 cwd: join ( homedir (), ".cache" , "factory" , "robo" ), 
 }, 
 }) 
```

3. 在本地起 playground 迭代（原文只说“启动本地 playground”，未给命令）。本地就能看日志、跑 evals，与部署后用的是同一套。
4. 写 evals 并做事件回放（event replay）——原文称开箱即用，用来确认关键流程按预期执行；具体写法原文未给，需查文档。
5. 部署：在项目目录执行

```
agent-sdk deploy
```

该命令会构建、分配 URL 并在 Cursor 基础设施上启动。secrets 与集成在 dashboard 管理。
6. 若要自托管：把 agent 作为单个 Node 进程打包进容器运行。
7. 让 agent 响应已有的事件（如 GitHub/GitLab/Bitbucket 的 PR 事件），按团队可检查、可修改的策略执行动作：评估变更风险、路由给正确的团队、对符合策略的变更批准。
8. 复杂任务拆解：agent 可把任务交给另一个带独立工具和会话的专用 agent，也可把工作分给并行子 agent。
9. 省力路径：从模板起步，或直接把编码 agent 指向官方文档，让 agent 帮你把这个 bot 一起写出来（SDK 自带引导编码 agent 走开发流程的 skills）。

## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）

- **能力发现**：原文点出的一类此前较少交付给 AI 的重复性工作——把「团队积累的经验/决策记录」变成每个 PR 的强制检查项（kb-reviewer：标记与已记录经验冲突的改动、引用对应笔记、促使工程师处理不一致）。同类还有合规流程执行、事故调查、变更风险分级与批准。
- **任务匹配**：按任务配置模型与参数（示例 `composer-2.5` + `effort: high` + `fast: true`）；能力边界按文件切分——提示词用 Markdown（对应“说什么”），工具用 TypeScript 函数（对应“能做什么”）；复杂任务用「移交专用 agent」或「并行子 agent」两种协作方式，而不是一个 agent 硬扛。
- **条件供给**：需要给出的是工具代码、对外服务连接、secrets 与集成（dashboard 管理）、可被检查和修改的策略，以及作为判断依据的知识库（且输出要引用出处）；反馈条件是 evals 与事件回放。
- **主动推进**：明确的事件触发模型——agent 响应团队本就在处理的事件（PR、合规、事故），kb-reviewer 是「跑在主库每个 PR 上」的持续执行，不靠人手动叫；子 agent 可并行分担任务。
- **效果验证**：SDK 内置 evals 与 event replay；本地与线上共用同一套 logs/evals/playground，便于上线前后对照。但原文没有给出 eval 具体指标或阈值。

## 证据与局限

原文给出的实证只有两处，且都是自述：

- Cursor 内部一个团队用 Agent SDK「大约一天」做出 kb-reviewer，现跑在主库每个 PR 上，会标记与已记录经验冲突的改动并引用对应笔记。属于单点内部案例，无准确率、误报率、节省工时等任何数字。
- PGA Tour 的 Michael Gyarmathy（Principal Engineer）一句推荐语，称用该 SDK 构建其「软件工厂」全部组件、内置 evals 让其快速迭代。属客户证言，无数据。

其余均为作者主张：agent 应当围绕团队自己的工作流定制、策略应可检查可修改、代码化便于走版本控制与评审。这些是合理的设计观点，但没有对照实验或基准支撑。

适用条件与局限：

- 面向软件团队、以 PR/合规/事故等事件为中心的重复性流程；非软件类工作只能借鉴其「代码化定义 + 评测 + 事件触发」的结构。
- 强绑定 Cursor 生态（模型 id、dashboard、部署基础设施）；自托管只说明是单 Node 进程可容器化，未给资源要求。
- 原文是产品发布文，缺安装与评测的具体写法、权限模型、成本与限额，动手前需读官方文档补齐。

## 怎么试、怎么验证

最小试用（建议 1–2 周，单人可做）：

1. 选一个标准写得出、每周至少发生数次的重复任务，例如「PR 是否符合团队约定/历史决策」。先把这份约定整理成可引用的条目（每条一个文件或一条笔记），这是 agent 的判断依据。
2. 按上面步骤 1–3 建项目、写提示词与一个工具（读 PR diff + 检索条目），本地 playground 跑通。
3. **先影子模式**：只输出发现与引用出处，不自动批准、不自动路由，人工处置。
4. 用 evals + 事件回放，把过去若干真实 PR 作为固定测试集，改一次提示词跑一次，避免越改越差。
5. 只有当误报可接受、且人工复核成本明显低于自己从头看时，再执行 `agent-sdk deploy` 上线，并逐步放开「路由」「批准」这类写操作权限。

判断有没有改善的指标：

- **命中率**：被 agent 标记且人工确认为真问题的比例（对照人工全量检查的结果算漏报）。
- **误报率 / 噪音**：每个 PR 平均无效告警数，以及工程师主动忽略/关闭的比例。
- **引用可核验率**：每条发现都能指到具体条目（原文的 kb-reviewer 做法就是强制引用），指错即为缺陷。
- **周期时间**：PR 从提交到合并的时间、需要人工 review 轮次的前后对比。
- **一致性**：同一批回放事件重复运行，结论是否稳定（用 event replay 做回归）。
- **采用率**：工程师对 agent 提出的问题实际处理（修正或明确驳回）的比例——原文强调「促使工程师处理不一致」，这是它宣称的价值点，也应成为验收点。
