## 是什么
这是一篇 Latent Space 对 Legora CTO Jacob Lauritzen 的访谈，主题是法律场景的 AI agent 如何落地。原文可提炼的核心不是“又一个法律聊天机器人”，而是三件事：在看不到客户数据（无 trace）时用模拟环境和领域专家做评测；用“每行一份文档、每列一个问题”的表格审阅批量处理合同；用 projects、agent、Tabular Review、lists、Slack intake 等原语把法律工作编排起来。原文是访谈而非教程，转录在约 15:00 处截断，后文只有摘要和时间戳，不能当作完整实施文档。

## 具体做法
原文未提供可直接复制的命令、配置或提示词；下面是把原文可操作点整理成试行步骤，代码块是据原文示例字段整理的模板，不是原文原样。

1. 前提：选一个高隐私、批量文档任务，把文件放进“项目”容器，让 agent 只在项目权限内读写。原文的产品原语是 projects hold files，agent 可起草和编辑 Word 文档。
2. 建表格审阅：每行是一份文档，每列是一个问题。原文示例是终止期限、知识产权归属条款、遣散条款。先不要跑全量。

```text
表格审阅模板（原文示例字段）
行：一份文档
列：
- termination period（终止期限）
- IP assignment clause（知识产权归属条款）
- severance terms（遣散/补偿条款）
执行顺序：先填 10 行 → 人工校对并修正列定义/提示词 → 再跑全量（原文称可支持最多一百万单元格）
```

3. 用前10行校准：原文明确 Tabular Review 从10行开始，让人先修正提示词，再跑剩余文档。前提是每列问题可被人快速判断对错。
4. 建模拟评测环境：如果无法读客户 trace，就复制客户常做的工作类型。原文做法是3名工程师加3名律师组成评测团队，构造类似“10,000文件数据室做尽调、最终报告要抓到正确 red flags”的 RL 环境。
5. 画评测热力图：按实践领域和任务类型记录模型表现，而不是只看一个总分。原文说新模型常常在某些法律工作上更好、在另一些上更差。
6. 生产环境做失败分类：把失败归入10–20个已知 failure modes，并用便宜的 LLM-based checks 放在 feature flags 后面运行。前提是已能收集到脱敏或模拟的失败样本。
7. 做模型路由，不默认让终端用户选模型：按子任务路由，权衡质量、成本、延迟、治理和区域可用性。原文说律师不该判断一个合同是 Sonnet-high 还是 Opus-mid 任务；只有用户强烈需要实验时才提供 model picker。
8. 给所有生成内容加可定位引用：agent 写出的内容要带 citation，能高亮源 PDF 中的 bounding box，并支持多层下钻。前提是源文档有页面和坐标信息。
9. 用 lists 和 intake 做工作编排：lists 是类似 Notion 的数据库，带 triggers 和 automations；agent 可创建和读取 lists，list 变化可启动 agent。Intake 是 Slack bot，把请求变成 list 上的 ticket。前提是有 Slack、任务队列和权限控制。
10. 人员分工：legal engineers 按高级用户方式无代码配置产品；forward deployed engineers 写生产代码、接 CRM 或文档管理系统，把经验回流核心产品，但不碰客户数据。大客户签约时配 legal engineers，需要时加 FDE；原文预计一年内可有轮转 FDE 驻场几个月。
11. 基础设施按合规选：原文因律所不接受 AWS 或 GCP、微软已通过 365 成为批准供应商，所以全部跑在 Azure。这不是通用建议，只在客户合规要求类似时适用。
12. 窄任务可后训练开源权重模型：原文对法律研究等窄任务做后训练，但明确不训练自己的前沿模型。前提是已有评测和窄任务数据；否则先不做。

## 对应的研究问题
- 能力发现：原文认为 AI 已能做批量合同字段提取和审阅、尽调报告生成并抓 red flags、Word 起草和编辑、法律检索，以及用 lists 和 intake 协调任务；受访者估计模型已能很好处理约60%法律工作，但这是估计不是独立测量。
- 任务匹配：Tabular Review 适合结构化批量提取；agent 适合起草、分析、编辑和检索；lists 加 triggers 适合编排；窄任务可后训练开源模型；模型选择应由平台按质量、成本、延迟、治理和区域可用性路由，而不是让律师判断模型档位；复杂分析和百万 token 合同编辑仍需更强模型。
- 条件供给：高隐私数据不能出客户环境，需要模拟环境、领域专家、项目文件权限、审计日志和数据保留、Azure 等已批准基础设施、引用到源 PDF 的定位信息，以及 Slack、CRM、DMS 集成；FDE 不碰客户数据。
- 主动推进：lists 的 triggers 和 automations 可在列表变化时启动 agent；Slack intake 把请求变成 ticket；原文还提到主动 agent 在内容进来时反应，以及类似 command center 的待审队列。但原文没有给具体触发配置。
- 效果验证：无 trace 时用 RL 环境和模拟数据室评测；按实践领域乘任务类型画 heat map；生产中用10–20类 failure modes 加廉价 LLM checks behind feature flags；表格审阅先10行校准；引用准确率可被观测，原文案例中70%到99%是模型升级带来，不是他们做了修复。
