## 怎么试、怎么验证（最小试用方式和判断有没有改善的指标）

**最小试用**：选一个 1 万行左右、你熟悉的有真实问题的仓库。自己定 5 类（安全、性能、正确性/错误处理、测试缺口、重复代码），按上面的提示词结构跑一次，要求输出 `文件:行号 + 严重度 + 建议`，然后人工逐条判定。

**对照基线**：同一个仓库、同一天，用**单个** Claude Code 会话一次性做全量 review（不分拆、不并行），以及团队已有的 linter/SAST 结果。

**判断指标**：

- 有效问题数：人工确认「真实存在且值得修」的条数，绝对值和每千行代码密度。
- 重复率：同一 `文件:行号` 被多个子代理重复报出的比例。高于约三成说明分工切得不好，需要调整类别边界。
- 增量发现：并行方案比单代理方案、比现有 linter 多找出的有效问题条数——这是核心指标，若接近 0 则不值得用。
- 噪音比：误报数 / 总报告数。
- 成本：整个流程的耗时与 token 消耗，对比单代理方案。

**结论判据**：只有当「增量有效发现明显 > 0」且「噪音比与重复率在人工可承受范围内」时，才把这条流程固化进手册；否则降级为「值得知道的一种提示词写法」。
