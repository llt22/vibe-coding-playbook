## 是什么

推文主张：在安装别人的技能包之前，先让 Claude Opus（原文写作“Opus 5.5”）通读整个仓库，并把它压缩成一页说明：哪些部分能独立运行、每部分何时触发、哪些会接触网络、会读取你的哪些文件。作者称自己在 superpowers（原文称 300K 星）上试了一次，结果是“每次新会话、/clear 和 compaction 时，一个钩子会注入 500+……”（原文在此处截断）。

本质上这是**第三方自动化资产的安装前审计**：把一份你不可能逐行读完的仓库，转换成一份可用于决策的一页权限与行为说明。

前提：能拿到目标仓库的完整文件（本地 clone 或可读的目录树）；使用长上下文模型；**不要在已经启用该技能包的环境里做审查**。

1. 把仓库拉到隔离目录，只读审查。
```
git clone <repo-url> ~/audit/<repo-name>
```
前提：此目录不参与你的日常会话，且不要在其中执行安装脚本。

2. 先确认入口文件和可执行部分，例如 README、安装脚本、hooks/、scripts/ 等；再把目录树一并交给模型。原文没有列出具体文件名，这一步是常规做法。

3. 让模型通读仓库，只输出一页，并固定四个字段（自拟提示词）：
```
你在审查一个即将被安装到我的 AI 工作环境中的第三方“技能包”仓库。
请通读仓库全部文件，只输出一页（不超过 500 字）审查，必须包含四部分：
1) 可独立运行的部分：哪些文件/脚本/技能能单独跑，哪些必须配合其他组件；
2) 触发时机：每个部分在什么条件下被激活（新会话、/clear、上下文压缩、特定命令、定时、事件等），逐条列触发条件；
3) 网络访问：哪些部分会发起外部请求，访问哪些域名/接口，是否可以关闭；
4) 文件读取与写入：它会读取/修改我本地的哪些路径、配置、凭据，范围多大。
规则：只写仓库里能查到的证据，每条结论后注明来源文件路径；查不到就写“未发现”，不要推测。
```
前提：模型上下文能覆盖整个仓库；仓库过大时分目录分批读，最后合并成一页。

4. 用产出做安装决策：对“会接触网络”“读取凭据或全局配置”“在新会话或压缩时自动注入”这三类逐条确认是否可接受、能否关闭。原文点名的自动注入场景（hook 在每次新会话、/clear、compaction 时写入内容）正是价值点：这类隐式行为平时看不出来。

5. 若决定继续安装，把“关闭方式”和“影响范围”记入你的技能清单，作为后续升级时重审的基线。
