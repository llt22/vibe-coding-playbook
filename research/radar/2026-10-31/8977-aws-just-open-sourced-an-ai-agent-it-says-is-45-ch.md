## 怎么试、怎么验证（最小试用方式和判断有没有改善的指标）

**最小试用设计**（前提：先从 AWS 官方渠道拿到仓库与安装说明，本推文不足以支撑执行）：

1. 选一个正在用 Claude Code 的真实小仓库，挑 5–10 个已完成的历史 issue 作为固定任务集（有标准答案，便于判定对错）。
2. 同一任务集分别用 Strands Harness 与当前在用的 Claude Code 各跑一遍，模型尽量选同一档，避免混淆变量。
3. 每跑完一个任务，记录四项：是否一次通过、人工返工次数、消耗 token/费用、端到端耗时。
4. 交替顺序再跑一轮，排除顺序效应。

**判断有没有改善的指标**：

- **单位任务成本**：总花费 ÷ 通过任务数。这是原文 45% 主张的直接检验对象。
- **任务通过率**：一次通过的任务数 ÷ 总任务数，用来检验 “broadly comparable accuracy” 是否成立。
- **返工轮次**：失败后需要人工介入的次数，成本节省如果以返工为代价则得不偿失。
- **迁移成本摊销**：接入、配置、调试所花的时间，折算成需要跑多少任务才能把 45% 的节省赚回来。

**判定规则建议**：只有在通过率不低于现有方案（差距在噪声范围内）、且单位任务成本确实更低、且迁移成本可在可接受周期内摊平的情况下，才把它从 watch 升级为 try。任何一项不达标，都维持 watch 或 drop。
