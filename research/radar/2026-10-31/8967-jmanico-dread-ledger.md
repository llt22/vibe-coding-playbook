## 是什么

Dread Ledger 是 Jim Manico（manicode.ai / Manicode Security）开源的一套**面向 AI 编码智能体的安全日志埋点提示词集**（MIT 许可，仓库 30 stars）。口号是 "Leave the evidence. Bury the secrets."，目标是：**在已有应用上，以小步、可验证的波次（wave）补齐安全日志**。

它由几部分组成（据 README）：

- 9 个提示词，覆盖「评估 → 基础 → 关键 → 高 → 中 → 上下文 → 每波验证与上线 → 定向修复 → 持续变更复核」；
- 一份 90 条安全事件审查清单（`reference/security-events.md`），跨度包括身份、数据、基础设施、交付、AI agents、审计健康；
- 配套参考：Runbook（范围、关卡、可复用的私有账本）、Coverage（应用专属清单与证据要求）、Event contract（隐私、可信字段、兼容性、投递语义）、Verification（应用专属安全检查）。

它自称受同作者的 Trim Reaper、Grim Prompter 启发。本质上是把「安全日志该记什么」这一横向工程，拆成一份可被智能体按步骤执行的作业单。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

> 说明：本次材料只有 README，**提示词正文未抓到**，所以下面只复述 README 明确给出的调用顺序与约束，不臆造提示词内容。使用时需到仓库取对应文件。

**前置条件**：一个已有日志设施（logger）的应用；一个能读写该应用代码的编码智能体；有代码评审与独立部署流程；安全敏感场景需安全人员复核结论。

1. **打开被测应用**
   在编码智能体中打开待改造的应用（不是打开 Dread Ledger 仓库本身）。

2. **先给共享约束，再给评估提示词**
   先粘贴 `prompts/00-shared-instruction.md`，再粘贴 `prompts/01-assess.md`，并在其中**指明要审查的服务**。
   剪贴板方式下，还必须把 `reference/security-events.md`（90 条清单）一并附上；评估阶段会**逐条过完 90 项**，再补充该应用特有的要求。

3. **两种使用形态，二选一**
   - 文件式：把本仓库 checkout 的路径 + 选定提示词给智能体；**库引用在 Dread Ledger checkout 里解析，实际改动落在应用 checkout 里**。
   - 剪贴板式：见第 2 步，需附带 90 条清单。

4. **跑基础波次 Wave 0（必须先做）**
   用 `prompts/02-foundation.md`，内容包括：安全的 schema、接入**已有** logger、隐私、有界投递（bounded delivery）。README 明确要求：**先建立安全基础，再谈覆盖面**。

5. **之后一波一波地做，一次只做一波**
   顺序与范围（README 表格原文）：

   | 波次 | 目的 | 提示词 |
   | --- | --- | --- |
   | Assess | 盘点代码、控制措施、消费方、证据缺口 | 01 · Assess |
   | Wave 0 · Foundation | 安全 schema、接入已有 logger、隐私、有界投递 | 02 · Foundation |
   | Wave 1 · Critical | 特权动作、敏感操作、监控被篡改 | 03 · Critical |
   | Wave 2 · High | 认证、授权、恢复、会话 | 04 · High |
   | Wave 3 · Medium | 校验、滥用控制、上传、工作流失败 | 05 · Medium |
   | Wave 4 · Lower-priority | 有用的生命周期与调查上下文 | 06 · Context |
   | 每一波 | 对抗性测试、消费方检查、canary 与回滚计划 | 07 · Verify and roll out |
   | 定向修复 | 已有日志泄露数据、注入记录或耗尽资源 | 08 · Repair |
   | 持续 | 审查 diff 是否丢失覆盖或 schema 漂移 | 09 · Change review |

6. **每波结束必须验证再进入下一波**
   跑 `prompts/07-verify-and-rollout.md`：对抗性测试 + 消费方检查 + canary + 回滚计划。**未验证不得开下一波。**

7. **保留账本（ledger）**
   每波结束后保留产出的 ledger，作为下一次会话的输入——这是跨会话记忆的载体，也是后续波次和复核的证据。

8. **排序原则（可照抄的判断规则）**
   - 波次优先级反映的是**覆盖缺口的后果**，不是事件的日志级别；
   - **可以按你自己应用的风险重排波次**，但安全基础必须先立；
   - **部署与本地实现分离**；
   - 智能体的报告里必须**列出没有执行的检查**（report checks not run）。

9. **两个专项入口**
   - 已有日志出问题（泄露数据 / 可被注入记录 / 耗尽资源）→ 用 `prompts/08-repair.md`；
   - 日常改动后 → 用 `prompts/09-change-review.md` 审 diff，找覆盖丢失与 schema 漂移。

**1. 能力发现**

## 怎么试、怎么验证

**最小试用（建议 1–2 天）**
1. 选一个**非生产**的中小服务（有 logger、有测试）。
2. 只跑第 2 步（shared instruction + 01 Assess），产出 gap 清单，**先不改代码**。
3. 人工按 90 条清单抽查其中 10 条判定，记录对/错。
4. 通过抽查后，只做 Wave 0（安全 schema + 接入已有 logger + 隐私 + 有界投递），部署到测试环境，不碰生产。
5. 保留 ledger，再跑一次 `09 · Change review` 做自检。

**判断有没有改善的指标**
- *清单准确率*：抽查 10 条中，智能体对「已覆盖 / 缺失」的判定正确条数（建议 ≥8/10 才继续）。
- *诚实度*：报告中「未执行的检查」是否真实罗列（故意留一个未跑的检查，看它是否漏报）。
- *隐私底线*：Wave 0 后检查日志中**不出现**凭证、令牌、个人敏感字段；schema 是否满足 event contract 的可信字段与兼容性要求。
- *可回滚性*：是否有明确回滚步骤，且实际演练一次成功。
- *回归探测*：故意删掉一行已有日志，看 `09 · Change review` 是否指出覆盖丢失——这是唯一能低成本量化的「它到底有没有用」。
- *成本*：全程 token 与时长，对比人工补同类埋点的工时。
- *对照实验（可选但有说服力）*：同一服务，用流程与不用流程各补一次同类埋点，按 90 条清单人工核对漏项数与返工次数。

**升级 / 放弃条件**：抽查准确率低、或 Wave 0 反复引入隐私问题 → 降为 study，只借「分波次 + 每波验证 + 持久化账本」这个流程骨架，不再用其提示词。
