**最小试用**：不安装插件也能验证这个思路。选一个中等规模的真实任务（例如“给某模块加一个功能”），做两轮对照：

- A 轮：全部在主 Agent 内完成。
- B 轮：手动把“源码调查（这个功能涉及哪些文件、现有实现是什么）”和“代码审查（改完之后挑问题）”各拆成一次独立会话，只把结论带回主会话，主会话只做实现与整合。

若确认有效，再考虑用 pi-subagents 把 B 轮流程自动化（并行以及后台运行带来的收益，要在 B 轮已有收益的前提下再评估）。

**判断指标**：

1. 主会话的上下文占用或对话轮次（预期下降）；
2. 端到端完成时间（并行和后台是否真的省时，还是被协调开销抵消）；
3. 审查环节发现的有效问题数（拆出去后审查质量是否下降，因为子 Agent 缺少主会话的隐含背景）；
4. 返工次数与返工原因（是否因信息在子 Agent 之间传递丢失）；
5. 人工介入次数。

**结论门槛**：如果第 1 项明显下降、第 3 项没有变差，再考虑把“按角色拆分只读型支线任务”写进手册；否则只保留为主 Agent 上下文管理的备选手段。
