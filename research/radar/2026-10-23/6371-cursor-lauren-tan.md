**最小试用方式（在完成上面「具体做法」第 1–4 步核实之后）**：

1. 选一个**有测试、体量小、失败可回滚**的仓库，不要用主分支或生产仓。
2. 只启用一条流程先跑——建议从「修 bug」入手，因为它有客观成功判据（测试从红变绿），比「加功能」好验证。
3. 连续跑 5–10 个真实小 bug，**每个都保留**：原始 issue、代理生成的补丁 diff、审阅 Agent 的结论、人工最终是否接受。
4. 对照组：同一批 bug 用你现有的方式（自己改 / 单代理直接改）处理，记录耗时与返工。

**判断有没有改善的指标**：

- **一次通过率**：补丁无需人工修改即被接受的比例。这是核心指标。
- **审阅 Agent 的有效性**：被审阅 Agent 拦下、且人工复核确认「确实该拦」的比例（准确率）；以及被放行、但人工发现问题的比例（漏检率）。漏检率高说明这道门禁是装饰。
- **范围蔓延**：补丁改动文件数/行数 是否超出 issue 涉及的模块。多代理最容易在这里出问题。
- **人工介入次数**：每个任务你需要敲几次键盘、做几次决策。流程再漂亮，如果人工介入不比原来少，就没有价值。
- **隔离是否真的生效**：跑完后 `git worktree list` 是否干净、有无残留分支和目录。残留说明工程化程度不足，长期用会污染仓库。
