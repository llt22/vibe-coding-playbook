## 是什么

Anthropic 与 Theorem 合作的实验报告：用 Claude 为 123 个 OSS-Fuzz 开源库中的 239 个 fuzz 入口点，在**编译后的 RISC-V 机器码层级**写出无崩溃证明（共约 1.8 亿行 Rocq 证明，典型单个证明约 60 万行，覆盖中位数 18,000 条 RISC-V 指令的二进制），并在过程中发现并修复了数百个传统 fuzzing 难以触发的 bug。

核心思路是把已有的 fuzz 测试「升级」为规范：fuzz 测试断言「这个入口点在任何输入下都不崩溃」，把这个断言形式化为「对所有小于 64MB 的输入、所有被建模的 Linux 行为与内存布局，程序都正常退出、不触发内存安全错误或断言失败」，让 Claude 去证明它。证明通过则 fuzz 在该入口点上再也找不到 bug；证明失败则反例即 bug 线索。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

> 前提说明：原文**没有给出可直接复制的命令、配置或完整提示词**，只给出流程、参数、信任边界与成本数据；落地入口是原文提到的两件事——定理公司 Theorem 提供「代为运行同一流水线」的服务，以及发布了一个帮助开发者上手自验证的 **Claude skill**。以下步骤是对原文流程的还原，标注了每步前提。

1. **选目标：挑一个已有 fuzz 入口点的库。**
   前提：项目在 Google OSS-Fuzz 中，或至少有一个作者自己写的、以「崩溃即 bug」为判据的测试入口（entry point 接收输入，触发崩溃即失败）。原文明确 fuzz 测试里常含高价值性质（编解码往返、幂等、代数律、差分测试、自一致性、与参考实现等价），证明「该测试永不崩溃」等价于证明该性质本身。

2. **把库和它的 fuzz 测试编译成 RISC-V 可执行文件。**
   前提：单线程、静态链接（musl libc）、固定内存预算、运行在 Linux 上。这是本方法的硬性适用边界，超出即不在证明范围内。原文另提到 OSS-Fuzz 会用 AddressSanitizer 插桩，使非法内存访问即刻崩溃；因此「不崩溃」也覆盖了 ASan 能捕获的内存错误。

3. **取得机器语义模型。**
   前提：Theorem 提供的 RISC-V 指令语义 + Linux 进程语义（原文称这些语义与部分证明已公开，可独立校验与复用）。这是必须信任的三个构件之一。

4. **机械生成规范（spec）。**
   由「可执行文件 + 语义模型 + 目标性质」三者机械导出待证定理。目标性质可写成：
   ```
   对所有小于 64MB 的输入，以及所有被建模的 Linux OS 响应与内存布局，
   该程序都正常退出，不触发内存安全错误、不触发断言失败
   ```
   前提：64MB 这个上界是参数，原文脚注说明「提高它只需要很小的人工改动参数、重新生成规范，再让 Claude 重新证明」。

5. **让 Claude 写证明，由外部检查器判定。**
   前提：预算充足（原文提到证明可能消耗数亿 token；其评测设置为每个任务 5M token 预算、三次独立单智能体尝试，首次完成即算证明成功）。判定权在 Rocq 内核，不在模型自称。

6. **证明卡住时，允许 Claude 直接改被测代码，然后重生成规范、重证。**
   前提：必须防 reward hacking。原文的做法是：
   - 对任何补丁施加惩罚（penalized any patch）；
   - 要求额外证明「这个补丁改变了哪些输入、改变了多少个」（加分项）；
   - 记录并审计所有补丁，检查是否存在「把程序改成永不会崩」这类作弊模式。
   流程为：Claude 打补丁 → 用打过补丁的代码重新生成规范 → Claude 继续证明新规范。

7. **明确信任边界，只审三样东西。**
   大量证明代码几乎不需要人工逐行审阅；开发者需要信任的只有：
   - RISC-V 与 Linux 进程的形式化模型；
   - 实际被证明的定理陈述（spec 是否写对了现实需求）；
   - Rocq 证明检查器本身（技术上还包括其依赖的硬件、OS、OCaml 编译器）。
   前提：接受「形式化验证 ≠ 无 bug」——检查器无法判断规范是否与现实一致。

8. **给多个 agent 一个共享工作区，让它们互相抄证明。**
   前提：证明像软件一样可递归复用，越小越可复用。原文数据：共享工作区时 agent 比单干少用 17% token，且有 agent 在单干失败后靠共享成功；36 个任务中 34 个完成的证明里，有 30 个单干成本更高。

9. **按依赖幂律排序，优先验证被广泛复用的共享库。**
   原文指向 Theorem 对 Nix 生态的路线图（glibc、OpenSSL、cURL 等）；包级复用意味着每个依赖只需被证明一次。

10. **先小规模试点，再上量。**
    原文自陈：目前规模是「数周内 239 个入口点」；并鼓励「所有开发者去探索用 LLM 做形式化验证，尤其是那些以前用较弱模型试过、觉得不行的人」。

## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）

- **能力发现**：原文展示了多数人不会想到交给 AI 的工作——(a) 在机器码层（RISC-V 汇编）为真实生产级库写安全性证明；(b) 在证明过程中顺手发现 fuzzer 极难触发的 bug：某解压器副本中约 20MB、具有罕见布局的输入才触发的计数器下溢导致越界写；某图像解码器需要 64MB 输入、超 2GB 内存的越界读；某库需要跨同一文件两个句柄的特定调用序列的越界读；libexpat 中 CVE-2026-56132 的重新发现（需深层嵌套输入）；以及根本不崩溃的逻辑 bug（某库用于限制应用可加载哪些文件的特性并非总是生效）；(c) 为完成 cpp-httplib 的证明，Claude 不得不在机器码层证明 libc++ 红黑树重平衡算法确实把树深压在对数界内；(d) 自主生成 ISA 形式化语义（x86），过程中发现官方参考文档中数百处错误和少量硬件 bug；(e) 从 RFC 1950 这样的技术文档写出形式化规范，再证明 Linux 内核里的 zlib 实现符合它。
- **任务匹配**：适合的是「目标明确、可机械判定成败、需要吞吐数百万行代码」的长程任务——证明写作交给前沿模型（Claude），正确性判定交给符号检查器（Rocq 内核、Verus 用于 Rust 程序），机器语义交给专门团队（Theorem）。原文另用 Verus 让 Claude 写 Rust 版 Python 解释器并证明其符合论文中的 CPython 语义，再用 170 万个随机 Python 程序实测，99.95% 行为一致。多个 agent 并行 + 共享工作区优于单 agent 单干。
- **条件供给**：需要 (a) 已有的 fuzz 入口点作为规范来源；(b) 可编译成 RISC-V 静态单线程二进制的构建环境；(c) RISC-V 与 Linux 进程的形式化语义模型；(d) Rocq 证明检查器；(e) 可以重新生成规范的流水线（改参数即重生成）；(f) 允许 agent 直接改代码的权限 + 补丁审计与反 reward hacking 的激励设计；(g) 极大 token 预算与时间（数周、数亿 token 量级）；(h) 明确的信任边界清单，把人工审查压缩到三个构件。
- **主动推进**：具备「时间/状态触发 + 持续完成」的形态——证明是长程自动任务，agent 在数周内自主推进，遇到 bug 不停下来等人，而是自行打补丁 → 规范随代码状态重新生成 → 继续证明（状态触发式重跑）；共享工作区让后来的 agent 复用已完成的证明（事件触发式复用）。原文也说明模型能力提升会持续降低这条路线的单位成本（Opus 5.5 相比 Opus 5 用约少 40% 的 token 证完 36 个任务中的一半）。
- **效果验证**：验证判据是**机器可判定的**——Rocq 内核检查通过即证明成立，不依赖模型自评；原文公开部分证明、语义与未证成的规范以便他人独立复核，并明确可信基只有三项。过程性指标包括：被证明的入口点数、单证明 token 成本、共享工作区带来的 token 节省（17%）、以及实测一致性（99.95%）。另一类效果证据是「真 bug 被抓到并被上游修复」。

## 证据与局限

**原文给出的数据/案例**：123 个 OSS-Fuzz 库、239 个入口点、约 1.8 亿行 Rocq 证明、典型证明约 60 万行、被证二进制中位数 18,000 条 RISC-V 指令、输入上界 64MB；36 个小型验证任务的成本对比（Opus 5.5 用少约 40% token 证完一半，5M token 预算 × 3 次尝试）；共享工作区省 17% token、34 个完成的证明中 30 个单干更贵；Rust 版 Python 解释器在 170 万随机程序上 99.95% 与 CPython 一致；某广泛使用的 PDF 阅读器「一周内发现的安全 bug 数量相当于通常一年的报告量」；某潜伏十余年的逻辑 bug；x86 语义生成过程中发现官方文档数百处错误。

**属于作者主张、未见完整证据的**：「据我们所知，这是首次在汇编层用 AI 对生产软件做大规模形式化验证」；「这条路线的成本会随模型变强持续下降」；「形式化验证将像今天的 fuzzing 一样普及」。另外「修了数百个 bug」的具体清单未在正文全量给出。

**适用条件与硬局限（原文自陈）**：
- 证明对象是**单线程、静态链接 musl libc 的 RISC-V 二进制**，而现实中多数人用 x86/ARM + 动态链接 glibc，模型与真实机器存在差距。
- 「不崩溃」的规范覆盖面有限：ASan 并不检测所有内存安全 bug；未验证每个库的全部入口点；即使全部入口点验证完，也不覆盖整个库（尤其死代码）；调用方误用库导致的内存破坏不在范围内（需要为每个公开函数写调用契约并强制遵守）。
- 可信基本身可能有 bug：语义模型、定理陈述、Rocq 检查器（以及其依赖的硬件/OS/OCaml 编译器）。
- 成本：单个证明可能消耗数亿 token；本方法的经济性依赖复用。
- 允许 agent 自改代码会引入 reward hacking 风险，原文只用「惩罚补丁 + 要求证明改动范围 + 审计」缓解，并非根除。
- 原文未提供可复制的命令、配置文件或提示词，复现需通过 Theorem 的流水线或其 Claude skill，这是把它当作「手册条目」时的最大缺口。

## 怎么试、怎么验证

**最小试用方式（建议 2–4 周、单项目）**

1. 选 1 个你依赖的、在 OSS-Fuzz 中且有活跃 fuzz 入口点的开源库（优先选被多个项目依赖的共享库，享受复用红利）。
2. 通过原文提到的两条入口之一启动：联系 Theorem 让其跑同一流水线，或用其发布的 Claude skill 自行起步；明确要求使用 RISC-V + Linux 语义模型 + Rocq 检查器这套组合，并锁定「单线程静态二进制、输入上界 64MB」的假设写进报告。
3. 选 1–3 个入口点，给每个证明设置固定预算（对齐原文评测：5M token × 3 次独立尝试），记录是否首次尝试完成。
4. 强制要求：任何代码补丁都要输出「改变了哪些输入、改变了多少」的说明，并保留补丁 diff 与日志供人工审计（这是原文的反 reward hacking 措施，必须照做）。
5. 只人工审查三样东西：语义模型版本、被证的定理陈述、检查器版本；证明本体交给 Rocq 内核。

**判断有没有改善的指标**

- **硬指标（通过/不通过）**：Rocq 内核是否接受了该入口点上「无崩溃」的定理；被证的定理陈述是否确实表达了你关心的性质（例如编解码往返、幂等），而不是一个空泛命题。
- **相对 fuzzing 的增量**：证明完成后，对同一入口点继续跑 fuzzer，看是否还能找到该入口点范围内的新崩溃；同时统计「证明过程中发现并已被上游确认修复的 bug 数」——后者即使证明最终未完成也构成收益（原文明确：即使目标未达成，尝试过程本身就会产出真 bug）。
- **成本指标**：单入口点 token 消耗、首次成功率、引入共享证明工作区前后的 token 差异（原文基线为省 17%）。
- **可信基增量**：纳入信任清单的构件数量是否被控制在可审计范围（语义模型、定理陈述、检查器），以及是否有独立第三方复核了证明。
- **反作弊检查**：审计所有自动补丁，确认没有「把程序改成永不崩溃」式的规避；补丁后原有测试套件与行为测试是否仍全部通过。

**何时判定不适合继续**：目标代码是多线程/动态链接/非 RISC-V 部署且短期无法建模；关心的性质超出入口点覆盖范围（如调用方误用、死代码）；预算无法支撑数亿 token 量级的单次证明且无可复用的既有证明。
