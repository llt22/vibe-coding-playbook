## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

原文没有提供可复制的命令或配置。以下是从原文提炼、且原文确实描述过的可迁移做法，每条标注前提与原文依据强度。

1. **先量化，再决定是否动基础设施。** 前提：能取到这些指标。原文给出的判据维度是：每日合并变更数、每日 checkout 次数、主干历史体积、工作副本体积、镜像运维成本。原文数值（仅作数量级参考，不可当阈值照抄）：主干历史约 100 GB、压缩工作副本 25 GB+、每天约 2,500 万次 CI checkout、朴素拉取约 600 PB/天、峰值运营数百个内部 git 镜像。
2. **没到上述量级就不要自建版本控制系统。** 前提：你能接受 git 现状。原文的建议是改造 git 的服务端而非替换它——服务端可以有和客户端不同的架构、可以提供完整的服务端 RPC、协商协议不一定要保持现状、稀疏/浅克隆特性应能组合使用。
3. **把整段子系统交给代理重写，而不是让它逐行改。** 前提：有一个能跑的原型、有明确必须保留的隐式不变量、有可验证的测试。原文案例：手写的 git→Scion 摄取管线原型交给内部早期模型，**无额外指令**的情况下重写为内存占用减少 20 倍、速度提升 4 倍，且保留了摄取顺序与数据结构的隐式不变量。
4. **评审只看变更意图，不逐行读代码。** 前提：每个 change request 写清动机，且团队维护了系统级约束清单。原文：团队成员仍然评审每一个 change request，但看的是意图而非每一行。
5. **由人明确说“不”，列出禁止模式。** 前提：有人能判断系统级权衡。原文点名的两类失控：(a) 为满足某个模式而破坏核心系统约束——例如有系统线性读 commit log 来查某变更何时合入主干，而不是问评审工具；(b) 对抗式评审导致的过度工程——例如对某个已知可信的内部服务加了过量校验和复杂度。
6. **让代理补齐重型测试。** 前提：存在可被模拟的基础设施交互。原文：为每一处非平凡的基础设施与源码管理交互建立密闭仿真（hermetic simulation），加上 fuzz 和精细化限流，作者据此称这是他们测试最充分、防御最完整的代码库之一。
7. **按组件设置常驻监控“superfan”。** 前提：该组件有遥测与日志访问权限、有可看的健康图表。原文做法：为每个组件建 Slack 频道，派一个 Claude 实例只盯这一个组件的健康，给它遥测与日志访问权，让它像“无事可做、只反复刷图表找异常”的资深工程师；保留传统告警作为并存手段，superfan 用于发现告警覆盖不到的细微新问题（原文举了 scion-daemon、scion-cache、Antique 合并队列等 superfan）。
8. **重审人类尺度的流程。** 前提：能承担合并后测试的成本。原文：合并队列的全局仓库锁在代理规模下无法照搬，改为投入**合并后 + 部署前**自动化测试；并发变更会冲突，但作者称 Claude 修冲突通常比人发现冲突还快（此为客户主张，无数据）。
9. **不要照抄的部分。** 原文自述：Scion 不面向通用场景，只在“数万工程师或大量代理疯狂写代码”的巨型 monorepo 下成立；且 Anthropic 内部可花的 token 远超一般企业；迁移意味着整条开发生命周期（评审、搜索、CI）都要重做。

- **主动推进**：可被状态触发的持续工作有两类——superfan 对单个组件健康指标的持续巡检；合并后/部署前自动化测试与（依赖 API 的）自动 bisect、revert 流水线。

## 怎么试、怎么验证

先明确：**不自建版本控制系统**，只试三条协作做法，各自独立、可分别回滚。

- **试用 A：单组件 superfan（最小成本，建议先做）**
  - 做法：选 1 个已有遥测与日志的服务，建一个频道，给一个代理实例只读的指标/日志查询权限，任务限定为“只盯这一个组件的健康，发现异常就在频道里说”，第一周只观察不改代码。
  - 指标：指出的有效异常数 / 误报数；从异常发生到被指出的时延；与现有告警的重叠比例；团队是否因此减少手工查图时间。
  - 判断改善：有效异常 ≥ 现有告警未覆盖的若干条，且误报可控、时延短于人工巡检周期。
- **试用 B：意图级评审 + 显式“不”清单**
  - 做法：要求每个代理提交的变更写清动机与触碰的系统约束；评审只回答三个问题（意图是否对、是否违反硬约束清单、是否属于过度防御/过度工程）；维护一份“禁止模式”清单并在发现后追加。
  - 指标：返工率、被拦下的过度设计变更数、单次评审耗时、逃逸到生产的缺陷数。
  - 判断改善：评审耗时下降而逃逸缺陷不上升，或缺陷下降而耗时持平。
- **试用 C：整段子系统重写**
  - 做法：挑一个有小规模测试保护的原型模块，一次性交给代理重写，明确列出必须保留的隐式不变量，不接受“顺手加防御性校验”。
  - 指标：重写前后内存/耗时对比（用你自己的基线，不要引用原文的 20x/4x）、测试通过率、人工返工小时数、是否引入对内部服务的过度耦合。
  - 判断改善：资源或时延有可测改善，且不变量全部保住、返工小时低于自己重写的估计。
