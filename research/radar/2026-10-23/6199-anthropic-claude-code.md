**做法 A：堆栈跟踪 + 文档 → 控制流（对应“安全”场景）**

1. 前提：你手上有一次真实故障的完整堆栈跟踪（不是截断的一两行），以及与该故障相关的文档：内部 runbook、所用框架或库的版本说明、相关接口文档。
2. 把堆栈跟踪原文和文档片段一起给 Claude Code，不要只丢堆栈。原文强调的是“堆栈跟踪 + 文档”这个组合，单独给堆栈只能得到泛泛的猜测。
3. 明确要求它输出控制流，而不是直接给修复补丁：让它从抛出点往回，逐帧说明调用路径、每层的输入状态、哪个分支导致走到这里。
4. 用它给出的控制流去对照代码验证，再决定改哪里。

```text
- 结合文档说明这段代码本应遵守什么约定
暂时不要给修复方案，先给控制流分析。

[堆栈跟踪]
...

[相关文档]
...
```

**做法 B：解释陌生代码（对应“推理”场景）**

1. 前提：有一段你需要理解但暂时读不懂的代码，可能是别人的模块、第三方库或遗留系统。
2. 直接把代码给 Claude Code，让它先讲整体职责，再逐段讲，而不是直接问“这段有什么问题”。
3. 原文的对比是“1 小时的搜索变成 10–20 分钟”，即替代的是查文档、翻资料、找示例的那段时间，不是替代读代码本身。
