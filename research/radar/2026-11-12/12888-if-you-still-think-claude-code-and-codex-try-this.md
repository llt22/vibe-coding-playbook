## 是什么

一条写给 Claude Code / Codex 这类编码代理的英文提示词，任务是让代理在既有应用里系统找出“happy-path 债务”（happy-path debt）：那些只有在数据加载快、不报错、列表非空、文案短、屏幕宽时才正常的界面，然后逐个组件补齐缺失状态与布局断裂，要求不改设计、不破坏现有功能，并按文件给出“改动前 vs 现在”的对照总结。作者的一句论断是：代理是照着 demo 写的，demo 里一切顺利，真实使用不是。

原文除提示词全文和这句论断外，没有步骤、配置、案例或数据。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

1. 前提：代码库能在本地跑起来、工作区干净，先开分支以便回滚。

```
git checkout -b happy-path-debt
```

2. 前提：编码代理（原文点名 Claude Code 或 Codex）已能读写该仓库。原文未要求任何额外配置、插件或文件。

3. 原样粘贴提示词：

```text
Find all the happy-path debt in my app: every screen that only works when data loads fast, nothing fails, lists aren't empty, text is short, and the screen is wide. Fix missing states and layout breaks, one component at a time, without changing my design and without breaking anything. Summarize by file: what happened before vs. how it works now.
```

4. 按“一个组件”为单位分批推进。原文要求 one component at a time，但提示词本身是一次性要求“全应用找 + 逐个修 + 汇报”，中大型仓库一轮很可能做不完；可按屏幕分批，在提示词后追加限定（此句为落地建议，非原文）。

5. 对照原文列出的五个条件逐个检查该组件的改动是否覆盖：加载慢/加载中、请求失败、列表为空、文案过长、屏幕变窄。

6. 审每一轮 diff：确认只是新增状态分支与布局兜底，没有改动设计基线（配色、间距、字体等），对应原文的 without changing my design。

7. 每轮结束后跑构建与现有测试，对应原文的 without breaking anything；不要靠代理自述“没破坏”。

8. 用原文要求的汇报格式做验收清单：按文件列 before / after，与实际 diff 抽查对照。

## 怎么试、怎么验证（最小试用方式和判断有没有改善的指标）

判断指标：

- 状态覆盖率：该页面 5 类状态（慢加载 / 失败 / 空列表 / 长文案 / 窄屏）试前试后各有几个有处理，用清单打勾对比。
- 回归：构建与现有测试是否全绿；diff 中与状态无关的样式/设计改动应为 0。
- 成本：审 diff 与返工耗时，对比手写这些状态所需时间。

若覆盖率明显上升且回归为 0，再扩大到整页乃至整个应用，并按组件拆成多批执行。
