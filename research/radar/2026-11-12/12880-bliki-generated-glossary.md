## 是什么

在专业领域（作者举的例子是任何规模稍大的组织的运营）里，LLM 会大量遇到训练集中没有的内部词汇：自造词、缩写，以及**认识但被用在陌生含义上的常见词**。作者认为后者最容易造成混乱。

做法是：拿组织内部的现成文本当语料，让 LLM 抽出一个领域术语清单并写成词典式定义，人类专家审校后，把这份 glossary（术语表）放到任何其他 LLM 都能查询的地方，作为它们在该领域工作时的上下文层；并像代码一样版本化、按 bounded context（DDD 的有界上下文）分片、定期刷新。

作者把它定位成“领域建模、构建本体、在企业数据里搭显式 context 层”这些工作里一个简单但有用的组成部分。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

> 说明：原文给的是一套**流程与要求**，没有给出提示词原文、工具配置或命令。下面按原文复述流程，凡原文未写的部分不补。

**前提**：能拿到组织内部文本（文档、邮件、聊天记录）；有愿意花时间审校的领域专家；有一个 agent 能读取的存放位置；能接入版本控制。

1. **准备语料**。来源可以是组织内的文档、邮件、聊天记录；音频/视频的转写“在某些情况下有帮助”，但作者说多数组织产生的文本已经够用，不必强求。
2. **让 LLM 抽术语**。要求它同时找两类东西：
   - 单个词，以及“经常一起出现、构成一个有意义的术语”的多词短语；
   - **对它来说是新的词**，以及**它认识但被用在陌生含义上的词**（原文特别强调后者最容易造成混乱）。
3. **让 LLM 生成定义**。要求：
   - 输出格式跟词典一致，重点是**精确与简洁**；
   - 同一个词有不同用法时，给出**替代定义**，并注明这些差异出现在什么上下文中。
4. **人类专家审校**。由该领域的专家审阅草稿，改掉 LLM 理解拧了的地方。这一步是原文明确要求的，不可省。
5. **放到其他 LLM 能查的地方**。形态要求：便于 LLM 查询，且**模型为找到某个词的含义所消耗的 token 尽量少**。
6. **表很大时的降 token 做法**：初始上下文里只放**术语清单 + 指向定义的链接**，模型在工作中只去取它真正需要的那些完整定义。
7. **版本控制 + 定期刷新**。放进版本库以便看到它随时间怎么变；设定日程，由 agent 和人类一起按固定间隔复审刷新。
8. **按 bounded context 分片，不要做单一标准表**。大组织在不同地方对同一词有细微不同的定义；代码库本身就是一个特别值得单独做一份的上下文（能看出术语在代码里怎么用）。有时一份表能跨几个上下文，有时每个上下文各做一份、让 LLM 按任务取相关的那几份。作者的原话是：劝所有人**抵制做一份统一标准术语表的诱惑**，他说自己还没见过这种做法成功；术语表的价值往往不在钉死唯一定义，而在**凸显它在不同上下文中的不同用法**。
9. **跨上下文比对**。有多个上下文时，可以比较不同术语表，或让 LLM 去比较并描述用法的差异；拿代码派生的术语表和人写的文本对比“特别有启发性”。
10. **收录“不该用的词”**。术语表可以包含禁用词，并给出应当改用哪个词；废弃词用这种方式处理，条目里标明该词在什么时间段内有效。
11. **在下游用起来**：
    - 指导代码生成，让生成的软件里的命名贴合企业词汇；
    - 在 harness 里放 sensor 检查这种用词，既查软件内部，也查用户界面；
    - 注意生成代码或文档时可能引入新的 bounded context：**面向客户的 UI 不应暴露内部名称**，因为客户处于与“服务他们的那部分企业”不同的上下文。

## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）

- **能力发现**：原文明确交给 LLM 的新工作有两类——从大批内部文本中抽取领域术语（包括识别“常见词被非常规使用”这种很难规则化的情况），以及比较不同上下文的术语表、描述用法差异。作者还把它接到代码生成与 harness 里的用词检查上。

## 怎么试、怎么验证

**最小试用（建议 1–2 天）**：

1. 选**一个** bounded context（比如一个子系统，或一个代码库连同它的周边文档），不要一开始就做全公司。
2. 取该上下文内 20–50 份文档/邮件/聊天记录（原文只说“组织内材料”，数量需自己定）。
3. 让 LLM 按第 2 步的两类目标产出术语候选清单。
4. 让 LLM 按词典格式写定义；一词多用时给替代定义 + 上下文说明。
5. 请领域专家用 30–60 分钟审校，记录改了哪些、为什么改。
6. 存成 markdown 放版本库；同时按“术语 + 链接”的形态做一份精简索引版。
7. 挑两个该领域的真实任务（例如生成一段业务代码、写一份内部说明），各做两遍：一次不带术语表，一次把术语表放进上下文。

**判断有没有改善的指标**：

- **抽取质量**：专家认为“本该入表”的术语里，LLM 抽到了多少（召回）；专家审校时被改动的条目占比（定义准确率的反向指标）。
- **下游效果**：生成代码/文档中内部术语误用的次数；面向客户产出中泄漏内部名称的次数；因术语理解错误导致的返工轮次。
- **成本**：每次刷新产生的 diff 大小、人工复审耗时；带术语表 vs 不带时，完成任务所消耗的上下文 token 与总时长的变化（用来验证“索引 + 链接”是否真的省 token）。
- **趋势**：如果第一轮专家改动很多、第二轮刷新后改动明显变少，说明这套流程在收敛；否则可能是语料或抽取目标设错了。
