## 怎么试、怎么验证

**最小试用（半天）**：
1. 选 2 个你正在用 agent 推进的项目，把两边**重复出现**的规范片段（角色设定、代码风格、常用技能说明）抄出来，合并成一份。
2. 建一个私有 start repo，按上面的示例放 `agents.md`、`skills/`、`design.md`、`wiki/`，并写一份 README，说明“每个文件解决什么问题、项目侧怎么引用”。
3. 在其中一个项目里删掉重复配置，改为引用 start repo；另一个项目保持原样作为对照。
4. 跑同一批真实任务（建议 5–10 个，覆盖两种以上任务类型），记录差异。

**判断有没有改善的指标**：
- **重复配置量**：同一段规范在多少个 repo 里各有一份（目标：从 N 降到 1）。
- **规范漂移**：改了规范后，需要手动同步几个仓库（目标：1 个）。
- **起手成本**：在新项目里从零到“agent 按你的规范干活”所需的操作步数与耗时。
- **上下文开销**：每次会话为加载 steering 文件消耗的 token 或用时是否明显上升，也就是集中化换来的成本。
- **输出一致性**：跨项目同一类任务（例如代码评审意见、提交信息风格）的合格率，由人工盲评对照组的差异。
- **回退信号**：一旦出现“为了符合通用规范反而要写一堆项目特例覆盖”，就说明分层没有设计好，该考虑在 start repo 里做“基础层 + 项目覆盖层”。

**建议**：先把它当作组织思路（study）使用；等你补上自己的指针文件写法和分层覆盖规则，并且对照实验显示重复配置确实减少、输出没有变差时，这个方案就可以升级为 try，写进手册。
