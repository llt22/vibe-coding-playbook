## 是什么

AWS 开源了一个 agent 评测框架 UAEF（Universal Agent Evaluation Framework，据推文描述为“framework-agnostic”，即与 agent 实现框架解耦）。

它要解决的是一个工程问题：团队不停重构 agent 时，如何有一套稳定、可复用的评测体系，而不是每次改完只看到一个平均分。推文转述的设计要点有五条：

1. 最前面加一层**转换器**：无论单步问答、多轮对话还是多智能体协作，都先把消息、工具调用、交接记录转成统一的标准轨迹，让后面的评测引擎不用关心 agent 用什么框架写的。
2. **按场景选指标**，不要一上来把所有指标全跑一遍（订机票的 agent 和查公司制度的问答 agent 评测方式完全不同）。
3. 打分时**能用代码直接比对的绝不用大模型**；必须用大模型当裁判时，把评分标准和被测内容分开发送、对内容做转义隔离，并强制裁判原封不动摘抄原文依据，原文核对不到则该次打分作废。
4. 每次跑测**绑定当时的配置和 Git 提交记录**，与基线版本逐项对比，某项指标跌幅超过 5% 就报告出来，避免平均分上涨掩盖关键功能倒退。
5. 报告**分两层**：第一层是纯数学计算的统计分布（不用大模型，保证同数据每次结果一致），第二层用大模型推演本次改动引发的问题，并给出下一轮怎么改的具体假设。

**重要限定**：本条材料是第三方推文正文，不是 AWS 原文；推文里的 GitHub 和博客链接在采集时都被截断了（`https://` + `github.com/awslabs/uaef` 分两行、`aws.amazon.com/cn/blogs/machi ne-learning/uaef-...` 中间断行），无法打开核对仓库内容与博客细节。所以下面只能给出流程骨架，没有可复制的东西。

## 具体做法

（前提：材料只提供了流程层面的描述，**没有给任何命令、配置、提示词或代码**。以下每一步都标注材料依据的强弱；具体实现需回到原文补齐，不要照本文臆造。）

1. **先建轨迹适配层**。前提是你使用的 agent 框架能导出结构化的消息、工具调用与多智能体交接记录。为每一种 agent 形态写一个转换器，输出同一种“标准轨迹”结构；评测引擎只读标准轨迹，从此与框架解耦。（依据：推文明确描述，但未给字段定义。）
2. **建立“场景 → 指标集”的映射**，每个场景只跑该场景相关的指标，不做全量跑。（依据：推文明确主张，但未给示例映射表。）
3. **逐条打分，把能写成断言的都写成代码断言**（精确匹配、结构校验、数值范围、必含字段等），只有代码判不了的主观质量才交给大模型裁判。（依据：推文明确主张“能用代码直接比对绝不用大模型”。）
4. **若用 LLM 裁判，做三件事**：① 评分标准（rubric）与被测内容分开发送，不让被测输出进入指令区；② 对被测内容做转义隔离；③ 强制裁判输出必须原样摘抄支撑结论的原文片段，再加一步程序化核对——在原始输出里找不到这段摘录，该条打分直接作废。（依据：推文明确描述，这是本条目最有移植价值的一条，且不依赖 UAEF 本身。）
5. **每次跑测固化环境快照**：记录当时的配置与 Git commit，结果与基线逐项对比而不是只比总分，对每一项设置回退阈值；推文给的阈值是**单项跌幅超过 5% 就报告**。（依据：推文明确给出的唯一具体数值。）
6. **报告拆两层产出**：
   - 第一层：统计报告，纯数学计算生成分布，完全不用大模型，保证同一份数据每次跑出来绝对一致（可复现、可进 CI 做门禁）。
   - 第二层：让大模型基于第一层数据做归因，说明“这次改动导致了哪些问题”，并给出下一轮怎么改的具体假设，作为下一次实验的输入，闭合回路。
7. **回路闭合**：第二层产出的假设进入下一轮改动 → 再次跑测 → 与基线逐项对比，形成闭环。（依据：推文标题/正文中的“closed-loop”表述与第 6 步描述可对应。）

## 怎么试、怎么验证

（以下为调研建议，材料未给具体做法与数字。）

**最小试用方式**：

1. 不做全量接入，先挑**一个**正在反复改的 agent。
2. 写一个最小的轨迹适配器，把它的运行记录（消息、工具调用、最终输出）落成统一的 JSON；用例数量按你自己场景定，够覆盖主要功能路径即可。
3. 给每条用例只写**代码可判**的断言（结构、必含字段、精确值、取值范围），暂时不引入 LLM 裁判。
4. 把这一轮的输出连同 Git commit 存成基线。
5. 下一次改动后重跑，做**逐项**对比（不是总分对比），先不设 5% 阈值，只观察每项的自然波动幅度。
6. 跑几轮摸清波动后，再为每项指标设自己的回退阈值（5% 可作为起点参考，不是定论）。
7. 最后再单点引入 LLM 裁判，只用在代码判不了的主观项上，并强制“摘抄原文依据 + 程序核对，对不上就作废”。

**判断有没有改善的指标**：

- **捕获率**：人工构造一次已知的功能回退，看这套流程能不能在总分不变的情况下把它报出来。这是验证“逐项对比”是否真的有效的最好办法。
- **可复现性**：同一份数据连跑两次，第一层统计报告应完全一致；出现任何差异说明第一层混入了非确定性成分。
- **裁判可信度**：LLM 裁判的“引用核对失败率”（摘抄在原文中找不到的比例）。失败率高说明隔离/转义没做好或裁判在编造，此时该裁判的分数不可用。
- **告警质量**：一段时间内触发的回退告警中，真正是问题的比例（误报率）与真正回退被漏掉的比例。
- **回路有效性**：第二层给出的“下一轮怎么改”的假设，有多少在下一轮验证中确实带来正向变化——这是判断这套闭环是不是只是“多写了一份报告”的关键。
