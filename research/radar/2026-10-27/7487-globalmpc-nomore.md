## 是什么

nomore 有两个相互独立的部分，可以分别采用：

1. **规则包（rule pack）**：作者抓取 `anthropics/claude-code` 仓库中带 `area:model` 或 `data-loss` 标签的 issue，人工挑出 20 条「一条 CLAUDE.md 规则就能改变的行为」，做成一个可直接下载的 Markdown 文件。README 列出前 5 条：不写没有信息量的代码注释；不用 "load-bearing" 这类反复出现的行话；未经许可不跑破坏性 git 命令（`reset --hard`、`checkout -- .`、`clean -f`、`push --force`）；保留弯引号、破折号等排版字符；不用 "belt-and-suspenders" 这类习语。
2. **CLI（preview）**：扫描你本机 Claude Code 的历史会话记录，找出你反复对 Claude 说的指令，逐条询问要不要写进 `CLAUDE.md`。

它要解决的是「把反馈变成持久上下文」这件事：你说过的纠正不再说第二遍。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

**A. 装规则包（10 秒版）**

前提：已装 Claude Code，且知道自己的 `CLAUDE.md` 在哪（项目根目录，或全局的 `~/.claude/`）。

1. 下载规则包到你想放置的位置：

```bash
curl -fsSL https://raw.githubusercontent.com/globalmpc/nomore/main/rules/CLAUDE.md -o nomore-rules.md
```

2. 在已有的 `CLAUDE.md` 里加一行导入：

```
@nomore-rules.md
```

若想对所有项目生效，把两个文件都放进 `~/.claude/`。

3. 删掉你不认同的规则。作者明确说可以删，重新下载会覆盖该文件（删除只在该次下载到下次覆盖之间有效，若要长期保留自定义版本，建议改文件名后导入）。

4. 每条规则都附了来源 issue 链接，逐条点开可核对是否适用于你的项目。例如第 3 条破坏性 git 命令是通用安全约束，第 4 条排版字符替换只对文案类工作有意义。

**B. 跑 CLI 找你自己重复说的话**

前提：Node 20+；本机能读到 Claude Code 的会话记录（工具会遵循 `CLAUDE_CONFIG_DIR` 环境变量）。README 声称全部本地运行、不外发数据。

5. 先只看不改，观察 30 天内活跃会话里的重复指令：

```bash
npx nomore
```

6. 逐条确认（yes / no / edit）后才写入 `CLAUDE.md`：

```bash
npx nomore --apply
```

7. 只针对单个项目，并把建议写进该项目的 `CLAUDE.md`：

```bash
npx nomore --project .
```

8. 需要对外分享或记录时，只要汇总数字：

```bash
npx nomore --card
```

**C.（可选）复现规则包的挖掘过程**

前提：仓库已克隆，装有 pnpm。

9. 按 README：


## 怎么试、怎么验证（最小试用方式和判断有没有改善的指标）

**最小试用（约一周，单项目）**

1. 选一个你日常最常用的项目，先记录**基线**：连续 3~5 个会话，每次手动记下「我又纠正了 Claude 什么」，只记条数和原话。
2. 装规则包（步骤 1–3），逐条过一遍，删掉与项目规范冲突的，保留 10 条以内。
3. 在同一项目跑 `npx nomore --project .`，只读不改，观察建议质量；再跑 `--apply`，逐条 yes/no/edit，只接受你觉得「这确实是偏好而不是任务」的条目。
4. 之后一周正常干活，继续按同样方式记录纠正条数。
5. 周末用 `npx nomore --card` 记录总量趋势。

**判断有没有改善的指标**

- 主指标：**同类纠正的重复次数**。把纠正的话归类（注释密度、git 危险操作、措辞风格、格式字符…），看同一类问题在试用周是否从「多次」降到「0~1 次」。这比总条数更有意义。
- 次指标：采纳规则数与被删规则数之比。如果采纳率很低（大量建议是 "commit"、"continue" 这类任务词），说明该工具对你这套工作流价值有限。
- 反指标：规则膨胀。`CLAUDE.md` 过长会稀释注意力，若试用后规则数超过你能记住的规模（经验上十几条以内），应合并或删减而不是继续加。
- 停止条件：如果两周内没有任何一类纠正因规则而消失，或 `--apply` 的建议几乎全是任务词，就只用规则包、弃用 CLI。

**注意**：一周的样本量很小，结论只应作为「是否值得继续用」的判断，不宜当作效果显著的证据。
