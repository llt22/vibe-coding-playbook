## 是什么

webframe 是 Jeff Lindsay 的一个小项目，主张“把网页当程序跑”：给它一个 URL 或本地文件，它会在隐藏的无头 web view 中执行该页面，把 `console.log()` 的输出送到标准输出，把异常送到标准错误。

实现上它是 Go 写的，基于 glaze 库，而 glaze 直接调用系统自带浏览器（macOS 的 WKWebView、Linux 的 WebKitGTK、Windows 的 WebView2），因此不打包自己的浏览器引擎，也不依赖 Playwright——原文明确把它类比为作者自己的 `shot-scraper javascript` 工具的“更小包装”。

本文是一次评测的记录：作者让 Claude Opus 5.5 跑通并试用 webframe、搭几个探索性原型，然后从“沙箱工具”和“按 shot-scraper JavaScript 模式抓网页的工具”两个角度评估。结论是：快、轻，适合抓取，性能与 shot-scraper 相当；但有若干明显问题——CSP 导致的失败、0×0 视口、加载挂起、拿不到 HTTP 元数据、浏览器控制能力有限。

## 怎么试、怎么验证

最小试用（不改动现有流程）：

1. 选 3–5 个真实目标页面，其中至少 1 个 CSP 严格、1 个加载慢。
2. 同一批页面分别用 webframe 和现有抓取方案（如 shot-scraper 或 Playwright 脚本）各跑一遍，页面内统一用 `console.log()` 输出提取结果。
3. 外层统一超时（例如 30 秒），超时即判失败。

判断是否改善的指标：

- 成功率：能取出目标数据的页面占比，不得低于现有方案。
- 挂起率：超时或需要人工中断的次数，直接决定它能否无人值守跑。
- 元数据可用性：是否能拿到状态码/响应头；拿不到时下游逻辑是否会误判。
- 视口相关功能：依赖布局、可见性或截图的提取是否失效（对应 0×0 视口问题）。
- 部署成本：依赖体积、是否需要 Playwright/独立浏览器引擎，这是原文主张它更轻的唯一可验证点。
- 错误可读性：异常是否清晰落到标准错误，够不够让智能体自行纠错。

只有在“成功率不低于现方案、挂起率可接受、不依赖视口和 HTTP 元数据”三条同时成立时，才值得把它推进到小范围试；否则保留为参考实现，继续用成熟工具。
