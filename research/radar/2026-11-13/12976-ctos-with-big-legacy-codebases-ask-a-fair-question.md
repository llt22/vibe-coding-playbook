## 是什么

针对“代码库太大，智能体怎么在上面干活”这一问题，作者给出的答案不是让智能体理解整个系统，而是先把任务缩小到智能体能干完的粒度，再让它跑一次有边界的执行。核心是三件事同时变小：任务粒度（epic → 可验收工单）、执行环境（每张工单一个用完即弃的沙箱）、上下文（不给整个仓库，只给依赖图和与本工单相关的那一小片）。作者明确说这里没有魔法：代码库的规模不再重要，是因为任务规模变小了。最后仍然由人来审 PR。作者还提出一个判断：智能体工作真正的难点在上游，即把工单写成智能体能真正做完的形式，而多数团队的待办列表还没这么写。

## 具体做法

原文只给了三步流程，没有给具体工具、命令或提示词，以下按原文步骤展开，并标出每步的前提（实现手段需自行选型）。

1. **拆解（Decompose）**
   - 前提：有一个 epic 或较大需求，且团队里有人能判断“什么样的验收标准算可核查”。
   - 把 epic 拆成多张工单，每张工单都写上“别人可以核查”的验收标准。
   - 关键判据（原文原话）：**如果一张工单没法被核查，它就不适合交给智能体，由工程师自己做。**
   - 自检问题（原文结尾的反问，可直接当团队评审问题用）：“你的待办列表里，有多少张工单是别人不用问作者就能核查的？”

2. **隔离（Isolate）**
   - 前提：项目环境能被预先配置好并复制（原文只说“项目已经配好的全新沙箱”，未指定技术栈）。
   - 每张工单在各自全新的沙箱里运行，任务结束后沙箱直接丢弃。
   - 目标：十张工单可以并行跑而互不干扰。
   - 前提条件：并行数量受限于你有多少可丢弃的干净环境，以及 PR 的评审吞吐。

3. **检索（Retrieve）**
   - 前提：代码库有一份“什么依赖什么”的映射（原文只说“智能体向代码地图询问依赖关系”，未指定是哪种索引或工具）。
   - 不要把整个仓库塞进上下文。让智能体先查依赖图，再只拉取与本工单相关的那一片。
   - 期望效果（作者表述，非实测）：大仓库退化成少量文件。

4. **收口（原文一句话带过，但是流程的一部分）**
   - 一次有边界的运行结束后，由人评审最终 PR。

以上四步构成一个完整循环：“三次缩小 + 一次有边界的运行 + 最后一个人审 PR”。

## 怎么试、怎么验证

**最小试用方式**

1. 选 1 个 epic，拆成 3–5 张工单，每张写清验收标准；先做一轮“可核查性”评审：让不参与编写的同事只看工单，不看作者解释，判断能否核查。记录不能核查的比例，以及哪些工单需要退回给工程师。
2. 为每张工单准备一个全新且预配置好的沙箱，同一批并行运行，任务结束后销毁；记录环境准备耗时，以及并行时是否出现互相干扰。
3. 让智能体先查依赖关系、只拉取相关文件，记录每次实际读取的文件数与 token 量；与“直接给仓库或大范围检索”的做法做对比。
4. 所有产出走人工审 PR，记录评审意见类型，区分“实现错误”与“工单描述不清”两类。

**判断是否改善的指标**

- 工单可核查率：不用问作者就能被他人核查的工单占比（这是作者本人提出的核心判据）。
- 单工单一次通过率与返工轮次；返工原因中“工单歧义”与“实现错误”的比例——若前者占主导，说明瓶颈在上游拆解，符合作者判断。
- 并行干扰事件数（应为 0）、环境准备时间、单工单成本。
- PR 评审耗时与评审意见密度（每 PR 意见数），用来判断人的评审是否成为新瓶颈。
- 上下文规模：单工单实际读取的文件数与 token 量，对比不建依赖图时的基线。

**决策规则（建议）**：若可核查率高、返工主要来自工单歧义而非实现错误、并行无干扰，则推广并可写入手册；若评审成为瓶颈或上下文切片效果不明显，则降级为 study，仅保留“拆成可核查工单”这一条。
