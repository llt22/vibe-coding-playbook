## 是什么

Omnigraph 是一个用 Rust 写的开源图数据库，核心主张是“像开发者给代码做版本管理那样给数据做版本管理”：

- 每个智能体在自己的分支上写入；
- 合并时 Omnigraph 针对最新的 main 做检查；
- 策略（policy）禁止直接写 main。

智能体通过 MCP 连接该数据库。作者用它解决一个他称为“所有 AI 公司都在解决”的问题：多个智能体写同一份数据时，如何避免一个智能体悄悄撤销另一个智能体的工作。

作者的论点是：行锁只在两个智能体同一瞬间命中同一条记录时有用，而一个智能体任务通常跨多条记录、持续数分钟；分支可以把整段改动隔离到合并为止，每次合并都留下可审查的 diff 和“谁改了什么”的历史。

## 怎么试、怎么验证

原文没有可执行步骤，所以最小试用应以“验证这套并发写入控制思路”为目标，而不是“部署 Omnigraph”：

1. **先做零成本对照**：挑一份多智能体需要共同修改的小型共享数据（例如服务目录表或配置表），用现有手段（git 分支或直接把数据放在 git 仓库里，加一条禁止直推 main 的保护规则）复现原文的两个任务：一个改 A 字段，一个改 B 字段，其中一个刻意与另一个改同一行。观察是否出现静默覆盖。
2. **再决定要不要引入 Omnigraph**：只有当第 1 步暴露出“行锁或文件级锁控制不住跨多条记录的长事务”时，才去仓库确认安装、MCP 与策略配置，做同场景复测。
3. **指标**：
   - 静默覆盖次数（目标为 0，这是原文承诺解决的核心问题）；
   - 真实冲突的检出率，以及误报率（两个智能体改同一行但互不冲突的字段时是否被判冲突）；
   - 从被判冲突到重建并成功合并的完成率与耗时（对应原文 Claude Code 那条路径）；
   - 人工审查一次合并 diff 所需时间，以及 diff 是否足以判断改动对错；
   - 总任务完成时长与智能体重试次数，与“无隔离直写”基线对照。
4. **判定改善**：如果静默覆盖降到 0，并且人工审查时间与总耗时没有明显变差，说明隔离机制值得留下；如果冲突误报频繁、重建成本高，则说明分支粒度或冲突判定粒度需要调整，此时回到原文也得不到答案，需要自行实验。
