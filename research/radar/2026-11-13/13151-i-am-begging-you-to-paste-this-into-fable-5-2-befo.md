## 具体做法

> 注意：原文没有给出任何可执行步骤或提示词。下面是根据推文中一句话的分工描述反推出的**实现骨架**，不是原文内容，需要自行编写提示词。

1. **准备输入 diff（前提：代码用 git 管理，且已拿到拟发布分支的 diff）**
   - 生成待审范围，例如 `git diff main...HEAD` 或 `git diff <last-release-tag>..HEAD`。
   - 把 diff 存成文件，作为“读 diff 角色”的唯一输入，避免把整仓库塞进上下文。

2. **拆出“仓库检索”角色（前提：审查工具能读仓库文件）**
   - 给它 diff + 仓库读权限，任务是补全 diff 之外的上下文：调用点、配置、密钥处理、依赖版本、相关历史修复。
   - 让它输出“与本次改动相关的文件与代码片段清单”，供后续审查者使用。

3. **隔离出 N 个“新鲜上下文”的对抗审查者（原文写 4 个，无依据）**
   - 每个审查者使用独立、无历史对话的上下文，避免被前序推理或作者的自我说明带偏。
   - 给每个审查者一个不同的攻击视角（如：身份认证与授权、输入注入、密钥与日志泄漏、依赖与供应链、并发与状态），避免它们重复输出同一问题。

4. **要求可复现的攻击路径而不是“风险提示”**
   - 输出格式固定为：问题位置（文件:行）+ 触发条件 + 最小复现步骤 + 影响 + 修复建议。
   - 无法给出触发条件的一律降级为“待确认”，防止审查结果变成泛泛而谈。

5. **汇总与去重**
   - 由一个汇总角色合并各审查者输出，按“可利用性 × 影响面”排序，标注哪些是多个审查者共同提到的问题、哪些是单个审查者的发现。
   - 人工只审 TOP 项，避免审查结果无人处理。

6. **把这一步挂到发布流程的触发点上**
   - 在发布前（打 tag、合并到主干、或部署流水线的预发布阶段）触发，而非人工记得才跑。

## 怎么试、怎么验证

**最小试用（半天量级，不接入生产流水线）**

1. 选 1 个小型仓库，最好是历史上有过已知漏洞、安全修复提交可查的仓库。
2. 回放：把“修复前”的 commit 当作待发布 diff，走一遍上述 6 步骨架，自写三段提示词（读 diff / 检索仓库 / 对抗审查 × N）。
3. 同时跑一个基线：单模型、单次提示词完成同样的 diff 审查。
4. 盲评：让不了解来源的人判断两组输出，只对照“已知问题是否被找到”。

**判断有没有改善的指标**

- 已知问题的召回率（回放场景下唯一可靠的指标）
- 误报数 / 每千行 diff
- 与单模型基线的**增量**发现数（而不是绝对发现数，绝对数会被啰嗦输出抬高）
- 端到端耗时与 token 成本
- 输出可用率：能给出可复现触发条件的条目占比

**采用门槛**：只有在已知问题上召回显著高于单模型基线、误报可控、成本可接受时，才值得把它固化为发布前的一个自动步骤；否则维持单模型审查 + 人工重点审查。
