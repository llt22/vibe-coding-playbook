## 是什么
一条 X 上的重度使用经验帖：作者高强度使用 Antigravity（agent 开发环境）搭配 Gemini 系列模型做开发，分享了四类可操作的判断——按任务类型分配模型（Gemini 写、GPT 评审、Claude 管理复杂分支和版本）、Antigravity harness 的三个具体痛点（读文件慢、Turbo 模式下工具调用要走 1–3 秒云端审核且一次复杂任务会触发几十次、回答过长）、自建白名单插件减少审批等待、以及用 swarm Skill 派发廉价子 Agent 做代码探索的绕道方案。作者还提到 Orchestrator 计划模式，但明确表示自己测试不足、暂不给结论。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）
1. **前提**：有 Antigravity 使用权限，并同时能用到 Gemini、GPT、Claude 多个模型（作者使用的是 200 美元档订阅）。没有多模型条件时，后续方案无法完整执行。
2. **按任务类型分配模型**（原文判断，不是配置）：
   - 复杂仓库的分支管理和版本管理、希望模型“主动告诉你当前存在什么问题”的工作交给 Claude；
   - 主力开发用 Gemini 4 Carbon（作者称效果优于 Argon，消耗相近）；
   - 写课程、视频脚本、需要“交流感”和文案的工作交给 Gemini；
   - 方案与代码一律让 GPT 交叉评审。作者理由是 Gemini 系列“比较自信”，方案和代码“经常缺胳膊少腿”却自认为不错。
3. **减少云端审核等待**：装作者自写的非官方插件 agy-fast-io（https://github.com/oil-oil/agy-fast-io），其中整理了“不需要走审核的白名单命令”，并提供提示词让 Antigravity 高效读代码。注意：原文只给了仓库链接，白名单内容与提示词正文未出现在材料里，需要打开仓库后照做；在配好白名单之前，不要用 Turbo 模式跑复杂任务，否则会反复触发 1–3 秒审核。
4. **加速代码探索（绕开原生子 Agent 档位限制）**：Antigravity 原生子 Agent 只支持 inherit / flash_lite / flash / pro 四档，不含 Gemini 4 系列；但内部有一个 swarm Skill，相当于多 Agent 协作系统，可派发任意模型（包括 Antigravity 内的 Claude）的子 Agent。做法是把一条项目规则配进去：需要探索代码时走 swarm + Gemini 4 Hydrogen (Low)。作者把这条规则做进了 oil-dev-skills 套件的 oil-explore（https://github.com/oil-oil/oil-dev-skills）；新项目开新话题时靠这条规则加速代码探索。
5. **Orchestrator（计划模式）**：机制是用能力强的模型先探索代码、写方案，再让较便宜的模型（如 Gemini 4 Hydrogen）按方案执行。作者只简单项目试过、自认测试不够，不下结论——建议只作为待验证项，不要直接进手册。原文同时指出该模式对“单纯读文件、问问题”没有加速，因为读代码全在第一阶段、跑的还是最慢的规划模型。

## 对应的研究问题
1. **能力发现**：作者把两件常人不默认外包的事交给 AI——一是让“另一个厂商的模型”承担方案与代码评审，二是把读代码、探索代码这类前置工作交给廉价快速子 Agent 而不是主力模型。
2. **任务匹配**：给出了明确的按任务类型分配模型的判断：复杂仓库和版本管理对应 Claude，主力开发和文案对应 Gemini，交叉评审对应 GPT，探索对应 Hydrogen (Low)。协作形态是“写—审—执行”三角色加主 Agent/子 Agent 分层；并指出规划阶段慢，所以纯阅读类任务不要走计划模式。
3. **条件供给**：需要多模型订阅与足够额度（作者称 200 美元档在重度开发 + Codex review 下，周额度到最后一两天还得单独做点重活才用得完）、项目级规则文件、命令白名单这类免审批权限、可派发任意模型子 Agent 的 swarm 能力。
4. **主动推进**：只提到 Orchestrator 的“先规划再执行”两阶段流水线，属于阶段式推进；原文没有时间、事件或状态触发的持续运行机制，也没有后台持续跑的做法。
5. **效果验证**：原文没有任何量化指标，只有主观对比（Carbon 比 Argon “任务效果更好”“消耗并没有高多少”）和等待时长的估算（单次审核 1–3 秒、复杂任务几十次、累计几分钟）。验证方式需要自行设计。

## 证据与局限
- **原文给出的数据或案例**：200 美元档套餐的额度使用情况（重度开发 + Codex review，周额度最后一两天仍需额外做点重活才用得完）；单次云端审核约 1–3 秒，复杂任务可能审核几十次，累计浪费好几分钟；原生子 Agent 只有四档且不含 Gemini 4 系列；单文件要读几行、思考、再读几行。
- **仅为作者主张、无验证**：Carbon 优于 Argon 且消耗相近；Claude 更“缜密、让人安心”、审美和开发能力更强；Hydrogen 能一定程度解决读文件慢；GPT 评审“搭配起来效果非常好”。这些都是个人体验，没有基准测试、截图或对照数据。
- **适用条件**：强绑定 Antigravity 这一个 harness 和特定订阅套餐；模型名称与版本按作者叫法（Gemini 4 Argon/Carbon/Hydrogen、Claude Opus 5.5），无法独立核对；两个仓库的实际内容未出现在材料中，白名单与提示词效果取决于仓库是否可访问、是否与当前版本兼容。
- **作者自认的局限**：Orchestrator 模式“测试得还不够多，所以不给大家结论”。

## 怎么试、怎么验证
- **最小试用**：挑一个中等规模仓库，选两个真实任务（一个 bug 修复、一个小功能）。A 组：单模型 Gemini 直接做；B 组：Gemini 写 + GPT 只做一轮评审（只指出问题、不代写代码）+ 探索阶段先用廉价子 Agent 跑一遍。各跑 2–3 次。
- **白名单从小开始**：先把纯只读命令（列目录、读文件、搜索）加入免审白名单，写操作保留人工审批；观察是否出现误放行。
- **指标**：任务总耗时；人工或云端审批的次数与累计等待秒数；评审指出的问题数与被采纳数；返工轮次；每任务额度消耗；一周额度是否够用。
- **判断改善**：审批等待明显下降，且返工轮次不上升，即通过；若 GPT 评审只是增加噪音（采纳率很低、问题重复已知），则降级为“仅思路参考”；Orchestrator 先在玩具项目上对比同一任务的耗时与失败率，再决定是否进入正式流程。
