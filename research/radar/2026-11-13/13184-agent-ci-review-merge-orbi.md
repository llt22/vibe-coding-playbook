## 是什么

Orbi 是一个开源（AGPL-3.0、可自托管）的「软件黑灯工厂」，把 agent 写代码之后那串值守型杂活接过去：守着 CI 变绿、把报错贴回去、等 review、最后点 merge。触发方式是在 GitHub Issue 里写清目标和验收标准并打上 `ai-ready` 标签，之后由 agent 写代码、开 PR，另开一个会话做独立评审，评审和 CI 都过了才合并。作者用它开发它自己。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

> 说明：原文只给出流程骨架和一条命令，未给出安装步骤、标签配置细节和提示词全文。以下步骤按原文描述整理，标「需自行补齐」的地方原文没有。

1. **前提**：一个托管在 GitHub 上的仓库；仓库已有可运行的 CI；准备模型接入方式——作者用过本机跑的开源模型 Qwen 27B 和 DeepSeek，开源版也可接 DeepSeek / GLM / Gemini，用你自己的 key；自托管 Orbi（AGPL-3.0）。安装与配置命令原文未给，需自行补齐。
2. **建 Issue，写清两件事**：目标（要做什么）与验收标准（怎样算做完）。这是整条流水线质量的上限——agent 后续所有判断都以此为据。
3. **打标签触发**：给该 Issue 打上 `ai-ready` 标签，Orbi 即接手。标签即触发器，不需要额外下指令。
4. **（可选）让 agent 帮你起草 Issue**：在仓库里跑
   ```
   orbi draft
   ```
   它会先读仓库，帮你起草 Issue 和验收标准，拿不准的地方会停下来问你。适合目标还没想清楚的场景。
5. **agent 写码并开 PR**：由 Orbi 完成，产出是一个 PR，人不需要盯过程。
6. **独立评审**：另开一个会话做评审，与写码会话隔离。这条是防自审自过的关键，不要省。
7. **双门禁合并**：只有「评审通过」且「CI 通过」两个条件同时满足才合并，任一不过就不合。
8. **发版保留人工**：你定版本号和开发版票，Orbi 跑完发版检查后打 tag、发 Release。作者明确把发版决策留给人。

## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）

- **能力发现**：原文点出了一类常被忽略的可委派工作——不是「写代码」，而是写代码之后的值守链：盯 CI、回贴报错、催 review、执行 merge。另外 `orbi draft` 说明「把模糊需求整理成带验收标准的 Issue」也可以先交给 agent 起草、人来确认。
- **任务匹配**：协作方式上，写码与评审分属两个会话（独立评审），形成对抗式结构；模型上不依赖最贵的模型——作者 9 月 22 日前用本机 Qwen 27B，之后换 DeepSeek，说明这类门禁驱动的流水线对模型档位不敏感，靠流程兜底而非靠模型上限。
- **条件供给**：需要给的信息是 Issue 里的目标与验收标准（最关键的输入）；需要的工具与权限是 GitHub 仓库读写、CI 流水线、标签体系（`ai-ready`）、模型 key、打 tag 与发 Release 的权限；反馈来自 CI 结果与独立评审两条信号。发版权限按原文应当保留在人手上。
- **主动推进**：典型的「状态/事件触发 + 持续完成」——打标签是触发事件，之后 CI 状态与评审结论驱动下一步，直到合并。证据是合并分布在一天 24 个钟点、最多一天合 41 个 PR，说明它是后台持续跑的，不占用人的连续时间。
- **效果验证**：原文的验证口径是过程指标——合并 PR 总数、其中由 Orbi 交付的占比、合并的时间分布、发布版本数；质量控制靠双门禁（CI + 独立评审）。缺结果侧指标（返工、回滚、缺陷、人工耗时），见「证据与局限」。

## 证据与局限

**原文给出的数据**：建仓至今合并 857 个 PR，其中 678 个由 Orbi 交付；合并分布在一天 24 个钟点，单日最多 41 个；累计发布 143 个版本；248 stars、32 forks；许可证 AGPL-3.0，可自托管。

**只是作者主张、未见佐证的**：以上全部为作者自述，无第三方审计，也无 PR 抽样说明；「Orbi 一直在用 Orbi 开发自己」是自举叙事，说明可行性但不说明产出质量。

**关键缺口**：
- 只报 PR 数量与占比，没有质量口径——返工率、评审驳回率、合并后回滚或修复的比例、每个 PR 的人工投入分钟数，一概没有。PR 多不等于改善结果。
- 没有安装配置、标签规则、CI 要求、评审会话的提示词细节，抄的时候这些都要自己补。
- 模型对比只是时间先后（先 Qwen 27B、后 DeepSeek），不是受控对比，不能据此推断模型优劣。
- 作者是项目作者，推文带推广动机。

**适用条件**：仓库必须有靠得住的 CI 和一定测试覆盖（否则「CI 通过」这个门禁形同虚设）；任务要能被写成清晰的目标与验收标准，探索性、需求模糊、跨系统改动大的任务不适合；需接受 AGPL-3.0 的许可证约束；发版仍需人参与。

## 怎么试、怎么验证

**最小试用方式**：
1. 选一个测试覆盖较好、CI 稳定的内部小仓库，不要一上来用在主干产品上。
2. 挑 3–5 个低风险、边界清晰的 Issue（如修小 bug、补测试、改文案逻辑），每个都写全「目标 + 验收标准」。
3. 对其中一个先用 `orbi draft` 起草，对比「自己写」与「agent 起草 + 自己改」的耗时差。
4. 全部打 `ai-ready`，让流水线跑到合并，全程记录人工介入的每一次。
5. 设对照组：同期在同一个仓库人工完成 3–5 个同类 Issue。

**判断有没有改善的指标**：
- 门禁质量：PR 首次 CI 通过率、独立评审的驳回率（驳回率过低说明评审在走过场，是危险信号）。
- 返工成本：每个 PR 需要人工返工的轮次与分钟数。
- 结果质量：合并后两周内的回滚/热修比例，与对照组比较。
- 吞吐与延迟：从 Issue 创建到合并的时长、单位时间内合并数、合并发生的时段是否分散到非工作时间。
- 人的体验：值守等待时间是否真的下降——这是作者提出的原始痛点，必须单独量一次。

若「合并后回滚/热修比例」不高于对照组，且人工返工分钟数明显低于人工直做，才算真的改善；如果只是 PR 数变多而返工与回滚同步上升，应降级为 study。
