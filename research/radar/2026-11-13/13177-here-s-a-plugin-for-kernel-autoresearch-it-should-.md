## 是什么

这是一个面向 GPU kernel 优化的 agent 插件（kernel-autoresearch-plugin），挂在 Claude Code / Codex 这类编码 harness 上使用。它把内核优化组织成一个多 agent 分工、可循环的闭环：先建立参考实现和能防作弊的正确性校验，再估算硬件性能上限（roofline floor），用 nsys / ncu / SASS 剖析当前最优内核，提出改动前先预估收益，实现后实测，最后审计检查漏掉的 bug，循环到预算耗尽或逼近上限。作者称做法大致沿用了其在 Muse Open Kernel Challenge 中的方法。

## 具体做法

原文只给出五个环节的描述，没有命令、配置或提示词。下面是从中提炼出的流程骨架，每步注明前提；具体参数需到仓库自取（本次未获取）。

1. 写参考实现与正确性校验（前提：算子规格明确、有可运行的测试输入）
   - 写一个“显然正确但慢”的参考实现。
   - 写正确性检查，并**证明该检查能拒绝作弊内核**（如：不真正计算、对特定 shape 硬编码结果、越界读写、跳过边界条件）。
2. 估算 roofline 上限（前提：知道 GPU 型号、显存带宽、峰值算力）
   - 实际测量该 GPU，按每个输入 shape 算出理论最快时间下限。
   - 这个 floor 同时充当后续“是否还值得继续优化”的停止判据。
3. 剖析当前最优内核（工具：nsys、ncu、SASS 反汇编，并阅读 CUDA 与 PTX 文档）
   - 目标是定位瓶颈：带宽、延迟、占用率，还是寄存器/共享内存限制。
4. 先估收益再实现（前提：第 3 步已有瓶颈证据）
   - 每个候选改动先写出“预计增益”和理由，再实现并在 GPU 上实测。
   - 实测不达预期即回退，避免无效的编译-测试循环烧掉预算。
5. 审计最优内核中被检查漏掉的 bug（越界、竞态、非确定性、未初始化）并修复。
6. 回到第 3 步循环，直到预算耗尽或性能接近第 2 步算出的 floor。

## 怎么试、怎么验证

最小试用：选一个已有正确实现、当前不够快的算子（优先带宽受限的 elementwise / reduction），在单卡上只跑第 1→4 步一轮，看循环是否收敛，不必先搭全自动 agent 团队。

记录：参考实现耗时、初始 kernel 耗时、估算 floor、每次改动的预估增益 vs 实测增益。

判断指标：
- 与 floor 的距离是否缩小（绝对指标，比“比之前快”更可信）。
- 预估增益与实测增益的偏差是否收敛（偏差小说明“先估后改”真在起作用，而不是事后解释）。
- 红队测试：人为注入一个硬编码结果的作弊内核，看正确性检查是否拦住。
- 审计阶段发现的真实 bug 数。

反面信号：预估增益与实测长期不相关；检查无法区分正确实现与作弊实现；循环在远离 floor 处就耗尽预算。
