## 具体做法

以下步骤中的第 2、3 步有原文依据；第 1、4、5 步是依据原文四条指令补出的操作前提，已在步骤中标注。

1. **准备（前提，原文未明说）**：在本地克隆待审计项目，在项目根目录启动 Claude Code，使其对整个仓库有读权限；能修则修的模式下还需写权限，并要求所有改动落在独立分支上。
2. **按原文列出的风险面逐类排查**（原文摘要，照录）：
   - 暴露的密钥：API key、`.env` 被误推到 GitHub
   - 访问控制失效：用户通过可预测 ID 或缺失所有权校验访问他人数据
   - SQL 注入：不安全查询让攻击者操纵数据库操作
   - 认证薄弱：明文密码、不安全 token 存储、缺少邮箱验证
   - 端点无保护：无速率限制、未校验的 webhook、不受限的文件上传
   - 生产卫生差：暴露堆栈信息、依赖版本过旧且有已知漏洞
3. **给 agent 的四条指令**（原文逐字）：

```
Find each vulnerability and identify its location.
Fix issues it can safely resolve.
Explain anything requiring human decisions.
Summarize remaining risks before deployment.
```

4. **按原文给定优先级处理前五项**（原文：“If you can only prioritize five”）：暴露的密钥、未启用行级安全（row-level security）、可预测 ID 且无所有权校验、SQL 注入、弱密码存储。
5. **人工复核（前提）**：逐条检查 agent 标记为“需要人工决策”的项，并复核它自动改动的代码；在部署前以“剩余风险汇总”作为是否上线的闸门。

## 怎么试、怎么验证

**最小试用方式**

1. 选一个由 AI 生成、尚未上线的小型项目（含登录 + 数据库 + 至少一个上传或 webhook 端点）。
2. 新建分支，在仓库根目录启动 Claude Code，把第 3 步的四条指令 + 第 2 步的六组风险面 + 第 4 步的五项优先级作为输入。
3. 要求产出三份分离的清单：已修复项（含文件与行号）、需人工决策项、未处理/剩余风险项。
4. 人工逐条复核改动，只把通过复核的提交合回主干。
5. 部署前以“剩余风险清单是否清零或已明确接受”作为上线闸门。

**判断有没有改善的指标**

- 五个高优项（密钥泄露、RLS、可预测 ID 无所有权校验、SQL 注入、密码存储）被检出并修复的数量 / 5。
- 误报率与误改率：agent 报告的漏洞中经人工判定为真的比例；agent 自动改动中被回退的比例。
- 人工复核耗时（分钟），对比不用 agent 时人工自查同一项目所需时间。
- 回归验证：修复后应用的登录、鉴权、上传等主流程测试是否全部通过（防止“修漏洞修坏功能”）。
- 对照覆盖度：另用一次独立检查（人工清单走查或依赖漏洞扫描）比对，看 agent 漏掉了哪些项——这是把本条线索升级为可照做流程前最必要的一次验证。
