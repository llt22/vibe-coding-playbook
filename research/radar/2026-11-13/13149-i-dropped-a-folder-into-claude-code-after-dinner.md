## 怎么试、怎么验证

**最小试用（建议两周，分三档上）**

1. 第一档（1–3 天，不接任何外部系统）：一个文件夹 + 2 个部门（如 research、ops）+ 2 个 agent，其中一个只写文件、一个只读不改。先把手册和两份 README 写出来，看结构是否撑得住。
2. 第二档（第 4–7 天，只读 MCP）：挂上 Make，只允许「列出可运行场景」和「读表格」，不允许发送、不允许写外部系统。
3. 第三档（第 8 天起，加发送但强审批）：接入 Gmail 发送，但所有外发内容一律先进入每日汇总的「待我点头」清单，人点过才发。定时触发先设成每天一次。

**判断有没有改善的指标**

- 每日摘要里「需要你点头」的条目数，以及其中真正被你采纳的比例（采纳率长期偏低说明 agent 在做无用功）。
- 人工返工率：草稿需要实质修改的比例。
- 端到端时延：从触发到收到那条汇总消息的时间。
- 越权与误发次数，期望为 0；出现一次即回退到第二档。
- 净收益：每周省下的时间 − 你维护手册与 README 的时间。前两周这项很可能为负，属正常。

**保留或放弃的判断**：若连续一周摘要里多数条目可直接采纳、返工率可接受、且零越权，则加部门、加触发频率；若返工率居高不下或出现一次误发，就缩回「只写不发」的形态，只保留 research/ops 这类低风险职能。
