## 是什么

一条 X 推文，作者 @taqimolavi 称谷歌发布了一份 9 页 PDF，主题是 **Harness Engineering（夹具工程）**。核心主张一句话：

> Agent = Model + Harness

即模型本身不是 Agent，让它变成可靠执行力的是围绕它搭的基础设施。推文把这个基础设施拆成六块：

1. **Guides**：规则和指导方针，把过去的失败经验固化为永久知识。
2. **Sensors**：测试、Linter、验证工具，确保错误输出不流入下一步。
3. **Agentic Loop**：规划—执行—检查—修正的循环，带预算限制和人类介入的可能。
4. **External Memory**：模型外部的记忆，保存决策、项目状态、此前会议的成果。
5. **Permissions**：控制 Agent 对工具的访问，划定其独立性边界。
6. **Observability**：记录和监控所有活动、成本、错误和重试。

推文后半段提出「Graph Engineering」：多个各自带 Harness 的 Agent（研究、分析、编码、验证）协同时，一个 Agent 的失败可以变成信号去修正其他人的表现；并把 Hermes 描述为「Agent 的执行环境」，让工具、技能、记忆、工作流在此汇聚。

4. 连续跑一到两周，保持其他条件不变。

**判断有没有改善的指标（全部来自推文点名的观测对象，可自行量化）：**

- **错误外泄次数**：带缺陷的输出进入下游/交付环节的次数，试用前后各统计一次，目标为下降。
- **重试次数与原因分布**：Observability 记录的重试次数，若重试集中在同一原因，说明该原因应写进 Guides。
- **单任务成本与耗时**：每任务 token 消耗与端到端时长，判断额外校验是否带来不可接受的开销。
- **人工介入次数**：每任务需要人介入的次数，若未下降而成本上升，说明补的两格没打在痛点上。
- **规则沉淀量**：Guides 中新增的、来自真实失败的条目数——若为零，说明失败信号没有被转化，Graph Engineering 那一步没有真正发生。
