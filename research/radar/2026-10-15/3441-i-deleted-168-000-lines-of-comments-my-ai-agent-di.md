# I Deleted 168,000 Lines of Comments. My AI Agent Didn't Notice

## 是什么

OpenStation 的作者 Roberto Aranda 做了一次受控对比实验：把代码库中所有注释删掉（约 16.8 万行），得到一份“无注释”副本，然后让同一个 AI 编码 agent 在“有注释”和“无注释”两份代码库上完成同样的任务，每个分支跑三次，两个任务（一个小任务、一个大任务）。

结论是：对 agent 而言，代码注释既不帮忙也不添乱，写出来的代码质量一样。作者的主张是——留不留注释，按“人读代码时需不需要”来决定，不要按 agent 需不需要来决定。

对调研项目而言，这篇文章更有价值的不是结论，而是它给出的**验证方法论**：怎么判断一个改动到底有没有影响 AI 的产出。文章用数据说明，单次运行的结果足以写出两篇结论相反的博客（同一任务、同一天，去掉注释既可能贵 30%，也可能便宜 31%）。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

以下是原文“How I ran it”部分给出的实验配置与流程，可作为对照实验模板。前提：有一个能编译、能跑 lint/类型检查/测试的真实项目，且有权限改代码、加测试、调用 agent。

1. **准备两个分支。** 主干一份，另一份做删注释的副本。删除范围包含所有注释，只保留工具本身需要的注释（如 lint 指令、插件头文件），这部分约 800 行。

2. **验证两份代码等价。** 前提是项目可编译。作者编译两份代码库，并检查编译产出的代码完全相同——确保唯一变量是注释，而不是别的差异。

3. **选定任务，两条分支用同一提示词。** 作者用两个真实功能：一个小任务（平铺所有打开的窗口），一个大任务（让窗口保持置顶）。要求是“真实功能”，且大小各一。

4. **固定 agent 与设置。** 原文配置：

```
gent: Claude Code with Opus 5.5 at high effort
Same model and settings for every run.
```

5. **检查方式统一。** 每个运行都过项目自带的 lint、类型检查、已有测试；大任务额外加一个 agent 从未见过的隐藏测试，且是 agent 完成后才加上，防止它为了通过测试而写代码。

6. **盲评打分。** 用一个独立的 Claude 会话读每个改动并打分，评分依据是**跑之前就写好**的清单，改动被贴上随机名字，评委不知道哪个来自哪个分支。原文描述的清单要点：

```
- does it work（能不能用）
- does it follow the project's conventions（是否符合项目约定）
- does it have tests（有没有测试）
- 等等
```

7. **每个分支每个任务跑三次，并交替分支跑。** 目的是让时段等外部因素对两个分支的影响均等。

8. **统计时看均值和离散度，不看单次。** 原文大任务三次运行的 token 消耗分别是：有注释 8.21M / 8.79M / 10.17M，无注释 7.01M / 9.70M / 10.64M。

9. **设计一个能暴露“注释本该有用”的暗坑。** 大任务里埋了一个陷阱：置顶状态必须在页面刷新后存活，而保存窗口会话的 PHP 函数会丢掉任何它不认识的 key。漏掉的话功能看着正常，一刷新就废。作者本意是看注释能不能帮 agent 避开它。

## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）

- **效果验证（问题 5，本文主要贡献）**：给出了一个可照做的验证套路——多分支对照、每分支多次运行、盲评、事先写好评分清单、agent 完成后才加隐藏测试、交替运行消除时段偏差。并用大任务三次运行的实测方差证明：单次运行的对比结果不可信（10.64M 对 8.21M 是“贵 30%”，7.01M 对 10.17M 是“便宜 31%”）。
- **条件供给（问题 3，部分相关）**：说明“注释”这类自然语言上下文对 agent 的效果接近于零；作者并指出下一篇将报告删掉 `docs/` 文件夹和 `AGENTS.md` 是**有影响**的——即真正起作用的供给物可能是文档与 agent 指令文件，而不是行内注释。
- **任务匹配（问题 2，弱相关）**：小任务（19 分制）上用无注释版本 token 少约 22%（2.18M → 1.71M，成本 $1.42 → $1.04），作者解释是“要读的东西本来就少了”；大任务上成本无差异（$3.84 vs $3.95）。可据此推测：上下文越大的任务，token 差异越容易被运行方差淹没。
- **能力发现（问题 1）**：无直接依据。
- **主动推进（问题 4）**：无依据。

## 证据与局限

**原文给出的数据：**

小任务（平铺所有打开窗口，满分 19）：

| 分支 | 分数 | Tokens | 成本 |
| --- | --- | --- | --- |
| 有注释 | 18.3 | 2.18M | $1.42 |
| 无注释 | 19.0 | 1.71M | $1.04 |

大任务（窗口保持置顶，满分 23）：

| 分支 | 分数 | Tokens | 成本 |
| --- | --- | --- | --- |
| 有注释 | 21.7 | 9.06M | $3.84 |
| 无注释 | 22.0 | 9.12M | $3.95 |

以上为三次运行的平均值。代码行数（用 `scc` 统计）：整仓库 765,491 → 597,332；插件源码（src/、includes/、apps/ 和 CSS，不含测试、文档、工具）408,527 → 280,421。六次运行（含与不含注释）都发现了那个“刷新后置顶状态丢失”的陷阱。

**只是作者主张、不是数据证明的：**
- “注释对 agent 不帮忙也不添乱”这一结论，作者自己声明“不能证明注释效果为零”。
- “下一篇会报告删掉 docs/ 和 AGENTS.md 有影响”——本文没有给出证据，只能当作线索。

**适用条件与局限：**
- 实验只覆盖一个模型（Claude Code + Opus 5.5 high effort）、两个任务、每分支三次运行。作者明说这“足以排除大效应，不足以排除小效应”。
- 评分由另一个 Claude 会话完成，作者未给出评委与人工评分的一致性数据。
- 小任务上有 22% 的 token 差异，大任务上没有——说明这种量级的差异在不同任务间不稳定。
- 删注释后保留约 800 行工具必需注释，说明“无注释”版本并非零注释。

## 怎么试、怎么验证

**最小试用方式（半天到一天）：**

1. 选一个你团队真实的、能跑测试的代码库，复制一份，做一个你怀疑“对 AI 有/没有影响”的上下文改动（删注释、删文档、改 AGENTS.md、换 prompt 等）。编译两份并确认产出等价。
2. 选两个真实任务，一大一小，两条分支用同一 prompt，同一个 agent、同一套设置。
3. 每分支每任务跑 3 次，交替跑（A-B-B-A 之类的次序），避免时段偏差。
4. 检查：项目自带 lint / 类型检查 / 测试，加一个 agent 完成后才写的隐藏测试（专门覆盖最容易漏的边界，例如“刷新后状态是否存活”这类只在重载时才暴露的问题）。
5. 用一个独立会话、按事先写好的清单盲评（改动贴随机标签），清单至少含：能否工作、是否符合项目约定、是否有测试。

**判断有没有改善的指标：**

- 通过率：lint / 类型检查 / 已有测试 / 隐藏测试，任一失败即为不合格（本文中六次运行全部通过，说明这类任务上该指标区分度低，需要更细的评分）。
- 盲评分数（满分制，看均值与三次的波动）。
- token 消耗与成本——**必须看三次的分布**，不要用单次差值。本文的方差显示单次对比可以得出 ±30% 的相反结论。
- 判据：只有当差异大于同一分支三次运行之间的波动时，才认为该改动“有效果”。

**可直接迁移到本项目的两条结论：**

- 不必为了 AI 而特意写代码注释；注释按人类读者的需要决定去留。
- 测量任何 agent 效果时，运行次数少于三次的对比不要采信。
