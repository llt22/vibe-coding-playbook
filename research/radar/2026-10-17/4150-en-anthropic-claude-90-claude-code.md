3. 测试通过后，另起一个独立会话/上下文的代理，只看 diff 做审查并输出问题清单（不让它看到编码过程的对话，避免继承同一偏见）。
4. 只对「问题清单」这一步做并行实验：同一份 diff 交给 2–3 个并行代理去搜 bug，再用一个验证代理对每条发现判定「真问题 / 误报」，只把判定为真问题的条目提交给人。
5. 记录每个 PR 的人工审查耗时、人工最终采纳的代理发现数、被人工判定为误报的条数。

判断有没有改善的指标（试用前先记录一段时间的基线）：

- 代理发现的真问题数 / 人工审查发现的真问题数；
- 代理发现的假阳性率（误报数 ÷ 总发现数）——用来判断「验证代理」这一步是否真的在起作用；
- 每个 PR 的人工审查耗时与往返轮次；
- 漏到人工之后才被发现的问题数量（用来防止代理审查只是制造了「已经查过」的错觉）。

如果两周内假阳性率没有下降或人工审查耗时没有减少，就应该停掉并行代理那一层，只保留「PR 前跑测试 + 单代理审查」。
