## 是什么

原文是一条推文，描述一份“工程书”把一个原本写给人看的 6 步建站流程，改写成交给 AI Agent 自动执行的版本：用户说一句“想做什么站”，再提供一个 Cloudflare API Token，Agent 就从调研开始，一路做到上线，最终交付：

- 一个能打开的 `https://xxx.pages.dev` 链接
- 源码
- 调研（内容）
- 上线包

本质上它做的是一件事：**把人类 SOP 翻译成 Agent 可执行流程，并把权限（API Token）和交付物（链接/源码/文档）一起标准化**。这个“流程改写 + 权限授予 + 交付物定义”的结构，比它具体建什么站更值得迁移。

## 怎么试、怎么验证

**最小试用方式（不依赖原文缺失的细节，先验证模式本身）：**

1. 自己选一个已有的、写给人看的多步流程（例如“建一个静态文档站”），把它写成显式编号的 SOP，每步标明输入、输出、判定完成的标准。
2. 用**专用 Cloudflare 子账户或最小权限 Token**（仅 Pages 写权限，可随时吊销）替代主账号 Token。这一步是原文没写但必须加的安全前提。
3. 让 Agent 按 SOP 执行一次，人只在开始给需求和结束时验收，中途不插手；全程记录它卡在哪一步、问了什么问题。
4. 重复 3 次同一类站点，观察结果是否稳定。

**判断有没有改善的指标：**

- 人工介入次数：理想是从“每步都要动手”降到“开始 1 次 + 验收 1 次”。如果中途仍要人补 3 次以上，说明 SOP 还没被改写到位。
- 端到端耗时与人工耗时对比。
- 一次通过率（3 次里几次产出可直接打开的链接且源码可用）。
- 返工成本：出错时需要人排查多久。这决定了省下来的时间是不是真的省下来了。
- 安全性检查：Token 权限是否可收敛到最小、是否可一键吊销、误部署能否回滚。

只有当“人工介入次数显著下降 + 一次通过率稳定 + 权限可控”三条同时成立，才建议把这个模式写进手册；否则停留在研读层面。
