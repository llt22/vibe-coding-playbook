## 是什么

“AI SRE”在原文中主要指 AI 增强的值班与事件处理工具，核心价值不是替代 SRE，而是把告警后的调查阶段做得更快：读取告警、仪表盘、日志、可观测性系统、运行手册和近期变更，在 Slack/Teams 的事件频道里汇总线索、提出根因假设并接受工程师指挥。原文访谈了 Rootly、incident.io、ResolveAI 三家厂商，也列举了 OpenAI Sevbot、Monzo Project Chip、Stripe 自建调查代理、Google ProdAgent 等内部实践。作者的判断是：会议舞台上演示的完全自主代理还不是现实，更常见的是 AI 做分诊、压低无意义页面、加速调查；是否让 AI 改代码仍有争议。

## 具体做法

以下编号步骤把原文分散在各节的做法整理成可执行的试点流程；原文没有给出完整配置和评测脚本的地方，已注明需要自行确定。

1. **选一个团队、一类事件，先开只读数据权限。** 前提：团队使用 Slack 或 Teams，且 AI 能读取告警、仪表盘、日志/可观测性数据、版本控制、运行手册和历史事件。原文强调 AI SRE 要有效，需要很广的数据访问；大公司常因信任问题选择自建，而不是把敏感数据交给第三方。

2. **从调查阶段开始，不要从自动修复开始。** 触发条件是告警触发或工程师宣布事件。可以先让代理对告警分桶：

```
needs human attention
can wait for business hours
noise
```

也可以让代理在呼叫人类之前先给出原因假设。前提：团队先确定分页策略，明确哪些告警可以延后、哪些必须叫人。

3. **搭建上下文层：知识图谱 + 记忆 + 工具。** 知识图谱至少覆盖：

```
services
data stores
cloud resources
deployments
runbooks
past incidents
```

记忆层保存过去调查的经验，例如“支付延迟飙升时，根因多半在连接池”“某服务发布后一小时内这个告警通常是噪音”。Rootly 的做法包括“激活”记忆笔记和“隔离”被推翻的记忆笔记，避免把过时信息继续喂给代理。工具层通过 MCP、连接器、插件接入内部系统；原文提到厂商普遍提供 Claude Code/Codex 插件。前提：权限最小化、敏感数据先清洗，并保留审计能力。

4. **按典型调查流程运行代理。** 原文给出的流程是：

```
Trigger -> Orientation -> Fan out -> Verify -> Report -> Steer -> Hand off
```

展开为：告警触发；拉取遥测、日志、近期部署和功能开关做定位；并行启动多个调查代理；用独立验证代理挑战结论；把进展报告到 Slack；工程师在 Slack 中指挥后继续展开调查；最后由工程师或编码代理执行缓解动作。前提：模型工具调用足够可靠；如果不可靠，可先退回脚本化流水线，例如 ResolveAI 早期使用的：

```
classify the alert
gather logs+metrics
extract insights
rank hypotheses
```

5. **采用多代理角色，避免自确认和上下文腐化。** ResolveAI 的最终架构分为：Investigator 追查一个又一个假设；Verifier 结构性独立地挑战调查者结论；Communicator 更新利益相关者。原文提到单代理方案会出现上下文饱和、代理重复请求已有数据、自相矛盾，以及“自己给自己的假设打分，几乎总是确认第一怀疑”。前提：验证者不能和调查者共享同一套会自我强化的上下文。

6. **把 Slack 事件频道作为人机接口。** 代理常驻事件频道，接受工程师指令，例如查看某个系统状态、挖特定日志。更新长度要拿捏：incident.io 的经验是太简略会让工程师不信任，太冗长会烦人。Rootly 让代理默认安静，只在以下情况发言：

```
a question in the channel goes unanswered
a stakeholder joins without context
someone declares mitigated without proof
a risky action is announced with no rollback plan
```

前提：团队约定频道规范，明确代理何时可以主动插话。

7. **修复动作保持在人在回路。** incident.io 把事件上下文交给工程师现有的编码代理；ResolveAI 自己写简单 PR，较大改动交给客户的编码代理；Rootly 的愿景是代理起草 PR、另一个代理判断是否安全合并，但原文明确“目前所有 PR 都在人类批准后产生”。试点阶段应让 AI 起草修复建议或 PR，由人批准，不自动合并。前提：代码库只读或受控访问，并有策略执行和审计轨迹。

8. **准确性验证使用对抗验证、混合模型、评测和回测。** 原文摘要提到用对抗代理验证事件假设、混合使用模型、运行 evals 和 backtesting；但这些细节位于付费截断部分，原文没有给出具体评测集或脚本。速度与成本方面，原文只给方向：模型路由、精简提示词、跟踪缓存命中率。前提：先用历史事件建立自己的回测集，因为原文强调“准确性”高度依赖公司和团队。

9. **用事件响应演练防止技能退化。** 原文提到值班工程师可能因 AI 代劳而失去部分调查技能，建议用 Uptime Labs 一类的事件响应模拟训练值班人员。前提：把演练纳入值班培训，而不是只测代理。

## 对应的研究问题

1. **能力发现：AI 已经能做哪些还没想到交给它的工作。** 原文显示 AI 已能读取告警、仪表盘、运行手册、日志和可观测性数据，在 Slack 中汇总调查进展、回答工程师问题、提出根因假设和缓解建议；还能对告警做分诊、压低噪音页面。OpenAI Sevbot 会收集细节、确定可能缓解措施但从不执行；Stripe 的调查代理有简单调查和深度调查两种运行；Google ProdAgent 能查事件详情、做因果分析、时间序列相关和日志分析，但不生成代码，只建议通过 MCP 暴露的工具。

2. **任务匹配：什么工作适合怎样的模型、工具和协作方式。** 最适合先交给 AI 的是“调查阶段”，不是生产变更决策。协作方式是多代理并行调查、独立验证、Slack/Teams 指挥、通过 MCP/连接器接内部系统；修复阶段更适合把上下文交给现有编码代理，简单 PR 可由 AI 起草，大改动人机协作。原文还提到用模型路由、混合模型、精简提示词和缓存命中率来平衡速度、成本与准确性。

3. **条件供给：需要提供哪些信息、工具、权限和反馈。** 需要只读或受控访问遥测、日志、可观测性系统、版本控制，某些调查甚至可能需要脱敏后的生产数据库只读副本；需要知识图谱、记忆层、运行手册、历史事件和工具连接器；需要 Slack 频道作为人机接口；需要策略执行、审计轨迹和工程师的实时反馈。原文特别强调信任：数据访问越广，越需要高信任度，大公司因此更倾向自建。

4. **主动推进：哪些工作可由时间、事件或状态触发并持续完成。** 告警触发或工程师宣布事件是主触发器；代理可并行展开调查、在 Slack 中持续报告，并在特定状态下主动发言，例如问题无人回答、无上下文的人加入、有人无证据宣布已缓解、有人宣布高风险动作但没有回滚计划。记忆层和知识图谱让代理能利用过去事件的状态。原文没有证明完全自主的持续修复已经成熟。

5. **效果验证：怎样判断确实改善了结果。** 原文提到用对抗验证、混合模型、evals 和 backtesting 提升准确性，但强调 AI SRE 的“准确性”很难衡量且高度 company-specific。可观察的运行指标包括页面总量、非工作时间页面、调查耗时、人工推翻率、变更建议采纳率和单次调查成本；原文给了 Rootly 的页面上升数据、Stripe 平均 3 分钟简单调查和 14 分钟深度调查作为例子。

## 证据与局限

原文给出的证据包括：对 Rootly、incident.io、ResolveAI 三家厂商的访谈；Rootly 的页面数据称页面总量上升、非工作时间页面几乎翻倍；作者称许多公司 PR 频率一年内翻倍甚至更多；ResolveAI 两年内重建三次调查架构，先后遇到上下文腐化、自确认和缺乏记忆的问题；Stripe 简单调查平均 3 分钟、深度调查平均 14 分钟；Google ProdAgent 通过 MCP 暴露工具并带有策略执行和审计轨迹；OpenAI Sevbot 会确定缓解措施但不执行，收到指令后才应用；Monzo 的 Project Chip 有事件模式。

但这些证据有明显局限：作者是 incident.io 的投资人，厂商访谈存在立场；多数能力是厂商自述，没有独立基准；原文明确说完全自主代理还不是现实，Meta 两年前的做法与现在相比变化不大；AI 相关故障正在成为一种新类别，值班工程师可能被更少但更难的事件打到，并存在技能退化风险。文章是付费内容，第 4 节“Making agents accurate”之后被截断，第 5、6 节只有摘要，因此缺少准确性评测、速度成本优化和自主代理时间表的完整细节。适用条件是大中型工程团队、使用 Slack/Teams、能提供广泛遥测和代码访问权限，并愿意承担供应商信任或自建维护成本。

## 怎么试、怎么验证

**最小试用方式：** 选一个服务和一个值班团队，只覆盖一类告警；给 AI 只读访问告警、日志、部署记录、运行手册和历史事件；在 Slack 事件频道部署调查机器人。保持人工批准所有变更。每次告警后让 AI 按“触发→定位→并行调查→独立验证→Slack 报告→工程师指挥→人工接手”的流程运行，目标是在告警后约 5 分钟给出可读的调查摘要，这是原文提到的价值点。用历史事件做回测：回放过去的告警，检查代理是否能提出正确根因假设和有依据的缓解建议；再用独立验证代理挑战结论。

**判断有没有改善的指标：** 告警到首份有效调查摘要的时间；告警到缓解的时间；页面总量和非工作时间页面数量；噪音/可延后告警分类的准确率和人工推翻率；根因假设命中率；变更建议被采纳率和回滚率；单次调查成本与缓存命中率；是否漏掉必须人工处理的高危告警；工程师对更新长度和可信度的主观评分。原文没有给出统一阈值，试点前应先定好基线和停止条件；如果调查更快但人工推翻率或高危漏报上升，就不应继续扩大。
