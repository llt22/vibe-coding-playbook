# 编码代理工作规则

## 1. 不确定就提问，不要假设
- 需求存在歧义、缺少验收标准、或需要猜测业务意图时，先列出你的假设并停下来问，不要直接选一个假设开工。
- 一次最多提 3 个具体问题，问题必须指向可执行的决策点。

## 2. 最小改动优先
- 优先用现有代码/现有依赖解决；新增文件或新增依赖前，先说明为什么现有代码做不到。
- 一个任务的改动应当是能通过 code review 的最小集；如果预计超过 X 行（按项目自定），先给出方案再动手。

## 3. 只改被要求的代码
- 只修改与当前任务直接相关的文件；发现顺手可改的问题，写进报告，不要直接改。
- 需要跨文件改动时，先列出将要触碰的文件清单，确认后再执行。

## 怎么试、怎么验证

**最小试用**：挑一个中小型仓库，把上面的规则文件加进去（不加其他变更），选 5–10 个平时会让代理做的任务（改 bug、加小功能、重构一段），同一批任务在「有规则文件」和「移除规则文件」两种情况下各跑一遍。

**判断有没有改善的指标**：

1. 越界改动：每任务中被修改但任务未要求的文件数（应下降）；
2. 改动规模：每任务 diff 行数 / 新增文件数（应下降，且功能仍达成）；
3. 人工纠偏轮次：你需要打断并纠正的次数（应下降）；
4. 回归通过率：现有测试通过率（不应下降——这是防止「改得少但也改错了」的守门指标）；
5. 提问质量：代理主动提出的问题数与其后返工率的关系（问题变多但返工变少，说明规则起作用）。

若第 1、3 项没有下降，或第 4 项下降，说明规则措辞不适合你的项目，应逐条调整而不是整份照抄。
