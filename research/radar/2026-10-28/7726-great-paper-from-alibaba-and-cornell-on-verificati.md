## 怎么试、怎么验证

**最小试用方式（需先拿到论文细节，否则以下只能作为待定方案）：**

1. 选 10–20 个你手上真实、可自动判定的 coding 任务（有测试或明确验收标准的），固定执行 agent 的模型与 prompt，先跑一遍得到基线。
2. 保持执行侧完全不变，只增加一次独立的 reviewer 调用：把「原始任务描述 + 执行 agent 的最终 diff + 测试运行输出」交给 reviewer，要求它输出「通过/不通过 + 具体问题清单」，不通过则让执行 agent 带着问题清单重做一轮（最多 N 轮，N 固定并记录）。
3. 记录三组数字：任务通过率、总 token 成本、总墙钟时间。

**判断有没有改善的指标：**

- 主指标：任务通过率相对基线的绝对提升（百分点），对照推文的 5.9–9.5 分量级；
- 成本：总 token 成本 / 基线成本，对照 1.13–1.25x；若明显超出，说明 reviewer 的上下文给多了或重试轮次没控住；
- 诊断指标：reviewer 的判错率（把通过的判成不通过、把不通过的判成通过各多少）——这一项推文未提，但对判断「增益是否真的来自 reviewer」至关重要；
- 若提升主要在「重试轮次更多」而非「reviewer 指出了执行 agent 看不到的问题」，则说明这个设计的价值被高估了，应降级处理。
