# @davekiss: Most of the code comments your agent writes should be deleted

## 是什么

一条给编码智能体的**注释准入判据**，转述自 Bun 的 `CLAUDE.md`（推文作者 @davekiss 归因为 @jarredsumner 的测试）：

> 每写完一条代码注释，问自己一句：“这条信息是不是下一个 Claude 需要花多次工具调用才能搞明白的？”

中心主张是：智能体写的注释大部分应当被删掉——因为多数注释是把代码本身已经说清楚的事重述一遍，对后续的模型（或人）不产生增量信息。

注意：原文正文在 `If the answer isn't` 处被截断，后续处置动作（删掉 / 不写）未见。本报告中的完整句式是按语义补全的，使用时请按团队口径改写。

## 具体做法

**前提**：项目里已经有一个会被 agent 自动加载的指令文件（Claude Code 的 `CLAUDE.md`、或通用的 `AGENTS.md`）；且 agent 能对仓库做检索（grep / 读文件 / 跳转定义），否则“多次工具调用”这个判据不成立。

1. 打开仓库根目录的 `CLAUDE.md`（没有就新建）。
2. 加入下面这段规则（方括号处按团队情况改写；后半句为按语义补全，原文截断）：

```markdown
## Comments

After every code comment you write, ask yourself:
"Is this information the next Claude would spend multiple tool calls trying to understand?"
If the answer isn't clearly yes, delete the comment.

Keep comments that explain *why* (non-obvious constraints, workarounds,
external system quirks, surprising tradeoffs). Delete comments that restate *what*
the next line already says.
```

3. 给判据补两个本地化例子，降低 agent 的理解偏差（例子要取自本仓库真实代码）：

```markdown
Bad (delete): `// increment counter` above `counter += 1`
Good (keep): `// Stripe rejects idempotency keys older than 24h, so we rotate daily.`
```

4. 让规则在评审环节闭环：code review 时把“无信息量注释”和“缺关键注释”都当作可提意见项，形成双向反馈，避免只单向删注释。
5. 明确例外白名单并写进同一条规则：公共 API 的 docstring、生成代码的头部声明、许可证头、必须解释“为什么”的决策注释，不走这条删除判据。

## 对应的研究问题

- **能力发现**：把“写注释”从默认行为改成需要过一道准入门槛的行为。这属于 agent 已经能做、但通常没有被明确要求做的自我过滤动作，成本只是指令文件里的一段话。
- **任务匹配**：适用于会读写仓库上下文、且产出会被后续会话继续读的编码 agent。对一次性脚本、跑完即弃的探索性代码意义不大。对“人类读注释比跑工具便宜”的场景（教学代码、给外部用户看的示例）判据会反向失效。
- **条件供给**：需要三项条件——(a) 存在被自动加载的指令文件；(b) agent 具备检索能力，否则“多次工具调用”无从估计；(c) review 环节愿意对注释质量给出反馈。缺任何一项，这条规则只会变成一句摆设。
- **主动推进**：属于常驻型规则，每次写注释时自动触发，不需要人再提醒；是“状态触发”最轻的一种形态（写注释这一动作即是触发器）。原文没有涉及跨会话、定时或事件驱动的更复杂形态。
- **效果验证**：原文没有给出任何指标。可从注释密度和评审追问率两个方向自行构造，见末节。

## 证据与局限

- **证据**：原文只有一条推文正文（采集时保存），互动量为 206 赞、7 转发、6 回复。没有任何数据、案例、前后对比、仓库名或提交记录；出处“Bun 的 CLAUDE.md”也只是转述，材料中未见到原文。
- **只是作者主张**：核心断言“agent 写的大部分注释应当删掉”没有量化支撑。
- **原文截断**：`If the answer isn't` 之后的处置动作缺失，补全内容属于推断，不是原文。
- **判据的隐含假设**：“下一个 Claude”是主要读者。若主要读者是人，成本结构不同（人读一行注释远便宜于自己 grep 三分钟），严格照此删除可能过度。
- **适用条件**：多人 / 多 agent 长期维护、会话之间需要靠仓库自身传递上下文的代码库；不适用于教学代码、对外 API 文档、以及必须记录“为什么”的合规性注释。

## 怎么试、怎么验证

**最小试用**：选 1 个中等规模仓库，在 `CLAUDE.md` 里只加这一条规则，跑 1 周或 5 个 PR，不叠加其他提示词改动，避免混淆变量。保留试用前的同等长度基线（前 5 个 PR）。

**判断改善的指标（前后对比）**：

1. 注释密度：每个 PR 新增注释行数 / 新增代码行数。目标是下降。
2. 无效注释评论数：review 中“这条注释没用 / 纯复述”类评论的条数。目标是下降。
3. 反向指标（防止删过头）：review 中“这里为什么这么写？”类追问数、以及因看不懂而导致的返工次数。目标是**不上升**。
4. 关键注释留存：抽 10 个 PR 人工判断，涉及外部约束、workaround、非显然取舍的注释是否仍被保留。目标是不漏。

**判定规则**：指标 1、2 下降，且指标 3 持平或下降，则保留规则并写入团队规范；若指标 3 明显上升，则不是废弃规则，而是补第 5 步的例外白名单与示例后重测一轮。
