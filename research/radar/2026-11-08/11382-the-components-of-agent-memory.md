## 是什么
Anthropic 把「智能体记忆」定义为 Claude 从经验（用户交互、任务）中获得、跨会话保留并可读取的上下文知识；不包括改权重、单次会话内学习、压缩摘要。文章提出记忆的几个组件：会话内写 memory notes；离线 dreaming 回看日志/transcript 来纠错、生成笔记、构建表示、把笔记提升到记忆层级顶部；用 wiki 等表示组织大量知识；用小型注入层（如 MEMORY.md 前 200 行/25KB）做索引，其余按需搜索。

## 具体做法
原文没有给出可直接复制的命令、配置或逐字提示词；以下步骤按原文描述整理，落地时需按所用 agent 框架改写。前提是运行环境支持跨会话持久目录、日志/transcript 保留、文件搜索和可选的上下文注入。

1. **建立跨会话记忆目录**。让每个新会话可以读取一个持久文件夹；会话开始时可以是 fresh session，但能检索该目录中的文件。原文在 CL-Bench 中仅告诉 Claude「有记忆文件夹可用」，强模型即可有效使用。
2. **让模型在会话中按显著性写笔记，而非预设过细规则**。对强模型，给「何时值得记」的判断空间；固定规则（如只记录失败）可能削弱记忆带来的提升。原文建议对前沿 Claude 只给简单指导：当人要求或明显值得记住时创建记忆笔记，判断交给模型。
3. **对旧模型增加「读记忆、检验假设」的引导**。原文发现 Sonnet 4.6 常不读记忆目录、也不检验错误理论；提示它回答前先读记忆文件、显式检验理论后，基准分数接近翻倍。新模型（Sonnet 5）多数会自行读取。
4. **把错误转化为学习循环**。任务有正确答案/评分反馈时，让 agent 记录失败、提出错误原因的理论、测试理论、把验证过的规则写回记忆；成功答案也标记为 confirmed，错误答案写 correction。CL-Bench 中强模型最终把规则、规则依据、旧题答案和陷阱警告 consolidated 到记忆。
5. **定期运行 dreaming（离线反思）**。保留原始 session transcript/log，在交互空闲或会话之间让 Claude 对照 transcript 检查记忆笔记，修正错误、生成新笔记/表示、把重要笔记提升到顶层。前提是有额外 compute，且原始日志可读。
6. **为大语料构建 wiki 作为记忆表示**。让 Claude 增量创建/修改带链接的 wiki 页面，合并重复、对照来源检查主张；多 agent 时用共享日志协调，每个 session 基于前序进度继续。原文用约 350,000 个文件、约 420M token 的内部文档语料，经 128 个 session 构建 wiki。注意 wiki 可能变得比原文还大，需修剪。
7. **把 wiki 与搜索工具结合**。原文中搜索+wiki 在多文档综合题上优于单独搜索；wiki 单独使用也有帮助，但最佳组合是搜索负责定位、wiki 负责结构化知识。
8. **控制注入层大小**。每会话预加载的记忆要少；可只加载 MEMORY.md 的前 200 行或 25KB 作为索引，显示「知道什么、去哪里找」，其余按需读取/搜索。原文提醒注入错误笔记会污染每个会话，且更长的指令文件会降低遵循度。
9. **按任务目标定制记忆生长指令**。合同任务中，最初多 agent 同时写共享合同条款表，导致 57 条中仅 41 条保留；改为每份合同一个页面、单 agent 写、逐字引用条款后，57/57 条保留，基于 wiki 的 brief 评分从 72% 升到 100%。说明记忆结构应围绕任务最关键事实设计。
10. **用第二次 dreaming 补链接和缺口**。原文示例中第二次 dreaming 找到 9 个指向缺失页面的链接并改指到已有页面，还新增 3 个页面（含索引）。

## 对应的研究问题
- **能力发现**：AI 可自己判断显著性、写记忆笔记、在反馈中形成规则、离线回看日志纠错、增量构建 wiki 并用链接组织知识；原文用 CL-Bench、Pokémon、文档语料展示这些能力。
- **任务匹配**：适合长程、状态持续、有可验证反馈的任务（数据库问答、游戏推进、多文档问答/法律 brief）；不适合每轮都能从屏幕直接读到状态的任务（存了也冗余），也不适合只需单文档文本检索的任务（wiki 无明显增益）。强模型适合给判断空间；弱模型需要更明确的读记忆/检验理论提示。多文档综合适合搜索+wiki；单文档检索用搜索即可。
- **条件供给**：需要持久记忆目录、会话日志/transcript、文件搜索、评分反馈、dreaming 的额外 compute、多 agent 共享日志、上下文注入机制；指令上要说明记忆的用途而非规定过细的使用规则；注入层要小。
- **主动推进**：dreaming 可由空闲时间/会话之间触发，自动回看日志并整理记忆；会话开始可自动预加载顶层记忆；多 session 可用共享日志接力。原文也把「何时创建记忆」「dreaming 频率」列为开放问题。
- **效果验证**：原文用有无记忆的对照、不同模型对比、wiki 随 dreaming session 增长的曲线、搜索 vs wiki vs 搜索+wiki、合同事实保留数和 brief 评分来验证；指标包括 graded criteria、徽章/进度、事实保留率、token 消耗。

## 与已有做法的关系
清单中相关条目是 **Claude Code**（工具，状态 adopt）。原文明确提到 Claude Code 的 auto memory：不把全部自动记忆载入每个会话，只加载 MEMORY.md 的前 200 行或 25KB 作为索引；并提醒更长的指令文件会降低遵循度。本文可视为对 Claude Code 这类持久记忆机制的补充设计素材：用小型注入索引 + 按需搜索/读取，配合 memory notes 和 dreaming 做离线整理。清单中没有其他相关条目。

## 证据与局限
- 数据/案例：CL-Bench 数据库任务；Pokémon Red 中 Sonnet 3.7 写 413 个文件/225 个文件夹、得 1 枚徽章，Fable 5 写 9 个文件/2 个文件夹+global.md、得 4 枚徽章；Opus 5.5 用小型笔记通关。文档语料约 350,000 文件/420M token，25 题，dreaming 从 2 到 128 sessions 使 graded criteria 从 13% 到 48%；搜索+wiki 从 54% 到 61%，搜索单独 53%，仅 wiki 最佳 48%，每问约省 20,000 tokens；Harvey LAB 多文档题 87% vs 73%；合同任务 41/57→57/57，brief 72%→100%。
- 作者主张：dreaming 有用；强模型给判断空间比固定规则好；注入层必须小；wiki 需要维护否则会膨胀/产生错误。
- 局限：多为 Anthropic 自家 Claude 模型与 Managed Agents 环境；部分对比是单次运行或特定任务，不能直接外推；原文没有给出可直接复制的命令/配置/完整提示词，只指向 cookbooks；dreaming 需要额外 compute，频率和「何时创建记忆」仍未解决；wiki 在单文档检索任务无增益，且可能大于源文档；长指令降低遵循度。适用条件：跨会话、长程、有反馈和可检索日志的任务；简单单会话或状态每轮可见的任务收益有限。

## 怎么试、怎么验证
最小试用：选一个跨会话、有标准答案/可评分的长程任务（如多文档问答或重复数据库查询），保留原始 transcript，挂载一个持久记忆目录。先跑无记忆基线；再只开 memory notes；再加一次 dreaming 校正；最后加 wiki+搜索。每一步用同一组任务和同一评分标准对比。
验证指标：
- 任务得分/满足评分标准比例（对应原文 graded criteria）；
- 重复错误率、错误笔记被后续会话读取的次数；
- 记忆文件数、注入层大小（若采用 Claude Code 式注入，是否控制在约 200 行/25KB 量级）、每问 token 消耗；
- 需要人工纠错的次数、完成时间；
- wiki 是否比源文档还大、是否出现失效链接。
判断改善：同一任务集上得分高于基线，且 token/时间不显著恶化；或达到同等得分但 token 明显下降；错误规则能被 dreaming 修正而不是被反复继承。若 wiki 在单文档检索任务没有增益，应保留搜索而不强行建 wiki。
