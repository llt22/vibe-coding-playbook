## 是什么

TypeSafe AI 发布 Jev，被其称为“System One models”（Simon Willison 更认同 Maggie Appleton 的叫法“decision models”）。它仍是文本输入，但输出不是文本，而是浮点数：对应类别、是/否问题的置信度、评分，以及相应的置信度分数。TypeSafe 自己的描述是“frontier-intelligence function call: unstructured state in, typed probabilistic decisions out”。

特点是快和便宜：只按输入计费、输出免费，首个模型输入价 $0.042/百万 token，比文中提到的 OpenAI GPT-5 Nano（$0.05/百万）更低。

## 具体做法

前提：原文没有给出注册、鉴权、API endpoint 等细节，只有使用形态和一条 CLI 示例。以下步骤中，API 侧只写到原文明确的程度。

1. 构造一个 state 对象，作为唯一输入。可以是：一个字符串、一个字符串数组、或一组 name-value 键值对。它描述的对象可以是文章、客户或任何记录。
2. 选择问题类型（原文给了三种）：
   - 是/否问题（Jev 称为“Noul”，CEO 在 Hacker News 确认是 Bernoulli 的缩写）：给一个陈述，返回 0–1 的浮点数表示模型认为该陈述为真的置信度。
   - 选择问题（Choice）：从给定选项里选一个，实际返回置信度分数加上在所有选项上的概率分布。
   - 评分问题（Score）：提供一串带描述的数值等级，返回落在该区间内的浮点分数。
3. 一次提交多个问题。同一个 state 可以带尽可能多、塞得进上下文窗口的问题；问题并行求值，发很多问题和只发一个耗时相近。
4. 用 LLM CLI 直接跑（需要先装好 LLM CLI 和 llm-typesafe 插件，原文只给了基本用法，其他查询类型的例子在插件 README 里）：

```bash
llm -m jev 'Please refund my last payment.' \
  -s 'Does this message explicitly request a refund?' 
```

5. 做检索重排时：先用便宜的算法（如 BM25）取出约 100 个可能匹配项，再让 Jev 针对原始 query 给这 100 个候选逐个打相关性分数并重排。
6. 规避已知弱项：据 Jev 1.13 的 jaggedness 文档，它目前在数字、日期和“对抗性内容”上表现不佳，不要把这类判断交给它。
7. 因为输出只有浮点数、无法要求解释，作者建议：评估和结构化实验比常规 LLM 项目更重要；好在成本极低，跑几百甚至几千次实验提示只要几美分。

## 对应的研究问题

- **能力发现**：把原本丢给通用大模型的“判断”拆成专用函数调用，可用于任何能表达为分类的工作，如垃圾邮件判定、建议标签、优先级与排序；作者自己在试检索重排（BM25 取 100 候选 → Jev 打分）。社区还给出非常规用法：jevchat（把 Jev 当聊天模型，每一步只问“给定用户问题和已写回复，下一个符号是什么”）、jev-leftpad（用 choice 问题实现 left-pad，选项从“0 spaces are needed”到“10 spaces are needed”）、jev-2048（用它玩 2048）。
- **任务匹配**：适合能表达成分类任务的工作；不适合数字、日期、对抗性内容；输出只有浮点数，因此不适合需要给出判断依据的任务。
- **条件供给**：需要提供 state（字符串 / 字符串数组 / 键值对）和问题（是/否陈述、选项集合、带描述的数值等级）；上下文窗口内能塞多少问题就塞多少，且并行求值。
- **主动推进**：原文没有涉及时间/事件/状态触发或持续运行的内容，无法据此给出依据。
- **效果验证**：作者明确指出，正因为 Jev 是黑箱，evals 与结构化实验比常规 LLM 项目更关键；而极低的价格让大规模实验成为可行手段。

## 证据与局限

原文给出的具体数据与事实：输入价 $0.042/百万 token、输出免费，并对比 GPT-5 Nano 的 $0.05/百万；三种问题类型及其返回形态；问题并行求值；jaggedness 文档指明数字、日期、对抗性内容三类弱项；Jev 发布不到一周社区就出现多个项目（jevchat、jev-leftpad、jev-2048）以及 open weight 复现和 JevBench。

属于作者主张或非正式观察的部分：检索重排只是“I've been experimenting with it”，没有给任何指标；作者拿湾区各城市问“Good city?”得到 Cupertino 最高、East Palo Alto 最低，是自己也说“Huh”的单次非正式实验，只能作为“存在潜在偏差”的提示，不能当作偏差结论；jevchat 被作者自己形容为“terrible”，社区评论把它比作“Morty 和 death crystal”，属娱乐性质。

适用条件与风险：模型刚发布不到一周，生态非常新；作者强烈提示不要用 Jev 给求职者排序这类高风险场景，因为浮点数会掩盖看不见的偏差，而且事后拆解偏差很困难；数字、日期、对抗性内容当前表现不佳。另外原文没有给出 API 鉴权配置、准确率或任何基准分数。

## 怎么试、怎么验证

最小试用方式：

1. 挑一个你现在用通用 LLM 做的、能表达成是/否或分类的门禁任务（例如“这条消息是否明确要求退款”）。
2. 取 100–200 条你已知正确答案的历史样本，按“字符串 / 字符串数组 / 键值对”构造 state，配上对应问题。
3. 跑 Jev 拿到 0–1 浮点数或概率分布，按阈值转成判断；同一批样本用你现有的方案再跑一遍作对照。
4. 若做检索重排：BM25 取约 100 个候选，让 Jev 对原始 query 打分重排，和原排序对比前 k 条的命中情况。
5. 做偏差对照：把样本里的姓名、性别、地区等标记替换成对照版本，看分数是否出现系统性偏移。
6. 因为便宜，把上面的样本集固定成回归集，改问题措辞时重跑。

判断改善的指标：与人工标签的一致率/准确率、相对当前方案的变化幅度、每千次调用成本、p95 延迟（注意多问题并行、耗时接近单问题）、以及偏差对照样本上的分数差。
