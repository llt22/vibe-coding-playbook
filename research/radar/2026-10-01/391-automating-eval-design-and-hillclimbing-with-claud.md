## 是什么

这是一篇讲「如何自动设计评测、并对着评测做爬坡优化」的实战文章。作者是 Lance Martin，发布在 claude.dev 博客（原文标注日期 2026-09-28）。

核心是 Claude Code 中 claude-api skill 的两个子命令：

- `/claude-api build-eval`：在你的代码库里从零建一套评测（用例 + grader + runner + 结果页）。
- `/claude-api hillclimb`：有了评测之后，让 Claude 一轮改一处、对着评测提升性能或降成本，并用留出集（held-out）抓过拟合。

文章结构是：先讲评测设计的四条原则与 hillclimbing 的三条选择标准、三条反过拟合对策，再讲这两个命令怎么把这些原则变成受人工确认约束的工作流，最后给两个带数字的内部案例。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

### A. 建评测：`/claude-api build-eval`

前提：在 Claude Code 中已装好 claude-api skill；准备好能访问的生产数据或示例（文章说你可以「通过提供示例（如 traces）来引导它」）。

1. 在 Claude Code 里运行：

   ```
   /claude-api build-eval
   ```

2. 接受 Claude 的访谈。它会问你生产数据的保留策略与敏感数据问题，然后按以下顺序采样输入：
   - 生产转录（production transcripts）；
   - bug 报告与支持工单；
   - 你手写的 5–10 个用例；
   - 从你的代码库合成的用例。

   前提：没有生产转录时，它会以你给的少量真实样本为锚点生成合成数据。

3. 人工确认输入。skill 会生成一个简单页面列出每一个输入并等你确认后才继续。确认时对照原则：用例分布要反映你真正关心的生产任务，而不是「好生成」或「好判分」的任务。

4. 让 Claude 提出「够用的最便宜 grader」。原文给的选型规则：
   - 输出空间受约束（精确匹配、固定标签集、符合 schema 的 JSON、能通过的测试）→ 用代码化的程序化验证；
   - 输出开放、有效答案多但有明确质量标准 → 用 LLM-as-judge；rubric 要写成**可核查的断言**，不要用 1–5 分制；如果有 baseline，judge 应随机顺序同时读两份输入、不告诉它哪份是 baseline，然后选更好的那份；judge 模型由你选，且**不能是被测的那个模型**。

5. 抽样读打分记录后再相信评测器。Claude 会先给少量用例打分并问你有没有哪条判分与你不同；作者强调「在相信评测器之前先读一部分已打分的 transcript」，判分错误是评测配错最常见的原因之一。

6. 确认 grader 后跑 baseline。skill 会告诉你评测规模（用例数 × 重复次数 × 模型，以及大致耗时），跑完打印得分和**置信区间**。产出物：用例、grader、runner、每用例一行 JSON、每用例完整 transcript、一个列出每个用例得分并链到 transcript 的普通页面。想要图或别的视图，直接让它加一个页面，默认是本地打开的静态文件、不联网加载任何东西。

7. 看诊断检查结果（skill 在 baseline 阶段自动做）：
   - Grader：同一份输出跑两次 grader，报告判定是否变化；
   - Plumbing：检查超时、API 错误、被截断的回答，避免基础设施噪声被当成模型方差；
   - Headroom：baseline 已经 ≥95% 时会告警，并提示 hillclimb 应转向探索成本或延迟，而不是质量。

### B. 爬坡：`/claude-api hillclimb`

前提：已有一套可用的评测（通常是上一步的产物）。

8. 运行：

   ```
   /claude-api hillclimb
   ```

9. 指定允许它改动的面。原文给的可选范围：
   - system prompt
   - skills 或 instruction 文件
   - tool 描述
   - 模型选择、effort level 及其他 API 参数
   - harness 代码

10. 说明优化目标，例如「提升性能」或「性能持平下降低成本」。之后 Claude 会把评测集随机拆成 train / test。若目标是成本，它会先看几个常见成本驱动项：prompt caching、审计 prompt 与所选模型的兼容性、模型与 effort 设置的选择。

11. 第一轮之前先核对噪声。Claude 检查「评测噪声（仅凭运气得分能移动的幅度）」是否小于「你愿意据以行动的最小改进」；如果不够小，它会直接说明并建议增加重复次数或用例数。

12. 每轮的机制（这是可以照抄的判断规则）：Claude 读上一轮 train 的 transcript，提出**一个** patch；改动要解决失败行为的根因（重写造成问题的那一节或补一条缺失规则），而不是改词句。跑完评测后：
    - train 升、test 平 → 怀疑过拟合，回滚该 patch；
    - 出现回退 → 回滚；
    - train 和 test 都升 → 保留。

13. 连续 2–3 轮分数停滞时（或一开始就发现没有任何单个改动能超过噪声时），Claude 不再编辑，而是读每一条剩余 train 失败并按原因归类。这一步能抓出模糊用例、harness 错误和 run-to-run 方差。只有**合法失败**才进入后续爬坡轮次。

14. 结束时它把代码停在「在你的目标下 test 集表现最好」的版本，并报告相对 baseline 的带置信区间的 test 结果；如果增益落在噪声内，它会明说并建议不要合并。

### C. 评测设计的自查清单（在 A 步骤里逐条对照）

- 任务镜像生产：用例来自你真正关心的场景分布。
- 更强模型/更高 effort 应该更好：如果没有，通常是任务模糊或 grader 失准。
- 前沿模型要留有「可通过」的余量：最强模型 + 最高 effort 应明显低于 100%，否则无法判断改动的影响；但缺口不能由「不可能或模糊的任务」造成——一个好任务是两位领域专家会得出同一结论、且 grader 检查的每一项都在任务里写明。
- 低 run-to-run 方差：方差常来自模糊任务或对同一输出给出不同结论的 grader；也可能藏在配置里（比如 effort 没有一致地应用）和环境中（上一轮的残留状态，如文件、git 历史，会把答案递给 agent）。
- 对抗采样要小心：不要因为「今天的模型在这些用例上失败」而选它们，那是在采样单个模型能力面的低谷、测它的失败指纹；要按**人类判断难**来选，并能说出它难在哪。来自生产流量、bug 报告、工单的具体失败可以纳入，但不要盲信用户流量——用户常常只试他们预期能成的东西，纯流量分布可能偏简单。

### D. 反过拟合三件事

- 拆用例：hillclimber 可读 train，test 永不打开；train 升而 test 平就是常见过拟合信号。
- 绝不把失败内容粘进 prompt：即使 hillclimber 读了失败 transcript，也不许把失败内容粘进 prompt。
- 把答案在结构上放到模型够不到的地方：模型有时会「reward hack」，直接找出评测答案。

### E. 选择爬坡对象的三条标准

- 廉价迭代：时间、成本、精力上改起来都便宜。文中提内部和客户多数把爬坡集中在文本（prompt、skill）上，因为好改好回滚；而对 agent harness 做开放式修改可能牵涉大量代码改动。
- 可归因：评测分数变化要能归因到你在改的那个面。例如把爬坡集中在 skill 触发上时，指标（触发率）直接耦合于被修改的 skill description。
- 目标界定清楚：不要给「提升性能」这种开放式请求；接近饱和的评测、或界定不清的面（比如笼统的「更新 harness」）更容易卡住。作者认为一个普遍好用的目标是成本：即使评测饱和，也可以要求「在性能持平下找降成本的办法」。

## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）

**1. 能力发现：AI 已经能做哪些还没想到交给它的工作**

- 把「设计评测」本身交给 AI：访谈式地采样输入（生产转录、工单、手写样例、从代码库合成）、提出最便宜的 grader、生成人工确认用的输入页面和结果页面（甚至可以追加图表页）。
- 把「对着评测做迭代改进」交给 AI：每轮自己读失败 transcript、提 patch、跑评测、按 train/test 结果决定保留还是回滚；停滞时自己把剩余失败按根因分类。案例中它自己发现了 skill 缺失 8 个功能的覆盖、C#/Java 类型表有错、以及「内容在但模型写旧 API 形态」这类根因，并加了一张「记住的形态 → 当前形态」对照表。
- 把「检查评测本身有没有坏」交给 AI：同一输出跑两次 grader 比对判定、检查超时/API 错误/截断、检测 headroom 是否耗尽、以及（案例中）发现任务措辞与 grader 要求不一致、grader 说明与文档矛盾并实测 API 判定文档为对。

**2. 任务匹配：什么工作适合怎样的模型、工具和协作方式**

- 适合交给自动爬坡的面：廉价可迭代、可归因、目标界定清楚的面——prompt、skill/instruction 文件、tool 描述、模型与 effort/API 参数；文本类最优，开放式的 harness 改动容易卡住。
- grader 与任务的匹配：输出受约束 → 程序化验证；输出开放 → LLM-as-judge（rubric 写成可核查断言，不用 1–5 分；有 baseline 时随机顺序盲比；judge 模型 ≠ 被测模型）。
- 评测集规模与重复次数的匹配：由「噪声必须小于你愿意据以行动的最小改进」倒推，不够就加重复或用例。

**3. 条件供给：需要提供哪些信息、工具、权限和反馈**

- 数据与权限：生产转录（要先谈保留策略和敏感数据）、bug 报告与支持工单、你手写的 5–10 个用例、代码库访问；案例里还给了文档与 SDK 的访问权，使 Claude 能自己发现错误并自我纠正。
- 约束条件：允许改动的面清单、优化目标（性能 or 成本持平）、被测模型与 judge 模型的指定。
- 反馈闭环：人工确认输入、人工抽样阅读打分 transcript 并回答「你有没有哪条会判得不一样」、以及结束后由人决定是否合并（增益在噪声内时不建议合并）。
- 环境要求：避免上一轮残留状态（文件、git 历史）把答案递给 agent；effort 等配置要一致应用。

**4. 主动推进：哪些工作可由时间、事件或状态触发并持续完成**

- 状态触发：分数连续停滞 2–3 轮 → 触发「只分类不编辑」的失败根因反思步骤；如果一开始就没有单个改动能超过噪声，也提前触发该步骤。
- 条件触发：baseline ≥95% → 告警并建议把 hillclimb 目标从质量改为成本或延迟。
- 自动化回滚规则：train 升/test 平（过拟合）或有回退 → 自动回滚 patch；train/test 同升 → 保留。这是可长期无人盯着跑的核心机制。
- 每轮 loop 本身是持续迭代：一次一个 patch，反复到收敛或停滞。

**5. 效果验证：怎样判断确实改善了结果**

这篇文章基本就是围绕这个问题：

- baseline 与最终结果都带**置信区间**；最终结果报的是 test 集（留出集）相对 baseline 的表现。
- 过拟合检测：train/test 拆分，train 升而 test 平即为告警。
- 噪声控制：先确认评测噪声小于最小可行动改进；增益落在噪声内就明说并建议不要合并。
- 评测器质量检查：同一输出跑两次 grader 看判定是否变化；读抽样打分 transcript 人工校验；检查 plumbing（超时、API 错误、截断）。
- 无效信号识别：某任务无论跑多少次都失败、且无法用「不可能或模糊」解释时，是任务或 grader 有问题的信号；案例中通过重写任务措辞和纠正 grader 与文档的矛盾来修复。

## 证据与局限

**原文给出的数据/案例（两个内部案例）：**

- 成本与性能同降（客服 benchmark）：44 张工单，30 张用于搜索、14 张留出。起点 Opus 4.8、default（high）effort，搜索集决策准确率 74.4%，每工单 token 成本 4.6 美分。爬坡先审计 prompt（移除强制 tool-call 仪式、一个 scratchpad 步骤、相互矛盾的规则），再试 Opus 5.5 + low effort，达 87.8%，成本降到 1.9 美分/工单（不到起点一半）。部分节省来自 Opus 5.5 的定价：输入输出 token 比 Opus 4.8 便宜 20%，cache read 便宜 60%。因为达标，继续降一档：Sonnet 5 + low effort 约 88.9%，成本约 1 美分/工单。最后用 routing rules 和「退款上限交叉引用」改 prompt，Sonnet 5 到 98.9%、成本基本不变。在搜索从未见过的 14 张留出工单上，最终配置 90.5% vs 原始设置 78.6%，成本约五分之一。
- 性能提升（对 claude-api skill 自身的评测）：起点 66%。给它文档和 SDK 访问权后，它自己发现 skill 缺 8 个功能的覆盖，补齐到 74%；又发现 C# 和 Java 类型表有错，升到 77%；停滞两轮后做失败根因分类，发现是模型在写旧 API 形态（如固定 token 预算的 extended thinking、旧版 web search / web fetch 工具），于是加了一张「旧形态 → 当前形态」对照表，并把「反对固定预算 thinking」的 C#/Java 警告移到 adaptive-thinking 示例之上，升到 80%；再修一个任务措辞与 grader 要求不一致的问题、以及一个 grader 说明与文档矛盾（实测 API 证明文档对）的问题，加上更多 skill 编辑，到约 88%。

**哪些只是作者主张：**

- 评测设计四要素（镜像生产、更强模型应更好、前沿有可通行的 headroom、低 run-to-run 方差）、对抗采样的风险、爬坡对象三标准（廉价迭代、可归因、目标明确）、反过拟合三对策，都是经验性主张或原则，文中没有给出对照实验来单独验证每一条。
- 「停滞 2–3 轮」「baseline ≥95%」「5–10 个手写用例」这类阈值来自作者实践，未说明是怎么校准的。

**适用条件与局限：**

- 依赖 Claude Code 中 claude-api skill 的可用性；文中命令、skill 名称与模型名（Opus 4.8、Opus 5.5、Sonnet 5）及发布日期（2026-09-28）均为原文所述，实际可用性和当前版本需自行核实。
- 两个案例都来自作者自己的内部基准（客服 benchmark、自家 skill 评测），不能直接外推到你的任务；文中也未给出评测集大小、重复次数、置信区间宽度的具体数值。
- 流程并非全自动：输入必须人工确认，打分必须抽样人工阅读，是否合并由人决定。
- 对「开放式 harness 改动」这类面，作者自己也指出容易卡住，所以本文方法不覆盖这类场景。

## 怎么试、怎么验证

**最小试用方式（半天到两天量级）：**

1. 选一个你已有明确成功标准的任务（例如邮件/工单路由、分类、抽取），准备 20–50 条真实输入，其中故意放入几条你能说清「为什么难」的硬例（不要只挑当前模型失败的例子）。
2. 在 Claude Code 里跑 `/claude-api build-eval`，按访谈回答数据保留与敏感数据问题，让它先用手写 5–10 例 + 从代码库/样本合成的方式建一个小评测集（不接生产转录也能起步）。
3. 人工过一遍输入页面，删掉模糊或超出你关心分布的任务；确认 grader 类型（输出受约束就用程序化验证，省成本也省噪声）。
4. 读 10 条左右打分 transcript，看有没有你自己会判得不一样的；有就改 rubric 或换 grader。
5. 跑 baseline，记下得分、置信区间和耗时。若 baseline ≥95%，直接把目标改成「性能持平下降成本/延迟」。
6. 跑 `/claude-api hillclimb`，第一轮只允许它改 system prompt（最廉价、最好回滚），目标写「性能持平下降低单位任务成本」。
7. 看它每轮保留/回滚的理由是否落在「train 升 test 平」这类信号上；如果它把失败内容粘进 prompt，按原文原则这是不该做的，要拦。

**判断有没有改善的指标：**

- 主指标：test（留出）集得分相对 baseline 的提升量，以及它是否**超出置信区间/噪声**；落在噪声内就不合并。
- 过拟合信号：每轮 train 与 test 的得分差；train 持续升、test 持平即为告警。
- 成本/延迟：每单位任务的 token 成本与端到端耗时（案例里的报告口径是「每工单美分」）。目标是性能不降的前提下这两项下降才算改善。
- 评测本身健康度：同一输出跑两次 grader 判定是否一致；重跑同一配置的 run-to-run 方差是否小于你要检测的最小改进；plumbing 错误（超时、API 错误、截断）是否为零或可忽略。
- 无效用例占比：连续多轮都无改善、且无法归因于内容缺失的用例数——这些应被修成合法用例或剔除，而不是继续在上面花轮次。
