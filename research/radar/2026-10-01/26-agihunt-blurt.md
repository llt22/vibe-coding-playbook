## 是什么

blurt 是一个可安装的 skill（仓库 AGIHunt/blurt），把「录屏 + 对着屏幕口述」作为给编码智能体的输入。它由两部分组成：一个菜单栏录制应用（macOS，Windows 为 Tk+ffmpeg），以及交给 agent 的 SKILL.md 流程。录制后，agent 本地转写语音，把一段杂乱的口述拆成独立条目，为每条挑出对应画面帧并框出鼠标所在地，写成 actual vs. expected、复现步骤、owner 和「可能是哪段代码负责」，最后在评审页逐条取舍，可导出到飞书/Lark、GitHub、Linear 或 Markdown，也可以直接说「fix them」让 agent 去改。

README 的核心主张：语音是瞎的、截图打字是慢的，最自然的方式是「指着屏幕说话」，像对旁边同事讲一样。

## 具体做法（编号步骤；可直接复制的命令、配置、提示词原样放进代码块；写清每步的前提）

1. 安装 skill。前提：已有能跑 skills 的编码 agent（README 明确支持 Claude Code、Codex 及任何运行 skills 的 agent）。

```bash
npx skills add AGIHunt/blurt
```

Claude Code 也可以用：

```
/plugin marketplace add AGIHunt/blurt
```

或者直接把仓库 URL 贴给 agent，让它自己装。

2. 在任意项目中让 agent 启动。触发语（原文）：

```
"start blurt" / 「开始口喷」
```

首次运行会自动为你的机器挑选语音模型，并安装 Blurt 菜单栏应用。

3. 划定录制区域：拖选一个区域、点选某个窗口，或全屏。README 说明 Tabs、书签等界面外内容不会进画面。

4. 倒计时 3-2-1 后开始口述。悬浮小条显示时间与麦克风电平，带 ⏸ 暂停、↺ 重录、Finish。悬浮条本身不会被录进视频。快捷键：`⌥⇧P` 暂停、`⌥⇧S` 完成。

5. 点 Finish 后回到工作，agent 在本地转写、写出条目、打开评审页（评审页就绪后自动弹出）。

6. 像刷信息流一样逐条分诊，全部为键盘操作：

```
A 保留 · X 丢弃 · J/K 上一条/下一条 · Z 撤销 · G 列表 · V 总览
```

然后导出，或对 agent 说「fix them」。

7. 常驻用法（菜单栏应用）：`⌥⇧R` 在任意位置开始录制，再按一次 `⌥⇧R` 结束；`⌥⇧B` 打开菜单。录制默认写到工作区 `~/Blurt`，也可以绑定到某个项目目录，好让 agent「带着代码」处理。

8. 后台自动处理：打开 *After recording → Claude Code / Codex*，此后每次录完都在后台被处理，评审页准备好后弹出。

9. 团队协作（无仓库的人也能参与）：队友从 releases 页下载 Blurt for macOS，解压后第一次右键 → Open，按 `⌥⇧R` 录制；然后用 *Recent recordings → Copy video* 把视频贴到 Slack/飞书里；或者绑定一个共享项目文件夹。条目会保留录制者姓名，导出落到团队已有的表格和列名上。

10. 语音模型与语言（首次运行会挑，也可以自带 key）：
    - 默认本地语音识别 SenseVoice（经 sherpa-onnx），约 240 MB，CPU 上很快，中英混说处理好；
    - Apple Silicon 或 NVIDIA 上可用 Whisper；
    - 也可以自带 Groq、OpenAI 或 DashScope 的 key；
    - 默认情况下没有任何数据离开本机；
    - SenseVoice 覆盖中、英、日、韩、粤语；德法西等 99 种语言用本地 Whisper 或云端 key；输入什么语言，条目就用什么语言输出。
    - 录制器用 macOS 的 ScreenCaptureKit，音视频同步误差在一帧以内；可以打开系统音频，它走单独音轨，因此转写能区分「你」和「对方」的话。

11. 录制对象不限于网页应用：终端、TUI、桌面应用同样录制和框选；手机用自带录屏并把麦克风打开；硬件类用手机拍下来，然后把视频交给 agent 说「process this video」。一次录制可以混合多种类型，由 agent 判断每条是什么。团队还可以加自己的 lens（如 `ux-research`、`sales-call`、`sop`），参考 `skills/blurt/reference/schema.md#custom-lenses`。

## 对应的研究问题（对照上面五个问题逐条说明，只写有依据的）

**1. 能力发现：AI 已经能做哪些还没想到交给它的工作。**
README 给出的、通常不会交给 AI 的几类活：
- 把半小时跳跃、自我纠正的口述拆成互不混淆的独立条目；
- 为每条自动挑出正确的那一帧，并按鼠标实际位置框出准确位置；
- 写成 actual vs. expected、复现步骤、owner，以及「可能是哪段代码负责」；
- 把浏览网页时的零散评价整理成 idea board（每条想法、为什么想到、来自哪里、下一步，外加一页摘要）；
- 竞品走查、UX 调研、「这东西怎么跑起来」这类笔记与发现，并带上可作证据的画面；
- 由不写代码的人（PM、设计、运营、客户）录制后交给开发者的 agent 处理。

**2. 任务匹配：什么工作适合怎样的模型、工具和协作方式。**
- 分工上：录制、语音转文字、抽帧、评审页、导出这些交给确定性脚本；判断全部留给 agent（SKILL.md），因此能适配你的产品、语言和团队。
- 模型上：需要带视觉能力的模型，越强越好（README 明确说质量随模型走）。
- 实测用的是 Claude Code + Opus 5.5 + 一个生产环境 Web 应用。
- 语音部分按语言和硬件选：默认本地 SenseVoice，Apple Silicon/NVIDIA 用 Whisper，或自带云端 key。
- 视频本身从不喂给模型，只喂转写文本和为成条时刻抽取的少量帧，所以成本跟「讲了多少件事」走，不跟录制时长走，静音和乱点不花钱。

**3. 条件供给：需要提供哪些信息、工具、权限和反馈。**
- 关键输入是「屏幕画面 + 同步语音」这一对，而不是纯文字描述。
- 鼠标位置被当作「我指的是这里」的信号，用来框出准确位置。
- 把录制落到项目目录（绑定项目而非默认 `~/Blurt`），agent 才能带着代码处理，给出代码指针。
- 打开系统音频会走单独音轨，转写能区分自己与对方说的话。
- 反馈环节是评审页：A/X 保留丢弃、J/K 翻条、Z 撤销，人在回路里做质量闸门，之后才导出或让 agent 去改。

**4. 主动推进：哪些工作可由时间、事件或状态触发并持续完成。**
- 菜单栏常驻 + 全局快捷键 `⌥⇧R`，任何位置都能起停录制，`⌥⇧B` 打开菜单。
- 打开 *After recording → Claude Code / Codex* 后，录制完成这个事件即触发后台处理，处理完评审页自动弹出，不需要人在中间操作。

**5. 效果验证：怎样判断确实改善了结果。**
README 给了两段真实会话的量：

| 录制 | 语音 | 条目 | 本地转写 | 录制→评审页 | 新增输入/输出 token | 按 API 价格 |
|---|---|---|---|---|---|---|
| 7.0 分钟 | 2.8 分钟 | 9 | 4 秒 | ~4 分钟 | ~142k / ~19k | ~$2 |
| 8.6 分钟 | 5.0 分钟 | 20 | 5 秒 | ~5 分钟 | ~150k / ~20k | ~$2 |

另注明：还要加上当前对话的缓存读取（~4–5M tokens，按输入价的 1/20 计，已含在上表中），具体取决于你聊天窗口已经多长。
README 还声称「过去要两天截图、画红框、填表格的事，现在是 30 分钟走查」——这是主张，没有对应数据。

## 与已有做法的关系

清单中相关条目：**Claude Code**（tool，status: adopt）。
blurt 以 skill 形式接进 Claude Code（也支持 Codex 及任何跑 skills 的 agent），并可以配置成录制完成后自动触发 Claude Code / Codex 处理。它不替代 Claude Code，而是在清单里已有的 agent 之上补一层输入与反馈通道：把「指屏幕 + 说话」变成 agent 能读的结构化条目。评审页的 A/X/J/K 与「fix them」则接在 agent 既有的改代码流程前面。

## 证据与局限

**原文给出的量**：上面那张两段真实会话的表（录制时长、语音时长、条目数、本地转写耗时、录制到评审页的耗时、输入/输出 token、约 $2 成本）；默认本地识别、视频不入模；语音模型体积约 240 MB；音视频同步误差一帧以内；SenseVoice 覆盖 5 种语言、Whisper 覆盖 99 种语言；两段会话使用 Claude Code + Opus 5.5 + 生产 Web 应用。

**只是作者主张、没有对应数据的**：
- 「原来两天、现在 30 分钟」；
- 「能挑对每一帧并框准位置」；
- 「能把跳跃、自我纠正的口述拆干净」；
- 「条目里包含可能是哪段代码负责」的准确率。
这些都需要自己复现才知道是否成立。

**适用条件与限制**：
- 这是仓库 README，属于产品自述，没有第三方评测、没有基准数据；仓库 40 stars，成熟度低；
- 录制端以 macOS 为主，Windows 只有 Tk + ffmpeg，路线图里的 Windows 托盘应用尚未完成；
- 前提是能看到问题、或用手机拍到问题；纯后端/无界面的问题需要另想办法（终端、TUI、桌面应用可以，硬件用手机拍）；
- 质量依赖带视觉的强模型，弱模型产出会明显下降；
- 成本不完全只看录制时长：除条目数外，还取决于当前对话已有多长（缓存读取 ~4–5M tokens）；
- 首次运行要下载约 240 MB 模型，或自备 Groq/OpenAI/DashScope key；
- 路线图里「浏览器捕获（把 console 报错和网络失败对齐到视频）」还没做，目前拿不到浏览器内部错误；
- 团队用法要求无仓库的同事手动下载、解压、首次右键打开。

## 怎么试、怎么验证

**最小试用方式（半天内可完成）**：
1. 选一个有真实小 bug 的 Web 项目，装好 skill：`npx skills add AGIHunt/blurt`，用 `"start blurt"` / 「开始口喷」启动。
2. 把录制工作区绑定到该项目目录，让 agent 能读到代码。
3. 录一段 5–10 分钟的走查：一边点页面一边口述问题，故意在中途跳一次话题、改一次口径，看看拆分是否混乱。
4. 等评审页弹出，全程只用键盘 A/X/J/K 过一遍，记录保留与丢弃各多少。
5. 对保留的条目说「fix them」，看 agent 是否照着复现步骤改对。
6. 第二段换一个不写代码的同事（PM/设计/运营）录，走 *Recent recordings → Copy video* 传给你，验证跨人交接这一环。

**判断有没有改善的指标**：
- 条目保留率：按 A 保留的条数 / 总条数，低于某个阈值说明拆分或描述不可用；
- 可直接照做率：保留的条目里有几条不需要再补上下文就能直接开工；
- 代码定位命中率：README 承诺的「可能负责的代码」指针有几条是对的；
- 端到端时间：从按下录制到评审页可用的实际耗时（对照 README 的 ~4–5 分钟）；
- token 与实际花费：对照 README 的 ~142k/19k、~$2 这一档，看是否随条目数而非录制时长增长；
- 与现状对比：同样这批问题，用原来的「截图 + 画红框 + 打字」方式要多久，两边直接比时长和遗漏数。

只要「条目保留率高 + 端到端时间明显短于原方式」，就值得在团队里固定成一种输入惯例；如果条目需要大量返工或代码定位经常错，先退回 study，把它当作「给 agent 补上下文」这一思路的参考即可。
